## 3. `-0` 대조

### RFC 7493

[RFC 7493 전문](https://www.rfc-editor.org/rfc/rfc7493.txt)에서 다음 검색을 수행했다.

- 대소문자 무시 고정 문자열 `negative zero`: 없음
- 대소문자 무시 고정 문자열 `minus zero`: 없음
- 독립된 숫자 토큰 형태의 정규식 `(?<![0-9A-Za-z])-0(?![0-9])`: 없음

따라서 RFC 7493에는 `-0`, `negative zero`, `minus zero`에 대한 규정이 없다.

### RFC 8259 §6

RFC 8259도 `negative zero`나 `minus zero`라는 이름으로 별도 규칙을 제시하지 않는다. 다만 숫자를 다음과 같이 정의한다.

> “A number is represented in base 10 using decimal digits. It contains an integer component that may be prefixed with an optional minus sign, which may be followed by a fraction part and/or an exponent part.”

```abnf
number = [ minus ] int [ frac ] [ exp ]
int = zero / ( digit1-9 *DIGIT )
minus = %x2D               ; -
zero = %x30                ; 0
```

— [RFC 8259 §6](https://www.rfc-editor.org/rfc/rfc8259.txt)

추론: 선택적 `minus` 뒤에 `int = zero`가 올 수 있으므로, 이 문법은 JSON 숫자 `-0`을 허용한다. 이는 Errata 7920의 “Since -0 is a valid JSON Number”와도 일치한다.

### RFC 8785 본문

JCS 숫자 직렬화 규칙은 다음과 같다.

> “Such data **MUST** be serialized according to Section 7.1.12.1 of [ECMA-262], including the ‘Note 2’ enhancement.”

— [RFC 8785 §3.2.2.3](https://www.rfc-editor.org/rfc/rfc8785.txt)

Appendix B의 직렬화 표는 다음 매핑을 명시한다.

```text
| 0000000000000000 | 0 | Zero       |
| 8000000000000000 | 0 | Minus zero |
```

— [RFC 8785 Appendix B](https://www.rfc-editor.org/rfc/rfc8785.txt)

즉 JCS 본문 기준으로 IEEE 754 minus zero는 canonical JSON에서 `0`으로 직렬화된다.

### RFC 8785 Errata 7920

검증된 정정은 RFC 8785 §5에 다음 문장을 추가하도록 한다.

> “Since -0 is a valid JSON Number but is serialized as 0, a JSON parser following this specification **SHOULD** generate an error condition (which in turn **SHOULD** stop processing) when it encounters -0, in order to thwart potential attacks on not yet parsed data.”

— [RFC Errata 7920, RFC 8785 §5 정정](https://www.rfc-editor.org/errata/eid7920), 상태 `Verified`

정정의 Notes에는 다음 설명이 있다.

> “IEEE 754 includes as distinct values both positive and negative zero. Section 7.1.12.1 of ECMA-262 says: If m is +0 or -0, return the String "0".”

— [RFC Errata 7920, Notes](https://www.rfc-editor.org/errata/eid7920)

따라서 정정된 JCS에서는 입력 `-0`을 발견했을 때 오류를 내고 처리를 중단하는 것이 각각 `SHOULD`다. `MUST`는 아니다.

## 4. 권장안

- **noncharacter는 「I-JSON 게이트」 아래 유지**하는 것이 정확하다. RFC 7493 §2.1이 직접 `MUST NOT`으로 금지한다.
- **`-0`은 「I-JSON 게이트」에서 분리**하는 것이 정확하다. RFC 7493에는 관련 규정이 없고, RFC 8259 문법상 유효한 JSON 숫자다.
- `-0` 검사는 **「JCS 정규화 전 검사」**, **「JCS 입력 안전성 검사」**처럼 JCS에 귀속시키는 편이 좋다. 근거는 RFC 8785 Appendix B의 `-0 → 0` 직렬화와 Verified Errata 7920의 오류 권고다.
- 다만 `-0` 거부 강도는 Errata에서도 `SHOULD`이므로, 문서에 이를 무조건적인 표준상 `MUST`로 표현해서는 안 된다.
- binary64 범위·정밀도 초과도 RFC 7493의 근거는 있지만 `SHOULD NOT`이다. 따라서 구현이 이를 하드 실패로 만든다면 “RFC 7493의 필수 거부”가 아니라 **제품의 엄격 프로파일 정책**임을 밝혀야 한다.
- NaN/Infinity는 **JSON 문법/유효성 검사**로 분류하는 것이 가장 정확하다. I-JSON도 JSON이어야 하므로 결국 거부되지만, RFC 7493 §2.2가 추가한 별도 숫자 제약은 아니다.

## 5. 못 가져온 것 / 열린 질문

- 지정된 네 자료는 모두 가져왔다. Errata URL은 리디렉션 후 HTML 본문을 확인했다.
- RFC 7493이 직접 참조하는 RFC 7159는 이번에 지정된 출처가 아니어서 가져오지 않았다. 따라서 NaN/Infinity의 동시대 참조 사슬을 RFC 7159 원문까지 확인하지는 않았다.
- api-kit이 binary64 초과와 `-0`을 실제로 `MUST` 수준의 하드 오류로 설명하는지는 해당 문서를 받지 않았으므로 판단하지 않았다. 여기서는 여섯 항목의 RFC 근거와 규범 강도만 판정했다.
