## 검토 항목별 판정

**조건마다 FAIL 상태를 한 문장으로 쓸 수 있는가** — 28 줄 모두 쓸 수 있다. 다만 DG-04 의 둘째 · 셋째 값 일부(`shellcheck rc=` · `n_*=`)는 FAIL 상태가
있어도 측정이 그 상태에 닿지 못한다(C1). SK-02 (c) 는 산출물이 아니라 이 맥의 셸 동작을 재는 전제 확인이다 — BUILD 가 무엇을 하든 값이 같으므로
산출물의 증거로 세지 않는다는 점만 알고 두면 된다(고칠 것 아님).

**측정이 의도를 실제로 재는가** — 대부분 잘 짜였다. 블록 조건(SK-01 · SK-03 · SK-05 · ER-04)은 러너와 따로 짠 측정이라 러너가 틀려도 떨어지고,
러너 조건(SK-07 · SK-08)은 변형 여덟과 zsh 대조 둘로 깨진 곳만 잡는지 본다. 문장 조건은 삭제 대조 38/38 이고, 두 판을 풀어 둔 폴더에서 재서
다른 Phase 의 미커밋 변경이 끼지 않게 했다. 구멍은 둘이다.

- DG-04: `printf … "$(basename "$f")" "$?"` 에서 명령 치환이 `$?` 보다 먼저 풀려 `$?` 가 `basename` 의 0 이 된다. 셋째 줄의 `-n` 문법 검사는 값이
  항상 0 이고, 둘째 줄 `shellcheck rc=` 도 항상 0 이다(`lines=` 는 살아 있다). 대조 표에 DG-04 줄이 없어 봉인 전에 드러나지 않았다
- AR-01 셋째 값: `find .harness …` 가 끝 판이 아니라 작업 폴더를 읽는다. 지금 작업 폴더에는 다른 세션이 고친 채 커밋하지 않은
  `.harness/sprint-contract-kaizen-0924-p01…p10` 이 있다(git 상태 `M`). 이 Phase 의 계약 사본이 작업 폴더에서만 바뀌어도 값이 떨어지고, 반대로 끝 판에서 깨진 것을
  작업 폴더가 가릴 수도 있다. `common.sh` 가 두 판을 풀어 두는 이유와 같은 이유로 끝 판을 읽어야 한다. contract-schema 권장 형태는 작업 폴더 기준이지만
  이 계약은 이미 모든 값을 끝 판에서 재므로 그 형태를 끝 판에 적용하면 된다

**처리 배정표 Phase 17 행이 빠짐없이 다뤄졌는가** — 다뤄졌다. `배정` 칸이 `Phase 17` 인 행은 `other-kits:P4` 하나이고(반영), `other-kits:P3` 의
howto-kit 단계는 러너 쪽 반영 + CI(깃허브에 올릴 때 자동으로 도는 검사) 줄 넘김이다(러닝북이 CI 수정을 Final 몫으로 정했다). P3 의 onboarding 시험 입력은
Phase 14 몫이라 빠진 것이 맞다. 적용 힌트 한 줄, 데이터 풀 §0-b · §0.5(howto 항목 없음), 러닝북 추가 과제(Phase 17 줄 없음)도 배경 절에 적혀 있다.
오케스트레이터 Step 17 의 Phase 1 대조는 했지만 한 행의 요약이 가이드와 다르다(C3).

외부 근거 파일 §5 의 열린 질문 둘 가운데 설치 복사본 버전 폴더 문제는 `하지 않기로 한 것` 에 결정이 적혀 있고, 「레포에서 고칠 때 플러그인 경로가 옛

**공유 파일을 건드리려 하지 않는가** — 건드리지 않는다. `plugin.json` 버전 · `ci.yml` · `.claude/skills/howto-kaizen/SKILL.md` · 문서 사이트 페이지는 notes 넘김 표로

**조건끼리 부딪히는가** — 부딪히지 않는다. SK-09 (evals.json 키 · 설명 변경)와 AR-03 (b) (`cases` · `runner` · `kit` 그대로), SK-09 (머리 주석)와 AR-03 (a)

### C1 — DG-04: 종료 코드를 `printf` 전에 받는다

`m.sh` `DG-04)` 갈래 둘째 · 셋째 줄을 이렇게 바꾼다 (`rc` 는 `m` 안에서 이미 `local` 이다).

```bash
    for f in "$RUN" "$GS"; do o=$(shellcheck -s sh "$E/$f" 2>&1); rc=$?; printf '%s shellcheck rc=%s lines=%s ' "$(basename "$f")" "$rc" "$(printf '%s' "$o" | grep -c .)"; done
    for f in /bin/dash /bin/sh bash zsh; do "$f" -n "$E/$RUN" 2>/dev/null; rc=$?; printf 'n_%s=%s ' "$(basename "$f")" "$rc"; done; echo ;;
```

기대값은 그대로다(예행 판에서 고친 명령으로 다시 돌려 둘째 줄 `run-evals.sh shellcheck rc=0 lines=0 howto-gate.sh shellcheck rc=0 lines=0 n_dash=0 n_sh=0 n_bash=0 n_zsh=0` 확인).
양성 · 음성 대조 표에 한 줄 더한다:

```text
DG-04   끝 판 러너 끝에 `echo $1` · `if then` 두 줄 (예행 변형)     → 둘째 줄 run-evals.sh shellcheck rc=1 lines=7 … n_dash=2 n_sh=2 n_bash=2 n_zsh=1
                                                                    (고치기 전 명령은 같은 사본에서 shellcheck rc=0 · n_*=0 — 이 검토 실측)
```

### C2 — AR-01 셋째 값: 끝 판의 `.harness/` 를 읽는다

`m.sh` `AR-01)` 갈래 셋째 값의 앞머리를 이렇게 바꾼다.

```bash
    find "$E/.harness" -type f -name 'sprint-contract*.md' -print0 | while IFS= read -r -d '' f; do verify_seal "$f"; done \
      | awk '$1=="SEAL_BROKEN"{print $2}' | sed "s#^$E/##" | sort -u | comm -12 - <( { my; echo "$CF"; } | sort -u) | grep -c .
```

AR-01 조건 줄의 셋째 설명은 「셋째 — 끝 판(`$END`)을 푼 폴더의 `.harness/` 에서, 슬러그를 열거하지 않고 봉인이 깨진 계약 가운데 이 Phase 가 건드린 것의 수 0
