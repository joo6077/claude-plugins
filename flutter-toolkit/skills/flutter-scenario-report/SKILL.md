# Flutter Scenario Report

## Gotchas

- **MCP 캡처는 24 시간 뒤 지워진다** — 서버는 캡처를 `.mcp_screenshots` 에 `screenshot-<시각>.png` 로 저장하고, 이름에 `screenshot-` 이 든 파일을 24 시간 뒤 지운다. 캡처하자마자 도구가 돌려준 파일을 케이스 폴더로 복사한다. 테스트가 끝난 뒤 모아서 복사하면 이미 없다
- **같은 위젯 캡처는 같은 파일 이름으로 덮어써진다** — 위젯 단위 캡처는 위젯마다 이름이 고정이라 두 번째 캡처가 첫 번째를 지운다. 단계마다 바로 복사하지 않으면 앞 단계 사진을 잃는다
- **판정은 캡처를 보고 짐작하지 않고 관측값으로 적는다** — `seen` 에는 위젯 찾기 · 보임 확인 도구나 데이터베이스 조회처럼 프로젝트 설정에서 읽은 도구가 돌려준 값을 쓴다. 사진이 "그럴듯해 보인다" 는 판정 근거가 아니다. 관측값을 못 얻었으면 그 시나리오는 판정하지 말고 `skipped` 에 이유를 쓴다
- **test-evidence 는 git 에서 빠진 원본이라 지우지 않는다** — 되돌릴 방법이 없다. 다시 돌리면 같은 파일 이름으로 덮어쓰고, 기록이 가리키지 않게 된 캡처는 스크립트 경고로 확인한 뒤 사용자에게 묻는다. 폴더를 통째로 지우거나 비우지 않는다. 2026-09-25 QA 평가자가 이 폴더를 자기가 만든 임시 폴더로 알고 지웠다
- **화면 코드를 고친 뒤 전·후 확인은 flutter-ui-verify 몫이다** — 이 스킬은 기능을 시나리오대로 돌려 결과를 기록으로 남긴다. 두 스킬이 같은 화면을 따로 캡처하지 않는다. 테스트 중 결함을 고치게 되면 고치기는 이 스킬 밖에서 하고, 고친 뒤 이 스킬로 다시 돌린다
- **시나리오 판정을 손으로 적지 않는다** — 스크립트가 단계의 `result` 로 계산한다. `result` 는 첫 `그러면` 부터의 확인 단계에만 붙는다. `만일` 에 붙이면 스크립트가 막는다
- **캡처 파일 없이 통과라고 하지 않는다** — 확인 단계마다 그 순간의 캡처가 케이스 폴더에 있어야 한다. 캡처가 없으면 보고에 부분 완료로 적는다

## 하는 일

기능을 시나리오대로 앱에서 실제로 돌리고, 단계마다 캡처와 관측값을 남겨 한 장짜리 HTML 보고서로 모은다.
보고서는 시나리오마다 사진을 왼쪽, 단계와 판정을 오른쪽에 두고, 실패한 단계 바로 아래 실제로 본 것과 확대 사진을 붙인다.
옆 칸에는 테스트 전 상태와 시나리오별 판정 목록이 스크롤을 따라온다.

## 언제 쓰나

- 기능을 사용자 관점 시나리오로 확인하고 그 결과를 남겨야 할 때 (PR 첨부, QA 공유, 회귀 확인)
- 이미 돌린 테스트의 캡처와 관측값을 기록으로 정리할 때 — 이때는 2 · 3 을 건너뛰고 4 부터 한다

## Input

`$ARGUMENTS`: 케이스 ID(`TC-003`) 또는 테스트할 기능 (선택). 없으면 이번 대화에서 다룬 기능을 대상으로 삼고, 무엇을 테스트할지 한 문장으로 되묻는다.

## Process

### 1. 프로젝트 감지

- 플러그인 공용 `references/project-detection.md` 를 실행한다. Step 8 의 `VISUAL_CHANNEL` 이 `mcp:<서버명>` 이어야 이 스킬을 쓸 수 있다. `none` 이면 멈추고 사용자에게 알린다. MCP 서버와 도구 이름은 이 파일에 적지 않는다 — 프로젝트 설정에서 읽은 이름만 쓴다
- 결과 폴더는 `{앱 루트}/.mcp_screenshots/test-evidence/` 다. git 에서 빠져 있는지 확인한다

```bash
git -C {앱 루트} check-ignore -q .mcp_screenshots/test-evidence/index.html && echo ignored || echo tracked
```

- `tracked` 가 나오면 `{앱 루트}/.gitignore` 에 `.mcp_screenshots/` 한 줄을 더하고 그 사실을 사용자에게 알린다. 결과물은 커밋하지 않는다
- 앱 실행과 MCP 연결은 프로젝트 규칙(`.claude/rules/`)이 있으면 그것을, 없으면 전역 규칙의 절차를 따른다

완료 기준: 채널 줄(`VISUAL_CHANNEL = mcp:<서버명>`), 결과 폴더 절대 경로, `ignored` 출력이 응답에 있다.

### 2. 시나리오 작성과 사용자 확인

- 케이스 ID 는 결과 폴더의 기존 `TC-` 번호 다음 번호로 한다. 케이스 폴더 이름은 `TC-{번호}-{영문 요약}` 이다 (`TC-003-leave-group`)
- 제목은 기대 동작 한 문장, 테스트 전 상태는 항목 목록으로 쓴다
- 시나리오마다 단계를 Gherkin 한국어 키워드로 3~5 개 쓴다 — 조건은 `먼저` · `조건`, 행동은 `만일` · `만약`, 확인은 `그러면` 과 그 뒤 `그리고` · `하지만` · `단`
- 확인 단계는 도구로 관측할 수 있는 문장으로 쓴다 ("안내 문구가 뜬다" · "목록에 두 그룹만 있다"). "잘 된다" 같은 문장은 판정할 수 없다
- 아래 표를 한 번 보여 주고 확인받는다. 확인 전에는 앱을 조작하지 않는다

```text
| 시나리오 | 만일 | 그러면 (확인할 것) |
|---|---|---|
| 1. {이름} | {행동} | {관측할 결과} |
```

완료 기준: 사용자가 표를 확인했다는 응답이 대화에 있다.

### 3. 실행·캡처

- 시나리오마다 테스트 전 상태를 만든 뒤 단계를 차례로 실행한다
- 확인 단계 직전에 캡처하고, 곧바로 도구가 돌려준 파일을 케이스 폴더로 복사한다. 이름은 `{두 자리 번호}-{영문 요약}.png` 이고 번호는 케이스 안에서 이어 매긴다 (`01-menu.png` · `02-picker.png`)

```bash
cp "{도구가 돌려준 파일 경로}" "{결과 폴더}/{케이스 폴더}/02-picker.png"
```

- 잘린 글자처럼 작은 부분이 판정의 핵심이면 원본을 잘라 확대 사진을 따로 둔다 (`02-picker-title.png`). 자를 도구가 없으면 확대 사진 없이 `seen` 에 위치를 글로 적는다
- 확인 단계마다 관측값(도구 출력의 핵심 수치나 문구)을 그때그때 적어 둔다. 부른 도구와 핵심 결과는 `run` 에 한 줄씩 남긴다
- 앞 시나리오의 결함 때문에 다음 시나리오를 진행할 수 없으면 멈추고 이유를 적는다. 결함을 이 자리에서 고치지 않는다

완료 기준: 확인 단계마다 케이스 폴더에 캡처 파일이 있다 (`ls {결과 폴더}/{케이스 폴더}`).

### 4. 판정 기록

- 이 스킬 폴더의 `references/record-format.md` 형식으로 `{결과 폴더}/{케이스 폴더}/record.json` 을 쓴다
- 확인 단계마다 `result`(`pass` · `fail`)와 `seen`(3 에서 적어 둔 관측값)을 붙인다. 확대 사진은 그 단계의 `zoom` 에 둔다
- 진행하지 못한 시나리오는 단계만 적고 `skipped` 에 이유를 쓴다
- `summary` 는 결론 한 문장이다. 실패가 있으면 어느 시나리오에서 무엇이 틀렸는지 쓴다

완료 기준: 케이스 폴더에 `record.json` 이 있다.

### 5. 보고서 만들기

`{스킬 폴더}` 는 이 스킬을 불렀을 때 알려 주는 스킬 기본 폴더다.

```bash
python3 "{스킬 폴더}/scripts/build_report.py" "{결과 폴더}" --check
python3 "{스킬 폴더}/scripts/build_report.py" "{결과 폴더}"
```

- `--check` 가 종료 코드 0 으로 끝날 때까지 오류 줄이 가리키는 필드를 고친다. 오류가 있으면 스크립트는 `index.html` 을 쓰지 않는다
- 두 번째 명령이 `{결과 폴더}/index.html` 을 만든다. 결과 폴더의 모든 케이스가 한 장에 들어가고, 실패한 케이스가 위로 온다
- `경고:` 줄(기록이 가리키지 않는 캡처)은 지우지 말고 보고에 옮겨 사용자 판단을 받는다
- 보고서를 브라우저로 연다 (macOS 는 `open "{결과 폴더}/index.html"`)

완료 기준: 두 번째 명령이 `보고서:` 줄을 찍고 종료 코드 0 으로 끝난다.

### 6. 완료 전 대조

완료를 말하기 전에 아래를 하나씩 확인하고 결과를 응답에 남긴다.

- [ ] `build_report.py --check` 종료 코드 0
- [ ] 판정한 단계마다 `seen` 에 도구가 돌려준 관측값이 있다 — 짐작한 문장이 아니다
- [ ] 캡처가 전부 케이스 폴더 안에 있다 — MCP 저장 폴더를 가리키는 경로가 없다
- [ ] 실패가 있으면 `summary` 가 어느 시나리오의 무엇인지 말한다
- [ ] 1 의 `git check-ignore` 결과가 `ignored` 다
- [ ] 위 Gotchas 를 한 줄씩 다시 읽고 어긴 것이 없다

보고는 아래 세 줄로 시작한다.

```text
보고서: {결과 폴더}/index.html
결과: 케이스 {N}개 · 실패 {N} · 통과 {N}
실패: {케이스 ID} 시나리오 {N} — {한 문장} (실패가 없으면 "없음")
```
