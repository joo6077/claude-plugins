Apple Human Interface Guidelines

Apple HIG 핵심 원칙, iOS/macOS/visionOS/watchOS/CarPlay 플랫폼별 차이, SF Symbols 심층, 주요 컴포넌트 패턴. design-kit 의 디자인 시스템 레이어가 참조하는 공식 가이드라인.

1 · 4대 핵심 원칙

Apple 의 디자인 철학은 명확성 · 존중 · 깊이 · 일관성 네 기둥으로 정의된다. 기능적 완결성과 콘텐츠 우선주의가 모든 결정을 관통한다.

01

명확성 (Clarity)

모든 요소가 읽기 쉽고 이해하기 쉬워야 한다. 크기 · 색상 · 무게로 위계를 신호하고, 전문 용어 없는 간결한 레이블, SF Symbols 기반 기능적 아이콘을 제공한다.

developer.apple.com/hig
02

존중 (Deference)

UI 는 콘텐츠의 프레임이지 경쟁자가 아니다. 유체 애니메이션 · 반투명으로 콘텐츠가 주인공이 되게 하고, 장식적 요소는 기능적 목적이 있을 때만 사용한다.

DEV Community — Practical Guide
03

깊이 (Depth)

레이어링과 자연스러운 전환으로 공간적 맥락을 제공한다. z 축 그림자 · 투명도 · 전환 애니메이션 · 제스처 연속성으로 사용자 현재 위치를 시각화한다.

developer.apple.com/hig
04

일관성 (Consistency)

플랫폼 전체에서 예측 가능한 경험. 시스템 제공 컨트롤과 표준 패턴을 우선 사용하고, 앱 내부에서도 용어 · 아이콘 · 동작의 일관성을 유지한다.

developer.apple.com/hig
2 · 플랫폼별 핵심 수치

각 플랫폼의 입력 방식과 맥락이 터치 타겟 · 인터랙션 시간을 결정한다. 이 수치는 최소값으로, 특수 맥락(운전 중 등)에서는 확장한다.

44 x 44 pt 의 귀속 — Apple HIG 필수 ≠ WCAG AA 하한

44 x 44 pt 는 Apple HIG 의 필수 요구사항이다. WCAG 2.2 의 AA 하한은 24 x 24 CSS px(SC 2.5.8 Target Size (Minimum))이며, 44 x 44 는 AAA(SC 2.5.5 Target Size (Enhanced))다. 두 기준을 섞어 "WCAG 가 44pt 를 요구한다" 고 쓰지 마라 — 감사 근거로 인용할 때 표준과 등급을 함께 적는다.

3 · iOS 주요 컴포넌트 패턴

탭 바 · 내비게이션 바 · 시트 · 알럿. 네 가지가 iOS 앱 구조의 90% 를 차지한다.

1내비게이션 바

Large Title — 정적 상태 34pt 좌측 정렬, 스크롤 시 17pt 중앙 정렬로 축소 전환. 최상위 화면에서만 사용하고 하위 화면은 표준 크기.

좌측 뒤로가기 · 중앙 제목 · 우측 트레일링 액션의 3단 구조를 유지한다.

developer.apple.com/.../navigation-bars

2탭 바

iPhone 최대 5개 탭 — 초과 시 "더보기" 탭 자동 생성. 각 탭은 독립적 내비 스택 유지. SF Symbols 아이콘 + 레이블 조합.

iPadOS 18+ 는 적응형 탭 바: 컴팩트(탭) ↔ 확장(사이드바) 사용자 전환.

developer.apple.com/.../tab-bars

3시트 (Sheets)

Page / Form / Full Screen 3가지 프레젠테이션. 모달 사용 최소화 — 주의 유발 · 작업 완료 · 중요 저장 시에만 사용. 시트 내부 시트 중첩 지양.

닫기/취소 동작(스와이프 다운 또는 버튼)을 항상 명확히 제공한다.

developer.apple.com/.../sheets

4알럿 (Alerts)

필수적 · 실행 가능한 정보만. 2개 버튼일 때 기본 액션 우측(또는 상단), 취소 좌측. 파괴적 액션은 빨간색 + 확인 단계 필수. 자동 사라짐 없음.

알럿(시스템 주도) vs 액션 시트(사용자 액션 응답) 구분.

developer.apple.com/.../alerts

5 · visionOS — 공간 컴퓨팅

Apple Vision Pro 는 시선 추적 + 핀치 손 제스처가 기본 입력이다. 2D UI 의 "여백" 개념이 실제 물리 공간의 거리/배치로 확장된다.

윈도우 (Windows)

SwiftUI 기반 2D 인터페이스가 공간에 배치. 기존 iOS/iPadOS 뷰를 재사용하며 3D 콘텐츠로 깊이 추가 가능.

HIG — visionOS

볼륨 (Volumes)

RealityKit 또는 Unity 3D 콘텐츠. 모든 각도에서 관찰 가능한 장면. 유리 바닥 그림자로 물리적 실재감.

몰입형 공간

Full Immersion vs Passthrough 모드. 사용자가 실제 환경과 가상 환경 사이를 단계적으로 전환할 수 있다.

커스텀 심볼 제작 · 자동 지역화

  • 9 무게(Ultralight~Black) × 3 스케일(S/M/L) = 27 변형이 이상적이나, 최소 Regular-Medium 1 개만 제작하면 나머지는 자동 보간된다

8 · 안티패턴 vs 올바른 패턴

HIG 원칙을 위반하는 전형적 실수와 교정안. design-kit 의 design-audit 스킬이 가장 자주 지적하는 항목.

✗ Bad — 한 손 조작 무시

주요 CTA 를 iPhone 화면 최상단에 배치. 큰 화면 사용자는 엄지 닿지 않아 양손 조작 강제.

✓ Good — 엄지 존 배치

주요 액션은 화면 하단 또는 탭 바 근처(엄지 닿는 영역)에 배치. 상단은 제목 · 보조 정보만.

✗ Bad — 탭 바 6개 이상

iPhone 탭 바에 6개 이상의 탭 강제 배치. 아이콘 간격이 좁아지고 오탭 빈번.

✓ Good — 5개 이하

최대 5개로 제한. 초과 항목은 "더보기" 탭 또는 첫 탭의 하위 메뉴로 배치.

✗ Bad — 시트 중첩

시트 안에서 또 다른 시트를 pushModal. 사용자가 어느 맥락에 있는지 혼란.

✓ Good — 푸시 내비

시트 내부에서는 내비게이션 스택으로 드릴다운. 최종 완료/취소만 시트를 닫음.

✗ Bad — 알럿 남용

저장 성공 · 새 메시지 · 단순 안내까지 알럿으로 표시. 사용자 경험 중단.

✓ Good — 토스트 · 배지

알럿은 필수/실행가능 정보에만. 저장 성공은 인라인 체크, 새 메시지는 배지로.

✗ Bad — SF Symbols 무시

커스텀 비트맵 아이콘 사용. 다크모드 · 동적 타이포 · RTL 에서 모두 수동 처리.

✓ Good — SF Symbols

시스템 심볼 우선 사용. 무게 · 스케일 · 다크모드 · RTL 자동 처리.

9 · Gotchas 체크리스트

HIG 준수 구현 시 반드시 확인할 항목. design-audit 에서 FAIL 빈도가 높은 순서로 정렬.

  • ✓
    터치 타겟 44×44pt (Apple HIG 필수) — 아이콘 시각 크기가 작아도 터치 영역은 44pt 확보. 인접 타겟 간 최소 8pt 간격. 웹 병행 구현이면 WCAG 2.2 AA 하한 24×24 CSS px(SC 2.5.8)도 함께 만족하는지 확인한다.
  • ✓
    Safe Area 대응 — 노치 · Dynamic Island · 홈 인디케이터를 피하는 레이아웃. 전체화면 콘텐츠는 Safe Area 무시 옵션 명시.
  • ✓
    Size Classes 분기 — iPhone Compact vs iPad Regular 에서 동일 앱이 레이아웃 재구성. 하드코딩된 width 금지.
  • ✓
    Dynamic Type 지원 — 시스템 타이포 스케일 사용. 고정 font size(17pt) 대신 .body, .headline 같은 스타일 토큰.
  • ✓
    Haptic Feedback — 중요 액션에 햅틱. 성공/실패/선택 변경 시 UIImpactFeedbackGenerator 또는 SwiftUI .sensoryFeedback.
  • ✓
    다크 모드 기본 구현 — UIColor.label, UIColor.systemBackground 같은 동적 컬러만 사용. 하드코딩 금지.
  • ✓
    VoiceOver 라벨 — 모든 인터랙티브 요소에 accessibilityLabel. 장식 이미지는 .isAccessibilityElement = false.
  • ✓
    Reduce Motion 대응 — UIAccessibility.isReduceMotionEnabled 체크 후 애니메이션 길이 축소 또는 제거.
  • ✓
    visionOS 포커스 상태 — 시선 추적 포커스에 대응하는 hover 상태 구현. .hoverEffect 또는 커스텀 스타일.
  • ✓
    키보드 단축키(macOS/iPadOS) — 주요 메뉴 항목에 Cmd+X 단축키. UIKeyCommand 또는 SwiftUI .keyboardShortcut.
10 · 실무 팁 · FAQ

실제 프로젝트 적용 시 자주 부딪히는 질문들. HIG 의 공식 가이드만으로는 답하기 어려운 경계 케이스.

Q. 커스텀 폰트를 써도 HIG 준수인가?

브랜드 아이덴티티가 강한 앱은 커스텀 폰트 허용. 단 Dynamic Type 연동은 필수 — UIFont.preferredFont 스케일을 따르거나 .scaledFont 수정자를 사용한다. 고정 크기 하드코딩은 HIG 접근성 원칙 위반.

Q. 탭 바 5개 규칙을 꼭 지켜야 하나?

iPhone 에서는 공간 제약으로 사실상 필수. 6개 이상 필요하면 "더보기" 탭으로 하위 메뉴화 또는 사이드바 패턴(iPad) 채택. iPadOS 18+ 의 적응형 탭 바는 확장 모드에서 7개까지 자연스럽게 표시 가능.

Q. 크로스 플랫폼 앱에 HIG 를 어떻게 적용?

iOS 빌드는 HIG, Android 빌드는 Material Design 를 각각 따른다. Flutter 는 CupertinoApp + MaterialApp 분기 또는 Platform.isIOS 감지로 플랫폼별 UI 전환. 공통 비즈니스 로직 + 플랫폼별 presentation 구조.

Q. visionOS 앱도 즉시 출시 가능한가?

iOS 앱은 Vision Pro 에서 "호환 모드"로 기본 동작. 하지만 시선/핀치 입력 최적화 · 공간 레이아웃 활용은 별도 튜닝 필요. ornaments · .hoverEffect · glass 재질을 도입해 visionOS 네이티브 경험 구현.

TL;DR — HIG 를 한 문장으로

"콘텐츠가 주인공이다. UI 는 콘텐츠를 돋보이게 하는 프레임이며, 플랫폼마다 입력 방식이 다르므로 그에 맞춰 인터랙션 패턴을 조정한다." — 이 원칙만 지켜도 대부분의 HIG 조항이 자동으로 충족된다.
