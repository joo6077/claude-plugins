Core Principles

목업을 지탱하는 네 가지 원칙

보기 좋은 화면보다 비교 가능하고 추적 가능하며 구현으로 안전하게 이어지는 시안을 우선한다.

01먼저 계약한다

파일 생성 전에 Variant Contract Matrix의 6개 열과 산출 개수를 사용자와 합의한다. 색상만 다른 안은 별도 시안이 아니다.

출처: Visual Change Protocol §5
02시각 원본을 보존한다

브라우저에서 승인된 색상·간격·타이포 값은 기존 토큰보다 우선한다. 토큰화가 필요하면 값을 바꾸지 않고 그 값으로 토큰을 정의한다.

출처: Visual Change Protocol §1
03접근성을 기본값으로 둔다

WCAG 2.2 AA 대비 4.5:1과 24×24 CSS px 최소 타겟을 지킨다. 시안 기본은 AAA와 플랫폼 권장치인 44×44 CSS px로 잡는다.

출처: W3C WCAG 2.2 SC 2.5.8
04증거 채널을 구분한다

목업 캡처는 artifact_snapshot이다. 실제 앱 화면의 정상 동작을 주장하려면 별도 런타임 증거가 필요하다.

출처: Visual Change Protocol §7

Step 1

Step 1: 화면 요구사항 파악

어떤 화면인지, 무엇을 해야 하는지, 누가 쓰는지를 먼저 고정한다.

페이지와 화면

로그인, 대시보드, 설정처럼 대상 화면을 특정한다. 파일 경로와 라우트도 함께 적고, 새 화면이면 신규라고 표시한다.

기능과 정보

핵심 행동, 반드시 보여야 할 데이터, 요소 이름과 배치를 한 문장으로 되말한다.

대상 사용자

누가 어떤 맥락에서 쓰는지 확인한다. 요청이 두 갈래로 읽히면 만들기 전에 질문한다.

산출 전 필수: Visual Change Protocol §0에 따라 대상 파일·라우트와 요청의 요소·배치를 되말한다.
Step 2

Step 2: 자동 감지 및 로드

이미 합의된 컨셉, 토큰, 승인 기록, 앱 관례를 먼저 읽어 새 시안의 입력으로 삼는다.

# 감지 대상
.design/concept.md          → 컨셉 로드
**/theme/** **/tokens/**    → 디자인 토큰 로드
**/design-tokens.*          → 디자인 토큰 로드
.design/approvals/*.md      → 같은 화면의 확정 구성 · 폐기한 대안 로드
찾은 입력의 적용
  • 컨셉: 무드 키워드, 컬러·타이포 방향, UI 패턴 반영
  • 토큰: 실제 컬러값, 타이포 스케일, 간격 반영
  • 둘 다 없음: 사용자 요구사항만으로 생성
  • 승인 기록: 확정 구성 유지, 폐기안은 요청 전까지 부활 금지
앱 코드가 있을 때

같은 역할의 기존 화면을 두 개 이상 읽고 §0 관례 표를 만든다. 재사용 부품은 grep으로 확인한 실제 이름만 쓰며, 확인된 관례를 Step 3-a의 constants에 넣는다.

Step 3

Step 3: 개수 계약 · Variant Contract Matrix 합의 후 하이파이 HTML 시안 생성

파일을 만들기 전에 개수와 차별화 축을 고정하고, 구별성 게이트를 통과한 시안만 생성한다.

Step 3-a · 개수와 축을 먼저 고정한다

variant_id strategy_label axis_vector constants intended_user_scenario 생성 파일
시안 식별자 전략적 우선순위 비교할 구조 축의 값 모든 안에서 고정할 관례 가장 잘 맞는 사용자 맥락 standalone HTML 경로
구별성 계산: 지정 축이 3개 이상이면 모든 쌍의 Hamming distance가 2 이상, 2개 이하면 1 이상이어야 한다. 색상·토큰 값·카피·아이콘만 바뀐 축은 계산하지 않는다.

Step 3-b · 합의된 개수만큼 생성한다

OUTPUT
standalone 하이파이 HTML

.design/mockups/{페이지명}-{특징}.html 경로에 실제 컬러·타이포·간격과 현실적인 콘텐츠를 담는다.

TRACEABILITY
모든 UI 요소에 ID

{컴포넌트명}-{4자리해시} 형식을 쓰고, 전체 시안에 걸쳐 해시가 겹치면 재생성한다. 호버 오버레이와 복사 기능도 포함한다.

RESPONSIVE
상태와 규칙을 함께 제시

요구사항에 반응형이 있으면 mobile/tablet/desktop에서 같은 시나리오 상태를 유지하고 컬럼 수·거터·max-width를 명시한다.

전략 레이블 후보 풀

전환 최적화형

사이드바 네비게이션과 메인 콘텐츠, 상단 고정 주요 CTA.

탐색성 강화형

탑바와 카드 그리드, 필터와 정렬을 전면 배치.

정보 밀도형

탭 기반 리스트 뷰와 스캔 가능한 텍스트 계층.

브랜드 임팩트형

풀스크린 히어로와 스크롤 섹션, 비주얼 중심 진입.

대시보드/제어형

위젯 패널, 상태 요약과 빠른 액션을 우선.

선택해서 사용

다섯 개 전부를 만드는 목록이 아니라 합의된 개수만큼 골라 쓰는 후보 풀이다.

반응형 구현 원칙

Container Queries

페이지 레벨 분기는 media queries, 컴포넌트 레벨 분기는 container-type: inline-size와 @container를 권장한다. 디바이스 이름보다 콘텐츠가 깨지는 지점에 breakpoint를 둔다. cqw/cqi 단위로 컨테이너 상대 크기도 지정할 수 있다.

Fluid Typography

clamp(min, preferred, max) 기반 글자 크기로 뷰포트 사이를 자연스럽게 전환한다. 특히 히어로와 디스플레이 텍스트에 효과적이다.

Step 4

Step 4: 디자인 의도 설명

각 화면을 나열하지 않고, 같은 문제를 어떤 전략으로 다르게 해결했는지 사용자 시나리오 흐름으로 설명한다.

1전략과 구조

전환·탐색·브랜드 같은 우선순위와 레이아웃 선택 이유, 정보 구조를 연결해서 설명한다.

2시선과 맥락

어디에 시선이 머무는지, 어떤 사용자 시나리오에 가장 잘 맞는지를 밝힌다.

3결정 근거

주요 구성의 이유를 짧게 제시해 취향 투표가 아니라 선택 기준에 관한 토론으로 만든다.

Step 5

Step 5: 사용자 선택 및 수정

사용자는 전략을 선택하고, 유니크 ID로 특정 요소를 지칭한다. 부분 변경은 Change Manifest로 변경 범위를 잠근다.

비교 상황기법
구조가 크게 다른 안side-by-side로 나란히 배치
동일 화면의 일부 요소 변경변경 전과 후를 겹쳐 설명
결정 근거·핸드오프 포함주석(annotation) 추가
인터랙션·상태 변화hover/focus/click 동작 포함

Change Manifest

## Change Manifest
- 변경: [속성 — 대상 ID — 현재값 → 목표값]
- 보존: [같은 요소의 나머지 시각 속성 — background / fill / radius /
         shadow / spacing / typography 중 해당분 · 요소 하나를 지목했으면
         같은 줄·같은 영역의 이웃 요소와 그 자리]

수정 후: 보존 목록의 값이 그대로인지 확인한다. 의도 밖 변화가 있으면 되돌리고 지목된 속성만 다시 적용한다. 확정된 최종본은 .design/mockups/에 유지한다.

Step 6

Step 6: 승인 기록 생성 (확정 시 필수)

사용자가 시안을 확정하면 대화 로그로 끝내지 않고, 선택과 시각 값을 재검증 가능한 파일로 남긴다.

# 승인 기록 — {화면명}

- 승인일: {YYYY-MM-DD}
- 승인 주체: {사용자 직접 확정 | 자율 모드 (판단 근거 명시)}
- 대상 산출물: .design/mockups/{파일명}.html
- 선택된 안: {전략 레이블 + 시안 ID}
- 확정된 시각 값: {승인 시점에 고정된 색상·타이포·간격 — 이후 토큰과 충돌 시 이 값이 우선}
- 확정 구성: {화면에 남는 요소와 배치}
- 폐기한 대안·이유: {이번 결정에서 버린 안·요소와 이유 — 없으면 `없음`}
- 미확정/후속: {합의되지 않아 남긴 항목}
- 원문 근거: {사용자 발화 인용}

생성 직후 검증

ls .design/approvals/                      # 파일 존재
grep -c '확정된 시각 값' .design/approvals/{파일명}.md   # → 1
grep -cE '^- (확정 구성|폐기한 대안·이유):' .design/approvals/{파일명}.md   # → 2
승인 후 다시 수정했다면: 승인 기록도 함께 갱신한다. 스테일 승인 기록은 기록이 없는 것보다 나쁘다.
Step 7

Step 7: Figma 전송 (선택)

사용자가 요청했을 때만 선택한 시안 또는 ID로 지정한 개별 컴포넌트를 Figma로 전송한다.

CONNECTED
MCP가 설정됨

선택한 전체 시안이나 지정한 개별 컴포넌트를 Figma로 전송한다.

NOT CONFIGURED
안내로 처리

에러를 내지 않고 “Figma 전송을 원하면 Figma MCP 설정이 필요합니다”라고 알린 뒤 HTML 파일 경로를 함께 제공한다.

FAILED
복구 경로 제공

전송 실패 시 오류 메시지와 함께 사용자가 직접 확인할 HTML 파일 경로를 안내한다.

Anti-patterns

나쁜 비교와 좋은 비교

형식적으로 여러 안을 만드는 대신, 계산 가능한 구조 차이와 명확한 선택 근거를 만든다.

Bad

A안 / B안, 색상만 교체

레이아웃과 구성 축은 같은데 accent, 카피, 아이콘만 바꾸고 별도 시안이라고 선언한다.

  • axis_vector의 Hamming distance는 0
  • 전략 레이블이 없어 취향 투표로 흐름
  • 요청하지 않은 토큰 파일과 카탈로그까지 생성
  • 정적 캡처로 인터랙션 정상까지 주장
Good

전환 최적화형 / 탐색성 강화형

합의한 네비게이션·콘텐츠 구조·정보 위계 축을 실제로 달리하고, 같은 사용자 시나리오에서 비교한다.

  • 모든 시안 쌍이 구별성 게이트 통과
  • 전략과 적합한 사용자 맥락을 함께 설명
  • 계약된 개수와 HTML 파일만 생성
  • artifact_snapshot과 앱 런타임 증거를 구분

부분 수정의 bad / good

Bad

“보더만” 요청에 전체 스타일 정규화

승인된 색을 기존 accent 토큰으로 바꾸고 radius, shadow, spacing까지 함께 손본다. 요청하지 않은 변화는 개선이 아니라 실패다.

Good

Change Manifest로 한 축만 변경

대상 ID와 현재값·목표값을 적고, 배경·채움·반경·그림자·간격·타이포 및 이웃 요소의 자리를 보존 목록으로 검증한다.

Gotchas

제출 전 체크리스트

원본의 17개 주의사항을 빠짐없이 점검한다.

  1. 1컬러 변형만으로 구분하지 않았는가? 구별성은 선언이 아니라 axis_vector와 Hamming distance로 계산한다.
  2. 2ID가 전역 유니크한가? {컴포넌트명}-{짧은해시}가 겹치면 재생성한다.
  3. 3접근성을 지켰는가? WCAG 2.2 AA 대비 4.5:1, AA 타겟 24×24 CSS px, 시안 기본 44×44 CSS px를 확인한다.
  4. 4Figma MCP 미설정을 오류로 취급하지 않았는가? 설정 필요 안내와 HTML 경로를 제공한다.
  5. 5Lorem ipsum을 쓰지 않았는가? 실제 콘텐츠나 현실적인 예시 데이터로 레이아웃을 평가한다.
  6. 6A안/B안만 붙이지 않았는가? 전략적 우선순위가 드러나는 레이블을 쓴다.
  7. 7디바이스 프레임을 목적에 맞게 선택했는가? near-final 발표에는 유용하지만 구조·밀도 비교를 방해할 수 있다.
  8. 8인터랙션 쟁점을 정적 화면만으로 판단하지 않았는가? hover/focus/click 또는 프로토타입을 제공한다.
  9. 9반응형 화면의 시나리오 상태가 같은가? 컬럼·거터·max-width 규칙도 함께 명시한다.
  10. 10컴포넌트 반응형에 Container Queries를 검토했는가? breakpoint는 디바이스 이름보다 콘텐츠 파손 지점에 둔다.
  11. 11Fluid Typography를 적용했는가? 특히 히어로 텍스트에 clamp()를 활용한다.
  12. 12mockup.html을 정상 HTML 산출물로 취급했는가? Markdown 계약과 형식이 다른 것은 의도된 설계다.
  13. 13확정 시 승인 파일을 생성했는가? 자율 승인도 승인 주체와 판단 근거를 기록한다.
  14. 14승인 값을 토큰으로 치환하지 않았는가? 승인된 시각 값이 프로젝트 팔레트보다 우선한다.
  15. 15부분 수정 전에 Change Manifest를 남겼는가? 변경과 보존 목록을 수정 후 다시 확인한다.
  16. 16산출 전에 Variant Contract Matrix를 합의했는가? 개수 상한과 부대 산출물 금지까지 계약한다.
  17. 17캡처를 artifact_snapshot으로 표기했는가? PASS에는 viewport, route/state, visible locator, count/height, screenshot id를 포함하고 사용자 실패 보고는 재현한다.
