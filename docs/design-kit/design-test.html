핵심 원칙

테스트가 증거가 되기 위한 조건

스냅샷 파일이나 초록색 실행 결과만으로 품질을 증명할 수 없습니다. 판정 기준, 활성화 실패, 콘텐츠 존재, 사용자 관측 채널을 함께 묶어야 합니다.

baseline은 통과가 아니다

Playwright 는 스냅샷이 없으면 실제 화면을 baseline 으로 자동 기록하고 그 실행을 통과 처리합니다(첫 실행 시 "A snapshot doesn't exist ... writing actual"). 따라서 --update-snapshots 직후의 green 은 아무것도 입증하지 않습니다 — 무엇과도 비교되지 않았기 때문입니다. 의도적 변형이 실제로 실패하는 negative control 과 되돌린 뒤 통과를 모두 확인해야 합니다.

두 임계값을 분리한다

maxDiffPixelRatio 는 달라도 되는 픽셀의 비율(0~1, 기본 unset)이고, threshold 는 같은 좌표 픽셀 간 허용 색차(YIQ 색공간, 0=엄격 ~ 1=관대, 기본 0.2)입니다. 둘은 다른 것이므로 색상 회귀를 잡으려면 threshold 를 낮춰야 하며, maxDiffPixelRatio 만 조정해서는 잡히지 않습니다.

Gotchas

생성 전에 확인할 체크리스트

15개 가드레일을 모두 확인합니다. 특히 10~15번은 시각 회귀 결과가 실제 사용자 관측을 증명하도록 만드는 규칙입니다.

  1. 1
    스택 감지 없이 테스트 생성 금지. React/Vue/Svelte/Flutter/HTML 등 프로젝트 프레임워크를 먼저 감지하라. Playwright 테스트를 Flutter 프로젝트에 생성하면 안 된다.
  2. 2
    WCAG 2.2 AA 기준 미적용 금지. 접근성 테스트는 반드시 WCAG 2.2 AA를 기준으로 한다. 대비 비율 4.5:1 (본문), 3:1 (큰 텍스트/비텍스트 UI), 터치 타겟 24×24px(AA) / 44×44px(AAA). 출처: design-kit design-audit Gotcha #3
  3. 3
    axe-core 룰셋 버전 확인. @axe-core/playwright 또는 axe-core 사용 시 프로젝트에 설치된 버전의 룰셋을 확인하라. 메이저 버전 간 룰 차이가 있다.
  4. 4
    시각 회귀 테스트의 threshold 미설정 금지. 픽셀 단위 비교는 anti-aliasing, 폰트 렌더링 차이로 false positive가 빈번하다. maxDiffPixelRatio: 0.01 같은 threshold 필수.
  5. 5
    토큰 검증에서 하드코딩 탐지 범위 명확히. CSS에서 #ff0000, 16px, 400 같은 raw value가 있다고 무조건 FAIL이 아니다. reset/normalize CSS, 외부 라이브러리 코드는 제외하라.
  6. 6
    반응형 테스트에서 breakpoint 출처 확인. 프로젝트의 디자인 시스템에 정의된 breakpoint를 사용하라. 임의로 320/768/1024를 넣지 마라.
  7. 7
    다크 모드 테스트 누락 금지. 디자인 토큰에 다크 모드 매핑이 있으면 반드시 양쪽 모드에서 테스트한다. prefers-color-scheme: dark 미디어 쿼리 또는 토큰 클래스 전환.
  8. 8
    Storybook 의존 여부 확인. 시각 회귀 테스트에 Storybook을 전제하지 마라. Storybook이 없으면 Playwright의 페이지 스크린샷으로 대체한다.
  9. 9
    APCA 대비 알고리즘은 informational. WCAG 2.2 AA(4.5:1 WCAG2 공식)가 판정 기준. APCA Lc는 추가 정보 제공용으로만 포함하고 PASS/FAIL 판정 기준으로 쓰지 마라. 출처: design-guide Gotcha #10
  10. 10
    첫 실행 baseline 생성을 "테스트 통과"로 보고 금지 (negative control 필수). Playwright 는 스냅샷이 없으면 실제 화면을 baseline 으로 자동 기록하고 그 실행을 통과 처리한다. 따라서 --update-snapshots 직후의 green 은 아무것도 입증하지 않는다 — 무엇과도 비교되지 않았기 때문이다(증거 유효성 검사 2 활성화 실패). baseline 을 만든 뒤에는 반드시 negative control 을 1 회 수행하라: 대상 요소에 의도적 변형(예: 배경색 1 단계 변경)을 준 상태로 테스트를 돌려 실패하는 것을 확인하고, 되돌린 뒤 통과를 확인한다. 이 두 실행의 출력을 증거로 인용하기 전에는 시각 회귀 테스트가 동작한다고 보고하지 마라. 출처: Playwright Visual Comparisons, harness/docs/guides/qa-evaluation-guide.md §Evidence Validity Gate 검사 2·3.
  11. 11
    빈 스냅샷/빈 페이지는 PASS 증거가 아니다. 렌더가 실패해 빈 화면이 캡처돼도 시각 회귀 테스트는 baseline 과 동일하면 통과한다. 시각 테스트에는 콘텐츠 존재 assertion 을 함께 생성하라 (핵심 요소 visible, 목록 항목 수 ≥ 1, 컨테이너 높이 > 0). 스냅샷 비교만 있는 테스트 파일은 unbounded-height collapse 같은 결함을 통과시킨다 — 실제 사고 사례다. 상세: ../../references/visual-change-protocol.md §3.
  12. 12
    부분 변경 검증은 scoped 스냅샷으로 — 의도 외 영역 변화 감지. "보더만 바꿨다" 를 검증할 때 전체 페이지 스냅샷 하나만 쓰면 배경까지 변한 것을 구분하지 못한다. 변경 대상 요소의 locator 단위 스냅샷과 주변 영역 스냅샷을 분리 생성하여, 대상은 변하고 주변은 변하지 않았음을 각각 판정하라. 주변 영역 스냅샷이 실패하면 그것은 회귀다. 상세: ../../references/visual-change-protocol.md §2.
  13. 13
    prefers-reduced-motion: reduce 는 "애니메이션 제거" 가 아니다. 이 설정은 vestibular trigger(scale·pan 등 이동감을 주는 모션)를 더 온건한 대안으로 교체하라는 의미이며 모든 전환을 없애라는 뜻이 아니다. 따라서 reduced-motion 테스트를 "애니메이션 개수 0" 으로 assert 하지 마라. transform: scale/translate 기반 모션이 사라지거나 opacity/dissolve 로 대체되었는지를 검증하라. 출처: MDN prefers-reduced-motion (Baseline 2020-01).
  14. 14
    골든만 있는 결정 전파 테스트는 FAIL — Decision Propagation Manifest Coverage. 확정된 디자인 결정이 어느 표면에 반영돼야 하는지는 .design/decisions.yaml 이 열거한다 (decision_id → required_surfaces[] → golden + assertions). 이 manifest 가 있으면 커버리지 규칙 4 조를 따라 테스트를 생성하라. 핵심은 golden 만 있고 핵심 요소의 visible / count / height assertion 이 없으면 FAIL 이라는 것 — 빈 화면도 baseline 과 같으면 통과하므로 스냅샷 단독은 "사용자가 본다" 를 증명하지 못한다 (Gotcha 11 과 같은 뿌리). excluded_surfaces 에 이유 없이 빠진 표면은 검토된 것이 아니라 커버리지 공백이다. 스키마·규칙·실행 가능한 체커: ../../references/visual-change-protocol.md §6 Decision Propagation Manifest.
  15. 15
    증거에 채널 이름을 붙여라 — 스냅샷 존재는 사용자 관측이 아니다. artifact_snapshot / dom_snapshot / browser_user_visible / device_user_visible 는 강도가 다르다. PASS 문장에는 viewport · route/state · visible locator · count/height · screenshot/golden id 5 요소가 들어가야 하며, 하나라도 없으면 [미검증] 이다. 채널 정의: ../../references/visual-change-protocol.md §7 Evidence Channels. 사용자가 실패를 보고했을 때의 우선순위 규약은 harness/docs/guides/skill-design-guide.md §3.8 이 정본이다 — 테스트 통과를 근거로 반박하지 마라.

Step 3

토큰 일관성 테스트 생성

디자인 토큰 파일을 분석하여 일관성을 검증하는 테스트를 생성합니다. CSS custom properties 를 파싱해 색상 포맷(hex/oklch/hsl), 스페이싱 스케일(base * multiplier), 컴포넌트 파일의 하드코딩 값, 라이트·다크 토큰 대응을 검사합니다.

// tests/design/tokens.test.ts
import { describe, it, expect } from 'vitest'
import fs from 'fs'

describe('Design Token Consistency', () => {
  // CSS custom properties 파싱
  const cssContent = fs.readFileSync('src/styles/tokens.css', 'utf-8')
  const tokens = [...cssContent.matchAll(/--([^:]+):\s*([^;]+)/g)]

  it('all color tokens use consistent format (hex/oklch/hsl)', () => {
    const colorTokens = tokens.filter(([, name]) => name.includes('color'))
    const formats = new Set(
      colorTokens.map(([, , value]) => {
        if (value.trim().startsWith('#')) return 'hex'
        if (value.trim().startsWith('oklch')) return 'oklch'
        if (value.trim().startsWith('hsl')) return 'hsl'
        return 'other'
      })
    )
    expect(formats.size).toBeLessThanOrEqual(1)
  })

  it('spacing tokens follow scale (base * multiplier)', () => {
    const spacingTokens = tokens
      .filter(([, name]) => name.includes('spacing'))
      .map(([, , value]) => parseFloat(value))
      .sort((a, b) => a - b)

    for (let i = 1; i < spacingTokens.length; i++) {
      const ratio = spacingTokens[i] / spacingTokens[i - 1]
      expect(ratio).toBeGreaterThan(1)
    }
  })

  it('no hardcoded values in component files', () => {
    const componentCss = fs.readFileSync('src/components/Button.css', 'utf-8')
    const rawColors = [...componentCss.matchAll(/#[0-9a-fA-F]{3,8}/g)]
    const rawPx = [...componentCss.matchAll(/:\s*\d+px/g)]
    // reset, normalize, 외부 라이브러리 파일은 검사 대상에서 제외
    expect(rawColors).toEqual([])
    expect(rawPx).toEqual([])
  })

  it('dark mode tokens cover all light mode tokens', () => {
    const lightNames = tokens
      .filter(([, name]) => !name.includes('dark'))
      .map(([, name]) => name.replace('light-', ''))
    const darkNames = tokens
      .filter(([, name]) => name.includes('dark'))
      .map(([, name]) => name.replace('dark-', ''))
    const missing = lightNames.filter(n => !darkNames.includes(n))
    expect(missing).toEqual([])
  })
})
하드코딩 값 검사는 reset·normalize CSS와 외부 라이브러리를 제외해야 합니다. #ff0000, 16px, 400이 있다는 이유만으로 무조건 FAIL 로 보지 않습니다 (Gotcha 5).
Step 4

접근성 테스트 생성

Step 1 에서 감지된 라우트마다 axe-core WCAG 2.2 AA 룰셋, 접근 가능한 이름, 색 대비 4.5:1, 24×24px 터치 타겟을 검사합니다. 토큰에 다크 모드가 있으면 다크 모드 대비 테스트를 더합니다.

// tests/design/a11y.test.ts
import { test, expect } from '@playwright/test'
import AxeBuilder from '@axe-core/playwright'

const pages = [
  { name: 'Home', path: '/' },

Step 5

시각 회귀 테스트 생성

mobile 375×812, tablet 768×1024, desktop 1440×900 예시 viewport에서 콘텐츠 존재 assertion 을 스냅샷 비교 "전에" 실행하고 스크린샷을 비교합니다. Storybook 이 감지될 때만 컴포넌트별 시각 테스트 섹션을 더합니다.

부분 변경 scoped 검증

특정 요소의 특정 속성만 바꾼 변경을 검증할 때는 대상과 주변을 분리합니다 (Gotcha 12). 주변 스냅샷이 실패하면 의도 외 영역이 변한 것이므로 회귀로 처리합니다.

대상 요소 (변경 허용)

target-card.png처럼 locator 단위로 캡처합니다. 의도한 변경은 이 영역에만 허용합니다.

주변 영역 (변경 금지 — 실패 시 회귀)

surrounding-panel.png을 따로 캡처합니다. "변하지 않아야" 하므로 대상보다 엄격한 0.001 을 쓰되, Gotcha 4 대로 0 은 쓰지 않습니다 — anti-aliasing·폰트 렌더링 차이로 상시 실패합니다.

// tests/design/scoped-change.test.ts
import { test, expect } from '@playwright/test'

test.describe('Scoped visual change — 대상만 변하고 주변은 불변', () => {
  test('대상 요소 스냅샷 (변경 허용)', async ({ page }) => {
    await page.goto('/')
    await expect(page.getByTestId('target-card'))
      .toHaveScreenshot('target-card.png', { maxDiffPixelRatio: 0.01 })
  })

  // 단 Gotcha 4 대로 0 은 쓰지 마라 — anti-aliasing·폰트 렌더링 차이로 상시 실패한다.
  test('주변 영역 스냅샷 (변경 금지 — 실패 시 회귀)', async ({ page }) => {
    await page.goto('/')
    await expect(page.getByTestId('surrounding-panel'))
      .toHaveScreenshot('surrounding-panel.png', { maxDiffPixelRatio: 0.001 })
  })
})
Step 5-b · 조건부

결정 전파 테스트 생성

.design/decisions.yaml이 있을 때만 실행합니다. manifest 가 없으면 이 단계를 건너뛰되 "해당 없음" 이 아니라 "manifest 부재" 로 보고합니다 — 체커가 NO_MANIFEST + exit 3 을 내는 이유와 같습니다. 대상 0 건과 통과는 다릅니다.

manifest 가 있으면 decision_id 마다 required_surfaces[] 를 순회하며 surface 당 테스트 1 개를 생성합니다. 스키마와 커버리지 규칙 4 조는 ../../references/visual-change-protocol.md §6 이 정본이며 여기서 재정의하지 않습니다. 생성 규칙은 셋입니다.

1셋업

surface 의 route_or_entry · state · viewport_or_container 를 테스트 셋업에 그대로 옮깁니다.

2assertion 우선

assertions[] 를 golden 비교보다 먼저 실행합니다 — 빈 렌더가 baseline 으로 굳는 것을 막습니다.

3영역 분리

selectors[] 는 대상 locator 스냅샷에, 그 바깥은 주변 영역 스냅샷에 씁니다 (Gotcha 12 와 짝).

// tests/design/decision-DEC-20260813-001.test.ts — manifest 에서 생성
import { test, expect } from '@playwright/test'

test('DEC-20260813-001 → dashboard.desktop.main', async ({ page }) => {
  await page.setViewportSize({ width: 1440, height: 900 })   // viewport_or_container
  await page.goto('/dashboard')                              // route_or_entry
  // assertions[] — golden 비교보다 먼저 (Gotcha 11·14)
  const main = page.locator('main').first()
  await expect(main).toBeVisible()
  await expect(page.locator("[data-surface='group-list'] > *")).not.toHaveCount(0)
  expect((await main.boundingBox())?.height ?? 0).toBeGreaterThan(0)
  // golden — 위 assertion 을 통과한 뒤에만 의미가 있다
  await expect(main).toHaveScreenshot(
    'DEC-20260813-001/dashboard.desktop.main.png', { maxDiffPixelRatio: 0.01 }
  )
})
생성 후 커버리지 체커(§6)를 돌려 종료 코드 0 을 확인합니다. 종료 코드 2(SCHEMA_ERROR)는 입력 모양이 틀려 판정하지 못한 것이라 FAIL 줄 없이 violations=0 이 찍혀도 통과로 읽지 않습니다. 종료 코드 3(NO_SURFACE · NO_DECISION)은 NO_MANIFEST 와 같이 대상 0 건으로 보고합니다. golden 만 있고 assertions 가 빈 surface 가 남아 있으면 그것은 FAIL 이며, 테스트 파일을 만들었다는 사실이 커버리지를 대체하지 않습니다. excluded_surfaces 에 올라온 표면은 테스트를 만들지 않되 보고에는 이유와 함께 열거합니다.
Step 6

반응형 레이아웃 테스트 생성

프로젝트 디자인 시스템의 breakpoint를 사용해 가로 오버플로, 모바일 본문 크기, 이미지 고정 폭 오버플로를 검사합니다.

// tests/design/responsive.test.ts
import { test, expect } from '@playwright/test'

// 프로젝트 디자인 시스템의 breakpoint 사용
const breakpoints = [
  { name: 'sm', width: 640 },
  { name: 'md', width: 768 },
  { name: 'lg', width: 1024 },
  { name: 'xl', width: 1280 },
]

test.describe('Responsive Layout', () => {
  for (const bp of breakpoints) {
    test(`no horizontal overflow at ${bp.name} (${bp.width}px)`, async ({ page }) => {
      await page.setViewportSize({ width: bp.width, height: 900 })
      await page.goto('/')
      const scrollWidth = await page.evaluate(() => document.documentElement.scrollWidth)
      const clientWidth = await page.evaluate(() => document.documentElement.clientWidth)
      expect(scrollWidth).toBeLessThanOrEqual(clientWidth + 2) // 2px tolerance
    })
  }

  test('text remains readable on mobile', async ({ page }) => {
    await page.setViewportSize({ width: 375, height: 812 })
    await page.goto('/')
    const bodyFontSize = await page.evaluate(() => {
      const body = document.querySelector('body')
      return parseFloat(getComputedStyle(body!).fontSize)
    })
    expect(bodyFontSize).toBeGreaterThanOrEqual(14) // 최소 14px
  })

  test('images are responsive (no fixed width overflow)', async ({ page }) => {
    await page.setViewportSize({ width: 375, height: 812 })
    await page.goto('/')
    const images = await page.locator('img').all()
    for (const img of images) {
      const box = await img.boundingBox()
      if (box) {
        expect(box.width).toBeLessThanOrEqual(375)
      }
    }
  })
})
예시 코드의 sm 640, md 768, lg 1024, xl 1280은 자리 표시일 뿐입니다. 실제 생성 시 프로젝트 디자인 시스템에 정의된 breakpoint로 바꾸고, 임의로 320/768/1024를 넣지 않습니다 (Gotcha 6).
Anti-patterns

실패를 통과로 오인하는 패턴

왼쪽은 원본 Gotchas 가 금지하는 방식, 오른쪽은 원본이 요구하는 교정 방식입니다.

1baseline 생성 직후 green (Gotcha 10)

Bad

스냅샷이 없어 현재 화면을 baseline 으로 기록한 실행이 통과했으므로 시각 회귀 테스트가 작동한다고 보고합니다. 무엇과도 비교되지 않은 결과입니다.

npx playwright test tests/design/visual-regression.test.ts --update-snapshots → passed → "시각 회귀 테스트 통과"
Good

대상에 의도적 변형(예: 배경색 1 단계 변경)을 준 실행이 실패하는지 보고, 되돌린 뒤 통과까지 확인해 두 출력을 인용합니다.

1. baseline 기록 2. negative control → 실패해야 한다 3. 되돌리기 → 통과 4. 2 와 3 의 출력 인용

2스냅샷 비교만 있는 테스트 (Gotcha 11)

Bad

스크린샷 비교만 수행합니다. 렌더가 실패해 빈 화면이 캡처돼도 baseline 과 동일하면 통과하고, unbounded-height collapse 같은 결함이 그대로 지나갑니다.

await expect(page).toHaveScreenshot( `${pg.name}-${vp.name}.png`, { maxDiffPixelRatio: 0.01 } )
Good

핵심 요소 visible, 컨테이너 높이 > 0 assertion 을 스냅샷 비교 전에 실행합니다.

const main = page.locator('main, [role="main"]').first() await expect(main).toBeVisible() const box = await main.boundingBox() expect(box?.height ?? 0).toBeGreaterThan(0) await expect(page).toHaveScreenshot(...)

3전체 페이지 하나로 부분 변경 검증 (Gotcha 12)

Bad

"보더만 바꿨다" 를 전체 페이지 스냅샷 하나로 판정해 배경까지 변한 것을 구분하지 못합니다.

await expect(page).toHaveScreenshot(...)
Good

대상 locator 와 주변 영역을 분리합니다. 주변 스냅샷 실패는 회귀로 처리합니다.

await expect(page.getByTestId('target-card')) .toHaveScreenshot('target-card.png', { maxDiffPixelRatio: 0.01 }) await expect(page.getByTestId('surrounding-panel')) .toHaveScreenshot('surrounding-panel.png', { maxDiffPixelRatio: 0.001 })

4threshold 미설정 또는 0 (Gotcha 4)

Bad

픽셀 단위 비교에 threshold 를 두지 않거나, 주변 영역을 엄격하게 하려고 0 을 씁니다. anti-aliasing·폰트 렌더링 차이로 false positive 가 빈번해 상시 실패합니다.

threshold 없음 또는 0
Good

일반 스냅샷은 0.01, 변하지 않아야 하는 주변 영역은 대상보다 엄격한 0.001 을 씁니다.

{ maxDiffPixelRatio: 0.01 } { maxDiffPixelRatio: 0.001 }

5픽셀 비율만으로 색상 회귀 잡기 (Step 7)

Bad

negative control 이 실패하지 않는데 maxDiffPixelRatio 만 조정합니다. threshold 기본값 0.2 가 이미 관대한 편이라 미묘한 색상 변화는 픽셀 비율과 무관하게 통과합니다.

maxDiffPixelRatio 만 조정
Good

두 축을 각각 확인합니다. 색상 회귀를 잡으려면 같은 좌표 픽셀 간 색차 기준인 threshold 를 낮춥니다.

maxDiffPixelRatio — 달라도 되는 픽셀의 비율 threshold — 허용 색차, 낮춰서 색상 회귀 검출

6APCA로 합격 판정 (Gotcha 9)

Bad

APCA Lc 값을 PASS/FAIL 판정 기준으로 씁니다.

APCA Lc → PASS/FAIL
Good

WCAG 2.2 AA(4.5:1 WCAG2 공식)를 판정 기준으로 쓰고 APCA Lc 는 추가 정보 제공용으로만 포함합니다.

.withTags(['wcag2a', 'wcag2aa', 'wcag22aa']) APCA Lc → informational

7reduced motion에서 애니메이션 0개 요구 (Gotcha 13)

Bad

사용자 설정을 모든 애니메이션 제거로 해석하고 reduced-motion 테스트를 "애니메이션 개수 0" 으로 assert 합니다.

Good

이동감을 주는 모션이 사라지거나 opacity/dissolve 로 대체되었는지를 검증합니다.

transform: scale/translate 사라짐 또는 opacity/dissolve 로 대체

8golden 만 있는 결정 전파 테스트 (Gotcha 14)

Bad

surface 에 golden 만 있고 assertions 가 비어 있습니다. excluded_surfaces 에 이유 없이 빠진 표면도 커버리지 공백입니다.

golden: 있음 assertions: []
Good

assertions[] 를 golden 비교보다 먼저 실행하고, 커버리지 체커가 종료 코드 0 으로 끝나는지 확인합니다.

9스택·도구 전제 (Gotcha 1 · 6 · 8)

Bad

스택 감지 없이 Flutter 프로젝트에 Playwright 테스트를 만들고, breakpoint 에 임의로 320/768/1024 를 넣고, 시각 회귀에 Storybook 을 전제합니다.

pubspec.yaml → Playwright 테스트 breakpoint 320 / 768 / 1024 Storybook 전제
Good

Step 0 감지 결과를 따릅니다. Flutter 는 flutter-test 스킬로 넘기고, breakpoint 는 디자인 시스템 정의를 쓰고, Storybook 이 없으면 페이지 스크린샷으로 대체합니다.

pubspec.yaml + Flutter → flutter-test 스킬 디자인 시스템 breakpoint Storybook 없음 → Playwright 페이지 스크린샷

10스냅샷 존재를 사용자 관측으로 보고 (Gotcha 15)

Bad

채널 이름 없이 "스냅샷 있음" 을 PASS 로 적습니다. 사용자가 실패를 보고했는데 테스트 통과를 근거로 반박합니다.

2 단계가 실패하지 않으면 비교 기준이 너무 관대한 것입니다. 두 축을 각각 확인하십시오 — 둘은 다른 것입니다.

maxDiffPixelRatio

달라도 되는 픽셀의 비율입니다 (0~1, 기본 unset). 크게 잡으면 국소 변경이 묻힙니다.

threshold

같은 좌표 픽셀 간 허용 색차입니다 (YIQ 색공간, 0=엄격 ~ 1=관대, 기본 0.2). 기본값이 이미 관대한 편이라 미묘한 색상 변화는 픽셀 비율과 무관하게 통과할 수 있습니다. 색상 회귀를 잡으려면 threshold 를 낮춰야 하며, maxDiffPixelRatio 만 조정해서는 잡히지 않습니다.
