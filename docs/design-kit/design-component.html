Design Kit · Skill Guide

컴포넌트 카탈로그

반복되는 UI 요소를 컴포넌트로 정의하고 카탈로그로 묶는다. 확정된 시안에서 뽑거나 사용자가 지정한 요소를 받아 variant · 상태 · 토큰 매핑을 담은 디자인 스펙을 만든다. 코드는 쓰지 않는다 — 구현은 toolkit 플러그인이 맡는다.

스펙만, 코드 없음 12 섹션 스펙 DTCG v1 중괄호 참조 요청한 컴포넌트만 인자 [component-name or mockup-id]
Workflow

디자인 흐름의 마지막 단계

컨셉 · 토큰 · 시안이 있으면 자동으로 불러와 일관성을 지킨다. 카탈로그가 확정되면 각 스택의 toolkit 이 실제 코드로 옮긴다.

design-concept → design-system → design-mockup → design-component

이럴 때 부른다

  • 「컴포넌트 정의」 · 「컴포넌트 리스트」 · 「design component」
  • 「UI 컴포넌트 정리」 · 「컴포넌트 만들어줘」 · 「컴포넌트 카탈로그」
  • 확정 시안의 요소 ID 를 주며 컴포넌트로 만들어 달라고 할 때 (예: card-product-a3f2)

이럴 때는 부르지 않는다

  • 실제 코드 구현 — Flutter · React · CSS 컴포넌트 코드는 해당 toolkit 플러그인이 만든다
  • 요청하지 않은 컴포넌트를 카탈로그에 더 채우는 일 — 필요해 보이면 따로 제안만 한다
Core Principles

스펙을 쓰는 여섯 가지 원칙

Gotchas 13 개 가운데 산출물의 모양을 결정하는 것을 먼저 모았다. 전체 목록은 아래 체크리스트에 있다.

GOTCHA 1

스펙만 만들고 코드는 넘긴다

이 스킬의 산출물은 디자인 스펙이다. Flutter · React · CSS 컴포넌트 코드를 직접 만들지 않고 해당 toolkit 플러그인에 맡긴다.

출처: design-component SKILL.md
GOTCHA 3

토큰은 DTCG v1 중괄호로 참조한다

컬러 · 타이포 · 간격 · 라디우스를 전부 토큰에 매핑한다. 별칭은 {color.background.surface} 처럼 중괄호로 쓴다. 중괄호 없는 점 표기는 참조가 아니라 문자열 값으로 읽힌다.

출처: W3C DTCG v1 발표 (2025-10-28)
GOTCHA 12

요청한 컴포넌트 안에서만 완전하게

「버튼 정의해줘」 면 버튼만 스펙으로 만든다. 상태 · anatomy · 접근성을 다 채우라는 말은 그 컴포넌트 안의 완전성이지, 카탈로그에 컴포넌트를 더 넣으라는 뜻이 아니다.

출처: zeroheight Design Systems Report 2026
GOTCHA 10

여러 파트면 Compound + Slot

Dropdown · Select · Modal · Accordion 은 Context 로 상태를 나누는 Compound Component 패턴과 named slot 을 Anatomy 에 적는다. 옵션을 props 하나에 몰아넣는 「prop soup」 는 안티패턴이다.

출처: patterns.dev Compound Pattern (research-log §G)
GOTCHA 11

다크모드 토큰을 같이 적는다

Design Tokens 섹션에 light · dark 양쪽 semantic 토큰을 적는다. 순수 블랙 #000000 을 피하고, 채도를 낮추고, 표면 레이어는 밝기 차이로 가른다. hover · focus 배경 대비는 3:1 이상.

출처: Designing Scalable Accessible Dark Theme (research-log §H)
GOTCHA 8

접근성은 스펙의 한 섹션이다

인터랙티브 컴포넌트에는 WAI-ARIA 역할 · 속성, 키보드 인터랙션 표, 라벨링 요구사항을 넣는다. 접근성 섹션이 없는 스펙은 불완전하다.

출처: WAI-ARIA Authoring Practices — Patterns

Step 0

자동 감지 및 로드

이전 단계 산출물을 찾아 불러온다. design-concept · design-mockup 의 Step 0 과 같은 패턴이다.

# 감지 대상
.design/concept.md              → 컨셉 로드 (컬러/타이포/UI 패턴 방향)
**/theme/** **/tokens/**        → 디자인 토큰 로드
.design/mockups/*.html          → 확정 시안 로드
감지 결과하는 일
시안 있음시안에서 반복되는 UI 요소를 자동 식별해 제안한다
토큰 있음컴포넌트별 토큰 매핑을 자동으로 만든다
시안 · 토큰 둘 다 없음사용자가 컴포넌트 목록을 직접 지정한다
앱 코드 있음같은 역할의 기존 부품을 찾아 관례 표의 재사용 부품 칸에 남긴다

재사용 부품 칸에 적는 것

칸적는 값
심볼 이름앱 코드의 실제 이름
위치파일:줄
용도한 줄 설명

칸 정의는 시각 변경 프로토콜 §0 관례 표를 그대로 쓴다.

기존 부품을 다루는 규칙

  • 이미 있는 부품은 새 컴포넌트로 다시 정의하지 않고, 스펙에서 그 부품을 가리킨다
  • 코드 검색에서 나오지 않은 부품 이름은 쓰지 않는다
  • 같은 역할 기존 화면이 2 개 미만이면 찾은 것을 다 적고 관례 없음 — 같은 역할 기존 화면 N 개
  • 앱 코드가 아직 없으면 관례 없음 — 앱 코드 없음
Step 0 은 독립 Process 단계다 (SK-05 재발 방지). 자동 감지 로직을 Gotchas 나 다른 Step 의 하위 항목으로 내리지 않는다. 평가자는 「프로세스 단계」로 세는 섹션에서만 자동 로드를 지켰는지 판정한다.
Gotcha 13

시각 산출물 규약은 다시 정의하지 않는다

편집 전 확정 · 승인 기록 · 증거 채널의 정의와 숫자는 design-kit 공통 규약 references/visual-change-protocol.md 에 있다. 이 스킬은 그 규약을 인용만 한다.

§0

편집 전 확정 — 대상 · 되말하기 · 관례 표

파일을 만들거나 고치기 전에 바꿀 대상, 요청을 한 문장으로 되말한 것, 같은 역할 기존 화면의 관례 표를 응답에 남긴다. Step 0 의 재사용 부품 칸이 이 관례 표의 한 칸이다.

§4

승인 기록

사용자가 시안 · 컨셉을 확정하면 대화 기록이 아니라 파일로 남긴다. 경로 .design/approvals/{YYYYMMDD}-{대상}.md 와 최소 필드가 이 절에 있다.

§7

증거 채널

증거를 인용할 때 채널 이름(artifact_snapshot · dom_snapshot · browser_user_visible · device_user_visible)을 함께 적는다. 멀쩡한 스크린샷도 사용자가 그 화면에서 그것을 본다는 증명은 아니다.

Step 1

대상 파악

컴포넌트로 만들 대상을 세 가지 방식 가운데 하나로 정한다. 어느 방식이든 사용자가 지목한 범위를 넘지 않는다.

시안에서 추출

시안 ID 로 지정

예: 「card-product-a3f2 를 컴포넌트화해줘」. 뽑은 컴포넌트의 시안 ID 를 카탈로그에 기록해 출처를 추적한다 (Gotcha 4).

자동 식별

2 회 이상 반복 패턴 제안

시안에서 두 번 이상 반복되는 UI 패턴을 찾아 제안한다. 시안의 모든 요소를 자동으로 카탈로그에 넣지 않는다.

사용자 직접 지정

이름으로 지정

예: 「버튼, 카드, 입력 필드 정의해줘」. 지정한 세 개만 스펙으로 만든다.

범위가 모호하면 추측으로 넓히지 않고 한 줄로 묻는다. 다른 컴포넌트가 더 필요해 보이면 산출물에 넣지 말고 「Input · Card 도 함께 정의할까요?」 처럼 따로 제안한다.

Anatomy 에 적는 것 (Gotcha 7 · 10)

  • Dialog · Menu · Accordion 같은 복합 컴포넌트는 파트 계층을 적는다
  • 어떤 파트가 필수 · 선택인지, 어떤 파트가 상태를 갖는지 표시한다
  • 여러 파트로 된 컴포넌트는 Compound 구조(네임스페이스 API)와 named slot 을 반영한다

When to use 에 적는 것 (Gotcha 9)

  • 모든 컴포넌트에 쓸 때와 쓰지 않을 때를 둘 다 적는다
  • 유사 컴포넌트와 가르는 기준을 넣는다 — Menu vs Select, Dialog vs Sheet
Step 2-2

API Doc 헤더 (필수)

모든 컴포넌트 스펙 맨 위에 프로그래밍 언어 API 문서 형식의 헤더를 둔다. 설명과 각 옵션의 이름 · 타입 · 허용값 · 기본값 · 의미를 적는다. 헤더가 없는 스펙은 불완전하다 (Gotcha 6).

## Button

범용 액션 트리거 컴포넌트. 폼 제출, 네비게이션, 인라인 동작에 사용한다.

### When to use
- 사용자 액션을 트리거할 때 (제출, 확인, 취소)
- 인라인 동작 (삭제, 편집, 공유)

### When not to use
- 페이지 이동만 할 때 → Link 사용
- 토글 상태 전환 → Switch 또는 ToggleButton 사용

### Anatomy
- Root — 클릭 영역 전체
- LeadingIcon (선택) — 좌측 아이콘
- Label — 텍스트 라벨
- TrailingIcon (선택) — 우측 아이콘
- Spinner (조건부) — loading=true일 때 표시

Anti-patterns

자주 틀리는 스펙

Gotchas 가 막으려는 실수를 나란히 놓았다.

Bad — 중괄호 없는 참조

문자열 값으로 읽힌다

중괄호 없는 점 표기와 접두어 없는 value · type 키는 참조가 아니고 Tokens Studio · Style Dictionary 호환도 깨진다.

{ "bg": { "type": "color",
          "value": "color.background.surface" } }
Good — DTCG v1 별칭

다른 토큰을 가리킨다

$type · $value 키와 중괄호 참조를 쓴다. 커스텀 $ 접두어 키를 새로 만들지 않는다.

{ "bg": { "$type": "color",
          "$value": "{color.background.surface}" } }
Bad — prop soup

옵션을 props 하나에 몰아넣는다

<Select options={...} renderOption={...}
  showSearch groupBy="team" footerText="..." />
Good — Compound + Slot

파트를 네임스페이스로 나눈다

Select.Root
├── Select.Trigger
├── Select.Content
│   └── Select.Item
└── Select.Footer   (slot)
Bad — 카탈로그 임의 확장

「버튼 정의해줘」 에 Input · Card · Modal 까지

함께 필요할 것 같다는 이유로 요청하지 않은 컴포넌트를 산출물에 넣는다. 시안의 모든 요소를 자동으로 카탈로그화하는 것도 같은 실수다.

Good — 요청한 것만, 나머지는 제안

버튼 하나를 12 섹션으로 완전하게

산출물은 버튼 스펙뿐이다. 끝에 한 줄로 「Input · Card 도 함께 정의할까요?」 라고 따로 묻는다.

Bad — 지어낸 부품 이름

앱에 없는 부품을 스펙에 쓴다

코드를 검색하지 않고 그럴듯한 이름을 붙이거나, 이미 있는 부품을 새 컴포넌트로 다시 정의한다.

Good — 찾은 부품을 가리킨다

심볼 이름 · 파일:줄 · 용도

코드 검색에서 나온 부품만 재사용 부품 칸에 적고, 스펙은 그 부품을 가리킨다. 찾지 못하면 관례 없음 으로 이유를 적는다.

Gotchas

완료 전 체크리스트

스킬의 Gotchas 13 개를 그대로 옮겼다. 하나라도 빠지면 스펙이 불완전하다.

  • 1구현 코드를 만들지 않았다 — 스펙만 출력하고 코드는 toolkit 에 맡겼다
  • 2상태를 빠뜨리지 않았다 — default · hover · active · disabled, 버튼 · 카드는 loading 까지
  • 3모든 값을 토큰에 매핑했다 — DTCG v1 중괄호 참조, $value · $type
  • 4시안 ID 를 기록했다 — {컴포넌트명}-{해시} 로 출처 추적
  • 5커스터마이징 옵션을 검토했다 — 필요 없는 것만 뺐다
  • 6API Doc 헤더가 맨 위에 있다 — 이름 · 타입 · 허용값 · 기본값 · 의미
  • 7Anatomy 를 적었다 — 필수 · 선택 파트, 상태를 갖는 파트
  • 8접근성 섹션이 있다 — ARIA 역할 · 속성, 키보드 표, 라벨링
  • 9When to use / not 을 적었다 — 유사 컴포넌트와 가르는 기준 포함
  • 10Compound · Slot 을 반영했다 — prop soup 없음
  • 11light · dark 토큰을 둘 다 적었다 — 순수 블랙 없음, hover · focus 3:1 이상
  • 12요청한 컴포넌트만 정의했다 — 더 필요하면 따로 제안, 모호하면 한 줄로 확인
  • 13시각 산출물 규약을 인용만 했다 — 편집 전 확정 · 승인 기록 · 증거 채널은 visual-change-protocol 을 따른다
