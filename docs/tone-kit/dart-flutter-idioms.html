다른 스택 어댑터는 존재하지 않는다 — 위반 실측이 없기 때문이다

이 문서는 이 킷의 유일한 어댑터 근거 문서다. Rust · TypeScript 같은 다른 스택 어댑터는 해당 스택에서 위반이 실제로 관측된 적이 없으므로 만들지 않았다. 어댑터가 필요해지면 그 스택에서 위반이 실측된 뒤에 만든다 — 이 문서를 복제해 스택 이름만 바꾸는 방식은 실측 없는 규칙을 강제하는 것이 된다.

원칙 12개 — 강도 배지 포함

각 카드의 강도 배지는 두 종류다. SHOULD 는 공개 1차 출처(Dart/Flutter 공식 문서·린터 규칙)가 권고하는 항목이고, 관측 컨벤션 은 이 코퍼스에서 실측으로 확정된 항목이다. 배지를 무시하고 관측 컨벤션을 MUST 로 서술하면 다른 코퍼스에서 근거 없는 강제가 된다.

1

null 은 ?? · ?. · early return · 패턴 매칭으로 다룬다

SHOULD어댑터:dart-flutter

기본 도구는 넷이다 — ??, ?., early return, 패턴 매칭. 강제 ! 는 경계부에만 쓴다. 경계부란 assert 직후, JSON 파싱 직후처럼 non-null 이 이미 증명된 자리다.

흐름 중간의 if (x != null) f(x!) 는 컴파일러가 이미 아는 사실을 사람이 다시 단언하는 것이라 경계부가 아니다. 위젯 Props 에서 항상 넘기는 필드도 nullable + ! 조합이 아니라 required 로 선언한다 — nullable 로 열어 두고 호출부 전수가 값을 채우는 상태는 타입이 실제 계약보다 넓은 것이다.

→ Dart null safety → Dart patterns → Effective Dart — design
2

nullable 삽입 문법은 위치가 정한다

SHOULD어댑터:dart-flutter

같은 "null 이면 넣지 않는다"도 문법 위치마다 답이 다르다. 여기를 틀리면 컴파일이 안 되고, 그래서 ! 로 되돌아가는 회귀가 생긴다.

children: [header, ?trailing]              // 컬렉션 리터럴 — null-aware element (Dart 3.8+)
if (label case final text?) Text(text)     // statement / collection element — non-null 바인딩
style: custom ?? defaultStyle              // expression 위치 — if case 불가. 2분기는 삼항
final view = switch (state) { ... };       // 3분기 이상 — switch expression

if case 는 statement 와 collection element 위치에서만 쓸 수 있다. 2분기 null 체크에 switch expression 을 쓰지 않는다 — 삼항이 더 짧고 switch 는 분기 3개부터 이득이 난다. 같은 기준이 sealed class 에도 적용돼 variant 가 2개면 if 로 충분하다.

→ Dart collections → Dart branches → Dart class modifiers → prefer_spread_collections

4

반복 렌더는 builder delegate 로

관측 컨벤션성능 근거는 SHOULD 수준어댑터:dart-flutter

for (final x in items) Widget(...) 이나 items.map(...).toList() 로 children 을 채우면 화면 밖 항목까지 전부 즉시 빌드된다. 반복 렌더는 SliverChildBuilderDelegate · ListView.builder · ListView.separated 처럼 보이는 만큼만 만드는 delegate 로 쓴다. SingleChildScrollView + Column 과 ListView(children: [...]) 은 eager 다. shrinkWrap: true 는 lazy 가 아니라 크기 맞춤 옵션이며, .builder 와 같이 써도 전체 높이를 재느라 모든 아이템을 빌드해 laziness 를 깬다.

헤더 + 섹션 + 리스트가 섞이면 CustomScrollView 하나에 SliverToBoxAdapter(고정 영역)와 builder sliver(목록)를 넣는다. 화면당 스크롤 컨테이너는 하나이고 중첩 shrinkWrap 리스트로 쌓지 않는다.

예외는 하나다 — 콘텐츠가 전부 화면에 들어와 스크롤이 실제로 불필요하면 off-screen 이 없어 lazy 이득이 0 이므로 plain ListView 를 쓸 수 있다. 이 예외는 사람이 명시적으로 허락한 건에만 적용한다. "다 보이니까 괜찮다"를 스스로 판정하지 않는다.

5

leaf 토글은 상태를 자기가 소유한다

관측 컨벤션어댑터:dart-flutter

체크박스·스위치·슬라이더·세그먼트 탭처럼 자기 상태를 가진 leaf 는 HookWidget 내부 useState 로 값을 소유하고 onChanged 로 부모에 통지한다. setState 는 "possibly triggering rebuilds for the entire subtree rooted at this widget" 이므로, 상태를 상위에 둔 채 하위만 쪼개면 격리 효과가 상쇄된다. 그런데 useState 만으로는 부모의 외부 override(전체 선택 등)가 반영되지 않는다 — 초기값은 첫 build 에만 쓰이기 때문이다.

final value = useState(props.value);
useEffect(() {
  if (value.value != props.value) value.value = props.value;
  return null;
}, [props.value]);

hook 은 items.isEmpty 같은 early return 위에 둔다(rules of hooks). useEffect 는 post-frame 이라 부모 override 시 한 프레임 stale 후 반영되며, 이 지연은 수용된 trade-off 다. 그룹형 선택자(라디오)는 형제 해제에 부모 rebuild 가 필수라 격리 이득이 없으므로 controlled StatelessWidget 으로 남기고, 내부 토글 상태가 없는 표시 위젯과 외부 controller 입력은 이 원칙의 대상이 아니다. 정확성(override 반영)과 격리(perf)는 별개 축이라, 격리까지 원하면 상태를 provider 로 올리고 행 단위 ref.watch(provider.select(...)) 로 구독을 좁힌다.

6

파생 뷰 번들은 freezed state 클래스로 — 익명 Record 금지

관측 컨벤션어댑터:dart-flutter

provider 나 VM 이 노출하는 파생값 묶음을 익명 Dart 레코드(({int count, bool done}) view(Ref ref))로 반환하지 않는다. 이유는 셋이다. 타입명이 없어 의미와 재사용성이 약하고, 프로젝트 전역이 freezed state 컨벤션이라 표기가 갈리며, 레코드의 == 는 List 필드를 identity 로 비교해 freezed 의 깊은 컬렉션 비교와 rebuild 결과가 달라진다.

raw 상태와 파생 상태는 분리한다. 선택·입력 같은 raw 는 Notifier state({widget_prefix}XxxState), 그로부터 계산된 뷰 번들은 derived provider 가 반환하는 별도 freezed state({widget_prefix}XxxViewState) 다. 위젯이나 provider 표면에 노출되지 않는 함수 내부 국소 튜플은 레코드로 둬도 된다. 화면이 ref.watch 로 받는 로컬 변수명은 반환 타입과 무관하게 state 로 통일하고, notifier 를 함께 잡으면 ref.read(...notifier) 를 별도 변수로 분리한다.

7

콜백 typedef 는 위젯별 시맨틱으로 로컬 정의한다

관측 컨벤션어댑터:dart-flutter

위젯이 노출하는 각 콜백 prop 은 자기 의미를 드러내는 typedef 로 선언한다. generic 프리미티브 typedef 를 prop 타입으로 직접 재사용하면 타입에서 의미를 읽을 수 없다 — 한 아이템의 onVisibleChanged · onFwUpdateChanged · onPairingChanged 가 전부 {widget_prefix}SwitchChanged 로 같아지는 상태가 그 증상이다.

소유권 규칙은 하나다. typedef 는 그 콜백의 의미 원천 위젯이 같은 파일 top-level 에 정의하고, 상위 컴포지트와 화면은 import 해서 쓴다. 의미 원천은 그 콜백이 제어하는 실제 UI 를 그리는 위젯이며, forward 만 하는 상위는 새로 정의하지 않는다. 프리미티브 위젯(switch/button/checkbox/radio/slider)은 자기 base typedef 를 계속 소유하고, 시맨틱 typedef 는 함수 시그니처가 같아 base prop 으로 forward 할 때 구조적으로 대입된다. 공유 typedef 파일(*_typedef.dart 류)은 만들지 않으며, 같은 이름 typedef 를 co-import 되는 두 파일에 각각 정의하는 것도 금지다.

8

/// 는 계약이 있을 때만

SHOULD어댑터:dart-flutter한국어

주석 문법의 기본값은 // 다. /// 는 dartdoc 이 수집하는 API 문서용이므로 세 자리에만 쓴다 — public 메서드의 파라미터·반환값 블록, 진짜 계약과 제약(textStyle 을 지정하면 textColor 가 무시되는 식의 오용 유발 규칙), 파일 헤더 관례.

커버리지 판정은 레이어가 아니라 로직 유무로 한다. provider · model · service · repository · util 뿐 아니라 화면·뷰의 핸들러·리스너 헬퍼도 로직이 있으면 doc 을 단다. 면제되는 것은 build 와 자명한 getter 뿐이고, private 도 자명하지 않으면 단다. 화면·VM 메서드 doc 을 "화면이니까"라는 이유로 떼는 것은 컨벤션 이탈이다.

필드 /// 는 비자명한 계약이 있을 때만 허용한다. 이름을 한국어로 옮기기만 하는 자명한 필드 doc 은 금지이며, 이는 antipattern-catalog.md 의 A 카테고리다. freezed 는 constructor parameter 의 /// 를 property 와 class 레벨로 전파하므로 자명한 필드에 붙이면 생성 코드까지 오염된다.

본문은 한두 문장으로 끝낸다. 정책: · 참고: · 주의: 같은 본문 내 섹션 헤더와 알고리즘 단계 나열은 doc 이 아니라 설계 문서의 몫이다. [] 대괄호 링크는 파라미터 선언부에서 의무이고 본문에서는 식별자 언급이 꼭 필요할 때만 쓴다. 라벨 표기와 본문 문체는 한국어 축이므로 korean-technical-writing.md 를 참조한다 — 이 문서는 표기를 다시 정의하지 않는다.

expression body 를 기본값으로, 1회용 로컬 변수는 인라인한다

SHOULD어댑터:dart-flutter

단일 expression 으로 표현되는 함수·콜백은 => expression body 로 쓴다. block body 는 분기가 있거나 statement 가 둘 이상일 때만이다. 로컬 변수가 한 곳에서만 쓰이면 선언 자체가 노이즈이므로 사용처에 인라인한다 — 메서드 반환값도 같아서, 한 번 쓰고 마는 final thumbnail = _thumbnail(); 보다 호출을 그 자리에 두는 편이 읽기 경로가 짧다. cascade(..)는 같은 참조에 연속 호출할 때만 쓰고, extension 은 짧고 명확한 도메인 어휘만 붙여 formatter·helper dumping ground 로 만들지 않는다.

Notifier 비대화를 막는다 — 상태 전이는 단일 reducer 로

관측 컨벤션어댑터:dart-flutter

Notifier 파일 하나에 enum + freezed 모델 + extension + Notifier 본체 + 헬퍼를 다 넣지 않는다. 1000줄을 넘으면 state 모델 · helper extension · Notifier 본체(실행 흐름과 reducer 만) 세 파일로 분할한다. 다만 비대화의 실제 원인은 줄 수가 아니라 조합 폭발이다.

  • ●_notifyXxxStarted/Progress/Completed/Failed/Cancelled 류 status 별 헬퍼 다발은 _setXxxState({required status, double? percent, String? message, T? result}) 단일 reducer 로 통합한다. status 5종 × sub-state 3종이면 헬퍼가 15개로 늘어난다.
  • ●isIdle · isRunning · isCompleted 같은 extension getter 를 sub-state 마다 양산하지 않는다. 호출부에서 enum 을 직접 비교하는 편이 명확하고, 정말 자주 쓰이는 1~2개만 추출한다.
  • ●호출자가 쓰지 않는 저수준 메서드를 public 으로 노출하지 않고, 미래 확장을 가정한 boilerplate 도 만들지 않는다. 통합 실행 흐름만 public 이고 그 안의 단계는 private 이거나 service 다.

비동기 진행 UI 도 같은 축이다. 다이얼로그 progress 용으로 ValueNotifier 를 새로 만들어 ValueListenableBuilder 를 중첩하지 않고, provider state 에 progress 를 넣은 뒤 ref.listen 으로 다이얼로그를 push/pop 한다.

Props 규칙은 두 벌이다 — 신규 설계와 기존 위젯 제거는 스코프가 다르다

관측 컨벤션어댑터:dart-flutter

두 규칙을 하나로 합치면 신규 위젯에 제거 기준을 적용하거나 리팩토링에서 설계 기준만 확인하고 끝내는 사고가 난다. 스코프를 명시해 둘 다 유지한다.

(a) 신규 위젯 Props 설계 시 — 항상 넘기는 필드는 required 로 선언하고 nullable + ! 강제 캐스트 조합을 만들지 않는다. 미사용 Props 는 처음부터 만들지 않으며 "나중에 쓸 수 있으니까"는 보존 사유가 아니다. 프로젝트에 이미 있는 장식 위젯이 있으면 Props 로 노출하지 말고 위젯 내부에서 직접 쓴다. 래퍼 위젯은 child 슬롯을 그대로 전달하고, 소비자가 어떤 레이아웃을 쓸지 추측해 Stack 이나 클리핑을 미리 감싸지 않는다.

(b) 기존 위젯 리팩토링 시 Props 제거 판정 — 제거 후보는 실제 화면 호출자가 0곳인 스타일 Props, 또는 호출자가 1곳뿐인데 매번 고정 장식값(색·radius·배경·fit)을 넘기는 Props 다. 후자는 범용성이 0이므로 build 에 값을 인라인하고 Props 에서 뺀다. 유지 대상은 치수 표준 옵션(width/height/size), slider 의 min/max, 동적값, required 핵심 데이터, 호출자 2곳 이상이며, 치수는 호출자 0건에 기본값과 중복이어도 제거하지 않는다. 사용 여부 판정에 공통 위젯 pass-through 와 dev 쇼케이스를 포함하지 않는다. 보고는 카운트가 아니라 각 호출자가 실제로 넘기는 값을 코드 그대로 인용한다.

bare catch (e) 는 이 코퍼스의 의도된 컨벤션이다

관측 컨벤션공개 1차 출처 없음어댑터:dart-flutter

} catch (e) { / } catch (e, st) { 처럼 on 절 없는 catch 는 실수가 아니라 선택이다. 목적은 Dart 의 모든 throwable(Object 루트 — Exception · Error · 임의 객체)을 전부 잡아 상태나 로그로 흡수하는 것이고, provider·VM 의 에러 싱크가 대표 사례다. on Exception 으로 좁히면 커버리지가 줄 뿐 늘지 않는다 — 비-Exception 객체를 던지는 경로(예: 응답 에러 필드 타입이 Object? 인 HTTP 레이어)가 있으면 좁힌 catch 가 그 throw 를 놓쳐 동작이 깨진다.

리뷰나 QA 가 bare catch 를 지적하면 무효 판정으로 처리한다. 이 규칙은 코퍼스 실측에 근거하며 공개 1차 출처가 없다. 다른 코퍼스로 옮길 때는 그 코퍼스에서 같은 비율이 관측되는지 먼저 확인하고, 확인 없이 이관하지 않는다.

◇ 프로젝트 실측 — bare catch (e) 27건 vs on Exception 3건 (2026-06-26) ◇ 공개 1차 출처 없음 — 링크할 URL 이 존재하지 않는다
강도 경고 — 권고를 강제로 승격하지 않는다

이 문서의 원칙 12개 중 SHOULD 는 4개(1 · 2 · 8 · 9) 뿐이고 나머지 8개는 관측 컨벤션이다. 공식 문구가 권고 수준인 항목을 MUST 로 바꿔 서술하면 다른 코퍼스에서 근거 없는 강제가 되고, 리뷰에서 무효 지적을 유발한다.

!

"모든 하위 위젯 별도 파일" 은 관측 컨벤션이다

파일 분할을 MUST 로 서술하지 않는다. 이 문서가 실제로 확정한 것은 Notifier 1000줄 초과 시 3파일 분할(원칙 10, 실측) 하나이고, 위젯을 별도 파일로 쪼개는 것 자체는 공개 1차 출처가 권고 수준이거나 없다.

게다가 파일을 나눈다고 rebuild 가 끊기지 않는다 — 격리 조건(동일 인스턴스, runtimeType + key)은 extraction-thresholds.md 원칙 5 가 소유한다. 상태 소유를 안 고친 채 파일만 늘리면 프레임 비용은 그대로다.

!

원칙 4 는 근거가 두 겹이다

lazy 렌더링은 성능 근거만 SHOULD 수준(Flutter 공식 performance 문서)이고, "화면당 스크롤 컨테이너 1개" 같은 구조 규칙은 관측 컨벤션이다. 두 겹을 하나로 뭉뚱그려 전부 MUST 로 쓰면 예외 판정(스크롤이 실제로 불필요한 화면)이 사라진다.

예외는 사람이 명시적으로 허락한 건에만 적용한다. 에이전트가 "다 보이니까 괜찮다"를 스스로 판정하지 않는다 — 이것이 이 원칙의 유일한 escape hatch 이자 오남용 지점이다.

!

원칙 12 는 공개 1차 출처가 아예 없다 — 이관 전 실측 필수

bare catch 컨벤션의 근거는 실측 비율(27 vs 3)이 전부다. 다른 프로젝트에 그대로 옮기면 실측 없는 규칙을 강제하는 것이 된다. 킷이 이 규칙을 켤 때는 대상 코퍼스에서 완료 게이트 7번 grep 을 먼저 돌려 같은 비율이 나오는지 확인한다.

코드 대비 — before / after

가장 자주 되돌아가는 네 지점. 왼쪽 형태를 코퍼스에서 발견하면 오른쪽으로 교체한다.

✗ before — 컴파일러가 아는 사실을 재단언
원칙 1경계부 아님
if (x != null) f(x!)

흐름 중간의 ! 다. 경계부(assert 직후, JSON 파싱 직후)가 아니므로 강제 캐스트의 정당성이 없다.

✓ after — 패턴 매칭으로 바인딩
if case final v?
if (label case final text?) Text(text)

! 가 사라진다. 단 if case 는 statement · collection element 위치 전용이라 expression 자리에서는 ?? 나 삼항으로 간다.

✗ before — 트릭성 체이닝 / 수동 SizedBox
원칙 3인지 비용 과다
children: sections.map(_body)
  .expand((w) => [divider, w]).skip(1).toList()
children: sections.indexed.expand((r) { ... }).toList()
children: [a, SizedBox(width: {TokenClass}.w10), b]

의도가 코드 형태에서 읽히지 않고, 항목이 늘 때마다 삽입 위치를 사람이 관리해야 한다.

✓ after — 프레임워크 파라미터
spacing:separatorBuilder
Column(spacing: {TokenClass}.w10, children: [a, b])
ListView.separated(
  separatorBuilder: (_, __) => divider,
  itemBuilder: ...,
)

고정 gap 은 spacing:, 리스트 separator 는 separatorBuilder. 루프마다 같은 위젯(divider)은 로컬 변수로 한 번 만들어 재사용한다.

✗ before — eager 렌더
원칙 4화면 밖까지 빌드
SingleChildScrollView(
  child: Column(children: [
    for (final x in items) Widget(x),
  ]),
)
ListView(shrinkWrap: true, children: items.map(...).toList())

shrinkWrap: true 는 lazy 수단이 아니라 크기 맞춤 옵션이다. .builder 와 같이 써도 전체 높이 측정이 laziness 를 깬다.

✓ after — builder delegate
CustomScrollView스크롤 컨테이너 1개
CustomScrollView(slivers: [
  SliverToBoxAdapter(child: header),   // 고정 영역
  SliverList(delegate: SliverChildBuilderDelegate(...)),
])

헤더 + 섹션 + 리스트가 섞이면 CustomScrollView 하나로 합친다. 중첩 shrinkWrap 리스트로 쌓지 않는다.

✗ before — useState 만, 동기화 없음
원칙 5외부 override 미반영
final value = useState(props.value);
// 부모의 "전체 선택" 이 화면에 반영되지 않는다
// 초기값은 첫 build 에만 쓰이기 때문

정확성 결함이다. 반대로 상태를 부모가 소유하면 토글 한 번에 subtree 전체가 rebuild 된다.

✓ after — useEffect 동기화
1프레임 stale 수용
final value = useState(props.value);
useEffect(() {
  if (value.value != props.value) value.value = props.value;
  return null;
}, [props.value]);

hook 은 early return 위에 둔다. 격리까지 원하면 상태를 provider 로 올리고 ref.watch(provider.select(...)) 로 구독을 좁힌다.

Gotchas — 개정 이력이 뒤집힌 지점

이 문서에서 가장 사고가 잦은 6가지. 특히 앞 두 항목은 옛 규칙이 남아 있고 뒤의 것이 승이라, 옛 예시를 다시 끌어오면 규칙이 파일마다 갈린다.

1

리스트 빌딩 규칙은 개정 이력이 뒤집혀 있다

원본 규칙 세트의 리스트 빌딩 절은 for-in 과 .indexed.map().toList() 로 children 을 채우는 것을 권장했지만, 이후 lazy 렌더링 절이 이를 전면 금지했다. 뒤의 것이 승이다. 옛 절에서 살아남은 것은 spacing: 사용과 함수형 체이닝 금지뿐이고, children 을 어떻게 만드는가는 builder delegate 가 지배한다. 옛 예시를 다시 끌어오지 마라.

2

useValueChanged 인용도 폐기됐다

상태 동기화 훅으로 useValueChanged 를 권고한 조항은 2026-06-22 에 useEffect 로 번복됐다. 근거는 성능이 아니라 프로젝트 일관성이며, 1프레임 stale 은 수용된 비용이다. 두 훅을 코퍼스에 섞어 두면 동기화 패턴이 파일마다 갈린다.

3

- 반환값: 없음 을 노이즈로 보고 지우지 마라

삭제 지시가 남아 있는 옛 문서를 보고 정리하면 "doc 이 없는 것"과 "반환값이 없는 것"을 구분할 수 없게 된다. 유지가 확정된 판정이고, 표기 규칙 자체는 korean-technical-writing.md 가 소유한다.

4

_build* grep 히트는 위반 건수가 아니다

이 문서는 접두사를 금지 목록에 올리지만, 인라인할지 위젯으로 승격할지의 판정식은 extraction-thresholds.md 와 antipattern-catalog.md I 카테고리에 있다. 히트를 세어 그대로 보고하면 추출이 정당한 건까지 위반으로 집계된다.

5

위젯 클래스로 뺐다고 rebuild 가 끊기지 않는다

격리 조건(동일 인스턴스, runtimeType + key)은 extraction-thresholds.md 원칙 5 에 있다. 상태 소유를 안 고친 채 파일만 늘리면 프레임 비용은 그대로다.

6

bare catch 컨벤션은 이 코퍼스 한정이다

실측 비율(27 vs 3)이 근거의 전부이고 공개 1차 출처가 없다. 다른 프로젝트에 그대로 옮기면 실측 없는 규칙을 강제하는 것이 된다. 킷이 이 규칙을 켤 때는 대상 코퍼스에서 같은 grep 을 먼저 돌린다.

7

다른 스택 어댑터를 이 문서에서 복제하지 마라

Rust 나 TypeScript 어댑터가 필요해지면 그 스택에서 위반이 실제로 관측된 뒤에 만든다. 코어 원칙은 extraction-thresholds.md 와 antipattern-catalog.md 가 이미 스택 무관으로 들고 있으므로, 어댑터는 문법 관용구와 슬롯 값만 갖는다.
