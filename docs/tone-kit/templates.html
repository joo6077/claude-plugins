골격이 이미 있는데 매번 새로 지어내는 것을 잡는다. 파일 헤더 · doc 주석 · typedef · 원장 · 브리핑 표는 형식이 확정돼 있고, 형식이 흔들리면 diff 노이즈와 재개 불능이 따라온다. 6종의 골격 전문을 그대로 싣는다 — 복붙해서 {...} 자리만 채우면 된다. 각 템플릿에 실제로 났던 사고를 붙였다. 그 사고가 그 템플릿이 존재하는 이유다. v0.1.0 · 최종 갱신 2026-09-02

여는 사고 — 골격을 옆 파일에서 복사하면 생기는 일
before 옆 파일에서 헤더를 복사했다
/// - 작성자  : 김이전

복사 원본의 작성자가 그대로 따라왔다. 헤더가 잡아야 할 유일한 정보(누가 왜 만들었나)가 거짓이 된 상태로 저장소에 남는다.

after git config user.name 을 읽어 채운다
/// - 작성자  : 박현재

골격은 복사하되 값은 감지해서 채운다. 이 페이지의 모든 골격이 같은 원칙 위에 있다 — 형식은 재사용 자산, 값은 프로젝트 소유.

강도 라벨(MUST · SHOULD · 관측 컨벤션 · 합성)의 뜻은 맨 아래 강도 표기 에 있다.

⚠️ 컴포넌트 골격과 상태 컨테이너 골격은 이 킷에 없다

이 킷이 소유하지 않는다. 스택 킷이 소유한다. 위젯 골격(typedef + freezed Props + Hook 3요소)은 flutter-toolkit templates/widget-freezed-props.md, provider / state 골격은 flutter-toolkit templates/provider-riverpod.md 로 이관됐다.

이 킷은 그 골격 위에 헤더 · doc · typedef 를 얹는다. 스택이 바뀌면 컴포넌트 골격은 통째로 갈리지만, 아래 6종은 어댑터 슬롯(스택별 문법을 갈아 끼우는 자리 — 골격은 그대로 두고 주석 문법과 라벨만 바뀐다)만 교체하면 그대로 산다.

골격은 만드는 순간이 정해져 있다. 그 순간을 놓치면 골격이 아니라 사후 정리 작업이 된다.

골격 카탈로그 — 전문 6종

각 골격은 전문이다. 요약하거나 발췌하지 않았다. 복사한 뒤 {...} 자리만 채우면 된다. 골격 바로 아래에 그 자리에 무엇을 채우는지가 표로 붙어 있다.

1

파일 헤더

MUST 관측 컨벤션 [코어] 재사용 빈도 1위

수기로 새 파일을 만들 때마다 붙인다. 코드 생성기 산출물에는 붙이지 않는다.

파일 헤더 골격 (전문) dart 
/// ----------------------------------------------------------------------------
/// - {label_file}  : {파일명}
/// - {label_desc}   : {한 줄 설명}
/// - {label_author}  : {현재 git user.name}
/// - {label_screen} : {화면 식별자 또는 없음 표기}
/// - {label_ref}    : {참고 URL 또는 없음 표기}
/// - {label_history} :
///   - {YYYY-MM-DD} : {최초 생성}
/// ----------------------------------------------------------------------------
자리필수채우는 값
{label_*}필수라벨 문자열. 언어 의존 상수이며 locale-korean.md 가 소유한다
{파일명}필수실제 파일명. 리네임하면 같이 고친다
{한 줄 설명}필수책임 한 줄. 파일명 한국어 번역 금지
{현재 git user.name}필수git config user.name 을 읽어 채운다
{화면 식별자} · {참고 URL}선택식별자 상수가 코드에 있으면 생략. 참고는 없으면 필드를 지운다
{YYYY-MM-DD}필수날짜 + 변경 요지. 여러 명이 만졌으면 항목마다 작성자 병기
before / after — 설명 필드
before 파일명을 한국어로 옮기기만 했다
/// - 설명   : 유저 프로필 카드

파일명이 이미 말하는 것을 되풀이했다. 정보량 0 이고 유지보수 대상만 하나 늘었다.

after 이 파일이 무엇을 책임지는지가 남는다
/// - 설명   : 프로필 요약 카드. 편집 진입점과 상태 배지를 함께 노출

코드에서 복원되지 않는 정보만 담았다. 열지 않아도 이 파일의 경계가 보인다.

실측

수기 작성 파일 290개 중 287개(99%). 재사용 빈도 1위. 구분선은 위아래 모두 234건 · 아래만 · 없음 3건 세 변종이 공존한다.

왜

헤더가 잡는 것은 "누가 왜 만들었나" 하나다. 이 정보는 코드에서 복원되지 않고 blame 은 포맷 커밋에 오염된다. 반대로 코드에서 복원되는 것(클래스 목록, 구현 요지)을 넣으면 그 순간부터 썩는다.

주의

작성자를 옛 파일에서 복사하는 사고가 실제로 났다. 스캐폴딩할 때 git config user.name 을 읽어라. 구분선 변종이 한 프로젝트에 섞이면 그 자체가 일관성 결함이니 하나를 고르고 길이까지 고정한다.

강도 · 출처

자화자찬 헤더("AI 기반", "자동 생성") 금지는 core-comment.md C-13 MUST. 고정 필드만 담고 구현 메모를 섞지 않는 규칙은 C-14 관측 컨벤션(공개 출처 없이 프로젝트 실측만 있는 규칙 — 준수 강도가 낮다는 뜻이 아니다). 라벨 부분 변경 금지는 locale-korean.md K-07 관측 컨벤션.

doc 주석 3변종 (Dart/Flutter)

MUST 관측 컨벤션 [코어] [어댑터:dart-flutter]

로직 · 부수효과가 있는 메서드와 공개 API 계약에 단다. build() 와 한 줄 위임 wrapper 에는 달지 않는다.

변종 1 — 반환값이 있는 메서드 dart 
/// {한 줄 요약. 무엇을 하는가.}
///
/// {선택: 언제 쓰는가 / 부수효과 / 제약. 없으면 이 블록 생략.}
///
/// - [{param}]: {설명}
/// - {label_return}: {반환 조건과 의미}
Future<bool> {methodName}({Type} {param}) async {
변종 2 — void + 파라미터 있음 dart 
/// {한 줄 요약}
///
/// - [{param}]: {설명}
/// - {label_return}: {label_void}
void {methodName}({Type} {param}) {
변종 3 — void + 파라미터 없음 dart 
/// {한 줄 요약}
///
/// - {label_return}: {label_void}
void {methodName}() {
자리채우는 값
{한 줄 요약}무엇을 하는가. 이름 번역이면 지운다
{선택 설명 블록}언제 쓰는가 / 부수효과 / 제약. 없으면 통째로 생략
{param}실제 선언 식별자. 철자가 틀려도 컴파일은 통과한다
{label_return} · {label_void}반환값 라벨과 void 표기. 언어 의존 상수이며 프로젝트 전체가 한 표기로 통일
before / after — 요약과 반환값
before 이름 번역 + 미기재 표기 잔존
/// 연결 상태를 확인한다.
/// - [timeout]: 타임아웃
/// - 반환값: N/A

요약이 메서드 이름의 한국어 번역이고, 파라미터 설명이 파라미터 이름의 번역이다. 반환값 자리에는 N/A 가 남아 계약 정보가 0 이다.

after 요약은 언제·왜, 반환값은 조건과 의미
/// 재연결 판단에 쓰는 헬스체크. 실패해도 예외를 던지지 않는다.
///
/// - [timeout]: 이 시간을 넘기면 실패로 간주
/// - 반환값: 응답이 정상이면 true

호출자가 읽어야 할 이유가 생겼다. 예외를 던지지 않는다는 제약과 true 의 조건은 시그니처에 없는 정보다.

줄 순서 고정 — 요약 → 빈 /// → 선택 설명 → - [param]: 목록(선언 순서) → - {label_return}: 은 항상 마지막.
완료 전 대조 — 네 항목 모두 0이어야 한다
  • 1{label_return}: N/A 잔존
  • 2로직 메서드에 /// 누락
  • 3- [param]: 만 있고 - {label_return}: 없음
  • 4doc 본문 안 섹션 헤딩 (/// 정책:, /// 참고:, /// 주의:)
실측

반환값 줄 577건 · 파라미터 줄 788건. void 메서드에 반환값 줄을 남긴 형태가 246건.

왜

doc 은 호출자가 읽는 계약이다. 시그니처가 이미 말하는 것을 되풀이하면 계약 정보는 0인데 유지보수 대상만 는다. 라벨을 하단 블록에 고정하는 이유는 grep 게이트가 성립하려면 표기가 하나여야 하기 때문이다.

주의

{label_return} 표기를 바꾸려면 전수 치환한다. 부분 변경하면 대조 grep 이 조용히 통과한다. void 에 반환값 줄을 남기는 것은 노이즈가 아니라 이 코퍼스의 관례(246건)이며, 반대로 정한 프로젝트도 유효하되 전수 일관해야 한다.

강도 · 출처

공개 API 는 doc 으로 계약을 쓴다가 core-comment.md C-06 MUST. 로컬 구현 세부를 doc 으로 감싸지 않는다가 C-17 관측 컨벤션. 라벨 부분 변경 금지는 locale-korean.md K-07 관측 컨벤션.

시맨틱 typedef (Dart/Flutter)

SHOULD 관측 컨벤션 합성 [어댑터:dart-flutter]

Props 필드 타입에 함수 시그니처를 직접 쓰려는 순간, 그 자리가 typedef 를 만들 자리다.

시맨틱 typedef 골격 (전문) dart 
typedef {widget_prefix}{Meaning}{Event} = void Function({T} value);
typedef {widget_prefix}{Meaning}{Event} = void Function();
typedef {widget_prefix}{Meaning}Of<T> = String Function(T item);
자리채우는 값
{widget_prefix}프로젝트 컨벤션의 위젯 접두사. 킷이 정하지 않는다
{Meaning}무엇에 대한 콜백인가 (도메인 용어)
{Event}무슨 일이 일어났는가. 프레임워크가 이미 정한 어휘를 쓴다 — onChanged · onTapDown · onLongPressStart · onSubmitted. 공식 어휘에 없는 도메인 이벤트만 프로젝트가 명명한다 (N-12 · D-15)
{T}호출부마다 타입이 다를 때만 제네릭
before / after — 이름에 의미가 있는가
before 시그니처를 이름으로 옮기기만 했다
typedef BoolCallback = void Function(bool value);
typedef VoidCb = void Function();

타입이 이미 말하는 것을 이름이 되풀이한다. 무엇이 바뀌었는지가 없다 — 호출부는 그 bool 이 무엇인지 알려고 위젯 구현을 열어야 한다.

after 이름에 의미와 이벤트가 있다
typedef {widget_prefix}SwitchChanged = void Function(bool value);
typedef {widget_prefix}SelectChanged<T> = void Function(T value);

도메인 용어(Switch · Select)와 이벤트(Changed)가 이름에 있다. 이름값은 한 줄이고 회수는 호출부 전부에서 일어난다.

소유권 — typedef 는 어디에 두는가

typedef 는 그 의미가 생겨난 위젯의 파일에 둔다. 공유 typedef 파일을 만들면 어느 위젯의 계약인지 추적이 끊긴다. 시그니처가 같아도 의미가 다르면 다른 typedef 이고, 의미 원천이 옮겨가면 typedef 도 같이 옮긴다.

실측

51 선언 / 32 파일. 전체 90 선언 중 26건은 FFI 바인딩이며 이 규칙의 대상이 아니다.

왜

콜백 prop 은 위젯 계약의 절반이다. 타입 자리에 void Function(bool) 이 있으면 호출부는 그 bool 이 무엇인지 알려고 위젯 구현을 열어야 한다. 이름값은 한 줄이고 회수는 호출부 전부에서 일어난다.

주의

typedef 를 만들고 Props 필드 타입만 바꾼 채 호출부를 안 고치면 반쪽이 된다. FFI 시그니처는 이 규칙으로 개명하지 마라 — 별도 관례를 따른다.

강도 · 출처

조립 형식의 prefix / suffix 는 킷이 아니라 프로젝트가 소유한다가 core-naming.md N-11 관측 컨벤션. 외형이 아니라 역할을 이름에 담는다가 N-01 SHOULD. 레이아웃 모양어 제한(N-02~N-06)은 합성(여러 디자인 시스템 어휘를 대조해 만든 규칙 — 단일 권위 출처가 없다).

붙이는 순간 검증 불가능한 주장이 된다. 근거는 코퍼스 실측 건수뿐이고 그것으로 충분하다. 이 페이지의 모든 골격이 관측 컨벤션 또는 프로젝트 실측을 근거로 삼으며, 인용 가능한 외부 URL 이 하나도 없다 — 그것이 이 문서의 정확한 상태이지 결함이 아니다.

쓰기 전 체크 — 골격을 망치는 6가지
  • 1 골격과 함께 값을 복사하지 마라 — 헤더의 작성자, 오버레이의 확정값, 원장의 기준 커밋은 전부 감지하거나 사람이 확정하는 값이다. 골격만 재사용 자산이다.
  • 2 라벨 상수를 부분 변경하지 마라 — {label_return} 같은 언어 의존 상수를 일부만 바꾸면 대조 grep 이 조용히 통과한다. 바꾸려면 전수 치환이다.
  • 3 확인이 필요한 값에 날짜를 빠뜨리지 마라 — 결정론적 감지값은 코드가 고쳐주지만 관례 6종은 낡아도 조용히 틀린다. 날짜가 유일한 신선도 신호다.
  • 4 범위 밖 위반을 그 자리에서 고치지 마라 — 원장의 범위 밖 발견 표에 적는다. diff 가 승인 범위를 벗어나면 리뷰 자체가 성립하지 않는다.
  • 5 제안과 실행을 한 턴에 붙이지 마라 — 브리핑 표는 편집 전에 낸다. 붙이는 순간 사용자가 항목 단위로 거부할 자리가 사라진다.
