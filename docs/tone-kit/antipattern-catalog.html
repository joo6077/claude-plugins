A~J 카테고리 요약

코드 · 이름 · 처리 · 강도 · 축 · 검색 패턴의 6열 SSOT. H 행만 보존이고 나머지 9행이 위반이다. 강도는 세 등급이다 — MUST 공식 문서가 금지·강제하거나 예외가 없음 · SHOULD 권고 수준, 명시 예외 존재 · 관측 컨벤션 공개 근거 없음, 실측만 존재.

코드이름처리강도축검색 패턴
A이름 번역 주석삭제 (또는 개명) MUST 코어 한국어 [a-zA-Z0-9_?],\s*//\s*[가-힣]
B템플릿 마커삭제 (예외 없음) MUST 코어 uniq -c | sort -rn 전역 빈도 집계

E접두사 fallback 변수명개명 (호출부 전수 동반) 관측 컨벤션 코어 \b(effective|resolved)[A-Z]
F구분선 블록삭제 MUST 코어 ^\s*//\s*[-=]{5,}

J중복 구현공통 요소로 수렴 SHOULD 코어 + 프로젝트 파라미터 공통 위젯 목록을 채운 뒤에만 생성 가능

검색 패턴은 후보 수집기이지 판정기가 아니다. grep 히트 수를 위반 건수로 보고하면 안 된다.

축 분포 — 코어 : 어댑터 = 8 : 1

주석·네이밍 규칙은 언어 문법에 묶이지 않으므로 대부분 코어다. 어댑터로 내려간 것은 I 하나뿐이고, J 는 규칙 자체는 코어지만 판정에 그 프로젝트의 공통 위젯 목록이 입력으로 필요하다.

J

[한국어] 라벨은 규칙이 아니라 신호에 붙는다

A 와 G 에만 병기한다. 두 규칙 자체는 언어 무관이고, 한국어에 결속된 것은 grep 패턴뿐이다. 다른 언어 코퍼스에서는 패턴을 다시 만들어야 하며, 그렇다고 규칙이 적용 불가해지는 것은 아니다.

판정 순서 — 보존 후보(H)를 먼저 표시한다

이 순서는 임의가 아니다. A 의 grep 패턴은 형태가 같은 H 주석을 함께 잡기 때문에, 삭제 후보를 먼저 고르면 좋은 주석이 같은 배치에 섞여 들어온다. 보존 마킹을 선행시키면 교차 단계에서 걸러낼 수 있다.

1

대상 트리 고정 + 코드 생성 산출물 제외

스캔 범위를 먼저 확정하고 *.g.dart · *.freezed.dart 류 생성 파일을 배제한다. 제외하지 않으면 B 의 빈도 집계 상위가 전부 생성기 배너로 채워진다.

▼
2

H 후보를 먼저 표시한다 — 삭제 금지 마킹

인과 접속이 들어간 주석(때문 · 안 하면 · 버그 · 무시되 · 제약 · 하드코딩)을 먼저 훑어 삭제 금지 후보로 마킹한다. 이 단계가 카탈로그 전체의 안전장치다.

▼
3

그다음에 삭제 후보를 고른다 — A~G · I · J

각 카테고리의 검색 패턴으로 후보를 수집한다. 이 시점의 결과는 후보 목록이지 위반 건수가 아니다. C 패턴은 정상 doc 을, A 패턴은 H 를 함께 잡는다.

▼
4

2단계 마킹과 교차 — 겹치면 H 가 이긴다

삭제 후보와 보존 마킹이 같은 줄을 가리키면 그 줄은 위반 목록에서 뺀다. D 와 H 의 경계도 여기서 갈린다 — 프레임워크 동작 서술은 D 지만, 그 동작 때문에 이렇게 쓸 수밖에 없었다는 이유는 H 다.

▼
5

카테고리별 처리 형태 배정

삭제(B·D·F) / 개명(A·E) / 흡수(G) / 수렴(J) / 재구성(I) 은 서로 다른 작업이다. 라벨만 붙이고 처리 형태를 구분하지 않으면 개명 카테고리가 삭제로 처리된다.

▼
6

파일 단위로 사람이 한 줄씩 확인 후 적용

grep 결과를 확인 없이 sed 로 일괄 치환하지 않는다. 파일 단위 확인이 캠페인 루프의 존재 이유다.

!

순서를 뒤집으면 좋은 주석이 같이 지워진다

실행 검증에서 surfaceTintColor: ..., // 안 끄면 M3가 배경색 위에 tint 덮음 이 A 패턴에 그대로 걸렸다. 형태(선언 뒤 한국어 주석)가 동일하고 내용만 다르기 때문이다. 2단계 보존 마킹 없이 3단계부터 시작하면 이 줄은 A 위반으로 집계되어 삭제 배치에 들어간다.

H 를 위반 목록에 넣고 A~J 를 일괄 삭제하는 것이 이 카탈로그의 최대 오용이다. 코드로 복원 불가능한 정보가 사라지며, 되돌리려면 원저자의 기억에 의존해야 한다.

처리 형태 — 삭제 / 개명 / 흡수 / 수렴 / 보존

카테고리 라벨만 붙이고 처리 방침을 구분하지 않는 것이 판정 실패 모드의 하나다. 다섯 형태는 작업 범위도, 컴파일 영향도, 되돌리기 비용도 전부 다르다.

H
위반 카테고리 Ⅰ — A~G (코어)

카드 상단 바 색이 강도다 — 빨강 MUST · 노랑 SHOULD · 회색 관측 컨벤션. 보존 카테고리 H 는 이 목록에 없다. 별도 섹션에 그린 계열로 분리했다.

A

이름 번역 주석

MUST 삭제
코어 한국어

식별자 이름과 타입이 이미 담고 있는 의미를 주석이 한국어로 되풀이하는 것. 주석을 지워도 정보 손실이 0이다. 

String? text,      // 버튼 텍스트
bool isChecked,    // 체크 여부
double min,        // 최소값
판정 신호 선언 뒤에 붙은 한국어 인라인 주석 — ^[[:space:]]*[A-Za-z_].*[a-zA-Z0-9_?],[[:space:]]*//[[:space:]]*[가-힣]
처리 삭제.
예외 단 하나 — 이름이 약해서 주석이 필요한 경우, 주석이 아니라 이름을 고친다. 주석만 지우고 이름을 그대로 두면 의미가 사라진다. hex 값의 alpha 퍼센트처럼 값에서 사람이 곧바로 읽어낼 수 없는 메타 정보는 A 가 아니다.
강도 승격 Effective Dart 의 등급은 AVOID 이고 이 카탈로그가 MUST 로 승격했다. 사유는 실측 최다 빈도(48파일 전역, 약 85건)와 제거 시 손실 0.

B

템플릿 마커

MUST 삭제
코어

파일마다 같은 위치에 기계적으로 반복되는 고정 라벨. //상태, //위젯 구현부, //뷰모델 류로, 그 파일이 무엇인지는 클래스 선언이 이미 말한다. 

grep -rhoE '^[[:space:]]*//[[:space:]]*[^[:space:]/*].*$' --include='*.dart' \
  --exclude='*.g.dart' --exclude='*.freezed.dart' . \
  | sed 's/^[[:space:]]*//' | sort | uniq -c | sort -rn | head -20
판정 신호 동일 주석 줄의 코퍼스 전역 빈도. 빈도 상위에 뜨는 짧은 라벨이 후보다. 생성 파일을 반드시 제외한다.
처리 삭제.
예외 없다. 파일 구조를 알려주는 역할이 필요하면 그것은 파일 분할이나 이름으로 해결할 문제이지 마커로 해결할 문제가 아니다.
→ Google Engineering Practices — code review
C

메서드명 반복 doc

SHOULD 삭제
코어

메서드 이름을 한국어 문장으로 풀어 쓴 doc 주석. handlePressStart() 위의 /// 눌림 시작 상태를 처리합니다. 가 전형이다. 번역투 종결형(~을 처리합니다, ~하도록 합니다)이 같이 따라온다. 

grep -rnE '^[[:space:]]*///.*(합니다|됩니다|하도록)' --include='*.dart' .
판정 신호 번역투 doc 후보 필터. 과수집되므로 히트를 위반으로 세지 말고 후보 목록으로만 쓴다.
처리 삭제.
예외 public API 계약 과 부수효과 순서가 호출자에게 중요한 경우. 이때는 doc 을 남기되 이름의 반복이 아니라 계약을 쓴다. 파라미터·반환값 블록의 표기 형식은 이 카탈로그가 아니라 어댑터의 정책 상수가 정한다 — 어댑터가 유지를 지시하면 C 로 판정하지 않는다.
→ Effective Dart — documentation
D

프레임워크 기본 설명

MUST 삭제
코어

프레임워크 공식 문서에 이미 적힌 기본 동작을 코드 옆에 옮겨 적은 주석. SizedBox 앞의 // 크기 지정, ClipRRect 앞의 // borderRadius 클리핑 같은 것이다.

판정 신호 정규식으로 분리되지 않는다. 판정은 리뷰로 한다 — 주석이 설명하는 내용이 그 API 문서 첫 문단에 있으면 D 다.
처리 삭제하되 “왜 이 선택을 했는가”는 남긴다. 남는 그 한 줄은 D 가 아니라 H 로 승격된다.
근거 프레임워크 기본 동작 서술은 정보량이 0일 뿐 아니라 프레임워크 버전이 오르면 거짓이 되므로 유지 비용이 음수다.
→ Flutter — Material.surfaceTintColor
E

접두사 fallback 변수명

관측 컨벤션
코어 실측 9건 / 4파일

effective* / resolved* 접두사로 “기본값이 적용된 값”임을 이름에 박는 것. ?? 연산자가 이미 fallback 을 표현하므로 접두사는 역할이 아니라 계산 과정을 드러낸다. 

final effectiveGradient = props.gradient ?? defaultGradient;
final resolvedChildren  = props.children.isNotEmpty ? props.children : fallback;
판정 신호 \b(effective|resolved)[A-Z]
처리 삭제가 아니라 도메인·역할명으로 개명이다. toolbarGradient, visibleChildren 처럼 그 값이 무엇인지로 바꾼다. 개명은 선언만 고치면 끝나지 않는다 — 호출부 전부를 함께 바꿔야 한다.
근거 등급 공개 통계 근거가 없다. 2026-08 조사에서 접두사별 LLM 과대표집 통계는 공개 1차 문헌 어디에도 확인되지 않았다. 강도를 관측 컨벤션 으로 낮춰 표기하고 각주를 붙이지 않는다. 실측은 유효한 국지 근거이므로 규칙을 지우지도 않는다.
실측 근거 프로젝트 실측 57 파일 / 9건 · 4파일 (2026-04~06) — 공개 URL 없음
F

구분선 블록

MUST 삭제
코어

// --- 를 수십 칸 늘여 만든 시각적 구획. 한 파일에 14개까지 쌓이면 구분 기능 자체가 사라진다.

해석 구분선이 필요하다고 느껴진다면 그것은 파일이 너무 길다는 신호이지 선이 필요하다는 신호가 아니다.

G

자명 구조 라벨

SHOULD 흡수
코어 한국어

위젯 트리나 블록 위에 붙은 짧은 한국어 라벨. // 제목, // 서버 이름, // 좌측: leading 또는 기본 뒤로가기 처럼 바로 아래 코드가 그대로 말하는 내용이다. 

grep -rnE '^[[:space:]]*//[[:space:]]*[가-힣][가-힣 ]{0,8}$' \
  --include='*.dart' .

판정 신호 — 단독 줄의 짧은 한국어 명사구.

처리 삭제가 아니라 흡수다. 라벨이 담던 의미를 변수명(serverNameText)이나 추출한 위젯 이름으로 옮긴 뒤 라벨을 지운다. 지우기만 하면 정보가 없어진다.

프로젝트에 이미 있는 공통 컴포넌트를 쓰지 않고 그것이 감싸던 저수준 조합을 호출부에서 다시 조립하는 것. 눌림 애니메이션 공통 위젯이 있는데 제스처 감지기와 스케일 애니메이션을 직접 엮는 식이다.

E 는 관측 컨벤션 이다 — 논문 각주를 붙이면 안 된다

effective* / resolved* 접두사가 LLM 산출물에서 과대표집된다는 공개 통계는 존재하지 않는다. 2026-08 조사에서 접두사별 과대표집 통계는 공개 1차 문헌 어디에서도 확인되지 않았다. 여기에 문헌 각주를 붙이는 순간, 국지 실측 9건을 문헌 근거로 위장하게 된다.

✗ 해서는 안 되는 것
  • ✗E 에 학술 논문·공식 문서 각주를 달아 MUST 로 격상
  • ✗“LLM 이 이 접두사를 많이 쓴다”를 출처 없이 단정
  • ✗근거가 약하다는 이유로 규칙 자체를 삭제
✓ 확정된 처리
  • ✓강도를 관측 컨벤션 으로 낮춰 표기하고 각주를 붙이지 않는다
  • ✓출처는 실측 배지로만 — 공개 URL 을 지어내지 않는다
  • ✓실측은 유효한 국지 근거이므로 규칙은 유지한다 (9건 / 4파일)

코드 대비 — 처리 형태별 before / after

같은 “위반” 이라도 손이 닿는 범위가 다르다. A 는 이름을 볼 것, E 는 호출부를 볼 것, G 는 구조로 옮길 것.

A — 삭제, 단 이름이 약하면 개명

✗ before
String? text,      // 버튼 텍스트
bool isChecked,    // 체크 여부
double min,        // 최소값
int c,             // 카드 개수

앞 세 줄은 이름이 이미 말하고 있어 주석이 잉여다. 마지막 줄은 이름이 약해서 주석이 짐을 지고 있다.

✓ after
String? text,
bool isChecked,
double min,
int cardCount,     // ← 주석 삭제가 아니라 개명

잉여 주석은 지운다. 약한 이름은 주석을 지우는 대신 이름을 고친다 — 주석만 지우면 원래보다 나빠진다.

E — 개명은 호출부 전수를 동반한다

✗ before
final effectiveGradient =
    props.gradient ?? defaultGradient;
final resolvedChildren =
    props.children.isNotEmpty
        ? props.children
        : fallback;

// 호출부
Container(gradient: effectiveGradient)
Column(children: resolvedChildren)

접두사가 계산 과정을 드러낼 뿐 그 값이 무엇인지는 말하지 않는다. ?? 가 이미 fallback 을 표현한다.

✓ after
final toolbarGradient =
    props.gradient ?? defaultGradient;
final visibleChildren =
    props.children.isNotEmpty
        ? props.children
        : fallback;

// 호출부 — 전수 동반 수정 필수
Container(gradient: toolbarGradient)
Column(children: visibleChildren)

도메인·역할명으로 바꾼다. 선언만 고치면 컴파일이 깨진다 — 삭제 카테고리와 작업 형태가 다르다.

G — 삭제가 아니라 흡수

✗ before — 그리고 잘못된 처리
// 서버 이름
Text(state.name, style: t.bodyLarge)

// 잘못된 처리 = 라벨만 삭제
Text(state.name, style: t.bodyLarge)
// ↑ 구획 정보가 어디로도 가지 않고 증발

G 를 삭제 카테고리로 오해하면 라벨이 담던 의미가 이름으로 옮겨가지 않고 그냥 없어진다.

✓ after — 흡수
final serverNameText = Text(
  state.name,
  style: t.bodyLarge,
);
// ...
serverNameText

라벨의 의미를 변수명 또는 추출한 위젯 이름으로 옮긴 뒤 라벨을 지운다. 섹션 라벨이 2개 이상의 선언을 묶고 그 축을 이름으로 표현할 수 없을 때만 남긴다.

D → H — 카테고리 경계에서의 승격

✗ D — 삭제

ClipRRect(borderRadius: r, child: c)

API 문서 첫 문단에 있는 내용이다. 정보량 0이고, 프레임워크 버전이 오르면 거짓이 된다.

✓ H — 보존
// surfaceTintColor 안 끄면 M3 가
// 지정 배경색 위에 tint 를 덮는다

같은 API 를 언급하지만 같은 카테고리가 아니다. 프레임워크 함정을 설명하므로 H 다.

집계 규칙 — 코드 생성 산출물 제외

집계는 판정과 다르다. 집계 단계에서 생성 파일을 빼지 않으면 순위가 통째로 오염되고, F 는 생성기 배너를 위반으로 잡는다.

✗

제외하지 않으면

  • ✗B 의 빈도 상위가 전부 코드 생성기 배너로 채워진다 — 실제 템플릿 마커가 순위에서 밀려 보이지 않는다.
  • ✗F 가 생성기 배너를 구분선 위반으로 집계한다 — 손댈 수 없는 파일이 위반 건수로 잡힌다.
  • ✗총 위반 건수가 부풀려져 캠페인 진척률이 왜곡된다.
✓

제외 플래그

--exclude='*.g.dart'
--exclude='*.freezed.dart'

B 의 빈도 집계 명령에 이미 포함되어 있다. F 의 예외 조항(“코드 생성기가 만드는 배너”)도 같은 제외로 처리한다.

안티패턴문제
H 를 위반 목록에 넣고 A~J 를 일괄 삭제 코드로 복원 불가능한 정보가 사라진다. H 는 방어 카테고리다.
이름은 그대로 두고 A 주석만 삭제약한 이름 + 주석 없음이 되어 원래보다 나빠진다. A 의 처리는 “삭제 또는 개명”이다
G 라벨을 흡수 없이 삭제구획 정보가 이름으로 옮겨가지 않고 그냥 없어진다
grep 히트 수를 위반 건수로 보고A 패턴은 H 를 함께 잡고, C 패턴은 정상 doc 을 함께 잡는다. 히트는 후보지 판정이 아니다
grep 결과를 확인 없이 sed 로 일괄 치환같은 정규식에 걸린 H 가 조용히 삭제된다. 파일 단위 확인이 캠페인 루프의 존재 이유다

J 를 공통 위젯 목록 없이 판정무엇이 중복인지 정의하는 입력이 빠져 있어 판정 자체가 성립하지 않는다

Gotchas — 실행 검증에서 확인된 함정

7종 grep 패턴을 Dart 트리 517 파일에 실제로 돌려본 뒤 남은 항목들.

  • !A 의 grep 은 H 를 같이 잡는다 — 실행 검증에서 surfaceTintColor: ..., // 안 끄면 M3가 배경색 위에 tint 덮음 이 A 패턴에 그대로 걸렸다. 형태(선언 뒤 한국어 주석)가 동일하고 내용만 다르기 때문이다. A 패턴 결과는 반드시 사람이 한 줄씩 읽는다.
  • !B 의 빈도 집계는 생성 파일에서 폭증한다 — 제외하지 않으면 상위 전부가 코드 생성기 배너로 채워져 실제 마커가 안 보인다. *.g.dart · *.freezed.dart 류를 반드시 제외한다.
  • !C 의 처리는 어댑터 정책 상수와 충돌할 수 있다 — 파라미터·반환값 블록 표기를 유지하라고 어댑터가 정했다면 그 형식은 C 가 아니다. 카탈로그가 어댑터를 이기지 않는다.
  • !E 는 선언만 고치면 컴파일이 깨진다 — 개명이므로 호출부 전수를 함께 바꾼다. 삭제 카테고리와 작업 형태가 다르다.
  • ![한국어] 라벨은 규칙이 아니라 신호에 붙는다 — A 와 G 의 규칙은 언어 무관이고, 한국어에 묶인 것은 grep 패턴뿐이다. 다른 언어 코퍼스에서는 패턴을 다시 만들어야 하며, 규칙이 적용 불가해지는 것은 아니다.
  • !“위반 0” 과 “규칙 적용 불가” 는 다르다 — 어떤 스택에서 실측이 0이라고 해서 코어 규칙이 그 스택에 안 맞는 것이 아니다. 이 카탈로그는 기존 코드 정리용이 아니라 새 코드 작성 표준이다.
  • !카테고리 경계에서는 D 가 H 로 승격된다 — 프레임워크 기본 동작 서술은 D 지만, 그 동작 때문에 이 코드를 이렇게 쓸 수밖에 없었다는 이유는 H 다. 같은 API 를 언급한다고 같은 카테고리가 아니다.
