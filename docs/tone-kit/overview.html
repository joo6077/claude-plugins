tone-kit / overview

Tone Kit 개요 — 이 킷이 잡는 것

코드를 다시 읽어 준 주석, 역할이 아니라 외형과 계산 과정을 담은 이름, 번역투 한국어 doc. 목표는 읽고 고치기 쉬운 코드이고 톤 개선은 그 부산물이다. v0.1.0 · 갱신 2026-09-02

이 문서가 잡는 것
1

다시 읽어 준 주석

이름 번역, 템플릿 마커, 구분선, 프레임워크 기본 설명. 코드를 한 번 더 읽어 주기만 하는 문장들이다.

2

역할이 아닌 이름

외형과 계산 과정을 담은 이름 — BlueDeviceRow, effectiveGradient, BoolCallback.

3

번역투 · 갈린 라벨

번역투 한국어 doc 과 표기가 둘로 갈린 doc 라벨. 규모가 커지면 커버리지 측정이 먼저 깨진다.

한 번에 다섯 가지가 걸린 파일

아래 한 조각에 템플릿 마커 · 구분선 · 이름 번역 주석 · fallback 접두사 · 번역투 doc 이 동시에 들어 있다. 이 킷이 다루는 범위 전체가 여기 압축돼 있다.

✗ before5개 동시 적발
// ------------------------------------------------
// 위젯 구현부
class {widget_prefix}BlueDeviceRowWidget extends StatelessWidget {
  final String? text;   // 버튼 텍스트
  /// 눌림 시작을 처리합니다.
  void handlePressStart() {
    final effectiveGradient = props.gradient ?? defaultGradient;
  }
}
템플릿 마커 구분선 이름 번역 주석 fallback 접두사 번역투 doc
✓ after역할어로 정렬
class {widget_prefix}DeviceItemWidget extends StatelessWidget {
  final String? text;
  /// 길게 누르기 반복을 시작한다.
  void startLongPressRepeat() {
    final toolbarGradient = props.gradient ?? defaultGradient;
  }
}
외형어 제거 능동 단문 doc 역할 기반 지역변수

이 킷은 AI 탐지 회피 도구가 아니다

목표는 읽고 고치기 쉬운 코드이고, 톤 개선은 그 부산물이다. 규칙마다 붙는 MUST SHOULD 관측 컨벤션 3등급의 판정 방법론은 이 문서가 소유하지 않는다 — ai-code-stylometry 가 소유한다. 여기서는 각 규칙에 붙은 강도만 읽으면 된다.

대표 before/after 10쌍

왼쪽이 before, 오른쪽이 after 다. 강도 배지는 소스 규칙의 값을 그대로 옮긴 것이며 이 페이지가 올리거나 내리지 않는다. MUST 는 공식 스타일 가이드가 문법 층위에서 규정한 것, SHOULD 는 공식 문구가 권고형인 것, 관측 컨벤션 은 공개 출처 없이 프로젝트 실측만 있는 것이다.

1

이름을 옮기기만 한 주석은 지운다

MUST
✗ before이름 번역 주석
String? text,      // 버튼 텍스트
bool isChecked,    // 체크 여부
✓ after
String? text,
bool isChecked,

이름과 타입이 이미 같은 말을 한다. 지워도 정보 손실이 0이다. 이름이 약해서 주석이 필요했던 경우가 유일한 예외이고, 그때는 주석이 아니라 이름을 고친다.

2

기계가 남긴 흔적은 지운다 — 마커 · 구분선 · 디자인 툴 참조

MUST
✗ before구분선 + 노드 ID
// ------------------------------------------------
// 상태
// 카드 배경 그라데이션 상단 (노드 12159:8715 Frame/Card)
static const cardBevelTop = ...;
✓ after
static const cardBevelTop = ...;

파일이 무엇인지는 선언부가 이미 말하고, 구분선은 여러 개 쌓이는 순간 구분 기능을 잃는다. 코드는 디자인 소스의 참조가 아니라 구현물이므로 노드 ID · 변수 경로 · CSS 원문을 남기지 않는다. 대체 수단은 빈 줄과 의미 있는 이름이다.

3

기본 동작 설명은 지우되 이유는 남긴다

삭제 MUST / 보존 MUST
✗ before프레임워크 기본 동작 서술
// 프레임워크 문서 첫 문단에 이미 있는 내용
// surfaceTintColor 는 Material 3 에서 표면에 색조를 입힌다.
surfaceTintColor: Colors.transparent,
✓ after복원 불가 정보
// 코드만 읽어서는 복원할 수 없는 정보
// M3 surface tint 가 배경을 덮어 지정색이 밝아진다. 그래서 tint 를 끈다.
surfaceTintColor: Colors.transparent,

기본 동작 서술은 정보량이 0일 뿐 아니라 버전이 오르면 거짓이 되므로 유지 비용이 음수다. 반대로 함정 · 제약 · 실패 모드를 담은 주석은 보존 대상이고, 안티패턴 목록만 보고 일괄 삭제하면 이쪽이 함께 날아간다. 보존 표시가 삭제 후보 선정보다 먼저다.

이름에 외형과 표 어휘를 넣지 않는다

외형 금지 SHOULD 표 어휘 금지 = 합성 규칙
✗ before색 + 표 어휘
class {widget_prefix}BlueDeviceRowWidget ...
class {widget_prefix}BlueDeviceRowState ...
✓ after
class {widget_prefix}DeviceItemWidget ...
class {widget_prefix}DeviceItemState ...

색은 테마가 바뀌면 거짓이 되고, Row 와 Cell 은 표 전용 어휘라 진짜 표가 생기면 이름이 충돌한다. 세로 리스트 한 장의 기본값은 Item 이다. 컴포넌트와 그것이 받는 데이터 타입은 같은 역할어로 정렬한다 — 어긋나면 검색이 한쪽만 잡는다.

합성 규칙이라는 표시는 6개 디자인 시스템의 어휘를 대조해 만든 규칙이라는 뜻이다. 단일 권위가 없으므로 아래 링크는 어휘 원천으로만 인용한다.

5

fallback 접두사를 이름으로 쓰지 않는다

관측 컨벤션
✗ before계산 과정이 이름에
final effectiveGradient = props.gradient ?? defaultGradient;
final resolvedChildren = props.children ?? const [];
✓ after역할이 이름에
final toolbarGradient = props.gradient ?? defaultGradient;
final visibleChildren = props.children ?? const [];

기본값 연산자가 이미 fallback 을 표현한다. 접두사는 역할이 아니라 계산 과정을 드러낸다. 삭제가 아니라 개명이고, 선언만 고치면 컴파일이 깨지므로 호출부 전수를 함께 바꾼다.

출처
프로젝트 실측만 — 9건 / 4파일 접두사별 공개 통계 확인 실패 — 논문 각주를 붙이지 않는다
6

콜백 타입에는 시그니처가 아니라 의미를 붙인다

관측 컨벤션
✗ before시그니처 타입명
typedef BoolCallback = void Function(bool value);
final void Function(bool) onVisibleChanged;
✓ after시맨틱 typedef
typedef {widget_prefix}EventVisibleChanged
    = void Function(bool value);
final {widget_prefix}EventVisibleChanged onVisibleChanged;

BoolCallback 은 타입에서 의미를 읽을 수 없다. 한 아이템의 콜백 세 개가 전부 같은 타입이면 그것이 증상이다. typedef 는 의미가 생겨난 위젯의 파일에 top-level 로 두고 공유 typedef 파일은 만들지 않는다 — 모아 두면 어느 컴포넌트의 계약인지 추적이 끊긴다.

7

위젯을 반환하는 헬퍼 대신 위젯을 만든다

SHOULD
✗ before_build 헬퍼
Widget build(BuildContext context) =>
    Column(children: [_buildHeader(), _buildBody()]);

Widget _buildHeader() => ...;
✓ afterconst 위젯
Widget build(BuildContext context) => const Column(
      children: [
        {widget_prefix}SettingsHeaderWidget(),
        {widget_prefix}SettingsBodyWidget(),
      ],
    );

헬퍼는 호출 단계만 늘리고 rebuild 는 끊지 못한다. 분리 조건은 넷이다. 하나라도 성립하면 위젯으로 빼고 넷 다 아니면 인라인한다. 줄 수는 판정식이 아니라 알람이다.

  • ✓관심사가 다른가
  • ✓같은 패턴이 3곳 이상인가
  • ✓독립 테스트 대상인가
  • ✓본문이 파일 오버헤드보다 큰가
강도가 SHOULD 인 이유 — 공식 문구가 prefer 이고 Builder 라는 공식 인라인 대안이 존재한다. MUST 로 올려 인용하면 첫 반박에 무너진다.

→ StatelessWidget → Builder → flutter#149932

doc 라벨은 자유 서술이 아니라 상수다

관측 컨벤션
✗ before표기 갈림 · 축약 파라미터명
/// 네트워크 상태를 확인합니다.
/// - [ctx]: 컨텍스트
/// - 리턴: N/A
✓ after고정 라벨
/// 네트워크가 끊겨 있으면 안내 다이얼로그를 띄운다.
///
/// - [context]: 다이얼로그 표시용 빌드 컨텍스트
/// - 반환값: 없음

이 규칙이 관측 컨벤션인데도 강한 이유는 규모다. 이 정도 규모에서 표기가 둘로 갈리면 커버리지 측정과 완료 게이트가 동시에 깨진다.

- [param]: 788건
- 반환값: 577건 / 80파일
- 반환값: 없음 을 노이즈로 보고 지우면 "doc 이 없는 것"과 "반환값이 없는 것"을 구분할 수 없다. 표기를 바꾸려면 전수 치환을 같은 커밋에서 끝낸다.

관측 컨벤션

공개 출처 없이 프로젝트 실측만 있는 규칙. 준수 강도가 낮다는 뜻이 아니라 근거가 국지적이라는 뜻이다. 논문 각주를 붙이지 않는다.

어댑터

코어 규칙을 특정 스택 문법에 결속하는 파일. 주석 기호, doc 라벨 구조, 금지 접두사, 완료 게이트 grep 을 채운다. 현재 dart-flutter 하나뿐이다.

완료 게이트

완료를 선언하기 전에 돌리는 grep · awk 묶음. 통과 기준은 "돌렸다"가 아니라 "히트마다 판정을 적었다" 다.

3축 레이어 — 규칙이 어디에 묶여 있나

규칙은 세 축이 직교한다. 한 규칙이 세 축에 동시에 걸릴 수 있다 — - 반환값: 없음 은 어댑터 × 한국어 × 공통이다.

축 1 · 스택 코어 / 어댑터 구분선 주석 금지 → 코어
_build* 접두사 금지 → dart-flutter
축 2 · 언어 중립 / 로케일 - 반환값: → 한국어
영어 프로젝트 → - Returns:
축 3 · 프로젝트 공통 / 파라미터 {widget_prefix} · {TokenClass}
→ .claude/tone-project.md

로케일이 바뀌어도 골격은 남는다

- 반환값: 라벨은 Dart 가 아니라 한국어에 묶여 있다. 영어 프로젝트에서는 - Returns: 가 되지만 골격과 커버리지 기준은 그대로 남는다.

파라미터는 킷이 정하지 않는다

{widget_prefix} 나 {TokenClass} 같은 값은 프로젝트가 소유하며, 확정값은 프로젝트의 .claude/tone-project.md 에 남는다.

완료 게이트는 이렇게 생겼다

완료를 선언하기 전에 돌리는 묶음의 실제 모양이다. 각 패턴에는 히트가 위반인지가 병기돼 있다.

SRC=lib; INC="--include=*.dart"                               # 프로젝트 값으로 교체

grep -rnE '^[[:space:]]*//[[:space:]]*[-=]{5,}' "$SRC" $INC   # 구분선 블록 — 히트 = 위반
grep -rnE '\b(effective|resolved)[A-Z]' "$SRC" $INC           # fallback 접두사 — 히트 = 개명 후보
grep -rnE '\b_build[A-Z][A-Za-z0-9]*\(' "$SRC" $INC           # 위젯 반환 헬퍼 — 히트 ≠ 위반
!

히트가 곧 위반은 아니다

세 번째 패턴은 추출이 정당한 건까지 잡으므로 히트 수를 위반 수로 보고하면 근거 없는 지적이 된다. 최종 판정은 파일을 열어야 나온다.

!

0건도 그 자체로는 통과가 아니다

0건은 "위반이 없는 것"과 "패턴이 죽은 것"을 구분하지 못한다. 준수 상태에서 0건이 정상인 패턴은 합성 양성 케이스로 살아 있음을 따로 증명한다.

통과 기준 요약 — 돌렸다가 아니라 히트마다 판정을 적었다. 그리고 0건 패턴은 살아 있음을 증명했다.
