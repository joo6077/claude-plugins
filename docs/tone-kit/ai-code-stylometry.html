AI Code Stylometry — tone-kit 포지셔닝과 인용 경계

tone-kit 이 무엇을 목표로 삼고 무엇을 목표로 삼지 않는지 정의한다. 이 킷은 maintainability / style gate 이며, 규칙의 정당화 축은 가독성·변경 용이성·리뷰 비용이다. 코드 대상 탐지 문헌은 "왜 이 방향을 목표로 삼지 않는가"를 설명할 때만 인용한다. 소스: docs/tone/ai-code-stylometry.md v0.1.0 · 2026-08-28.

Positioning — 이 문서의 결론

이 킷은 AI 탐지 회피 도구가 아니다. 코드 탐지 문헌은 표면적 humanizing 을 Adversarial 이라는 별도 위험군으로 분류한다.

"AI 티를 지운다"를 목표 문장으로 삼으면, 그 목표는 학계가 위험 행위로 분류한 범주 와 정확히 겹친다. 목표 문장은 "읽고 고치기 쉬운 코드"여야 하고, 스타일 신호 약화는 그 부산물이다. SemEval-2026 Task 13 Subtask C 는 Human-written / Machine-generated / Hybrid / Adversarial 4-way 분류를 공식 채택한다 — Adversarial 은 개선된 코드가 아니라 독립 클래스다.

원칙 — 인용 경계와 규칙 강도

6개 원칙. 앞의 네 개는 공개 1차 문헌으로 근거가 확인된 것이고, 5번은 근거 확인에 실패한 규칙을 어떻게 다룰지, 6번은 이 킷 전체를 관통하는 강도 체계를 정의한다. 각 카드 하단의 출처는 소스 문서의 > **출처:** 줄을 그대로 옮긴 것이며, 확인 실패 항목은 링크 대신 텍스트 배지로 표시한다.

1

코드 탐지 연구와 텍스트 탐지 연구를 섞어 인용하지 마라

AI 생성물 탐지 문헌은 자연어 텍스트 대상과 소스 코드 대상이 갈라져 있고, 신호도 방법론도 다르다. 코딩 표준의 근거로는 코드 대상 연구만 인용할 수 있다.

Droid 는 AI 생성 코드 탐지 전용 리소스 suite 다. 단일 탐지기가 아니라 DroidCollection(데이터)과 DroidDetect(탐지기) 로 구성된다. 수집 대상에 완전 AI 생성물뿐 아니라 인간-AI 공동 작성 코드와 탐지 회피용으로 의도 제작된 adversarial 샘플이 포함된다.

표면적 humanizing 은 개선이 아니라 별도 위험군이다

기계 생성 코드를 사람이 쓴 것처럼 보이게 표면만 고치는 행위는 문헌에서 독립 클래스로 다뤄진다. Droid 는 이를 adversarial samples · adversarially humanised · machine-humanised code 로 부르고, prompt 기반 공격과 preference-tuning 기반 공격으로 나눈다.

3

탐지기는 취약하지만 그 취약성은 규칙의 근거가 아니다

Droid 실측에서 기존 baseline 탐지기는 adversarial 샘플에 약했다. GPT-Zero 의 adversarial recall 은 0.10 이다. 반대로 adversarial 샘플을 명시 학습한 DroidDetectCLS-Base/Large 는 0.92 를 보고한다.

이 수치가 말하는 것은 "탐지를 피할 수 있다"가 아니라 provenance 탐지 자체가 불안정한 기반 이라는 것이다. 불안정한 기반 위에 코딩 표준을 세우지 마라.

스타일 신호는 언어를 가로질러 존재한다 — 그래서 규칙도 스택 무관 축을 가진다

다국어 코드 스타일로메트리 연구는 단일 multilingual 모델로 10개 언어에서 accuracy 84.1% ± 3.8%, F1 84.0% ± 4.0% 를 보고한다.

근거 없는 규칙은 "관측 컨벤션"으로 표기하라 — 논문 인용을 붙이지 마라

effective* / resolved* 접두사가 LLM 생성 코드에 통계적으로 과대표집된다는 주장은 공개 1차 문헌에서 확인되지 않는다. 확인된 코드 탐지 문헌들은 identifier length, naming convention 같은 넓은 신호는 다루지만 특정 접두사 통계는 제시하지 않는다.

이런 규칙은 버리는 것이 아니라 강도를 낮춰 표기 한다. 프로젝트 코드베이스 실측을 "관측된 관례"로 쓰는 것은 정직하다. 논문 각주를 붙이는 순간 거짓이 된다.

규칙 강도는 출처 강도를 넘지 못한다

이 킷의 모든 규칙은 MUST / SHOULD / 관측 컨벤션 세 등급 중 하나를 명시한다. 등급은 규칙의 중요도가 아니라 근거의 강도에서 나온다.

공식 문서가 prefer 라고 쓴 것을 킷이 MUST 로 승격하면, 그 승격분은 킷의 창작이지 근거가 아니다. 승격하려면 승격 사유를 프로젝트 컨텍스트로 따로 밝혀야 한다.

MUST공식 문서/표준이 금지·강제
SHOULD공식 문서가 prefer 수준 권고
관측공개 근거 없음 · 실측만
강도 체계조용한 승격 금지
킷 내부 규약 이 원칙은 외부 문헌 인용이 아니라 tone-kit 이 스스로에게 부과하는 표기 규칙이다
규칙 강도 3등급 — 이 킷 전체를 관통하는 체계

모든 규칙 문장은 아래 세 등급 중 하나를 반드시 달고 있어야 한다. 등급이 없는 규칙은 미완성 규칙이다. 등급은 근거의 강도에서 파생되며, 근거를 넘어서는 등급은 붙일 수 없다.

MUST

조건 — 공식 문서나 표준이 해당 행위를 명시적으로 금지하거나 강제한다. 언어 스펙, 공식 스타일 가이드의 must / never 문장이 이 등급의 유일한 재료다.

표기 → 규칙 문장에 근거 URL 병기
SHOULD

조건 — 공식 문서가 prefer 수준으로 권고한다. 강제가 아니라 선호다. 이 등급을 MUST 로 올리려면 프로젝트 컨텍스트에 근거한 승격 사유를 별도로 남겨야 한다.

표기 → 근거 URL + "권고" 명시
관측 컨벤션

조건 — 공개 근거가 없고 프로젝트 실측만 존재한다. 규칙을 지우지 말고 이 등급으로 내려서 살린다. 논문 각주를 붙이면 그 순간 거짓 인용이 된다.

표기 → "관측 컨벤션 (실측 N건)" 라벨 필수
등급조건표기승격 가능 여부
MUST 공식 문서/표준이 금지 또는 강제 규칙 문장에 근거 URL 병기 최상위 — 더 올릴 곳이 없다
SHOULD 공식 문서가 prefer 수준으로 권고 근거 URL + "권고" 명시 MUST 승격 시 승격 사유를 프로젝트 컨텍스트로 별도 명시

제외된 인용 — 이 킷이 인용하지 않는 문헌

아래 두 논문은 AI 생성물 탐지 문헌에서 자주 인용되지만, 자연어 텍스트 탐지기다. 코드 스타일 규칙의 근거로 쓰면 대상 범위를 벗어난 인용이 된다. 이 킷은 두 논문을 인용하지 않는다. 소스 문서에 URL 이 없으므로 여기에도 링크를 붙이지 않는다.

어댑터 — 스택 특화

언어별 공식 스타일 가이드·표준이 규정하는 축. 이 층의 규칙만이 MUST 등급을 받을 수 있다 — 공식 문서가 금지·강제하는 문장이 존재하기 때문이다.

대상 언어C++ · C · C# · Go · Java
대상 언어JavaScript · Kotlin · Python
대상 언어Ruby · Rust
언어 목록 출처 SANER 2025 실험 대상 10개 언어 — 어댑터 우선순위의 참고값이지 킷의 지원 범위 선언이 아니다
Gotchas — 이 문서를 쓸 때 반복되는 5가지 실수

문서·스킬·README 를 작성할 때 매번 확인해야 하는 5개 항목. 특히 첫 번째 항목은 목적 문장 하나로 킷 전체의 정당성이 뒤집히는 사안이다.

  • ! "AI 티 제거"는 마케팅 문구로도 쓰지 마라 — 킷 description, README, 스킬 트리거 어휘 어디에도 탐지 회피를 목표로 읽히는 표현을 두지 않는다. Droid/SemEval 이 그 범주를 위험군으로 분류하기 때문에, 목적 문장 하나가 킷 전체의 정당성을 뒤집는다.
  • ! SemEval Task 13 언어 목록은 출처 간 불일치가 있다 — 공식 README(training: C++/Python/Java, unseen: Go/PHP/C#/C/JS)와 overview paper Table 1(C, C#, C++, Go, Java, JavaScript, Python)이 PHP/C 표기에서 어긋난다. 언어를 열거해야 하면 "multiple languages including …" 형태로 완화하거나 공식 dataset label 파일로 재확인하라.
  • ! Droid 는 탐지기 이름이 아니라 suite 이름이다 — DroidCollection(데이터) + DroidDetect(탐지기) 구성. "Droid 탐지기가 …"라고 쓰면 부정확하다.
  • ! "근거 없음"을 발견하면 규칙을 지우지 말고 등급을 내려라 — 실측이 있는 규칙은 관측 컨벤션으로 살아남는다. 지우면 프로젝트가 실제로 지키던 관례가 사라지고, 논문을 붙이면 거짓이 된다. 세 번째 선택지가 정답이다.
  • ! 탐지 문헌은 "하지 않을 것"을 정의할 때만 인용된다 — 이 문서 외의 다른 리서치 문서에서 탐지 논문을 규칙 근거로 재인용하지 마라. 나머지 문서의 근거 축은 가독성·유지보수 문헌(Ousterhout, Fowler, Beck, 공식 스타일 가이드)이다.
