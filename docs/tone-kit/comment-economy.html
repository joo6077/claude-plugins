주석은 공짜가 아니라 코드와 함께 썩는 자산이다. 남길 이유를 대지 못하면 지운다. 스택·언어에 무관한 코어 원칙 9개와 삭제/보존 판정 절차, 그리고 실측에서 나온 수치 기준을 정리한다. 실측 표본은 57파일 / 안티패턴 약 275건이었고 그중 보존 가치가 있던 것은 약 11%뿐이었다.

주석 하나를 집었을 때 위에서부터 순서대로 묻는다. 앞 단계에서 걸리면 뒤는 묻지 않는다. 중요한 것은 "지울까?"가 아니라 "옮길 곳이 있는가?"다 — 정보가 실제로 필요한데 위치만 틀린 경우가 섞여 있다.

START

주석 하나를 집는다

파일 단위로 훑되 판정은 주석 단위로 한다. 정규식으로 유형을 한 번에 지우면 계약 doc과 실패 모드 주석까지 매칭된다.

Q1

코드가 이미 같은 말을 하고 있는가?

타입·이름·시그니처가 말하는 것을 문장으로 반복했는가. 템플릿 마커(// 상태, // 구현부), 구분선 블록(// ----), 이름 번역 주석(// 버튼 텍스트), 프레임워크 기본 동작 설명이 여기에 걸린다.

Yes삭제. 정보량 0이고 코드가 바뀌면 거짓이 된다. 구획이 필요하면 빈 줄과 함수·파일 분리로 표현한다.
NoQ2로 내려간다.
Q2

주석이 있어야 이해되는 이름인가?

주석을 달아야 이해되는 이름은 이름 자체가 결함이다. 설명을 붙이는 대신 역할명으로 바꾼다(red → error, surface → cardBackground).

Yes이름으로 이동. 이름을 먼저 고치고 나서 주석을 지운다. 순서를 뒤집으면 정보가 순삭된다.
NoQ3으로 내려간다.
Q3

보존 3범주에 해당하는가?

보존 게이트

읽다가 "왜 이렇게 했지?"가 생기는 지점만 기록한다. 실무에서 이 조건을 통과하는 것은 대체로 아래 셋이다. 사전 카테고리를 미리 늘리지 않는다 — 새 유형은 실제로 겪은 뒤에 추가한다.

Yes보존. 단, what이 아니라 why로 다시 쓴다. 대안을 버린 근거가 문장에 들어 있어야 한다.
NoQ4로 내려간다.
Q4

공개 API의 계약 정보인가?

파라미터 의미, 반환값, 오용을 유발하는 규칙(옵션 A를 넘기면 옵션 B가 무시됨 등)이면 계약이다. 계약은 라인 주석이 아니라 문서 주석으로 승격한다.

Yesdoc 주석으로 이동. 공개 API에는 문서 주석을 단다 — 이 항목만 MUST다.
NoQ5로 내려간다.
Q5

해설이 3줄을 넘는가?

긴 해설이 필요하다는 것은 흐름이 이미 인지 한계를 넘었다는 신호다. 주석이 아니라 그 구조를 줄여야 한다. "여기 복잡하니 설명을 달자"는 순간이 함수를 쪼갤 순간이다.

Yes함수 경계로 이동. 리팩토링 신호로 간주하고 구조를 분해한다. 중첩 삼항은 1단까지만.
No마지막 판정으로.

다섯 질문 모두 걸리지 않으면 → 삭제

남길 이유를 대지 못한 주석은 남길 이유가 없는 주석이다. 기본값은 삭제이고, 보존이 예외다.

Q3 보존 3범주 — 이것만 살린다

1

프레임워크 함정

프레임워크·런타임의 비직관적 기본 동작. 코드만 봐서는 왜 이 순서, 왜 이 플래그인지 추론할 수 없는 지점이다.

2

제약 · trade-off

외부 API가 강제하는 제약. 내부 하드코딩 값, 변경 불가 옵션처럼 우리가 고른 게 아니라 받아들인 조건.

3

실패 모드

재현된 실패 모드. 이 구조를 바꾸면 특정 버그가 되살아난다는, 실제로 겪어 본 사실.

세 범주 어디에도 안 들어가는데 "혹시 몰라서" 남기는 것은 보존이 아니라 유예다.

원칙 9개 — 강도 · 축

실측에서 안티패턴 275건 중 보존 가치가 있던 주석은 약 30건(11%)뿐이었고, 나머지는 전부 코드를 다시 읽어 준 문장이었다.

안티패턴 목록보다 이 섹션이 더 중요하다. 목록만 보고 달려들면 보존 대상 약 11%가 같이 날아가고, 새 인원이 프레임워크 함정을 코드만으로 추론해야 한다.

1

전면 삭제로 과교정

안티패턴 목록만 보고 일괄 삭제하면 보존 대상 약 11%가 같이 날아간다. 삭제 전에 원칙 5의 세 범주에 걸리는지 먼저 판정하라.

2

탐지 회피를 목표로 삼기

"AI 티 지우기"를 목적으로 두면 문장이 더 인위적으로 꼬인다. 목표는 읽기 쉬움이고 톤 개선은 부산물이다.

3

주석만 지우고 이름은 그대로

번역 주석이 붙어 있었다는 것은 이름이 약했다는 증거다. 주석만 지우면 정보가 순삭되고 다음 사람이 같은 주석을 다시 단다. 원칙 3을 먼저 적용하라.

4

정규식 일괄 치환

유형별 패턴은 겹쳐 있어서 한 번에 지우면 계약 doc과 실패 모드 주석까지 매칭된다. 파일 단위로 보존 후보를 먼저 표시한 뒤 나머지를 지운다.

5

한 파일만 정리하고 종료

형제 파일이 옛 정책으로 남으면 일관성이 깨진 상태가 새 기준이 된다. 카테고리 전체를 범위로 잡거나 아예 착수하지 마라.

6

주석으로 리팩토링을 대체

"여기 복잡하니 설명을 달자"는 순간이 함수를 쪼갤 순간이다. 해설이 3줄을 넘으면 구조 문제로 간주하라.

7

삭제 대상과 이동 대상을 혼동

정보가 실제로 필요한데 위치가 틀린 경우가 있다. 목적지는 셋이다.

① 이름으로

번역 주석 → 역할명 (원칙 3 / Q2)

② 함수 경계로

긴 해설 → 구조 분해 (원칙 7 / Q5)

③ 공개 API 계약 doc으로

계약 정보 → 문서 주석 (원칙 6 / Q4)

착수 전 체크리스트

배치 정리를 시작하기 직전에 한 번 훑는다. 원칙 8(카테고리 단위 통일)이 여기서 강제된다.

  • 1범위를 카테고리로 잡았는가 — 같은 디렉토리·같은 역할의 형제 파일이 전부 범위에 들어왔는지. 한 파일만 하고 끝내면 일관성이 깨진 상태가 새 기준이 된다.
  • 2첫 파일에서 정책을 확정했는가 — 주석 밀도, doc 주석 적용 범위, 헤더 고정 필드를 첫 파일에서 정하고 나머지에 일괄 적용한다.
  • 3보존 후보를 먼저 표시했는가 — 삭제 전에 프레임워크 함정 / 제약·trade-off / 실패 모드 세 범주에 걸리는 주석을 파일 단위로 마킹한다.
  • 4정규식 일괄 치환을 쓰고 있지 않은가 — 유형별 패턴이 겹쳐 계약 doc과 실패 모드 주석까지 매칭된다.
  • 5이름 개선을 주석 삭제보다 먼저 했는가 — 번역 주석은 이름 결함의 증거다. 순서를 뒤집으면 정보가 순삭된다.
  • 63줄 넘는 해설을 리팩토링 신호로 처리했는가 — 설명을 다듬는 대신 구조를 줄인다. 중첩 삼항은 1단까지.
  • 7공개 API 계약이 doc 주석에 있는가 — 파라미터 의미·반환값·오용 규칙. 이 항목만 MUST다.
  • 8목표가 "AI 티 지우기"로 바뀌지 않았는가 — 목표는 읽기 쉬움이다. 톤 개선은 부산물일 뿐이다.
