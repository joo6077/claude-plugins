Korean Technical Writing — 한국어 축 SSOT

한국어로 쓰는 주석·doc 의 문체 규칙을 정의한다. 번역투 제거, 종결형, 외래어 처리, 용어 번역표 작성이 대상이다. 이 문서가 "한국어 의존" 축의 SSOT 다 — 다른 문서는 한국어 규칙을 다시 정의하지 말고 여기를 가리킨다. 소스: docs/tone/korean-technical-writing.md v0.1.0 · 2026-08-28.

3축 직교 — 스택 · 언어 · 프로젝트

규칙의 의존성은 세 축으로 나뉜다. 스택 축(Dart/Flutter · Rust · TypeScript), 언어 축(한국어 · 영어), 프로젝트 축(강도 승격 · 도메인 어휘)이다. 세 축은 서로를 결정하지 않는다. 그래서 규칙 하나를 고칠 때 어느 축을 건드리는지부터 정한다.

원칙 8개 — 강도 · 축 배지

강도는 3단계다. MUST 는 킷 구조를 결정하고, SHOULD 는 공개 근거가 있으며 프로젝트가 MUST 로 올릴 수 있고, 관측 컨벤션 은 실측 근거만 존재한다. 축 배지는 그 규칙을 어느 문서가 소유하는지 가리킨다.

1

한국어 축은 스택 축과 직교한다

MUST[코어][한국어]킷 구조 결정

dart doc 의 - 반환값: 라벨이 대표 사례다. 이 라벨은 Dart 의존이 아니라 한국어 의존이다. 같은 규칙을 영어 프로젝트로 옮기면 표기만 바뀌고 구조는 그대로 남는다. 어댑터 문서는 라벨 상수와 주석 문법만 정의한다.

2

번역투 킬러 패턴 6종을 제거한다

SHOULD[한국어]MUST 승격 가능

6개 패턴이 AI 톤을 가장 강하게 만든다. 각각 원인이 되는 영어 구문과 대체형이 정해져 있다. 종결형 규칙과 독립이므로 치환 뒤에 6종을 따로 잡는다.

3

능동형·주체 직설·원인 결과 구체성으로 대체한다

SHOULD[한국어]

패턴을 지우는 것만으로는 문장이 완성되지 않는다. 능동형으로 쓰고, 주체와 결과를 직설로 밝히고, 원인과 결과를 구체적으로 연결한다. 문장 수사보다 정보 설계가 먼저이고, 주석의 값어치는 what 이 아니라 why 에서 나온다.

→ LINE 테크니컬 라이팅
4

종결형은 한다체 하나로 고정한다

관측 컨벤션[코어][한국어]

doc 본문 동사는 한다체로 고정한다. 만든다 · 수집한다 · 건너뛴다 · 검증한다 · 조립한다 처럼 쓰고 합니다체와 명사형 종결을 섞지 않는다. 한 코드베이스에 두 종결형이 공존하면 grep 기준이 무너진다. 인라인 // 주석은 예외다 — 파편형·단문을 허용하고, 코드만 읽어도 뜻이 통하면 아예 지운다.

5

외래어는 3원칙으로 가른다

SHOULD[한국어]

공식 API 이름은 영어 원문, 일반 명사는 한국어, 음역은 금지다. 경계에 정착 외래어가 있고, 정착 여부는 팀이 판정한 뒤 결과를 용어 번역표에 적는다. 코드 식별자는 이 규칙의 대상이 아니다.

6

이름 번역 주석은 한국어 프로젝트 고유의 최대 덩어리다

SHOULD[코어][한국어]

식별자가 영어이고 주석이 한국어라서 번역 주석이 정보를 더하는 것처럼 보인다. 실제로는 같은 내용의 반복이다. 영어 단일 언어 프로젝트라면 // button text 는 누구도 안 쓴다.

String? text,        // 버튼 텍스트   ← text 가 이미 '텍스트'
bool isChecked,      // 체크 여부     ← isChecked 가 이미 '체크 여부'
double min,          // 최소값        ← min 이 이미 '최소값'

처리 기준은 삭제다. 이름이 약해서 주석이 필요했다면 주석 대신 이름을 고친다. 남길 것은 이름·타입에서 안 읽히는 계약뿐이다 — 값의 우선순위, 무효화 조건, 허용 범위가 그것이다.

7

doc 라벨은 언어 의존 상수다 — 표기를 쪼개지 마라

관측 컨벤션[어댑터:dart-flutter][한국어]

파라미터·반환값 블록의 라벨은 자유 서술이 아니라 상수다. 한국어 프로젝트에서는 - [param]: 설명 과 - 반환값: 설명 두 형태로 고정한다. void 반환은 - 반환값: 없음 으로 쓰고 N/A 를 새로 도입하지 않는다. 본문은 한두 문장으로 끝낸다.

/// - [context]: 다이얼로그 표시용 빌드 컨텍스트

관측 컨벤션[코어][한국어]

원칙 5 의 3원칙만으로는 매번 판정이 갈린다. 판정 결과를 누적하는 표가 프로젝트마다 하나 있어야 하고, 그 표는 킷이 아니라 프로젝트 저장소에 둔다. 도메인 어휘와 정착 외래어 판정은 프로젝트마다 다르고, 공용 문서로 올리면 다른 프로젝트에 잘못된 번역을 강제한다.

Before / After — 주석 다시 쓰기 5쌍

원칙 3 의 대체 원칙을 문장 단위로 적용한 결과다. 세 번째 쌍은 번역투(~에 의해)와 음역(오버레이)이 함께 걸린 사례다. 한 문장이 두 규칙을 동시에 어기는 일이 흔하므로 고칠 때 둘 다 본다.

!

부분 변경이 검색 게이트를 깬다

라벨을 "더 자연스럽게" 다듬고 싶어지는 순간이 온다. 이것은 상수다. 표기를 바꾸려면 전수 치환을 같이 하고, 부분 변경은 금지다.

  • !- 반환값: 을 - 리턴: 이나 - 결과: 로 바꾸면 577건짜리 커버리지 측정이 그 자리에서 무너진다.
  • !void doc 에 N/A 를 새로 들이면 한 프로젝트 안에서 상수가 두 표기로 쪼개진다.
  • !- 반환값: 없음 을 지우면 "doc 이 없는 것"과 "반환값이 없는 것"을 구분할 수 없다.

외래어 3원칙

세 갈래로 가른 뒤, 경계에 걸린 단어만 용어 번역표로 넘긴다.

1

공식 API 이름은 영어 원문

surface tint, BoxDecoration, strokeAlign 을 번역하지 않는다. 문서·검색·자동완성이 전부 원문 기준으로 움직인다.

원문 유지
2

일반 명사는 한국어

배경색, 그림자, 테두리. 원문을 남길 이유가 없으면 한국어가 기본값이다.

한국어 기본값
3

음역 금지

보더 라디우스 는 쓰지 않는다. 한국어도 영어도 아니라 검색이 안 되고 공식 API 이름과도 어긋난다.

금지
허용 정착 외래어
  • ✓다운로드 · 업로드
  • ✓파싱 · 파일 · 폴더
  • ✓이미 한국어 어휘로 굳은 말이라 그대로 쓴다
금지 굳지 않은 음역
  • ✗잡(job) → 작업
  • ✗큐(queue) → 대기열
  • ✗보더 라디우스 → 공식 API 이름을 원문으로 쓴다

코드 식별자는 이 규칙의 대상이 아니다

타입·함수·변수·메서드 이름은 영어를 그대로 둔다. 번역하면 doc 링크가 끊긴다. 음역 금지는 한국어 본문만 겨냥한다. 정착 여부는 팀이 판정하고 결과를 용어 번역표에 적는다(원칙 8).

용어 번역표 — 작성 규칙 (표 내용은 프로젝트 소유)

  • 13열 고정 — 용어(영어 원문) / 주석에서 쓸 표기 / 비고(판정 근거). 비고에는 Material 3 API, 일반 명사, 음역 금지 처럼 원칙 5 의 어느 갈래인지 적는다.
  • 2판정이 갈렸던 것만 올린다 — 원칙 5 로 자명하게 갈리는 단어를 전부 나열하면 표가 규칙을 대체해 버린다. 초기 규모는 6행 안팎이면 충분하다.
  • 3새 케이스가 생길 때 한 행씩 늘린다 — 표를 미리 채우지 않는다.
  • 4기준 코드베이스를 명시한다 — 애매하면 어느 디렉토리의 네이밍을 따를지 표 하단에 적는다.
  • 5AI 톤 오염 영역은 기준으로 삼지 않는다 — 오염된 표기가 표를 통해 정식 규칙으로 승격된다.

Bad ~을 처리합니다 로 doc 본문 종결동사가 비어 메서드명을 한국어로 반복하는 데 그친다. 주석이 정보를 0 만큼 더한다
Bad 종결어미만 한다체로 바꾸고 끝내기~에 의해 · ~되어 있는 경우 는 종결형과 무관하다. 문장 구조가 그대로면 번역투도 그대로다
Bad 보더 라디우스 같은 음역한국어도 영어도 아니라 검색이 안 되고 공식 API 이름과도 어긋난다
Bad 코드 식별자를 한국어로 번역doc 링크가 끊기고 코드와 문서가 어긋난다. 음역 금지는 본문에만 적용된다

Bad - 반환값: 없음 을 노이즈로 보고 삭제"doc 이 없는 것"과 "반환값이 없는 것"을 구분할 수 없게 된다

Gotchas — 반복 실수 6가지

규칙을 알고도 매번 같은 자리에서 미끄러진다. 아래 6개는 그 자리를 미리 표시한 것이다.

  • !번역투는 종결어미 문제가 아니라 문장 구조 문제다 — 합니다 를 한다 로 바꾸는 치환은 30초면 끝나고, 그래서 그것만 하고 완료로 보고하게 된다. 킬러 패턴 6종은 종결형과 독립이므로 치환 후에 6종을 따로 grep 한다.
  • !라벨을 "더 자연스럽게" 다듬으면 grep 이 깨진다 — - 반환값: 을 - 리턴: 이나 - 결과: 로 바꾸고 싶어지는 순간이 온다. 이것은 상수다. 표기를 바꾸려면 전수 치환을 같이 하고, 부분 변경은 금지다.
  • !정착 외래어와 음역의 경계는 팀이 한 번 정하고 끝낸다 — 파싱 은 허용이고 보더 라디우스 는 금지라는 판정에 일반 규칙은 없다. 매번 재논쟁하지 말고 판정을 용어 번역표에 적어 다음 세션이 그것을 읽게 한다.
  • !규칙 문서 자신이 번역투를 쓴다 — 규칙을 설명하는 문장에서 번역투가 특히 잘 나온다. 문서를 다 쓴 뒤 자기 본문에 6종을 grep 하는 자기모순 검사를 한 번 돌린다.
  • !다른 스택 어댑터가 생길 때 이 문서를 복사하지 마라 — Rust 나 TypeScript 어댑터가 필요해지면 라벨 상수와 주석 문법만 그쪽에 정의하고 문체는 이 문서를 참조한다. 복사하는 순간 두 벌이 갈라지고, 갈라진 사실을 아무도 모른다.
  • !AI 톤이 낀 영역을 번역 기준으로 삼으면 오염이 승격된다 — "기존 코드가 이렇게 쓰니까" 로 표기를 정하면, 정리 대상이던 표기가 표를 통해 정식 규칙이 된다. 기준 디렉토리는 정리 이력이 없는 쪽으로 명시한다.
