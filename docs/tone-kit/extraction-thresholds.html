Extraction Thresholds — 언제 추출하고 언제 두는가

메서드 추출 · 클래스 추출 · 인라인 유지 중 무엇을 고를지의 판단 기준. 과잉 추출(pass-through 래퍼, 헬퍼 체인)과 과소 추출(비대한 단일 build) 양방향을 같은 잣대로 다룬다. 이 문서의 상위 원칙은 관심사가 다르면 분리한다 하나이고, 줄 수·헬퍼 개수는 그 원칙을 다시 묻게 만드는 트리거일 뿐이다.

판정 위계 — 무엇이 판정하고 무엇이 알람인가

이 페이지를 줄 수 기준표로 읽으면 정확히 반대로 쓰게 된다. 분리 여부를 결정하는 것은 관심사 하나뿐이고, 임계치는 "이미 늦었다"를 알리는 하한 알람이다. 알람은 재점검을 요청할 수 있을 뿐 판정을 대신하지 못한다.

Tier 1 · 판정식

관심사가 다른가?

책임이 다른 것이 한 함수·클래스·파일에 섞여 있으면 분리한다. 하나면 두께와 무관하게 유지한다. Fowler 의 기준도 길이가 아니라 "의도와 구현을 분리할 수 있는가"다. 분리 여부는 이 층에서만 결정된다.

파일 500줄 초과, 위젯 반환 헬퍼 8개 이상 같은 값은 하한 알람이다. 넘었다는 사실 자체가 분리 사유가 되지 않으며, 넘지 않았다는 사실도 유지 사유가 되지 않는다. 알람이 울리면 Tier 1 을 다시 묻는다.

추출 판정 절차 — 조기 종료 순서도

위에서부터 순서대로 통과시킨다. 각 게이트는 "여기서 끝날 수 있다"는 조기 종료구를 갖는다. 중요한 것은 결론이 아니라 어느 게이트에서 멈췄는지다 — 멈춘 게이트가 곧 판정 근거이므로, 리뷰나 커밋 메시지에는 "추출함/안 함"이 아니라 멈춘 게이트를 남긴다.

G0

불필요 분기부터 지운다

실사용 조합이 하나인데 null 조합 4가지를 방어하고 있다면 그 복잡도는 실제 복잡도가 아니라 가상 복잡도다. 추출로 감출 대상이 아니라 삭제 대상이다. 조합 제약은 흐름이 아니라 생성자 assert 같은 경계에서 표현한다.

G4

추출한다 — 형태와 격리 조건을 확정

헬퍼 메서드보다 위젯 클래스를 선호하되 금지는 아니다. rebuild 격리를 노렸다면 동일 인스턴스가 전달되는지, 상태 소유 위치가 이미 leaf 로 내려가 있는지까지 확인해야 격리가 실제로 발생한다. 파일 단위로 뺄지는 성능이 아니라 탐색성 근거로 결정한다.

최종 추출 — 근거 병기

판정 근거: 관심사 분리 + (선택) rebuild 빈도. 강도를 MUST 로 올릴 때는 사유를 규칙 옆에 적는다. (원칙 3·4·5·7)

규칙 강도 — 어디까지가 공개 근거인가

이 문서의 원칙은 두 종류다. 공개 1차 출처가 지지하는 SHOULD 와, 공개 근거가 없는 관측 컨벤션. 둘을 같은 무게로 읽으면 관측 컨벤션이 표준처럼 유통된다.

!

공개 문서는 권고 수준까지만 지지한다

Flutter 공식 문서의 문구는 prefer 이고, 큰 build() 에 대한 공식 LOC 임계값은 존재하지 않는다. 공식 반례도 같은 문서군 안에 있다 — Builder 는 스스로를 클래스 정의의 인라인 대안이라고 밝히고, 공식 마이그레이션 문서에는 위젯 반환 함수 예시가 실려 있다. 따라서 단순 조건 분기나 아주 작은 local glue 까지 MUST NOT 으로 금지할 공개 근거는 없다.

관측 컨벤션 — 공개 근거 없음

  • !"모든 하위 단위를 별도 파일로" — 공개 1차 출처는 "different widgets" 까지만 지지하고 "different files" 는 지지하지 않는다. 파일 분리를 성능 문서로 정당화하면 안 된다. 근거는 탐색성이다. (원칙 7)
  • !헬퍼 체인 허용 깊이 0단 — 체인 깊이 임계값을 명시한 공개 1차 출처는 없다. (원칙 6)
  • !반복 3회 추출 임계 — 원칙 9 의 본체는 공개 근거를 갖지만 3회라는 숫자 자체는 관측 컨벤션이다.

강도를 올리려면 사유를 함께 적어라

  • →원칙 3 을 프로젝트 규칙에서 MUST 로 승격할 수 있는 범위는 성능 핫스팟이거나 자주 rebuild 되는 큰 subtree 에 한한다.
  • →승격하는 경우 승격 사유(프로파일링 결과 또는 rebuild 빈도)를 규칙 옆에 명시해야 한다. 사유 없는 전역 MUST 는 킷의 창작이다.
  • →사유 없이 MUST 로 쓰면 나중에 그 규칙이 왜 있는지 아무도 재구성하지 못하고 규칙만 남는다.

1

관심사가 다르면 분리한다 — 줄 수는 트리거일 뿐 기준이 아니다

SHOULD코어

책임이 다른 것이 한 함수·클래스·파일에 섞여 있으면 분리한다. 줄 수·헬퍼 개수 임계치는 "이미 늦었다"를 알리는 하한 알람이지 분리 여부의 판정식이 아니다. 임계치 미만이어도 관심사가 다르면 분리하고, 임계치를 넘겨도 관심사가 하나면 쪼개지 않는다.

Fowler 는 함수 길이 자체를 기준으로 삼지 않는다. 기준은 "의도와 구현을 분리할 수 있는가"다. 길이는 냄새를 알아채는 신호이지 규칙이 아니다. 공개 1차 출처는 길이 기준을 명시적으로 부정하지만 대체 판정식을 기계적으로 제시하지는 않는다 — 그래서 MUST 가 아니라 SHOULD 다.

3

큰 build() 는 분리한다 — 기준은 LOC 가 아니라 rebuild 빈도다

SHOULD어댑터:dart-flutter조건부 MUST 승격 가능

Flutter 공식 성능 문서는 "Avoid overly large single widgets with a large build() function" 과 "Split them into different widgets" 를 권고한다. 다만 공식 문서에 LOC 임계값은 없다. 분리 기준은 줄 수가 아니라 encapsulation 과 "how they change" 다.

같은 문서군의 반대편도 읽어야 한다. StatefulWidget 문서는 "built once then never update" 하는 위젯에 대해 "somewhat complicated and deep build methods" 를 문제 삼지 않는다. 라우트 최상단처럼 사실상 rebuild 되지 않는 위젯의 큰 build 는 공식적으로 용인되는 영역이다. 반대로 build 는 "potentially as often as once per rendered frame" 호출될 수 있으므로, 프레임마다 재실행되는 큰 subtree 는 분리 우선순위가 높다.

4

헬퍼 메서드보다 위젯 클래스를 선호한다 — 그러나 금지는 아니다

SHOULD어댑터:dart-flutter

StatelessWidget 문서는 "prefer using a widget rather than a helper method" 라고 쓴다. 이유는 스타일이 아니라 메커니즘이다. 위젯으로 분리하면 프레임워크가 "short-circuit most of the rebuild work" 를 할 수 있는 지점이 생긴다. 헬퍼 메서드가 반환한 위젯은 그 지점이 없어 부모와 항상 함께 재실행된다.

반대 방향도 같이 알아야 한다. Flutter 는 클래스 추출을 우회하는 공식 API 를 스스로 제공한다. Builder 문서는 자신을 "inline alternative to defining a StatelessWidget subclass" 라고 정의한다. 공식 마이그레이션 문서에는 Widget _getToggleChild() 같은 위젯 반환 함수 예시가 실려 있고, 프레임워크 이슈 트래커에도 "reevaluate if we are making the right trade-off here between naginess and performance" 라는 논의가 남아 있다.

5

rebuild 격리를 노렸다면 격리 조건까지 확인하라

SHOULD어댑터:dart-flutter

위젯 클래스로 뺐다는 사실만으로 rebuild 가 끊기지 않는다. Element 는 "the same instance is returned each time" 인 경우에만 "the element skips updating itself" 한다. 매 build 마다 새 인스턴스를 만들어 넘기면 타입만 늘고 격리는 0 이다. 그리고 위젯 교체 판정은 runtimeType and key 로 이뤄지므로, 같은 타입에 다른 인자를 넘기면 element 는 갱신된다.

✗ 격리 안 됨
// 부모 build 마다 새 인스턴스
Column(children: [SectionHeader(title: title)])
✓ 격리 됨
// 동일 인스턴스 (const)
const Column(children: [SectionHeader(title: '설정')])

상태 소유 위치가 추출보다 먼저다. setState 는 "possibly triggering rebuilds for the entire subtree rooted at this widget" 이므로, 상태를 상위에 둔 채 하위만 쪼개면 분리 효과가 상쇄된다.

6

헬퍼가 헬퍼를 부르는 체인은 만들지 않는다

관측 컨벤션코어

build() → _buildA() → _buildB() 식 체인은 주 흐름을 읽기 위해 왕복 이동을 강제한다. 허용 깊이는 0 단 — 헬퍼가 다른 헬퍼를 호출하면 인라인하거나 별도 위젯으로 승격한다. 각 단계의 이름이 본문보다 의미를 더하는지 개별 판정하면, 체인 중간 단계는 대개 원칙 2 의 Inline 대상으로 떨어진다.

강도 주의. 체인 깊이 임계값을 명시한 공개 1차 출처는 없다. 관측 프로젝트 규칙(2026-04-17 제정, 위젯 리팩토링 세션 피드백)이며 아래 링크는 보조 근거다.

7

"모든 sub-widget 은 별도 파일" 은 관측 컨벤션이다

관측 컨벤션어댑터:dart-flutter

관측 프로젝트는 위젯 조각을 같은 파일 인라인 클래스로도 두지 않고 예외 없이 별도 파일로 뺀다. thin wrapper 도 예외가 아니며, 파일이 private 접두사를 못 쓰므로 public 클래스 + 프로젝트 접두사({widget_prefix}) 규칙과 짝을 이룬다. 이유는 성능이 아니라 탐색성이다 — 화면 파일이 길어지면 로직을 찾기 어렵다.

공개 1차 출처는 "different widgets" 까지만 지지하고 "different files" 는 지지하지 않는다. 파일 분리를 성능 문서로 정당화하지 마라. 파일 단위 규칙을 쓰려면 근거를 프로젝트 탐색성으로 밝혀야 한다. 실측 범위는 Props 골격 보유 110 파일(2026-08-31 재측정)이다.

8

발생하지 않는 분기는 추출 대상이 아니라 제거 대상이다

SHOULD코어

실사용 조합이 하나인데 null 조합 4가지를 방어하면, 그 복잡도는 실제 복잡도가 아니라 가상 복잡도다. "현재 요구를 이해하기 어렵게 만드는 추상화는 presumed guilty" 다. 이런 코드는 헬퍼로 빼서 감출 게 아니라 지운다.

조합 제약은 흐름이 아니라 경계에서 표현한다. Flutter 자체 위젯도 build 안에서 모든 조합을 방어하지 않고 생성자 assert 로 유효 조합을 강제한다 — Tab 은 text/child 동시 사용을 막고, Positioned 는 left + right + width 동시 지정을 막는다. Dart 의 assert 는 debug 에서만 살아 있으므로 내부 호출자 대상 제약에 적합하고, 외부 입력 경계에는 명시적 검증을 쓴다.

pass-through 래퍼는 과분할이다

SHOULD코어3회 임계는 관측 컨벤션

받은 것을 그대로 넘기기만 하는 래퍼 레이어는 형제 위젯 유무와 무관하게 추가 간접층이다. 클래스가 제 몫의 책임을 갖지 못하면 Inline Class 대상이다. 추출의 유일한 실효인 rebuild 격리조차, 형제가 싼 위젯이면 정당화되지 않는다.

같은 이유로 "재사용 가능성" 하나만으로 1회성 로직을 클래스로 승격하지 않는다. 실사용처가 1~2곳이면 인라인이 적정이고, 같은 패턴이 3곳 이상 반복될 때 추출을 검토한다. 다만 반복 3회 임계값 자체는 관측 컨벤션이다.

양방향 실패 모드 — 과소 추출 vs 과대 추출

이 문서는 한 방향만 막지 않는다. 거대 단위를 방치하는 과소 추출과 pass-through 래퍼를 쌓는 과대 추출은 같은 잣대(관심사)로 판정되며, 서로 반대 방향의 실패다. 한쪽만 경계하면 반대쪽으로 넘어간다.

⚠ 과소 추출 — 거대 단위

관심사가 섞였는데 그대로 둔다

  • !한 build() 에 레이아웃·상태 해석·포맷팅이 함께 산다 (원칙 1 위반)
  • !프레임마다 재실행되는 큰 subtree 가 통째로 남아 분리 우선순위를 놓친다 (원칙 3)
  • !헬퍼 메서드로만 쪼개서 프레임워크가 rebuild 를 short-circuit 할 지점이 없다 (원칙 4)
  • !탐지 신호: 파일 500줄 초과 또는 위젯 반환 헬퍼 8개 이상 — 알람이지 판정이 아니다
✗ 과대 추출 — pass-through 래퍼

관심사가 하나인데 쪼갠다

  • ✗받은 것을 그대로 넘기는 래퍼가 책임 없이 간접층만 늘린다 (원칙 9)
  • ✗이름이 본문과 같은 수준이라 읽기 비용이 정의부로 이동만 한다 (원칙 2)
  • ✗헬퍼가 헬퍼를 불러 주 흐름을 읽는 데 왕복 이동이 강제된다 (원칙 6)
  • ✗발생하지 않는 null 조합을 헬퍼로 감싸 가상 복잡도를 영구화한다 (원칙 8)
✓ 두 실패를 동시에 피하는 판정 순서

"과분할 금지"와 "관심사 분리 의무"는 충돌하지 않는다 — 판정 순서가 다를 뿐이다. 먼저 "관심사가 실제로 다른가"를 묻고(원칙 1), 다르면 분리한다. 같은데 길이만 길면 쪼개지 않는다.

pass-through 래퍼 금지(원칙 9)는 후자에만 적용되며, 관심사가 다른 sub-widget 추출 의무를 취소하지 않는다. 순서도의 G1 을 통과한 뒤에야 G2·G3 의 과대 추출 방지 게이트가 의미를 갖는다.

Gotchas — 7항목

이 규칙군을 적용할 때 반복적으로 어긋나는 지점들. 판정 전에 한 번 훑는다.

  • 1위젯 클래스로 뺀다고 paint boundary 가 생기지 않는다 — 리페인트 격리는 RepaintBoundary 라는 별도 메커니즘이고, 클래스 추출은 rebuild(위젯 재구성) 축이다. "쪼갰으니 다시 그리지 않는다"는 두 축을 섞은 오해다. 리페인트가 문제면 추출이 아니라 RepaintBoundary 를 검토하고, 경계 자체도 비용이 있으므로 남발하지 마라. (RepaintBoundary)
  • 2"과분할 금지"와 "관심사 분리 의무"는 충돌하지 않는다 — 판정 순서가 다르다. 먼저 "관심사가 실제로 다른가"를 묻고, 다르면 분리한다(원칙 1). 같은데 길이만 길면 쪼개지 않는다. pass-through 래퍼 금지(원칙 9)는 후자에만 적용되며, 관심사가 다른 sub-widget 추출 의무를 취소하지 않는다.
  • 3분리 강도를 프로젝트 규칙으로 올릴 때 사유를 같이 적어라 — 공식 근거는 SHOULD 까지다. rebuild 빈도나 프로파일링 결과 없이 MUST 로 쓰면, 나중에 그 규칙이 왜 있는지 아무도 재구성하지 못하고 규칙만 남는다.
  • 4상태 소유 위치를 안 고치고 하위만 쪼개면 격리가 없다 — setState 는 subtree 전체를 rebuild 시킨다. 추출 전에 상태를 leaf 로 내릴 수 있는지 먼저 본다. 순서를 뒤집으면 파일만 늘고 프레임 비용은 그대로다.
  • 5const 는 추출의 목적이 아니라 조건이다 — 클래스로 빼는 이유가 const 라면, 실제로 const 로 생성되는지까지 확인해야 이득이 발생한다. 동적 인자를 받는 위젯은 const 가 되지 않으므로 그 경우 추출 근거를 rebuild 격리가 아닌 관심사 분리로 다시 세워야 한다.
  • 6폐기 이력 — 원본 규칙 세트의 판단표와 1단 헬퍼 허용 조항은 2026-06-09 개정으로 폐기됐다. 본문은 이관하지 않는다. 아래 별도 블록 참조.
  • 7인용 금지 출처를 다시 끌어오지 마라 — 이 규칙군의 원본 근거였던 비공개 사내 가이드라인 문서는 공개 킷에서 인용할 수 없다. 위 원칙 3·4 의 공개 URL 이 대체 근거이며, 규칙 강도도 그 URL 의 문구 강도를 넘지 않는다.
