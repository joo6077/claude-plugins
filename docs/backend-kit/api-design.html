01 · Principles

원칙

공식 표준(RFC)과 업계 가이드라인에 근거한 REST API 설계 규칙 일곱 가지.

리소스와 메서드 원칙 1 · 2

1

URI는 리소스 명사 중심, 행위는 HTTP 메서드로 표현한다

/users(리소스)에 GET/POST/PUT/DELETE를 적용한다. /getUsers, /createUser 같은 동사 URI는 쓰지 않는다.

  • 컬렉션은 복수형 — /users
  • 개별 리소스는 식별자 — /users/{id}
  • 중첩은 2단계까지 — /users/{id}/orders
  • 그 이상은 독립 리소스로 승격한다
Microsoft REST API Guidelines
2

HTTP 메서드와 상태 코드는 RFC 의미론을 준수한다

  • GET: 안전(safe), 멱등(idempotent). 서버 상태를 변경하지 않는다.
  • POST: 리소스 생성. 201 Created + Location 헤더 반환.
  • PUT: 전체 교체(full replacement). 멱등.
  • PATCH: 부분 수정(partial update). 멱등성은 구현에 따라 다르다.
  • DELETE: 리소스 삭제. 멱등.

상태 코드 범위:

1xx정보
2xx성공
3xx리다이렉션
4xx클라이언트 에러
5xx서버 에러

100~599 범위에서 RFC 9110이 정의한 코드만 사용한다. 자체 정의 상태 코드는 금지.

RFC 9110 — HTTP Semantics

에러 응답 원칙 3

3

에러 응답은 application/problem+json(RFC 9457)으로 표준화한다

모든 4xx/5xx 응답은 다음 5개 필드를 포함한다.

필드설명
type에러 유형 URI (문서 링크)
title사람이 읽을 수 있는 짧은 설명
statusHTTP 상태 코드 (정수)
detail이 요청에 대한 구체적 설명
instance이 에러 발생의 고유 참조 URI
다섯 필드를 모두 넣는 것은 이 킷의 규칙이다. RFC 9457 은 type 이 없으면 about:blank 로 본다. 
{
  "type": "https://api.example.com/errors/insufficient-balance",
  "title": "Insufficient Balance",
  "status": 422,
  "detail": "계좌 잔액이 50,000원 부족합니다.",
  "instance": "/transfers/abc-123"
}
RFC 9457 — Problem Details for HTTP APIs

페이지네이션 원칙 4

4

큰 컬렉션은 cursor 기반 페이지네이션을 우선한다

Offset

장점
임의 페이지 점프 가능
단점
삽입/삭제 시 row 누락·중복, OFFSET N이 클수록 성능 저하

Cursor 우선

장점
일관된 결과, O(1) 탐색
단점
임의 페이지 점프 불가

Cursor 응답 형태:

{
  "data": [...],
  "next_cursor": "eyJpZCI6MTAwfQ==",
  "has_more": true
}
!

Offset은 데이터 변경이 드문 정적 목록(관리자 대시보드 등)에서만 사용한다. 실시간 피드, 타임라인, 검색 결과는 반드시 cursor를 쓴다.

스펙 · 버전 · 쿼리 원칙 5 · 6 · 7

5

OpenAPI 스펙은 코드와 항상 동기화한다

OpenAPI 3.2.1 스펙을 단일 소스로 유지한다. 코드에서 스펙을 생성하거나(code-first), 스펙에서 코드를 생성하는(spec-first) 방식 중 하나를 선택하되 혼용하지 않는다.

CI에서 스펙과 실제 응답의 불일치를 검증하는 계약 테스트를 실행한다.

OpenAPI Specification 최신판 3.2.1 OpenAPI 3.2.1 release
6

API 버전은 URL 경로 또는 헤더 방식 중 하나를 선택한다

  • URL 경로: /v1/users — 명시적, 캐싱 친화적.
  • 헤더: Accept: application/vnd.api+json;version=1 — URL 깔끔.

하이브리드(경로 + 헤더 동시 사용)는 혼란을 유발하므로 지양한다. 메이저 버전만 URL에 반영하고, 하위 호환 변경은 버전을 올리지 않는다.

원본 문서가 출처를 달지 않은 이 킷의 규칙이다.
7

필터와 정렬은 쿼리 파라미터로 표현한다

/users?status=active&sort=-created_at&fields=id,name 형태를 사용한다. 리소스 경로에 필터를 넣지 않는다 (/users/active 금지 — 이것은 active라는 ID의 사용자처럼 보인다).

복합 필터가 필요하면 둘 중 하나의 컨벤션을 선택한다.

  • LHS brackets — filter[status]=active
  • RHS colon — status:eq:active
원본 문서가 출처를 달지 않은 이 킷의 규칙이다.

03 · Anti-patterns

안티패턴

피해야 할 패턴과 그 이유. 아래 비교는 표와 원칙 1 · 3 · 6 · 7 을 요청 모양으로 옮긴 것이다.

안티패턴문제
GET 바디에 데이터 전송 RFC 9110은 GET 바디의 의미를 정의하지 않음. 프록시/캐시가 무시할 수 있다.
모든 응답 200 OK + 커스텀 에러 코드 HTTP 인프라(로드밸런서, 모니터링)가 에러를 감지 못한다.
버전 없는 API Breaking change 시 모든 클라이언트가 동시에 깨진다.
에러 포맷 비표준 클라이언트마다 파싱 로직이 달라지고, 에러 처리 자동화 불가.
GET 바디에 조건 싣기

프록시/캐시가 바디를 무시할 수 있다. 조건은 쿼리 파라미터로 보낸다(원칙 7).

나쁜 예 
GET /users
{ "status": "active" }
좋은 예 
GET /users?status=active&sort=-created_at
200 OK 에 자체 에러 코드 넣기

로드밸런서 · 모니터링이 에러를 못 본다. 상태 코드와 problem+json 다섯 필드로 답한다(원칙 3).

나쁜 예 
HTTP/1.1 200 OK
{ "success": false, "code": "E1001" }
좋은 예 
HTTP/1.1 422
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/insufficient-balance",
  "title": "Insufficient Balance",
  "status": 422,
  "detail": "계좌 잔액이 50,000원 부족합니다.",
  "instance": "/transfers/abc-123"
}
버전 없이 공개하기

깨지는 변경 한 번에 모든 클라이언트가 같이 깨진다. 메이저 버전만 경로에 싣는다(원칙 6).

나쁜 예 
GET /users
좋은 예 
GET /v1/users
동사를 URI 에 넣기

행위는 HTTP 메서드가 맡는다. URI 는 리소스 명사, 컬렉션은 복수형(원칙 1).

나쁜 예 
GET  /getUsers
POST /createUser
좋은 예 
GET  /users
POST /users
필터를 경로에 넣기

/users/active 는 active 라는 ID 의 사용자처럼 보인다(원칙 7).

나쁜 예 
GET /users/active
좋은 예 
GET /users?status=active
GET /users?filter[status]=active
04 · Gotchas

Gotchas

반복적으로 놓치는 함정과 확인해야 할 체크 포인트.

!
PATCH는 부분 수정이지 upsert가 아니다

리소스가 없으면 404를 반환해야 한다. upsert가 필요하면 PUT을 사용하거나 별도 엔드포인트를 만든다.

!
204 No Content는 body가 없어야 한다

일부 프레임워크가 빈 JSON {}을 반환하면 클라이언트 파서가 실패할 수 있다. Content-Length: 0이 올바른 동작이다.

!
Cursor 토큰이 영구 유효하다고 가정하면 안 된다

서버 재시작, 데이터 마이그레이션, TTL 만료로 cursor가 무효화될 수 있다. 클라이언트는 400 응답 시 처음부터 다시 시작하는 로직을 갖춰야 한다.
