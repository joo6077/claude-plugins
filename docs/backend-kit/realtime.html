Core Principles

원칙

실시간 통신은 프로토콜 선택만으로 끝나지 않는다. 수명 관리, 인증의 지속 검증, 확장 시의 fan-out, 순서 보장, 백프레셔까지 한 세트로 설계해야 한다.

1

프로토콜은 상호작용 패턴에 맞게 선택한다

WebSocket은 full-duplex 양방향으로 채팅, 게임, 협업 편집처럼 클라이언트-서버 양쪽이 자유롭게 메시지를 주고받는 경우에 쓴다. SSE(Server-Sent Events)는 서버→클라이언트 단방향으로 알림, 피드, 로그 스트리밍처럼 서버가 일방적으로 push하는 경우에 적합하다. Long polling은 최후의 fallback이다 — WebSocket/SSE를 지원하지 않는 환경에서만 쓴다. 상호작용이 필요하면 WebSocket, 단순 피드면 SSE를 선택한다.

RFC 6455 — WebSocket Protocol
2

WebSocket 수명 관리를 설계한다

HTTP Upgrade 핸드셰이크 이후 TCP 연결이 장시간 유지된다. heartbeat(ping/pong)로 연결 생존을 확인하고, clean close (1000 Normal Closure)로 정상 종료를 보장한다. 핸드셰이크만 하고 수명 관리를 생략하면 zombie connection이 계속 쌓여 서버 리소스를 잠식한다.

RFC 6455 — WebSocket Protocol
3

SSE는 브라우저 자동 재연결 + Last-Event-ID가 장점

EventSource API는 연결이 끊기면 자동으로 재연결하고, Last-Event-ID 헤더로 마지막으로 수신한 이벤트 ID를 서버에 전달한다. 서버가 event ID 전략을 올바르게 구현하면 유실 없는 재개가 가능하다. ID 없이 보낸 이벤트는 재개 불가능하다는 점에 유의한다.

HTML Living Standard — Server-Sent Events
4

인증은 연결 시점, 인가는 메시지 시점에도 계속 검증

연결 수립 시 토큰/쿠키로 1차 인증한다. 이후 권한 변경(역할 변경, 차단 등)이 발생할 수 있으므로 민감한 메시지나 채널 구독 시 message-level authorization을 추가로 검증한다. 연결만 인증하고 끝내면 권한이 회수된 사용자가 계속 데이터를 수신한다.

ASP.NET Core SignalR — Authn & Authz
5

연결 관리는 4종 세트로 완성한다

ping/pong으로 연결 생존 확인, heartbeat timeout 초과 시 연결 종료 판단, 재연결 시 exponential backoff로 서버 부하 방지, 재연결 후 resubscribe로 이전 구독을 자동 복원한다. 이 중 하나라도 빠지면 불완전한 연결 관리가 된다.

RFC 6455 — WebSocket Protocol
6

수평 확장 시 프로토콜별 특성을 고려한다

Long polling은 매 요청이 다른 서버에 갈 수 있어 sticky session이 필요하다. WebSocket은 단일 TCP 연결이라 sticky에 덜 민감하지만, 다수 서버 간 메시지 전달을 위해 Redis Pub/Sub 등 브로커로 fan-out 해야 한다. 프로토콜 선택 시점에 확장 전략도 함께 결정한다.

Socket.IO — Using Multiple Nodes
7

메시지 순서는 연결 단위일 뿐 전체 시스템 순서가 아니다

단일 WebSocket/SSE 연결 내에서는 순서가 보장된다. 그러나 재연결, 멀티노드 fan-out, 네트워크 분할 상황에서는 전체 순서가 보장되지 않는다. 전역 순서가 필요하면 시퀀스 번호나 벡터 클럭 같은 별도 메커니즘을 도입해야 한다.

Redis — Pub/Sub
8

백프레셔를 명시적으로 설계한다

서버가 클라이언트보다 빠르게 메시지를 생산하면 outbound buffer가 무한히 증가한다. 브라우저 WebSocket API는 백프레셔 메커니즘을 제공하지 않으므로, 서버에서 queue length 상한과 drop/throttle 정책을 구현해야 한다. bufferedAmount는 관찰용일 뿐 흐름 제어가 아니다.

MDN — WebSockets API
Numeric Standards

수치 기준

실시간 프로토콜 스펙에 명시된 상수와 업계 표준 구현체의 기본값. 이 수치들을 기준선으로 두고 프로젝트 특성에 맞게 조정한다.

항목 값
WS control opcode Close 0x8, Ping 0x9, Pong 0xA
Control frame payload 상한 125 bytes
SSE readyState 0=CONNECTING, 1=OPEN, 2=CLOSED
Socket.IO pingInterval / pingTimeout 25s / 20s
Redis Pub/Sub 전달 보장 at-most-once (구독자 부재 시 유실)
Reconnect backoff 시작 0.5s → max 30s
Heartbeat 간격 권장 15~30s
Anti-patterns

안티패턴

실시간 시스템에서 반복적으로 발견되는 실패 패턴. 각 항목마다 왜 문제가 되는지와 올바른 대안을 함께 기록했다.

모든 실시간을 무조건 WebSocket
Bad
단방향 알림 피드까지 WebSocket으로 구현해 양방향 프로토콜의 복잡도와 연결 관리 비용을 떠안는다.
Good
단방향이면 SSE. 브라우저 자동 재연결 + Last-Event-ID로 HTTP 기반 단순성과 재개 품질을 동시에 얻는다.
Connection 인증만 하고 message authz 생략
연결 시점에 토큰만 확인하고 이후 메시지에는 권한 체크를 생략한다. 권한 변경(역할 박탈, 차단)이 발생해도 기존 연결은 계속 데이터를 수신 — 민감 정보가 권한 회수 후에도 흐른다. 채널 구독/메시지 발송 시 현재 권한을 재검증해야 한다.
Long polling + 멀티노드에 sticky session 없음
매 요청이 다른 서버로 라우팅되어 세션 상태를 찾지 못하고 연결이 반복 실패한다. Long polling은 반드시 sticky session과 세트. 또는 session 상태를 Redis 같은 공유 스토어에 올려 stateless로 만든다.
Redis Pub/Sub를 durable queue로 사용
Redis Pub/Sub는 at-most-once이므로 구독자가 연결되지 않은 동안의 메시지는 사라진다. "잠깐 끊겼다가 다시 붙으면 복구" 같은 기대를 하면 안 된다. 재전송이 필요하면 Redis Streams 또는 Kafka 같은 durable broker를 쓴다.
Outbound buffer 상한 없이 push
느린 클라이언트가 한 명이라도 있으면 서버 outbound buffer가 무한 증가해 OOM으로 이어진다. queue length 상한 + drop/throttle 정책(가장 오래된 메시지 폐기, 중요도 기반 선별 등)이 반드시 필요하다.
Gotchas

체크리스트

문서를 읽고도 놓치기 쉬운 함정들. 구현 전 한 번, PR 올리기 전 한 번 훑어본다.

  • SSE 자동 재연결이지만 서버 event ID 전략이 없으면 복구 품질이 낮다 브라우저가 재연결해도 서버가 Last-Event-ID를 처리하지 않으면 유실된 이벤트를 복구할 수 없다. ID 없이 보낸 이벤트는 재개 불가능하다.
  • WebSocket API는 백프레셔가 약하다 bufferedAmount 속성으로 미전송 데이터 크기를 확인할 수는 있지만 흐름 제어 메커니즘은 아니다. 서버에서 queue length 모니터링과 drop 정책을 직접 구현해야 한다.
  • Redis Pub/Sub는 메시지 유실을 허용한다 구독자가 없거나 연결이 끊긴 동안의 메시지는 사라진다. 재전송이 필요한 시나리오에서는 Redis Streams나 별도 메시지 브로커(Kafka 등)를 사용해야 한다.
