Backend Kit v0.1

GraphQL

Versionless evolution, nullability, 커서 기반 페이지네이션, N+1 해결, demand control, persisted query, Apollo Federation, subscription, 에러 처리 — 스펙과 프로덕션 운영 양쪽을 모두 고려한 GraphQL 설계 가이드.

Principles

10가지 핵심 원칙

graphql.org, GraphQL Spec(October 2021), Apollo GraphOS 문서, DataLoader 레퍼런스 구현을 근거로 한 설계 원칙. 각 카드의 링크로 1차 출처를 확인할 수 있다.

01
Versionless evolution이 기본이다

스키마에 버전 번호를 붙이지 않는다. field/type 추가와 @deprecated(reason:) 디렉티브로 진화한다. 삭제는 실제 사용량이 0에 수렴한 후에만 수행한다. REST와 달리 클라이언트가 필요한 필드만 요청하므로 추가는 breaking change가 아니다.

GraphQL — Schema Design
02
Nullability는 보수적으로 설정한다

non-null(!)로 선언한 필드가 런타임에 null을 반환하면 해당 필드뿐 아니라 상위 nullable 부모까지 null-bubble이 전파된다. "이 필드는 절대 null이 아니다"는 강한 보장이므로, 확신이 없으면 nullable로 두고 클라이언트가 처리하게 한다.

Schema Design GraphQL Spec
03
대량 리스트는 cursor-based connection

Relay 스타일 connection(edges / node / cursor / pageInfo)을 표준으로 채택한다. offset pagination은 공개 스키마 표준으로 적합하지 않다. connection은 양방향 탐색, 총 개수 힌트, 커서 기반 안정적 순회를 제공한다.

GraphQL — Pagination
04
N+1 문제는 DataLoader로 해결한다

DataLoader는 요청(request) 범위에서 동일 리소스에 대한 개별 fetch를 배치(batch)로 묶고, 같은 키를 캐싱하여 중복 조회를 제거한다. resolver마다 개별 DB 쿼리를 실행하면 필드 수에 비례하여 쿼리가 폭증한다.

graphql/dataloader
05
Demand control은 여러 기법을 조합한다

depth limiting, breadth/alias limiting, batch query limiting, complexity analysis를 함께 적용한다. 단일 기법만으로는 우회가 가능하다. complexity budget은 필드별 가중치를 부여하여 쿼리 비용을 사전에 계산한다.

GraphQL — Security
06
Persisted query / trusted documents

클라이언트가 전체 쿼리 문자열 대신 해시(APQ ID)를 전송하여 네트워크 비용을 줄이고, 서버는 allowlist에 등록된 쿼리만 실행한다. first-party 앱은 빌드 시 쿼리를 추출하여 allowlist를 생성한다.

GraphQL — Security
07
Federation은 단일 supergraph 계약

각 팀이 독립적으로 subgraph를 개발·배포하되, composition(스키마 병합)의 안정성을 최우선으로 관리한다. entity ownership을 명확히 하고, @key 디렉티브로 subgraph 간 참조를 정의한다.

Apollo Federation
08
Subscription은 신중하게 사용한다

subscription root field는 정확히 1개만 허용한다. stateful transport(WebSocket)와 pub/sub 인프라가 필요하므로 query/mutation보다 운영 비용이 높다. 폴링으로 충분한 경우 subscription을 쓰지 않는다.

GraphQL Spec
09
에러는 errors[] + partial data로 전달

GraphQL 응답은 data와 errors를 동시에 포함할 수 있다. request error는 data가 없고, execution error는 data에 부분 결과와 함께 errors가 온다. 에러를 200 + 불투명 메시지로만 반환하면 클라이언트가 부분 렌더링을 할 수 없다.

GraphQL Spec
10
Breaking change는 schema diff + usage

스키마 diff만으로는 사용되지 않는 필드 삭제를 불필요하게 차단하고, usage만으로는 새로 추가된 클라이언트를 놓칠 수 있다. CI에서 schema check를 실행하여 실제 트래픽 기반으로 안전성을 판단한다.

Anti-patterns

피해야 할 패턴

운영 환경에서 사고를 일으키는 대표적인 안티패턴과 그에 대응하는 권장 패턴.

Anti-pattern
Offset pagination을 공개 스키마 표준으로
데이터 변경 시 row 누락·중복이 발생하고, 대규모 offset에서 성능이 급격히 저하된다.
Recommended
Relay 스타일 cursor connection
edges/node/cursor/pageInfo를 표준으로 채택하여 안정적 순회와 양방향 탐색을 보장한다.
Anti-pattern
DataLoader를 전역 singleton으로
cross-request 캐시 오염, 메모리 누수, 인증 경계 무시.
Recommended
요청 범위로 생성
HTTP 요청마다 새 DataLoader 인스턴스를 만들어 context에 주입한다.
Anti-pattern
Public API에 introspection/batch/alias/depth 모두 개방
DoS 공격 표면 최대화. 하나만 제한해도 다른 벡터로 우회할 수 있다.
Recommended
다층 방어 + persisted query
depth + breadth + complexity + batch limit을 조합하고, 궁극적으로 trusted documents로 전환.
Anti-pattern
Federation entity ownership 불명확
subgraph 간 충돌, composition 실패, 책임 소재 불분명.
Recommended
entity 단위 팀 소유권
각 entity를 owning subgraph에 고정하고, 참조는 @key로 명시.
Anti-pattern
에러를 200 + opaque message만으로 반환
부분 렌더링 불가, 에러 분류·모니터링 불가.
Recommended
errors[] + extensions.code
스펙 준수 errors 배열과 구조화된 extensions로 클라이언트가 분기할 수 있게 한다.
Gotchas

반복 실수 방지 체크리스트

GraphQL 서버를 설계·운영할 때 반복적으로 빠지는 함정들.

!
Introspection 비활성화는 보안 보조일 뿐 allowlist를 대체하지 못한다 introspection을 끄더라도 공격자가 필드명을 추측하거나 유출된 스키마로 악의적 쿼리를 보낼 수 있다. trusted documents / persisted query가 근본 대책이다.
!
errors가 있어도 data가 함께 올 수 있다 execution error는 실패한 필드만 null로 만들고 나머지는 정상 반환한다. 클라이언트는 errors 존재 여부만으로 전체 실패를 판단하면 안 된다.
!
DataLoader는 요청 범위 캐시이다 한 HTTP 요청 내에서만 배치와 캐싱이 동작한다. cross-request 캐싱이 필요하면 별도 캐시 레이어(Redis 등)를 사용해야 한다.
