Gotchas

Gotchas 체크리스트

생성 전·구현 중·완료 보고 전에 확인해야 할 17개 제약이다. 실제 의존성을 썼는지와 실제 대상을 호출했는지는 서로 다른 축으로 판정한다.

  • 1. 스택 감지 없이 생성 금지Step 0의 프로젝트 감지를 먼저 수행한다. Python에 Jest, Node.js에 pytest를 생성하지 않는다.
  • 2. DB 의존 테스트는 실제 DB가 원칙가능하면 Testcontainers 또는 Docker Compose로 실제 DB를 띄운다. Mock DB로는 스키마 드리프트를 놓칠 수 있다.
  • 3. API test client 우선FastAPI TestClient, Express supertest, Spring MockMvc/WebTestClient, Go httptest를 우선한다. 실제 포트 바인딩은 integration/e2e에서만 한다.
  • 4. 테스트 격리 필수공유 전역 상태나 DB 레코드에 의존하지 않는다. 트랜잭션 롤백 또는 테스트별 시드 데이터로 독립 실행을 보장한다.
  • 5. 에러 경로 누락 금지happy path와 함께 최소 400, 401, 404, 500 응답과 RFC 9457 problem+json 형식을 검증한다.
  • 6. Mock 남용 금지결제 API나 이메일 같은 외부 서비스만 mock한다. 내부 서비스와 리포지토리를 mock해 실제 동작과 멀어지지 않게 한다.
  • 7. 기존 테스트 패턴 준수디렉토리, 네이밍, fixture, assert 라이브러리를 먼저 파악하고 따른다. 새 패턴을 무단 도입하지 않는다.
  • 8. 환경 변수 하드코딩 금지DB URL과 API 키는 .env.test 또는 fixture/conftest에서 주입한다.
  • 9. 비동기 테스트 타임아웃 필수async 테스트의 무한 대기가 CI를 멈추지 않도록 적절한 타임아웃을 설정한다.
  • 10. ORM 목록 조회에서 N+1 검증Django assertNumQueries, SQLAlchemy connection.execute 카운트, JPA Hibernate statistics 등으로 쿼리 수를 assert한다.
  • 11. Pact v4 + Testcontainers 계약 테스트외부 서비스 연동에는 consumer-driven contract를 권장한다. Pact v4는 REST 외 gRPC, Kafka·RabbitMQ 같은 async messaging, GraphQL을 지원하며 Pact Broker는 Testcontainer로 CI에서 격리 실행할 수 있다.
  • 12. Sibling Consistency 유지독립적인 Step 0 스택 감지, 기존 테스트 패턴 탐색, 외부 실환경 강제 금지를 backend-test와 infra-test에 공통으로 유지한다.
  • 13. mock-only를 integration으로 보고하지 않기MockDatabase와 인메모리 대체물만 쓰면 단위 테스트다. 파일 경로, 테스트 이름, 완료 보고를 실제 수준과 맞춘다. 실행 출력 없이 통과했다고 보고하지 않는다.
  • 14. 통합 테스트 전 마이그레이션 확인fixture/conftest에서 컨테이너 기동 → 마이그레이션 실행 → 시드 순서를 보장한다. 컨테이너 재사용 시에는 별도의 스키마 최신화 경로를 둔다.
  • 15. 계약 변경은 양면 갱신응답 형태, 상태코드, 직렬화 변경 시 provider 테스트뿐 아니라 consumer 계약과 픽스처도 같은 스프린트에서 갱신한다. 별도 저장소라면 저장소명과 갱신 필요 파일을 보고한다.
  • 16. production 코드 경로를 통과테스트가 SQL 술어, 가드 분기, 핸들러 파이프라인을 독립 재작성하면 결합이 없다. production 심볼, 실제 바이너리 또는 로컬 provider를 호출하고 결합: {테스트 파일:라인} → {구현 심볼}을 남긴다.
  • 17. 핵심 guard는 negative test와 쌍으로동시성, 인증·인가, 멱등 arbiter에 한해 가드를 무력화하면 FAIL하는 음성 대조를 만든다. 실행하지 못하면 “guard proof 없음”으로 미완 보고하며 모든 테스트에 전면 강제하지 않는다.

Process · Step 2

Step 2: 기존 패턴 탐색

새 테스트를 쓰기 전에 현재 프로젝트의 관례를 읽는다. 기존 테스트가 없을 때만 해당 스택의 커뮤니티 표준 패턴을 사용한다.

1

구조와 import

디렉토리가 mirror인지 flat인지 확인하고 기존 import 스타일과 assert 라이브러리를 따른다.

2

Fixture와 factory

conftest, beforeAll, @BeforeEach 등 준비·정리 패턴을 확인한다.

3

Mock 방식

unittest.mock, jest.fn, Mockito, gomock 가운데 프로젝트가 이미 쓰는 방식을 따른다.

4

네이밍

test_, should_, describe/it, @Test 관례를 확인한다.

Process · Step 3

Step 3: 테스트 코드 생성

AAA(Arrange–Act–Assert)를 지키고 각 public 함수·메서드마다 최소 1개 테스트를 만든다. happy path와 error path를 모두 다루고 이름은 구현 방법이 아니라 행위를 서술한다.

Py

Python · pytest

tests/test_{module}.py에 클래스 기반으로 구성하고 pytest.raises로 에러를 검증한다. DB fixture는 conftest.py에 둔다.

# tests/test_{module}.py
import pytest
from {module} import {target}

class TestTargetName:
    """대상 함수/클래스의 행위 테스트."""

    def test_happy_path(self):
        # Arrange
        # Act
        result = target(valid_input)
        # Assert
        assert result == expected

    def test_error_case(self):
        with pytest.raises(ExpectedException):
            target(invalid_input)

# DB 의존 시 — conftest.py에 fixture 정의
@pytest.fixture
async def db_session():
    # Testcontainers 또는 트랜잭션 롤백
    ...
JS

Node.js · Jest/Vitest

__tests__/{module}.test.ts에서 describe/it과 expect를 사용한다. Express API는 supertest를 쓴다.

import { describe, it, expect } from 'vitest'
import { target } from '../{module}'

describe('TargetName', () => {
  it('should return expected result', () => {
    expect(target(validInput)).toEqual(expected)
  })

  it('should throw on invalid input', () => {
    expect(() => target(invalidInput))
      .toThrow(ExpectedError)
  })
})
Jv

Java · JUnit 5

src/test/java/{package}/{Target}Test.java에 두고 AssertJ와 @DisplayName을 사용한다. Spring API는 MockMvc를 사용한다.

class TargetTest {
    @Test
    @DisplayName("valid input returns expected result")
    void happyPath() {
        var result = target.method(validInput);
        assertThat(result).isEqualTo(expected);
    }

    @Test
    void errorCase() {
        assertThatThrownBy(() -> target.method(invalidInput))
            .isInstanceOf(ExpectedException.class);
    }
}
Go

Go · testing + testify

{module}_test.go에 배치하고 require/assert를 사용한다. API는 httptest로 검증한다.

// {module}_test.go
package {pkg}

import (
    "testing"
    "github.com/stretchr/testify/assert"
    "github.com/stretchr/testify/require"
)

func TestTarget_HappyPath(t *testing.T) {
    result, err := Target(validInput)
    require.NoError(t, err)
    assert.Equal(t, expected, result)
}

func TestTarget_ErrorCase(t *testing.T) {
    _, err := Target(invalidInput)
    assert.ErrorIs(t, err, ErrExpected)
}

// API 테스트 — httptest
func TestGetResource(t *testing.T) {
    req := httptest.NewRequest(http.MethodGet, "/api/resource", nil)
    w := httptest.NewRecorder()
    handler.ServeHTTP(w, req)
    assert.Equal(t, http.StatusOK, w.Code)
}

API handler 보강

프레임워크 test client를 사용하고, OpenAPI spec이 있으면 요청·응답 스키마를 대조하며 인증 헤더 fixture를 포함한다.

적용 범위 통제

음성 대조는 동시성 guard, 인증·인가 guard, 멱등 arbiter에 한정한다. 단위 테스트 전체에 Testcontainers나 계약 도구를 강제하지 않는다.

Numeric Rules

수치 기준표

원본이 명시한 최소 수치와 관찰값만 모았다. 임의의 커버리지 목표나 실행 시간 기준은 추가하지 않는다.

Anti-patterns

안티패턴 Bad / Good 비교

겉으로는 통과하지만 결함을 잡지 못하는 테스트를 실제 의존성과 실제 구현 경로에 결합된 테스트로 바꾼다.

Mock-only 테스트를 integration으로 명명

Bad

MockDatabase와 인메모리 repository만 사용하면서 tests/integration/에 두고 “실제 PostgreSQL 통합 테스트 통과”라고 보고한다.

Good

mock-only면 unit으로 이름과 경로를 맞춘다. integration이면 실제 DB를 기동하고 마이그레이션과 실행 출력을 증거로 남긴다.

테스트 안에서 production 로직 재작성

Bad

실제 DB는 쓰지만 production의 SQL 술어와 동시성 가드를 테스트 파일 안에 복사한다. 구현을 삭제해도 테스트가 통과한다.

Good

production 리포지토리나 핸들러를 직접 호출하고 테스트 위치에서 구현 심볼까지의 결합을 보고한다.

핵심 guard의 positive 경로만 검증

Bad

현재 버전이 일치해 성공하는 경우만 확인한다. guard가 제거되어도 테스트 결과가 바뀌지 않는다.

Good

읽은 뒤 다른 경로로 행을 변경해 stale 상태를 만들고, 영향 행 0과 conflict 승격 및 상태 미변경을 확인한다.

실행하지 않고 “통과” 보고

Bad

테스트 코드를 생성한 사실만으로 성공을 선언하거나 Docker/DB 오류를 보고에서 생략한다.

Good

명령과 통과·실패 건수가 있는 출력을 인용한다. 실행 불가 시 [미검증] 네 칸을 채우고 부분 완료로 보고한다.

Process · Step 5

Step 5: 실행 검증

생성한 테스트를 실행하고 실패 원인을 분석해 수정한다. testcontainers나 supertest 같은 의존성이 없으면 설치 안내를 제공한다.

스택실행 명령
Pythonpytest {test_file} -v
Node.jsnpx vitest run {test_file} 또는 npx jest {test_file}
Java./gradlew test --tests {TestClass} 또는 mvn test -Dtest={TestClass}
Gogo test -v -run {TestFunc} ./{pkg}/...
Elixirmix test {test_file}
실행 증거 규칙
  • 보고에는 실행 명령과 통과/실패 건수를 포함한 출력을 인용한다.
  • Docker 미설치나 DB 접속 불가라면 해당 항목을 [미검증]으로 표시한다.
  • 막는 것, 시도한 우회와 결과, 통제 불가 사유, 재검증 명령의 네 칸을 채운다.
  • 핵심 guard 증명을 실행하지 못했다면 “guard proof 없음”으로 미완 보고한다.
Process · Step 6

Step 6: 결과 보고

생성 파일, 테스트 케이스 수, 실행 결과를 사용자에게 제시한다. 추가 테스트가 필요한 edge case, 성능, 보안 영역도 제안한다.

1

변경 목록

생성된 테스트와 fixture, 설정 파일을 빠짐없이 나열한다.

2

검증 결과

케이스 수와 실행 명령, 통과·실패 출력을 함께 제시한다.

3

남은 범위

edge case, 성능, 보안 또는 외부 조건 때문에 검증하지 못한 영역을 명시한다.
