Shape

피라미드는 비율이 아니라 비용 곡선이다

상단으로 갈수록 실행 시간, 유지 비용, 비결정성(flakiness)이 기하급수적으로 증가한다. 비율이 뒤집힌 "아이스크림 콘"은 느리고 깨지기 쉬운 스위트를 만든다.

E2E · 10%

사용자 시나리오 전체

브라우저/API 레벨에서 핵심 플로우(happy path)에만 한정한다. 가장 느리고 가장 잘 깨진다.

Integration · 20%

실 의존성과의 상호작용

실제 DB · 메시지 큐와의 상호작용을 검증한다. 단 실 대상까지 만족해야 한다(§8).

Unit · 70%

격리된 로직

밀리초 단위로 빠르고 외부 의존성 없이 실행한다. 개발 피드백 루프의 기반.

근거: Martin Fowler — The Practical Test Pyramid

Principles

8가지 원칙

§8 은 이번 개정에서 추가됐다 — 실 의존성과 실 대상은 다른 축이라는 것. 실 DB 를 띄웠다는 사실만으로 통합 테스트가 되지는 않는다.

01

테스트 피라미드를 따른다

단위 테스트를 가장 많이, 통합 테스트를 중간, E2E 테스트를 최소로 유지한다. Google 엔지니어링 팀 기준 권장 비율은 단위 70% / 통합 20% / E2E 10% 이다. 피라미드 상단으로 갈수록 실행 시간, 유지 비용, 비결정성이 기하급수적으로 증가한다.

Fowler — Practical Test Pyramid
02

각 테스트 유형의 역할을 구분한다

단위 테스트는 밀리초 단위로 빠르고 외부 의존성 없이 격리 실행한다. 통합 테스트는 실제 DB, 메시지 큐 등 실제 의존성과의 상호작용을 검증한다. E2E 테스트는 사용자 시나리오 전체를 브라우저/API 레벨에서 검증하며, 핵심 플로우에 집중한다.

Fowler — Practical Test Pyramid
03

Contract testing으로 서비스 간 계약을 검증한다

마이크로서비스 환경에서 consumer-driven contract testing은 서비스 간 API 계약이 깨지지 않음을 보장한다. Consumer가 기대하는 요청/응답 형태를 Pact 파일로 정의하고, Provider가 이를 검증한다. 통합 테스트 환경 없이도 서비스 간 호환성을 확인할 수 있다.

Pact Documentation
04

테스트 더블을 목적에 맞게 선택한다

더블역할
Mock행위 검증 (호출 여부 · 횟수 · 인자)
Stub미리 정해진 응답 반환
Fake경량 구현체 (인메모리 DB 등)
Spy실제 객체를 감싸 호출 기록

Mock 과다 사용은 구현에 결합된 깨지기 쉬운 테스트를 만든다 — 가능하면 상태 기반 검증(stub/fake)을 우선한다.

Fowler — TestDouble
05

DB 테스트는 실제 데이터베이스로 실행한다

인메모리 DB(H2 등)는 실제 DB와 동작이 다르다. Testcontainers는 Docker로 실제 DB(PostgreSQL, MySQL, MongoDB 등)를 테스트 시 자동 생성/폐기한다. 테스트 간 격리는 트랜잭션 롤백 또는 테스트별 스키마 생성으로 보장한다.

Testcontainers
06

부하 테스트로 성능 기준선을 설정한다

k6는 JavaScript로 시나리오를 작성하고 CLI에서 실행하는 부하 테스트 도구다. 기본 설정은 VU 10~50명, duration 30초~5분으로 시작하여 점진적으로 늘린다. Artillery도 YAML 기반으로 유사한 기능을 제공한다. 성능 기준선(p95 응답 시간, 에러율)을 CI에 통합하면 성능 회귀를 조기에 탐지한다.

Grafana k6 Documentation
07

커버리지는 지표이지 목표가 아니다

커버리지 80%를 넘으면 수확체감이 발생한다. 100% 커버리지가 버그 없음을 보장하지 않는다 — 코드 경로를 실행한 것이지 결과의 정확성을 검증한 것이 아니다. 커버리지보다 mutation testing이 테스트 품질을 더 정확히 측정한다. 커버리지를 KPI로 설정하면 의미 없는 assertion 없는 테스트가 양산된다.

Fowler — TestCoverage
08

통합 테스트는 "실 의존성"과 "실 대상"을 모두 만족해야 한다

두 조건은 다른 축이다. 실제 DB/브로커를 띄웠더라도 테스트가 검증 대상 로직(SQL 술어 · 가드 분기 · 핸들러 파이프라인)을 독립적으로 재작성했다면 구현과의 결합이 0 이라, 구현에서 그 로직을 삭제해도 테스트는 통과한다.

  • 통합 테스트로 계상하려면 production 심볼(함수 · 리포지토리 · 핸들러) 또는 실제 실행 바이너리 / 로컬 기동 provider 를 호출해야 한다
  • provider 검증도 유효한 타깃 증명이다 — 다만 요청 본문을 검증하기 전 레이어를 stub 하면 어떤 garbage body 도 통과하므로 stub 위치를 함께 확인한다
  • 핵심 guard 는 그 지점을 무력화했을 때 테스트가 FAIL 해야 의미가 있다
  • 다만 mutation/negative control 을 전 코드베이스에 적용하지 마라 — 비용이 크다. 핵심 guard 로 범위를 한정한다
Pact — Provider verification · PIT · Testcontainers
Target Proof

의존성이 진짜인가 ≠ 대상이 진짜인가

실 DB 를 쓰면서도 테스트가 SQL 을 독립 재작성하면, 구현의 가드를 지워도 통과한다. 두 축을 나눠서 본다.

축묻는 질문PASS 증거
실 의존성 Testcontainers / 실 DB 인가, 인메모리 대체물인가 실제 엔진 기동 설정 · 접속 대상
실 대상 테스트가 구현 심볼을 실제로 통과하는가 결합: {테스트 파일:라인} → {구현 심볼}
판별력 guard 를 무력화하면 이 테스트가 FAIL 하는가 결함 주입 시 실패 관측 기록

같은 실 DB, 다른 결과

Bad — 의존성은 진짜, 대상이 가짜
# 실 PostgreSQL 을 띄웠지만 SQL 을 테스트가 다시 씀
async def test_optimistic_lock(db):
    await db.execute(
      "UPDATE orders SET status='paid' "
      "WHERE id=$1 AND status='pending'")
    # 구현의 가드를 지워도 이 테스트는 통과한다

query-level 보조 테스트로 재분류하고 통합 테스트 개수에 계상하지 않는다.

Good — 구현 심볼을 호출한다
from app.orders.repository import mark_paid   # 구현 심볼

async def test_optimistic_lock(db):
    ok = await mark_paid(db, order_id, expect="pending")
    assert ok is True
    dup = await mark_paid(db, order_id, expect="pending")
    assert dup is False        # 영향 행 수 0 → conflict

결합 확인은 정적으로 결정론적이다 — 테스트가 구현 심볼을 import · 호출하는지 grep 으로 판정된다.

범위 한정 음성 대조(결함 주입) 요구는 동시성 가드 · 인증/인가 guard · 멱등 arbiter 세 가지에만 적용한다. 전 코드베이스 mutation score 임계값을 세우면 계약에 없는 비용이 된다. 상세 절차는 쓰기 경로 무결성 프로토콜 §5 를 따른다.

Anti-patterns

피해야 할 5가지

아이스크림 콘 (E2E 과다)
E2E 비율이 단위 테스트보다 높으면 테스트 스위트가 느리고, 비결정적이며, 유지 비용이 높다. E2E는 핵심 플로우에만 한정하고 나머지는 하위 레벨에서 검증한다.
Mock 과다 (가짜 그린)
모든 의존성을 mock하면 테스트가 항상 통과하지만 실제 통합 문제를 잡지 못한다. Mock은 외부 서비스 경계에만 사용하고, 내부 모듈 간에는 실제 구현을 사용한다.
로직을 재작성한 "통합" 테스트
실 DB 를 띄워놓고 테스트가 SQL 을 직접 다시 작성해 "일반적인 동작"만 확인하면, 구현의 가드를 지워도 통과한다. 의존성은 진짜인데 대상이 가짜인 경우다. 테스트는 구현 심볼을 호출해야 한다.
테스트 간 상태 공유
테스트가 공유 DB 레코드나 전역 변수에 의존하면 실행 순서에 따라 결과가 달라진다. 각 테스트는 독립적으로 setup/teardown해야 한다.
커버리지 강박
커버리지 수치 자체를 목표로 삼으면 getter/setter 테스트, assertion 없는 테스트 등 의미 없는 코드가 양산된다. 비즈니스 로직과 엣지 케이스에 집중한다.
Gotchas

반복 실수 방지 체크리스트

  • Testcontainers는 CI에서 Docker 필요 GitHub Actions는 기본 지원하지만, 일부 CI 환경(CircleCI machine executor 아닌 경우 등)에서는 Docker-in-Docker 설정이 필요하다.
  • Mock이 실제 API와 drift Mock을 수동 관리하면 실제 API가 변경되어도 테스트가 통과한다. Contract testing이나 자동 생성 mock(OpenAPI spec 기반)으로 방지한다.
  • Flaky test는 즉시 수정 또는 격리 비결정적 테스트를 방치하면 팀이 테스트 실패를 무시하는 습관이 생긴다. 재현 불가능하면 quarantine 처리 후 별도 추적한다.
