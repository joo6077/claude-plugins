데이터베이스를 다루는 10가지 원칙

조회 성능은 측정으로 조정하고, 쓰기 무결성은 데이터베이스 primitive로 보장한다. 시각은 모두 같은 값이 아니므로 순간과 두 종류의 벽시계를 구분한 뒤 저장 형태를 정한다.

01

정규화 우선, 읽기 성능 병목에서만 반정규화한다

Connection pooling은 운영 환경 필수다

  • HikariCP — JVM 생태계 표준 풀

08

쓰기 경합은 invariant 를 분류한 뒤 DB primitive 로 막는다

read-check-then-write의 두 문장 사이에는 다른 트랜잭션이 끼어든다. 지킬 규칙을 먼저 분류한다.

  • 조건부 갱신은 READ COMMITTED에서도 갱신된 row에 WHERE 재평가
  • 영향 행 수 0은 성공이 아니라 도메인 conflict
  • Serializable만 serialization anomaly를 방지 — Snapshot Isolation은 write skew를 허용
  • SELECT FOR UPDATE는 반환된 기존 row만 잠금
PostgreSQL — Transaction Isolation PostgreSQL — Explicit Locking Berenson et al.
09

조건부 unique 제약과 upsert 의 충돌 대상은 문자 그대로 일치해야 한다

일부 행에 적용되는 제약의 조건을 upsert가 빠뜨리면 제약이 있어도 충돌 대상으로 쓰지 못한다.

  • partial index는 predicate를 만족하는 subset에만 적용하며, 일반 정리 증명기가 없어 쿼리 조건과 index predicate가 정확히 맞아야 하는 경우가 많음
  • ON CONFLICT의 column, expression, predicate가 arbiter index와 일치해야 하며 inference 실패는 에러
  • DO UPDATE에는 conflict target이 필수이고, DO NOTHING의 target 생략은 사용 가능한 모든 제약 위반을 회피하므로 의도한 멱등 결과를 보장하지 않음
PostgreSQL — Partial Indexes PostgreSQL — INSERT
10

시각은 종류부터 나누고, 종류마다 저장 형태를 정한다

“전부 UTC로 저장”은 한 순간에만 맞는다. 벽시계를 순간 하나로 바꾸면 시간대·서머타임 변화 뒤 의도와 어긋난다.

  • 순간 — TIMESTAMPTZ
  • 받는 사람 지역을 따라가는 벽시계 — 시간대 없는 TIME · TIMESTAMP
  • 특정 지역에 묶인 벽시계 — 시간대 없는 값 + IANA 시간대 이름
RFC 5545 §3.3.5 — DATE-TIME PostgreSQL — Date/Time Types
Write Path

invariant 유형 → 담당 primitive

깨지면 안 되는 규칙의 범위를 분류해 row 가드, 쓰기 SQL 술어, 제약·lock·Serializable 중 맞는 수단을 고른다.

invariant 유형담당 primitive예시
같은 row의 상태 전이 조건부 UPDATE ... WHERE <기대 상태/버전> UPDATE orders SET status='paid' WHERE id=$1 AND status='pending'
존재 · 권한 · 가시성 predicate 쓰기 SQL 자체의 WHERE EXISTS (...) / 조인 술어 사전 SELECT 대신 INSERT ... SELECT ... WHERE EXISTS
cross-row · absence · aggregate unique / partial unique / exclusion 제약, 명시적 lock, Serializable + 재시도 구간 겹침 금지 → exclusion 제약

read-check-then-write를 쓰기 술어로 접는다

Bad — 두 문장 사이의 창
row = SELECT status FROM orders WHERE id = $1;
if row.status != 'pending': raise Conflict
UPDATE orders SET status = 'paid' WHERE id = $1;

트랜잭션으로 감싸도 판단과 쓰기 사이의 경합 창은 닫히지 않는다.

Good — 기대 상태를 술어에 포함
UPDATE orders
   SET status = 'paid'
 WHERE id = $1
   AND status = 'pending';

-- affected == 0 → domain conflict

동시 갱신자를 기다린 뒤 갱신된 row에 WHERE를 재평가한다.

주의
같은 row 상태 전이의 해법을 모든 predicate로 일반화하지 않는다. 복잡한 search condition은 일관성 판단에 부적합할 수 있고, SELECT FOR UPDATE는 존재하지 않는 row를 잠그지 않는다.
Upsert Arbiter

조건부 제약과 충돌 대상을 함께 대조한다

partial unique index를 arbiter로 쓰려면 column이나 expression뿐 아니라 predicate까지 맞춘다.

Bad — predicate 누락
CREATE UNIQUE INDEX uq_token_active
  ON device_tokens (user_id, token)
  WHERE revoked_at IS NULL;

INSERT INTO device_tokens (...)
VALUES (...)
ON CONFLICT (user_id, token)
DO UPDATE SET updated_at = now();

조건부 unique index를 올바르게 inference하지 못한다.

Good — index predicate와 일치
INSERT INTO device_tokens (...)
VALUES (...)
ON CONFLICT (user_id, token)
  WHERE revoked_at IS NULL
DO UPDATE SET updated_at = now();

제약과 upsert의 column · expression · predicate를 양쪽에서 대조한다.

Time Model

시각 종류별 저장 계약

필드마다 뜻, 저장 형태, 순간으로 바꾸는 규칙, 시간대의 출처를 계약에 기록한다.

시각 종류예저장 형태 (PostgreSQL)순간이 필요할 때
순간 결제 시각, 생성 시각 TIMESTAMPTZ 그대로 쓴다
받는 사람 지역을 따라가는 벽시계 어디에 있든 현지 06:30에 울리는 알림 TIME · TIMESTAMP — 시간대 없음 받는 사람의 지금 시간대로 계산
특정 지역에 묶인 벽시계 한 지점의 영업시간, 한 도시의 행사 TIME · TIMESTAMP + 시간대 이름 칸 레코드에 적힌 시간대로 계산
IANA 식별자
Asia/Seoul 같은 지역 이름을 쓴다. 나라 코드 하나로 시간대를 결정하지 않는다.
PostgreSQL 타입
TIMESTAMPTZ는 입력 시간대를 UTC로 바꿔 저장하고 원래 시간대를 남기지 않는다. 사용자가 고른 시간대가 업무 정보면 별도 칸에 둔다. TIMESTAMP는 시간대 표시를 무시하고 날짜·시각만 저장한다.
DST 계약
같은 시각이 두 번 오거나 없는 전환 구간의 해석을 정한다. RFC는 첫 번째와 전환 전 오프셋을 쓴다.
Floating time과 시간대 출처
받는 사람 지역을 따라가는 벽시계는 RFC 5545의 floating time이다. 보는 사람의 시간대와 무관하게 같은 시·분·초를 뜻하므로 서로 다른 지역의 사용자는 서로 다른 UTC 순간에 참여한다. 합리적인 경우에만 이 형태를 쓰고, 대부분은 UTC나 시간대 참조로 시각을 고정한다. 시간대를 요청·기기·사용자 설정·레코드 중 어디서 받는지와 저장할지 매 요청마다 받을지를 계약한다. 한 나라에 시간대가 여럿일 수 있으므로 나라 코드로 정하지 않는다.
Bad — 벽시계를 UTC 순간으로 고정

현지 알림이나 영업시간이 시간대 변경과 서머타임 뒤 사람이 정한 시각에서 어긋난다.

Good — 뜻과 시간대 출처를 계약

순간, floating time, 지역 고정 벽시계를 구분하고 요청·기기·사용자 설정·레코드 중 시간대 출처를 정한다.

출처: RFC 5545 §3.3.5 · PostgreSQL — Date/Time Types

안티패턴 · Anti-patterns

Bad / Good로 보는 피해야 할 9가지

성능, 쓰기 무결성, 시각 모델에서 잘못된 선택과 교정 방향을 함께 대조한다.

Bad — 관성적인 조회 최적화

모든 컬럼에 인덱스를 만들고 SELECT *와 lazy loading을 방치하며 pool을 무제한으로 키운다.

Good — 쿼리와 부하로 결정

실제 쿼리 패턴과 실행 계획으로 최소 인덱스, 필요한 컬럼, 로딩 전략, pool 상한을 정한다.

Bad — 앱 레벨에서 경합 방어

사전 SELECT와 if로 판단하고 영향 행 수 0을 성공 처리하며 partial unique와 다른 conflict target을 쓴다.

Good — DB primitive로 보장

조건을 쓰기 SQL에 넣고 영향 행 수를 검사한다. cross-row 규칙은 제약, lock, Serializable과 재시도로 보호한다.

Bad — 시각과 지역을 하나로 고정

벽시계를 TIMESTAMPTZ 하나로 저장하고 시간대·나라를 상수나 한 나라 기본값으로 박는다.

Good — 종류와 출처를 계약

순간과 두 종류의 벽시계를 구분하고 시간대의 출처와 서머타임 전환 규칙을 정한다.

Gotchas

반복 실수 방지 체크리스트

구현과 리뷰에서 아래 다섯 항목을 빠뜨리지 않았는지 확인한다.

  • GIN 인덱스는 쓰기 성능을 저하시킨다 fastupdate=on으로 완화할 수 있지만 첫 읽기에서 펜딩 리스트를 정리해 latency 스파이크가 생길 수 있다.
  • EXPLAIN과 EXPLAIN ANALYZE는 다르다 전자는 통계 기반 예측이고 후자는 실제 실행이다. 차이가 크면 ANALYZE로 통계를 갱신한다.
  • Serializable은 기본값이 아니다 직렬화 실패 재시도와 abort율 관측이 필요하다. cross-row·absence·aggregate invariant에만 후보로 올린다.
  • READ COMMITTED + 복잡한 search condition을 “안전”으로 일반화하지 않는다 조건부 UPDATE 하나가 cross-row predicate 전체를 보호한다고 서술하지 않는다.
  • Connection pool exhaustion은 deadlock처럼 보인다 모든 연결이 점유되면 새 요청이 timeout까지 멈춘다. pool 사용률을 반드시 모니터링한다.
