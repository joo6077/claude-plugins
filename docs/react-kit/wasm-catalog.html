핵심 수치

Boundary Cost — JS↔WASM 경계 비용

WASM 결정에서 가장 자주 오해되는 축. "WASM이 빠르니까 작은 것도 옮기자"는 이 수치 때문에 거의 항상 손해다.

JS↔WASM 호출 오버헤드 (정수 인자)
50~100 ns
/ call. secondary source 추정, unverified
문자열 마샬링 (짧은 문자열)
600~2,500 ns
/ call. UTF-16↔UTF-8 변환 비용 포함
ArrayBuffer 전송 (Transferable)
~0
zero-copy 이동
50 ns = "초당 2천만 회 이하 호출이면 누적 경계 비용이 CPU 1% 미만". 2,500 ns = "초당 40만 회 문자열 호출이면 경계 비용이 CPU 100%". 경계를 자주 넘을수록 WASM이 불리하다.

공개된 프로덕션 시스템 또는 엔진팀 벤치마크에서 WebAssembly가 JavaScript를 유의미하게 앞선 것이 확인된 영역.

카테고리 근거 프로덕션 사례 출처

resize, filter, codec		 Figma dense-file 로드 29s → <8s (약 3.6x). Squoosh WASM 코덱 전 브라우저 이득 확인 Figma, Squoosh ↗ Figma
비디오/오디오 인코딩·디코딩 ffmpeg.wasm이 SIMD/threads로 C/C++ 코덱을 실용 속도로 구동. JS 대안이 현실적으로 없음 ffmpeg.wasm ↗ ffmpeg.wasm
압축/해제
lz4, brotli, zstd, gzip		 lz4-wasm: 66k JSON에서 compression ~2.9x, decompression ~25x vs lz4 js lz4-wasm, fflate, brotli-wasm ↗ lz4-wasm

JS/TS 유지

10개 비권장 카테고리

WASM으로 이식해도 이득이 없거나 오히려 손해인 영역. /react-wasm은 이 카테고리 매칭 시 제안을 거부한다.

카테고리 이유 출처
UI 상태, DOM 인접 작업, 컴포넌트 렌더 WASM은 DOM 직접 접근 불가. 모든 DOM 업데이트가 JS 글루를 통과하므로 경계 비용이 본 작업을 지배 ↗ MDN WASM
폼 검증, 작은 함수, 소규모 리스트
<1만 아이템		 V8 JIT (Sparkplug, Maglev, TurboFan)이 hot small code path를 공격적으로 최적화. JS↔WASM 래퍼 비용이 남아 JS 동률 또는 우위 ↗ V8 Maglev
JSON 파싱 / 직렬화 V8이 Chrome 138에서 JSON.stringify를 "2x 이상" 향상. JSON 경로는 이미 네이티브 SIMD급 최적화 ↗ V8 JSON
문자열 처리
정규식, split, concat, template		 JS 문자열은 엔진 네이티브. WASM은 UTF-16↔UTF-8 마샬링/복사 비용을 항상 지불 ↗ bridge overhead 경고
Web Crypto 소규모 호출
단발 AES-GCM, SHA-256 한 번		 브라우저가 이미 네이티브 crypto API를 노출. 소규모 호출의 WASM 우위는 경계 비용에 묻힐 가능성 큼 ↗ SubtleCrypto
고빈도 콜백 (>1만/sec) 매 호출마다 JS↔WASM 경계를 넘으면 누적 비용이 compute 비용을 압도. 배치화 불가능하면 금기 ↗ JS callback overhead
tiny 함수 (<100μs per call) 호출 오버헤드 50~100 ns가 상대적으로 크게 느껴짐. 호출당 compute가 작을수록 JS 우위 ↗ V8 90
애니메이션, 스크롤, 드래그 requestAnimationFrame + CSS/GPU 경로가 정답. WASM은 프레임 예산 16ms를 깎아먹을 뿐 ↗ rAF
네트워크 호출, fetch 래퍼 I/O 바운드. CPU 가속 의미 없음 ↗ Fetch API
이벤트 버스, 작은 reducer, Zustand 업데이트 hot small path. V8 JIT 영역. dispatch마다 경계 비용 발생 ↗ V8 Maglev
카탈로그 미스 시

5가지 판정 휴리스틱

카탈로그 테이블에 정확히 해당하지 않는 요청이 오면 아래 5개 중 3개 이상 WASM 쪽이면 이식 제안, 아니면 JS 유지.

H1 · 데이터 크기
WASM바이너리 버퍼 (Uint8Array, Float32Array) + KB~MB 단위
JS문자열, 일반 객체, 작은 배열 (<1 KB)
H2 · 호출 빈도
WASM낮은 빈도 (초당 <100) + 무거운 본 작업 (ms 단위)
JS높은 빈도 (초당 >1만) + 가벼운 본 작업
H3 · 내부 연산 형태
WASM반복 루프 중심, 분기 적고, 숫자·바이너리, 행렬·벡터
JS문자열/객체 조작, 정규식, JSON.parse, DOM 인접
H4 · 외부 리소스 접근
WASM순수 함수. fetch, DOM, timer, Tauri API 불필요
JS외부 접근 있음 — WASM은 JS 브리지 거쳐야 함
H5 · 알고리즘 특성
WASMSIMD/threads 활용 가능 — 픽셀, 해시, 행렬, 정렬, 컨볼루션
JS본질적으로 순차적 — 상태 기계, DOM 업데이트, UI 애니메이션

오해

WASM이 이길 것 같지만 실제로는 지는 케이스

오해진실
"React 로직을 WASM으로 빼면 빠르다" React는 DOM 인접 작업. state 업데이트는 V8 JIT 대상이고 렌더는 브라우저 페인트 파이프라인. WASM으로 빼는 순간 매 렌더 경계 비용 발생
"JSON 파싱을 WASM으로 빼면 빠르다" V8은 Chrome 138에서 JSON.stringify를 2x 이상 개선. JSON parse는 이미 SIMD 경로 사용. 빠르게 하려면 포맷 자체를 바이너리(Arrow, Protobuf)로 바꿔야 함
"큰 데이터면 무조건 WASM이 이긴다" 크기가 아니라 연산 밀도 (compute per byte)가 결정. 1 GB라도 한 번 훑으면 V8 선형 스캔으로 충분. 10 MB라도 복잡한 재계산이면 WASM 이득
"Threads를 켜면 자동으로 빨라진다" COOP/COEP 헤더 없이는 SharedArrayBuffer가 차단. 그리고 작업이 상호 의존성 없는 분할 가능한 compute여야만 효과 있음
"Rust는 빠른 언어라서 WASM도 무조건 JS보다 빠르다" JS↔WASM 경계가 존재하는 한 경계 비용이 본 작업보다 클 수 있음. 언어 자체의 속도가 아니라 경계 패턴이 결정
↗ wasm-bindgen Guide ↗ MDN WebAssembly

케이스 스터디

프로덕션 사례 5건

케이스문제해결교훈
Figma 대용량 파일 로딩에서 JS 기반 파서/렌더러 성능 한계 C++ 핵심 로직을 WebAssembly 이식. 초기 로드 29s → 8s (약 3.6x) 단일 진입점으로 들어가서 내부에서 오래 머무는 작업이 WASM 최적 후보
Squoosh 브라우저에서 MozJPEG, WebP, AVIF 코덱을 실제로 돌려야 하는데 JS 구현이 없음 각 코덱 C 구현을 WASM으로 컴파일. 코덱마다 .wasm 파일 분리해서 lazy load "JS 대안이 없는" 영역에서는 WASM이 선택의 문제가 아니라 유일한 길
DuckDB-Wasm 브라우저에서 대용량 CSV/Parquet에 대한 분석 SQL 실행 DuckDB 컬럼 엔진을 WASM 으로 빌드. Worker에서 실행, Arrow IPC로 zero-copy 교환 전문화된 실행 엔진을 통째로 가져오는 것이 JS로 재구현보다 훨씬 현실적
MediaPipe 실시간 손 추적을 JS로는 frame rate 확보 불가 XNNPACK + WASM SIMD. 14~15 FPS → 38~40 FPS (약 2.6x) ML 추론은 텐서 연산이라 SIMD 효과가 강하게 나오는 전형적 WASM 승리 카테고리
Photopea PSD 파일 파싱, 레이어 블렌딩, 필터 적용 모두 JS로는 성능 한계 C++ 이미지 처리 코어를 WASM 으로 컴파일. 필터/블렌딩은 대부분 WASM 내부에서 수행 "인터랙션 → 대량 픽셀 처리 → 결과 표시" 사이클은 WASM 코어 + JS UI 조합의 이상적 분할
