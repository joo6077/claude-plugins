Planning Kit v0.1 · GitHub Integration

GitHub Integration

2026년 기준 GitHub Projects v2 · Issues · Milestones는 planning substrate로도 꽤 강하다. 도구 선호보다 운영 모델 정렬이 핵심이다. PRD → Epic → Story → Task 매핑과 gh CLI 자동화를 명확히 하라.

01 · Patterns

GitHub 기반 planning 패턴

Projects · Issues · Milestones · CLI · 비교 관점을 정리.

1

Projects v2 + Issues + Milestones 베스트 프랙티스

Projects는 planning/tracking 허브, Issues는 계층형 sub-issues · dependencies · labels · issue types · milestones로 work decomposition을 지원한다.

  • Project = 팀/프로덕트 단위 운영판 (single source of truth)
  • Issue → sub-issue 분해
  • blocking/blocked dependency 명시
  • views · fields · automation · insights를 역할별 분리
GitHub Docs — Projects Best Practices
2

gh CLI 패턴

gh issue, gh project, gh search issues 계열이 planning 자동화의 핵심. project scope 권한과 JSON 출력이 중요.

  • 이슈 생성 시 label/milestone/project 함께 지정
  • 반복 리포팅은 --json + --jq
  • Project field schema를 CLI로 재현 가능하게 관리
  • 비개발 직군용 대시보드는 별도 제공
gh Manual — gh issue
3

Linear 와의 비교

Linear는 product development system. GitHub integration으로 PR/commit/issue sync를 제공. GitHub는 code-adjacent planning, Linear는 planning-adjacent code sync에 강하다.

  • code review + planning 단일 surface → GitHub
  • workflow · triage · templates opinionation → Linear
  • OSS + product 혼합 → GitHub
  • 많은 팀은 둘을 병행 사용
Linear Docs — GitHub Integration
4

PRD → Epic → Story → Task 분해

계층을 tool primitive에 맞게 매핑하는 것이 핵심. PRD는 외부 문서/issue document, Epic은 parent issue, Story는 child issue, Task는 sub-issue/checklist.

  • Milestone = release 또는 timebox
  • PR은 task/story에 연결 (PRD를 직접 닫지 않음)
  • 팀 규모에 따라 3단계로 축소 가능
GitHub Docs — About Issues
5

Milestones 사용 규칙

Milestone은 대부분의 팀에서 release 또는 timebox 둘 중 하나로 고정해야 한다. 섞어 쓰면 burndown이 무의미해진다.

  • release milestone: 시멘틱 버전 태그와 1:1
  • timebox milestone: "2026-Q2 Sprint 3" 같은 시간 상자
  • 완료 기준은 milestone description에 명시
GitHub Docs — About Milestones
6

Project Templates / Issue Documents

Linear 스타일에 영향을 받아 GitHub에도 project template · issue template · issue document가 자리잡았다. 반복되는 프로세스의 필수 필드를 사전 강제한다.

  • issue template에 Context · Success · Risks 필드 포함
  • project template에 기본 view · milestone 구조 포함
  • 새 initiative는 template에서 fork하여 시작
Linear Docs — Project Templates (참고)
02 · Layer Mapping

PRD → Epic → Story → Task 매핑표

각 레이어의 질문과 GitHub primitive.

Layer질문GitHub primitive닫히는 조건
PRD 왜 지금 이걸 하는가? Notion/Linear/README · project document outcome metric 달성
Epic / Initiative 어떤 outcome을 이루나? parent issue (issue type: Epic) 모든 child story가 closed
Story 어떤 사용자 가치를 제공하나? child issue (issue type: Story) acceptance criteria 충족 PR merge

03 · gh CLI Recipes

gh CLI 자동화 레시피

반복 planning 작업의 최소 자동화.

# 이슈 생성 (label · milestone · project · assignee 한번에)
gh issue create \
  --title "결제 webhook reconciliation 개선" \
  --body-file ./specs/billing-recon.md \
  --label "area/billing,type/story" \
  --milestone "2026-Q2-Sprint3" \
  --project "Product Planning" \
  --assignee "@me"

# 내 할 일 JSON으로 조회 (in_progress + high priority)
gh search issues \
  --owner my-org --state open --assignee "@me" \
  --label "priority/P1" \
  --json number,title,labels,milestone \
  --jq '.[] | "\(.number)  \(.milestone.title)  \(.title)"'

# Project v2 item의 status 필드 업데이트
gh project item-edit \
  --id PVTI_lAHO... \
  --field-id PVTSSF_lAHO... \
  --single-select-option-id 47fc9ee4 \
  --project-id PVT_kwHO...
04 · Anti-patterns

안티패턴 vs 좋은 패턴

GitHub planning에서 반복되는 실수.

Bad

상태 · 날짜 · owner를 여러 곳에 중복 기록

Project field + issue body + README가 서로 어긋난다.

Good

single source of truth 규칙 명문화

상태 = Project field, owner = issue assignee, 날짜 = milestone due date.

Bad

Milestone을 release와 timebox에 섞어 사용

burndown · 완료율 지표가 무의미해진다.

Good

두 종류를 label prefix로 분리

release/*, sprint/*로 분리하거나 Milestone은 한 용도만 사용.

Bad

Project field schema를 수시 변경 + 스크립트 방치

자동화 파이프라인이 조용히 깨진다.

Good

field schema를 코드 리포에 버전 관리

변경 시 PR · CI에서 스크립트 호환성 체크.

05 · Gotchas

Gotchas

GitHub planning에서 자주 놓치는 함정.

!
PR close keyword가 상위 issue까지 닫는다

Story나 Epic을 PR close로 닫으면 부분 작업만으로 큰 단위가 closed. close는 task/sub-issue 수준까지.

!
gh CLI project scope 토큰 누락

Personal access token에 project scope가 없으면 field 편집이 조용히 실패. 초기 권한 점검 필수.

!
sub-issue 계층이 3단계를 넘어간다

운영비가 급증. 팀 규모/cadence에 맞게 최대 3단계로 제한.

!
비개발 직군이 CLI를 못 써 소외된다

Projects web view + saved view 기반 UI를 별도 제공. CLI는 엔지니어링 자동화용.

!
Linear 병행 시 sync가 쌍방향으로 흐른다

어느 쪽이 "source"인지 team level에서 명시. 대개 planning = Linear, code = GitHub로 단방향.
