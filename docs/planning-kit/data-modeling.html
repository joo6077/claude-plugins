Data Modeling

제품 기획에서 데이터 모델링은 DB(데이터베이스) 테이블 설계의 하위 작업이 아니다. 도메인 개념이 무엇인지, 어떤 경계 안에서 어떤 규칙이 작동하는지, 어떤 이벤트가 시스템 동작을 바꾸는지를 분명히 하는 일이다.

00 · Overview

개요 — 네 가지를 한 흐름으로

DDD(도메인 주도 설계) · Event Storming · ERD(엔터티 관계도) · Data Dictionary 를 제품 기획 관점에서 잇고, Mermaid 로 문서 안에 둔다.

데이터 모델링이 약하면 PRD(제품 요구사항 문서)는 화면 설명서가 되고, 구현은 우연히 생긴 상태 필드의 모음이 된다.

DDD 는 복잡한 비즈니스 규칙을 모델의 언어로 끌어올리는 접근이고, Event Storming 은 그 모델을 여럿이 함께 찾아내는 워크숍 형식이다. ERD 와 Data Dictionary 는 그 뒤에 구조를 더 명시적으로 고정하는 산출물이다. Mermaid 는 이것들을 텍스트 문서 안에서 유지하기 쉽게 만든다.

  1. 발견 — Event Storming도메인에서 일어나는 사건을 벽에 붙이며 함께 이해한다
  2. 언어와 경계 — DDDBounded Context · Aggregate 로 규칙이 통하는 범위를 정한다
  3. 구조 고정 — ERD · Data Dictionary엔터티 관계와 필드 계약을 명시한다
  4. 문서 안에 유지 — MermaiderDiagram · classDiagram 을 Markdown 에 텍스트로 둔다
01 · Domain-Driven Design

DDD 핵심 개념

Bounded Context / Aggregate / Entity / Value Object / Domain Event — 다섯 낱말이 모델의 뼈대다.

Bounded Context특정 모델과 언어가 일관되게 통하는 경계
Aggregate변경 일관성의 단위
Entity식별성이 중요한 객체

1

모델을 코드와 문서 모두의 중심에 둔다

Eric Evans 의 DDD 는 모델을 코드와 문서 모두의 중심에 둔다. 기획 문서에 이 개념이 필요한 이유는 기능을 화면 기준으로만 쪼개지 않기 위해서다.

예를 들어 「구독」 「청구」 「권한」 을 한 모델로 섞으면 용어가 부딪히고, 나중에 조직 · 시스템 경계도 꼬인다. 반대로 Bounded Context 를 의식하면 PRD 의 용어도 더 안정된다.

핵심 질문

  • 어떤 용어가 어떤 컨텍스트에서만 참인가?
  • 어떤 데이터는 식별성보다 값 동등성이 중요한가?
  • 어떤 변경은 같은 aggregate 안에서만 강한 일관성이 필요한가?
  • 어떤 사건을 domain event 로 명시하면 흐름이 더 또렷해지는가?
적용 시점복잡한 도메인 정의, 마이크로서비스 경계 논의, 핵심 비즈니스 규칙 모델링
한계 · 주의DDD 용어만 붙이고 CRUD(생성 · 조회 · 수정 · 삭제 위주) 설계를 유지하면 효과가 없다. 모든 곳에 aggregate 를 크게 잡으면 오히려 병목이 생긴다.

02 · Event Storming

Event Storming (Alberto Brandolini)

그림을 완성하는 것보다 도메인을 함께 이해하는 과정이 더 중요하다.

2

도메인 이벤트 중심으로 빠르게 모델링하는 협업 기법

복잡한 비즈니스 프로세스를 도메인 이벤트 중심으로 빠르게 모델링한다. Alberto Brandolini 는 이를 deliberate collective learning(의도적인 집단 학습)으로 설명한다. 완성도 높은 다이어그램을 만드는 것보다 도메인을 함께 이해하는 과정이 더 중요하다는 뜻이다.

넓게 보기 Big Picture Event Storming 프로세스와 병목을 발견하는 데 알맞다.
좁혀 보기 Process Design / Software Design command, policy, aggregate, read model 을 더 세밀히 다루는 데 알맞다.

제품 기획 단계에서 특히 좋은 점은 business 와 tech 가 같은 벽 앞에서 같은 언어를 쓰게 만든다는 점이다.

핵심 질문

  • 도메인에서 실제로 일어나는 사건을 과거형 event 로 적었는가?
  • hotspot · unknown area(아직 모르는 영역)가 드러나는가?
  • command, policy, actor 를 나눠 볼 필요가 있는가?
  • 병목 · 대기 · 핸드오프가 어디서 생기는가?
적용 시점도메인 탐색, 프로세스 재설계, bounded context 후보 탐색
한계 · 주의벽에 스티커를 붙이는 행위가 목적이 되면 실패한다. 퍼실리테이션이 약하면 소음만 많은 브레인스토밍(noisy brainstorm)으로 끝난다.

03 · Entity Relationship Diagram

ERD — Crow's Foot 표기

화면 정의보다 상위의 구조를 보여 준다. 관계가 복잡한 도메인이면 필수다.

3

엔터티와 관계를 구조로 명시한다

ERD 는 엔터티와 관계를 구조적으로 명시한다. Crow's Foot 표기는 one-to-many(일대다)와 optionality(없어도 되는 관계인지)를 눈으로 분명히 보여 줘 데이터 모델을 설명할 때 널리 쓴다.

관리자 제품, B2B SaaS(기업 대상 구독형 서비스), 업무 도메인처럼 관계가 복잡하면 필수다. 엔터티 이름은 가급적 단수형으로 두고, 관계의 뜻은 동사로 읽히게 쓴다.

핵심 질문

  • 엔터티가 진짜 도메인 개념을 반영하는가?
  • 관계의 cardinality · optionality 가 명시되는가?
  • 속성이 아니라 별도 엔터티여야 할 개념을 잘 분리했는가?
  • 한 관계를 실제 문장으로 읽었을 때 자연스러운가?
적용 시점구조 설계, 데이터 저장 모델 합의, 분석용 이벤트 구조를 정하기 전 단계
한계 · 주의ERD 는 행위 규칙과 시간 흐름을 잘 설명하지 못한다. DDD · 이벤트 모델과 함께 본다.

04 · Mermaid erDiagram

Mermaid erDiagram 공식 패턴

Markdown 안에서 가벼운 ERD 를 유지한다. 렌더러 판이 바뀌면 같은 코드도 그림이 달라진다.

렌더러 판 바뀜 · Mermaid 12.0.0 (2026-09-10 공개)

ERD 기본 배치가 Dagre 에서 ELK 로 바뀌었다

Mermaid 12.0.0 부터 ERD 의 기본 배치 엔진이 Dagre 에서 ELK 로, 기본 모양(theme · look)도 바뀌었다. 문법은 그대로라도 같은 코드가 11 이하와 다른 그림으로 나올 수 있다. 그래서 렌더 결과를 비교할 때는 렌더러 버전을 함께 적는다. Dagre 와 ELK 는 둘 다 상자와 선의 자리를 자동으로 정하는 배치 엔진이다.

Mermaid erDiagram 은 Markdown 안에서 가벼운 ERD 를 유지하기에 알맞다. 공식 문법은 PlantUML 호환 관계 표기와 attribute block 을 지원한다.

  • cardinality 가 정확한가?

05 · Mermaid classDiagram

Mermaid classDiagram 공식 패턴

속성과 행위를 함께 적는다 — ERD 보다 행위 쪽 모델을 더 잘 담는다.

5

개념 모델과 aggregate 내부 구조

Mermaid classDiagram 은 개념 모델, aggregate 내부 구조, 도메인 오브젝트 관계를 표현하는 데 알맞다. 속성과 메서드를 함께 적을 수 있어 단순 ERD 보다 행위적 모델을 더 잘 담는다.

핵심 질문

  • 클래스 이름이 도메인 언어와 일치하는가?
  • 속성과 행위를 함께 보아야 하는 개념인가?
  • 연관 · 구성 · 상속을 구분했는가?
적용 시점도메인 모델 초안, aggregate 설명, 객체 협력 설명
한계 · 주의구현 클래스 다이어그램으로 곧장 내려가면 추상 수준이 너무 빨리 무너질 수 있다.

06 · Data Dictionary

Data Dictionary 포맷

필드 이름 목록이 아니라 데이터 계약(data contract)이다.

6

최소한 담아야 하는 것

이름, 설명, 타입, 허용값, null 가능 여부, 생성 주체, 시스템 오브 레코드(값의 기준이 되는 시스템), 변경 규칙.

기획 단계에서 만들면 분석 이벤트 이름이 조금씩 어긋나는 것(naming drift)을 줄이고, API(프로그램끼리 주고받는 창구) · DB · UI 가 서로 다른 이름을 쓰는 문제를 일찍 막는다.

적용 시점API 설계, 이벤트 구조 정의, analytics tracking plan(분석 이벤트 수집 계획), admin · reporting 제품
한계 · 주의운영 ownership(누가 계속 고치는지) 없이는 금방 썩는다. glossary 와 schema registry(필드 정의를 모아 두는 저장소)가 따로 놀면 같은 내용을 두 곳에서 고치게 된다.

08 · Anti-patterns

안티패턴과 바꿀 방향

원본 각 절의 「한계 · 주의사항」 을 나쁜 예 · 좋은 예 짝으로 옮겼다.

Bad

구독 · 청구 · 권한을 한 모델로 섞는다

용어가 부딪히고, 나중에 조직 · 시스템 경계도 꼬인다.

Good

Bounded Context 마다 모델과 용어를 나눈다

어떤 용어가 어떤 컨텍스트에서만 참인지 묻는다. PRD 의 용어가 안정된다.

Bad

모든 곳에 aggregate 를 크게 잡는다

오히려 병목이 생긴다.

Good

강한 일관성이 필요한 변경만 한 aggregate 로 묶는다

「같은 aggregate 안에서만 강한 일관성이 필요한 변경인가」 를 먼저 묻는다.

Bad

Event Storming 에서 스티커 붙이기가 목적이 된다

퍼실리테이션이 약하면 소음만 많은 브레인스토밍으로 끝난다.

Good

함께 이해하는 과정에 초점을 둔다

과거형 event 로 적고, hotspot 과 병목 · 대기 · 핸드오프를 드러낸다.

Bad

ERD 하나로 행위 규칙과 시간 흐름까지 설명한다

ERD 는 구조는 잘 보여 주지만 행위와 시간 흐름은 잘 설명하지 못한다.

Good

DDD · 이벤트 모델과 함께 본다

행위는 classDiagram 과 domain event 로, 구조는 ERD 로 나눠 담는다.

Bad

Mermaid 렌더 그림을 판 번호 없이 비교한다

12.0.0 부터 ERD 기본 배치가 ELK 로 바뀌어, 같은 코드도 11 이하와 다른 그림이 나올 수 있다.

Good

렌더 결과 옆에 렌더러 버전을 적는다

그림이 달라진 까닭이 코드인지 렌더러인지 가를 수 있다.

Bad

Data Dictionary 를 만들고 책임자를 정하지 않는다

운영 ownership 이 없으면 금방 썩는다.

Good

필드마다 source of truth 와 owner 를 적는다

glossary 와 schema registry 가 따로 놀지 않게 한곳에서 고친다.

09 · Gotchas

모델링 문서에서 자주 놓치는 것

원본 핵심 질문 가운데 빠뜨리기 쉬운 것만 골랐다.

!
값 동등성이 중요한 데이터에 식별자를 붙인다

속성값 자체가 의미의 전부라면 Value Object 다. Entity 로 다루기 전에 「식별성보다 값 동등성이 중요한가」 를 묻는다.

!
별도 엔터티여야 할 개념을 속성 칸에 넣는다

ERD 핵심 질문 「속성이 아닌 별도 엔터티여야 할 개념을 잘 분리했는가」 를 엔터티마다 확인한다.

!
관계 라벨이 두 번째 엔터티 쪽에서 읽힌다

erDiagram 라벨은 첫 번째 엔터티 관점에서 읽혀야 한다. 문장으로 소리 내 읽어 보면 어긋남이 드러난다.

!
attribute block 에 PK · FK 를 적지 않는다

키를 적어야 관계 의도가 attribute 수준에서도 드러난다.

!
classDiagram 을 구현 클래스 그림으로 곧장 내린다

클래스 이름이 도메인 언어와 일치하는지부터 본다. 추상 수준이 너무 빨리 무너지면 기획 문서의 역할을 잃는다.

!
PII 여부와 보관 규칙 칸을 비운다

Data Dictionary 체크리스트 마지막 줄이다. 생성 · 수정 시점 규칙과 함께 필드마다 채운다.
