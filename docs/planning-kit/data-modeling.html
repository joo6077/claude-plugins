Data Modeling

제품 기획에서 데이터 모델링은 DB 스키마 설계의 하위 작업이 아니다. 어떤 도메인 개념이 어떤 경계 안에서 작동하고, 어떤 이벤트가 시스템 동작을 바꾸는지 모델의 언어로 끌어올리는 일이다.

01 · Methods

모델링 방법론

DDD · Event Storming · ERD · Data Dictionary를 한 흐름으로 연결한다.

1

DDD 핵심 개념

Eric Evans의 DDD. Bounded Context(모델 · 언어가 일관된 경계), Aggregate(변경 일관성 단위), Entity(식별성), Value Object(속성값 자체가 의미), Domain Event.

  • 용어 충돌 방지를 위한 컨텍스트 구분
  • 같은 aggregate 안에서만 강한 일관성 보장
  • 도메인 이벤트로 흐름을 드러냄
Domain Language — DDD Reference
2

Event Storming (Alberto Brandolini)

복잡한 비즈니스 프로세스를 도메인 이벤트 중심으로 빠르게 모델링하는 협업 기법. Big Picture → Process Design → Software Design 3단계로 해상도를 올릴 수 있다.

  • 실제 발생하는 사건을 과거형 event로 기록
  • hotspot · unknown area를 먼저 드러냄
  • command · policy · actor · read model 구분
EventStorming.com
3

ERD (Crow's Foot)

엔터티와 관계를 구조적으로 명시한다. Crow's Foot 표기는 one-to-many · optionality를 시각적으로 분명히 보여준다.

  • 엔터티명은 단수형 권장
  • 관계를 문장으로 읽었을 때 자연스러운가 점검
  • 속성 vs 별도 엔터티 판단
Mermaid — ER Diagram
4

Mermaid erDiagram

Markdown 안에 가벼운 ERD를 유지하기에 적합. PlantUML 호환 관계 표기와 attribute block 지원.

  • 관계 라벨은 first entity 관점에서 읽기
  • PK / FK 명시
  • 복잡한 물리 스키마 전체는 별도 도구 사용
Mermaid — erDiagram
5

Mermaid classDiagram

개념 모델 · aggregate 내부 구조 · 도메인 오브젝트 관계 표현에 적합. 속성 + 행위를 함께 적을 수 있어 ERD보다 행위적 모델을 담기 쉽다.

  • 클래스명 = 도메인 언어
  • 연관 · 구성 · 상속 구분
  • 구현 클래스 다이어그램으로 곧장 내려가지 않기
Mermaid — Class Diagram
6

Data Dictionary

필드 목록이 아니라 데이터 계약. 이름 · 설명 · 타입 · 허용값 · null 가능성 · owner · 변경 규칙을 담는다. analytics/event naming drift 방지 효과.

  • source of truth / owner 명시
  • PII 여부와 retention rule
  • 생성/수정 시맨틱스 정의

04 · Anti-patterns

안티패턴 vs 좋은 패턴

"DDD 용어만 붙이고 CRUD를 유지"하는 전형적 실수.

Bad

구독 · 청구 · 권한을 한 모델로 섞기

용어 충돌이 생기고 나중에 조직/시스템 경계도 꼬인다.

Good

Bounded Context별로 용어 사전 분리

Subscription context의 "status"와 Authorization context의 "status"가 다를 수 있음을 인정.

Bad

Aggregate를 지나치게 크게 잡기

전체 Workspace를 하나의 aggregate로 묶으면 동시성 병목 · 트랜잭션 실패가 늘어난다.

Good

변경 일관성이 필요한 최소 단위로 분리

Issue · Comment · Label 등 별도 aggregate, cross-aggregate는 eventual consistency.

Bad

Event Storming이 스티커 부착 워크숍으로 끝남

벽에 메모만 쌓이고 모델/문서로 정제되지 않는다.

Good

Storming 결과를 classDiagram · Context Map으로 문서화

워크숍 직후 24~48시간 내 artifact 확정 규칙 운영.

05 · Gotchas

Gotchas

모델링 문서에서 자주 놓치는 함정.

!
ERD만으로 도메인을 설명하려 한다

ERD는 구조 표현이 강하지만 행위 규칙과 시간 흐름을 잘 보여주지 못한다. Event Storming · classDiagram과 함께.

!
Value Object를 Entity처럼 다루기

주소 · 금액 · 기간처럼 속성값 자체가 의미의 전부인 객체에 id를 붙이면 equality 비교가 복잡해진다.

!
Data Dictionary에 owner가 빠짐

운영 ownership 없이는 금방 썩는다. glossary와 schema registry가 분리되면 중복 관리가 생긴다.

!
Mermaid erDiagram에 FK 표시 누락

attribute block에 PK/FK를 명시해야 관계 의도가 드러난다.

!
DDD 용어를 "코드 주석용 장식"으로 쓴다

용어만 붙이고 CRUD 설계를 유지하면 효과가 없다. aggregate 경계가 코드의 트랜잭션 경계로 이어져야 한다.
