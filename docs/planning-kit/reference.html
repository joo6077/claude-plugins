Reference & Competitive Analysis

"X 같은 앱을 만들고 싶다"에서 곧바로 기능 목록을 쓰지 않는다. Lightning Demos · Teardown · Feature Matrix · JTBD · Positioning · Blue Ocean · Red Route · Kano · Flywheel · MY/NO/LIKE까지 16가지 렌즈로 기존 제품을 분해하고 경쟁 구도를 재정의해 feature parity trap을 피한다.

00 · Workflow

적용 순서

수집 → 해부 → 비교 → 재정의 → 차별화 → 우선순위 → 편향 점검. 한 방법론에 과신하지 않고 서로의 맹점을 보완한다.

Step 1

Lightning Demos

직접 + 인접 레퍼런스를 6~10개 수집한다.

Step 2

Competitive Teardown

상위 2~4개 제품을 깊게 분해한다.

Step 3

Feature Matrix

checkbox가 아니라 완성도 · 제약까지 적는다.

Step 4

JTBD 재정의

경쟁 집합을 다시 정의하고 non-consumption 포함.

Step 5

Positioning / Blue Ocean

차별화 문장을 만든다.

Step 6

Red Route / Kano

실제 MVP 우선순위를 줄인다.

Step 7

Bias Check

Parity Trap · Survivorship Bias로 결론을 교정.

ComfyUI 같은 노드 편집기, Notion 같은 지식도구, Figma 같은 협업 캔버스처럼 이미 강한 기준 제품이 있는 카테고리에서는, 사용자가 실제로 무엇을 "고용(hire)"하는지 구조적으로 보지 않으면 곧바로 feature parity trap에 빠진다.

16가지 렌즈

수집 · 분석 · 전략 · 우선순위 · 편향 점검을 한 흐름으로 묶는다.

1수집

Lightning Demos (GV Sprint · Jake Knapp)

짧은 시간에 경쟁 제품과 인접 카테고리 모범 사례를 훑어 팀의 공통 참조면(reference surface)을 만든다. 제품당 3분 — 깊게 평가가 아니라 빠르게 수집하고 시각적으로 공유가 목적이다.

  • 1분 배경 · 1분 핵심 플로우 · 1분 캡처할 아이디어
  • 직접 경쟁 3~5 + 인접 레퍼런스 3~5를 섞는다
  • 캡처는 화면보다 "의도" 단위로 남긴다
  • 이 단계에서는 우열 판단 금지, 패턴 수집만

얕게 보면 "보기 좋은 화면 수집"으로 전락한다. 비즈니스 모델 · 제약 · 기술 부채는 보이지 않는다.

GV Sprint — Lightning Demos
2수집

Competitive Teardown (IDEO · NN/g)

사용자 흐름 · 정보구조 · 인터랙션 · 카피 · 가격 · 신뢰 장치 · 성장 루프까지 분해해 "무엇이 어떻게 작동하는가"를 분석한다. Lightning Demos가 breadth라면 teardown은 depth다.

  • 로그인 전후 경험을 분리해 본다
  • empty state · error state · export/share state 필수
  • 가격 · 플랜 벽이 어디서 등장하는지 기록
  • "있음/없음"이 아니라 "언제 어떤 비용으로 드러나는가"

"왜 이렇게 설계했는가"는 추론일 뿐이다. 사실과 추론을 분리해 적어야 한다.

IDEO Design Kit — Analogous Inspiration
3분석

Value Proposition Canvas (Osterwalder)

고객의 Jobs / Pains / Gains와 제품의 Products & Services / Pain Relievers / Gain Creators를 맞물리게 본다. 레퍼런스 분석에 적용하면 "경쟁사가 어떤 pain을 얼마나 직접적으로 줄이는가"를 비교할 수 있다.

  • 기능을 적기 전에 고객 job을 먼저 적는다
  • pain은 빈도와 심각도를 분리한다
  • "좋아 보이는 기능"보다 "불편 제거"에 점수를 높게 준다

인터뷰 없이 작성하면 팀의 추측을 예쁘게 정리한 문서가 된다. B2B · 멀티사이드는 세그먼트 분리 필수.

Strategyzer — VPC Instruction Manual
4분석

Feature Matrix / Comparison Grid

기능 · 품질 · 제약 · 가격 · 협업성 · API · 학습곡선을 표로 비교하는 기본 도구다. 잘못 쓰면 checkbox 수집기가 되므로 반드시 JTBD · red route · Kano 해석과 같이 쓴다.

  • 존재 여부 · 완성도 · 발견 가능성 · 제약 · 가격 연동 · 차별화 코멘트
  • 코어 플로우 기능과 edge-case 기능을 분리
  • "우리도 넣자" 대신 "왜 여기서 중요해졌나"를 적는다

열이 늘수록 중요한 차이가 묻힌다. 정성적 품질 차이를 한 칸으로 압축하면 오판한다.

April Dunford — An Introduction to Positioning (2020-05)
5재정의

JTBD 경쟁 재정의

경쟁사는 같은 카테고리 제품만이 아니다. 같은 job을 끝내기 위해 고용하는 모든 대안이 경쟁이다. ComfyUI의 경쟁은 다른 노드 편집기만이 아니라 스크립트, 템플릿 마켓, SaaS 워크플로 도구, 수작업 프로세스일 수 있다.

  • 핵심 Job · 현재 고용 대안 · switching trigger
  • desired outcome · anxieties / habits
  • 지금 쓰는 우회 수단을 반드시 포함
  • "왜 아직 안 바꿨는가"를 습관 · 리스크 · 학습비용으로 본다

job을 너무 추상화하면 모두가 경쟁처럼 보이고, 너무 좁히면 차별화 기회가 사라진다.

HBR — Know Your Customers' Jobs to Be Done (2016-09)
6전략

Porter's Five Forces (간략)

제품 단위가 아니라 산업 구조 단위에서 압력을 읽는 틀이다. "왜 경쟁사들이 비슷한 기능 세트를 가지게 되는가", "왜 가격 · 유통 · API 전략이 수렴하는가"를 해석하는 데 유용하다.

  • 신규 진입자 · 대체재 위협
  • 공급자 · 구매자 교섭력
  • 기존 경쟁 강도가 기능 · 가격 · 배포 · 데이터 중 어디서 높아지는가
  • 각 force를 낮음/중간/높음 + 근거 2~3줄 + 설계 함의 한 줄

세밀한 UX 의사결정을 직접 돕지 않는다. 빠르게 변하는 소프트웨어 시장에서 정태적 분석으로 끝나기 쉽다.

HBR — The Five Competitive Forces (2008-01)
7전략

Blue Ocean Strategy Canvas / Four Actions

Strategy Canvas는 업계 경쟁 요소와 각 제품의 투자 강도를 한눈에 비교하게 한다. Four Actions Framework는 Eliminate / Reduce / Raise / Create로 차별화 결정을 강제한다.

  • 축은 기능명이 아니라 구매 기준으로 잡는다
  • 곡선 차이를 설명할 수 있어야 한다
  • Create보다 Eliminate / Reduce를 먼저 검토한다

예쁜 곡선 그리기에 빠지면 실행 가능성이 사라진다. 차별화를 위한 차별화는 가치 파괴다.

Blue Ocean Strategy — Strategy Canvas
8우선순위

Red Route Analysis

사용자가 가장 자주 · 가장 중요하게 수행하는 과업 경로를 식별하고 그 성공률과 마찰을 최우선으로 다룬다. "경쟁사 전체 기능"보다 "가장 중요한 2~3개 경로"를 먼저 비교하게 만든다.

  • Route name · 사용 빈도 · 비즈니스 중요도
  • 현재 단계 수 · 마찰 지점 · 개선 기회
  • top task 3개부터 선정하고 성공 정의를 정한다
  • empty / error / loading / collaboration 상태까지 포함

데이터 없이 팀 추정으로만 route를 고르면 정치적 우선순위 싸움이 된다.

NN/g — Heuristic Summary (PDF)
9전략

Positioning (April Dunford)

메시지 작성이 아니라 어떤 시장 범주에서 어떤 대안 대비 왜 이길 자격이 있는지를 정의하는 일이다. teardown 결과를 전략 문장으로 압축한다.

  • Competitive alternatives · Unique capabilities
  • Value themes · Best-fit customers · Market category
  • 차별점은 기능명이 아니라 "가치 차이"까지 연결
  • 제품 설명보다 category choice를 먼저 검토

너무 이른 시점에 고정하면 제품 탐색이 경직된다. 제품 경험이 없으면 빈 약속이 된다.

April Dunford — Obviously Awesome
10전략

Flywheel / Moat Analysis

사용 · 데이터 축적 · 공유 · 콘텐츠 · 네트워크 · 신뢰가 서로를 강화하는 순환 구조를 찾는다. moat analysis는 그 순환의 모방 저항성을 본다. 기능이 아니라 "왜 시간이 갈수록 강해지는가"를 읽는다.

  • Trigger → Usage → Data/Content → Better outcomes → More adoption
  • 단계별 증거와 모방 난이도 평가
  • 네트워크 효과와 규모의 경제를 혼동하지 않는다

flywheel이 있다고 가정하고 억지로 선을 잇기 쉽다. 초기에는 loop보다 선형 성장 장치가 중요할 수 있다.

Jim Collins — Turning the Flywheel (2019-01)
11의사결정

MY / NO / LIKE 실무 shorthand

표준 학술 프레임워크라기보다 teardown 회의에서 쓰는 실무 shorthand로 보는 편이 정확하다. 여기서는 MY = 반드시 자기 것으로 삼을 것, NO = 의도적으로 하지 않을 것, LIKE = 참고하되 복제하지 않을 것으로 정의한다.

  • MY핵심 차별화 또는 핵심 route에 직접 기여
  • NO포지셔닝을 흐리거나 복잡도만 높임
  • LIKE패턴은 유효하지만 구현은 변형 필요
  • 항목마다 근거 한 줄 이상, NO가 충분히 많아야 한다

공식 정의가 고정된 방법론이 아니다. 팀 합의된 의미를 먼저 명시하지 않으면 감상평 분류로 흐른다.

Blue Ocean Strategy — Four Actions Framework
12우선순위

Kano Model 재적용

기능을 Must-be / Performance / Attractive / Indifferent / Reverse로 분류해 만족과 불만족의 비대칭을 파악한다. teardown 후 다시 적용하면 "경쟁사가 다 갖춘 기능이라도 이제는 위생요인인가"를 판단할 수 있다.

  • 없으면 불만이지만 있어도 감동 없는 기능은?
  • 경쟁사가 아직 약한 delighter는?
  • early adopter와 mainstream을 분리해 본다
  • delight 기능이 red route를 해치지 않는지 확인

설문 설계가 부정확하면 분류 신뢰도가 낮다. 카테고리 성숙도에 따라 분류가 빠르게 이동한다.

Kano et al. — Attractive Quality and Must-be Quality (1984-01)
13분석

Heuristic Evaluation (Nielsen 10)

인터페이스를 보편적 사용성 원칙으로 점검하는 전문가 리뷰다. teardown에 결합하면 취향 비평이 아니라 공통 기준으로 UX 품질을 비교할 수 있다.

  • 휴리스틱 10개를 행으로, 제품별 위반 사례와 심각도를 열로
  • aesthetic critique와 heuristic violation을 구분
  • 한 화면이 아니라 end-to-end flow로 본다
  • 에러 메시지와 빈 상태를 반드시 포함

도메인 특화 UX 문제는 휴리스틱만으로 안 잡힌다. 평가자 편차가 크므로 근거 캡처를 남긴다.

NN/g — 10 Usability Heuristics
14문서화

UX Teardown 템플릿

실무 teardown 템플릿은 보통 목표 행동 · 화면 캡처 · 가설 · 인지 원리 · 개선 아이디어로 구성된다. Growth.Design은 behavioral design lens를, UX Collective는 case-study형 해설 포맷을 제공한다.

  • Step · Screenshot · Observed pattern
  • Why it likely exists · User impact
  • Reuse / Avoid / Differentiate
  • 관찰과 해석을 분리하고 persuasion과 dark pattern을 구분

템플릿이 너무 정교하면 기록 비용이 커진다. 심리학 해석은 과잉추론이 되기 쉽다.

Growth.Design — Case Studies
15편향 점검

Feature Parity Trap

경쟁사 기능 목록을 따라가다 제품 전략이 흐려지고 복잡도만 누적되는 함정이다. 용어는 실무에서 널리 쓰이지만, 문제 자체는 Positioning · Blue Ocean · JTBD 문헌이 반복 경고해 온 주제다.

  • 경쟁사가 있어서 넣는가, 가치 제안을 강화해서 넣는가?
  • 없으면 판매가 막히는가, 단지 열세처럼 보이는가?
  • deal-breaker parity와 vanity parity를 구분
  • NO 결정 근거를 명시한다

parity를 무시하자는 뜻이 아니다. 위생요인조차 무시하면 시장 진입 자체가 막힌다.

April Dunford — An Introduction to Positioning (2020-05)
16편향 점검

Survivorship Bias

눈에 띄는 성공 제품만 보고 그 특징을 성공 원인으로 착각하는 편향이다. 레퍼런스 분석은 "잘된 제품이 채택한 기능"만 모으기 쉬워 특히 위험하다.

  • 실패한 제품, 철수한 기능은 무엇이었는가?
  • 성공 제품의 기능 중 결과이지 원인이 아닌 것은?
  • winner만 보지 말고 late entrant · shutdown 사례도 본다
  • 기능 성공과 distribution success를 분리한다

실패 사례는 정보 접근성이 낮다. 지나치게 회의적이면 학습 속도가 떨어진다.

04 · Worked Example

Strategy Canvas 예시 해석

곡선을 그리는 것으로 끝내지 않고 Four Actions 결정과 가치 문장까지 이어 붙인다.

ComfyUI 같은 노드 편집기를 만든다면 업계 공통 경쟁 요소를 학습 용이성 · 표현력 · 디버깅 가시성 · 템플릿 생태계 · 협업성 · 확장성으로 둘 수 있다. 기존 강자들이 표현력과 확장성에 과투자하고 학습 용이성 · 디버깅 가시성이 낮다면, 우리 곡선은 아래처럼 결정된다.
Action대상이유
Raise학습 용이성 · 디버깅 가시성기존 강자가 비운 축이자 red route 성공률에 직결
Reduce범용 확장성초기 사용자에게 비용만 발생, 마켓은 후순위
Eliminate초기 복잡 설정첫 성공까지의 시간을 가장 크게 갉아먹는 요소
Createguided debug flow실패 원인 파악을 제품 고유 경험으로 전환
차별화는 "기능이 더 많다"가 아니라 가치로 번역되어야 한다 — 이 예시의 결론 문장은 "복잡한 워크플로를 더 빨리 성공시키게 한다"이다.

06 · Anti-patterns

안티패턴 vs 좋은 패턴

teardown이 "스크린샷 컬렉션"으로 전락하는 실수들.

Bad

기능 매트릭스를 체크박스로만 채운다

없음/있음만 보고 "우리도 넣자"로 결론. 복잡도만 누적된다.

Good

완성도 · 제약 · 가격 연동 · 차별화 코멘트까지

기능의 존재보다 언제 어떤 비용으로 드러나는가를 기록한다.

Bad

경쟁사를 카테고리 기준으로만 정의

같은 앱 카테고리 제품만 본다. non-consumption을 놓친다.

Good

JTBD로 job 기준 재정의

스크립트 · 템플릿 · 수작업까지 포함해 switching trigger를 찾는다.

Bad

Blue Ocean 곡선을 예쁘게 그리는 데 집착

실행 가능성 없는 차별화. 역행 자체가 목적이 된다.

Good

Eliminate / Reduce를 Create보다 먼저 검토

축소 결정이 차별화의 핵심. 범위와 포지셔닝 문장이 동시에 단단해진다.

Bad

성공 제품의 기능만 수집해 결론

생존 편향 위험. 실패한 동일 기능 · 철수 제품을 못 본다.

Good

late entrant · shutdown 사례 포함

기능 성공과 distribution success를 분리해 "지금도 유효한가"를 재검토한다.

Bad

실무 shorthand를 표준 방법론처럼 인용

MY/NO/LIKE에는 고정된 공식 정의가 없다. 출처가 있는 것처럼 쓰면 신뢰가 깎인다.

Good

팀 합의 정의를 문서 첫머리에 명시

세 라벨의 의미와 적용 조건을 적어두고 근거 한 줄씩을 강제한다.

07 · Gotchas

Gotchas

teardown 실무에서 자주 빠지는 함정.

!
Lightning Demo는 breadth, Teardown은 depth — 섞지 말 것

Lightning Demo에서 갑자기 플로우 해부를 시작하면 시간을 다 쓴다. 수집과 해부를 물리적으로 분리하라.

!
VPC · JTBD는 인터뷰 없이 작성하면 팀 추측 정리본이 된다

고객 목소리가 없으면 예쁜 문서로 끝난다. B2B · 멀티사이드는 세그먼트 분리가 필수다.

!
JTBD job은 추상 ↔ 구체 스케일 조절이 핵심

너무 추상화하면 모든 제품이 경쟁처럼 보이고, 너무 좁히면 차별화 기회가 사라진다.

!
Red Route를 데이터 없이 팀 추정으로만 고르지 말 것

정치적 우선순위 싸움이 된다. 사용 빈도와 비즈니스 중요도를 분리해 근거를 남겨라.

!
Heuristic Evaluation은 도메인 특화 UX 문제를 못 잡는다

평가자 편차도 크므로 근거 캡처를 남겨라. UX Teardown 템플릿과 조합할 때 균형이 생긴다.

!
MY/NO/LIKE는 공식 정의가 없다

팀 합의된 의미를 먼저 명시하지 않으면 감상평 분류로 흐른다. LIKE가 슬그머니 MY로 번지는 경향에 주의.

!
Flywheel이 있다고 가정하고 억지로 선을 잇지 말 것

loop가 실제로 닫히는지 확인하라. 초기 제품 단계에서는 선형 성장 장치가 더 현실적이다.

!
teardown의 "왜"는 추론이다

화면 분해만으로는 구매 동기와 유지 이유를 알 수 없다. 사실과 추론을 문서에서 시각적으로 분리하라.
