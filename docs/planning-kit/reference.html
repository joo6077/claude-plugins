Reference & Competitive Analysis

"X 같은 앱 만들어 줘" 요청에서 곧바로 기능 목록을 쓰기 전 단계. Lightning Demos · Competitive Teardown · Feature Matrix · JTBD · Positioning · Blue Ocean · Red Route · Kano · Flywheel · MY/NO/LIKE까지 16가지 렌즈를 묶어 feature parity trap을 피하고 차별화 여지를 찾는다.

01 · Methods

16가지 렌즈

수집·분석·전략·우선순위·편향 점검을 한 흐름으로.

1수집

Lightning Demos (GV Sprint)

짧은 시간에 경쟁·인접 제품을 훑어 팀의 공통 참조면(reference surface)을 만든다. 제품당 3분 — 깊게 평가가 아니라 빠르게 수집이 목적.

  • 직접 3~5 + 인접 3~5를 섞는다
  • "의도 단위"로 캡처
  • 우열 판단 금지, 패턴 수집만
Sprint Book — Jake Knapp
2수집

Competitive Teardown (IDEO · NN/g)

사용자 흐름 · IA · 인터랙션 · 카피 · 가격 · 신뢰 장치 · 성장 루프까지 분해한다. breadth의 Lightning Demos와 달리 depth 중심.

  • 로그인 전후를 분리해 본다
  • empty · error · share state 필수
  • "기능 있음/없음"이 아닌 "언제 어떤 비용으로 드러나는가"
IDEO Design Kit — Teardown 맥락
3가치

Value Proposition Canvas (Osterwalder)

고객의 Jobs · Pains · Gains와 제품의 Products · Pain Relievers · Gain Creators를 맞물리게 본다. 경쟁사별 축약 캔버스로 비교.

  • 기능 전에 고객 job을 먼저 적는다
  • pain은 빈도·심각도 분리
  • "좋아 보이는 기능"보다 "불편 제거" 가중
Strategyzer — VPC Manual
4비교

Feature Matrix / Comparison Grid

제품 간 기능·품질·제약·가격·API·학습곡선 비교표. checkbox 수집기가 되지 않도록 JTBD · Red Route · Kano와 반드시 같이 쓴다.

  • 존재 여부 + 완성도 + 발견 가능성 + 제약 + 가격 연동
  • core vs edge-case 기능 분리
  • "우리도 넣자"가 아니라 "왜 여기서 중요해졌나"
April Dunford — Positioning
5재정의

JTBD 경쟁 재정의 (Christensen · Klement)

경쟁은 같은 카테고리 제품만이 아니다. 사용자가 같은 job을 위해 고용하는 모든 대안이 경쟁 — 스크립트, 템플릿, 수작업 포함.

  • progress 경쟁으로 보면 대안 집합이 달라진다
  • 현재 우회 수단 · switching trigger 기록
  • non-consumption도 포함
HBR — Know Your Customers' JTBD
6산업

Porter's Five Forces

제품이 아니라 산업 구조 단위의 압력. "왜 경쟁사들이 비슷한 기능·가격·API 전략으로 수렴하는가"를 해석한다.

  • 신규 진입 · 대체재 · 공급자 · 구매자 · 기존 경쟁
  • 각 force 낮음/중간/높음 + 2~3줄 근거
  • UX 상세 결정엔 부적합
HBR — Porter Five Forces
7전략

Blue Ocean Strategy Canvas / Four Actions

업계 경쟁 요소와 제품별 투자 강도를 곡선으로 비교. Eliminate · Reduce · Raise · Create로 차별화를 강제한다.

  • 축은 기능명이 아니라 구매 기준
  • Create보다 Eliminate/Reduce를 먼저
  • differentiation for its own sake는 가치 파괴
Blue Ocean — Strategy Canvas
8우선순위

Red Route Analysis

가장 자주·중요한 과업 경로를 먼저. GOV.UK 실무 기법 + NN/g의 top tasks와 결이 맞는다. 경쟁사 전체 기능보다 top task 2~3개를 비교한다.

  • Route · 빈도 · 중요도 · 단계 수 · 마찰 · 기회
  • empty · error · loading · collab 상태 포함
  • 성공 정의를 route별로 확정
NN/g — Heuristic Summary PDF
9전략

Positioning (April Dunford)

메시지 작성이 아니라 시장 범주와 경쟁 대안 대비 우위 정의. Competitive Alternatives · Unique Capabilities · Value Themes · Best-fit Customers · Market Category.

  • 차별점은 기능명이 아니라 가치 차이
  • 구매 시점의 실제 비교군을 반영
  • category choice를 제품 설명보다 먼저
April Dunford — Obviously Awesome
10전략

Flywheel / Moat Analysis

Jim Collins의 flywheel. 사용 → 데이터 → 공유 → 네트워크 → 신뢰가 서로 강화되는 순환. moat는 모방 저항성을 본다.

  • loop가 실제로 닫히는가
  • 네트워크 효과 vs 규모의 경제 분리
  • 반복될수록 강해지는 메커니즘만 남긴다
Jim Collins — Turning the Flywheel
11결정

MY / NO / LIKE

teardown 결과를 채택/비채택/변형 채택으로 가르는 decision lens. 공식 학술 프레임은 아니며 팀 합의된 정의를 먼저 명시해야 한다.

  • MY — 핵심 차별화·red route에 직접 기여
  • NO — 포지셔닝을 흐리거나 복잡도만 높임
  • LIKE — 패턴 유효, 구현 변형 필요
Blue Ocean — Four Actions
12우선순위

Kano Model 재적용

Must-be · Performance · Attractive · Indifferent · Reverse. teardown 후 다시 적용해 "경쟁사가 갖춘 기능이라도 이제는 위생요인인가"를 본다.

  • 현재 시장 기대치 반영해 재분류
  • early adopter와 mainstream 분리
  • delighter가 red route를 해치지 않게
Qualtrics — Kano Analysis
13UX

Heuristic Evaluation (Nielsen 10)

보편 사용성 원칙으로 경쟁사 UX를 공통 기준으로 비교한다. 취향 비평과 구분하기 위해 근거 캡처 필수.

  • 10개 휴리스틱을 행, 제품을 열
  • 한 화면이 아니라 end-to-end 플로우
  • error message · empty state 포함
NN/g — 10 Usability Heuristics
14UX

UX Teardown 템플릿 (Growth.Design · UX Collective)

behavioral design lens + case-study형 서술. Step · Screenshot · Pattern · Why · Impact · Reuse/Avoid/Differentiate.

  • 관찰과 해석을 분리해 적는다
  • persuasion과 dark pattern 구분
  • 템플릿이 너무 정교하면 기록 비용 초과
Growth.Design — Case Studies
15편향

Feature Parity Trap

경쟁사 기능 목록을 따라가다 전략이 흐려지고 복잡도만 쌓이는 함정. deal-breaker parity와 vanity parity를 분리하라.

  • 없으면 판매가 막히는가, 단지 열세로 보이는가
  • onboarding · IA · pricing · support cost 영향
  • NO 결정 근거 명시
April Dunford — Positioning
16편향

Survivorship Bias

눈에 띄는 성공 제품만 보고 그 특징을 성공 원인으로 착각하는 편향. late entrant · shutdown 사례를 반드시 포함해 결론을 교정한다.

  • 기능 성공 vs distribution success 분리
  • 실패 제품의 철수 기능 복기
  • "지금도 유효한가"를 시장 시점으로 검토
Strategyzer — Evidence Resources

04 · Anti-patterns

안티패턴 vs 좋은 패턴

teardown이 "스크린샷 컬렉션"으로 전락하는 실수들.

Bad

기능 매트릭스를 체크박스로만 채운다

없음/있음만 보고 "우리도 넣자"로 결론. 복잡도만 누적된다.

Good

완성도·제약·가격 연동·차별화 코멘트까지

기능의 존재보다 언제 어떤 비용으로 드러나는가를 기록한다.

Bad

경쟁사를 카테고리 기준으로만 정의

같은 앱 카테고리 제품만 본다. non-consumption을 놓친다.

Good

JTBD로 job 기준 재정의

스크립트·템플릿·수작업까지 포함해 switching trigger를 찾는다.

Bad

Blue Ocean 곡선을 예쁘게 그리는 데 집착

실행 가능성 없는 차별화. 역행 자체가 목적이 된다.

Good

Eliminate/Reduce를 Create보다 먼저 검토

축소 결정이 차별화의 핵심. 범위 축소와 포지셔닝 문장이 동시에 단단해진다.

Bad

성공 제품의 기능만 수집해 결론

생존 편향 위험. 실패한 동일 기능·철수 제품을 못 본다.

Good

late entrant · shutdown 사례 포함

기능 성공과 distribution success를 분리해 "지금도 유효한가"를 재검토한다.

05 · Gotchas

Gotchas

teardown 실무에서 자주 빠지는 함정.

!
Lightning Demo는 breadth, Teardown은 depth — 섞지 말 것

Lightning Demo에서 갑자기 플로우 해부를 시작하면 시간을 다 쓴다. 수집과 해부를 물리적으로 분리하라.

!
VPC · JTBD는 인터뷰 없이 작성하면 팀 추측 정리본이 된다

고객 목소리가 없으면 예쁜 문서로 끝난다. B2B/멀티사이드는 세그먼트 분리 필수.

!
JTBD job은 추상 ↔ 구체 스케일 조절이 핵심

너무 추상화하면 모든 제품이 경쟁처럼 보이고, 너무 좁히면 차별화 기회가 사라진다.

!
Red Route를 데이터 없이 팀 추정으로만 고르지 말 것

정치적 우선순위 싸움이 된다. 사용 빈도와 비즈니스 중요도를 분리해 근거를 남겨라.

!
Heuristic Evaluation은 도메인 특화 UX 문제를 못 잡는다

평가자 편차도 크므로 근거 캡처를 남겨라. UX Teardown 템플릿과 조합할 때 균형이 생긴다.

!
MY/NO/LIKE는 공식 정의가 없다

팀 합의된 의미를 먼저 명시하지 않으면 감상평 분류로 흐른다. `LIKE`가 슬그머니 `MY`로 번지는 경향 주의.

!
Flywheel이 있다고 가정하고 억지로 선을 잇지 말 것

초기 제품 단계에서는 loop보다 선형 성장 장치가 더 현실적이다.
