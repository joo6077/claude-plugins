제품 기획에서 flow artifact 는 「어떤 화면이 어디로 이동하는가」 만 설명하는 도표가 아니다. User Flow · Journey Map · Service Blueprint · IA 는 각기 다른 해상도로 경험과 구조를 표현한다. 이 차이를 구분하지 않으면 문서가 맞는 질문에 답하지 못한다.

00 · Overview

개요 — 네 가지 도구, 네 가지 질문

화면 이동 도표 하나로는 경험 · 운영 · 정보 구조를 다 답할 수 없다.

User Flow, Journey Map, Service Blueprint, IA(Information Architecture, 정보 구조)는 각기 다른 해상도로 경험과 구조를 표현한다.

User Flow 는 사용자가 목표를 달성하려고 밟는 분기 · 단계에 집중하고, Journey Map 은 감정과 맥락을 포함한 경험 전체를 다룬다. Service Blueprint 는 frontstage(사용자와 만나는 접점)와 backstage(접점 뒤의 운영) 체계를 함께 그린다. IA 는 정보와 내비게이션 구조를 설계한다.

Mermaid 는 이들을 가볍게 문서화할 때 쓸모 있는 공식 문법을 준다. 이 쪽의 뒤쪽 네 절이 그 문법 — flowchart · sequenceDiagram · stateDiagram · journey — 를 하나씩 다룬다.

01 · User Flow · Journey Map · Service Blueprint

셋은 대체 관계가 아니다 — 질문이 다른 도구다

User Flow 는 과업 완료 경로를, Journey Map 은 시간 순 경험과 감정 곡선을, Service Blueprint 는 접점 뒤의 운영 · 시스템 층까지 담는다.

Service Blueprint 핵심 질문 — 이 네 층이 서로 이어지는가.

1

문서가 어떤 질문에 답하려는지부터 적는다

User Flow 는 task completion(과업 완료) 경로를, Journey Map 은 시간 순 경험과 감정 곡선을, Service Blueprint 는 사용자 접점 뒤의 내부 운영 · 시스템 계층까지 포함한다. 셋은 대체 관계가 아니라 질문이 다른 도구다.

핵심 질문

  • User Flow: 목표, 단계, 분기, 예외 흐름이 있는가?
  • Journey Map: 단계별 행동, 감정, pain point, 채널이 있는가?
  • Service Blueprint: frontstage · backstage · support process · 시스템이 연결되는가?
  • 현재 문서가 어떤 질문에 답하려는지 명시했는가?
적용 시점기능 흐름 설계(user flow), 경험 진단(journey), 운영 개선(service blueprint)
한계 · 주의하나의 도표에 셋을 다 넣으려 하면 가독성이 무너진다. 의사결정 목적에 맞는 artifact 를 따로 만드는 편이 낫다.

02 · Information Architecture

IA — 화면 목록보다 한 단계 위

콘텐츠와 기능을 사람이 이해하고 찾기 쉬운 구조로 조직하는 작업이다.

축 1organization정보를 어떻게 묶는가
축 2labeling묶음을 무엇이라 부르는가
축 3navigation어떻게 옮겨 다니는가
축 4search어떻게 찾아내는가
2

무엇을 맨 위에 둘지, 어떤 말로 묶을지, 어디서 길을 잃는지

Rosenfeld · Morville 전통에서는 organization, labeling, navigation, search 시스템을 핵심 축으로 다룬다.

제품 기획 관점에서 IA 는 화면 목록 작성보다 상위 개념이다. 무엇을 top-level 로 노출할지, 어떤 용어로 묶을지, 사용자가 어디서 길을 잃는지를 다루기 때문이다. 특히 복잡한 B2B SaaS(기업을 상대로 파는 구독형 서비스)와 설정 화면, 문서형 제품에서 중요하다.

핵심 질문

  • 정보 단위가 사용자 mental model(사용자가 머릿속에 그리는 구조)에 맞게 묶였는가?
  • 라벨이 내부 조직 용어가 아니라 사용자 언어인가?
  • navigation depth(깊이)와 breadth(폭)가 과도하지 않은가?
  • 검색이 필요한 영역과 browse(둘러보기)가 적합한 영역을 구분했는가?
적용 시점내비게이션 재설계, 복잡한 정보 구조 정리, 문서 · 설정 · 관리자 제품
한계 · 주의IA 를 사이트맵만으로 줄이면 실제 탐색 경험을 놓친다. 사용자 리서치 없이 taxonomy(분류 체계)를 만들면 내부 조직도를 옮겨 적은 문서가 되기 쉽다.

3

방향을 선언하고 노드 · 엣지를 텍스트로 정의한다

Mermaid flowchart 는 빠른 decision flow, onboarding path, approval branch 를 Markdown 안에 직접 넣을 때 쓸모 있다. 공식 문서 기준으로 flowchart LR 또는 graph LR 를 선언하고 노드 · 엣지를 텍스트로 정의한다.

핵심 질문

  • 방향(LR, TD)이 목적에 맞는가?
  • 분기 조건이 edge label 로 표현되는가?
  • 소문자 end 같은 breaker(그림을 깨뜨리는 낱말)를 피했는가?
적용 시점기능 흐름, 승인 분기, funnel 시각화
한계 · 주의복잡한 experience map 전체를 flowchart 하나에 몰아넣지 않는다.

상호작용이 중심인 흐름에 쓴다

sequenceDiagram 은 actor · system 사이의 메시지 순서를 표현한다. API(프로그램끼리 주고받는 창구) handshake, approval workflow, payment callback 처럼 주고받는 순서가 핵심인 흐름에 알맞다.

핵심 질문

  • participant 를 역할 단위로 정의했는가?
  • 요청 · 응답 순서가 시간축대로 보이는가?
  • 조건 분기는 alt · else 를 쓰는가?
적용 시점시스템 상호작용, external integration(외부 서비스 연동), async callback(나중에 돌아오는 호출) 설명

08 · Anti-patterns

안티패턴과 바꿀 방향

원본 각 절의 「한계 · 주의사항」 을 나쁜 예 · 좋은 예 짝으로 옮겼다.

Bad

한 도표에 user flow · journey · blueprint 를 다 넣는다

가독성이 무너지고, 어느 질문에도 제대로 답하지 못한다.

Good

의사결정 목적마다 artifact 를 따로 만든다

문서마다 어떤 질문에 답하려는지 먼저 적고, 그 질문에 맞는 도구 하나를 고른다.

Bad

IA 를 사이트맵 한 장으로 줄인다

화면 목록은 남지만 실제 탐색 경험을 놓친다.

Good

organization · labeling · navigation · search 네 축을 다 본다

navigation 깊이와 폭, 검색이 필요한 영역과 둘러보기가 맞는 영역을 함께 따진다.

Bad

사용자 리서치 없이 taxonomy 를 만든다

내부 조직도를 옮겨 적은 문서가 되기 쉽다.

Good

사용자 언어와 mental model 로 묶는다

라벨이 내부 조직 용어가 아니라 사용자 언어인지, 정보 단위가 사용자가 그리는 구조와 맞는지 확인한다.

Bad

experience map 전체를 flowchart 하나에 몰아넣는다

flowchart 는 분기와 단계를 그리는 도구라 감정 · 맥락을 담지 못한다.

Good

flowchart 는 기능 흐름 · 승인 분기 · funnel 에 쓴다

경험 전체는 Journey Map 으로 따로 그린다.

Bad

화면 흐름을 sequenceDiagram 으로 그린다

읽기 어려워질 수 있다.

Good

sequence 는 시스템 상호작용에 쓴다

외부 연동, 나중에 돌아오는 콜백처럼 주고받는 순서가 핵심인 흐름에 한정한다.

Bad

화면 이동과 상태 전이를 섞는다

stateDiagram 에 「A 화면 → B 화면」 을 적으면 상태 규칙이 흐려진다.

Good

stateDiagram 은 엔터티 lifecycle 에 쓴다

issue · order · review 처럼 상태가 상호배타적이고 끝 상태가 있는 대상에 쓴다.

Bad

Mermaid journey 로 상세 service blueprint 를 대신한다

점수와 actor 만으로는 blueprint 를 대체하지 못한다.

Good

journey 는 간단한 as-is 여정 정리에 쓴다

운영 층까지 봐야 하면 Service Blueprint 를 따로 그린다.

09 · Gotchas

flow 문서에서 자주 놓치는 것

원본 핵심 질문 가운데 빠뜨리기 쉬운 것만 골랐다.

!
문서가 답하려는 질문을 적지 않는다

질문이 없으면 User Flow · Journey Map · Service Blueprint 가운데 무엇을 그려야 할지 정할 수 없다.

01 · 핵심 질문 넷째 줄
!
User Flow 에 예외 흐름이 없다

목표 · 단계 · 분기만 그리고 예외 흐름을 빼면 원본 체크리스트 한 칸이 빈다.

01 · User Flow 체크리스트
!
Service Blueprint 의 층이 끊겨 있다

frontstage · backstage · support process · 시스템이 서로 연결되는지 확인한다. 층만 나열하면 blueprint 가 아니다.

01 · Service Blueprint 체크리스트
!
IA 라벨이 내부 조직 용어다

라벨은 사용자 언어로 쓴다. 조직도 이름을 그대로 쓰면 사용자는 어디로 가야 할지 모른다.

02 · IA 핵심 질문
!
flowchart 에 소문자 end 를 쓴다

원본이 breaker 로 꼽은 낱말이다. 노드 이름에 쓰지 않았는지 확인한다.

03 · flowchart 핵심 질문
!
stateDiagram 에 끝 상태가 없다

상태가 상호배타적인지, 전이 이벤트가 명확한지와 함께 terminal state 가 있는지 본다. 원본 예시는 Released --> [*] 로 끝낸다.

05 · stateDiagram 핵심 질문
!
journey 점수 범위가 섞인다

task score 는 1~5 범위로 일관되게 쓰고, actor 를 빠뜨리지 않는다.

06 · journey 핵심 질문
!
Mermaid 예시를 렌더 확인을 거친 그림으로 믿는다

원본은 flowchart 예시를 공식 문서 문법에 맞췄을 뿐, 2026-09-24 에 확인한 최신 안정판 12.0.0 에서 렌더해 보지는 않았다고 적는다.
