Planning Kit v0.1 · Stories

Stories

스토리는 backlog를 예쁘게 적는 기술이 아니라, 작게 나누되 맥락을 잃지 않게 만드는 언어 체계다. INVEST · Gherkin · Story Mapping · Acceptance Criteria를 함께 써서 가치 · 맥락 · 검증 기준을 동시에 담는다.

01 · Methods

스토리 작성 방법론

네 가지 도구가 서로 다른 질문에 답한다.

1

INVEST

좋은 user story의 품질 체크리스트. Independent · Negotiable · Valuable · Estimable · Small · Testable 여섯 조건으로 스토리를 점검한다.

  • Independent: 다른 스토리에 과도하게 묶이지 않음
  • Negotiable: 솔루션이 아니라 대화 가능한 요구
  • Valuable · Estimable · Small · Testable
Agile Alliance — INVEST
2

Gherkin / Given-When-Then

executable specification 문법. Given(초기 맥락), When(사건), Then(기대 결과)로 비즈니스 규칙을 예시로 표현한다.

  • UI 버튼 위치가 아닌 관찰 가능한 결과를 서술
  • 각 시나리오 3~5 step으로 유지
  • 도메인 언어 사용, 구현 세부는 금지
Cucumber — Gherkin Reference
3

Story Mapping (Jeff Patton)

backlog를 납작한 리스트가 아니라 사용자 활동 흐름에 따라 배치한다. end-to-end 맥락 유지 + release slicing에 강하다.

  • backbone activity를 사용자 여정 순서대로 배치
  • activity 아래에 세부 story 분해
  • 첫 release slice = 작지만 완결된 경험
Jeff Patton — Story Mapping
4

Acceptance Criteria 패턴

스토리가 "done"인지 판단하는 명시적 조건. 관찰 가능 · 테스트 가능해야 하며, 범위와 예외를 명확히 한다.

  • 성공 조건 · 예외 조건 · 권한/제약을 분리
  • happy path뿐 아니라 edge case · error state · data 제약 포함
  • 구현 힌트를 주되 구현을 강제하지 않음
Cucumber — Examples as Contract
02 · Gherkin Example

Gherkin 시나리오 예시

관찰 가능한 결과 중심으로 쓴 수용 기준.

Feature: 워크스페이스 초대 수락
  As a 초대받은 사용자
  I want 초대 링크를 클릭하면 워크스페이스에 즉시 참여하도록
  So that 온보딩 첫 단계에서 이탈하지 않게

  Scenario: 유효한 초대 링크 수락
    Given "acme" 워크스페이스의 유효한 초대 토큰을 가진 사용자가 있다
    And 해당 사용자는 아직 계정이 없다
    When 사용자가 초대 링크를 클릭하고 이메일/비밀번호를 등록한다
    Then 사용자는 "acme" 워크스페이스의 member 권한으로 입장한다
    And 워크스페이스 홈의 첫 3단계 온보딩이 노출된다

  Scenario: 만료된 초대 링크
    Given 만료된 초대 토큰
    When 사용자가 링크를 클릭한다
    Then "초대가 만료되었습니다" 페이지가 표시된다
    And 초대자에게 재발송 요청 버튼이 제공된다
03 · INVEST Scorecard

INVEST 체크 기준

backlog refinement에서 스토리 하나를 6축으로 점검한다.

축합격 기준실패 신호
Independent다른 스토리 종료를 기다리지 않고 시작 가능"A가 끝나야 시작할 수 있음"
Negotiable해결 방법에 여지가 있음구현 상세가 스토리에 박제됨
Valuable사용자/비즈니스 가치가 한 문장으로 설명됨기술 태스크 제목과 동일
Estimable팀이 대략 추정 가능"해봐야 안다"만 반복
Small한 iteration 안에 소화 가능1 스프린트 이상 소요
Testableacceptance criteria가 관찰 가능"잘 동작하면 OK"
04 · Story Map Structure

Story Map 기본 구조

backbone activity 위에 slice별 세부 story가 얹힌다.

Backbone (사용자 활동 흐름):
  [Discover] →  [Sign up] →  [Onboard] →  [Invite team] →  [Get value]

Release slice 1 — Walking Skeleton (MVP):
  Discover     : 랜딩 페이지에서 가치 한 줄 노출
  Sign up      : 이메일 + 비밀번호 가입만 지원
  Onboard      : 워크스페이스 생성 1단계
  Invite team  : 이메일 초대 1건
  Get value    : 첫 프로젝트 생성 + 1 issue 만들기

Release slice 2 — Activation 강화:
  Discover     : 비교 표 · 데모 비디오
  Sign up      : Google / GitHub OAuth
  Onboard      : 템플릿 선택 · 샘플 데이터
  Invite team  : 링크 기반 bulk 초대
  Get value    : 첫 automation / integration 연결

Release slice 3 — Team scale:
  Onboard      : role 기반 onboarding 분기
  Invite team  : SSO · SCIM 프로비저닝
  Get value    : cross-team 대시보드
05 · Anti-patterns

안티패턴 vs 좋은 패턴

스토리가 task 티켓으로 쪼그라드는 전형적 실수.

Bad

"결제 버튼 추가" 같은 task 제목형 스토리

가치 · 맥락 · 검증 기준이 전부 빠져 있다. 완료의 의미가 불명확.

Good

"사용자는 장바구니에서 즉시 결제할 수 있다" + Acceptance

사용자 가치가 드러나고, 완료 판정 기준이 관찰 가능하다.

Bad

Gherkin에 UI step 범람

"버튼 X를 클릭한다"가 누적되며 brittle test 문서로 전락한다.

Good

도메인 언어로 "행동 규칙"을 기술

UI 세부는 step definition에 격리. 테스트의 수명이 길어진다.

Bad

Story Map이 워크숍 사진으로만 남음

backlog/roadmap과 연결되지 않아 휘발된다.

Good

Map의 slice가 release plan에 그대로 연결됨

매 release마다 map 업데이트 + PR 링크로 추적.

06 · Gotchas

Gotchas

스토리 작성에서 반복되는 실수.

!
INVEST 항목을 형식적으로만 맞추기

여섯 축이 모두 체크돼도 실제로는 맥락 없는 스토리일 수 있다. 품질 체크이지 우선순위 도구가 아니다.

!
모든 스토리를 Gherkin으로 쓰지 않는다

비즈니스 규칙이 중요한 스토리에만 Gherkin을 쓰고, 단순 작업은 체크리스트형 acceptance로 충분하다.

!
Story Map 상세화가 유지비를 폭발시킴

map은 "전체 구조 이해"용이지 상세 scheduler가 아니다. 고해상도 slice는 sprint board가 맡는다.

!
Acceptance Criteria를 설계 문서화

너무 상세해지면 협상 가능성이 사라지고, 너무 추상적이면 쓸모가 없다. 관찰 가능한 행동 수준에서 멈춰라.

07 · Acceptance Styles

Acceptance Criteria 3가지 포맷

상황에 맞는 포맷을 고르고 섞지 않는다.

포맷적합한 상황예시
Checklist 단순 UI/CRUD 스토리 "초대 링크 입력 필드 · 복사 버튼 · 만료일 표시"
Gherkin 비즈니스 규칙 · edge case가 복잡 Given/When/Then 시나리오 세트
Rule-based 규칙이 많지만 시나리오는 단순 "만료 72h 전 이메일 · 만료 후 7d 로그 보존 · 재발송 rate 5/h"
