PRD Patterns

PRD(제품 요구사항 문서)는 더 이상 한 가지 형식으로 고정되지 않는다. 서사를 먼저 쓰는 문서, Shape Up pitch, 이슈 · 문서 템플릿 중심의 가벼운 스펙까지 모양은 다르지만, 중요한 것은 형식보다 의사결정 구조다.

00 · Overview

개요 — 형식이 아니라 의사결정 구조

조직 문화마다 PRD 모양이 다르다. 그래도 강한 패턴은 같은 다섯 가지를 나눠 적는다.

어떤 조직은 서사를 먼저 쓰는 문서(narrative-first)를 쓰고, 어떤 조직은 Shape Up pitch 처럼 appetite 와 no-go 를 강조하며, 어떤 조직은 이슈 · 문서 템플릿 중심의 가벼운 스펙을 선호한다. 중요한 것은 형식보다 의사결정 구조다.

아래 패턴들은 각기 다른 조직 문화를 반영하지만, 공통으로 「실행팀이 독립적으로 좋은 판단을 내릴 수 있는 정보 밀도」를 높이는 데 초점이 있다.

이번 판(v0.2.0)은 여섯 패턴 뒤에 원칙 하나를 더했다 — 사용자가 버리기로 한 결정을 PRD 비범위 절 한 곳에만 적는 규칙이다.

  1. 문제 정의지금 풀어야 할 문제
  2. 대상 사용자 · 고객누구를 위한 것인가
  3. 성공 기준무엇을 보고 성공이라 할 것인가
  4. 범위 · 비범위하는 것과 하지 않는 것
  5. 남아 있는 리스크아직 풀리지 않은 위험

원본 개요가 「최소한 다섯 가지를 분리한다」 고 적은 그 다섯. 패턴별로 어디서 다루는지는 03 절에 모았다.

01 · Patterns

PRD 작성 패턴 여섯 가지

패턴마다 요약 · 핵심 질문 · 적용 시점 · 한계 · 출처를 원본 그대로 옮겼다.

1

Amazon Working Backwards (PR/FAQ)

내부 아이디어를 고객 관점의 보도자료(Press Release)와 FAQ(자주 묻는 질문)로 먼저 표현하는 방식으로 알려져 있다. 기능 명세보다 고객 효익과 고객이 느끼는 변화를 먼저 쓰고, 어려운 질문의 답을 미리 적는다.

PR/FAQ 는 팀이 고객 언어로 생각하게 만든다. 보도자료는 「출시 후 세상」 을 가정하고, FAQ 는 내부 실행 위험과 까다로운 반대 질문을 드러낸다. 그래서 아이디어의 모호함과 부풀린 기대를 초기에 깎아낸다.

핵심 질문

  • 보도자료 첫 문단에서 고객 가치가 분명한가?
  • 누구를 위한 출시인지 적혀 있는가?
  • FAQ 가 칭찬용 질문이 아니라 실제 반대 질문을 다루는가?
  • 고객 혜택 · 운영 영향 · 가격 · 정책 · 단계적 출시(롤아웃) 제약이 들어 있는가?
  • 문서만 읽고도 「왜 지금 이걸 하는지」 가 이해되는가?
적용 시점신규 제품 제안, 큰 베팅(bets) 검토, 임원 검토(exec review) 전 서사 정렬
한계 · 주의서사가 강해도 실행 세부는 별도 산출물이 필요하다. 조직이 문서로 토론하는 훈련이 약하면 구호 문서로 전락하기 쉽다.

2

Shape Up Pitch (Basecamp / Ryan Singer)

pitch 는 Problem · Appetite · Solution · Rabbit holes · No-gos 다섯 요소를 뼈대로 삼는다. 전통적 PRD 처럼 세부 요구사항을 빠짐없이 적는 문서가 아니라, 팀이 6 주 주기 안에서 스스로 마무리할 수 있는 경계를 설계하는 문서다.

Shape Up 은 범위를 약속하지 않고 appetite(이 문제에 쓸 의향이 있는 시간)를 약속한다. 그래서 pitch 는 「무엇을 다 만들 것인가」 보다 「이 시간 상자 안에서 어떤 문제를 어느 정도 해상도로 풀 것인가」 를 분명히 한다. Rabbit holes(빠지기 쉬운 함정)와 No-gos(이번에 하지 않을 것)는 함정과 비범위를 문서에서 먼저 드러낸다는 점에서 특히 실무적이다.

핵심 질문

  • Problem — 지금 해결해야 할 문제는 무엇인가?
  • Appetite — 이 문제에 얼마의 시간을 쓸 의향이 있는가?
  • Solution — 팀이 출발할 수 있을 만큼 구체적인가?
  • Rabbit holes — 빠지기 쉬운 함정은 무엇인가?
  • No-gos — 이번 사이클에 하지 않을 것은 무엇인가?
적용 시점시간 상자형 전달, 불확실성 높은 개선 과제, 범위가 슬금슬금 불어나는 것(scope creep)을 막아야 할 때
한계 · 주의과제를 다듬는(shaping) 역량이 약하면 지나치게 모호해질 수 있다. appetite 는 있는데 성공 기준이 약하면 결과 평가가 흐려진다.

Linear 공개 문서 패턴

Linear 는 전통적 장문 PRD 템플릿보다 issue template · project template · issue document 중심의 가벼운 문서 구조를 공개한다. 스펙을 계획 도구 안에 붙여 두고, 이슈 · 프로젝트 상태와 떨어지지 않게 한다.

실무에서는 「문서 따로, 실행 보드 따로」 두 벌을 관리하는 비용을 줄이는 패턴으로 읽을 수 있다. 템플릿으로 필수 필드와 자리 표시 글(placeholder)을 강제하고, project template 에 milestone 과 issue 를 미리 넣어 두는 방식은 반복 계획에 강하다.

핵심 질문

  • 이슈를 만들 때 반드시 채워야 할 맥락 필드가 있는가?
  • project template 에 milestone · issue 구조를 미리 정해 두었는가?
  • 스펙 문서가 이슈 · 프로젝트와 링크된 한 작업 공간(single workspace) 안에 있는가?
  • 템플릿이 들어온 이슈를 먼저 볼 것부터 골라내는 일과 보고 체계까지 고려하는가?
적용 시점빠르게 반복하는 팀, 계획과 실행 통합, 템플릿 기반 운영을 자리 잡게 할 때
한계 · 주의문서가 지나치게 가벼우면 복잡한 전략 맥락을 잃기 쉽다. 템플릿만 복제하고 사고 구조를 복제하지 못하면 품질이 들쭉날쭉해진다.

Notion 공개 Product Spec / PRD 템플릿

Context · Goals/KPI(핵심 성과 지표) · Constraints · Assumptions · Dependencies · Tasks 처럼 범용이면서 협업에 바로 쓸 수 있는 절 구조를 준다. 문서 안에서 관련 데이터베이스와 페이지를 relation 으로 잇기 쉽다는 점이 특징이다.

이 패턴은 깊이 있는 전략 문서보다 함께 고쳐 가는 살아 있는 문서(living document)에 맞다. 개요 문서와 세부 리서치, 사용자 페르소나, 작업 분해를 링크로 묶어 PRD 를 허브 문서로 운영할 수 있다.

핵심 질문

  • Context — 배경을 1~2 문장으로 요약했는가?
  • Goals/KPI — 성공을 어떻게 재는가?
  • Constraints — 기술 · 정책 · 자원 제약은 무엇인가?
  • Assumptions — 아직 사실이 아닌 전제는 무엇인가?
  • Dependencies/Tasks — 선행 조건과 실행 항목이 이어져 있는가?
적용 시점문서 허브형 운영, 여러 직군이 함께하는 협업(cross-functional), 연결된 데이터베이스(linked database)로 추적할 때
한계 · 주의자유도가 높아 표준화가 약해질 수 있다. relation 설계 없이 문서만 늘어나면 찾는 비용이 커진다.

Stripe 공개 문서형 spec 패턴

원본이 밝힌 한계 2026-04-14 기준으로 검증할 수 있는 Stripe 의 공식 「PRD 템플릿」 주소는 확인하지 못했다. 아래는 PRD 템플릿이 아니라 공개 문서에서 읽어 낸 구조다.

Stripe 는 제품 가이드와 문서 페이지에서 목적 · 핵심 개념 · 요구 필드 · 예시 · 운영 규칙을 매우 구조적으로 보여 준다. 공개 산출물 관점에서는 이것이 사실상 스펙 구실을 한다.

고객이나 개발자가 직접 쓰는 제품은 내부 PRD 가 아니어도 공개 문서에서 요구사항 구조가 드러난다. 즉 PM(제품 관리자) 문서는 배경과 의사결정, 공개 문서는 계약과 사용법으로 나뉠 수 있다.

핵심 질문

  • 제품 개념과, 데이터가 어떤 모양이어야 하는지 정한 틀을 나눠 설명하는가?
  • 필드마다 요구 수준(required · recommended · optional)이 분명한가?
  • 예시 값 · 검증 규칙 · 갱신 규칙이 있는가?
  • 문서가 연동 계약(integration contract) 구실을 하는가?
적용 시점프로그램끼리 주고받는 창구(API) · 플랫폼 제품, 외부 개발자 대상 기능, 문서가 곧 제품 계약인 경우
한계 · 주의PRD 를 대신하는 문서가 아니라 공개 계약 문서 패턴이다. 내부 의사결정 근거, 무엇을 얻고 무엇을 내줬는지(trade-off), 비범위는 별도 문서가 필요하다.
출처 Stripe Docs — How products and prices work Stripe Docs — Agentic commerce product catalog

Google Design Sprint 산출물

Google/GV Design Sprint 는 긴 PRD 대신 짧은 기간에 map → sketches → decision → storyboard → prototype → test 라는 연속 산출물을 만든다. 「문서로 합의」 보다 가설을 눈에 보이게 만들고 검증하는 데 특화되어 있다.

그래서 sprint 산출물은 PRD 를 대체한다기보다 발견 단계에서 스펙으로 넘어가는 다리 구실을 한다. 팀이 문제 공간과 해법 공간을 좁혀 가는 과정 자체가 문서가 되고, 테스트 결과를 바탕으로 요구사항을 뒤늦게 굳힌다.

핵심 질문

  • Map — 사용자와 핵심 흐름이 한 장에 정리됐는가?
  • Sketch — 각자 해법을 그림으로 제안했는가?
  • Decide — 어떤 접근을 골랐는가?
  • Storyboard — 테스트할 수 있는 처음부터 끝까지의 흐름이 있는가?
  • Prototype/Test — 실제 사용자 반응으로 검증했는가?
적용 시점불확실성이 큰 신규 흐름, 여러 직군의 방향 맞추기, 빠른 시제품(prototype) 검증
한계 · 주의sprint 는 실행 결정까지 빠르게 가지만 뒤이은 상세 스펙을 자동으로 만들어 주지는 않는다. 반복 운영 체계 없이 1 회성 워크숍으로 끝나면 효과가 급감한다.
출처 The Sprint Bookdated 2025-10 GV — The Design Sprint
02 · Discarded decisions

폐기한 결정 — 비범위 절 한 곳에 적는다

이번 판에 새로 들어온 원칙. 여섯 패턴 어느 형식을 쓰든 버린 결정을 적는 자리는 하나다.

새 절 · 원본 v0.2.0

결정 원문은 PRD 비범위 절 한 곳에만 둔다

사용자가 버리기로 한 기능 · 설정 항목은 그 기능 PRD 의 비범위 절에 적는다. 디자인 승인 기록 · 작업 계약 · 핸드오프처럼 같은 결정을 다시 언급하는 문서는 이 PRD 경로를 가리키고 결정을 다시 쓰지 않는다 — 원문이 두 곳에 있으면 한쪽만 고쳐진다.

형식마다 절 이름

PR/FAQ · Linear-style 스펙 ## Non-goals (폐기한 결정 포함) 비범위 절 이름에 폐기한 결정이 들어 있음을 밝힌다.
Shape Up pitch ## No-gos 원문 용어를 그대로 쓴다. pitch 다섯 요소 가운데 하나다.

원문 한 곳, 나머지는 가리키기만

원문 그 기능 PRD 의 비범위 절 버린 항목 · 이유 · 범위 · 코드에 남은 흔적을 네 칸 표로 적는다. PRD 를 쓴 뒤에 나온 폐기 결정도 새 문서가 아니라 이 표에 한 줄 더한다.
  • ←
    디자인 승인 기록PRD 경로만 가리킨다
  • ←
    작업 계약PRD 경로만 가리킨다
  • ←
    핸드오프PRD 경로만 가리킨다

세 문서는 결정을 다시 쓰지 않는다. 결정을 고칠 일이 생기면 PRD 표 한 줄만 고치면 된다.

비범위 표 — 네 칸

칸 이름과 범위 값 · 없음 규칙은 원본 체크리스트 그대로다. 셋째 칸 「적는 것」 은 원본 문장에서 옮겼다.
칸적는 것규칙
하지 않는 것사용자가 버리기로 한 기능 · 설정 항목PRD 를 쓴 뒤에 나온 폐기 결정도 이 표에 한 줄 더한다
이유왜 뺐는가Shape Up No-gos 정의가 「무엇을 뺐는지와 왜 뺐는지」 의 출처다
범위결정이 어디까지 미치는가이번 PRD · 이번 사이클 · 제품 전체 가운데 하나
코드에 남은 흔적서버 필드 · 호출되지 않는 화면 파일 등흔적이 없으면 없음 이라고 적는다. 흔적은 채울 빈틈이 아니라 치울 목록이다

핵심 질문

  • 비범위 표가 네 칸(하지 않는 것 · 이유 · 범위 · 코드에 남은 흔적)을 갖는가? 흔적이 없으면 없음 이라고 적었는가?
  • 범위 칸이 이번 PRD · 이번 사이클 · 제품 전체 가운데 하나인가?
  • PRD 를 쓴 뒤에 나온 폐기 결정을 새 문서가 아니라 이 표에 한 줄 더했는가?
  • 뒤 단계 산출물(스토리 · 흐름 · 데이터 모델)이 표의 항목을 다시 만들지 않았는가?

근거가 어디서 왔나

INVEST 의 Negotiable(협상할 수 있다)은 스토리를 특정 기능의 고정 계약으로 보지 않는다 Agile Alliance 용어집 외부 방법론
코드에 남은 흔적 칸과 「흔적은 채울 빈틈이 아니라 치울 목록」 이라는 분류 — 이 킷의 운영 규칙
적용 시점PRD 작성, 기획 도중 사용자가 기능이나 설정 항목을 없애기로 한 때, 스토리 · 흐름 · 데이터 모델을 PRD 에서 이어 만들 때
한계 · 주의폐기는 영구 금지가 아니다. Shape Up 의 No-gos 는 그 pitch 와 appetite 안의 결정이고, INVEST 의 Negotiable 은 스토리를 특정 기능의 고정 계약으로 보지 않는다. 그래서 뒤 단계 산출물이 표의 항목과 겹치면 되살리지 말고 먼저 묻는다. PRD 가 없는 프로젝트의 기록 자리는 이 절이 정하지 않는다.

04 · Pattern picker

어떤 패턴을 고를까

왼쪽은 원본의 「적용 시점」 그대로다. 조직 문화와 전달 주기, 문서를 읽는 사람에 따라 궁합이 다르다.

신규 제품 제안 · 큰 베팅 검토 · 임원 검토 전 서사 정렬
→

빠르게 반복하는 팀 · 계획과 실행 통합 · 템플릿 기반 운영
→
Linear 템플릿스펙을 이슈 · 프로젝트 옆에 붙여 둔다
문서 허브형 운영 · 여러 직군 협업 · 연결된 데이터베이스로 추적
→
Notion Product Specrelation 으로 리서치 · 페르소나 · 작업을 묶는다

05 · Shape Up skeleton

Shape Up pitch 뼈대

다섯 절 제목과 원본 핵심 질문만 둔 빈 틀이다. No-gos 절에 02 절의 네 칸 표가 들어간다.

# [Pitch] <제목>

## Problem
<!-- 지금 해결해야 할 문제는 무엇인가? -->

## Appetite
<!-- 이 문제에 얼마의 시간을 쓸 의향이 있는가? -->

## Solution
<!-- 팀이 출발할 수 있을 만큼 구체적인가? -->

## Rabbit holes
<!-- 빠지기 쉬운 함정은 무엇인가? -->

## No-gos
<!-- 이번 사이클에 하지 않을 것 · 폐기한 결정 -->

| 하지 않는 것 | 이유 | 범위 | 코드에 남은 흔적 |
| --- | --- | --- | --- |
| <항목> | <왜 뺐나> | 이번 사이클 | 없음 |

PR/FAQ · Linear-style 스펙이면 마지막 절 제목만 ## Non-goals (폐기한 결정 포함) 으로 바꾼다. 표는 같다.

경계를 설계하는 문서 세부 요구사항을 빠짐없이 적는 대신, 팀이 6 주 주기 안에서 스스로 마무리할 수 있는 경계를 그린다.
Rabbit holes · No-gos 는 먼저 적는다 함정과 비범위를 문서에서 먼저 드러낸다는 점이 이 형식의 실무적 강점이다.
성공 기준은 따로 챙긴다 다섯 절에 성공 기준 칸이 없다. appetite 는 있는데 성공 기준이 약하면 결과 평가가 흐려진다는 것이 원본이 적은 한계다.
No-gos 는 영구 금지가 아니다 그 pitch 와 appetite 안의 결정이다. 뒤 단계 산출물이 겹치면 되살리지 말고 먼저 묻는다.
06 · Anti-patterns

안티패턴 vs 좋은 패턴

원본 핵심 질문을 뒤집으면 드러나는 실패. 오른쪽은 그 질문을 통과한 모습이다.

Bad

보도자료가 기능 설명으로 시작한다

PR/FAQ 형식을 써도 첫 문단이 고객 가치가 아니면, 팀을 고객 언어로 생각하게 만드는 장점이 사라진다.

Good

첫 문단에 고객 가치와 대상을 적는다

보도자료 첫 문단에서 고객 가치가 분명하고, 누구를 위한 출시인지 적혀 있다.

Bad

FAQ 가 칭찬용 질문뿐이다

까다로운 반대 질문이 빠지면 모호함과 부풀린 기대를 초기에 깎아내지 못한다.

Good

FAQ 가 실제 반대 질문을 다룬다

고객 혜택 · 운영 영향 · 가격 · 정책 · 단계적 출시 제약까지 답을 미리 적는다.

Bad

버린 결정을 여러 문서에 다시 쓴다

디자인 승인 기록 · 작업 계약 · 핸드오프에 같은 결정을 옮겨 적으면, 나중에 한쪽만 고쳐진다.

Good

원문은 PRD 비범위 절 한 곳

다른 문서는 그 PRD 경로를 가리키기만 한다. PRD 뒤에 나온 폐기 결정도 같은 표에 한 줄 더한다.

Bad

뒤 단계 산출물이 버린 항목을 되살린다

스토리 · 흐름 · 데이터 모델을 이어 만들다가 비범위 표에 있는 항목을 슬그머니 다시 만든다.

Good

겹치면 먼저 묻는다

폐기는 영구 금지가 아니다. 그래서 되살릴지 말지를 혼자 정하지 않고 사용자에게 먼저 묻는다.

07 · Gotchas

함정 — 원본의 한계 · 주의사항

일곱 절 각각의 「한계/주의사항」 을 한곳에 모았다.

!
PR/FAQ 서사만으로 실행이 보장되지 않는다

서사가 강해도 실행 세부는 별도 산출물이 필요하다. 조직이 문서로 토론하는 훈련이 약하면 구호 문서로 전락하기 쉽다.

Amazon Working Backwards

!
appetite 만 있고 성공 기준이 없다

shaping 역량이 약하면 pitch 가 지나치게 모호해진다. appetite 는 있는데 성공 기준이 약하면 결과 평가가 흐려진다.

Shape Up Pitch

!
가벼운 템플릿이 전략 맥락을 잃는다

문서가 지나치게 가벼우면 복잡한 전략 맥락을 잃기 쉽다. 템플릿만 복제하고 사고 구조를 복제하지 못하면 품질이 들쭉날쭉해진다.

Linear 공개 문서 패턴

!
허브 문서가 늘기만 한다

자유도가 높아 표준화가 약해질 수 있다. relation 설계 없이 문서만 늘어나면 찾는 비용이 커진다.

Notion Product Spec / PRD

!
공개 문서는 PRD 를 대신하지 않는다

공개 계약 문서 패턴일 뿐이다. 내부 의사결정 근거, 무엇을 얻고 무엇을 내줬는지, 비범위는 별도 문서가 필요하다. Stripe 의 공식 PRD 템플릿 주소는 2026-04-14 기준으로 확인하지 못했다.

Stripe 공개 문서형 spec

!
Design Sprint 를 1 회 워크숍으로 끝낸다

sprint 는 실행 결정까지 빠르게 가지만 뒤이은 상세 스펙을 자동으로 만들어 주지 않는다. 반복 운영 체계 없이 1 회성으로 끝나면 효과가 급감한다.

Google Design Sprint

!
폐기를 영구 금지로 읽는다

No-gos 는 그 pitch 와 appetite 안의 결정이다. 뒤 단계 산출물이 표의 항목과 겹치면 되살리지 말고 먼저 묻는다. 흔적 칸과 「치울 목록」 분류는 외부 방법론이 아니라 이 킷의 운영 규칙이고, PRD 가 없는 프로젝트의 기록 자리는 이 절이 정하지 않는다.

폐기한 결정 — 비범위 절 한 곳에 적는다
