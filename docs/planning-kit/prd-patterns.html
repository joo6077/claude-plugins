PRD Patterns

PRD는 한 가지 형식이 아니다. narrative-first · Shape Up pitch · lightweight issue template · 공개 문서형 spec · Design Sprint 산출물까지. 형식보다 실행팀이 독립적으로 좋은 판단을 내릴 수 있는 정보 밀도가 중요하다.

01 · Patterns

PRD 작성 패턴

각 패턴은 문제 · 대상 · 성공기준 · 범위/비범위 · 리스크를 다르게 분리한다.

1

Amazon Working Backwards (PR/FAQ)

내부 아이디어를 고객 관점의 보도자료와 FAQ로 먼저 표현한다. 기능 명세 전에 고객 효익과 까다로운 반대 질문을 선제적으로 드러낸다.

  • PR 첫 문단에 고객 가치가 명확히 드러남
  • FAQ는 칭찬이 아니라 실제 반대 질문을 다룸
  • 고객 혜택 · 운영 영향 · 가격 · 롤아웃 제약을 포함
Amazon — Working Backwards culture
2

Shape Up Pitch (Basecamp / Ryan Singer)

Problem · Appetite · Solution · Rabbit holes · No-gos를 핵심 구성요소로 삼는다. 범위를 약속하지 않고 appetite(시간 상자)를 약속한다.

  • Appetite: 6주 · 2주 같은 시간 상자 단위
  • Rabbit holes: 빠지기 쉬운 함정을 미리 명시
  • No-gos: 이번 사이클 비범위를 문서에 고정
Shape Up — Writing the Pitch
3

Linear 공개 문서 패턴

장문 PRD 대신 issue template · project template · issue document 중심의 경량 문서 구조. spec을 planning system 안에 두어 문서와 실행 보드의 이중 관리 비용을 줄인다.

  • issue 생성 시 필수 컨텍스트 필드 강제
  • project template에 milestone/issue 사전 포함
  • spec이 보드와 같은 workspace 안에 존재
Linear Docs — Issue Templates
4

Notion 공개 Product Spec / PRD

Context · Goals/KPI · Constraints · Assumptions · Dependencies · Tasks 등 범용 섹션 구조 + relation 기반 링크로 허브 문서를 구성한다.

  • Context를 1~2문장으로 요약
  • Assumptions = 아직 사실이 아닌 전제를 명시
  • Dependencies/Tasks를 relation으로 연결
Notion — Product Spec Template
5

Stripe 공개 문서형 spec

고객/개발자-facing 제품에서 공식 문서 자체가 spec 역할을 한다. 목적 · 핵심 개념 · 요구 필드 · 예시 · 운영 규칙이 매우 구조적으로 제시된다.

  • 제품 개념과 스키마가 분리돼 설명
  • 필드별 required/recommended/optional 명시
  • 예시 값 · validation rule · update rule 포함
Stripe Docs — Products & Prices
6

Google Design Sprint 산출물

긴 PRD 대신 map → sketches → decision → storyboard → prototype → test의 연속 산출물을 만든다. 문서로 합의하지 않고 가설을 시각화해 검증한다.

  • Map: 사용자와 핵심 흐름을 한 장에 정리
  • Storyboard: 테스트 가능한 end-to-end 흐름
  • Prototype/Test: 실제 사용자 반응 검증
The Sprint Book — GV Design Sprint
02 · Structure

좋은 PRD의 5 블록

형식은 달라도 공통적으로 분리되는 정보 축.

블록질문산출물 예
Problem지금 해결해야 할 문제는 무엇인가?user quote, baseline metric
Audience누구를 위한 것인가?segment · persona · JTBD

Scope / Non-goals무엇을 하고, 무엇을 하지 않는가?MoSCoW, No-gos, rabbit holes

03 · Shape Up Skeleton

Shape Up Pitch 스켈레톤

시간 상자형 delivery에서 가장 자주 쓰는 경량 포맷.

# [Pitch] 워크스페이스 초대 재설계

## Problem
초대 수락률이 42% → 29%로 떨어졌다. 신규 사용자가 초대 메일에서
워크스페이스 컨텍스트를 이해하지 못한다는 피드백이 반복된다.

## Appetite
6주 (small batch). 그 이상 걸리면 접는다.

## Solution
- 초대 메일에 워크스페이스 프리뷰 카드 추가
- 수락 화면에 "왜 이 워크스페이스인가" 설명 + 첫 3단계 온보딩
- 이메일 검증과 초대 수락을 한 플로우로 통합

## Rabbit holes
- SSO/SAML 조직의 로그인 흐름을 같이 건드리지 않는다
- 이메일 템플릿 i18n 리팩토링을 여기서 하지 않는다

## No-gos
- 초대 링크 보안 모델 변경
- 새 권한 체계 도입
04 · Anti-patterns

안티패턴 vs 좋은 패턴

PRD를 설명 문서로만 쓰면 빠지는 함정.

Bad

해결책을 먼저 적고 문제를 역으로 맞춘다

PR/FAQ 형식이라도 고객 가치가 아니라 기능 설명으로 시작하면 실패.

Good

고객 언어로 "출시 후 세상"부터 적는다

보도자료 1문단에 고객 혜택과 변화가 나타날 때까지 리라이트.

Bad

Shape Up pitch에 No-gos가 없다

scope creep이 생기고 6주 안에 못 끝낸다.

Good

Rabbit holes와 No-gos를 문서 레벨에서 고정

팀이 6주 동안 직접 참조 가능한 경계.

Bad

Notion 허브 문서가 점점 기능 목록으로 변함

자유도 높은 템플릿이 표준화를 잃는다.

Good

Context + Assumptions + Success 블록은 reserved

최소 고정 필드를 정해 협업형 허브 문서의 장점을 유지.

05 · Gotchas

Gotchas

PRD 작성 시 반복되는 함정.

!
PR/FAQ는 narrative만으로 실행을 보장하지 않는다

narrative가 강해도 엔지니어링 세부 · 운영 리스크는 별도 artifact가 필요하다. 문서 토론 훈련 없는 조직에서는 슬로건화되기 쉽다.

!
Shape Up appetite만 있고 성공 기준이 없다

appetite는 "얼마의 시간을 쓸 것인가"다. 그 안에서 어떤 결과를 "성공"으로 볼지는 별도로 정의해야 한다.

!
Linear 경량 템플릿에 전략 문맥이 사라진다

템플릿만 복제하고 사고 구조를 복제하지 못하면 품질이 들쭉날쭉해진다. PRD 상위에 왜(why) 문서를 따로 둬라.

!
Stripe형 공개 문서 = PRD 대체재가 아니다

공개 문서는 계약과 사용법. 내부 trade-off · 비범위 · 의사결정 근거는 내부 문서로 남겨야 한다.

!
Design Sprint 1회 워크숍으로 끝내면 효과가 급감한다

sprint는 discovery-to-spec 브리지다. 후속 상세 spec과 반복 운영 체계가 없으면 휘발된다.
