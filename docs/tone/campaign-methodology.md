# 코드 정리 캠페인 운영 방법론

수십~수백 파일을 규칙 기준으로 정리하는 장기 작업을 어떻게 굴리는가. 한 번에 한 파일, 승인 게이트, 재개 가능한 원장, 복수 착지점 피드백이 뼈대다.
이 문서의 근거는 대부분 한 프로젝트에서 2개월 반 동안 실제로 굴린 캠페인의 실측이며, 스택·언어에 의존하는 내용은 포함하지 않는다.

---

## 원칙

### 1. 한 번에 한 파일 `[코어]`

**강도:** MUST

캠페인의 편집 단위는 파일 1개다. 여러 파일을 모아 한 번에 고치면 승인 게이트가 형식만 남는다 — 사용자는 diff 총량을 확인할 수 없고, 되돌릴 때도 무관한 파일까지 함께 되돌아간다.
"일괄 편집 금지, 제안 없이 선수정 금지"는 캠페인 문서에 처음부터 박아 두는 3대 금지 중 둘이다. 나머지 하나가 원장 임의 전환 금지다.
파일 하나를 닫기 전에는 다음 파일을 열지 않는다. 예외는 삭제 대상 파일처럼 편집이 0줄인 경우뿐이다.

> **출처:** 프로젝트 실측 — 피드백 로그 89 엔트리 / 30 세션 (2026-04-16 ~ 2026-06-29)

### 2. 배치 순서는 의존 방향을 따른다 `[코어]`

**강도:** SHOULD

정리 순서는 "피참조 수가 많은 쪽 먼저"다. 공유 상수·토큰 → 기반 유틸/헬퍼 → 원자 컴포넌트 → 복합 컴포넌트 → 조립 화면.
이유는 명명 결정이 아래에서 위로 전파되기 때문이다. 토큰 이름을 나중에 확정하면 이미 정리한 상위 파일 전부가 재작업 대상이 된다. 실제 캠페인에서 최초 배치의 토큰 리네이밍 1회가 사용처 175곳 일괄 치환으로 이어졌다 — 이 순서가 아니었다면 그 175곳이 두 번 고쳐졌다.
같은 카테고리 안에서는 첫 파일에서 패턴을 확정하고 나머지에 복제한다. 파일마다 감으로 다시 판단하면 배치 내부에서 불일치가 생긴다.

> **출처:** 프로젝트 실측 — 8단 배치(공유 상수 → 기반 → 원자 → 복합 → 조립) 완주 기록

### 3. 파일당 루프는 5단이다 `[코어]`

**강도:** MUST

한 파일의 처리는 다음 순서로만 진행한다.

```text
1. 읽기·진단  — 대상 파일을 읽고 카테고리별로 "어디를 어떻게 고칠지" 제안한다
2. 사용자 분기 — 컨펌 / 수정 지시 / 사용자 직접 편집(에이전트는 검증만) 중 택1
3. 편집       — 승인된 범위만
4. diff 보고  — 변경 요약을 능동 보고
5. 원장 체크  — 사용자가 완료 승인을 내린 뒤에만 체크 전환
```

2단을 건너뛰고 편집으로 점프하지 않는다. 사전 분석 문서에 "문제 없음" 판정이 이미 적혀 있어도 1·2단은 수행한다 — 기존 판정은 스킵 면허가 아니다.
5단의 체크 전환 주체는 사용자다. 에이전트가 스스로 체크하면 원장이 진행 상태가 아니라 에이전트의 자기평가가 된다.

> **출처:** 프로젝트 실측 — 캠페인 문서 "작업 방법" 5단 루프 및 그 위반 피드백 2건(F6, F24)

### 4. 브리핑은 산문이 아니라 표다 `[코어]`

**강도:** MUST

정리 제안은 표로 낸다. 최소 4컬럼: `[대상 | 타입 | 실제 사용값 | 판정]`.
핵심은 3번째 컬럼이다. "호출부 N건"처럼 **카운트만 적으면 사용자가 유지/제거/통일을 판단할 수 없어 되묻게 된다.** 각 호출부가 실제로 넘기는 값을 코드 그대로 인용한다.
실측 사례: 한 파라미터를 "호출부 2곳"으로만 보고했더니 사용자가 "값이 똑같을 텐데?"로 되물었고, 실제로는 두 호출부의 값이 서로 달랐다. 카운트 표기가 한 번의 왕복을 통째로 만들어 낸 것이다.
표에 추정값을 넣지 않는다. 확인하지 못한 칸은 비워 두고 "미확인"으로 표기한다 — 추정값과 확인값이 같은 서식으로 섞이면 표 전체의 신뢰도가 0이 된다.
데모·쇼케이스용 호출부는 판정 근거에 올리지 않는다. 실사용 판정은 실제 제품 코드만 기준으로 한다.

> **출처:** 프로젝트 실측 — 브리핑 포맷 보정 2회(카운트→실전달값, 데모 호출부 제외)

### 5. 원장은 진행 기록이 아니라 재개 장치다 `[코어]`

**강도:** SHOULD

원장(ledger)의 유일한 설계 목표는 "세션이 끊겨도 원장만 읽고 이어갈 수 있는가"다. 대화 컨텍스트가 남아 있다는 전제를 깔면 원장이 아니라 메모가 된다.
재개에 필요한 최소 필드는 다음과 같다.

```text
- 범위     — 대상 경로/확장자와 총 파일 수
- 기준     — 어떤 규칙 문서를 근거로 판정하는가 (파일명으로 열거)
- 순서 근거 — 배치를 왜 이 순서로 놓았는가 (1줄씩)
- 배치 목록 — 배치별 파일 체크박스, 완료 시 [x]
- 캠페인 중 추가된 규칙 — 진행 도중 확정된 추가 규칙 (몇 번 배치부터 적용인지 명시)
- 후처리   — 전 배치 완료 후에 해야 하는 전역 작업
```

진행 상태(어떤 파일이 끝났는가)는 프로젝트 소유다. 원장 **포맷**은 재사용 자산이지만 원장 **내용**은 이관 대상이 아니다.
"캠페인 중 추가된 규칙" 필드가 특히 중요하다. 장기 캠페인에서는 중간에 규칙이 늘어나며, 어느 배치부터 적용인지 적어 두지 않으면 앞 배치를 다시 열어야 하는지 판단할 수 없다.

> **출처:** 프로젝트 실측 — 캠페인 원장 279줄 / 8배치 / 56파일 운영 기록

### 6. 완료 선언 전에 규칙을 전수 대조한다 `[코어]`

**강도:** MUST

"편집했다"와 "규칙을 만족한다"는 다른 명제다. 완료를 선언하기 전에 규칙별 검색 패턴으로 잔여 위반을 직접 세고, 그 결과를 보고에 포함한다.
실측이 명확하다. 완료 전 대조를 도입하기 전에는 잔여 위반이 사용자 지적으로 발견됐고, 도입 후 배치별 잔여 위반이 **2 / 3 / 2 / 3건으로 수렴**했다. 편차가 사라진 것이 핵심이다 — 대조가 없으면 잔여량 자체를 알 수 없다.
**사용자가 첫 피드백 루프가 되면 안 된다.** 사용자가 잡아 주는 위반은 정의상 대조에서 놓친 위반이며, 이 상태가 반복되면 사용자가 캠페인의 QA 인력이 된다.
읽지 못한 규칙 소스는 "위반 0"으로 보고하지 않는다. 검사해서 없는 것과 검사하지 못한 것은 다른 결과이며, 보고에 각각 파일명으로 구분해 적는다.

> **출처:** 프로젝트 실측 — 완료 전 대조 도입 전후 배치별 잔여 위반 추이

### 7. 피드백은 복수 착지점에 동시에 남긴다 `[코어]`

**강도:** MUST

한 곳에만 기록한 규칙은 죽는다. 89개 피드백 엔트리의 착지점 분포가 그것을 그대로 보여 준다.

| 착지 유형 | 건수 | 비율 |
|---|---|---|
| 복수 착지 (2곳 이상) | 50 | 56.2% |
| 규칙 문서만 | 18 | 20.2% |
| 고아 (로그 전용 / 코드 수정만) | 11 | 12.4% |
| 메모리만 | 7 | 7.9% |
| 프로젝트 지침만 | 2 | 2.2% |
| 대상 문서만 | 1 | 1.1% |

**고아 규칙은 재발한다.** 코드 수정만으로 닫은 규칙 하나(섹션 라벨 금지)가 규칙 문서에 남지 않아 **17 엔트리 뒤에 같은 위반으로 재발**했다. 같은 사용자가 같은 지적을 두 번 한 것이다.
기본 착지 범위는 4곳으로 잡는다: 글로벌 메모리 + 메모리 인덱스 + 프로젝트 지침 + 규칙 문서. 여기에 피드백 로그를 더한다. "이건 분류상 여기만 해당"이라는 판단으로 일부만 갱신하지 마라 — 의심스러우면 전부다.

> **출처:** 프로젝트 실측 — 피드백 로그 89 엔트리 / 30 세션 (2026-04-16 ~ 2026-06-29)

### 8. 착지 강제는 사람의 의지가 아니라 도구가 한다 `[코어]`

**강도:** 관측 컨벤션

같은 실측이 파이프라인 성숙 시점을 정확히 찍는다. 고아 11건은 **전부 54번 엔트리 이전에 몰려 있고, 55번 이후 35건은 고아가 0건이다.**
전환점은 둘이다. (1) "메모리만이 아니라 프로젝트 문서에도 남겨라"는 결정(44번, 2026-04-25), (2) 피드백 기록을 자동 트리거하는 도구의 도입(62번, 2026-05-07).
즉 **파이프라인이 성숙한 시점 = 도구가 "여러 착지점 일괄 반영"을 강제하기 시작한 시점**이다. 그 이전 규칙은 한 곳에만 남거나 아예 어디에도 안 남았다. 결심이나 지침 문장만으로는 착지율이 오르지 않았다.
캠페인을 설계할 때 피드백 기록을 사람의 성실성에 맡기지 말고, "정리해 / 기록해 / 규칙으로 정해 / 다음에도 적용" 같은 표현에서 자동 트리거되는 절차로 만든다.

> **출처:** 프로젝트 실측 — 고아 엔트리 시계열 분포 (F1~F54 구간 11건 / F55~F87 구간 0건)

### 9. 범위 밖은 손대지 않는다 `[코어]`

**강도:** MUST

승인받은 범위 = 그 파일, 그 카테고리, 그 제안 표에 적힌 항목이다. 그 밖은 발견해도 보고만 하고 고치지 않는다.
특히 정적 분석 경고를 임의로 정리하지 마라. 미사용 필드·미사용 지역변수·긴 줄·도달 불가 코드는 의도적으로 남긴 코드일 수 있다. "에러 다 없애줘"는 error 심각도만 대상이며, info/warning은 명시 요청이 있을 때만 손댄다.
자동 수정 도구를 디렉토리 전체에 거는 것도 같은 위반이다. 포매터·린트 픽서는 이번 편집 대상 파일만 개별 인자로 실행한다.
정리 대상이 아닌 인접 파일까지 "일관성을 위해" 함께 고치고 싶으면, 그것은 지금 하는 일이 아니라 후속 배치로 원장에 추가할 항목이다.

> **출처:** [Google Engineering Practices — What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)

### 10. 캠페인과 배치 일괄 편집은 다른 도구다 `[코어]`

**강도:** 관측 컨벤션

"체크리스트 → 승인 → 일괄 편집" 방식과 이 문서의 캠페인은 방향이 반대다. 전자는 배치 단위로 위반을 열거하고 한 번에 닫는다. 후자는 파일 단위로 점진 진행하며 파일마다 승인을 받는다.
이 킷은 둘을 근본적으로 화해시키려 하지 않는다. 선택 기준만 둔다.

| 조건 | 적합한 방식 |
|---|---|
| 대상이 3파일 이하이고 규칙이 기계적 | 배치 일괄 편집 |
| 판정에 사용자 취향·도메인 맥락이 개입 | 캠페인 |
| 앞 파일의 결정이 뒤 파일의 기준을 바꿈 | 캠페인 |
| 위반 유형이 단일하고 검색으로 완전 열거됨 | 배치 일괄 편집 |
| 총 대상이 수십 파일이고 여러 세션에 걸침 | 캠페인 |
| 되돌리기 단위를 파일별로 유지해야 함 | 캠페인 |

경계에서 헷갈리면 "이 편집을 사용자가 파일별로 되돌리고 싶어 할까"를 물어라. 그렇다면 캠페인이다.

> **출처:** 프로젝트 실측 — 캠페인 8배치 / 56파일 운영과 일괄 감사 도구 병행 사용 기록

## 안티패턴

| 안티패턴 | 문제 |
|----------|------|
| 여러 파일 일괄 편집 | 승인 게이트가 형식만 남고, 되돌리기 단위가 파일 경계를 잃는다 |
| 제안 없이 선수정 | 사용자 분기(컨펌/수정 지시/직접 편집)가 사라져 되돌림 왕복이 생긴다 |
| 에이전트가 원장 체크 전환 | 원장이 진행 상태가 아니라 에이전트 자기평가가 된다 |
| 카운트만 적은 브리핑 표 | 사용자가 유지/제거를 판단 못 해 되묻는다. 왕복 1회가 표 서식 때문에 생긴다 |
| 표에 추정값 기재 | 확인값과 같은 서식으로 섞여 표 전체의 신뢰도를 0으로 만든다 |
| 소비자부터 착수 | 하위 명명이 나중에 바뀌면 이미 정리한 상위가 전부 재작업 대상이 된다 |
| 코드만 고치고 규칙화 생략 | 고아 규칙이 되어 재발한다 (실측: 17 엔트리 뒤 동일 위반) |
| 한 착지점만 갱신 | 다음 세션이 그 표면을 안 읽으면 규칙이 없는 것과 같다 |
| 요청 없는 경고 정리 | 의도적으로 남긴 코드를 지운다. 범위 밖 편집은 리뷰 불가 |
| 자동 수정기를 디렉토리 전체에 실행 | 이번 편집과 무관한 파일이 오염되고 diff가 읽히지 않는다 |
| 사용자 지적으로 잔여 위반 발견 | 완료 전 대조를 건너뛴 결과다. 사용자를 QA 인력으로 만든다 |
| 원장을 대화 컨텍스트로 대체 | 세션이 끊기면 재개 불가. 원장의 유일한 존재 이유가 재개다 |
| 읽지 못한 규칙 소스를 "위반 0"으로 보고 | 미검사와 무위반을 같은 결론으로 합친다 |

## Gotchas

- **"작은 배치니까 한 번에"** — 파일 수가 적어 보일수록 일괄 편집 유혹이 크지만, 캠페인 대상은 정의상 판정에 취향이 개입하는 항목이다. 3파일 이하이고 규칙이 기계적일 때만 일괄이며, 그 판정은 원칙 10의 표로 한다.
- **사전 분석의 "문제 없음"을 스킵 면허로 읽음** — 계획 문서에 "이 파일은 OK"라고 적혀 있어도 진단·브리핑은 수행한다. 실측에서 그 판정을 믿고 종결하려다 번복한 사례가 있다.
- **원장이 캠페인 후반에 뒤처짐** — 후반에는 파일당 편집량이 줄어 체크 전환을 미루기 쉽다. 미루면 다음 세션에서 어디까지 했는지 코드로 역추적하게 된다. 파일 하나가 끝날 때마다 그 자리에서 전환한다.
- **캠페인 도중 늘어난 규칙을 앞 배치에 소급 안 함** — 중간에 확정된 규칙은 "몇 번 배치부터 적용"인지 원장에 적는다. 적지 않으면 앞 배치의 재점검 필요 여부를 판단할 근거가 사라진다.
- **피드백 기록을 "나중에 몰아서"** — 몰아서 쓰면 착지점이 줄고 문맥이 날아간다. 실측의 고아 11건이 전부 자동 트리거 도입 이전 구간이다. 기록은 그 세션 안에서, 도구로 닫는다.
- **범위 밖 발견을 조용히 고침** — 인접 파일에서 같은 위반을 봤을 때 고치는 것이 친절해 보이지만, diff가 승인 범위를 벗어나면 리뷰가 성립하지 않는다. 발견은 보고하고 원장 후처리로 넘긴다.
- **완료 대조를 서술로 대체** — "규칙을 지켰다"는 문장은 대조가 아니다. 규칙별 검색 패턴을 실제로 돌리고 건수를 적는다. 서술만 있는 완료 보고는 실측에서 잔여 위반을 남겼다.
- **첫 파일의 패턴을 배치 후반에 바꿈** — 배치 내부 일관성이 깨지고, 그 배치를 참조하는 다음 배치까지 흔들린다. 패턴을 바꾸려면 그 배치를 처음부터 다시 훑는 비용을 감수하거나, 다음 배치부터 적용한다고 원장에 명시한다.
