# 코드 정리 캠페인 운영 방법론

## 이 문서가 잡는 것

- 여러 파일을 한 번에 고쳐 승인 게이트가 사후 통보로 전락하는 것
- 브리핑에 카운트만 적어 사용자가 "값이 똑같을 텐데?"라고 되묻게 만드는 것
- 규칙을 한 곳에만 남겨 몇 세션 뒤 같은 지적을 두 번 받는 것

대표 before/after — 브리핑 표 3번째 컬럼:

```text
[before] 카운트만 적음 — 사용자가 유지/제거를 판단할 수 없다
| 대상                        | 타입    | 사용처    | 판정      |
|-----------------------------|---------|-----------|-----------|
| {widget_prefix}Card.padding | double? | 호출부 2곳 | 통일 가능 |
→ 사용자: "값이 똑같을 텐데?" → 왕복 1회. 실제로는 두 값이 달랐다

[after] 각 호출부가 실제로 넘기는 값을 코드 그대로
| 대상                        | 타입    | 실제 사용값                              | 판정        |
|-----------------------------|---------|------------------------------------------|-------------|
| {widget_prefix}Card.padding | double? | 목록: {TokenClass}.md / 상세: {TokenClass}.lg | 값 상이 — 유지 |
→ 사용자가 표만 보고 그 자리에서 판정. 왕복 0회
```

수십~수백 파일을 규칙 기준으로 정리하는 장기 작업을 어떻게 굴리는가. 한 번에 한 파일, 승인 게이트, 재개 가능한 원장, 복수 착지점 피드백이 뼈대다.
이 문서의 근거는 대부분 한 프로젝트에서 2개월 반 동안 실제로 굴린 캠페인의 실측이며, 스택·언어에 의존하는 내용은 포함하지 않는다.

각 원칙은 **결론 → before/after → 왜 → 강도·출처** 순으로 적혀 있다. 맨 끝의 강도(MUST / SHOULD / 관측 컨벤션)와 축 라벨을 읽는 법은 [라벨 읽는 법](#라벨-읽는-법) 절에 한 문단으로 있다.

---

## 원칙

### 1. 한 번에 한 파일

캠페인의 편집 단위는 파일 1개다. 파일 하나를 닫기 전에 다음 파일을 열지 마라.

```text
[before] 배치를 통째로 열고 한 번에 보고
에이전트: 3배치 원자 컴포넌트 7개 정리 완료. 변경 7파일, +180 -240.
사용자:  4번째 파일의 그 변경만 되돌려줘.
에이전트: 되돌리면 5·6·7번 파일의 참조도 같이 되돌아갑니다.
→ 승인이 사후 통보가 됐고, 되돌리기 단위가 파일 경계를 잃었다

[after] 파일 하나씩 열고 닫는다
에이전트: 3배치 1/7 — <파일 A> 진단 결과입니다. (제안 표 4컬럼)
사용자:  2·3번만 반영, 1번은 유지.
에이전트: 반영 완료. diff +12 -31. 원장 체크 전환할까요?
사용자:  체크.
에이전트: 3배치 2/7 — <파일 B> 진단 결과입니다.
```

여러 파일을 모아 고치면 사용자는 diff 총량을 확인할 수 없고, 되돌릴 때 무관한 파일까지 함께 되돌아간다. "일괄 편집 금지, 제안 없이 선수정 금지"는 캠페인 문서에 처음부터 박아 두는 3대 금지 중 둘이다(나머지 하나가 원장 임의 전환 금지). 예외는 삭제 대상 파일처럼 편집이 0줄인 경우뿐이다.

**강도:** MUST · **축:** `[코어]`

> **출처:** 프로젝트 실측 — 피드백 로그 89 엔트리 / 30 세션 (2026-04-16 ~ 2026-06-29)

### 2. 배치 순서는 의존 방향을 따른다

피참조 수가 많은 쪽부터 정리한다: 공유 상수·토큰 → 기반 유틸/헬퍼 → 원자 컴포넌트 → 복합 컴포넌트 → 조립 화면.

```text
[before] 눈에 보이는 화면부터 착수
1배치 조립 화면 → 2배치 복합 → … → 8배치 공유 토큰
8배치에서 토큰 1개 리네이밍 확정
→ 이미 정리를 끝낸 사용처 175곳이 재편집 대상. 같은 줄을 두 번 고친다

[after] 피참조 많은 쪽부터
1배치 공유 상수·토큰 → 2배치 기반 유틸 → … → 8배치 조립 화면
1배치에서 같은 리네이밍 확정
→ 사용처 175곳을 한 번만 고친다. 상위 배치는 확정된 이름 위에서 시작
```

명명 결정이 아래에서 위로 전파되기 때문이다. 토큰 이름을 나중에 확정하면 이미 정리한 상위 파일 전부가 재작업 대상이 된다. 같은 카테고리 안에서는 첫 파일에서 패턴을 확정하고 나머지에 복제한다 — 파일마다 감으로 다시 판단하면 배치 내부에서 불일치가 생긴다.

**강도:** SHOULD · **축:** `[코어]`

> **출처:** 프로젝트 실측 — 8단 배치(공유 상수 → 기반 → 원자 → 복합 → 조립) 완주 기록

### 3. 파일당 루프는 5단이다

한 파일의 처리는 읽기·진단 → 사용자 분기 → 편집 → diff 보고 → 원장 체크 순서로만 진행한다.

```text
[before] 2단을 건너뛰고 편집으로 점프
1. 읽기·진단
3. 편집        ← 사용자 분기 없이 바로 수정
4. diff 보고
5. 원장 체크   ← 에이전트가 자기 판단으로 [x] 전환
→ 사용자는 "되돌려줘"로만 개입할 수 있고, 원장은 진행 상태가 아니라 자기평가가 된다

[after] 5단 전부
1. 읽기·진단  — 대상 파일을 읽고 카테고리별로 "어디를 어떻게 고칠지" 제안한다
2. 사용자 분기 — 컨펌 / 수정 지시 / 사용자 직접 편집(에이전트는 검증만) 중 택1
3. 편집       — 승인된 범위만
4. diff 보고  — 변경 요약을 능동 보고
5. 원장 체크  — 사용자가 완료 승인을 내린 뒤에만 체크 전환
```

사전 분석 문서에 "문제 없음" 판정이 이미 적혀 있어도 1·2단은 수행한다 — 기존 판정은 스킵 면허가 아니다. 5단의 체크 전환 주체는 사용자다.

**강도:** MUST · **축:** `[코어]`

> **출처:** 프로젝트 실측 — 캠페인 문서 "작업 방법" 5단 루프 및 그 위반 피드백 2건(F6, F24)

### 4. 브리핑은 산문이 아니라 표다

정리 제안은 최소 4컬럼 표로 낸다: `대상 | 타입 | 실제 사용값 | 판정`. 3번째 컬럼에 카운트가 아니라 실제로 넘어가는 값을 코드 그대로 적는다.

```text
[before] 카운트 표기 + 추정값 혼입
| 대상                          | 타입    | 사용처       | 판정      |
|-------------------------------|---------|--------------|-----------|
| {widget_prefix}Card.padding   | double? | 호출부 2곳    | 통일 가능 |
| {widget_prefix}Card.elevation | double? | 아마 기본값만 | 제거      |
→ "호출부 2곳"이 왕복을 만든다. "아마"가 확인값과 같은 서식으로 섞여 표 전체 신뢰도가 0

[after] 실전달값 + 미확인 명시 + 쇼케이스 호출부 제외
| 대상                          | 타입    | 실제 사용값                                   | 판정         |
|-------------------------------|---------|-----------------------------------------------|--------------|
| {widget_prefix}Card.padding   | double? | 목록: {TokenClass}.md / 상세: {TokenClass}.lg | 값 상이 — 유지 |
| {widget_prefix}Card.elevation | double? | 미확인 (제품 코드 호출부 못 찾음, 쇼케이스만 존재) | 판정 보류    |
```

실측 사례: 한 파라미터를 "호출부 2곳"으로만 보고했더니 사용자가 "값이 똑같을 텐데?"로 되물었고, 실제로는 두 호출부의 값이 서로 달랐다. 카운트 표기가 왕복 하나를 통째로 만들어 낸 것이다. 확인하지 못한 칸은 추정으로 채우지 말고 "미확인"으로 표기하며, 데모·쇼케이스용 호출부는 실사용 판정 근거에 올리지 않는다.

**강도:** MUST · **축:** `[코어]`

> **출처:** 프로젝트 실측 — 브리핑 포맷 보정 2회(카운트→실전달값, 데모 호출부 제외)

### 5. 원장은 진행 기록이 아니라 재개 장치다

원장(ledger)은 "세션이 끊겨도 원장만 읽고 이어갈 수 있는가" 하나만 만족하면 된다. 대화 컨텍스트가 남아 있다는 전제를 깔면 원장이 아니라 메모가 된다.

```markdown
[before] 진행 메모 — 다음 세션이 코드로 역추적해야 한다
## 정리 캠페인
- 오늘 카드 계열 3개 정리함
- 토큰 이름은 지난주에 얘기한 대로
- 남은 건 다음에 이어서

[after] 재개 가능한 원장 — 6개 필드
# 정리 캠페인 원장

범위:      <컴포넌트 루트>/**/*.<확장자> — 총 56파일
기준:      naming-rules.md · api-shape-rules.md · doc-comment-rules.md
순서 근거:  피참조 수 내림차순. 토큰 확정이 상위 명명을 결정하므로 1배치에 둔다.

## 1배치 공유 상수·토큰 (8/8)
- [x] <파일 A>
- [x] <파일 B>

## 3배치 원자 컴포넌트 (2/7)
- [x] <파일 D>
- [x] <파일 E>
- [ ] <파일 F>   ← 다음 세션 여기부터

## 캠페인 중 추가된 규칙
- 섹션 라벨 주석 금지 — 4배치부터 적용 (1~3배치는 소급하지 않음)

## 후처리
- 전 배치 완료 후 미사용 export 전역 재검색
```

진행 상태(어떤 파일이 끝났는가)는 프로젝트 소유다. 원장 **포맷**은 재사용 자산이지만 원장 **내용**은 이관 대상이 아니다. "캠페인 중 추가된 규칙" 필드가 특히 중요하다 — 어느 배치부터 적용인지 적어 두지 않으면 앞 배치를 다시 열어야 하는지 판단할 근거가 사라진다.

**강도:** SHOULD · **축:** `[코어]`

> **출처:** 프로젝트 실측 — 캠페인 원장 279줄 / 8배치 / 56파일 운영 기록

### 6. 완료 선언 전에 규칙을 전수 대조한다

완료를 선언하기 전에 규칙별 검색 패턴을 실제로 돌려 잔여 위반을 세고, 그 건수를 보고에 넣는다.

```text
[before] 서술형 완료 보고
"3배치 7파일 정리 완료. 명명 규칙·API 형태 규칙 모두 준수했습니다."
→ 이후 사용자가 잔여 위반 3건을 직접 발견. 사용자가 첫 피드백 루프가 됐다

[after] 규칙 소스별 대조 결과를 수치로
3배치 완료 전 대조 (규칙별 검색 패턴 실행)
| 규칙 소스           | 검색 패턴                | 잔여   |
|---------------------|--------------------------|--------|
| naming-rules.md     | 접두사 없는 public 심볼   | 2      |
| api-shape-rules.md  | 위치 인자 3개 초과        | 0      |
| doc-comment-rules.md| (파일 접근 실패로 미읽음) | 미검사 |
잔여 2건은 4배치 선행 항목이라 원장 후처리로 이월.
```

"편집했다"와 "규칙을 만족한다"는 다른 명제다. 완료 전 대조를 도입하기 전에는 잔여 위반이 사용자 지적으로 발견됐고, 도입 후 배치별 잔여 위반이 **2 / 3 / 2 / 3건으로 수렴**했다 — 편차가 사라진 것이 핵심이다. 읽지 못한 규칙 소스는 "위반 0"이 아니라 "미검사"로 적는다. 검사해서 없는 것과 검사하지 못한 것은 다른 결과다.

**강도:** MUST · **축:** `[코어]`

> **출처:** 프로젝트 실측 — 완료 전 대조 도입 전후 배치별 잔여 위반 추이

### 7. 피드백은 복수 착지점에 동시에 남긴다

규칙 하나를 한 곳에만 기록하지 마라. 기본 착지 범위는 4곳(글로벌 메모리 + 메모리 인덱스 + 프로젝트 지침 + 규칙 문서) + 피드백 로그다.

```text
[before] 코드만 고치고 닫음
사용자 지적 → 해당 파일의 섹션 라벨 주석 삭제 → 종료
→ 17 엔트리 뒤 다른 파일에서 같은 위반 재발. 같은 사용자가 같은 지적을 두 번 했다

[after] 5곳에 동시 착지
1. 글로벌 메모리    — "섹션 라벨 주석 금지" 항목 신규
2. 메모리 인덱스    — 위 항목을 인덱스에 등록 (안 하면 다음 세션이 못 읽는다)
3. 프로젝트 지침    — 코딩 컨벤션 절에 1줄
4. 규칙 문서        — 판정 기준표에 행 추가 + "4배치부터 적용" 명시
5. 피드백 로그      — 엔트리 번호·날짜·원문 지적 보존
```

89개 피드백 엔트리의 착지점 분포가 근거다.

| 착지 유형 | 건수 | 비율 |
| --- | --- | --- |
| 복수 착지 (2곳 이상) | 50 | 56.2% |
| 규칙 문서만 | 18 | 20.2% |
| 고아 (로그 전용 / 코드 수정만) | 11 | 12.4% |
| 메모리만 | 7 | 7.9% |
| 프로젝트 지침만 | 2 | 2.2% |
| 대상 문서만 | 1 | 1.1% |

**고아 규칙은 재발한다.** 코드 수정만으로 닫은 규칙 하나(섹션 라벨 금지)가 규칙 문서에 남지 않아 17 엔트리 뒤에 같은 위반으로 재발했다. "이건 분류상 여기만 해당"이라는 판단으로 일부만 갱신하지 마라 — 의심스러우면 전부다.

**강도:** MUST · **축:** `[코어]`

> **출처:** 프로젝트 실측 — 피드백 로그 89 엔트리 / 30 세션 (2026-04-16 ~ 2026-06-29)

### 8. 착지 강제는 사람의 의지가 아니라 도구가 한다

피드백 기록을 성실성에 맡기지 말고, 트리거 표현에서 자동으로 도는 절차로 만든다.

```text
[before] 지침 문장으로 강제 시도
프로젝트 지침: "피드백은 메모리와 규칙 문서 양쪽에 남길 것"
→ F1~F54 구간 고아 11건. 문장은 있었지만 착지율은 오르지 않았다

[after] 트리거 표현 → 도구가 전 착지점 일괄 반영
트리거: "정리해 / 기록해 / 규칙으로 정해 / 다음에도 적용"
   ↓ (자동 실행)
글로벌 메모리 + 메모리 인덱스 + 프로젝트 지침 + 규칙 문서 + 로그  = 5곳 동시 기록
→ F55~F87 구간 35건, 고아 0건
```

같은 실측이 파이프라인 성숙 시점을 정확히 찍는다. 고아 11건은 전부 54번 엔트리 이전에 몰려 있고, 55번 이후 35건은 고아가 0건이다. 전환점은 둘 — (1) "메모리만이 아니라 프로젝트 문서에도 남겨라"는 결정(44번, 2026-04-25), (2) 피드백 기록을 자동 트리거하는 도구의 도입(62번, 2026-05-07). 즉 파이프라인이 성숙한 시점은 도구가 일괄 반영을 강제하기 시작한 시점이다.

**강도:** 관측 컨벤션(공개 출처 없이 프로젝트 실측만 있는 규칙 — 준수 강도가 낮다는 뜻이 아니다) · **축:** `[코어]`

> **출처:** 프로젝트 실측 — 고아 엔트리 시계열 분포 (F1~F54 구간 11건 / F55~F87 구간 0건)

### 9. 범위 밖은 손대지 않는다

승인받은 범위는 그 파일, 그 카테고리, 그 제안 표에 적힌 항목이다. 그 밖은 발견해도 보고만 하고 고치지 않는다.

```text
[before] "온 김에" 함께 정리
승인 범위: <파일 C>의 명명 규칙 3건
실제 diff: 명명 3건 + 미사용 지역변수 삭제 2건 + 인접 파일 2개 동일 위반 수정
        + 포매터를 <컴포넌트 루트> 전체에 실행 → 무관 파일 40개가 diff에 섞임
→ 리뷰가 성립하지 않는다. 의도적으로 남긴 코드까지 지워졌다

[after] 승인 범위만 편집하고 나머지는 보고
diff: 명명 3건 (+9 -9)
범위 밖 발견 — 수정하지 않음:
  - <파일 C> 미사용 지역변수 2건 — 의도 여부 확인 필요
  - 인접 <파일 G>·<파일 H> 동일 위반 — 5배치 대상, 원장 후처리에 추가
포매터는 <파일 C> 하나만 인자로 실행
```

정적 분석 경고를 임의로 정리하지 마라. 미사용 필드·미사용 지역변수·긴 줄·도달 불가 코드는 의도적으로 남긴 코드일 수 있다. "에러 다 없애줘"는 error 심각도만 대상이며, info/warning은 명시 요청이 있을 때만 손댄다. 인접 파일까지 "일관성을 위해" 고치고 싶으면 그것은 지금 하는 일이 아니라 원장에 추가할 후속 배치 항목이다.

**강도:** MUST · **축:** `[코어]`

> **출처:** [Google Engineering Practices — What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)

### 10. 캠페인과 배치 일괄 편집은 다른 도구다

두 방식을 화해시키려 하지 말고 아래 기준표로 고른다. 헷갈리면 "사용자가 이 편집을 파일별로 되돌리고 싶어 할까"를 물어라.

```text
[before] 취향이 개입하는 56파일을 일괄 편집으로 처리
전 파일 검색 → 위반 120건 열거 → 한 번에 승인 → 일괄 치환 → 커밋 1개
→ 판정에 도메인 맥락이 필요한 항목이 섞여 승인이 통과 의례가 됐고,
   되돌리기 단위가 커밋 하나로 뭉쳐 파일별 롤백이 불가능해졌다

[after] 성격이 다른 두 묶음을 분리
- import 정렬 등 기계적 위반, 3파일  → 배치 일괄 편집 (검색으로 완전 열거됨)
- 명명·API 형태 판정, 56파일        → 캠페인 (파일당 5단 루프 + 파일별 롤백)
```

| 조건 | 적합한 방식 |
| --- | --- |
| 대상이 3파일 이하이고 규칙이 기계적 | 배치 일괄 편집 |
| 판정에 사용자 취향·도메인 맥락이 개입 | 캠페인 |
| 앞 파일의 결정이 뒤 파일의 기준을 바꿈 | 캠페인 |
| 위반 유형이 단일하고 검색으로 완전 열거됨 | 배치 일괄 편집 |
| 총 대상이 수십 파일이고 여러 세션에 걸침 | 캠페인 |
| 되돌리기 단위를 파일별로 유지해야 함 | 캠페인 |

전자는 배치 단위로 위반을 열거하고 한 번에 닫는다. 후자는 파일 단위로 점진 진행하며 파일마다 승인을 받는다. 이 킷은 둘을 근본적으로 화해시키려 하지 않고 선택 기준만 둔다.

**강도:** 관측 컨벤션 · **축:** `[코어]`

> **출처:** 프로젝트 실측 — 캠페인 8배치 / 56파일 운영과 일괄 감사 도구 병행 사용 기록

## 안티패턴

| 안티패턴 | 문제 |
| ---------- | ------ |
| 여러 파일 일괄 편집 | 승인 게이트가 형식만 남고, 되돌리기 단위가 파일 경계를 잃는다 |
| 제안 없이 선수정 | 사용자 분기(컨펌/수정 지시/직접 편집)가 사라져 되돌림 왕복이 생긴다 |
| 에이전트가 원장 체크 전환 | 원장이 진행 상태가 아니라 에이전트 자기평가가 된다 |
| 카운트만 적은 브리핑 표 | 사용자가 유지/제거를 판단 못 해 되묻는다. 왕복 1회가 표 서식 때문에 생긴다 |
| 표에 추정값 기재 | 확인값과 같은 서식으로 섞여 표 전체의 신뢰도를 0으로 만든다 |
| 소비자부터 착수 | 하위 명명이 나중에 바뀌면 이미 정리한 상위가 전부 재작업 대상이 된다 |
| 코드만 고치고 규칙화 생략 | 고아 규칙이 되어 재발한다 (실측: 17 엔트리 뒤 동일 위반) |
| 한 착지점만 갱신 | 다음 세션이 그 표면을 안 읽으면 규칙이 없는 것과 같다 |
| 요청 없는 경고 정리 | 의도적으로 남긴 코드를 지운다. 범위 밖 편집은 리뷰 불가 |
| 자동 수정기를 디렉토리 전체에 실행 | 이번 편집과 무관한 파일이 오염되고 diff가 읽히지 않는다 |
| 사용자 지적으로 잔여 위반 발견 | 완료 전 대조를 건너뛴 결과다. 사용자를 QA 인력으로 만든다 |
| 원장을 대화 컨텍스트로 대체 | 세션이 끊기면 재개 불가. 원장의 유일한 존재 이유가 재개다 |
| 읽지 못한 규칙 소스를 "위반 0"으로 보고 | 미검사와 무위반을 같은 결론으로 합친다 |

## 라벨 읽는 법

각 원칙 끝에는 강도와 축(이 킷이 규칙을 분류하는 계열 라벨 — 이 문서는 전부 `[코어]`, 즉 프로젝트·스택을 가리지 않고 그대로 적용되는 계열)이 붙는다.
강도는 셋이다. **MUST**는 어기면 캠페인 자체가 성립하지 않는 규칙, **SHOULD**는 상황에 따라 조정 가능하지만 이탈 시 비용을 감수해야 하는 규칙, **관측 컨벤션**은 공개 출처 없이 프로젝트 실측만 근거로 가진 규칙이다. 관측 컨벤션이 가장 약한 등급이라는 뜻이 아니라, 근거의 출처가 외부 문헌이 아니라는 표시다.

## Gotchas

- **"작은 배치니까 한 번에"** — 파일 수가 적어 보일수록 일괄 편집 유혹이 크지만, 캠페인 대상은 정의상 판정에 취향이 개입하는 항목이다. 3파일 이하이고 규칙이 기계적일 때만 일괄이며, 그 판정은 원칙 10의 표로 한다.
- **사전 분석의 "문제 없음"을 스킵 면허로 읽음** — 계획 문서에 "이 파일은 OK"라고 적혀 있어도 진단·브리핑은 수행한다. 실측에서 그 판정을 믿고 종결하려다 번복한 사례가 있다.
- **원장이 캠페인 후반에 뒤처짐** — 후반에는 파일당 편집량이 줄어 체크 전환을 미루기 쉽다. 미루면 다음 세션에서 어디까지 했는지 코드로 역추적하게 된다. 파일 하나가 끝날 때마다 그 자리에서 전환한다.
- **캠페인 도중 늘어난 규칙을 앞 배치에 소급 안 함** — 중간에 확정된 규칙은 "몇 번 배치부터 적용"인지 원장에 적는다. 적지 않으면 앞 배치의 재점검 필요 여부를 판단할 근거가 사라진다.
- **피드백 기록을 "나중에 몰아서"** — 몰아서 쓰면 착지점이 줄고 문맥이 날아간다. 실측의 고아 11건이 전부 자동 트리거 도입 이전 구간이다. 기록은 그 세션 안에서, 도구로 닫는다.
- **범위 밖 발견을 조용히 고침** — 인접 파일에서 같은 위반을 봤을 때 고치는 것이 친절해 보이지만, diff가 승인 범위를 벗어나면 리뷰가 성립하지 않는다. 발견은 보고하고 원장 후처리로 넘긴다.
- **완료 대조를 서술로 대체** — "규칙을 지켰다"는 문장은 대조가 아니다. 규칙별 검색 패턴을 실제로 돌리고 건수를 적는다. 서술만 있는 완료 보고는 실측에서 잔여 위반을 남겼다.
- **첫 파일의 패턴을 배치 후반에 바꿈** — 배치 내부 일관성이 깨지고, 그 배치를 참조하는 다음 배치까지 흔들린다. 패턴을 바꾸려면 그 배치를 처음부터 다시 훑는 비용을 감수하거나, 다음 배치부터 적용한다고 원장에 명시한다.
