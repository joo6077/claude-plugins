# 한국어 기술 문서·주석 문체

한국어로 쓰는 주석·doc 의 문체 규칙을 정의한다. 번역투 제거, 종결형, 외래어 처리, 용어 번역표 작성이 대상이다. **이 문서가 "한국어 의존" 축의 SSOT 다** — 다른 문서는 한국어 규칙을 다시 정의하지 말고 여기를 가리킨다.

---

## 원칙

### 1. 한국어 축은 스택 축과 직교한다 `[코어][한국어]`

**강도: MUST** (킷 구조 결정)

규칙의 의존성은 두 축으로 나뉜다. **스택 축**(Dart/Flutter · Rust · TypeScript)과 **언어 축**(한국어 · 영어)이다. 두 축은 서로를 결정하지 않는다.

dart doc 의 `- 반환값:` 라벨이 대표 사례다. 이 라벨은 Dart 의존이 아니라 한국어 의존이다. 같은 규칙을 영어 프로젝트로 옮기면 표기만 바뀌고 구조는 그대로 남는다.

```text
한국어 프로젝트: /// - 반환값: 연결되어 있으면 true
영어 프로젝트:   /// - Returns: true when connected
```

바뀐 것은 라벨 문자열 하나뿐이다. "파라미터와 반환값을 doc 하단에 라벨 블록으로 붙인다"는 골격, "void 는 한 가지 표기로 통일한다"는 제약, 커버리지 기준은 언어와 무관하게 남는다. 반대로 스택을 Dart 에서 Rust 로 바꾸면 주석 문법과 링크 문법(`[param]` → `` `param` ``)은 바뀌지만 한국어 문체 규칙은 한 줄도 안 바뀐다. 따라서 어댑터 문서(`dart-flutter` 등)는 **라벨 상수와 주석 문법만** 정의하고, 문체는 이 문서를 참조한다.

> **출처:** [국립국어원 공공언어 자료](https://korean.go.kr/front/etcData/etcDataView.do?etc_seq=663) · 원본 프로젝트 전수 감사 (2026-08-28, 규칙 625줄 / 39 섹션)

### 2. 번역투 킬러 패턴 6종을 제거한다 `[한국어]`

**강도: SHOULD** (국립국어원·번역투 연구 근거, 프로젝트가 MUST 로 승격 가능)

아래 6개 패턴이 한국어 주석에서 AI 톤을 가장 강하게 만든다. 각각 원인이 되는 영어 구문이 있고, 대체형이 정해져 있다.

| 패턴 | 문제 | 대체형 |
|---|---|---|
| `~을 처리합니다` / `~을 관리합니다` | 동사가 비어 있어 메서드명을 한국어로 되풀이하는 데 그친다 | 실제 동작 동사: `길게 누르기 반복을 시작한다` |
| `~에 대해서` / `~에 대해` | `about` / `for` 직역. 목적격 조사면 충분하다 | `서버 이름을 보여 준다` |
| `~하도록 합니다` | 사역 구문 직역. 주체가 사라진다 | 단정형 `~한다`: `키보드 입력을 이어 간다` |
| `~에 의해` | `by` 직역 수동태 | 주어를 되살린 능동형: `surface tint 가 배경색을 덮는다` |
| `~되어 있는 경우` | `if ... is set` 직역. 조건 서술이 두 배로 길어진다 | `값이 없으면 …` |
| 과한 수동태 (`표시됩니다` · `적용됩니다`) | 행위 주체가 사라져 원인을 추적할 수 없다 | 주체 + 능동: `이 위젯이 …를 그린다` |

종결어미만 `한다`체로 바꾸고 `~에 의해` 를 남기면 번역투는 그대로다. 6종은 종결형 규칙과 별개로 각각 잡는다.

> **출처:** [국립국어원 공공언어 자료](https://korean.go.kr/front/etcData/etcDataView.do?etc_seq=663) · [한국어 번역투 연구 (KCI)](https://www.kci.go.kr/kciportal/landing/article.kci?arti_id=ART002178732)

### 3. 능동형·주체 직설·원인 결과 구체성으로 대체한다 `[한국어]`

**강도: SHOULD**

패턴을 지우는 것만으로는 문장이 완성되지 않는다. 대체 원칙 세 가지를 같이 적용한다. 능동형으로 쓰고, 주체와 결과를 직설로 밝히고, 원인과 결과를 구체적으로 연결한다.

```text
Bad  : /// 눌림 시작을 처리합니다.
Good : // 길게 누르기 반복을 시작한다.

Bad  : // 서버 이름에 대해 표시합니다.
Good : // 선택된 서버 이름을 그대로 보여 준다.

Bad  : // 배경색이 오버레이에 의해 변경됩니다.
Good : // Material 3 surface tint 가 배경색을 덮어 실제 색이 더 밝아 보인다.

Bad  : // 포커스를 잃지 않도록 합니다.
Good : // 드롭다운을 닫은 뒤에도 키보드 입력을 이어 가야 한다.

Bad  : // 값이 설정되어 있는 경우에만 표시되도록 합니다.
Good : // 값이 없으면 빈 영역을 만들지 않는다.
```

세 번째 Bad 줄은 번역투(`~에 의해`)와 음역(`오버레이`)이 함께 걸린 사례다. 한 문장이 두 규칙을 동시에 어기는 일이 흔하므로 고칠 때 둘 다 본다. 문장 수사보다 정보 설계가 먼저이고, 주석의 값어치는 `what` 이 아니라 `why` 에서 나온다.

> **출처:** [LINE 테크니컬 라이팅](https://engineering.linecorp.com/ko/blog/why-are-engineers-so-bad-at-writing/) · [Google Engineering Practices](https://google.github.io/eng-practices/review/reviewer/looking-for.html)

### 4. 종결형은 `한다`체 하나로 고정한다 `[코어][한국어]`

**강도: 관측 컨벤션** (실측 근거만 존재)

doc 본문 동사는 `한다`체로 고정한다. `만든다` · `수집한다` · `건너뛴다` · `검증한다` · `조립한다` 처럼 쓰고 `합니다`체와 명사형 종결을 섞지 않는다. 한 코드베이스에 두 종결형이 공존하면 grep 기준이 무너지고, 파일마다 톤이 달라진다.

인라인 `//` 주석은 예외다. 파편형·단문을 허용하고, 코드만 읽어도 뜻이 통하면 아예 지운다. 즉 종결형 고정은 **문장을 쓰기로 한 자리**에만 적용된다.

이 규칙에는 공개 1차 근거가 없다. 근거는 실측이다. 동일 모노레포의 공용 패키지 한 곳에서 `반환합니다` 종결 doc 이 125건 나왔고, 번역투 doc 주석 전체는 129건이었다. 종결형을 고정하지 않으면 이런 덩어리가 조용히 쌓인다.

> **출처:** 프로젝트 실측 — 공용 패키지 번역투 doc 129건(`반환합니다` 125건), 2026-08-28 전수 감사. 공개 문헌 근거 없음

### 5. 외래어는 3원칙으로 가른다 `[한국어]`

**강도: SHOULD**

1. **공식 API 이름은 영어 원문.** `surface tint`, `BoxDecoration`, `strokeAlign` 을 번역하지 않는다. 문서·검색·자동완성이 전부 원문 기준으로 움직인다.
2. **일반 명사는 한국어.** 배경색, 그림자, 테두리. 원문을 남길 이유가 없으면 한국어가 기본값이다.
3. **음역 금지.** `보더 라디우스` 는 쓰지 않는다. 한국어도 영어도 아니라 검색이 안 되고 공식 API 이름과도 어긋난다.

경계에 정착 외래어가 있다. `다운로드` · `업로드` · `파싱` · `파일` · `폴더` 는 이미 한국어 어휘로 굳었으므로 허용한다. 반대로 `잡`(job) 은 `작업`으로, `큐`(queue) 는 `대기열`로 쓴다. 정착 여부는 팀이 판정하고 결과를 용어 번역표에 적는다(원칙 8).

**코드 식별자는 이 규칙의 대상이 아니다.** 타입·함수·변수·메서드 이름은 영어를 그대로 둔다. 번역하면 doc 링크가 끊긴다. 음역 금지는 한국어 본문만 겨냥한다.

> **출처:** [Effective Dart documentation](https://dart.dev/effective-dart/documentation) · [국립국어원 공공언어 자료](https://korean.go.kr/front/etcData/etcDataView.do?etc_seq=663)

### 6. 이름 번역 주석은 한국어 프로젝트 고유의 최대 덩어리다 `[코어][한국어]`

**강도: SHOULD**

식별자가 영어이고 주석이 한국어라서, 번역 주석이 정보를 더하는 것처럼 보인다. 실제로는 같은 내용의 반복이다.

```dart
String? text,        // 버튼 텍스트   ← text 가 이미 '텍스트'
bool isChecked,      // 체크 여부     ← isChecked 가 이미 '체크 여부'
double min,          // 최소값        ← min 이 이미 '최소값'
```

원본 코드베이스 진단에서 이 유형이 48개 파일에 약 85건으로 단일 최대 카테고리였고, 전체 안티패턴 약 275건의 30% 를 차지했다. 영어 단일 언어 프로젝트라면 `// button text` 는 누구도 안 쓴다. 번역이라는 명분이 붙어야 생기는 유형이므로 한국어 축에 속한다.

처리 기준은 삭제다. 다만 이름이 약해서 주석이 필요했다면 주석 대신 이름을 고친다. 남길 것은 이름·타입에서 안 읽히는 계약뿐이다. 값의 우선순위, 무효화 조건, 허용 범위가 그것이다.

> **출처:** [Effective Dart documentation](https://dart.dev/effective-dart/documentation) (`AVOID redundancy with the surrounding context`) · [Microsoft Code with Engineering Playbook](https://microsoft.github.io/code-with-engineering-playbook/documentation/guidance/code/)

### 7. doc 라벨은 언어 의존 상수다 — 표기를 쪼개지 마라 `[어댑터:dart-flutter][한국어]`

**강도: 관측 컨벤션**

파라미터·반환값 블록의 라벨은 자유 서술이 아니라 상수다. 한국어 프로젝트에서는 `- [param]: 설명` 과 `- 반환값: 설명` 두 형태로 고정한다. void 반환은 `- 반환값: 없음` 으로 쓰고 `N/A` 를 새로 도입하지 않는다.

```dart
/// 네트워크 연결 상태를 확인하고, 끊긴 경우 안내 다이얼로그를 띄운다.
///
/// - [context]: 다이얼로그 표시용 빌드 컨텍스트
/// - [ref]: 네트워크 모니터 상태 조회용 ref
/// - 반환값: 연결되어 있으면 true, 끊겨 있으면 false
```

상수로 다루는 이유는 검색성이다. 원본 코드베이스에서 `- 반환값:` 은 80개 파일에 577건, `- [param]:` 은 788건 나왔다. 이 규모에서 표기가 둘로 갈리면 커버리지 측정과 일괄 치환이 모두 깨진다. `- 반환값: 없음` 을 노이즈로 보고 지우는 것도 금지다 — 있고 없음이 섞이면 "doc 이 없는 것"과 "반환값이 없는 것"을 구분할 수 없다.

본문은 한두 문장으로 끝낸다. `정책:` · `참고:` · `주의:` 같은 본문 내 섹션 헤더와 알고리즘 단계 나열은 doc 이 아니라 설계 문서의 몫이다.

> **출처:** [Effective Dart documentation](https://dart.dev/effective-dart/documentation) · 프로젝트 실측 — `- 반환값:` 577건 / 80파일, `- [param]:` 788건 (2026-08-28)

### 8. 용어 번역표는 프로젝트가 소유한다 `[코어][한국어]`

**강도: 관측 컨벤션**

원칙 5 의 3원칙만으로는 매번 판정이 갈린다. 판정 결과를 누적하는 표가 프로젝트마다 하나 있어야 하고, 그 표는 **킷이 아니라 프로젝트 저장소에 둔다.** 도메인 어휘와 정착 외래어 판정은 프로젝트마다 다르고, 공용 문서로 올리면 다른 프로젝트에 잘못된 번역을 강제한다.

표 작성 규칙은 다음과 같다.

- **3열 고정** — 용어(영어 원문) / 주석에서 쓸 표기 / 비고(판정 근거). 비고에는 `Material 3 API`, `일반 명사`, `음역 금지` 처럼 원칙 5 의 어느 갈래인지 적는다.
- **판정이 갈렸던 것만 올린다.** 원칙 5 로 자명하게 갈리는 단어를 전부 나열하면 표가 규칙을 대체해 버린다. 초기 규모는 6행 안팎이면 충분하다.
- **새 케이스가 생길 때 한 행씩 늘린다.** 표를 미리 채우지 않는다.
- **기준 코드베이스를 명시한다.** 애매하면 어느 디렉토리의 네이밍을 따를지 표 하단에 적는다. AI 톤 오염이 진행된 영역은 기준으로 삼지 않는다 — 오염된 표기가 표를 통해 정식 규칙으로 승격된다.
- **표 내용은 이관 대상이 아니다.** 킷이 옮기는 것은 "표를 어떻게 만들고 유지하는가"이고, 행 자체는 각 프로젝트가 자기 도메인으로 채운다.

| `보더 라디우스` 같은 음역 | 한국어도 영어도 아니라 검색이 안 되고 공식 API 이름과도 어긋난다 |
| 코드 식별자를 한국어로 번역 | doc 링크가 끊기고 코드와 문서가 어긋난다. 음역 금지는 본문에만 적용된다 |
| 이름 번역 주석 (`String? text, // 버튼 텍스트`) | 타입과 이름이 이미 담은 의미의 반복. 이름이 약하면 이름을 고칠 자리다 |
| void doc 에 `N/A` 표기 도입 | 언어 의존 상수를 프로젝트 안에서 두 표기로 쪼갠다. 커버리지 측정과 일괄 치환이 깨진다 |
| `- 반환값: 없음` 을 노이즈로 보고 삭제 | "doc 이 없는 것"과 "반환값이 없는 것"을 구분할 수 없게 된다 |
| 용어 번역표를 공용 킷 문서로 승격 | 도메인 어휘는 프로젝트 소유다. 공용화하면 다른 프로젝트에 잘못된 번역을 강제한다 |
| 한국어 규칙을 스택 어댑터 문서에 다시 정의 | SSOT 가 무너져 개정 때 한쪽만 갱신된다. 어댑터는 라벨 상수와 주석 문법만 갖는다 |

## Gotchas

- **번역투는 종결어미 문제가 아니라 문장 구조 문제다** — `합니다` 를 `한다` 로 바꾸는 치환은 30초면 끝나고, 그래서 그것만 하고 완료로 보고하게 된다. 킬러 패턴 6종은 종결형과 독립이므로 치환 후에 6종을 따로 grep 한다.
- **라벨을 "더 자연스럽게" 다듬으면 grep 이 깨진다** — `- 반환값:` 을 `- 리턴:` 이나 `- 결과:` 로 바꾸고 싶어지는 순간이 온다. 이것은 상수다. 표기를 바꾸려면 전수 치환을 같이 하고, 부분 변경은 금지다.
- **정착 외래어와 음역의 경계는 팀이 한 번 정하고 끝낸다** — `파싱` 은 허용이고 `보더 라디우스` 는 금지라는 판정에 일반 규칙은 없다. 매번 재논쟁하지 말고 판정을 용어 번역표에 적어 다음 세션이 그것을 읽게 한다.
- **규칙 문서 자신이 번역투를 쓴다** — 규칙을 설명하는 문장에서 `~하도록 합니다` 와 `~에 대해` 가 특히 잘 나온다. 문서를 다 쓴 뒤 자기 본문에 6종을 grep 하는 자기모순 검사를 한 번 돌린다.
- **다른 스택 어댑터가 생길 때 이 문서를 복사하지 마라** — Rust 나 TypeScript 어댑터가 필요해지면 라벨 상수와 주석 문법만 그쪽에 정의하고 문체는 이 문서를 참조한다. 복사하는 순간 두 벌이 갈라지고, 갈라진 사실을 아무도 모른다.
- **AI 톤이 낀 영역을 번역 기준으로 삼으면 오염이 승격된다** — "기존 코드가 이렇게 쓰니까" 로 표기를 정하면, 정리 대상이던 표기가 표를 통해 정식 규칙이 된다. 기준 디렉토리는 정리 이력이 없는 쪽으로 명시한다.
