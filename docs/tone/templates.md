# 템플릿 카탈로그

골격이 이미 있는데 매번 새로 지어내는 것을 잡는다. 파일 헤더·doc 주석·typedef·원장·브리핑 표는 형식이 확정돼 있고, 형식이 흔들리면 diff 노이즈와 재개 불능이 따라온다.
6종의 골격 전문을 그대로 싣는다 — 복붙해서 `{...}` 자리만 채우면 된다. 각 템플릿에 실제로 났던 사고를 붙였다. 그 사고가 그 템플릿이 존재하는 이유다.

```dart
// before — 옆 파일에서 헤더를 복사했다. 작성자가 남의 이름이다
/// - 작성자  : 김이전
// after — git config user.name 을 읽어 채운다
/// - 작성자  : 박현재
```

강도 라벨(`MUST` · `SHOULD` · `관측 컨벤션` · `합성`)의 뜻은 맨 아래 [강도 표기](#강도-표기)에 있다.

## 이 킷에 없는 골격

컴포넌트 골격과 상태 컨테이너 골격은 이 킷이 소유하지 않는다. 스택 킷이 소유한다 — 위젯(typedef + freezed Props + Hook 3요소)은 flutter-toolkit `templates/widget-freezed-props.md`, provider / state 는 flutter-toolkit `templates/provider-riverpod.md`.
이 킷은 그 골격 **위에** 헤더·doc·typedef 를 얹는다. 스택이 바뀌면 컴포넌트 골격은 통째로 갈리지만 아래 6종은 어댑터 슬롯(스택별 문법을 갈아 끼우는 자리 — 골격은 그대로 두고 주석 문법과 라벨만 바뀐다)만 교체하면 그대로 산다.

## 1. 파일 헤더

수기로 새 파일을 만들 때마다 붙인다. 코드 생성기 산출물에는 붙이지 않는다.

```dart
/// ----------------------------------------------------------------------------
/// - {label_file}  : {파일명}
/// - {label_desc}   : {한 줄 설명}
/// - {label_author}  : {현재 git user.name}
/// - {label_screen} : {화면 식별자 또는 없음 표기}
/// - {label_ref}    : {참고 URL 또는 없음 표기}
/// - {label_history} :
///   - {YYYY-MM-DD} : {최초 생성}
/// ----------------------------------------------------------------------------
```
```dart
// before — 파일명을 한국어로 옮기기만 했다. 정보량 0
/// - 설명   : 유저 프로필 카드
// after — 이 파일이 무엇을 책임지는지가 남는다
/// - 설명   : 프로필 요약 카드. 편집 진입점과 상태 배지를 함께 노출
```

| 자리 | 필수 | 채우는 값 |
|---|---|---|
| `{label_*}` | 필수 | 라벨 문자열. 언어 의존 상수이며 `locale-korean.md` 가 소유한다 |
| `{파일명}` | 필수 | 실제 파일명. 리네임하면 같이 고친다 |
| `{한 줄 설명}` | 필수 | 책임 한 줄. 파일명 한국어 번역 금지 |
| `{현재 git user.name}` | 필수 | `git config user.name` 을 읽어 채운다 |
| `{화면 식별자}` · `{참고 URL}` | 선택 | 식별자 상수가 코드에 있으면 생략. 참고는 없으면 필드를 지운다 |
| `{YYYY-MM-DD}` | 필수 | 날짜 + 변경 요지. 여러 명이 만졌으면 항목마다 작성자 병기 |

**실측** — 수기 작성 파일 290개 중 287개(99%). 재사용 빈도 1위. 구분선은 위아래 모두 234건 · 아래만 · 없음 3건 세 변종이 공존한다.
**왜** — 헤더가 잡는 것은 "누가 왜 만들었나" 하나다. 이 정보는 코드에서 복원되지 않고 blame 은 포맷 커밋에 오염된다. 반대로 코드에서 복원되는 것(클래스 목록, 구현 요지)을 넣으면 그 순간부터 썩는다.
**주의** — 작성자를 옛 파일에서 복사하는 사고가 실제로 났다. 스캐폴딩할 때 `git config user.name` 을 읽어라. 구분선 변종이 한 프로젝트에 섞이면 그 자체가 일관성 결함이니 하나를 고르고 길이까지 고정한다.
**강도·출처** — 자화자찬 헤더("AI 기반", "자동 생성") 금지는 `core-comment.md` C-13 `MUST`. 고정 필드만 담고 구현 메모를 섞지 않는 규칙은 C-14 `관측 컨벤션`(공개 출처 없이 프로젝트 실측만 있는 규칙 — 준수 강도가 낮다는 뜻이 아니다). 라벨 부분 변경 금지는 `locale-korean.md` K-07 `관측 컨벤션`.

## 2. doc 주석 3변종 (Dart/Flutter)

로직·부수효과가 있는 메서드와 공개 API 계약에 단다. `build()` 와 한 줄 위임 wrapper 에는 달지 않는다.

```dart
/// {한 줄 요약. 무엇을 하는가.}
///
/// {선택: 언제 쓰는가 / 부수효과 / 제약. 없으면 이 블록 생략.}
///
/// - [{param}]: {설명}
/// - {label_return}: {반환 조건과 의미}
Future<bool> {methodName}({Type} {param}) async {

/// {한 줄 요약}
///
/// - [{param}]: {설명}
/// - {label_return}: {label_void}
void {methodName}({Type} {param}) {

/// {한 줄 요약}
///
/// - {label_return}: {label_void}
void {methodName}() {
```
```dart
// before — 메서드 이름을 한국어로 옮겼고, 반환값 자리에 미기재 표기가 남았다
/// 연결 상태를 확인한다.
/// - [timeout]: 타임아웃
/// - 반환값: N/A

// after — 요약은 언제·왜, 반환값은 조건과 의미
/// 재연결 판단에 쓰는 헬스체크. 실패해도 예외를 던지지 않는다.
///
/// - [timeout]: 이 시간을 넘기면 실패로 간주
/// - 반환값: 응답이 정상이면 true
```

| 자리 | 채우는 값 |
|---|---|
| `{한 줄 요약}` | 무엇을 하는가. 이름 번역이면 지운다 |
| `{선택 설명 블록}` | 언제 쓰는가 / 부수효과 / 제약. 없으면 통째로 생략 |
| `{param}` | 실제 선언 식별자. 철자가 틀려도 컴파일은 통과한다 |
| `{label_return}` · `{label_void}` | 반환값 라벨과 void 표기. 언어 의존 상수이며 프로젝트 전체가 한 표기로 통일 |

줄 순서 고정 — 요약 → 빈 `///` → 선택 설명 → `- [param]:` 목록(선언 순서) → `- {label_return}:` 은 **항상 마지막**. 완료 전 대조는 네 항목 모두 0이어야 한다.

```text
1. `{label_return}: N/A` 잔존
2. 로직 메서드에 `///` 누락
3. `- [param]:` 만 있고 `- {label_return}:` 없음
4. doc 본문 안 섹션 헤딩 (`/// 정책:`, `/// 참고:`, `/// 주의:`)
```

**실측** — 반환값 줄 577건 · 파라미터 줄 788건. void 메서드에 반환값 줄을 남긴 형태가 246건.
**왜** — doc 은 호출자가 읽는 계약이다. 시그니처가 이미 말하는 것을 되풀이하면 계약 정보는 0인데 유지보수 대상만 는다. 라벨을 하단 블록에 고정하는 이유는 grep 게이트가 성립하려면 표기가 하나여야 하기 때문이다.
**주의** — `{label_return}` 표기를 바꾸려면 전수 치환한다. 부분 변경하면 대조 grep 이 조용히 통과한다. void 에 반환값 줄을 남기는 것은 노이즈가 아니라 이 코퍼스의 관례(246건)이며, 반대로 정한 프로젝트도 유효하되 전수 일관해야 한다.
**강도·출처** — 공개 API 는 doc 으로 계약을 쓴다가 `core-comment.md` C-06 `MUST`. 로컬 구현 세부를 doc 으로 감싸지 않는다가 C-17 `관측 컨벤션`. 라벨 부분 변경 금지는 `locale-korean.md` K-07 `관측 컨벤션`.

## 3. 시맨틱 typedef (Dart/Flutter)

Props 필드 타입에 함수 시그니처를 직접 쓰려는 순간, 그 자리가 typedef 를 만들 자리다.

```dart
typedef {widget_prefix}{Meaning}{Event} = void Function({T} value);
typedef {widget_prefix}{Meaning}{Event} = void Function();
typedef {widget_prefix}{Meaning}Of<T> = String Function(T item);
```
```dart
// before — 시그니처를 이름으로 옮기기만 했다. 무엇이 바뀌었는지가 없다
typedef BoolCallback = void Function(bool value);
typedef VoidCb = void Function();

// after — 이름에 의미와 이벤트가 있다
typedef {widget_prefix}SwitchChanged = void Function(bool value);
typedef {widget_prefix}SelectChanged<T> = void Function(T value);
```

| 자리 | 채우는 값 |
|---|---|
| `{widget_prefix}` | 프로젝트 컨벤션의 위젯 접두사. 킷이 정하지 않는다 |
| `{Meaning}` | 무엇에 대한 콜백인가 (도메인 용어) |
| `{Event}` | 무슨 일이 일어났는가 — `Changed` · `Tap` · `Blur` · `Submit` |
| `{T}` | 호출부마다 타입이 다를 때만 제네릭 |

**소유권** — typedef 는 **그 의미가 생겨난 위젯의 파일** 에 둔다. 공유 typedef 파일을 만들면 어느 위젯의 계약인지 추적이 끊긴다. 시그니처가 같아도 의미가 다르면 다른 typedef 이고, 의미 원천이 옮겨가면 typedef 도 같이 옮긴다.
**실측** — 51 선언 / 32 파일. 전체 90 선언 중 26건은 FFI 바인딩이며 이 규칙의 대상이 아니다.
**왜** — 콜백 prop 은 위젯 계약의 절반이다. 타입 자리에 `void Function(bool)` 이 있으면 호출부는 그 bool 이 무엇인지 알려고 위젯 구현을 열어야 한다. 이름값은 한 줄이고 회수는 호출부 전부에서 일어난다.
**주의** — typedef 를 만들고 Props 필드 타입만 바꾼 채 호출부를 안 고치면 반쪽이 된다. FFI 시그니처는 이 규칙으로 개명하지 마라 — 별도 관례를 따른다.
**강도·출처** — 조립 형식의 prefix / suffix 는 킷이 아니라 프로젝트가 소유한다가 `core-naming.md` N-11 `관측 컨벤션`. 외형이 아니라 역할을 이름에 담는다가 N-01 `SHOULD`. 레이아웃 모양어 제한(N-02~N-06)은 `합성`(여러 디자인 시스템 어휘를 대조해 만든 규칙 — 단일 권위 출처가 없다).

## 4. 프로젝트 파라미터 오버레이

프로젝트에 이 킷을 처음 붙일 때 한 번 만든다. 위치는 프로젝트의 `.claude/tone-project.md`.

```text
# tone-kit 프로젝트 파라미터
- 감지 일시: {YYYY-MM-DD}
- 어댑터: {dart-flutter | 없음}
- 주석 언어: {ko | en | ...}
## 결정론적 감지값
| 키 | 값 | 감지 근거 |
|---|---|---|
| `scope_paths` | {디렉토리 목록} | {디렉토리 존재} |
| `token_class_names` | {클래스 목록} | {선언 위치} |
| `state_lib` | {라이브러리} | {의존성 파일} |
| `test_dir` | {경로} | {디렉토리 존재} |
| `shared_component_dir` | {경로} | {디렉토리 존재} |
| `i18n_keys_class` | {클래스} | {생성 파일} |
## 확인이 필요한 값 (관례 선언)
| 키 | 감지 후보 | 확정값 | 확인 |
|---|---|---|---|
| `widget_prefix` | {후보} | {확정} | {YYYY-MM-DD} |
| `widget_suffix` | {후보} | {확정} | {YYYY-MM-DD} |
| `props_suffix` | {후보} | {확정} | {YYYY-MM-DD} |
| `screen_split_path` | {후보} | {확정} | {YYYY-MM-DD} |
| `file_header_fields` | {후보} | {확정} | {YYYY-MM-DD} |
| `divider_style` | {후보} | {확정} | {YYYY-MM-DD} |
## 명령
| 키 | 값 | 출처 |
|---|---|---|
| `codegen_cmd` | {명령} | {감지 위치} |
| `analyze_cmd` | {명령} | {감지 위치} |
## 용어 번역표
| 용어 | 주석 표기 | 비고 |
|---|---|---|
| {원어} | {표기} | {근거} |
## 프로젝트 확정 판정
| 사안 | 판정 | 날짜 |
|---|---|---|

```
```text
before — 확인 날짜가 비었다. 접두사가 바뀐 뒤에도 이 파일은 옛 값을 계속 주장한다
| `widget_prefix` | Btn / Ui | Ui |  |
after — 언제 확정한 값인지가 남는다
| `widget_prefix` | Btn / Ui | Ui | 2026-09-02 |
```

| 표 | 채우는 값 |
|---|---|
| 결정론적 감지값 | 코드에서 다시 읽으면 복원된다. 값 + 감지 근거 |
| 확인이 필요한 값 | 사람이 확정해야 하는 관례 6종. **확인 날짜가 필수다** |
| 명령 | 프로젝트 설정에 이미 있으면 그것을 읽는다. 중복 스키마를 만들지 않는다 |
| 용어 번역표 | 기준 디렉토리는 정리 이력이 없는 쪽으로 고른다 |
| 프로젝트 확정 판정 | 규칙끼리 충돌했을 때 무엇을 골랐는지와 날짜 |

**실측** — 프로젝트당 1개. 여기 담기는 6개 확인 키가 킷이 값을 정하지 않고 프로젝트에 위임하는 전부다.
**왜** — 킷이 접두사나 헤더 필드 집합을 고정하면 프로젝트마다 킷을 포크하게 된다. 값과 판정만 이 파일에 두고 규칙 본문은 `references/` 에 남기면 킷을 업데이트해도 프로젝트 결정이 덮이지 않는다.
**주의** — 결정론적 감지값은 낡아도 코드에서 복구되지만 **확인이 필요한 값은 낡으면 조용히 틀린다.** 확인 날짜를 빠뜨리지 마라. 용어 번역표 기준을 정리 대상이던 영역에서 뽑으면 오염이 규칙으로 승격된다.
**강도·출처** — 조립 형식 소유권은 `core-naming.md` N-11 `관측 컨벤션`. 용어 번역표는 프로젝트 저장소가 소유하며 킷으로 승격하지 않는다가 `locale-korean.md` K-08 `관측 컨벤션`. 감지 규칙 자체는 `project-detection.md` 가 소유한다.

## 5. 캠페인 원장

파일 수십~수백 개를 규칙 기준으로 정리하는 장기 작업을 시작할 때 만든다. 원장 파일은 프로젝트가 소유하고 킷은 형식만 준다.

```text
# {캠페인 이름}
- 범위: {디렉토리 / 파일 패턴}
- 기준 커밋: {시작 시점 커밋}
- 적용 규칙: {references 목록 + 버전}
- 시작: {YYYY-MM-DD}
## 배치
### S1 — {토큰 · 스타일}  ({n}개)
- [ ] S1-1 {경로}
- [ ] S1-2 {경로}
### S2 — {원자 컴포넌트}  ({n}개)
- [ ] S2-1 {경로}
### S3 — {복합 컴포넌트}  ({n}개)
- [ ] S3-1 {경로}
### S4 — {화면 · 라우트}  ({n}개)
- [ ] S4-1 {경로}
## 규칙 추가 이력
| 날짜 | 규칙 | 적용 시작 배치 | 앞 배치 소급 |
|---|---|---|---|
| {YYYY-MM-DD} | {규칙 요지} | S{n} | 필요 / 불필요 |
## 범위 밖 발견
| 파일 | 발견 | 처리 |
|---|---|---|
| {경로} | {위반 요지} | 후처리 대상 |
## 후처리
```

| 자리 | 채우는 값 |

| 규칙 추가 이력 | 캠페인 도중 확정된 규칙의 적용 시작 배치와 소급 여부 |

**실측** — 279줄 / 8배치 / 56파일 운영 기록. 파일당 루프는 5단(제안 → 분기 → 편집 → diff → 원장 체크)이고 5단의 체크 전환 주체는 사용자다.
**왜** — 원장의 유일한 설계 목표는 "세션이 끊겨도 원장만 읽고 이어갈 수 있는가"다. 대화 컨텍스트가 남아 있다는 전제를 깔면 원장이 아니라 메모가 된다. 배치를 역순으로 잡으면 하위가 바뀔 때마다 상위를 다시 손대게 된다.
**주의** — 후반부에 체크 전환을 미루는 사고가 실제로 났다. 편집량이 줄면 미루기 쉽고, 미루면 다음 세션이 코드로 진행 상태를 역추적한다. 범위 밖에서 같은 위반을 봐도 그 자리에서 고치지 않는다 — diff 가 승인 범위를 벗어나면 리뷰가 성립하지 않는다.
**강도·출처** — 3대 금지(일괄 편집 금지 · 제안 없이 선수정 금지 · 원장 임의 전환 금지)와 5단 루프는 `campaign-methodology.md` 원칙 5 `관측 컨벤션`, 출처는 프로젝트 실측 279줄 / 8배치 / 56파일 운영 기록. 원장 내용은 프로젝트 소유이고 포맷만 재사용 자산이다.

## 6. 브리핑 표

파일 하나를 편집하기 **전에** 낸다. 제안과 실행을 한 턴에 붙이지 않는다. 골격 셋 — 위반 제안 · Props 판정 · 완료 보고.

```text
【{파일 경로}】 위반 {n}건
| # | 규칙 | 현재 | 제안 | 근거 |
|---|---|---|---|---|
| 1 | {규칙 ID} | {현재 코드 · 파일:라인} | {변경 후} | {references 위치} |
| 2 | {규칙 ID} | {현재 코드 · 파일:라인} | {변경 후} | {references 위치} |
진행할까요?

【{컴포넌트}】 Props {n}개 · 호출부 {m}곳
| Prop | 타입 | 실전달값 | 판정 |
|---|---|---|---|
| {name} | {Type} | {호출부에서 관측된 값 목록} | 유지 |
| {name} | {Type} | 전달 없음 (기본값만) | 제거 |
| {name} | {Type} | 전 호출부 동일값 | 내부 상수로 |

【{파일 경로}】 완료
변경: {n}건
| # | 규칙 | 결과 |
|---|---|---|
| 1 | {규칙 ID} | 적용 |
| 2 | {규칙 ID} | 미적용 — {사유} |
대조 결과 (전부 0이어야 함)
| 패턴 | 건수 |
|---|---|
| {grep 패턴} | 0 |
```
```text
before — 카운트만 적었다. 사용자가 유지·제거를 판단 못 해 되묻는다
| showLabel | bool | 호출부 4곳 | 검토 |
after — 실제 호출부를 열어 관측한 값이 있다. 판정이 따라 나온다
| showLabel | bool | 전 호출부 true | 내부 상수로 |
```

| 자리 | 채우는 값 |
|---|---|
| `{규칙 ID}` | `core-comment.md` C-01 처럼 references 의 ID |
| `{현재 코드 · 파일:라인}` | 실제 위치. 추정 금지 |
| `{호출부에서 관측된 값 목록}` | 호출부를 실제로 열어 확인한 값. 데모 호출부는 제외 |
| `{판정}` | 유지(호출부마다 값이 다름) · 제거(아무도 안 넘김) · 내부 상수로(전부 같은 값) · 분리(한 prop 이 두 관심사 겸함) |
| `{사유}` · `{grep 패턴}` | 미적용 이유와 대조 패턴. 건수는 실행 결과다 |

**실측** — 브리핑 표 최소 컬럼은 4개(`대상｜타입｜실제 사용값｜판정`). 이 포맷은 운영 중 2회 보정됐다 — 카운트를 실전달값으로 바꾼 것, 데모 호출부를 제외한 것.
**왜** — 산문 대신 표를 쓰는 이유는 승인·거부를 항목 단위로 받기 위해서다. 산문으로 내면 통째 승인 아니면 통째 거부가 되고 그 사이에 있는 "3번만 빼고"가 표현되지 않는다.
**주의** — 실전달값에 추정을 넣는 사고가 났다. 카운트만 적으면 사용자가 판단하지 못해 왕복이 1회 는다. 근거 열에 규칙 본문을 복사하지 말고 references 안의 위치를 가리켜라.
**강도·출처** — 브리핑은 산문이 아니라 표다가 `campaign-methodology.md` 원칙 4, 출처는 프로젝트 실측(브리핑 포맷 보정 2회 — 카운트에서 실전달값으로, 데모 호출부 제외). 완료 선언 전 대조 grep 을 1회 실행하고 결과를 보고한다가 `locale-korean.md` K-10 `MUST`.

## 강도 표기

| 라벨 | 뜻 |
|---|---|
| `MUST` | 공식 문서가 금지·강제하거나 예외가 없다. 위반 시 REJECT |
| `SHOULD` | 외부 스타일 가이드가 지지하는 권고. 명시 예외가 있고 위반 시 근거를 요구한다 |
| `관측 컨벤션` | 공개 출처 없이 프로젝트 실측만 있다. 프로젝트가 완화할 수 있다 |
| `합성` | 여러 디자인 시스템 어휘를 대조해 만든 규칙. 단일 권위 출처가 없다 |

`관측 컨벤션` 에 논문 각주를 붙이지 마라. 붙이는 순간 검증 불가능한 주장이 된다. 근거는 코퍼스 실측 건수뿐이고 그것으로 충분하다.
