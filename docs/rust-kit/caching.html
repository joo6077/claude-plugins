캐싱 원칙

moka 0.12.x(인메모리 L1)와 deadpool-redis 0.23.x(분산 L2)를 계층적으로 조합한다. moka는 동일 프로세스 내 고속 캐시, Redis는 다중 인스턴스 공유 캐시로 사용한다.

캐시 계층 구조

L1(moka) → L2(Redis) → DB 순서로 조회한다. 히트 시 상위 계층에 backfill한다.

L1 — moka (인메모리) 동일 프로세스 내 · 네트워크 왕복 없음 · TTL 5분 · max 10,000개
L1 miss → L2 조회
L2 — Redis (분산) 다중 인스턴스 공유 · deadpool-redis 풀 · TTL 데이터 성격에 따라
L2 miss → DB 조회 + backfill
DB — PostgreSQL (원본) sqlx PgPool · 캐시 미스 시에만 직접 조회
핵심 원칙

moka 인메모리 캐시, deadpool-redis 풀, 계층 캐시 구현 원칙 3가지.

1

moka::future::Cache — 인메모리 L1

thundering herd(동시 캐시 미스 폭주)는 get_with로 방지한다. 동일 키에 대한 동시 초기화를 한 번만 실행한다.

// Cargo.toml
moka = { version = "0.12", features = ["future"] }

pub fn build_user_cache() -> Cache<Uuid, Arc<User>> {
    Cache::builder()
        .max_capacity(10_000)
        .time_to_live(Duration::from_secs(300))   // 5분 TTL
        .time_to_idle(Duration::from_secs(60))    // 60초 미사용 퇴거
        .build()
}

// thundering herd 방지 — get_with
let user = cache
    .get_with(user_id, async {
        Arc::new(db.find_user(user_id).await.unwrap())
    })
    .await;
// 동시 요청이 와도 초기화 클로저는 한 번만 실행
moka 0.12.x + future feature
2

deadpool-redis — 분산 L2

Redis 연결을 매 요청마다 생성하지 않는다. deadpool-redis로 풀을 구성하고 pool.get()으로 연결을 빌린다.

// Cargo.toml
deadpool-redis = { version = "0.23", features = ["rt_tokio_1"] }
redis = "0.28"

pub fn build_redis_pool(url: &str) -> Pool {
    Config::from_url(url)
        .create_pool(Some(Runtime::Tokio1))
        .expect("Redis pool creation failed")
}

// GET
pub async fn get_cached(pool: &Pool, key: &str) -> Option<String> {
    let mut conn = pool.get().await.ok()?;
    redis::cmd("GET")
        .arg(key)
        .query_async::<String>(&mut conn)
        .await.ok()
}

// SETEX — TTL 포함
pub async fn set_cached(
    pool: &Pool, key: &str, value: &str, ttl_secs: u64,
) -> Result<(), anyhow::Error> {
    let mut conn = pool.get().await?;
    redis::cmd("SETEX")
        .arg(key).arg(ttl_secs).arg(value)
        .query_async::<()>(&mut conn)
        .await?;
    Ok(())
}
deadpool-redis 0.23.x
3

L1 + L2 계층 캐시 패턴

L1 조회 → 미스 시 L2 조회 → L2 히트 시 L1 backfill → 미스 시 DB 조회. 무효화는 양쪽 계층에 동시에 적용한다.

pub struct TieredCache {
    l1: Cache<String, Arc<UserProfile>>,
    l2: Pool,
}

impl TieredCache {
    pub async fn get(&self, key: &str) -> Option<Arc<UserProfile>> {
        // 1. L1 먼저
        if let Some(v) = self.l1.get(key).await {
            return Some(v);
        }
        // 2. L2 fallback
        let mut conn = self.l2.get().await.ok()?;
        let json: String = redis::cmd("GET")
            .arg(key)
            .query_async(&mut conn)
            .await.ok()?;
        let profile: UserProfile = serde_json::from_str(&json).ok()?;
        let arc = Arc::new(profile);
        // 3. L1 backfill
        self.l1.insert(key.to_string(), arc.clone()).await;
        Some(arc)
    }

    pub async fn invalidate(&self, key: &str) {
        // L1 + L2 동시 무효화
        self.l1.invalidate(key).await;
        if let Ok(mut conn) = self.l2.get().await {
            let _ = redis::cmd("DEL")
                .arg(key)
                .query_async::<()>(&mut conn)
                .await;
        }
    }
}

안티패턴

캐시 구현 시 반복되는 실수와 올바른 대안.

Bad — L1 없이 모든 요청을 Redis로
// 매 요청마다 Redis 왕복 ❌
pub async fn get_user(id: Uuid) -> Option<User> {
    let key = format!("user:{id}");
    // 네트워크 왕복 발생 — 동일 프로세스에서
    // 자주 읽는 데이터도 매번 Redis 조회
    redis_get(&pool, &key).await
}
Good — L1 moka 먼저 확인
// L1에서 먼저 확인 — 네트워크 왕복 없음 ✅
pub async fn get_user(id: Uuid) -> Option<Arc<User>> {
    let key = format!("user:{id}");
    if let Some(u) = l1_cache.get(&key).await {
        return Some(u); // 인메모리 히트
    }
    // miss 시에만 Redis 조회
    redis_get(&pool, &key).await
}
Bad — 쓰기 후 캐시 무효화 누락
pub async fn update_user(id: Uuid, data: UpdateUser) {
    db.update_user(id, data).await?;
    // 캐시 무효화 누락 ❌
    // 이후 조회에서 낡은 데이터 반환
}
Good — 쓰기 후 즉시 invalidate
pub async fn update_user(id: Uuid, data: UpdateUser) {
    db.update_user(id, data).await?;
    // L1 + L2 동시 무효화 ✅
    let key = format!("user:{id}");
    tiered_cache.invalidate(&key).await;
}
Bad — Redis 직접 연결 매 요청 생성
pub async fn get_session(id: &str) -> Option<String> {
    // 매 요청마다 새 연결 생성 ❌
    let client = redis::Client::open(REDIS_URL)?;
    let mut conn = client.get_async_connection().await?;
    conn.get(id).await.ok()
    // 연결 오버헤드 + 연결 수 폭증
}
Good — deadpool 풀 재사용
// 앱 시작 시 한 번 생성
let pool = build_redis_pool(&redis_url);

// 매 요청마다 풀에서 빌림 ✅
pub async fn get_session(pool: &Pool, id: &str) -> Option<String> {
    let mut conn = pool.get().await.ok()?;
    redis::cmd("GET").arg(id)
        .query_async(&mut conn).await.ok()
}
Gotchas 체크리스트

캐시 구현 시 반복적으로 실수하는 포인트.

  • ✓ moka::future::Cache는 Clone이 O(1) — 내부적으로 Arc를 사용하므로 AppState에 직접 포함해도 된다. 별도로 Arc<Cache<...>>로 감쌀 필요가 없다.
  • ✓ get_with는 thundering herd 자동 방지 — 여러 태스크가 동시에 캐시 미스를 경험해도 초기화 클로저는 한 번만 실행된다. 실패 시 에러를 반환하는 try_get_with도 같은 보장을 제공한다.
  • ✓ deadpool-redis는 MultiplexedConnection 사용 — 단일 물리 연결을 멀티플렉싱하므로 pub/sub이나 블로킹 커맨드(BLPOP 등)에는 적합하지 않다. 블로킹 작업에는 별도 연결을 사용한다.
  • ✓ Redis 직렬화는 JSON 명시 — Redis는 바이트열만 저장한다. serde_json::to_string()으로 직렬화하고 serde_json::from_str()로 역직렬화하는 패턴을 일관되게 유지한다.
  • ✓ TTL 없는 캐시 항목 금지 — Redis에 TTL을 설정하지 않으면 메모리가 무한히 증가한다. SET key value 대신 반드시 SETEX key ttl value 또는 SET key value EX ttl을 사용한다.
