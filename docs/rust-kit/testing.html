테스팅 원칙

Rust 는 언어 차원에서 테스트를 지원한다(#[test], #[cfg(test)]). 외부 크레이트(cargo-nextest, mockall)는 실행 속도와 모킹을 보완한다. 테스트는 격리되어야 하고, 외부 의존성(DB, 네트워크)은 주입 가능해야 한다.

source: docs/rust/fundamentals/testing.md frontmatter v0.1.0 정정 2026-08-13 — sqlx::test 격리 단위는 DB
핵심 원칙

테스트 배치(1) → 실행기(2) → 의존성 격리(3) → DB 격리(4) 순서로 읽는다. 4번은 이번 사이클에 사실 정정이 있었다.

1

단위 테스트는 같은 파일, 통합 테스트는 tests/

Test Organization

Rust 관례: 단위 테스트는 구현 파일 하단의 #[cfg(test)] 모듈, 통합 테스트는 크레이트 루트의 tests/ 디렉토리. 통합 테스트는 크레이트 public API 만 사용한다.

// src/domain/user.rs
pub fn validate_email(email: &str) -> bool { ... }

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn valid_email_passes() {
        assert!(validate_email("user@example.com"));
    }

    #[test]
    fn empty_email_fails() {
        assert!(!validate_email(""));
    }
}
crates/domain/
├── src/
│   └── user.rs       # 단위 테스트 포함
└── tests/
    └── user_flow.rs # 통합 테스트 — public API만

2

cargo-nextest로 테스트를 실행한다

Test Runner

cargo test보다 2~3배 빠르고, 테스트를 프로세스 단위로 격리한다. 글로벌 상태 오염이 자동으로 방지된다. CI 에서도 cargo nextest run을 표준으로 사용한다.

# 설치
cargo install cargo-nextest

# 실행
cargo nextest run
cargo nextest run --test-threads 4   # 병렬 수 제한
cargo nextest run -p domain          # 특정 크레이트만
# .config/nextest.toml
[profile.default]
fail-fast = false          # 실패해도 계속 실행
test-threads = "num-cpus"  # CPU 수만큼 병렬

[profile.ci]
fail-fast = true

3

trait 기반 모킹으로 외부 의존성을 격리한다

Dependency Injection

헥사고날 아키텍처의 Port trait 을 활용하면 테스트에서 가짜 구현을 주입할 수 있다. mockall 크레이트는 #[automock] 매크로로 mock 을 자동 생성한다.

// domain/src/ports/database.rs
#[cfg_attr(test, mockall::automock)]
#[async_trait::async_trait]
pub trait DatabasePort: Send + Sync {
    async fn find_user(&self, id: UserId)
        -> Result<Option<User>, DomainError>;
}

// 테스트에서 mock 사용
#[tokio::test]
async fn get_user_returns_not_found() {
    let mut mock_db = MockDatabasePort::new();
    mock_db
        .expect_find_user()
        .with(eq(UserId::from(1)))
        .returning(|_| Ok(None));

    let service = UserService::new(Arc::new(mock_db));
    let result = service.get_user(UserId::from(1)).await;
    assert!(matches!(result, Err(DomainError::NotFound { .. })));
}

DB 테스트는 sqlx::test로 테스트별 새 테스트 DB 를 쓴다

DB Isolation

#[sqlx::test]는 테스트 함수마다 새 테스트 DB 를 만들어 live connection 을 주입하고, migrations 폴더가 있으면 자동 적용하며, 테스트가 성공하면 그 DB 를 정리한다. 테스트 간 DB 상태 오염이 없다.

정정 2026-08-13
이전 판이 “테스트마다 트랜잭션을 열고 끝나면 롤백한다” 고 적었으나 공식 문서 기준 사실이 아니다. 격리 단위는 트랜잭션이 아니라 DB 이며, 커밋된 데이터도 남았다가 DB 단위로 폐기된다. Postgres/MySQL 은 DATABASE_URL 이 필요하다. 
// adapters/tests/user_repository.rs
#[sqlx::test(fixtures("users"))]
async fn find_existing_user(pool: sqlx::PgPool) {
    let adapter = PostgresUserAdapter::new(pool);
    let result = adapter.find_user(UserId::from(1)).await;
    assert!(result.unwrap().is_some());
}

// tests/fixtures/users.sql
INSERT INTO users (id, email)
VALUES (1, 'test@example.com');
↗ sqlx — Testing
sqlx::test 격리 모델 — 무엇이 정정되었나

격리 단위를 잘못 알면 “커밋됐으니 다음 테스트에서 보이겠지” 또는 “롤백되니 DATABASE_URL 없이 돌겠지” 같은 잘못된 기대가 생긴다. 두 모델의 차이는 실패 양상이 다르다.

틀린 모델 — 트랜잭션 롤백

테스트 시작 시 BEGIN, 끝나면 ROLLBACK 이라고 가정한다. 이 모델을 믿으면 다음이 따라온다.

• 커밋된 데이터는 사라진다고 기대
• 격리 비용을 "롤백 ~5ms" 로 고정 수치화
• 커넥션이 하나뿐이라고 가정
  → 동시성 가드 negative test 가
    설계 자체로 불가능해진다
실제 모델 — 테스트별 새 DB

테스트 함수마다 DB 를 새로 만들고, migrations 를 적용하고, 성공 시 그 DB 를 정리한다.

• 커밋된 데이터도 남는다 (DB 단위로 폐기)
• 비용 = DB 생성 + migration — 환경 의존
• 실 커넥션이 주입되므로 별도 트랜잭션·
  동시 커넥션으로 경합 시나리오 재현 가능
• Postgres/MySQL 은 DATABASE_URL 필요

실행 전제 — 환경이 없으면 테스트가 아니라 스킵이다

#[sqlx::test] 는 실 DB 엔진을 요구한다. CI 에서 DATABASE_URL 이 비어 있으면 “통과” 가 아니라 측정이 없었던 것이다. 실행 증거에는 명령 · 실행된 테스트 수 · 종료 코드를 함께 남긴다.

# 실행 전제
export DATABASE_URL=postgres://localhost/app_test
cargo nextest run -p adapters

# 증거로 남길 것
running 12 tests   # ← 실행된 테스트 수
exit code: 0
↗ sqlx — #[sqlx::test] attribute

mock 과 실 DB 는 상호 배타가 아니다

mock 단위 테스트는 control flow(0 행일 때 conflict 분기, 후속 호출 0 회)를 검증하고, 실 DB 통합 테스트는 SQL 술어의 의미를 검증한다. 한쪽만으로 “검증됨” 이라고 보고하지 않는다.

mock  → repository 분기·호출 횟수
실 DB → WHERE 술어가 실제로 행을 거르는가

두 층을 계층 표기까지 정확히 구분해서 보고한다.
→ 동시성 가드 프로토콜 §3
수치 기준

테스트 계층별 목표 실행 시간과 도구별 오버헤드. 환경 의존적인 항목은 고정 수치를 쓰지 않고 프로젝트에서 실측한다.

항목기준값비고
cargo-nextest vs cargo test 속도 2~3× 빠름 프로세스 격리 + 병렬 실행
mockall 모킹 오버헤드 무시 가능 테스트 전용 코드
sqlx::test 테스트별 새 테스트 DB 생성 + migration 프로젝트에서 실측 트랜잭션 롤백이 아니라 DB 생성·정리 비용 — 환경 의존이라 고정 수치를 쓰지 마라
단위 실행 목표 < 1ms / 테스트 외부 I/O 없을 때
통합 실행 목표 < 100ms / 테스트 DB, 네트워크 포함
안티패턴

테스트 품질을 낮추는 흔한 실수 패턴.

Bad — 글로벌 상태로 데이터 공유
// ✗ 테스트 순서에 따라 결과가 달라짐
static mut SHARED_STATE: Vec<Item> = Vec::new();

#[test]
fn test_a() {
    unsafe { SHARED_STATE.push(item); }
}
Good — 각 테스트가 독립적으로 데이터 생성
// ✓ 독립적, 순서 무관
#[test]
fn test_a() {
    let state = vec![item()]; // 로컬 생성
    assert_eq!(process(&state), expected);
}
Bad — 단위 테스트에서 실제 DB 연결
// ✗ 느리고 환경에 의존적
#[test]
fn test_user_service() {
    let pool = PgPool::connect(&DATABASE_URL).unwrap();
    let service = UserService::new(pool);
    // ...
}
Good — Port trait mock 주입
// ✓ 빠르고 격리됨
#[tokio::test]
async fn test_user_service() {
    let mock_db = MockDatabasePort::new();
    let service = UserService::new(Arc::new(mock_db));
    // ...
}
Bad — 테스트 파일에 #[allow(dead_code)] 남기기
// ✗ 죽은 헬퍼가 계속 쌓인다
#[allow(dead_code)]
fn unused_helper() -> Fixture { ... }
Good — 사용하지 않는 헬퍼는 삭제
// ✓ 테스트 코드도 프로덕션과 같은 품질 기준
// 필요해지면 그때 다시 만든다
Bad — unwrap() 으로 실패 메시지를 감추기
// ✗ "called `Option::unwrap()` on a `None` value"
let result = find_user(id).await.unwrap();
Good — 구체적인 실패 메시지
// ✓ 실패 원인을 바로 알 수 있음
let result = find_user(id).await
    .expect("user should exist in fixture");
// 또는
assert!(result.is_ok(), "error: {:?}", result.err());
Gotchas

테스트 환경에서 자주 발생하는 함정.

  • !
    #[tokio::test]와 #[sqlx::test]를 동시에 사용할 수 없다
    #[sqlx::test]는 자체 tokio 런타임을 포함한다. 두 속성을 중복 사용하면 런타임 중첩 에러가 발생한다. DB 테스트에는 #[sqlx::test]만 사용한다.
  • !
    mockall expect_*은 drop 시 검증한다
    MockDatabasePort가 드롭될 때 expect_*으로 설정한 호출 횟수를 검증한다. assert! 이전에 mock 이 드롭되면 검증이 테스트 결과와 분리된다. 명시적으로 drop(mock)을 테스트 마지막에 호출하거나 블록 스코프를 사용한다.
  • !
    cargo test와 달리 nextest 는 --nocapture 대신 --no-capture
    출력을 확인하려면 cargo nextest run --no-capture를 사용한다. cargo test -- --nocapture와 플래그 이름이 다르다.
  • !
    fixture 경로는 크레이트 루트 기준이다
    #[sqlx::test(fixtures("users"))]는 tests/fixtures/users.sql을 찾는다. 경로가 잘못되면 “fixture not found” 에러가 발생한다.
  • !
    “롤백되니까 DB 없이도 돈다” 는 성립하지 않는다
    격리 단위가 DB 이므로 Postgres/MySQL 에서는 DATABASE_URL 이 반드시 필요하다. 환경이 없으면 테스트는 통과한 것이 아니라 실행되지 않은 것이다.
