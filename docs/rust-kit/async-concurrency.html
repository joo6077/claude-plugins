비동기와 동시성 원칙

Rust async는 Zero-cost abstraction이다. async fn은 상태 머신으로 컴파일되며 런타임 스레드 비용이 없다. Tokio는 멀티 스레드 work-stealing 런타임으로 I/O 집약 서버 애플리케이션의 사실상 표준이다. async와 동기 코드의 경계를 명확히 하는 것이 핵심이다.

핵심 원칙
1

async 컨텍스트에서 블로킹 코드를 실행하지 않는다

No Blocking in Async

Tokio 런타임은 적은 수의 OS 스레드(기본 CPU 코어 수)로 수만 개의 태스크를 처리한다. 하나의 태스크가 스레드를 블로킹하면 같은 스레드의 다른 태스크가 모두 지연된다.

블로킹 기준: 100µs 이상 CPU 점유, 동기 I/O, std::thread::sleep

// ❌ 금지 — async 내 블로킹 호출
async fn process(path: &str) -> Result<String> {
    std::fs::read_to_string(path)?  // 런타임 스레드 블로킹
}

// ✅ 블로킹 작업을 별도 스레드풀로 위임
async fn process(path: String) -> Result<String> {
    tokio::task::spawn_blocking(move || {
        std::fs::read_to_string(&path)
    }).await?
}

// ✅ 또는 Tokio async I/O 사용
async fn process(path: &str) -> Result<String> {
    tokio::fs::read_to_string(path).await
}
↗ Tokio — spawn_blocking
2

async에서는 tokio::sync, 동기 코드에서는 std::sync

Sync Primitives

std::sync::Mutex::lock()은 스레드를 블로킹한다. async 태스크 안에서 사용하면 런타임 스레드를 점유한다. tokio::sync::Mutex는 lock을 기다리는 동안 스레드를 양보한다.

// async 컨텍스트 — tokio::sync 사용
use tokio::sync::{Mutex, RwLock};
let shared = Arc::new(Mutex::new(HashMap::new()));
let guard = shared.lock().await; // 스레드 블로킹 없이 대기

// 예외: lock 대기 시간이 매우 짧고
// await가 없는 경우 std::sync::Mutex가 더 빠름 (~10ns vs ~50ns)

lock 범위를 최소화하고, Mutex guard를 보유한 채로 .await를 호출하지 않는다.

3

태스크 간 통신은 채널로 한다

Message Passing

공유 상태 대신 메시지 전달이 데이터 경쟁을 구조적으로 방지한다. Tokio는 용도별 채널을 제공한다.

채널용도비고
mpsc단방향 다대일가장 일반적. 작업 큐, 이벤트 수집
oneshot단발 응답요청-응답 패턴
broadcast일대다 방송이벤트 팬아웃
watch상태 관찰최신 값만 필요한 경우
 
// mpsc — 워커 풀 패턴
let (tx, mut rx) = tokio::sync::mpsc::channel::<Job>(100);

tokio::spawn(async move {
    while let Some(job) = rx.recv().await {
        process(job).await;
    }
});
tx.send(job).await?;

4

태스크 취소와 타임아웃을 명시적으로 처리한다

Cancellation

Tokio 태스크는 JoinHandle::abort()로 취소되거나 tokio::time::timeout으로 제한할 수 있다. 취소 지점은 .await이다 — await 없이 CPU만 사용하는 루프는 취소되지 않는다.

use tokio::time::{timeout, Duration};

let result = timeout(
    Duration::from_secs(5),
    fetch_data(url)
).await.map_err(|_| AppError::Timeout)?;

// JoinSet으로 여러 태스크 관리
let mut set = tokio::task::JoinSet::new();
for item in items {
    set.spawn(process(item));
}
while let Some(result) = set.join_next().await {
    handle(result?)?;
}

안티패턴

async 코드에서 자주 범하는 실수 패턴.

Bad — async 내 std::thread::sleep
// ❌ 스레드 블로킹
async fn wait() {
    std::thread::sleep(Duration::from_secs(1));
}
Good — tokio::time::sleep
// ✅ 스레드 양보
async fn wait() {
    tokio::time::sleep(Duration::from_secs(1)).await;
}
Bad — JoinHandle 무시 (fire-and-forget)
// ❌ 패닉이 조용히 소실됨
tokio::spawn(important_task());
Good — JoinHandle 보관 후 await
// ✅ 결과 확인
let handle = tokio::spawn(important_task());
handle.await??; // JoinError + 태스크 에러 처리
Bad — 모든 곳에 Arc<Mutex>
// ❌ 채널로 해결 가능한 경우
let state = Arc::new(Mutex::new(Vec::new()));
// 여러 태스크가 동시에 lock 경쟁
Good — 채널로 소유권 이전
// ✅ 단일 소유자가 상태 관리
let (tx, mut rx) = mpsc::channel(32);
tokio::spawn(async move {
    while let Some(item) = rx.recv().await {
        state.push(item); // lock 경쟁 없음
    }
});
Gotchas

async 코드에서 반복적으로 발생하는 컴파일 에러와 런타임 함정.

  • !
    async Mutex guard를 .await 경계에서 보유하면 컴파일 에러
    MutexGuard를 들고 .await를 호출하면 "future is not Send" 에러가 발생한다. guard를 먼저 드롭하거나 별도 블록으로 분리한다. 
    // ❌ guard가 await를 가로지름
let guard = mutex.lock().await;
do_something_async().await; // guard가 아직 살아있음

// ✅ guard 먼저 드롭
let value = { mutex.lock().await.clone() };
do_something_async().await;
  • !
    spawn_blocking 클로저는 'static을 요구한다
    별도 스레드에서 실행되므로 'static이어야 한다. 지역 변수를 캡처하려면 move 클로저와 Arc::clone을 사용한다.
  • !
    select!에서 취소된 브랜치의 사이드 이펙트 주의
    먼저 완료된 브랜치를 선택하고 나머지를 취소한다. 취소된 future가 이미 부분 실행된 경우(네트워크 요청 시작 등) 사이드 이펙트가 남을 수 있다. 취소 안전성이 필요한 작업은 select! 외부로 분리한다.
  • !
    async 테스트에는 반드시 #[tokio::test]
    #[test]만 달면 컴파일은 되지만 async 코드가 실행되지 않는다. 빈 테스트처럼 항상 통과한다.
