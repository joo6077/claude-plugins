성능 원칙

Rust는 기본적으로 빠르지만 잘못된 패턴은 불필요한 힙 할당과 복사를 유발한다. 최적화는 측정 후 수행한다 — 추측 기반 최적화는 코드 복잡도를 높이고 실제 병목과 다를 수 있다. cargo flamegraph와 criterion 벤치마크로 병목을 확인한 뒤 수정한다.

측정 없이 최적화하지 않는다. criterion 벤치마크가 먼저, 코드 변경이 나중이다.
핵심 원칙
1

불필요한 힙 할당을 줄인다

Heap Allocation

힙 할당(Box, Vec, String 생성)은 ~50ns 수준의 비용이다. 루프 안에서 반복 할당하거나 크기를 알고 있는데도 동적 할당하면 성능에 영향을 준다.

// 비효율 — 루프마다 String 할당
for item in items {
    let s = format!("prefix_{}", item.name); // 매 반복 힙 할당
    process(&s);
}

// 효율 — 버퍼 재사용
let mut buf = String::with_capacity(64);
for item in items {
    buf.clear();
    write!(&mut buf, "prefix_{}", item.name).unwrap();
    process(&buf);
}

2

크기를 알면 Vec::with_capacity로 사전 할당

Vec Capacity

Vec::new()에 원소를 push하면 용량 초과 시 2배 재할당이 발생한다. 원소 수를 알거나 추정할 수 있으면 with_capacity로 재할당을 방지한다.

// 재할당 발생 가능
let mut results = Vec::new();
for item in source.iter() {
    results.push(transform(item));
}

// 재할당 없음
let mut results = Vec::with_capacity(source.len());
for item in source.iter() {
    results.push(transform(item));
}

// 또는 Iterator::collect — 크기 힌트 자동 활용
let results: Vec<_> = source.iter().map(transform).collect();

3

Iterator 체이닝은 collect 없이 지연 평가

Lazy Evaluation

collect()는 새 컬렉션을 힙에 할당한다. 중간 결과가 필요 없으면 iterator 체인을 끝까지 이어서 한 번에 처리한다.

// 중간 Vec 할당 2번
let filtered: Vec<_> = items.iter()
    .filter(|x| x.active).collect();    // 힙 할당
let names: Vec<_> = filtered.iter()
    .map(|x| &x.name).collect();        // 힙 할당

// 지연 평가 — collect 한 번
let names: Vec<_> = items.iter()
    .filter(|x| x.active)
    .map(|x| &x.name)
    .collect();

// 소비만 할 경우 collect 불필요
items.iter()
    .filter(|x| x.active)
    .for_each(|x| process(x));

4

criterion으로 벤치마크를 측정하고 최적화

Benchmark First

직관 기반 최적화 전에 반드시 측정한다. criterion은 통계적으로 유의미한 결과를 제공하며, 워밍업과 반복 실행을 자동 처리한다.

# Cargo.toml
[[bench]]
name = "user_processing"
harness = false

[dev-dependencies]
criterion = { version = "0.5", features = ["html_reports"] }
// benches/user_processing.rs
use criterion::{black_box, criterion_group, criterion_main, Criterion};

fn bench_validate_email(c: &mut Criterion) {
    c.bench_function("validate_email valid", |b| {
        b.iter(|| validate_email(black_box("user@example.com")))
    });
}

criterion_group!(benches, bench_validate_email);
criterion_main!(benches);
# 실행
cargo bench
cargo bench -- user_processing
cargo bench -- --save-baseline main  # 기준선 저장

5

release 빌드로 성능을 측정한다

Release Profile

debug 빌드는 최적화가 없어 release 빌드보다 10~100배 느릴 수 있다. 성능 측정과 프로파일링은 항상 --release로 실행한다.

cargo build --release
cargo bench                   # 자동으로 release 빌드
cargo flamegraph --release     # 프로파일링

release 프로파일 추가 최적화 (빌드 시간과 트레이드오프):

# Cargo.toml
[profile.release]
opt-level = 3       # 기본값. 최대 최적화
lto = true          # +5~20% 성능, 빌드 시간 증가
codegen-units = 1   # 최적화 향상, 병렬 빌드 비활성화

안티패턴

측정 없이 최적화하거나 잘못된 방식으로 성능을 낭비하는 패턴.

Bad — 루프 내 반복 String 생성
// ❌ 매 반복 힙 할당
for item in items {
    let s = String::new();
    // s 사용 후 드롭 → 재할당
}
Good — 버퍼 재사용
// ✅ 버퍼 한 번 할당
let mut buf = String::with_capacity(64);
for item in items {
    buf.clear();
    // buf 재사용
}
Bad — collect 후 즉시 iterate
// ❌ 불필요한 중간 Vec
items.iter()
    .map(f)
    .collect::<Vec<_>>()
    .iter()
    .for_each(g);
Good — 체인 유지
// ✅ 중간 할당 없음
items.iter()
    .map(f)
    .for_each(g);
Bad — debug 빌드로 성능 측정
// ❌ 의미 없는 벤치마크 결과
cargo run   # debug 빌드 기본값
// "느린 것 같아서" 최적화 진행
Good — release + criterion
// ✅ 통계적으로 유의미한 결과
cargo bench  # release 빌드 + black_box
// 실제 병목 확인 후 최적화
Gotchas

성능 측정과 최적화에서 자주 발생하는 함정.

  • !
    criterion 0.4와 0.5는 API가 다르다
    BenchmarkGroup의 일부 메서드 시그니처가 0.5에서 변경됐다. Cargo.toml의 버전을 명시하고, 업그레이드 시 변경 사항을 확인한다.
  • !
    flamegraph는 release 빌드에 debug 심볼이 필요하다
    cargo flamegraph로 프로파일링하려면 [profile.release] debug = 1 설정이 필요하다. 성능에는 영향 없음.
  • !
    lto = true는 CI 빌드 시간을 크게 늘린다
    LTO는 링크 단계에서 전체 코드베이스를 최적화한다. 프로덕션 릴리스에만 활성화하고, CI에는 별도 프로파일(profile.release-lto)로 분리한다.
  • !
    black_box 없이 벤치마크를 작성하면 컴파일러가 최적화로 제거한다
    컴파일러가 벤치마크 함수 호출을 사용하지 않는 코드로 판단해 제거할 수 있다. criterion::black_box로 입력과 출력을 감싸 최적화를 방지한다.
  • !
    커스텀 iterator의 size_hint가 잘못되면 collect 재할당이 발생한다
    크기를 알면 반드시 size_hint()를 정확히 구현한다. 잘못된 힌트는 collect 시 재할당으로 이어진다.
