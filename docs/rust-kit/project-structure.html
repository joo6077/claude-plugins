프로젝트 구조 원칙

Rust 프로젝트는 Cargo workspace로 여러 크레이트를 관리한다. 크레이트 경계가 의존성 규칙을 컴파일 타임에 강제한다 — 도메인이 인프라를 import하면 컴파일이 실패한다. 초기부터 workspace를 구성하면 나중에 분리 비용이 없다.

핵심 원칙
1

Cargo workspace로 시작한다

Workspace First

초기에 workspace 구조를 설정하면 이후 리팩토링 비용을 줄인다. 공통 의존성은 workspace 루트 Cargo.toml에 선언하여 버전을 일관되게 유지한다.

# Cargo.toml (workspace 루트)
[workspace]
members = ["crates/*"]
resolver = "2"

[workspace.dependencies]
tokio = { version = "1", features = ["full"] }
serde = { version = "1", features = ["derive"] }
thiserror = "2"
sqlx = { version = "0.8", features = [
    "postgres", "runtime-tokio-native-tls", "uuid"
] }

# crates/domain/Cargo.toml
[dependencies]
thiserror = { workspace = true }
serde = { workspace = true }

크레이트는 의존 방향 기준으로 분리한다

Dependency Direction

의존 방향은 항상 단방향이다. domain은 외부 인프라 크레이트를 가지지 않는다. 순환 의존은 Cargo가 컴파일 에러로 차단한다.

app
→
api
→
adapters
→
domain
crates/
├── domain/   # 외부 인프라 없음 (thiserror, serde만)
├── adapters/ # domain만 의존. sqlx, aws-sdk 포함
├── api/      # domain + adapters. axum HTTP 레이어
└── app/      # 모든 크레이트. main.rs, DI 조립

3

mod.rs 대신 파일명 기반 모듈

Module Style (Rust 2018+)

Rust 2018 edition부터 mod.rs 없이 foo.rs + foo/bar.rs 구조를 사용할 수 있다. mod.rs는 디렉토리 안에 숨어 있어 에디터에서 혼동을 일으킨다.

권장 (Rust 2018+)
src/
├── lib.rs
├── user.rs
└── user/
    ├── model.rs
    └── service.rs
지양 (구형 스타일)
src/
├── lib.rs
└── user/
    ├── mod.rs  ← 혼동 유발
    ├── model.rs
    └── service.rs

가시성은 필요한 최소 범위로 제한한다

Visibility Control

기본은 비공개. 과도한 pub은 내부 구현이 외부 계약이 되어 리팩토링을 어렵게 만든다.

pub
외부 API. 명시적으로 공개할 때만
pub(crate)
크레이트 내부 공유. 외부 미노출
pub(super)
상위 모듈에만 공개
(없음)
기본값. 같은 모듈 내부만
pub struct UserService {          // 외부 공개
    db: Arc<dyn DatabasePort>,    // 비공개 필드
}
pub(crate) fn internal_helper() { ... }
pub(super) fn module_helper() { ... }

안티패턴

프로젝트 구조에서 자주 저지르는 실수.

Bad — 모든 타입을 pub으로 선언
// ❌ 내부 구현이 외부 계약이 됨
pub struct DbRow { ... }
pub fn build_query(...) { ... }
pub fn format_result(...) { ... }
Good — 필요한 것만 공개
// ✅ 최소 가시성에서 시작
struct DbRow { ... }
pub(crate) fn build_query(...) { ... }
pub fn find_user(...) { ... }  // 진짜 API만
Bad — 단일 크레이트에 모든 코드
// ❌ 도메인 코드가 인프라를 import해도 경고 없음
// src/lib.rs에 domain, adapters, api 혼재
Good — workspace + 크레이트 분리
// ✅ 아키텍처 규칙을 컴파일 타임에 강제
crates/
├── domain/   # sqlx import → 컴파일 에러
├── adapters/
└── api/
Bad — use super::super:: 체인
// ❌ 모듈 구조 변경 시 모두 수정 필요
use super::super::domain::user::UserId;
Good — 절대 경로 또는 re-export
// ✅ 안정적인 경로
use crate::domain::user::UserId;
// 또는 pub use로 단축 경로 제공
Gotchas

workspace와 모듈 시스템에서 자주 발생하는 혼동.

  • !
    workspace Cargo.lock은 루트에 하나만 존재한다
    workspace 멤버 크레이트에 별도 Cargo.lock이 생기지 않는다. 멤버 크레이트를 독립 배포하는 경우에는 별도 workspace로 분리한다.
  • !
    pub use glob re-export는 API surface를 의도치 않게 넓힌다
    pub use adapters::*처럼 glob re-export하면 내부 타입이 모두 공개된다. 명시적으로 필요한 타입만 re-export한다.
  • !
    workspace feature는 멤버에 자동 전파되지 않는다
    루트 Cargo.toml의 workspace.dependencies에 feature를 미리 나열하거나, 멤버의 Cargo.toml에서 직접 feature를 지정한다.
  • !
    크레이트 이름과 파일 시스템 경로는 독립적이다
    crates/domain/Cargo.toml의 [package] name = "my-domain"이 크레이트 이름이다. 디렉토리명과 다를 수 있다. 혼동을 방지하려면 이름을 일치시키는 것이 좋다.
