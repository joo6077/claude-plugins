gRPC / Tonic

tonic 0.14.x는 Rust의 표준 gRPC 구현이다. .proto 파일에서 tonic-prost-build로 서버·클라이언트 코드를 생성하고, tokio 위에서 비동기로 동작한다. Proto-first 워크플로우를 따르면 타입 안전성과 코드 생성 이점을 모두 얻는다.

원칙

핵심 패턴 4가지

tonic 서비스를 올바르게 구성하는 네 가지 핵심 패턴이다.

1

build.rs에서 proto를 컴파일한다

tonic-prost-build를 build-dependency로 추가하고 build.rs에서 컴파일 설정을 선언한다.

[dependencies]
tonic = "0.14"
prost = "0.13"

[build-dependencies]
tonic-prost-build = "0.14"
// build.rs
fn main() -> Result<(), Box<dyn std::error::Error>> {
    tonic_prost_build::configure()
        .build_server(true)
        .build_client(true)
        .compile_protos(
            &["proto/user.proto"],
            &["proto/"],
        )?;
    Ok(())
}
2

proto 서비스 정의

단방향 RPC와 서버 스트리밍을 하나의 서비스에 정의한다.

// proto/user.proto
syntax = "proto3";
package user;

service UserService {
    rpc GetUser (GetUserRequest)
        returns (UserResponse);
    rpc ListUsers (ListUsersRequest)
        returns (stream UserResponse);
    rpc CreateUser (CreateUserRequest)
        returns (UserResponse);
}

message GetUserRequest { string id = 1; }
message UserResponse {
    string id    = 1;
    string email = 2;
    string name  = 3;
}
3

생성된 trait을 구현하여 서버를 만든다

서버 스트리밍 핸들러는 associated type으로 반환 타입을 명시해야 한다.

use tonic::{transport::Server, Request, Response, Status};

pub mod user {
    tonic::include_proto!("user");  // 인자는 패키지명
}
use user::user_service_server::{UserService, UserServiceServer};

#[derive(Debug, Default)]
pub struct UserServiceImpl {
    db: Arc<dyn DatabasePort>,
}

#[tonic::async_trait]
impl UserService for UserServiceImpl {
    async fn get_user(
        &self,
        request: Request<GetUserRequest>,
    ) -> Result<Response<UserResponse>, Status> {
        let id = request.into_inner().id;
        let user = self.db.find_user(&id).await
            .map_err(|e| Status::internal(e.to_string()))?
            .ok_or_else(|| Status::not_found("User not found"))?;

        Ok(Response::new(UserResponse {
            id: user.id.to_string(),
            email: user.email,
            name: user.name,
        }))
    }

    // 서버 스트리밍 — associated type 필수
    type ListUsersStream =
        Pin<Box<dyn Stream<Item = Result<UserResponse, Status>> + Send>>;

    async fn list_users(
        &self,
        _request: Request<ListUsersRequest>,
    ) -> Result<Response<Self::ListUsersStream>, Status> {
        let users = self.db.list_all_users().await
            .map_err(|e| Status::internal(e.to_string()))?;

        let stream = futures::stream::iter(users.into_iter().map(|u| {
            Ok(UserResponse {
                id: u.id.to_string(),
                email: u.email,
                name: u.name,
            })
        }));
        Ok(Response::new(Box::pin(stream)))
    }
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let addr = "[::1]:50051".parse()?;
    let svc = UserServiceImpl::default();

    Server::builder()
        .add_service(UserServiceServer::new(svc))
        .serve(addr)
        .await?;
    Ok(())
}
4

tonic::Status로 gRPC 에러를 표현한다

HTTP 상태 코드 대신 gRPC status code를 사용한다. 민감한 정보는 절대 포함하지 않는다.

// 표준 Status 생성자
Status::ok("success")
Status::not_found("User not found")
Status::invalid_argument("Email is required")
Status::unauthenticated("Invalid token")
Status::permission_denied("Insufficient permissions")
Status::internal("Database error")          // ← 메시지에 내부 정보 금지
Status::unavailable("Service temporarily unavailable")
Status::already_exists("Email already registered")

// 메타데이터 포함 (요청 ID 등 디버깅 정보)
let mut status = Status::invalid_argument("Validation failed");
status.metadata_mut().insert(
    "x-request-id",
    request_id.parse()?
);
Err(status)

// 인터셉터로 인증 공통 처리
Server::builder()
    .add_service(UserServiceServer::with_interceptor(svc, check_auth))
// check_auth: fn(Request<()>) -> Result<Request<()>, Status>

tonic을 처음 사용할 때 반복되는 실수 패턴이다.

피해야 할 패턴

Rust 구조체를 직접 작성

tonic은 .proto 파일에서 타입과 서비스 코드를 생성한다. Rust 구조체를 직접 작성하면 proto 스키마와 불일치가 생기고 클라이언트와의 호환성이 깨진다.

올바른 패턴

.proto → codegen → 구현 순서 준수

항상 .proto 파일을 먼저 작성하고, build.rs를 통해 코드를 생성한 뒤, 생성된 trait을 구현한다. 타입 정의는 proto가 single source of truth다.

피해야 할 패턴

Status::internal에 민감한 정보 포함

Status::internal(db_error.to_string())처럼 내부 DB 에러나 스택 트레이스를 그대로 넣으면 클라이언트에 내부 구조가 노출된다.

올바른 패턴

서버 로그 + 일반 메시지 분리

상세 내용은 tracing::error!로 서버 로그에 기록하고, 클라이언트에는 Status::internal("internal error")처럼 일반적인 메시지만 반환한다.

피해야 할 패턴

스트리밍에서 전체 데이터 메모리 수집

Vec 전체를 수집한 뒤 스트림으로 변환하면 메모리 사용량이 증가하고 스트리밍의 지연 전송 이점이 없어진다.

올바른 패턴

futures::stream::try_unfold로 진짜 스트리밍

futures::stream::try_unfold나 DB cursor를 활용하여 데이터를 청크 단위로 가져오면서 클라이언트에 즉시 전송한다.

Gotchas

반드시 알아야 할 함정

이 항목들을 모르면 컴파일 에러나 런타임 버그로 시간을 낭비한다.

  • ✓
    include_proto! 인자는 파일명이 아닌 패키지명
    tonic::include_proto!("user")의 인자는 파일명이 아니라 .proto 파일 내 package user; 선언의 패키지명이다. 파일명이 user_service.proto여도 패키지가 user면 인자는 "user"다.
  • ✓
    build.rs 변경 후 cargo clean이 필요할 수 있다
    proto 파일을 수정했는데 변경이 반영되지 않으면 cargo clean && cargo build로 생성 코드를 재생성한다. 빌드 캐시가 오래된 생성 파일을 참조하는 경우다.
  • ✓
    서버 스트리밍의 반환 타입은 associated type으로 선언해야 한다
    type ListUsersStream = Pin<Box<dyn Stream<Item = Result<UserResponse, Status>> + Send>>처럼 associated type을 명시해야 한다. async_trait과 달리 tonic은 이 패턴을 직접 요구한다.
  • ✓
    인터셉터로 인증을 공통 처리한다
    UserServiceServer::with_interceptor(svc, check_auth) 형태로 등록한다. check_auth는 fn(Request<()>) -> Result<Request<()>, Status> 시그니처다. 각 핸들러에 중복 인증 코드를 넣지 않는다.
