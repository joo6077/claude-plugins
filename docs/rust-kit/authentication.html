인증 원칙

jsonwebtoken 10.x를 사용한 JWT 기반 인증 패턴. access token과 refresh token을 분리하고, axum의 FromRequestParts로 인증된 사용자를 Extractor로 추출한다.

핵심 원칙

JWT 발급-검증-추출-갱신 전 흐름을 타입 안전하게 구현하는 4가지 원칙.

1

Claims 구조 정의

표준 필드(sub, exp, iat, jti)와 커스텀 필드(token_type, roles)를 함께 정의한다. jti는 토큰 revocation에 필수다.

#[derive(Debug, Serialize, Deserialize, Clone)]
pub struct Claims {
    pub sub: String,           // user id
    pub exp: usize,            // expiration (Unix ts)
    pub iat: usize,            // issued at
    pub jti: String,           // revocation 용 JWT ID
    pub token_type: TokenType,
    pub roles: Vec<String>,
}

#[derive(Debug, Serialize, Deserialize, Clone, PartialEq)]
#[serde(rename_all = "lowercase")]
pub enum TokenType { Access, Refresh }

2

JwtService — 앱 시작 시 초기화

EncodingKey와 DecodingKey를 앱 시작 시 한 번 초기화한다. jsonwebtoken 10.x는 crypto backend feature를 요구한다.

// Cargo.toml
jsonwebtoken = { version = "10", features = ["aws_lc_rs"] }

pub struct JwtService {
    encoding_key: EncodingKey,
    decoding_key: DecodingKey,
    access_duration: Duration,
    refresh_duration: Duration,
}

impl JwtService {
    pub fn new(secret: &[u8]) -> Self {
        Self {
            encoding_key: EncodingKey::from_secret(secret),
            decoding_key: DecodingKey::from_secret(secret),
            access_duration: Duration::minutes(15),
            refresh_duration: Duration::days(30),
        }
    }

    pub fn verify(&self, token: &str) -> Result<Claims, JwtError> {
        let validation = Validation::new(Algorithm::HS256);
        decode::<Claims>(token, &self.decoding_key, &validation)
            .map(|data| data.claims)
            .map_err(JwtError::Decode)
    }
}
crypto backend 필수
3

AuthUser Extractor

핸들러마다 토큰 검증 코드를 반복하지 않는다. AuthUser Extractor 하나로 통일한다. Bearer 헤더 추출 → 검증 → token_type 확인 순서로 처리한다.

// axum-extra = { version = "0.10", features = ["typed-header"] }

pub struct AuthUser(pub Claims);

#[async_trait]
impl<S> FromRequestParts<S> for AuthUser
where
    S: Send + Sync,
    AppState: FromRef<S>,
{
    type Rejection = ApiError;

    async fn from_request_parts(
        parts: &mut Parts, state: &S,
    ) -> Result<Self, Self::Rejection> {
        let TypedHeader(Authorization(bearer)) =
            TypedHeader::<Authorization<Bearer>>
                ::from_request_parts(parts, state)
                .await
                .map_err(|_| ApiError::Unauthorized("Bearer token required"))?;

        let app_state = AppState::from_ref(state);
        let claims = app_state.jwt.verify(bearer.token())
            .map_err(|_| ApiError::Unauthorized("Invalid token"))?;

        if claims.token_type != TokenType::Access {
            return Err(ApiError::Unauthorized("Access token required"));
        }
        Ok(AuthUser(claims))
    }
}

4

Refresh Token Rotation

Refresh token은 서버 저장소(Redis/DB)와 연동하여 관리한다. 매 갱신마다 새 토큰으로 교체(rotation)하고, 이전 토큰을 무효화한다.

1 refresh token 검증 (verify()) — 서명 + 만료 확인
2 token_type == TokenType::Refresh 확인 — access token으로 갱신 불가
3 token_store.is_revoked(&jti) — Redis 블랙리스트 조회
4 token_store.revoke(&jti) — 기존 토큰 무효화 (rotation)
5 새 access + refresh 토큰 발급 및 반환
Redis TTL = token exp

안티패턴

JWT 인증 구현에서 반복되는 보안 실수와 올바른 대안.

Bad — Refresh token을 로컬스토리지에 저장
// 웹 클라이언트 측 코드
localStorage.setItem('refresh_token', token);
// XSS 공격으로 탈취 가능 ❌
Good — HttpOnly 쿠키 사용
// 서버에서 Set-Cookie 헤더로 설정
Set-Cookie: refresh_token=...; HttpOnly; Secure;
            SameSite=Strict; Path=/auth/refresh
// JS에서 접근 불가 ✅
Bad — 핸들러마다 토큰 직접 파싱
async fn get_user(req: Request) -> impl IntoResponse {
    // 반복 코드, 일관성 없는 에러 처리 ❌
    let token = req.headers()
        .get("Authorization")...;
    let claims = jwt.verify(token)?;
    // 모든 핸들러에 동일 패턴 반복
}
Good — AuthUser Extractor 사용
async fn get_user(
    auth: AuthUser,  // 자동 추출 + 검증 ✅
    State(state): State<AppState>,
) -> impl IntoResponse {
    let user_id = &auth.0.sub;
    // 인증 로직 없이 바로 비즈니스 처리
}
Bad — JWT를 즉시 revoke 불가로 가정
// "JWT는 stateless라 revoke 불가"
// 로그아웃 후에도 토큰 유효 ❌
// 비밀번호 변경 후에도 기존 토큰 유효 ❌
Good — jti Redis 블랙리스트
// 로그아웃 시 jti를 Redis에 추가
state.token_store.revoke(&claims.jti).await?;

// 검증 시 블랙리스트 조회
if state.token_store.is_revoked(&claims.jti).await? {
    return Err(ApiError::Unauthorized("Revoked"));
} // ✅
Gotchas 체크리스트

JWT 인증 구현 시 반복적으로 실수하는 포인트.

  • ✓ exp 필드 크로스 플랫폼 문제 — usize는 32bit에서 2038 문제가 생길 수 있다. u64나 i64로 정의하고 Validation.set_required_spec_claims(&["exp", "sub"])로 명시적 검증을 설정한다.
  • ✓ Validation::new()는 exp 자동 검증 — Validation::new(Algorithm::HS256)은 exp 검증을 자동으로 수행한다. 별도 만료 체크가 불필요하다. 보안이 중요하면 validation.leeway = 0으로 시계 오차 허용을 제거한다.
  • ✓ HMAC 시크릿 최소 32바이트 — 짧은 시크릿은 브루트포스에 취약하다. openssl rand -hex 32로 생성하고 환경 변수로 주입한다. 코드에 하드코딩 절대 금지.
  • ✓ axum-extra typed-header feature — TypedHeader를 사용하려면 axum-extra = { version = "0.10", features = ["typed-header"] }를 명시해야 한다. feature 없이 사용하면 컴파일 에러.
  • ✓ 에러 응답 세분화 — 토큰 파싱 실패, 만료, 서명 불일치를 구분하지 않고 "Unauthorized"만 반환하면 디버깅이 어렵다. 서버 로그에는 상세 에러를, 응답에는 일반 메시지를 반환한다.
