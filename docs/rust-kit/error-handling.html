에러 처리 원칙

Rust의 에러 처리는 Result<T, E>로 표현된다. panic은 복구 불가능한 프로그래밍 오류에만 사용하고, 예상 가능한 실패는 모두 Result로 전파한다. 라이브러리 크레이트와 애플리케이션 크레이트는 에러 전략이 다르다.

핵심 원칙
1

라이브러리는 thiserror, 앱은 anyhow

Crate Split

두 크레이트는 목적이 다르다. thiserror는 호출자가 매칭할 수 있는 구체 에러 타입을 생성한다. anyhow는 컨텍스트를 추가하며 빠르게 전파할 때 사용한다.

// 라이브러리 — thiserror
#[derive(Debug, thiserror::Error)]
pub enum DomainError {
    #[error("user not found: {id}")]
    NotFound { id: UserId },
    #[error("persistence error: {0}")]
    Persistence(String),
    #[error("validation failed: {field} — {reason}")]
    Validation { field: String, reason: String },
}

// 애플리케이션 — anyhow
fn main() -> anyhow::Result<()> {
    let config = Config::load()
        .context("config 로드 실패")?;
    run(config).await
}

// Handler: DomainError → HTTP 응답 (axum)
impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        let (status, body) = match self {
            ApiError::Domain(DomainError::NotFound { .. })
                => (StatusCode::NOT_FOUND, "not found"),
            ApiError::Domain(DomainError::Validation { .. })
                => (StatusCode::UNPROCESSABLE_ENTITY, "validation error"),
            _ => (StatusCode::INTERNAL_SERVER_ERROR, "internal error"),
        };
        (status, body).into_response()
    }
}

?와 From impl로 보일러플레이트 제거

From Conversion

From<E1> for E2가 구현되면 ?가 자동 변환한다. #[from] 속성(thiserror)으로 From impl을 자동 생성할 수 있다.

#[derive(Debug, thiserror::Error)]
pub enum DomainError {
    #[error("db error: {0}")]
    Db(#[from] sqlx::Error),   // From<sqlx::Error> 자동 생성
    #[error("io error: {0}")]
    Io(#[from] std::io::Error),
}

async fn load_user(id: UserId, pool: &PgPool)
    -> Result<User, DomainError>
{
    let row = sqlx::query_as!(UserRow, "SELECT * FROM users WHERE id = $1", id.0)
        .fetch_one(pool)
        .await?; // sqlx::Error → DomainError::Db 자동 변환
    Ok(row.into())
}

에러 컨텍스트를 보존한다

Error Context

에러 메시지만으로는 원인 파악이 어렵다. .context() (anyhow) 또는 #[error("... {source}")] (thiserror)로 원인 체인을 유지한다.

// anyhow — 컨텍스트 추가
let user = repo.find(id).await
    .context(format!("user {id} 조회 실패"))?;

// 에러 로깅
tracing::error!(error = %err, "요청 처리 실패");  // Display
tracing::error!(error = ?err, "요청 처리 실패");  // Debug (cause chain)
수치 기준

에러 처리 방식별 런타임 비용. 에러 경로는 hot path가 아니므로 성능보다 명확성이 우선이다.

항목 기준값 비고
Result<T, E> 반환 오버헤드~0ns값 크기만큼 스택 이동. 인라인 최적화
Box<dyn Error> (anyhow)~1 힙 할당에러 경로에서만 발생. 정상 경로 영향 없음
unwrap() panic 비용프로세스 종료에러 경로에서 사용 금지
From 변환 (#[from])~0ns인라인 컴파일. 런타임 비용 없음
thiserror derive 컴파일 추가 시간~무시 가능proc-macro, 한 번만 실행
안티패턴

에러 처리에서 자주 범하는 실수 패턴.

Bad — .unwrap() 프로덕션 코드
// ❌ 서비스 코드에서 프로세스 종료
let user = repo.find(id).await.unwrap();
let config = Config::load().expect("failed");
Good — ? 연산자로 전파
// ✅ 호출자에게 에러 위임
let user = repo.find(id).await
    .context("user 조회 실패")?;
let config = Config::load()?;
Bad — 에러를 String으로 변환
// ❌ 호출자가 에러 종류 매칭 불가
DomainError::Persistence(e.to_string())
Good — 구조체 variant 보존
// ✅ 원본 에러를 source로 유지
DomainError::Db(#[from] sqlx::Error)
// 또는 source 필드로 체이닝
Bad — 라이브러리에 anyhow 사용
// ❌ 호출자가 에러 종류를 알 수 없음
pub fn find_user(id: u32)
    -> anyhow::Result<User> { ... }
Good — 구체 에러 타입 노출
// ✅ 타입 정보 보존
pub fn find_user(id: UserId)
    -> Result<User, DomainError> { ... }
Bad — 에러를 조용히 삼키기
// ❌ 에러 발생 여부를 알 수 없음
let value = result.unwrap_or_default();
Good — 로그에 남기거나 전파
// ✅ 에러를 명시적으로 처리
let value = result.unwrap_or_else(|e| {
    tracing::warn!(error = ?e, "fallback 사용");
    Default::default()
});
Gotchas

컴파일러가 알려주지 않는 에러 처리 함정.

  • !
    #[from]과 수동 From impl이 충돌한다
    thiserror #[from]이 있으면 동일한 From<E>를 수동으로 작성하면 "conflicting implementations" 컴파일 에러가 발생한다. 둘 중 하나만 사용한다.
  • !
    IntoResponse에서 민감 정보 노출 주의
    DomainError를 직접 HTTP 응답 body에 포함하면 내부 DB 쿼리, 스택 트레이스가 클라이언트에 노출된다. 반드시 별도 ApiError로 변환하고 추상적 메시지만 반환한다.
  • !
    tokio::spawn 내부의 ?는 태스크 내에서 에러가 소실된다
    JoinHandle의 반환값을 .await하고 에러를 명시적으로 처리해야 한다. fire-and-forget으로 두면 패닉이 조용히 사라진다.
  • !
    에러 타입이 Send + Sync를 구현하지 않으면 tokio task에서 사용 불가
    Arc<dyn Error>를 tokio task 간에 전달하려면 에러가 Send + Sync여야 한다. Box<dyn Error> 대신 Box<dyn Error + Send + Sync>를 사용한다.
