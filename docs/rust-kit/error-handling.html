에러 처리 원칙

Rust의 에러 처리는 Result<T, E>로 표현된다. panic은 복구 불가능한 프로그래밍 오류에만 사용하고, 예상 가능한 실패는 모두 Result로 전파한다. 라이브러리 크레이트와 애플리케이션 크레이트는 에러 전략이 다르다.

핵심 원칙

원칙 1~4는 에러를 어떻게 표현하고 전파할지를, 원칙 5는 애초에 에러가 될 수 없는 상태를 어떻게 타입에서 지울지를 다룬다.

1

라이브러리는 thiserror, 앱은 anyhow

Crate Split

두 크레이트는 목적이 다르다. thiserror는 라이브러리(domain, adapters) 전용으로, 호출자가 매칭할 수 있는 구체 에러 타입을 생성한다. anyhow는 애플리케이션 바이너리(main.rs, CLI, scripts) 전용으로, 타입 정보를 버리는 대신 컨텍스트를 얹어 빠르게 전파한다.

// 라이브러리 — thiserror
#[derive(Debug, thiserror::Error)]
pub enum DomainError {
    #[error("user not found: {id}")]
    NotFound { id: UserId },
    #[error("persistence error: {0}")]
    Persistence(String),
    #[error("validation failed: {field} — {reason}")]
    Validation { field: String, reason: String },
}

// 애플리케이션 — anyhow
fn main() -> anyhow::Result<()> {
    let config = Config::load()
        .context("config 로드 실패")?;
    run(config).await
}

3계층 에러 변환: Infra → Domain → API

Error Boundary

에러는 계층 경계에서 변환된다. 하위 계층의 에러 타입이 상위 계층에 그대로 노출되면 의존성 역전이 발생한다.

// Handler: DomainError → HTTP 응답 (axum)
impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        let (status, body) = match self {
            ApiError::Domain(DomainError::NotFound { .. })
                => (StatusCode::NOT_FOUND, "not found"),
            ApiError::Domain(DomainError::Validation { .. })
                => (StatusCode::UNPROCESSABLE_ENTITY, "validation error"),
            _ => (StatusCode::INTERNAL_SERVER_ERROR, "internal error"),
        };
        (status, body).into_response()
    }
}

3

?와 From impl로 보일러플레이트 제거

From Conversion

From<E1> for E2가 구현되어 있으면 ?가 자동으로 변환한다. thiserror의 #[from] 속성으로 From impl을 자동 생성할 수 있다.

#[derive(Debug, thiserror::Error)]
pub enum DomainError {
    #[error("db error: {0}")]
    Db(#[from] sqlx::Error),   // From<sqlx::Error> 자동 생성

    #[error("io error: {0}")]
    Io(#[from] std::io::Error),
}

async fn load_user(id: UserId, pool: &PgPool)
    -> Result<User, DomainError>
{
    let row = sqlx::query_as!(UserRow, "SELECT * FROM users WHERE id = $1", id.0)
        .fetch_one(pool)
        .await?; // sqlx::Error → DomainError::Db 자동 변환
    Ok(row.into())
}

4

에러 컨텍스트를 보존한다

Error Context

에러 메시지만으로는 원인 파악이 어렵다. .context()(anyhow) 또는 #[error("... {source}")](thiserror)로 원인 체인을 유지한다. 로그에 남길 때는 {:?}(Debug, cause chain 포함)를 사용한다.

// anyhow — 컨텍스트 추가
let user = repo.find(id).await
    .context(format!("user {id} 조회 실패"))?;

// 에러 로깅
tracing::error!(error = %err, "요청 처리 실패");  // Display
tracing::error!(error = ?err, "요청 처리 실패");  // Debug (cause chain)

5

불가능한 상태는 타입으로 제거한다 (치환보다 설계)

Parse, Don't Validate

프로덕션 .unwrap()/.expect()를 발견했을 때 반사적으로 ?로 바꾸면, “여기서는 절대 None일 리 없다”는 자리는 그대로 남는다. 검증 결과를 버리고 넓은 타입을 계속 들고 다니면 같은 검증을 아래층에서 다시 하게 되고, 그 자리에 panic이 생긴다.

// ✗ 치환 — 넓은 타입이 그대로 남는다
fn send(to: &str) -> Result<(), Error> {
    let addr = parse_email(to).ok_or(Error::BadEmail)?;  // 호출부마다 반복
    ...
}

// ✓ 설계 — 한 번 파싱하면 이후 층은 검증이 필요 없다
pub struct Email(String);            // 필드 private
impl Email {
    pub fn parse(s: &str) -> Result<Self, ParseError> { ... }
}
fn send(to: &Email) { ... }          // 불변식이 타입에 있다
↗ parse, don't validate ↗ nonempty ↗ typestate
상황별 설계 수단 — 원칙 5

상황설계 수단

강제는 lint 로 한다 — 문장 규칙만으로는 재발한다

2026-08-12 실측(AP-05)에서 확인된 사항이다. 워크스페이스 lint 테이블에 deny 로 박아 빌드가 막히게 한다.

# Cargo.toml (workspace root)
[workspace.lints.clippy]
unwrap_used         = "deny"
expect_used         = "deny"
panic               = "deny"
panic_in_result_fn  = "deny"
↗ clippy — unwrap_used

해법이 아닌 것

  • ✕
    unwrap_or_default() 치환 — 에러가 조용히 사라진다.
  • ✕
    “더 좋은 메시지의 expect” — 여전히 프로세스가 죽는다.
  • ✕
    파일 단위 #[allow(...)] — 게이트를 통째로 무력화한다.
  • ✕
    clippy::restriction 그룹 전체 deny — 서로 모순되는 lint 가 섞여 빌드가 못 돈다.

안티패턴

에러 처리에서 자주 범하는 실수 패턴. 왼쪽이 실제로 관측된 코드, 오른쪽이 정본이다.

Bad — .unwrap() / .expect() 를 프로덕션에 남기기
// ✗ 서비스 코드에서 프로세스 종료
let user = repo.find(id).await.unwrap();
let config = Config::load().expect("failed");

// ✗ "불가능한 상황이니 괜찮다" 주석
//    → 그 상태가 아직 타입에 남아 있다는 신호
Good — main 초기화만 허용 + lint deny
// ✓ 서비스 코드는 전파
let user = repo.find(id).await
    .context("user 조회 실패")?;

// ✓ 허용 범위: 테스트 코드 + main 초기화
// ✓ 감지: clippy unwrap_used = "deny"
// ✓ 제거 순서: 원칙 5 판정표 → 타입 설계
Bad — 반사적 ? 치환으로 끝내기
// ✗ panic 은 사라졌지만 넓은 타입은 남았다
fn charge(card: &str, amount: i64)
    -> Result<(), Error>
{
    let card = validate(card).ok_or(Error::Card)?;
    // 아래층에서 또 검증한다
}
Good — 불변식을 타입으로 올리기
// ✓ 경계에서 한 번 파싱, 이후 층은 무조건 유효
pub struct CardNumber(String);
impl CardNumber {
    pub fn parse(s: &str)
        -> Result<Self, ParseError> { ... }
}
fn charge(card: &CardNumber, amount: Money) { ... }
Bad — 모든 에러를 String 으로 변환
// ✗ 호출자가 에러 종류를 매칭할 수 없다
DomainError::Persistence(e.to_string())
Good — 구조체 variant + source 보존
// ✓ 원본 에러를 source 로 유지
#[derive(Debug, thiserror::Error)]
pub enum DomainError {
    #[error("db error: {0}")]
    Db(#[from] sqlx::Error),
}
Bad — 라이브러리에 anyhow 사용
// ✗ 호출자가 에러 종류를 알 수 없음
pub fn find_user(id: u32)
    -> anyhow::Result<User> { ... }
Good — 구체 에러 타입 노출
// ✓ 타입 정보 보존 — 호출자가 match 가능
pub fn find_user(id: UserId)
    -> Result<User, DomainError> { ... }
Bad — 에러를 무시하고 기본값 반환
// ✗ 에러가 발생했는지 알 수 없음
let value = result.unwrap_or_default();
Good — 로그에 남기거나 전파
// ✓ fallback 을 쓴 사실이 관측된다
let value = result.unwrap_or_else(|e| {
    tracing::warn!(error = ?e, "fallback 사용");
    Default::default()
});
Gotchas

컴파일러가 알려주지 않는 에러 처리 함정.

  • !
    #[from]과 수동 From impl 이 충돌한다
    thiserror #[from]은 From impl 을 자동 생성한다. 동일한 From<E> impl 을 수동으로 작성하면 “conflicting implementations” 컴파일 에러가 발생한다. #[from]을 쓸 때는 수동 impl 을 제거한다.
  • !
    IntoResponse impl 에서 민감 정보 노출
    DomainError를 직접 HTTP 응답 body 에 포함하면 내부 구현(DB 쿼리, 스택 트레이스)이 클라이언트에 노출된다. API 레이어에서 별도 ApiError로 변환하고 사용자에게는 추상적인 메시지만 반환한다.
  • !
    ? 연산자는 async 클로저 안에서 주의가 필요하다
    tokio::spawn(async { some_result? }) 패턴은 에러가 spawn 된 태스크 안에서 소실될 수 있다. JoinHandle의 반환값을 .await하고 에러를 처리해야 한다.
  • !
    에러 타입이 Send + Sync를 구현하지 않으면 tokio task 에서 사용 불가
    Arc<dyn Error>를 tokio task 간에 전달하려면 에러가 Send + Sync여야 한다. thiserror derive 는 구현체가 Send + Sync이면 자동으로 만족한다. Box<dyn Error>는 기본적으로 Send + Sync가 아니므로 Box<dyn Error + Send + Sync>를 사용한다.
  • !
    lint 를 켜는 것과 지키는 것은 다르다
    unwrap_used = "deny"를 켠 뒤 파일 상단에 #[allow(clippy::unwrap_used)]를 붙이면 게이트가 무력화된다. 예외가 필요하면 표현식 단위로 좁히고 사유를 남긴다.
