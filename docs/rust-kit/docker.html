Docker

cargo-chef 0.1.x를 활용한 멀티스테이지 빌드로 Docker 레이어 캐시를 극대화한다. 의존성 레이어를 소스 레이어와 분리하여 소스만 변경될 때 의존성 재컴파일을 방지한다. 최종 이미지는 debian:bookworm-slim(glibc) 또는 scratch(musl 정적 바이너리)로 최소화한다.

빌드 구조

cargo-chef 3단계 멀티스테이지 패턴

각 스테이지가 담당하는 역할을 이해하면 캐시 전략이 명확해진다.

planner
recipe.json 생성
→
builder
의존성 + 소스 컴파일
→
runtime
바이너리만 복사
1

표준 3단계 멀티스테이지 Dockerfile (glibc / debian:slim)

의존성 레이어(cargo chef cook)가 소스 변경과 독립적으로 캐시된다. 소스만 바뀌면 마지막 cargo build만 재실행된다.

# syntax=docker/dockerfile:1

# ── 1단계: planner ──────────────────────────────────────────
FROM rust:1.87-slim AS planner
WORKDIR /app
RUN cargo install cargo-chef --locked
COPY . .
RUN cargo chef prepare --recipe-path recipe.json

# ── 2단계: builder ──────────────────────────────────────────
FROM rust:1.87-slim AS builder
WORKDIR /app
RUN cargo install cargo-chef --locked
COPY --from=planner /app/recipe.json recipe.json

# 의존성만 먼저 컴파일 (캐시 레이어)
RUN cargo chef cook --release --recipe-path recipe.json

# 소스 복사 후 최종 빌드
COPY . .
RUN cargo build --release --bin my-server

# ── 3단계: runtime ───────────────────────────────────────────
FROM debian:bookworm-slim AS runtime
WORKDIR /app

RUN apt-get update && apt-get install -y \
    ca-certificates \
    libssl3 \
    && rm -rf /var/lib/apt/lists/*

COPY --from=builder /app/target/release/my-server /usr/local/bin/my-server

EXPOSE 8080
CMD ["my-server"]

musl 정적 바이너리로 scratch 이미지 사용

OpenSSL 없는 서비스(rustls 사용)는 musl로 완전 정적 바이너리를 만들어 scratch 이미지에 넣으면 이미지 크기가 ~10MB 수준으로 줄어든다.

FROM rust:1.87-slim AS builder
WORKDIR /app
RUN rustup target add x86_64-unknown-linux-musl
RUN apt-get update && apt-get install -y musl-tools

RUN cargo install cargo-chef --locked
COPY --from=planner /app/recipe.json recipe.json
# --target 플래그를 cook과 build 모두에 동일하게 지정
RUN cargo chef cook --release \
    --target x86_64-unknown-linux-musl \
    --recipe-path recipe.json

COPY . .
RUN cargo build --release \
    --target x86_64-unknown-linux-musl \
    --bin my-server

FROM scratch AS runtime
COPY --from=builder \
    /app/target/x86_64-unknown-linux-musl/release/my-server \
    /my-server
EXPOSE 8080
ENTRYPOINT ["/my-server"]

안티패턴

흔한 실수 4가지

피해야 할 패턴

단일 스테이지 빌드

소스 한 줄이 바뀌어도 모든 의존성을 재컴파일한다. CI에서 매번 5~10분이 걸린다.

올바른 패턴

cargo-chef 3단계 패턴

의존성 레이어를 캐시하면 소스 변경 시 cargo build 단계만 재실행된다. 반복 빌드가 수십 초로 줄어든다.

피해야 할 패턴

수동 Cargo.toml 복사 패턴

COPY Cargo.toml Cargo.lock ./ 후 더미 src/main.rs를 만드는 수동 패턴은 workspace 구조에서 쉽게 깨진다.

올바른 패턴

cargo-chef가 더 안정적

cargo chef prepare가 workspace 전체를 분석해 정확한 의존성 그래프를 생성한다. workspace 구조 변경에 자동 대응한다.

피해야 할 패턴

.dockerignore에 target/ 누락

로컬 빌드 후 Docker 빌드를 실행하면 수 GB의 target/이 빌드 컨텍스트에 포함되어 전송 시간이 급격히 증가한다.

올바른 패턴

.dockerignore 첫 줄에 target/ 추가

.dockerignore의 첫 줄에 target/을 추가한다. 빌드 컨텍스트 크기가 수 MB 수준으로 줄어든다.

피해야 할 패턴

runtime stage에 빌드 도구 포함

rust:latest를 runtime image로 사용하면 이미지 크기가 1GB 이상이 된다.

올바른 패턴

바이너리만 slim/scratch로 복사

COPY --from=builder로 바이너리만 debian:slim 또는 scratch로 복사한다. 빌드 도구는 runtime에 불필요하다.

Gotchas

반드시 알아야 할 함정

  • ✓
    cargo chef cook과 cargo build의 --target 플래그를 일치시켜야 한다
    musl 빌드 시 cargo chef cook --target x86_64-unknown-linux-musl과 cargo build --target x86_64-unknown-linux-musl을 동일하게 설정해야 캐시가 유효하다. 플래그가 다르면 캐시가 무효화된다.
  • ✓
    OpenSSL vs rustls 선택
    debian:slim 런타임에서 OpenSSL 링크 에러가 나면 libssl-dev 설치 또는 rustls feature로 전환한다. sqlx의 경우 runtime-tokio-rustls feature를 사용하면 OpenSSL 의존성이 없어진다.
  • ✓
    cargo install cargo-chef --locked의 --locked가 중요하다
    --locked가 없으면 최신 버전으로 업그레이드될 수 있고, planner/builder 단계 간 버전 불일치가 발생한다. 두 단계 모두 동일한 --locked 명령으로 설치한다.
  • ✓
    workspace 구조에서 COPY . . 위치가 중요하다
    cargo chef prepare는 전체 workspace를 스캔한다. COPY . . 이전에 일부 파일만 복사하면 recipe.json이 불완전하게 생성된다.
