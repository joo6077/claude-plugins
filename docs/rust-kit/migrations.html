마이그레이션 원칙

sqlx migrate는 SQL 파일 기반의 데이터베이스 마이그레이션 도구다. sqlx::migrate!() 매크로로 앱 시작 시 자동 실행하거나 sqlx-cli로 수동 관리한다.

핵심 원칙

마이그레이션 파일 명명, reversible 분리, 자동 실행, CI 검증 4가지 원칙.

1

타임스탬프 접두사 네이밍

sqlx migrate add <name> 명령이 현재 시각 기반 타임스탬프를 자동으로 붙인다. 숫자 오름차순이 실행 순서를 결정한다.

migrations/
  20240101000000_create_users.sql
  20240102000000_create_posts.sql
  20240103000000_add_user_roles.sql
# 자동 타임스탬프 생성
sqlx migrate add create_users
# → migrations/20240101000000_create_users.sql
YYYYMMDDHHmmss
2

Reversible 마이그레이션 — up/down 분리

-r 플래그로 reversible 마이그레이션을 생성하면 .up.sql과 .down.sql이 한 쌍으로 생성된다.

sqlx migrate add -r create_users
# migrations/20240101000000_create_users.up.sql
# migrations/20240101000000_create_users.down.sql
-- .up.sql
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email TEXT NOT NULL UNIQUE,
    name TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at TIMESTAMPTZ
);
CREATE INDEX idx_users_email ON users(email);

-- .down.sql
DROP TABLE IF EXISTS users;
-r flag
3

앱 시작 시 자동 마이그레이션

sqlx::migrate!()는 ./migrations를 기본 경로로 사용한다. 경로는 Cargo.toml 위치 기준이다.

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let pool = PgPoolOptions::new()
        .connect(&env::var("DATABASE_URL")?)
        .await?;

    // migrations/ 디렉토리의 SQL을 순서대로 실행
    sqlx::migrate!("./migrations")
        .run(&pool)
        .await?;

    // 라우터 시작...
    Ok(())
}

// 워크스페이스 구조에서 절대 경로 사용
sqlx::migrate!(
    concat!(env!("CARGO_MANIFEST_DIR"), "/migrations")
)
CARGO_MANIFEST_DIR 기준
4

CI — cargo sqlx prepare --check

.sqlx/ 디렉토리를 git에 커밋하면 DB 없이 cargo build가 가능하다. CI에서 --check로 드리프트를 감지한다.

1 개발 환경: cargo sqlx prepare 실행 → .sqlx/ 캐시 생성
2 git add .sqlx/ && git commit — 캐시 커밋
3 CI: cargo sqlx prepare --check — 캐시가 최신인지 검증
4 CI: SQLX_OFFLINE=true cargo build — DB 없이 빌드

안티패턴

마이그레이션 작업에서 반복되는 실수와 올바른 대안.

Bad — 기존 마이그레이션 파일 수정
-- 20240101000000_create_users.sql 수정
-- 컬럼 추가를 위해 기존 파일 편집 ❌
CREATE TABLE users (
    id UUID PRIMARY KEY,
    email TEXT NOT NULL,
    new_column TEXT  -- 나중에 추가
);
-- 체크섬 불일치로 실행 거부됨
Good — 새 마이그레이션 파일 추가
# 변경은 새 파일로 ✅
sqlx migrate add add_new_column_to_users

-- 20240105000000_add_new_column_to_users.sql
ALTER TABLE users ADD COLUMN new_column TEXT;
-- 기존 체크섬 유지, 새 변경만 추가
Bad — 프로덕션에서 migrate revert
# .down.sql이 DROP TABLE을 포함할 수 있음
sqlx migrate revert  # ❌ 데이터 삭제 위험

# 백업 없이 실행 → 복구 불가
# 확인 없이 실행 → 운영 데이터 손실
Good — 백업 + 수동 검토 후 실행
# 1. DB 백업 먼저
pg_dump $DATABASE_URL > backup.sql

# 2. .down.sql 내용 직접 확인
cat migrations/20240101000000_*.down.sql

# 3. 스테이징에서 먼저 테스트
# 4. 검토 후 프로덕션 실행 ✅
Bad — 하나의 파일에 너무 많은 변경
-- 20240101000000_initial_setup.sql
CREATE TABLE users (...);
CREATE TABLE posts (...);
CREATE INDEX ...;
INSERT INTO roles VALUES (...);  -- 데이터 마이그레이션도
-- 롤백 범위가 너무 큼 ❌
Good — 논리적 단위로 분리
-- 20240101000000_create_users.sql
CREATE TABLE users (...);

-- 20240102000000_create_posts.sql
CREATE TABLE posts (...);

-- 20240103000000_seed_roles.sql
INSERT INTO roles VALUES (...);
-- 각각 독립적으로 롤백 가능 ✅
Gotchas 체크리스트

마이그레이션 작업 시 반복적으로 실수하는 포인트.

  • ✓ migrate!() 경로는 Cargo.toml 기준 — ./migrations는 현재 실행 디렉토리가 아니라 Cargo.toml이 있는 크레이트 루트 기준이다. 워크스페이스 구조에서는 concat!(env!("CARGO_MANIFEST_DIR"), "/migrations")를 사용한다.
  • ✓ _sqlx_migrations 테이블 자동 생성 — 마이그레이션 추적 테이블은 sqlx가 자동으로 만든다. 별도로 생성하거나 수동으로 관리하지 않는다.
  • ✓ CLI와 코드 혼용 가능 — sqlx migrate run(CLI)과 sqlx::migrate!()(코드) 모두 같은 _sqlx_migrations 테이블을 공유한다. 두 방식을 혼용해도 중복 실행되지 않는다.
  • ✓ reversible/non-reversible 혼용 금지 — 프로젝트 내에서 한 가지 방식으로 통일한다. 혼용하면 revert가 non-reversible 파일에서 실패한다.
  • ✓ 체크섬 검증은 변경 불가 — sqlx는 실행된 마이그레이션 파일의 체크섬을 저장한다. 기존 파일을 수정하면 체크섬 불일치로 이후 모든 마이그레이션 실행이 거부된다.
