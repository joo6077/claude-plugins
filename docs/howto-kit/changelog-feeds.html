Changelog Feeds — 무엇을 폴링해 최신성을 지킬 것인가

절차 안내 문서는 만든 순간부터 낡는다. 콘솔 라벨이 바뀌고 메뉴가 옮겨간다. 이 페이지는 그 변화를 언제 알아챌 것인가에 답한다 — 각 벤더 변경 로그의 기계 판독 주소와, 그 주소가 지금 실제로 무엇을 돌려주는지의 실측 기록이다. 조회일 2026-09-09

이 표의 값은 “벤더가 그렇게 적었다”가 아니다

포맷 판정은 전부 응답 본문의 루트 엘리먼트에서 읽었다. 벤더 문서가 “RSS 를 제공한다”고 적었다는 사실은 근거로 쓰지 않았다 — 실제로 Google Cloud 는 Atom 인데 text/xml 로 내려온다. Content-Type 을 믿었으면 파서를 잘못 골랐을 것이다.

그리고 이 표 자체가 낡는다. 인용하기 전에 다시 조회하라 — 아래 §1.1 의 호스트 이전이 그 증거다.

확정된 폴링 대상 5건

조회일 2026-09-09. 포맷 열은 응답 본문 루트 엘리먼트 기준이고, Content-Type 열은 응답 헤더 원문이다. 두 열이 어긋나는 행이 있다는 것이 이 표의 핵심이다.

AWS 는 2026-09-08 원장에 없던 신규 확정이다. Google Cloud 의 서브타입(Atom vs RSS)은 그때 미확정으로 남아 있다가 이번에 해소됐다.

각 피드가 지금 무엇을 싣고 있나

조회 시점에 각 피드의 첫 항목이다. 폴링 구현이 파싱 대상으로 삼을 필드가 피드마다 다르다는 것을 보여준다 — Atom 은 <updated>, RSS 는 <pubDate> 다.

Google Cloud 는 날짜를 엔트리 제목으로 쓴다. 제목에서 변경 내용을 뽑으려는 파서는 이 피드에서 아무것도 얻지 못한다.

판정 규칙 4가지

아래 넷은 모두 이번 조사에서 실제로 틀릴 뻔한 지점에서 나왔다. 일반론이 아니라 실측 반례가 각각 하나씩 붙어 있다.

1

포맷은 Content-Type 이 아니라 루트 엘리먼트로 판정한다

Google Cloud 피드는 text/xml 로 내려오지만 본문 루트는 Atom 이다. Content-Type 으로 파서를 고르면 RSS 파서를 물려 아무 항목도 못 읽는다. 헤더는 힌트이지 계약이 아니다.

<?xml version="1.0" encoding="UTF-8"?>
<!-- AUTOGENERATED FILE. DO NOT EDIT. -->
<feed xmlns="http://www.w3.org/2005/Atom">
  <id>tag:google.com,2016:gcp-release-notes</id>
  <title>Google Cloud Platform (GCP) - Release notes</title>
Atom 인데 text/xml
출처
docs.cloud.google.com/feeds/gcp-release-notes.xml (조회 2026-09-09)
2

리다이렉트를 따라라 — 양방향으로 함정이다

구 호스트 cloud.google.com/feeds/gcp-release-notes.xml 은 죽지 않았다. 301 로 docs.cloud.google.com 에 넘긴다 — 리다이렉트를 안 따르는 클라이언트만 빈 응답을 받는다. 반대 함정도 있다: Azure 의 /updates/feed/ 는 301 로 피드가 아닌 HTML 에 데려간다.

$ curl -sSLD - https://cloud.google.com/feeds/gcp-release-notes.xml
HTTP/2 301
location: https://docs.cloud.google.com/feeds/gcp-release-notes.xml
HTTP/2 200
content-type: text/xml
301 → 피드301 → HTML
출처
cloud.google.com/feeds/gcp-release-notes.xml — 301 확인 (2026-09-09) azure.microsoft.com/en-us/updates/feed/ — HTML 로 리다이렉트 (2026-09-09)
3

200 을 피드 존재로 읽지 마라

firebase.google.com/support/releases.xml 은 200 을 돌려준다. 그런데 Content-Type 이 text/html 이고 본문이 <html lang="en"> 로 시작한다 — 문서 사이트가 미지의 경로에 그냥 페이지를 내주는 soft 200 이다. 상태 코드만 보는 탐색기는 여기서 “피드 발견”을 보고한다.

✗ 상태 코드만 본다
200 → "피드 있음"
✓ 본문까지 본다
200 + text/html
+ <html> → soft 200
출처
firebase.google.com/support/releases — HTML changelog (조회 2026-09-09)
4

피드가 없는 대상은 HTML 폴링으로 내린다

없는 피드를 있다고 적는 것보다, HTML 을 긁는 비용을 감수하는 편이 낫다. 폴링 대상에서 아예 빼는 것이 최악이다 — 그러면 그 벤더의 변경은 영영 감지되지 않는다.

내림 순서 — 기계 판독 피드 → 공식 HTML changelog → (그것도 없으면) 문서 최종 수정일. 어느 단계로 내렸는지를 문서에 적는다.
출처
docs.stripe.com/changelog — HTML changelog (조회 2026-09-09)
이번 조사가 무효화한 판정 방법

HTML 문서의 <link rel="alternate" type="application/rss+xml"> 는 피드를 찾는 관례적 수단이다. 그래서 “이 페이지에 autodiscovery 가 없으니 피드도 없다” 는 추론이 자연스러워 보인다. AWS 가 그 추론의 반례다.

✗ 틀린 추론피드를 놓친다
$ curl -sSL https://aws.amazon.com/new/ \
  | grep -c 'rel="alternate".*rss'
0

→ "AWS 는 RSS 피드가 없다"
✓ 실제피드는 살아 있다
$ curl -sSLD - \
  https://aws.amazon.com/about-aws/whats-new/recent/feed/
content-type: application/rss+xml;charset=UTF-8
<rss version="2.0"><channel>
  <title>Recent Announcements</title>

그러므로 Firebase 와 Stripe 도 autodiscovery 부재를 근거로 “피드 없음”이라 쓰지 않는다. 셋 다 [미확인] 이며, 근거는 “찾지 못했다”이지 “없다”가 아니다. 이 구분이 이 킷의 존재 이유다.

Azure 의 403 은 부재 증명이 아니다

releasecommunications 엔드포인트는 접근이 차단됐을 뿐이고, 다른 네트워크나 인증 상태에서는 열릴 수 있다. 그래서 “Azure 는 피드가 없다”가 아니라 [미확인] 이다. /updates/feed/ 도 죽은 것이 아니라 HTML 로 리다이렉트된다 — 과거에 피드였던 주소가 지금은 페이지 쿼리로 넘어가는 형태다.

폴링 운영 체크리스트

이 문서를 인용해 폴링을 구현하거나 표를 갱신할 때 순서대로 확인한다.

  • 1포맷을 루트 엘리먼트로 판정했는가. Content-Type 으로 판정하지 않았는가 (§판정 규칙 1)
  • 2리다이렉트를 따라갔는가. 최종 URL 과 최종 Content-Type 을 둘 다 기록했는가 (§판정 규칙 2)
  • 3200 응답의 본문 첫 바이트를 확인했는가. soft 200 을 피드로 세지 않았는가 (§판정 규칙 3)
  • 4확인 실패를 “없음”으로 승격하지 않았는가. autodiscovery 부재는 근거가 못 된다 — AWS 반례
  • 5차단(403)과 부재를 구분해 적었는가
  • 6이 표의 URL 을 조회일 단서 없이 사실로 인용하고 있지 않은가. 인용 전에 다시 조회하라
조회 기록
2026-09-08 · 1차 Codex 위임 (read-only) 4건 확정 · 3건 확인 실패
2026-09-09 · 2차 Codex + 로컬 curl 보강 5건 확정 · 3건 확인 실패

2 차 사이클의 Codex 위임(MODE=research · read-only · foreground · 검색 하드캡 20)은 정상 완주했다 — rollout 로그의 turn_aborted 가 0 건이다. 다만 Codex 샌드박스는 DNS 가 막혀 XML 원문을 열지 못해 루트 엘리먼트와 Content-Type 을 전부 확인 실패로 반환했다. 부족분은 세션 로컬 curl 로 피드 원문을 직접 조회해 채웠다.
