Deprecation Policy — 출처보다 강한 주장을 막는 단계 구분

절차 문서가 “이 방식은 지원 종료됐다”고 쓸 때 그 주장이 1 차 출처보다 강하면 날조다. 권장하지 않음 을 deprecated 로, deprecated 를 제거됨 으로 올리는 것이 전형적인 형태다. 조회일 2026-09-10

설계 브리프가 확인 실패로 남겨 둔 항목이다

§11-4 — “Google Cloud 정책 문서 안에서 용어를 각각 정의한 문장과 Apple 의 동등한 정의를 확인하지 못했다. 3 단계 구분은 AWS · Amazon SP-API 근거로 세웠다.”

이번 사이클이 Google Cloud 를 해소했고 Apple 은 여전히 확인 실패다.

3 단계 — 각 단계에 1 차 출처가 있다
단계정의 원문출처
deprecated“Deprecated indicates that the resource is no longer in active development as of the deprecation date.” — 호출은 아직 된다Amazon SP-API
sunset / shutdown“Sunset services have a sunset time line (typically 12 months). The sunset date is the date AWS will end operations and support of the service.”AWS
removed“Removed indicates that calls to the resources fail as of the removal date.”Amazon SP-API

Google Cloud 도 같은 전이를 정의한다 — 이번에 확인

“After a service, feature, or product is officially deprecated, it continues to be available for at least the period of time defined in the Terms of Service. After this period of time, the service is scheduled for shutdown.”

출시 단계 정의에서 removed 까지 잇는다 — “Deprecated features are scheduled to be shut down and removed.”

출처
docs.cloud.google.com/service-usage/docs/deprecations (조회 2026-09-10) cloud.google.com/products (조회 2026-09-10)
권장하지 않음 ≠ deprecated ≠ 제거됨. 1 차 출처가 deprecated 라고 말하지 않은 것을 deprecated 로 쓰지 마라.
통지 기간 — 약속과 관행은 다르다

두 벤더 모두 “12 개월”이라는 숫자를 쓴다. 그런데 강도가 다르다.

AWS“보통 12 개월”“12 개월이 보장됩니다” — 출처보다 강한 주장

영문한국어 공식 표기

“지원 중단됨 — 지원 중단된 기능은 서비스 종료 및 삭제가 예정된 기능입니다.”

deprecated 를 지원 종료 로 옮기면 한 단계 올려 말하는 것이다. Google Cloud 기준으로 지원 종료 에 대응하는 영문은 shut down 이고, deprecated 는 지원 중단됨 이다.

G4 게이트의 false negative — 이번에 고쳤다

위 매핑이 게이트 결함을 드러냈다. howto-gate.sh 의 deprecation 토큰 목록에 삭제 계열이 없었다. 그래서 한국어 1 차 출처를 그대로 옮긴 삭제 예정 주장은 근거가 없어도 통과했다.

수정 전
  근거 없는 "삭제 예정" 주장   G4_DEPRECATION PASS unsourced_claims=0   ← 놓친다

수정 후 (토큰 '삭제 예정|삭제가 예정' 추가)
  근거 없는 "삭제 예정" 주장   G4_DEPRECATION FAIL unsourced_claims=1   ← 잡는다
  같은 주장 + 출처 뒷받침      G4_DEPRECATION PASS unsourced_claims=0
  정상 "계정을 삭제한다" 절차   G4_DEPRECATION PASS unsourced_claims=0

왜 삭제 를 단독 토큰으로 넣지 않았나

세 번째 줄이 그 이유다. 단독으로 넣으면 계정 삭제 · 파일 삭제 같은 정상 액션이 deprecation 주장으로 오탐된다 — 실측 unsourced_claims=2. 좁은 형태(삭제 예정 · 삭제가 예정)만 넣어야 양성만 잡고 정상 절차는 통과한다.

세 케이스는 howto-kit/evals/fixtures/ 에 픽스처로 커밋했고 evals.json 에 등록했다 (E10 · E11 · E12).

단계별로 절차 문서에 뭐라고 쓰나

같은 기능이라도 지금 어느 단계인가에 따라 사용자가 할 일이 다르다. 단계를 올려 말하면 아직 쓸 수 있는 것을 못 쓰게 만들고, 내려 말하면 곧 깨질 것을 계속 쓰게 만든다.

단계지금 상태절차 문서에 쓸 문장사용자가 할 일
deprecated 호출은 아직 된다. 신규 개발만 멈춤 “이 방식은 지원 중단됐습니다. 아직 동작하지만 신규 등록에는 쓰지 마세요.” 새로 만들 때만 피한다
sunset / shutdown 종료일이 정해졌다 “<날짜> 에 종료됩니다. 그전에 <대체> 로 옮기세요.” 기한 안에 마이그레이션
removed 호출이 실패한다 “이 방식은 제거됐습니다. <대체> 를 쓰세요.” 즉시 전환 (선택지 없음)

단계를 올려 말하면

✗ 출처보다 강함아직 쓸 수 있는데 막는다
출처: "no longer in active
      development"  (deprecated)

문서: "이 API 는 제거됐으니
      쓸 수 없습니다"
✓ 출처와 같은 강도
문서: "이 API 는 지원 중단됐습니다.
      호출은 아직 되지만 신규
      개발에는 쓰지 마세요"

단계를 내려 말하면

✗ 곧 깨진다기한을 안 알려준다
출처: sunset date 명시됨

문서: "권장하지 않는 방식입니다"
✓ 기한을 준다
문서: "<날짜> 에 종료됩니다.
      그전에 <대체> 로 옮기세요"
판정 규칙 — 출처 문장에 날짜가 있으면 최소 sunset 이다. “fail” / “removed” 가 있으면 removed 다. 둘 다 없고 “no longer in active development” 계열이면 deprecated 에서 멈춰라. 출처에 없는 단계로 올리지 마라.
Apple — [미확인]

Apple 은 개별 API · 기능 종료 공지는 제공하지만, AWS · Amazon SP-API · Google Cloud 처럼 단계를 정의한 일반 lifecycle 정책 문서를 확보하지 못했다.

킷의 처리 — Apple 을 단계 정의의 근거로 인용하지 않는다. Apple 절차에서 deprecation 을 말해야 하면 그 기능의 개별 공지 페이지를 출처로 달아라.

시도한 URL 은 howto-kit/references/provenance-notes.md §8 에 원장으로 남아 있다. not recommended 를 Google Cloud 가 별도 공식 용어로 정의한 문장도 확인 실패다.

검증 함정 4번째 — 공백 정규화

인용 8 건을 세션 로컬 조회로 대조했다. 그중 Google Cloud deprecations 인용이 raw 대조에서 MISS 였다.

정정 — 원인을 처음에 잘못 짚었다

이 사이클은 처음에 원인을 HTML 엔티티로 적었다. QA 가 재현되지 않는다고 지적해 다시 확인한 결과 원인이 달랐다 — 엔티티가 아니라 원문의 줄바꿈과 들여쓰기였다.

찾은 문자열:  defined in the Terms of Service
응답 본문:    defined in the\n  Terms of Service.

HTML 은 줄바꿈과 들여쓰기를 렌더링에서 공백 하나로 접지만 grep -F 에는 그대로 남는다. 문장이 두 줄에 걸치면 리터럴 대조가 실패한다.

이제 이 킷이 아는 검증 함정은 네 가지다.

함정증상대응
HTML 엔티티you&#39;re 가 you're 로 안 잡힘엔티티 디코드 후 대조
공백 정규화 신규문장이 줄바꿈으로 갈려 안 잡힘태그 제거 + \s+ → 공백 하나
SPAHTML 이 껍데기뿐문서 데이터 API
PDF폰트 서브셋으로 정규식 불가pdftotext 추출
이번 사례가 하나를 더 가르쳐 준다 — 실패 원인을 짚을 때도 그것을 재현해 보고 적어라. 원인을 잘못 짚으면 다음 사람이 엉뚱한 도구를 쓴다.

알려진 잔여 오탐 — 삭제 예정

QA 가 적대적 탐색으로 찾았다. “30일 지난 데이터를 삭제 예정입니다” 같은 데이터 보존 정책 문구도 G4_DEPRECATION FAIL 로 잡힌다. 다만 게이트가 요구하는 것은 “그 주장에 출처를 달라”이고 보존 기간도 출처가 필요한 사실 주장이므로, 동작은 방어 가능하고 분류 라벨이 부정확한 상태로 남겨 둔다. 종료 예정 · 폐지 예정 단독형은 여전히 미탐이다 (기존 갭, 범위 밖).

deprecation 서술 체크리스트
  • 11 차 출처가 쓴 단계 그대로 옮겼는가. 권장하지 않음 을 deprecated 로 올리지 않았는가
  • 2통지 기간을 쓴다면 그것이 약관상 약속인지 관행 서술인지 구분했는가
  • 3Google Cloud 의 12 개월을 인용할 때 대체 서비스 예외 단서를 함께 적었는가
  • 4한국어로 옮길 때 deprecated → 지원 중단됨, shut down → 지원 종료 / 서비스 종료 매핑을 지켰는가
  • 5Apple 절차에서 단계를 말한다면 개별 공지 페이지를 출처로 달았는가. 일반 정책은 존재를 확인하지 못했다
