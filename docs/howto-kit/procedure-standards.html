Procedure Standards — 스텝 하나를 어떻게 쓰라고 하는가

이 킷의 Step Contract 는 DITA 1.3 을 뼈대로 삼는다. 이 페이지는 그 인용이 실제로 표준에 있는지, 그리고 킷이 표준을 어디서 넘어섰는지를 기록한다. 조회일 2026-09-10

넘어선 곳을 감추면 잘못 인용된다

킷은 몇 곳에서 표준보다 강한 규칙을 쓴다. 그것을 “표준이 그렇다”고 적으면 과대 인용이 되고, 그게 바로 이 킷이 막으려는 F3 다. 강화한 지점은 강화했다고 적는다.

킷의 <taskbody> 인용이 불완전했다

킷은 콘텐츠 모델을 이렇게 인용했다. 어느 모델인지 밝히지 않았다.

<prereq>?, <context>?, (<steps>|<steps-unordered>)?, <result>?, <postreq>?

“Beginning with DITA 1.2, the DTD and Schema packages distributed by OASIS contain two task models. The general task model allows two additional elements inside the task body (…); it also allows multiple instances and varying order… The strict task model maintains the order and cardinality of the DITA 1.0 and 1.1 content model.”

킷이 인용한 고정 순서 모델은 strict task model 이고, 그것이 OASIS 기본이다. 그러므로 킷의 인용은 틀리지 않았지만 불완전했다. 모델명을 안 쓰면 general 을 쓰는 사람이 “킷이 DITA 를 잘못 인용했다”고 판단한다.

표준을 모르고 어기는 것이 아니다. 이 도메인의 실패 데이터가 다르다 — 막으려는 실패가 무증상 실패다. 절차를 다 따랐는데 아무 일도 일어나지 않고 에러도 안 난다. 확인 지점이 없으면 사용자는 마지막 스텝까지 가서야 아무것도 안 됐다는 것을 알고, 어느 스텝이 실패했는지 되짚을 수 없다.

Google 의 규정도 결과를 쓰라고는 하되 순서만 정한다 — “State the action first and the result second.”

“매 스텝에 확인을 넣어라”고 규정한 스타일 가이드 조항은 찾지 못했다 — [미확인]. 그러므로 verify 필수는 표준의 인용이 아니라 도메인 실패 데이터에 근거한 강화다. 다른 표기는 과대 인용이다.

킷의 처리 — ISO 를 근거로 인용하지 않는다. 유료 전문의 내용을 2 차 요약으로 추정해 쓰지 않는다.

원문이 두 줄에 걸쳐 있어 raw 대조로는 안 잡혔다. 함정 목록이 없었으면 이 인용은 “확인 실패”로 잘못 기록됐을 것이다. 목록이 사이클을 거치며 실제로 값을 하고 있다.

표준 인용 체크리스트

절차 규약에 표준을 근거로 달 때 순서대로 확인한다.

  • 1인용한 문장이 그 URL 에 실재하는가. 정규화 대조기로 확인했는가 (엔티티 · 공백 · SPA · PDF)
  • 2표준에 변종이 있는가. DITA task 처럼 모델이 둘이면 어느 것인지 명시했는가
  • 3규약이 표준보다 강한가. 강하다면 “강화”라고 적고 왜 강화했는지 근거를 댔는가
  • 4표준에 대응 조항이 아예 없는 규약인가. 그렇다면 “킷 고유”로 표기했는가
  • 5유료 표준의 내용을 2차 요약으로 추정해 쓰고 있지 않은가. 공개 범위에서 본 것만 인용하라
  • 6접근 실패를 부재로 승격하고 있지 않은가. iso.org 가 스텁을 주는 것은 차단이지 없는 것이 아니다

위임 결과를 그대로 받았으면 멀쩡한 인용을 고칠 뻔했다

Codex 가 킷의 오류를 지적했다 — <taskbody> 모델이 킷 인용과 다르다는 것이다. 직접 확인한 결과 지적은 절반만 맞았다: 킷 인용이 틀린 게 아니라 두 모델 중 어느 것인지 안 밝힌 것이 문제였다.
