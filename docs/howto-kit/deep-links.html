Deep Links — 벤더 문서가 콘솔 URL 을 박아 두는 방식

메뉴 이름은 개편마다 바뀌지만 URL 은 훨씬 덜 바뀐다. 그래서 이 킷은 딥링크를 메뉴 경로보다 위에 둔다. 그 원칙이 서려면 전제가 하나 성립해야 한다 — 벤더가 공식 문서 본문에 콘솔 URL 을 실제로 박아 둔다는 것. 이 페이지는 그 전제의 실측 기록이다. 조회일 2026-09-09

콘솔 URL 자체를 열어 검증하지 않는다

로그인 리다이렉트라 무엇도 증명하지 못한다. 근거는 언제나 그 URL 을 담고 있는 공식 문서 페이지이고, 아래 인용은 전부 그 페이지의 응답 본문에서 추출한 것이다.

이 표는 낡는다. 인용하기 전에 다시 조회하라.

자리표시자 표기를 통일하지 마라

같은 “여기에 당신 값을 넣으라”를 벤더마다 다르게 쓴다. 절차 문서에서 이걸 예쁘게 통일해 버리면 사용자가 문서와 화면을 대조하지 못한다. 원문 표기를 그대로 옮겨라.

벤더자리표시자형태
Firebase_경로 세그먼트 project/_/
Google CloudPROJECT_ID쿼리 값 ?project=PROJECT_ID
Apple[Team ID]대괄호 + 공백 포함
Stripe<ACCOUNT_ID> <MODE> <PAGE>꺾쇠

Apple 과 Google Cloud 는 자리표시자를 문장으로 설명한다 — 아래 원칙 카드의 인용 참조.

벤더별 함정 4가지

넷 다 이번 조사에서 실제로 틀릴 뻔한 지점이다. 일반론이 아니라 원문 인용이 각각 붙어 있다.

1

Stripe — 모드가 경로 세그먼트다. 생략하면 live

Stripe 는 딥링크 문법을 정식으로 문서화한 드문 사례다. 그 문법에서 모드는 쿼리 파라미터가 아니라 경로 세그먼트다.

https://dashboard.stripe.com/<ACCOUNT_ID>/<MODE>/<PAGE>?apps[<APP_ID>][TARGET]=VIEWPORT_ID
“MODE: Use test for sandboxes (including the test mode sandbox) or omit a value for live mode”

생략하면 live 라는 것이 함정이다. 절차 문서에 dashboard.stripe.com/apikeys 라고만 쓰면 운영 모드 화면이 열리고, 테스트 키를 찾는 사용자는 원하는 값을 보지 못한다. 실제로 docs.stripe.com/keys 본문의 “API keys” 링크는 /test/apikeys 를 가리킨다.

출처
docs.stripe.com/stripe-apps/deep-links (조회 2026-09-09) docs.stripe.com/keys (조회 2026-09-09)
2

Azure — 딥링크가 프래그먼트에 있다

Azure Portal 의 딥링크는 경로가 아니라 URL 프래그먼트에 들어간다.

https://portal.azure.com/#view/Microsoft_Azure_Monitoring/AzureMonitoringBrowseBlade/%7E/logs

프래그먼트는 서버로 전송되지 않는다. 그래서 이 URL 은 리다이렉트 검사로 검증할 수 없다 — 근거는 Learn 문서가 그 링크를 건다는 사실뿐이고, 그 이상으로 단정하지 않는다.

검증 불가 ≠ 근거 없음
출처
learn.microsoft.com … log-analytics-overview (조회 2026-09-09)
3

AWS — 리전이 URL 에 박히고 리다이렉트된다

AWS 는 로그인 엔드포인트 자체에 리전을 실을 수 있다. 절차 문서가 리전을 박아 두면 다른 리전을 쓰는 사용자는 엉뚱한 리전의 콘솔에 도착한다.

“You can manually request a certain regional sign-in endpoint by signing in to the region-enabled main console home page using a URL syntax like the following:”
https://alias.signin.aws.amazon.com/console?region=ap-southeast-1

리전을 아는 경우가 아니면 슬롯을 비워라.

출처
docs.aws.amazon.com … id_users_sign-in (조회 2026-09-09)
4

문서가 SPA 면 HTML 로는 못 잡는다

developer.apple.com 문서는 클라이언트 렌더링이다. HTML 을 받아도 17KB 껍데기만 오고 본문 문장이 없다. 이 사실을 모르면 Apple 인용은 영원히 “확인 실패”로 남는다 — 이번 사이클의 Codex 위임이 정확히 그렇게 끝났다.

https://developer.apple.com/tutorials/data/documentation/<문서 경로>.json

본문이 inlineContent 배열로 들어 있어 문장을 그대로 뽑을 수 있다 (8.7KB, application/json).

일반 규칙 — 응답 크기가 부자연스럽게 작고 <script> 만 몇 개 있으면 SPA 를 의심하라. 그 벤더의 문서 데이터 API 를 찾아라. 못 찾으면 그 인용은 [미확인] 이다.
출처
developer.apple.com … infrastructure-validation-builds (조회 2026-09-09)
확인 실패 2건 — [미확인]

둘 다 관행으로는 통용되지만 1 차 출처가 없다. 규칙은 유지하되 근거를 “벤더가 그렇게 문서화했다”고 말하지 않는다.

항목확정된 것확정 못 한 것킷의 처리
Google 계정 슬롯 /u/0/ — 다중 계정에서 다른 계정으로 리다이렉트된다는 공식 문장 슬롯을 빼고 안내하는 규칙은 유지
Firebase _ URL 안에 project/_/ 가 등장한다 _ 가 프로젝트 id 자리라고 설명하는 문장 관행 설명은 [추정] 으로 표기

시도한 URL 은 howto-kit/references/provenance-notes.md §5 에 원장으로 남아 있다.

위임 결과를 그대로 옮기지 않았다

Codex 위임 1 회 (MODE=research · read-only · foreground · 검색 하드캡 20). rollout 로그의 turn_aborted 는 0 건으로 정상 완주했고, 결과는 5 건 확정 · 2 건 확인 실패였다. 그 결과를 로컬 curl 로 대조했더니 8 건 중 3 건이 MISS 였다.

교훈은 양방향이다

위임이 돌려준 “확인 실패”는 그 도구의 환경 한계일 수 있다 — 문서에 옮기기 전에 다른 경로로 한 번 더 시도하라. 반대로 위임이 “확인됨”이라 답한 인용도 대조 없이 옮기지 마라 — 이번에 8 건 중 3 건이 1 차 대조에서 어긋났다.

딥링크 안내 체크리스트
  • 1URL 의 근거가 그 URL 을 담은 공식 문서인가. 콘솔을 열어 본 것을 근거로 삼지 않았는가
  • 2자리표시자를 벤더 표기 그대로 옮겼는가 (_ / PROJECT_ID / [Team ID] / <ACCOUNT_ID>)
  • 3Stripe 라면 모드 세그먼트를 넣었는가. 생략은 live 다
  • 4리전 · 계정 인덱스 슬롯을 임의로 박지 않았는가
  • 5검증 못 한 URL 을 확정처럼 쓰고 있지 않은가. 프래그먼트는 서버로 가지 않아 리다이렉트 검사가 불가능하다
  • 6이 표의 URL 을 조회일 단서 없이 인용하고 있지 않은가
