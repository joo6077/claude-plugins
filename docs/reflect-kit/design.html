02 · Canonical Schema

YAML 스키마 (정본)

reflections-YYYY-MM.md의 각 ## <ISO8601+TZ> 아래에는 여러 블록이 올 수 있으며, 문제가 없으면 no issues 한 줄만 기록합니다.

primary_category: misunderstanding | repeated_error | wrong_approach | tool_failure
also_applies: []
mistake_tag: <kebab-case 영문 태그>
trigger: <상황 스니펫 1줄>
undesired_behavior: <잘못 1줄>
desired_behavior: <원한 것 1줄>
severity: low | medium | high
actionability: claude_behavior | user_environment
scope: session | project | global
risk_class: low | medium | high
procedurality: single_rule | multi_step_procedure
enforcement_need: soft_reminder | hard_gate
evidence_turns: <int>
tools_used:
  skills: []
  agents: []
  mcp_servers: []
approach_note: <접근법 1줄>

misunderstanding

사용자 의도, 파일 범위, 전제를 잘못 이해.

repeated_error

교정 뒤에도 동일 실수를 반복.

wrong_approach

더 적절한 skill·agent·MCP 대신 비효율적인 접근.

tool_failure

맥락이 의미 있는 도구 실패. 단순 exit code-only는 제외.

Bad · 단일 필드 압축

겹치는 원인을 버리고 surface_candidate 하나로 원인과 해결책을 함께 표현합니다.

Good · 원인과 surface 분리

primary_category + also_applies로 분류하고 네 축과 빈도로 surface를 계산합니다.

축의미값
scope적용 범위session / project / global
risk_class위반 피해low / medium / high
procedurality단일 규칙 vs 체크리스트single_rule / multi_step_procedure
enforcement_need안내 vs 차단soft_reminder / hard_gate
actionability: user_environment는 precedence에서 제외해 환경 액션으로만 보고합니다. 반복분은 억제해 .env-issues.tsv에 누적합니다.
03 · Promotion Decision

Surface Precedence Table

user_environment를 제외한 뒤 canonical + aliases의 cluster_freq를 사용합니다. 위에서 아래로 처음 맞는 하나만 적용합니다.

#조건승격 surface
0user_stated_constraint == true, freq ≥ 1임계값 우회 fast-track: global이면 글로벌 CLAUDE.md, 아니면 project CLAUDE.md
1hard_gate, 빈도 무관hook 검토
2multi_step_procedure AND freq ≥ 2skill 신설/보강
3global AND 복수 프로젝트 freq ≥ 3high는 글로벌 CLAUDE.md, 나머지는 글로벌 memory
4project AND freq ≥ 3project CLAUDE.md, 200줄 초과 예상 시 path-scoped rule
5project AND freq ≥ 2project memory
6low risk AND freq == 1관망
7그 외수동 review
임계값은 hypothesis: 2회는 memory, 3회는 CLAUDE.md로 시작하고 월 1회 30일 재발률로 조정합니다.

CLAUDE.md 용량 예산

공식 권고 200줄 이하. 초과 예상 시 .claude/rules/<tag>.md 또는 skill로 스필오버합니다.

04 · Regression

Promotion Ledger 스키마

경로는 ~/.claude/logs/<project_id>/promotions-ledger.md이며, 승격마다 append하고 30일 뒤 post_freq를 채웁니다.

- rule_id: <UUID>
  mistake_tag: <canonical_tag>
  aliases: []
  promoted_to: project_claude_md | project_memory | global_claude_md |
               global_memory | skill | path_scoped_rule | hook
  enforcement_level: E1 | E2 | E3
  target_path: <실제 수정 경로>
  promoted_at: <ISO8601 with TZ>
  source_evidence:
    - path: ~/.claude/logs/<id>/reflections-YYYY-MM.md
      anchor: <타임스탬프 헤더>
  initial_freq: <int>
  calibration_window_days: 30
  post_freq: <int>
  status: active | demoted | removed
  demotion_reason: <str>
결과판정과 행동
post_freq == 0 AND low risk과잉제약 가능성, demoted 후보
post_freq == 1등급 유지, 문구 명확화
post_freq ≥ 2등급 상향: 2회 이상 E2, 3회 이상 또는 비가역·신뢰 손상은 E3
post_freq < initial_freq AND ≤ 1효과 있음, 유지
canonical tag만 세지 않고 mistake_tag + aliases 전체를 합산합니다.

10 · Identity

결정 #3 상세 — Hybrid project_id (v0.3.0 전환)

v0.1.0~v0.2.0의 상시 6자 md5 hex는 실제 7개 프로젝트에서 basename 충돌이 0건이라 과설계였습니다.

A · hash 유지

운영 데이터로 정당화되지 않아 부적합.

B · basename only

UX는 좋지만 breaking change와 강제 이관 발생.

C · Hybrid 선정

basename 기본 + 충돌 fallback + 기존 hash read. 데이터 이동 0건.

상황id동작
첫 write<basename>bucket + .project-root 생성
마커가 자기 repo<basename>no-op
같은 repo 워크트리본 repo basename본 repo root 마커 일치
다른 root, 같은 basename<basename>-<hash6>PID 기반 중복 억제 stderr 경고
기존 hash readglob unionnormalize_project_query로 두 형태 스캔

Backward-compat과 마커

  • 두 project query 형식은 같은 결과이며 이관 스크립트가 필요 없습니다.
  • .project-root는 생성 때 한 번 쓰고 stat + cat으로 충돌을 감지합니다.
  • 마커 없는 v0.2.0 디렉토리는 충돌 없음으로 보고 read에만 포함합니다.
  • 동시 write의 마커 생성 전 race는 개인 규모에서 무시합니다.

워크트리 · 2026-09-25

실측 로그 폴더 31개 중 12개가 워크트리 이름이었습니다. git-dir과 common-dir이 다르고 공통 폴더 이름이 .git일 때만 그 부모를 본 repo로 씁니다.

두 조건은 서브모듈을 modules로 묶는 오류와 --separate-git-dir 오판을 피합니다. bare repo는 이전처럼 워크트리 이름을 씁니다. git rev-parse 문서 →

기존 12개 폴더는 옮기지 않습니다. reflections는 없고 raw 로그와 오류만 있으며, 이동하면 cwd:와 폴더 이름이 어긋납니다. project=all은 계속 전부 순회합니다.
