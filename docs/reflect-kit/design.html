Design — Reflect Kit

Reflexion 방법론을 개인 Claude Code 사용자에게 적용한 피드백 파이프라인의 구조·판정 규칙·회귀 측정 설계. 수집 훅 3종 → digest 집계 → precedence table 기반 surface 승격 → ledger 기반 30일 재발률 추적이라는 닫힌 사이클로 구성된다.

파이프라인 설계 · 설계 결정 정본
데이터 플로우

3채널 수집 → 분석 → 승격 → 측정

[ 사용자 프롬프트 ] → UserPromptSubmit → log-prompt.sh → redact → YYYY-MM.md [ 도구 실패 ] → PostToolUseFailure → log-tool-failure.sh → redact → YYYY-MM.md [ 세션 종료 ] → Stop (nohup 백그라운드) → log-reflection.sh └─► codex exec 분석 → reflections-YYYY-MM.md └─► 실패 시 → .errors.log │ ▼ /reflect-digest (집계 + 승격 후보) │ ▼ /reflect-promote (반영 + ledger append) │ ▼ /reflect-kaizen (품질 스팟체크 + 30d calibration)
수집 3채널 분리의 이유 — 한 채널이 실패해도 나머지 2채널이 관측을 계속한다. Stop 훅의 codex 분석이 실패해도 raw 프롬프트와 도구 실패 로그는 그대로 쌓이므로 사후 수동 분석이 가능하다.
Surface 판정 4축

단일 필드 대신 다차원 분해

🗺️

scope

이 규칙이 어느 범위에 적용되어야 하는가. session / project / global. 프로젝트 간 공통 패턴은 global로 승급.

⚠️

risk_class

위반 시 피해 정도. low / medium / high. high일수록 CLAUDE.md 또는 hook으로 승격.

📋

procedurality

단일 규칙인가 다단계 체크리스트인가. single_rule은 memory/CLAUDE.md, multi_step_procedure는 skill.

🔒

enforcement_need

안내로 충분한가 차단이 필요한가. soft_reminder는 텍스트 surface, hard_gate는 hook.

Surface Precedence Table

위에서 아래로 적용, 먼저 맞는 규칙 하나만 선택

#조건승격 surface
1enforcement_need == hard_gate (빈도 무관)hook 검토 (다른 축 무시)
2procedurality == multi_step_procedure AND freq ≥ 2skill 신설/보강
3scope == global AND 복수 프로젝트 freq ≥ 3risk=high → 글로벌 CLAUDE.md / 나머지 → 글로벌 memory
4scope == project AND freq ≥ 3project CLAUDE.md (200줄 초과 예상 시 path_scoped_rule)
5scope == project AND freq ≥ 2project memory (feedback 타입)
6risk_class == low AND freq == 1관망 (다음 주 재평가)
7그 외수동 review 후보
임계값은 hypothesis — freq 2 / 3 기준은 초기 가설이다. Claude 공식 권고는 "같은 실수 2번째 → CLAUDE.md"이지만, 과잉제약을 피하기 위해 한 단 낮게 설정했다. 30일 운영 데이터가 쌓이면 /reflect-kaizen이 pre/post 재발률로 calibration 한다.
Ledger

Promotion Ledger — 30일 회귀 측정의 근간

경로: ~/.claude/logs/<project_id>/promotions-ledger.md

- rule_id: <uuid>
  mistake_tag: <tag>
  promoted_to: project_claude_md | project_memory | global_claude_md |
               global_memory | skill | path_scoped_rule | hook
  target_path: <실제 수정된 파일 절대경로>
  promoted_at: <ISO8601 with TZ>
  source_evidence:
    - path: ~/.claude/logs/<id>/reflections-YYYY-MM.md
      anchor: <타임스탬프 헤더>
  initial_freq: <int>
  calibration_window_days: 30
  post_freq: <int | null>     # 30일 뒤 kaizen이 업데이트
  status: active | demoted | removed
  demotion_reason: <str>      # 강등 시만

회귀 판정 규칙

  • post_freq == 0 AND risk_class == low → status: demoted 후보 (과잉제약)
  • post_freq >= initial_freq → 효과 없음, 프롬프트 재작성 또는 surface 변경 후보
  • post_freq < initial_freq → 효과 있음, 유지
SCHEMA.md 전문 →
CLAUDE.md 용량 예산

200줄 한도 + path-scoped 스필오버

공식 권고는 CLAUDE.md 200줄 이하. reflect-promote는 승격 전에 현재 라인 수를 측정하고, 180줄 이상이면 .claude/rules/<tag>.md (path-scoped, 특정 glob 편집 시만 로드)로 자동 fallback 한다. 사용자에게 fallback 사유를 보고하고 승인을 받는다.
핵심 설계 결정

10가지 결정 요약

1. kit 이름 reflect-kit

Reflexion 논문 + 한국어 "성찰" 뉘앙스 + joo6077-plugins 네이밍 컨벤션.

2. raw 저장 + redaction

편의성 유지 + 시크릿 자동 치환. 민감 패턴 10종 (sk-ant-*, ghp_*, AKIA*, JWT, private key 등).

3. project_id Hybrid (v0.3.0)

<basename> 기본 + 충돌 감지 시 -<hash6> fallback. 기존 hash 디렉토리는 glob union 으로 read 지원 (backward-compatible).

4. 카테고리 multi-label

primary_category + also_applies. misunderstanding과 wrong_approach는 상호배타 아님.

5. Surface 4축 분해

단일 필드 대신 scope × risk × procedurality × enforcement로 precedence 판정.

6. 임계값 hypothesis

freq 2/3은 임시값. kaizen이 30일 calibration.

7. Stop 훅 백그라운드

nohup & disown으로 체감 지연 0. async 필드 의존 안 함.

8. codex exec 사용

API 키 불필요. 사용자 기존 인증 재사용.

9. 성공 사례 수집 보류

ROI 낮음. ledger post_freq로 간접 측정.

10. 보존 정책 = 누적

자동 삭제/압축 없음. 용량 이슈 시 재논의.
