Infra Kit v0.1

컨테이너

Dockerfile 작성, 멀티스테이지 빌드, 레이어 캐싱, 이미지 보안, docker-compose 프로덕션 운영, 리소스 제한, 헬스체크, 로깅 전략 — 작고 안전하고 예측 가능한 컨테이너의 원칙.

01 · Principles

핵심 원칙

PRINCIPLE 01

멀티스테이지 빌드를 기본으로 사용

빌드 도구(컴파일러, 패키지 매니저, 테스트 프레임워크)는 빌드 스테이지에만 존재해야 한다. 최종 이미지에는 런타임에 필요한 바이너리와 설정만 복사한다. 이미지 크기가 줄고, 공격 표면이 축소되며, 빌드 캐시 효율이 올라간다. COPY --from=builder로 필요한 산출물만 가져온다.

Docker — Multi-stage builds
PRINCIPLE 02

.dockerignore로 빌드 컨텍스트를 최소화

.git, node_modules, .env, 테스트 디렉토리 등 빌드에 불필요한 파일을 제외한다. 빌드 컨텍스트가 크면 전송 시간이 늘고, 민감 정보가 이미지에 포함될 수 있으며, 관련 없는 파일 변경이 레이어 캐시를 무효화한다.

Docker — Dockerfile best practices
PRINCIPLE 03

non-root 사용자로 실행을 강제

USER 지시어로 비특권 사용자를 지정한다. 베이스 이미지는 distroless 또는 minimal(alpine, slim) 계열을 우선한다. distroless에는 셸이 없어 컨테이너 탈출 공격을 원천 차단한다. Trivy 등 스캐너로 알려진 CVE를 CI에서 정기 점검한다.

Dockerfile reference — USER
PRINCIPLE 04

프로덕션 Compose는 개발용 설정과 분리

개발 환경의 바인드 마운트, 디버그 포트, 소스 코드 동기화를 프로덕션에 가져가지 않는다. docker-compose.yml(공통) + docker-compose.prod.yml(오버라이드) 구조로 환경별 설정을 분리하고, 프로덕션에서는 restart: always, 로그 드라이버, 리소스 제한을 명시한다.

Docker — Use Compose in production
PRINCIPLE 05

CPU / 메모리 / PIDs 제한을 명시

컨테이너에 리소스 상한을 두지 않으면 단일 워크로드가 호스트 전체를 점유하는 noisy-neighbor 문제가 발생한다. 메모리 초과 시 커널 OOM killer가 임의 프로세스를 종료하므로, 워크로드별 하드 리밋을 설정하여 예측 가능한 격리를 확보한다.

Docker — Resource constraints
PRINCIPLE 06

헬스체크는 트래픽 처리 가능성을 검증

프로세스가 살아 있어도 데드락, 커넥션 풀 고갈, 초기화 미완료 등으로 요청을 처리하지 못할 수 있다. HEALTHCHECK 지시어의 CMD는 실제 엔드포인트(/healthz, /readyz)를 호출하여 애플리케이션 수준의 준비 상태를 확인해야 한다.

Dockerfile reference — HEALTHCHECK
PRINCIPLE 07

로그는 stdout/stderr로 출력

컨테이너 내부 파일에 로그를 쓰면 수집이 어렵고 디스크가 차서 장애가 발생한다. stdout/stderr로 보내면 Docker 로깅 드라이버가 수집하고, 외부 시스템(ELK, Loki, CloudWatch)으로 라우팅할 수 있다. json-file 드라이버는 반드시 max-size/max-file 로테이션을 설정한다.

03 · Anti-patterns

안티패턴 & 올바른 접근

Bad

빌더 포함 단일 스테이지

컴파일러, 소스, 테스트 도구가 프로덕션 이미지에 그대로 남아 이미지 크기가 비대해지고 공격 표면이 확대된다. 불필요한 패키지의 CVE까지 모두 떠안는다.

Good

멀티스테이지로 런타임만 복사

FROM ... AS builder로 빌드 후, 최종 스테이지에서 COPY --from=builder로 산출물만 가져온다. distroless 또는 alpine 런타임 베이스로 크기 최소화.

Bad

루트 실행

USER 없이 PID 1이 root로 실행되면 컨테이너 탈출 시 호스트 권한 획득이 가능하다. 볼륨 마운트된 호스트 파일도 root 권한으로 조작 가능.

Good

비특권 사용자 지정

RUN adduser --uid 10001 app 후 USER app. 컨테이너 내부에서도 권한이 제한되어 exploit 영향이 축소된다.

Bad

소스 전체를 먼저 COPY

의존성 설치 전에 소스를 복사하면 코드 한 줄 변경에도 의존성 레이어 캐시가 무효화된다. 매번 npm/pip install을 반복 수행하여 빌드가 느려진다.

Good

의존성 파일 먼저 → install → 소스 COPY

COPY package.json package-lock.json ./ → RUN npm ci → COPY . . 순서. 의존성 변경이 없으면 install 레이어는 캐시 히트.

Bad

json-file 무제한

max-size/max-file 없이 json-file 드라이버를 쓰면 로그가 무한히 쌓여 디스크 포화로 호스트 전체가 장애. 가장 흔한 운영 사고 중 하나.

Good

로그 로테이션 명시

logging.driver: json-file + options: { max-size: "20m", max-file: "5" }. 또는 local 드라이버(기본 100MB 롤링) 사용.

Bad

readiness 없는 depends_on

depends_on은 컨테이너 시작만 보장하고 애플리케이션 준비 상태는 확인하지 않는다. DB가 아직 커넥션을 받지 못하는 상태에서 앱이 먼저 시작되어 크래시.

Good

condition: service_healthy 사용

의존 서비스에 healthcheck를 정의하고 depends_on.db.condition: service_healthy로 대기. 실제 준비될 때까지 앱 시작을 지연.

04 · Gotchas

Gotchas 체크리스트

✓
docker compose의 depends_on은 running과 ready를 구분하지 않는다. DB 컨테이너가 시작되었어도 커넥션을 받을 준비가 안 됐을 수 있다. depends_on.condition: service_healthy를 사용해야 실제 준비 상태를 기다린다.
✓
메모리 제한 초과가 즉시 kill이 아닐 수 있다. 커널 OOM killer는 메모리 압박 상황에서 점수 기반으로 프로세스를 선택하므로, 제한을 초과한 컨테이너가 즉시 종료되지 않는 경우가 있다. --oom-kill-disable은 더 위험하다.
✓
--memory-swap 의미를 오해한다. --memory=300m --memory-swap=1g은 swap이 1g가 아니라 메모리+swap 합계가 1g라는 뜻이다. 즉 swap 사용량은 700m이다.
✓
기존 컨테이너는 daemon 로깅 설정을 상속하지 않는다. daemon.json의 로깅 드라이버를 변경해도 이미 실행 중인 컨테이너에는 적용되지 않는다. 컨테이너를 재생성해야 한다.
