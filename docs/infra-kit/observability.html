Infra Kit v0.1

관측성

메트릭 · 로그 · 트레이스 상호연결, Prometheus 타입 선택, 대시보드 설계, 구조화 로깅, SLI/SLO, 알림 전략, 카디널리티 관리까지 — 운영 가능한 관측성 시스템을 구축하기 위한 7가지 원칙.

Principles

운영 가능한 관측성을 위한 7원칙

각 원칙은 공식 문서/표준 명세를 근거로 한다. 카드의 출처 링크로 원본 레퍼런스를 직접 확인할 수 있다.

01

메트릭·로그·트레이스를 공통 컨텍스트로 상호연결한다

세 신호를 독립적으로 수집하면 장애 시 연결 고리가 없어 진단이 지연된다. OpenTelemetry는 signals, context propagation, OTLP, semantic conventions를 표준화하여 trace_id 하나로 메트릭 → 트레이스 → 로그를 탐색할 수 있게 한다. 수집 파이프라인을 통합하는 것이 아니라 컨텍스트를 공유하는 것이 핵심이다.

OpenTelemetry — Signals
02

Prometheus 메트릭 타입을 엄격히 선택한다

counter는 누적 증가값(요청 수, 에러 수), gauge는 증감하는 현재값(큐 길이, 온도), histogram은 분포와 SLO 계산(지연 시간 버킷), summary는 클라이언트 측 quantile이다. 타입을 잘못 선택하면 집계 결과가 의미 없어지거나 멀티 인스턴스 환경에서 합산이 불가능해진다.

Prometheus — Metric Types
03

대시보드는 운영 의사결정 도구로 설계한다

상단에 사용자 영향 지표(에러율, 지연 시간, 가용성)를 배치하고, 하단에 원인 후보(CPU, 메모리, 큐 깊이)를 배치한다. 각 패널은 drill-down이 가능해야 하며, 패널 수집장이 아닌 "무엇이 잘못되었고 어디를 파야 하는가"에 답하는 구조여야 한다.

Grafana — Alerting Best Practices
04

로그는 구조화(JSON/ECS) 우선으로 출력한다

비구조화 텍스트 로그는 파싱 비용이 높고 필드 기반 검색이 어렵다. JSON 또는 ECS(Elastic Common Schema) 형식으로 출력하되, trace_id, service.name, env 필드를 반드시 포함한다. 이 필드들이 메트릭·트레이스와의 연결 고리가 된다.

Elastic — ECS Application Logs
05

SLI/SLO는 제품 우선순위 결정 장치다

SLI(Service Level Indicator)는 측정 가능한 사용자 경험 지표이고, SLO(Service Level Objective)는 그 목표 수준이다. error budget(1 − SLO)을 릴리스 속도와 연결하면 "안정성에 투자할 때"와 "기능에 투자할 때"를 정량적으로 판단할 수 있다. SLO 없이 모니터링만 하면 경보 피로만 쌓인다.

Google SRE Workbook — Implementing SLOs
06

알림은 사용자 증상 중심으로 설정한다

latency, error rate, availability SLI 기반 경보만 페이징(즉시 대응)으로 설정한다. CPU 사용률, 디스크 여유 같은 인프라 경보는 티켓 또는 업무시간 알림으로 분류한다. 모든 경보를 페이징으로 설정하면 경보 피로로 인해 실제 장애를 놓치게 된다.

Google SRE Workbook — Alerting on SLOs
07

카디널리티를 적극적으로 관리한다

pod_name, user_id, request_id 같은 고유값을 메트릭 라벨에 넣으면 시계열 수가 폭증하여 저장 비용과 쿼리 지연이 급증한다. 이런 값은 로그나 structured metadata로 전달하고, 메트릭 라벨은 유한한 집합(status_code, method, endpoint 등)으로 제한한다.

Anti-patterns

반복되는 안티패턴과 교정

실제 장애와 비용 폭증의 직접 원인. 왼쪽 패턴을 발견하면 오른쪽으로 교체한다.

Anti-pattern

모든 라벨에 high-cardinality 값 사용

pod_name, user_id를 메트릭 라벨로 넣어 시계열이 폭증한다. 저장 비용과 쿼리 지연이 급증하며 Prometheus/Loki 안정성을 위협한다.

Correct

라벨은 유한 집합, 고유값은 로그/트레이스로

status_code, method, endpoint 등으로 라벨을 제한하고 user_id/request_id는 structured log 또는 trace attribute로 전달한다.

Anti-pattern

로그에 trace_id 누락

트레이스에서 로그로 drill-down이 불가능해져 관측성 3대 신호의 연결 고리가 끊긴다.

Correct

모든 로그에 trace_id / service.name 필수

OTel context propagation을 거쳐 JSON 로그에 trace_id를 항상 포함시킨다. Elastic ECS 스키마의 서브셋으로 강제한다.

Anti-pattern

대시보드를 패널 수집장으로 운영

목적 없는 패널이 수십 개 나열되면 장애 시 어디를 봐야 할지 모른다. 경험 있는 엔지니어에게만 의미가 있고 온보딩이 느려진다.

Correct

증상 → 원인 순서의 목적형 대시보드

상단: 사용자 증상(SLI). 하단: 원인 후보(리소스/의존성). 각 패널에 drill-down 링크(trace, log query)를 연결한다.

Anti-pattern

summary로 전역 p95 계산

멀티 인스턴스 환경에서 summary quantile은 수학적으로 합산 불가능하다. 인스턴스별 p95의 평균은 전역 p95가 아니다.

Correct

histogram + histogram_quantile

버킷 기반 histogram으로 수집하고 서버 측에서 histogram_quantile()로 전역 percentile을 계산한다. SLO 산출에도 동일하게 사용한다.

Anti-pattern

모든 경보를 paging으로 설정

경보 피로가 누적되어 실제 장애 알림을 무시하게 된다. 온콜 엔지니어의 수면과 심리 안전이 파괴된다.

Correct

증상 기반 SLI 경보만 페이징

latency/error rate/availability SLI 경보만 페이징. 리소스 경보는 티켓/업무시간 알림으로 분류한다.

Gotchas

놓치기 쉬운 함정

도입만으로는 해결되지 않는 운영 세부 사항. 구현 전 체크리스트로 점검한다.

  • OTel SDK를 도입하는 것만으로 표준화가 되지 않는다. semantic conventions를 팀 규칙으로 정의하고 리뷰해야 일관성이 유지된다.
  • summary는 멀티 인스턴스 SLO 계산에 부적합하다 — histogram으로 서버 측에서 집계해야 정확한 전역 percentile을 얻는다.
  • 로그 샘플링은 비용 절감에 효과적이지만 보안 로그, 감사(audit) 로그에는 적용 금지 — 규정 준수 위반 위험이 있다.
  • tracing span naming 품질이 낮으면(예: 모든 span이 "HTTP request") 트레이스 검색과 분석의 실효성이 급격히 떨어진다.
