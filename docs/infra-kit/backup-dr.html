01 · Principles

핵심 원칙

PRINCIPLE 01

RTO/RPO를 먼저 정하고 전략을 선택한다

Recovery Time Objective(RTO)는 서비스 복구까지 허용 가능한 최대 시간, Recovery Point Objective(RPO)는 허용 가능한 최대 데이터 손실 시간이다. 이 두 지표가 백업 빈도, 복제 방식, 자동화 수준, 비용을 결정한다. RTO/RPO 없이 백업 전략을 세우면 과잉 투자이거나 과소 보호다.

AWS Prescriptive Guidance — Backup and Recovery for RDS
PRINCIPLE 02

논리 백업과 물리 백업/PITR은 보완재다

논리 백업(pg_dump, mysqldump)은 사람이 읽을 수 있고 특정 테이블만 복원 가능하지만 느리다. 물리 백업(스냅샷, WAL 아카이브)은 빠른 전체 복원과 PITR을 지원하지만 세밀한 선택적 복원이 어렵다. 두 방식을 병행하여 각각의 약점을 보완한다.

AWS — Getting Started with Backup and Restore
PRINCIPLE 03

핵심 DB는 PITR을 기본 옵션으로 활성화

Point-in-Time Recovery(PITR)는 특정 시점으로 데이터베이스를 복원한다. 사람의 실수(잘못된 DELETE/UPDATE)에 대응할 수 있는 유일한 자동화 수단이다. RDS는 자동 백업 활성화 시 PITR을 제공하며, retention window 내 임의 시점(초 단위)으로 복원 가능하다.

AWS RDS — Point-in-Time Recovery
PRINCIPLE 04

멀티리전 DR은 복제 + runbook을 모두 포함한다

데이터 복제가 끝이 아니다. DNS 전환, 로드 밸런서 재설정, 시크릿 동기화, 캐시 워밍, 외부 서비스 엔드포인트 변경 등 전체 의존성 체인을 재구성하는 runbook이 있어야 한다. 복제본이 있어도 runbook이 없으면 실제 장애에서 RTO를 지키지 못한다.

AWS RDS — Automated Backups and PITR
PRINCIPLE 05

DR은 문서가 아니라 정기 테스트로 검증

DR 계획은 테스트하지 않으면 신뢰할 수 없다. 분기별 또는 반기별로 실제 복구 절차를 실행하고, RTO/RPO 달성 여부를 측정한다. Chaos engineering(예: AWS FIS, Gremlin)으로 장애를 주입하여 시스템과 팀의 대응 능력을 검증한다.

03 · Anti-patterns

안티패턴 & 올바른 접근

Bad

스냅샷만 믿고 PITR 부재

하루 1회 스냅샷만 있다면, 스냅샷과 스냅샷 사이에 변경된 데이터는 손실된다. 사용자 실수로 인한 DELETE는 다음 스냅샷까지 기다릴 수 없다.

Good

PITR로 초 단위 복원 경로 확보

자동 백업 활성화 + 트랜잭션 로그 아카이빙으로 retention window 내 어떤 시점으로도 복원 가능. 스냅샷은 장기 보관용, PITR은 운영 실수 대응용.

Bad

백업 성공 알림만 보고 restore 미실시

백업이 존재해도 복원이 실패할 수 있다. 포맷 손상, 종속성 변경, 복구 도구 버전 차이 등으로 정작 필요할 때 복원이 안 되는 사례가 많다.

Good

정기 restore 테스트 + 데이터 정합성 검증

분기별 또는 반기별로 실제 복원을 격리 환경에서 실행하고 스키마·레코드 수·샘플 데이터의 정합성을 확인한다. 테스트되지 않은 백업은 백업이 아니다.

Bad

복구 순서 미문서화

DB만 복원해도 앱 서버, 캐시, 외부 연동이 정상이지 않으면 서비스가 작동하지 않는다. 장애 시점에 의존성 순서를 기억해내려 하면 이미 늦다.

Good

의존성 복구 순서 runbook 명시

DB → 캐시 워밍 → 앱 서버 → 메시지 큐 → 외부 웹훅 재설정 등 전체 체인의 복구 순서를 체크리스트로 문서화. 담당자와 예상 소요 시간까지 기재.

Bad

멀티리전 복제를 DR 완료로 간주

복제는 DR의 한 요소일 뿐이다. 복제본이 있어도 DNS, 시크릿, 네트워크, 모니터링 전환 절차가 없으면 실제 장애에서 무력하다.

Good

전체 스택 전환 절차 포함

복제 + DNS failover + 시크릿 동기화 + 네트워크 라우팅 + 모니터링 전환을 한 번의 runbook으로 묶고, 정기 훈련으로 검증. 복제는 시작점일 뿐.

04 · Gotchas

Gotchas 체크리스트

✓
PITR 복구는 원본 인스턴스를 덮어쓰지 않고 새 인스턴스를 생성한다. 기존 인스턴스에서 새 인스턴스로 트래픽을 전환하는 cutover 절차가 별도로 필요하다.
✓
복구된 인스턴스는 기본 parameter group으로 붙을 수 있다. 커스텀 parameter group, option group을 원본과 동일하게 재적용해야 한다.
✓
복구 후 태그, Security Group, 서브넷 그룹, 연결 문자열(endpoint) 업데이트가 누락되는 사례가 빈번하다. runbook에 체크리스트로 포함한다.
✓
RDS 자동 백업 보존을 0으로 설정하면 PITR이 비활성화된다. 기본값(7일)을 반드시 확인한다.
✓
Cross-region 스냅샷 복사는 수동 또는 자동화(Lambda/EventBridge)로 구성해야 한다. 자동 백업은 동일 리전에만 저장된다.
