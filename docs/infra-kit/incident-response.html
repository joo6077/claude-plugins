인시던트 대응

Severity 분류, 온콜 체계, 역할 분리, Runbook, Postmortem, RCA, Status Page, 복구 우선순위. 장애는 언제든 일어난다 — 대응 방식이 조직의 성숙도를 결정한다.

Core Principles
핵심 원칙 8

Google SRE, Atlassian IM 가이드, Statuspage 공식 문서 기반. 각 원칙은 사용자 체감 영향과 조직 학습을 기준으로 정렬된다.

1
Severity는 사용자/비즈니스 영향 기준으로 분류한다
기술적 원인(서버 다운, DB 락)이 아니라 사용자가 체감하는 영향 범위와 심각도로 분류한다. 기술 원인 기준으로 분류하면 영향이 큰 장애를 과소평가하거나, 영향이 작은 문제에 과잉 대응하게 된다.
Atlassian — Severity Levels
2
온콜은 primary/secondary 분리하고 handoff 시간을 명시한다
Primary가 응답하지 못할 경우 secondary로 자동 에스컬레이션되어야 한다. handoff 시간(교대 시점)을 명확히 정의하여 "누가 지금 담당인가"에 모호함이 없어야 한다. 온콜 부담은 팀 전체에 공정하게 분배한다.
Google SRE — Being On-Call
3
탐지 → 선언 → 지휘 → 커뮤니케이션 역할을 분리한다
Incident Commander(IC)가 의사결정과 조율을 맡고, Communicator가 이해관계자 업데이트를 담당한다. IC가 직접 디버깅에 뛰어들면 전체 조율이 중단된다. 역할이 명확해야 병렬 작업이 가능하다.
Atlassian — IR Roles
4
Runbook은 실행 절차다
개념 설명이 아니라 "따라 하면 자동화 가능한 수준"의 단계별 명령 시퀀스여야 한다. 판단이 필요한 지점은 분기 조건을 명시한다. Runbook이 실행 불가능한 산문이면 장애 시 아무도 참조하지 않는다.
Google SRE — Service Best Practices
5
Postmortem은 blameless로 수행한다
사람의 실수를 비난하는 대신, 그 실수를 허용한 환경과 안전장치 부재를 고친다. Blame culture가 형성되면 장애를 숨기거나 축소 보고하게 되어 조직 학습이 중단된다.
Google SRE — Service Best Practices
6
RCA는 "왜 방어선이 실패했는가"에 집중한다
직접 원인(what)이 아니라 방어선 실패(why)를 추적한다. 5 Whys + timeline 조합으로 인과 관계를 시간순으로 재구성한다. "서버가 죽었다"가 아니라 "왜 자동 복구가 작동하지 않았는가"가 핵심 질문이다.
Atlassian — 5 Whys Analysis
7
Status page를 단일 진실원천(SSoT)으로 운영한다
내부 슬랙, 이메일, 전화 등 여러 채널에 장애 상태가 흩어지면 혼란이 가중된다. Status page 하나를 공식 채널로 지정하고, 모든 업데이트를 여기에 먼저 게시한다. 고객, 내부 팀, 경영진 모두 같은 정보를 본다.
Statuspage — Developer API
8
복구 우선순위: data integrity > core availability > noncritical
데이터 무결성이 최우선이다. 데이터가 손상된 상태로 서비스를 복구하면 피해가 확산된다. 핵심 기능의 가용성이 그다음이고, 부가 기능은 마지막이다. 이 순서를 사전에 합의해두지 않으면 장애 시 우선순위 논쟁으로 시간을 소모한다.

Reference Values
Severity 분류 및 커뮤니케이션 기준

SEV 기준과 공지 cadence는 사전에 합의된 수치로 운영한다. 장애 시점에 협상하면 이미 늦는다.

Severity 정의 첫 공지 업데이트 주기 에스컬레이션
SEV1 전면 장애 또는 데이터 손상. 모든 사용자 영향. 15분 이내 30분 cadence 즉시 전사 에스컬레이션
SEV2 핵심 기능 중대 저하. 우회 불가 또는 매우 어려움. 30분 이내 60분 cadence 엔지니어링 리더 공지
SEV3 부분 기능 저하. 우회 가능. 업무 시간 내 필요 시 담당 팀 내부 처리
SEV4 경미한 이슈. 사용자 영향 최소. 공지 불필요 — 티켓 백로그

Anti-Patterns
피해야 할 패턴

실전 장애에서 반복적으로 관찰되는 실수. "원인 먼저 vs 공지 먼저"는 특히 신뢰와 직결된다.

Bad
원인을 찾은 뒤에야 공지
"완전히 파악하고 올려야 프로페셔널하다"는 착각. 고객은 원인보다 인지하고 있음을 먼저 알고 싶어한다. 공지 지연 10분마다 신뢰 하락이 누적된다.
Good
탐지 즉시 investigating 공지
"결제 기능 이상 징후 확인, 조사 중입니다." — 확인된 사실만 게시하고 cadence에 맞춰 업데이트한다. 추측성 원인 언급은 금지.
IC가 직접 디버깅에 몰두
조율자가 사라지면 병렬 작업이 중단되고 커뮤니케이션이 끊긴다. IC는 의사결정과 조율에만 집중하고, 실제 복구 작업은 Subject Lead에게 위임한다.
Postmortem을 개인 실수 보고서로 작성
"누가 잘못했는가"로 프레이밍하면 blame culture가 형성된다. 다음 장애는 은폐되거나 축소 보고된다. "어떤 안전장치가 없었는가"로 질문을 바꾼다.
Runbook을 개념 문서로 작성
"Redis 메모리가 높으면 적절히 조치한다" 같은 산문은 장애 시 쓸모가 없다. 단계별 명령어, 예상 출력, 분기 조건까지 명시해야 한다.
Chaos Engineering을 무작위 실험으로 수행
steady state 가설과 abort condition 없이 장애를 주입하면 그냥 장애다. Litmus/Gremlin 같은 도구는 가설 기반 실험 프레임워크 위에서만 의미가 있다.
Gotchas
체크리스트

인시던트 대응 체계를 구축·운영할 때 반복 실수를 방지하기 위한 자가 진단 항목.

  • ✓ SEV 기준이 "내부 긴장도"가 아닌 사용자 영향 범위·비즈니스 지표로 객관화되어 있는가? 조직마다 다르게 해석되는 기준은 합의가 아니다.
  • ✓ Status page에 추측성 문구("아마 곧 복구될 것")가 없는가? 복구 지연 시 신뢰가 더 크게 훼손된다. 확인된 사실만 게시한다.
  • ✓ RCA에 timeline이 포함되어 있는가? 시간순 재구성이 빠지면 "왜 그 시점에 그 판단을 했는가"를 이해할 수 없고 교훈이 남지 않는다.
  • ✓ Chaos 실험마다 steady state 정의 + abort condition이 사전에 작성되어 있는가? Litmus/Gremlin은 도구일 뿐이다.
  • ✓ 온콜 primary/secondary handoff 시점이 달력에 명시되어 있는가? "누가 지금 담당인가"에 모호함이 남으면 SEV1 초기 대응이 지연된다.
  • ✓ 복구 순서(data integrity → availability → noncritical)가 사전에 합의되어 있는가? 장애 시점에 우선순위 논쟁은 시간 낭비다.
  • ✓ Runbook의 각 단계가 카피-페이스트 가능한 명령어인가? 판단이 필요한 지점에는 분기 조건과 예상 출력이 함께 적혀 있는가?
