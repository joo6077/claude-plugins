Infra Kit SSOT · 신설 2026-08-13 (Phase 8 kaizen)

인프라 게이트 결과 상태 taxonomy

infra-kit 안에서 이 파일이 상태어 SSOT 다. infra-test 가 생성하는 검증 스크립트, infra-audit 의 rule 판정, infra-reviewer 의 근거 열은 아래 5 상태만 쓰고 자기 문서에서 상태를 다시 정의하지 않는다. 인용만 한다.

여기서 정의하지 않는 것 (상위 SSOT 를 인용만 한다):
· exit 숫자의 의미 → harness/evals/gate-exit-codes.md
· [미검증] 마커 의미 · 임계값 · 카운터 분리 → harness/docs/guides/qa-evaluation-guide.md §Canonical Unverified-Evidence Protocol
Why — 실측

"위반 0" 으로 접히는 세 가지 버그

2026-07-27 Phase 8 은 infra-test 가 생성해주는 CI 검증 스크립트에서 버그 3 건을 고쳤다.

  • 1 grep 앵커 누락 — 미핀닝 3 건 중 1 건만 검출했다.
  • 2 결함을 echo WARN 하고 exit 0 — 게이트가 무력화됐다.
  • 3 매칭 없는 glob 이 리터럴 패턴으로 남음 — "YAML syntax error" 오보를 냈다.
공통 뿌리 셋의 공통 뿌리는 결과에 "검사를 수행하지 못했다" 라는 상태가 없다는 것이다. 상태가 없으면 도구 부재도, 대상 부재도, 실행 실패도 전부 "위반 0" 으로 접힌다. 인프라 감사는 hadolint · actionlint · kubeconform · conftest · cosign · trivy 가 없는 환경, kubectl·레지스트리 접근이 막힌 환경이 흔하므로 이 접힘이 특히 자주 일어난다.

도구 부재를 통과로 집계하는 게이트는 없는 것보다 나쁘다 — 통과 기록이 남기 때문이다.
Taxonomy

5 상태

상태마다 exit 코드와 평가자 분류를 짝지어 둔다. exit 열은 harness/evals/gate-exit-codes.md, 평가자 분류 열은 qa-evaluation-guide.md 에서 온 것이다.

상태 의미 exit (gate-exit-codes.md) 평가자 분류 (qa-evaluation-guide.md)
PASS 검사를 실제로 수행했고 위반이 없다 0 pass PASS
VIOLATION 검사를 수행했고 위반을 찾았다 1 policy_violation FAIL
SKIP_NO_TARGET 검사 대상이 하나도 없었다 (해당 카테고리 미사용) 3 no_data_not_run N/A (카테고리 미해당 · 사유 필수)
TOOL_OR_ENV_MISSING 대상은 있는데 도구·런타임·접근권이 없어 수행하지 못했다. 리포트에는 [미검증] TOOL_OR_ENV_MISSING 으로 적는다 2 usage_or_infra_error [미검증:ENV] = UNVERIFIED_ENV — 단 남용 방지 4 요건 충족 시에만. 미충족이면 [미검증:INVALID]
EXECUTION_ERROR 도구는 있으나 실행·파싱·권한에서 실패했다 2 usage_or_infra_error 도구 출력은 남았으나 결과가 공허하면 [미검증:INVALID] (증거 무효 분기)

exit 숫자의 의미와 [미검증] 분류는 위 두 파일이 정의한다. 이 표는 그 정의를 인용할 뿐 바꾸지 않는다.

01

SKIP_NO_TARGET 과 TOOL_OR_ENV_MISSING 을 섞지 마라

전자는 볼 것이 없는 것이고 후자는 볼 수 없는 것이다. 전자는 정상 종결이지만 후자는 커버리지 손실이다.

taxonomy §5 상태
02

TOOL_OR_ENV_MISSING 과 VIOLATION 도 섞지 마라

도구가 없어 돌리지 못한 rule 은 PASS 도 N/A 도 아니고 [미검증] 이다. 같은 원칙은 규칙 소스에도 해당한다 — audit-criteria.md 를 읽지 못했다면 그 카테고리는 검사하지 않은 것이므로 위반 0 으로 보고하지 마라.

harness — QA 평가 가이드
Precedence

우선순위 — 실행 불완전이 정책 위반을 이긴다

한 run 에서 VIOLATION 과 TOOL_OR_ENV_MISSING/EXECUTION_ERROR 가 동시에 나오면 종료 코드는 2 다. 실행이 불완전한 run 의 결과 집합을 완전한 분석 결과로 보고해서는 안 되기 때문이다 (근거·규칙 원문: harness/evals/gate-exit-codes.md §규칙).

Anti-pattern

위반이 나왔으니 exit 1 로 끝낸다

TOOL_OR_ENV_MISSING 이나 EXECUTION_ERROR 가 같이 나온 run 인데 exit 1 을 내면, 실행이 불완전한 run 의 결과 집합을 완전한 분석 결과로 보고하는 셈이 된다.

Correct

실행 불완전이 섞이면 exit 2

VIOLATION 이 함께 있어도 종료 코드는 2 다. 규칙 원문은 harness/evals/gate-exit-codes.md §규칙에 있고, 이 파일은 그것을 인용한다.

Anti-pattern

종료 코드 하나만 남기고 다른 카운트를 감춘다

종료 코드는 하나뿐이다. 그 하나만 남기면 위반 · 미검증 · 실행 오류가 각각 몇 건이었는지는 보고에서 빠진다.

Correct

요약 줄에 세 카운트를 모두 출력

종료 코드가 하나라고 해서 다른 카운트를 감추지 마라. 아래 형식을 그대로 출력한다. 

VIOLATION=<n>  [미검증]=<n>  EXECUTION_ERROR=<n>
Preamble

머리말 4 카운터 — 검사 시작 전 출력 · 필수

게이트 스크립트와 감사 리포트는 결과보다 먼저 아래 4 줄을 출력한다. 이 머리말이 없으면 "위반 0" 은 해석 불가다 — 분모를 모르기 때문이다. 

대상 <단위> 수     : <n>   (<탐색 경로>)
규칙 소스 수       : <n>   (<규칙 이름 나열 또는 읽은 파일 경로>)
사용 가능 도구 수  : <n>   [<command -v 로 확인된 도구>]
미설치 도구 수     : <n>   [<확인 실패한 도구 — 해당 rule 은 전부 [미검증]>]
A

도구 유무는 추측하지 않는다

command -v <tool> 결과만 적는다. 사용 가능 · 미설치 두 줄 모두 이 출력에서 나온다.

taxonomy §머리말 4 카운터
B

대상 0 이면 그 자리에서 종결

대상 수가 0 이면 그 자리에서 SKIP_NO_TARGET 으로 종결한다 (exit 3). PASS 로 넘기지 마라.

gate-exit-codes.md §4 값
C

읽지 못한 규칙 소스도 [미검증]

규칙 소스를 읽지 못했으면 그 소스 이름을 [미검증] 목록에 넣는다. 읽지 못한 카테고리를 위반 0 으로 보고하지 않는다.

Tool Tiers

핵심 도구 / 선택 도구 분리

Re-verification

재검증 명령 의무

TOOL_OR_ENV_MISSING 을 출력할 때는 환경이 갖춰졌을 때 이 rule 을 통과시킬 실행 가능한 명령을 같은 줄에 적는다. 이것은 상위 SSOT 의 남용 방지 4 요건 4 항이 요구하는 것이며, 없으면 그 항목은 UNVERIFIED_ENV 가 아니라 UNVERIFIED_INVALID_EVIDENCE 로 강등된다. 

[미검증] TOOL_OR_ENV_MISSING: kubeconform 미설치 — 재검증: brew install kubeconform && bash tests/k8s-validation.sh

리포트로 옮길 때 — 네 칸

위 한 줄은 스크립트가 찍는 형식이다. 리포트에서는 이 줄을 그대로 붙이지 않고 네 칸으로 옮긴다 — 스크립트의 이 줄과 그 근거인 command -v <도구> 출력을 막는 것 칸으로 옮기고 나머지 세 칸(시도한 우회 · 통제 불가 사유 · 재검증 명령)을 채운다.

한 줄 + 도구 확인 결과

[미검증] TOOL_OR_ENV_MISSING: … 줄과, 그 줄의 근거인 command -v <도구> 출력. 

[미검증] TOOL_OR_ENV_MISSING: kubeconform 미설치 — 재검증: …

네 칸

  • 칸 1 막는 것 스크립트의 이 줄과 command -v <도구> 출력을 옮긴다
  • 칸 2 시도한 우회 채운다
  • 칸 3 통제 불가 사유 채운다
  • 칸 4 재검증 명령 채운다

이 네 칸을 쓰는 리포트는 세 곳이다.

Checklist

게이트를 쓰기 전 점검

스크립트를 생성하거나 감사 리포트를 쓰기 전에 위 규칙을 순서대로 확인한다.

  • 결과보다 먼저 머리말 4 카운터를 출력했는가 — 대상 수 · 규칙 소스 수 · 사용 가능 도구 수 · 미설치 도구 수.
  • 도구 유무를 추측하지 않고 command -v 결과만 적었는가.
  • 대상 0 을 SKIP_NO_TARGET(exit 3)으로 종결했는가 — PASS 로 넘기지 않았는가.
  • 핵심 도구 검사를 머리말 출력 직후, 첫 rule 실행 전에 두었는가 — 없으면 즉시 EXECUTION_ERROR + exit 2 로 검사를 시작하지 않는다.
  • 선택 도구가 없을 때 해당 rule 만 TOOL_OR_ENV_MISSING 으로 두고 나머지는 계속 검사했는가.
  • TOOL_OR_ENV_MISSING 줄에 재검증 명령을 같은 줄로 붙였는가.
  • 리포트로 옮길 때 스크립트 줄과 command -v 출력을 막는 것 칸에 넣고 나머지 세 칸(시도한 우회 · 통제 불가 사유 · 재검증 명령)을 채웠는가.
  • VIOLATION 과 실행 불완전이 함께 나왔을 때 종료 코드를 2 로 냈는가.
  • 요약 줄에 VIOLATION · [미검증] · EXECUTION_ERROR 세 카운트를 모두 출력했는가.
  • 읽지 못한 규칙 소스를 [미검증] 목록에 넣었는가 — 그 카테고리를 "위반 0" 으로 보고하지 않았는가.
