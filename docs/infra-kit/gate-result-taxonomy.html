Infra Kit SSOT · 신설 2026-08-13 (Phase 8 kaizen)

인프라 게이트 결과 상태 taxonomy

infra-kit 안에서 이 문서가 상태어 SSOT다. infra-test가 생성하는 검증 스크립트, infra-audit의 rule 판정, infra-reviewer의 근거 열은 아래 5 상태만 쓰고 자기 문서에서 상태를 다시 정의하지 않는다. 인용만 한다.

여기서 정의하지 않는 것 (상위 SSOT를 인용만 한다):
· exit 숫자의 의미 → harness/evals/gate-exit-codes.md
· [미검증] 마커 의미 · 임계값 · 카운터 분리 → harness/docs/guides/qa-evaluation-guide.md §Canonical Unverified-Evidence Protocol
Why — 실측

"위반 0"으로 접히는 세 가지 결함

2026-07-27 Phase 8은 infra-test가 생성해주는 CI 검증 스크립트에서 버그 3건을 고쳤다. 셋의 공통 뿌리는 하나다 — 결과에 "검사를 수행하지 못했다"는 상태가 없다는 것.

  • 1 grep 앵커 누락 — 미핀닝 3건 중 1건만 검출했다. 탐지 범위가 좁아진 것을 "위반이 적다"로 읽었다.
  • 2 결함을 echo WARN하고 exit 0 — 게이트가 무력화됐다. 실패해야 할 파이프라인이 초록불로 통과했다.
  • 3 매칭 없는 glob이 리터럴 패턴으로 잔존 — "YAML syntax error" 오보를 냈다. 대상이 0건인 것과 문법이 깨진 것을 구분하지 못했다.
공통 뿌리 상태가 없으면 도구 부재도, 대상 부재도, 실행 실패도 전부 "위반 0"으로 접힌다. 인프라 감사는 hadolint · actionlint · kubeconform · conftest · cosign · trivy가 없는 환경, kubectl·레지스트리 접근이 막힌 환경이 흔하므로 이 접힘이 특히 자주 일어난다.

도구 부재를 통과로 집계하는 게이트는 없는 것보다 나쁘다 — 통과 기록이 남기 때문이다.
Taxonomy

5 상태

상태어 · exit 코드 · 평가자 분류의 3열 매핑이 정본이다. exit 숫자의 의미는 harness/evals/gate-exit-codes.md, [미검증] 계열 분류는 qa-evaluation-guide.md가 상위 SSOT다.

상태 의미 exit 평가자 분류
PASS 검사를 실제로 수행했고 위반이 없다 0 pass PASS
VIOLATION 검사를 수행했고 위반을 찾았다 1 policy_violation FAIL
SKIP_NO_TARGET 검사 대상이 하나도 없었다 (해당 카테고리 미사용) 3 no_data_not_run N/A (카테고리 미해당 · 사유 필수)
TOOL_OR_ENV_MISSING 대상은 있는데 도구·런타임·접근권이 없어 수행하지 못했다. 리포트에는 [미검증] TOOL_OR_ENV_MISSING으로 적는다 2 usage_or_infra_error [미검증:ENV] = UNVERIFIED_ENV — 단 남용 방지 4 요건 충족 시에만. 미충족이면 [미검증:INVALID]
EXECUTION_ERROR 도구는 있으나 실행·파싱·권한에서 실패했다 2 usage_or_infra_error 도구 출력은 남았으나 결과가 공허하면 [미검증:INVALID] (증거 무효 분기)

exit 열은 harness/evals/gate-exit-codes.md, 평가자 분류 열은 harness/docs/guides/qa-evaluation-guide.md의 정의를 인용한 것이다. 이 표에서 그 정의를 변경하지 않는다.

01

SKIP_NO_TARGET과 TOOL_OR_ENV_MISSING을 섞지 마라

전자는 볼 것이 없는 것이고 후자는 볼 수 없는 것이다. 전자는 정상 종결이지만 후자는 커버리지 손실이다. 같은 자리에 넣는 순간 "이 프로젝트는 해당 없음"과 "이 환경은 검사 불가"가 구별되지 않는다.

02

TOOL_OR_ENV_MISSING과 VIOLATION도 섞지 마라

도구가 없어 돌리지 못한 rule은 PASS도 N/A도 아니고 [미검증]이다. 같은 원칙이 규칙 소스에도 적용된다 — audit-criteria.md를 읽지 못했다면 그 카테고리는 검사하지 않은 것이므로 위반 0으로 보고하지 마라.

harness — QA 평가 가이드
Precedence

실행 불완전이 정책 위반을 이긴다

한 run에서 VIOLATION과 TOOL_OR_ENV_MISSING/EXECUTION_ERROR가 동시에 나오면 종료 코드는 2다. 실행이 불완전한 run의 결과 집합을 완전한 분석 결과로 보고해서는 안 되기 때문이다.

Anti-pattern

위반이 있으니 exit 1로 끝낸다

도구 3개가 미설치라 rule 절반을 못 돌렸는데 exit 1만 남기면, "검사했고 위반 N건"이라는 완전한 분석 결과로 읽힌다. 커버리지 손실이 기록에서 사라진다.

Correct

실행 불완전이 있으면 exit 2

VIOLATION이 함께 있어도 종료 코드는 2다. 근거·규칙 원문은 harness/evals/gate-exit-codes.md §규칙을 따른다. 이 문서는 그 규칙을 인용할 뿐 재정의하지 않는다.

Anti-pattern

종료 코드 하나로 요약을 대신한다

exit 2만 보고 나머지 카운트를 감추면 위반이 몇 건인지, 미검증이 몇 건인지, 실행 실패가 몇 건인지를 호출자가 알 수 없다.

Correct

요약 줄에 세 카운트를 모두 출력

종료 코드가 하나라고 해서 다른 카운트를 감추지 마라. 아래 형식을 그대로 출력한다. 

VIOLATION=<n>  [미검증]=<n>  EXECUTION_ERROR=<n>
Preamble

머리말 4 카운터 — 검사 시작 전 출력 · 필수

게이트 스크립트와 감사 리포트는 결과보다 먼저 아래 4줄을 출력한다. 이 머리말이 없으면 "위반 0"은 해석 불가다 — 분모를 모르기 때문이다. 

대상 <단위> 수     : <n>   (<탐색 경로>)
규칙 소스 수       : <n>   (<규칙 이름 나열 또는 읽은 파일 경로>)
사용 가능 도구 수  : <n>   [<command -v 로 확인된 도구>]
미설치 도구 수     : <n>   [<확인 실패한 도구 — 해당 rule 은 전부 [미검증]>]
A

도구 유무는 추측 금지

command -v <tool> 결과만 적는다. "보통 설치되어 있다"는 가정은 머리말을 거짓으로 만든다.

taxonomy §머리말 4 카운터
B

대상 0건이면 그 자리에서 종결

SKIP_NO_TARGET으로 종결한다 (exit 3). PASS로 넘기지 마라 — 검사하지 않은 것을 통과로 기록하는 순간 그 기록이 다음 사이클을 속인다.

taxonomy §머리말 4 카운터
C

읽지 못한 규칙 소스도 [미검증]

규칙 소스를 읽지 못했으면 그 소스 이름을 [미검증] 목록에 넣는다. 규칙이 없으면 판정도 없다.

harness — QA 평가 가이드
Tool Tiers

핵심 도구 / 선택 도구 분리

미설치를 전부 하드 실패로 막으면 CI 재현성은 좋아지지만 기여자 진입 장벽이 오른다 (트레이드오프). 그래서 두 층으로 나눈다.

층 없을 때 이유
핵심 도구
(grep · python3)		 즉시 EXECUTION_ERROR + exit 2. 검사를 시작하지 않는다 없으면 모든 rule 결과가 오보다. 실측 회귀: grep이 없으면 grep -q가 비영 종료해 "checkout 스텝 없음" VIOLATION을 오보했다
선택 도구
(hadolint · actionlint · kubeconform · conftest · cosign · trivy) 		해당 rule만 TOOL_OR_ENV_MISSING, 나머지는 계속 검사 부분 커버리지가 0 커버리지보다 낫다
배치 위치 핵심 도구 검사는 머리말 출력 직후, 첫 rule 실행 전에 둔다. 그래야 사용자가 "무엇이 없어서 아무것도 못 했는지"를 본다.
Re-verification

재검증 명령 의무

TOOL_OR_ENV_MISSING을 출력할 때는 환경이 갖춰졌을 때 이 rule을 통과시킬 실행 가능한 명령을 같은 줄에 적는다. 이것은 상위 SSOT의 남용 방지 4 요건 4항이 요구하는 것이며, 없으면 그 항목은 UNVERIFIED_ENV가 아니라 UNVERIFIED_INVALID_EVIDENCE로 강등된다. 

[미검증] TOOL_OR_ENV_MISSING: kubeconform 미설치 — 재검증: brew install kubeconform && bash tests/k8s-validation.sh

같은 줄에 붙이는 이유

미검증 항목은 나중에 누군가가 되살려야 한다. 명령이 리포트 밖에 있으면 그 항목은 영구 미검증으로 남는다. 줄 단위로 자기완결해야 grep 한 번으로 복구 절차가 나온다.

taxonomy §재검증 명령 의무

강등 규칙

재검증 명령이 없으면 UNVERIFIED_ENV로 인정되지 않는다. 분류 자체와 남용 방지 4 요건의 정의는 상위 SSOT에 있으며 이 문서는 그것을 인용만 한다.

Checklist

게이트를 쓰기 전 점검

스크립트를 생성하거나 감사 리포트를 쓰기 전에 아래를 순서대로 확인한다.

  • 결과보다 먼저 머리말 4 카운터를 출력했는가 — 대상 수 · 규칙 소스 수 · 사용 가능 도구 수 · 미설치 도구 수.
  • 도구 유무를 command -v로 실제 확인했는가. 추측으로 적은 줄은 머리말을 거짓으로 만든다.
  • 대상 0건을 SKIP_NO_TARGET(exit 3)으로 종결했는가 — PASS로 넘기지 않았는가.
  • 도구 부재를 TOOL_OR_ENV_MISSING으로 적고 같은 줄에 재검증 명령을 붙였는가.
  • 핵심 도구 검사를 첫 rule 실행 전에 배치했는가 — 없으면 즉시 EXECUTION_ERROR + exit 2로 중단해야 한다.
  • VIOLATION과 실행 불완전이 함께 나왔을 때 종료 코드를 2로 냈는가.
  • 요약 줄에 VIOLATION · [미검증] · EXECUTION_ERROR 세 카운트를 모두 출력했는가.
  • 읽지 못한 규칙 소스를 [미검증] 목록에 넣었는가 — 그 카테고리를 "위반 0"으로 보고하지 않았는가.
