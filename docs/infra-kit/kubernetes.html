리소스 매니페스트, Helm/Kustomize, RBAC, 네임스페이스, Pod Security Standards, requests/limits, HPA/VPA, 프로브, PDB. 클러스터는 기본값이 안전하지 않다 — 원칙으로 기본값을 덮어쓴다.

Core Principles
핵심 원칙 8

Kubernetes 공식 문서와 Helm Best Practices 기반. requests/limits, probe 역할, RBAC 스코핑이 운영 안정성의 기본 축이다.

1
모든 워크로드에 requests/limits를 명시한다
requests는 스케줄러가 노드를 선택하는 기준이고, limits는 런타임 상한이다. requests가 없으면 노드에 과밀 배치되고, limits가 없으면 단일 Pod가 노드 전체를 점유할 수 있다. 두 값을 모두 명시하여 예측 가능한 스케줄링과 격리를 확보한다.
k8s — Manage Resources Containers
2
liveness/readiness/startup probe 역할을 분리한다
liveness 실패는 컨테이너 재시작, readiness 실패는 서비스 엔드포인트 제외, startup은 느린 초기화 완료 대기 전용이다. 역할을 혼동하면 초기화 중인 Pod가 재시작 루프에 빠지거나, 장애 Pod가 트래픽을 계속 받는다.
k8s — Liveness/Readiness/Startup Probes
3
네임스페이스는 팀/정책 경계용이다
네임스페이스는 RBAC, ResourceQuota, NetworkPolicy의 스코핑 단위다. 팀, 환경(dev/staging/prod), 서비스 그룹 단위로 분리한다. 버전 구분(v1/v2)에는 네임스페이스가 아닌 labels와 selectors를 사용한다. default에 워크로드를 배치하지 않는다.
k8s — Namespaces
4
RBAC는 namespace-scoped RoleBinding을 우선한다
ClusterRoleBinding은 클러스터 전체에 영향을 주므로 최소한으로 제한한다. 대부분의 권한은 namespace-scoped RoleBinding으로 충분하다. wildcard(*) 리소스/동사, cluster-admin 바인딩을 남용하지 않는다.
k8s — RBAC Good Practices
5
Pod Security Standards를 단계적으로 도입한다
restricted 프로파일을 최종 목표로 설정하되, 기존 워크로드에 즉시 enforce하면 대량 실패가 발생한다. warn → audit → enforce 순서로 단계적으로 적용한다. 네임스페이스 레이블로 프로파일을 지정하며, privileged는 시스템 워크로드에만 허용한다.
k8s — Pod Security Standards
6
HPA와 VPA의 역할을 구분한다
HPA는 부하 증가 시 Pod 수를 늘린다. VPA는 개별 Pod의 requests/limits를 실 사용량에 맞게 조정(rightsizing)한다. 같은 CPU 메트릭에 HPA와 VPA를 동시 적용하면 충돌한다 — VPA는 메모리 rightsizing 또는 recommendation 모드로만 병행한다.
k8s — Horizontal Pod Autoscale
7
Helm은 값 구조와 재사용성, Kustomize는 base/overlay 조합이다
Helm은 템플릿 엔진으로 values.yaml을 통해 환경별 설정을 주입한다. Kustomize는 base 매니페스트 위에 overlay를 패치하는 방식으로 원본을 수정하지 않는다. 프로젝트 특성에 맞게 하나를 선택하거나 Helm 생성 후 Kustomize로 환경별 패치하는 조합도 가능하다.
Helm — Chart Best Practices
8
PDB는 자발적 disruption 완화 전용이다
PodDisruptionBudget은 노드 drain, 클러스터 업그레이드 등 자발적 disruption 시 최소 가용 Pod 수를 보장한다. 하드웨어 장애, OOM kill 같은 비자발적 disruption에는 적용되지 않는다. minAvailable/maxUnavailable로 설정하며, 모든 다운타임을 방지하는 장치가 아니다.
k8s — Disruptions
Probes
Probe 역할 분리

세 probe의 효과는 완전히 다르다. 혼동하면 재시작 루프나 장애 Pod 트래픽 수신 같은 심각한 버그로 이어진다.

livenessProbe
→ Container Restart
컨테이너가 살아있는지 확인. 실패 시 kubelet이 컨테이너를 재시작한다. 애플리케이션이 데드락 상태일 때 복구 수단.
readinessProbe
→ Endpoint Removal
트래픽을 받을 준비가 되었는지 확인. 실패 시 Service의 Endpoints에서 제외된다. 컨테이너는 계속 실행되며 재시작되지 않는다.
startupProbe
→ Gate Other Probes
초기화가 끝날 때까지 liveness/readiness를 비활성화한다. 부팅이 느린 앱이 재시작 루프에 빠지지 않게 한다.
Reference Values
수치/기준값

probe 기본값, HPA 동기화 주기, CPU 단위 등. 기본값을 알고 있어야 의도적으로 조정할 수 있다.

항목 값 비고
Probe 기본 periodSeconds 10 점검 간격
Probe 기본 timeoutSeconds 1 응답 대기 시간
Probe 기본 failureThreshold 3 연속 실패 횟수
terminationGracePeriodSeconds 30 SIGTERM 후 SIGKILL까지
Startup probe 예시 failureThreshold 30 × periodSeconds 10 = 300s 느린 앱 부팅 허용
HPA sync 주기 15s --horizontal-pod-autoscaler-sync-period
HPA CPU 초기화 안정 기간 5m --horizontal-pod-autoscaler-cpu-initialization-period
HPA readiness delay 30s --horizontal-pod-autoscaler-initial-readiness-delay
CPU 최소 단위 1m 1 milliCPU = 0.001 CPU
500m CPU 0.5 CPU 코어 1000m = 1 CPU
Anti-Patterns
피해야 할 패턴

k8s 클러스터에서 반복적으로 관찰되는 설정 실수. probe 역할 혼동이 특히 파괴적이다.

Bad
liveness probe로 readiness를 대체
"요청이 느려지면 재시작하면 되지"라는 착각. 일시적으로 바쁜 Pod가 불필요하게 재시작되면서 응답이 더 느려지고, 캐스케이딩 장애로 번진다. 부하 = 재시작 사유가 아니다.
Good
readiness로 트래픽 제외 + liveness로 데드락 감지
readiness는 "지금 트래픽을 받을 수 있는가", liveness는 "이 컨테이너를 재시작해야 하는가"로 질문이 다르다. 두 probe의 엔드포인트와 임계치를 독립적으로 설계한다.
모든 워크로드를 default 네임스페이스에 배치
RBAC, ResourceQuota, NetworkPolicy 스코핑이 불가능해진다. 팀/환경별 네임스페이스 분리가 기본이며, default는 튜토리얼용이라고 취급한다.
requests 없이 limits만 설정
스케줄러가 적절한 노드를 선택하지 못하고, QoS 클래스가 Burstable로 설정되어 OOM 우선순위가 높아진다. requests = 스케줄링 기준, limits = 런타임 상한이다.
ClusterRoleBinding으로 광범위 권한 부여
한 서비스의 권한 과잉이 클러스터 전체 보안 위험으로 확대된다. namespace-scoped RoleBinding으로 시작하고, ClusterRoleBinding은 예외로만 사용한다.
PDB를 롤링 업데이트 보호로 오해
PDB는 자발적 disruption(drain)용이다. 롤링 업데이트 전략은 Deployment의 maxUnavailable/maxSurge로 제어한다. 두 메커니즘을 혼동하면 업데이트가 교착된다.
Gotchas
체크리스트

매니페스트 작성·배포 시 반복 실수를 방지하기 위한 자가 진단 항목. 기본값이 의외인 경우가 많다.

  • ✓ limits만 설정하면 requests가 limits로 복사될 수 있음을 인지하는가? LimitRange가 설정된 네임스페이스에서 requests를 생략하면 기본값이나 limits 값이 requests로 들어가 스케줄링이 실패할 수 있다.
  • ✓ readiness probe 실패는 재시작이 아닌 엔드포인트 제외라는 점을 이해하는가? Service의 Endpoints 목록에서 해당 Pod가 빠질 뿐, 컨테이너는 계속 실행된다.
  • ✓ PDB는 kubectl delete pod를 막지 못한다는 것을 아는가? 직접 삭제는 Eviction API를 거치지 않으므로 PDB가 개입하지 않는다.
  • ✓ VPA는 별도 CRD 설치가 필요하다는 것을 확인했는가? k8s 코어에 포함되지 않으며, autoscaler 리포지토리에서 Recommender/Updater/Admission Controller를 별도 설치해야 한다.
  • ✓ startup probe가 필요한 앱(JVM, 대규모 초기화 등)을 식별하고 failureThreshold × periodSeconds로 충분한 부팅 시간을 확보했는가?
  • ✓ HPA와 VPA를 같은 CPU 메트릭에 동시 적용하지 않았는가? VPA는 메모리 rightsizing 또는 recommendation 모드로만 병행한다.
  • ✓ Pod Security Standards를 warn → audit → enforce 단계로 도입 중인가? 즉시 enforce하면 기존 워크로드가 대량 실패한다.
