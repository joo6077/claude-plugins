## 2. 근거 등급 재판정

이 킷의 핵심 자산은 규칙 목록이 아니라 **규칙마다 붙은 강도 등급** 이다. 이관 과정에서 세 건을 격하했다.

| 규칙 | 구 상태 | 판정 | 근거 |
|---|---|---|---|
| "모든 하위 위젯은 별도 **파일**" | 사실상 MUST | **관측 컨벤션** | 공개 1차 출처는 "different widgets" 까지만 지지하고 "different files" 는 지지하지 않는다 |
| 헬퍼보다 위젯 클래스 선호 | MUST 로 인용됨 | **SHOULD** | 공식 문구가 `prefer` 이고, 공식 인라인 대안(`Builder`)과 함수 반환 예시가 공식 문서에 존재 |
| `effective*` / `resolved*` 접두사 금지 | 탐지 연구 인용 | **관측 컨벤션** | 접두사별 통계가 공개 1차 문헌에 없음 (2026-08 확인). 실측 9건 / 4파일만 근거 |
| 위젯 접미사 taxonomy | "업계 표준" 서술 | **합성 규칙** | 6개 디자인 시스템 중 어느 곳도 이 구분을 문서화하지 않는다. 화면 상단 하나를 4가지 용어로 부른다 |

## 3. 인용 교체

| 제외 | 사유 | 대체 |
|---|---|---|
| DetectGPT (ICML 2023) | 자연어 텍스트 탐지기 | Droid (EMNLP 2025) — 코드 대상 |
| Binoculars (ICML 2024) | 자연어 텍스트 탐지기 | SemEval-2026 Task 13 — 코드 대상 벤치마크 |
| LLM 텍스트 스타일로메트리 | 대상이 텍스트 | SANER 2025 — 다국어 코드 스타일로메트리 |
| 비공개 사내 코딩 가이드라인 PDF | 공개 URL 없음. 소비자가 검증 불가 | Flutter 공식 성능 문서 + 위젯 API 문서 |

포지셔닝도 함께 뒤집었다. 코드 탐지 문헌은 표면적 humanizing 을 `Adversarial` 이라는 **별도 위험군** 으로 분류한다. 따라서 "AI 티 제거" 를 목표 문장으로 삼으면 그 목표가 학계가 위험으로 분류한 범주와 겹친다. 킷의 목표는 maintainability / style gate 이고 톤 개선은 부산물이다.

## 4. 모순 판정 (킷 콘텐츠 확정)

원본은 수정하지 않았다. 킷에는 승자만 실었다.

| 사안 | 판정 |
|---|---|
| 섹션 번호 중복·순서 붕괴 | 번호 체계를 승계하지 않고 주제별 reference 로 재배치 |
| "사용처 1곳 위젯은 분리 안 함" ↔ "예외 없이 별도 파일" | 후자 승. 단 §2 에 따라 관측 컨벤션으로 표기 |
| `for-in` children 채우기 권장 ↔ 전면 금지 | 금지 승. 권장 미이관 |
| `_build*` 1단 헬퍼 허용 조항 | 미이관 (개정으로 폐기됨) |
| 폐기 선언 후 본문 잔존 38줄 | 미이관. 폐기 이력 한 줄만 |
| `useValueChanged` ↔ `useEffect` | `useEffect` 승 |
| `- 반환값: 없음` 유지 ↔ 삭제 | 유지 승 (실측 246건이 이 관례) |
| Props 판정 규칙 3중 중복 | 하나를 SSOT 로, 나머지는 포인터 |
| 줄 수 임계치 ↔ 관심사 분리 | 관심사 분리가 상위 원칙, 줄 수는 하위 트리거 |
| 과잉 추출 금지 ↔ 인라인 위젯 금지 | 후자 승. 전자는 폐기 마킹 대상 |
| 피드백 기록 위치 (프로젝트 로그만 ↔ 전 착지점) | 전 착지점 승 |
| HookWidget 선호 ↔ hooks 3종 통합 | 후자로 통합 |
| Props 설계 ↔ Props 제거 기준 | **스코프 분리** — 전자는 신규 설계, 후자는 기존 리팩토링. 둘 다 유지 |
| 필드 문서 주석 | **비자명한 계약이 있을 때만 허용.** 이름 번역·자명한 필드 문서는 금지 |
| 헬퍼 시그니처 예외 조항 | 근거 사례가 소멸해 예외 삭제 |
| 코드 생성 명령 (래퍼 없이 ↔ 래퍼 경유) | 래퍼 경유 승. 래퍼 없는 명령은 종료 코드 0으로 조용히 실패한다 |
| bare catch | 의도된 컨벤션으로 유지. 좁히라는 규칙 미이관. 공개 근거 없어 관측 컨벤션 |

## 6. 구조 결정

- **3축 레이어** — 스택(core/adapter) · 언어(neutral/locale) · 프로젝트(universal/param). 구 spec 의 2축으로는 문서 주석 라벨 같은 규칙이 표현되지 않는다.
- **스킬 3개 상한** — audit 은 별도 스킬로 분리하지 않고 각 스킬에 내장한다 (규칙 보유 스킬은 자기 audit 을 내장한다).
- **어댑터는 dart-flutter 하나** — 위반 실측이 없는 스택에 어댑터를 만드는 것은 이 킷 자신의 원칙 위반이다. 계약만 정의해 두고 관측 시 파일 하나를 추가한다.
- **references 는 flat** — 검증 스크립트 glob 과 문서 동기화가 1-level 만 본다.

## 7. 후속 안건 (이번 범위 밖)

1. **원본 정리** — 섹션 번호 재배열, 폐기 조항 본문 삭제, 로그 번호 중복, 평가자 규칙의 stale 인용, 비공개 PDF 인용 대체.
2. **글로벌 메모리 정리** — 폐기 3건을 삭제하지 말고 "폐기됨 + 승계 포인터" 로 마킹, 빈 `name` 2건, 인덱스 누락 1건, stale 브랜치명, 최근 규칙군 대응 메모리 부재.
3. **flutter-toolkit 충돌 8건** — 전부 실제 파일 대조로 확인됐다. 가장 위험한 것은 리팩터 체크리스트가 의존성 파일만 보고 조건 없이 상태 관리 규칙 소스를 로드하는 소비 경로다.
4. **피드백 기록 ↔ 승격 파이프라인 절차 충돌 4건.**
5. **프로젝트 지침 문서 다이어트** — 승격분 제거 후 예산 초과 해소.
