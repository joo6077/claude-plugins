카운터 분리

자동 REJECT 임계 2 는 invalid_evidence 에만 적용된다

invalid_evidence(B2 + C) — 0 건 통상 · 1 건 PASS 허용 + 경고 명시 · 2 건 이상 자동 REJECT(개별 FAIL 이 없어도).

env_gaps(B1) — 자동 REJECT 카운터에 합산하지 않는다. 대신 verified_coverage = (조건 총수 − env_gaps) / 조건 총수 가 0.60 미만이면 APPROVE 불가이고, verdict 는 REJECT 가 아니라 BLOCKED(insufficient_verified_coverage)다.

임계 0.60 은 증명된 값이 아니라 출발값이다. 이 게이트가 BLOCKED 를 낸 사례가 3 회 누적되면 evaluator-kaizen 이 실측 분포로 다시 정한다.

남용 방지 4 요건

하나라도 없으면 B1 이 아니라 B2 다

(1) 1 차 도구 시도 기록 — 계약이 지정한 도구를 실제로 호출하고 그 결과(에러·타임아웃·미설치 출력)를 인용 (2) fallback 시도 기록 — 계약의 단계 2 를 수행(계약에 fallback 이 없으면 "fallback 미기술" 을 계약 결함으로 기록하는 것까지) (3) 실패 로그 — 서술이 아니라 출력으로("확인 불가했다" 는 로그가 아니다) (4) 통제 불가 사유 + 재검증 명령.

왜 4 요건인가: 카운터를 분리하면 "미구현을 도구 부재로 세탁" 하는 경로가 열린다. 4 요건은 그 세탁을 비싸게 만든다 — 세탁하려면 존재하지 않는 도구 호출 로그와 재검증 명령까지 지어내야 하고, 그것은 유효성 검사 4(출처)에서 걸린다.

같은 조건이 2 iteration 연속 UNVERIFIED_ENV 면 그것은 환경 문제가 아니다

계약이 검증 경로를 적지 않은 결함이다. 해당 조건을 [low-confidence] 로 강등하고 Improvement 를 [조건 ID] 검증경로-미기재 — {명시할 fallback 오라클 또는 부여할 MCP 바인딩} 형식으로 적는다(산문 권고 금지). 그리고 이 조건은 더 이상 env_gaps 로 세지 않고 invalid_evidence 로 센다 — 환경을 두 번 기다려 준 뒤에도 계약이 그대로면 그것은 계약 측 미해결이다.

트레이드오프 (반드시 읽어라): abstention 완화는 회피 경로가 된다. 4 요건 없이는 UNVERIFIED_ENV 분류를 허용하지 마라. 이 개정은 "미검증을 봐주는 규칙" 이 아니라 "통제할 수 없는 것과 통제할 수 있는 것을 다른 장부에 적는 규칙" 이다.

왜 별도 축인가

판정자는 타당성이 아니라 그럴듯함을 채점한다

프런티어 판정자 2 종이 필요한 아티팩트를 한 번도 가져오지 않은 답변에 0.90 / 0.85 를 주고 추론이 "tight and well-structured" 라고 칭찬했다. 실행 trace 를 결정론적으로 대조하자 같은 답변의 점수는 0.000 이었다.

같은 연구의 실패 분류 중 invalid absence — "충분히 탐색하지 않고 없다고 단언" — 이 실제 사고 형태다. 빈 스냅샷을 "문제 없음" 으로 읽는 것이 곧 invalid absence 다.

검사 5 특칙

서술은 실행이 아니다 (zsh 이식성 포함)

zsh 는 기본 nomatch 라 매치 없는 glob 이 명령을 통째로 죽인다 — for f in a.md b-*.md 는 b-*.md 가 없으면 루프에 진입조차 못 하고 [ -f "$f" ] || continue 가드도 무력하다. 셸 무관 열거는 find … \( -name A -o -name B \) 로 쓴다.

exit 0 은 통과 기준이 아니다. 스니펫이 뽑아낸 값이 비교 대상과 실제로 일치하는지 본다 — frontmatter reader 가 따옴표를 안 벗기면 owner_session: "abc" 는 abc 와 영원히 불일치한다(출력은 나오지만 로직은 죽어 있다).

이 특칙이 없어서 놓친 사고: 적대적 검증에서 25/25 조건이 문언상 PASS 였는데 런타임은 세 군데가 깨져 있었다. 오라클이 문서 서술만 검사했기 때문이다.

User Reports
사용자 보고가 들어오면 — 이 절차가 유효성 5 검사보다 먼저다

두 절은 서로 다른 검사다. §Evidence Validity Gate 는 자기 증거가 무언가를 입증하는가를 PASS 확정 전에 묻는다. §User-Reported Failure Protocol 은 자기 증거와 사용자 증거가 충돌할 때의 우선순위를 사용자 보고가 들어온 시점에 묻는다(이미 PASS 를 준 뒤일 수 있다). 순서를 뒤집으면 "내 증거는 유효하다" 를 근거로 사용자 보고를 기각하게 된다.

Which Contract
평가를 시작하기 전 — 어떤 계약을 채점하는가

계약이 단일 고정 경로였을 때는 없던 문제다. 같은 프로젝트에서 세션을 병렬로 돌리면 A 의 평가자가 B 의 계약을 채점한다. 2026-07-27 카이젠에서 실제로 발생했다.

1   HARNESS_CONTRACT 로 경로를 받았고 test -f 통과 ────────→ 그 경로
1x  경로를 받았는데 파일이 없다 ───────────────────────────→ BLOCKED (아래로 흘려보내지 않는다)
0   후보가 0 건 ─────────────────────────────────────────→ BLOCKED (부재 · 복구책이 다르다)
2   status: active + owner_session 일치가 정확히 1 개 ─────→ 그것
3   status: active 가 전체에서 정확히 1 개 ────────────────→ 그것
3.5a active 0 개 + 레거시 plain sprint-contract.md 존재 ──→ 그것 + legacy_contract_used
3.5b active 0 개 + plain 없음 + 레거시 정확히 1 개 ────────→ 그것 + legacy_contract_used
4   그 외 (active 2 개 이상 · 브릿지 불성립) ───────────────→ BLOCKED (후보 나열 + 복구 2 가지)
판정 근거

파일 개수가 아니라 status 다

status: active 가 명시된 계약만 active 로 센다. 필드가 없거나 frontmatter 자체가 없으면 레거시로 간주해 active 후보에서 제외한다(파싱 실패로 중단하지 않는다).

레거시 제외는 선택이 아니라 필수다 — 실측 배포본의 접미형 계약 40 개는 전부 status 가 없다. active 로 세면 후보가 27 개가 되어 정상 프로젝트의 QA 가 영구 BLOCKED 된다. 디렉토리의 파일 수를 세는 구현은 이 지점에서 반드시 깨진다.

모호할 때

조용히 하나를 고르는 fallback 을 두지 않는다

mtime 최신순으로 고르거나 그럴듯한 것을 골라 진행하면, 잘못 고른 계약의 verdict 가 다른 세션의 작업을 오판하고 글로벌 피드백 저장소까지 오염시킨다. 오염된 피드백은 이후 카이젠의 입력이 되므로 손실이 누적된다.

BLOCKED 보고에는 후보 목록(경로 · status · owner) 과 레거시 제외 건수, 복구 방법 2 가지를 함께 적는다. 사유만 적은 BLOCKED 는 사용자를 막다른 길에 세우는 것이다.

CONTRACT_ROOT

먼저 만나는 .harness 에서 멈춘다

project.yaml 만 찾으며 올라가는 구현은 계약을 실제로 가진 디렉토리를 지나쳐 조상의 다른 계약을 경고 없이 채점한다. BLOCKED 는 사용자가 알아채고 고칠 수 있지만 이 오귀속은 아무 신호도 남기지 않는다 — BLOCKED 보다 나쁘다.

.harness 는 있는데 project.yaml 이 없으면 그 디렉토리를 채택하고 contract_root_unconfigured: true 를 노출한다. 경고이지 실패가 아니다 — 복구책은 /harness init 이다. 조상의 project.yaml 을 대신 읽지 마라.

지문을 고정하고 저장 직전 재확인한다

선택 시점에 경로 + 내용 sha256 + status 3 요소를 고정하고 verdict 저장 직전 다시 계산해 대조한다. 하나라도 다르거나 파일이 사라졌으면 verdict 를 저장하지 않고 BLOCKED — 이미 산출한 판정은 다른 계약에 대한 것이므로 무효다.

APPROVE 직후 status 를 done 으로 전환하는 주체는 평가자다. 전환하지 않으면 active 가 단조 증가해 두 번째 스프린트부터 ladder 3 이 무너진다. 단 레거시에는 status 를 새로 써 넣지 마라 — 다음 호출에서 브릿지 후보가 사라져 없던 BLOCKED 를 만든다.

샘플링 정직성

불가피하게 샘플링했다면 그 사실을 숫자로 남긴다

샘플링 조건에는 [샘플링-N개/전체-M개] 태그를 붙이고, 미검증 대상은 invalid_evidence 로 집계한다 — 시간 제약은 도구·환경 부재가 아니라 "검사되지 않음" 이므로 ENV 가 아니다.

l3_unreached 진단이 13 회 누적됐다. 부분 검증을 감추면 다음 세션의 평가자가 구멍을 찾지 못한다.

서브체크 분해

Likert 대신 boolean — 일치도 0.45 개선

각 조건을 Yes/No 로 답할 수 있는 boolean 서브체크로 분해한다(질문당 하나의 검증 포인트만). PASS 비율이 아니라 전체 PASS 가 조건 충족 기준이며, 서브체크 하나라도 FAIL 이면 조건 FAIL 이다.

고수준 항목이 여전히 모호하면 한 번 더 재귀 분해한다. 한 번 분해했는데도 서브체크 1 개가 10+ 라인을 Read 해야 판정 가능하면 그것이 재귀 분해 신호다.

용어 충돌

계약의 [L1] 을 검증 깊이 L1 로 읽지 마라

이 가이드의 L1/L2/L3 는 evaluator 검증 깊이이고, 계약서의 [L1]/[L2]/[L3] 태그는 조건 구체성 레벨이다. 같은 기호지만 의미가 다르다.

레거시 매핑은 [L1] ≡ [exact], [L2] ≡ [structural], [L3] ≡ [goal]. 검증 깊이는 계약 태그와 무관하게 항상 L3 까지 간다.

Discrimination
측정이 구현을 실제로 재는가 — 9 항에만 적용한다

유효성 검사 3(반증 가능성)은 묻기만 했다. 실측에서 그 질문에 "예" 라고 답하고 넘어간 뒤 사후 mutation 으로 정반대가 확인됐다 — ER-02: "실제 코드에서 동시성 가드를 완전히 삭제해도 이 테스트는 여전히 통과한다." 필요한 것은 새 질문이 아니라 답을 강제로 확인하는 절차다.

동시성 가드인증 / 권한 멱등성입력 검증 데이터 유실 방지마이그레이션 안전성 재시도 / 중복제거보안 경계 사용자 결함 보고 ↔ 테스트 PASS 충돌
1 · 결합 확인 (static · 필수)

측정이 계약이 지목한 구현을 직접 경유하는지 Grep 으로 본다. 테스트가 로직을 독립 재작성했으면 결합이 0 이고 그 측정은 증거가 아니다 → 조건 FAIL. 근거란에 결합: {테스트 파일:라인} → {구현 심볼} 을 남긴다.

2 · 계약의 음성 대조: 절 확인

기재돼 있으면 그 지점을 판정 기준으로 삼는다. 기재가 없으면 조건 결함이지 구현 결함이 아니다 — 자동 FAIL 하지 말고 Improvement 를 [조건 ID] 측정-판별력-미기재 로 기록한다.

3 · 실행 음성 대조 (안전 조건부)

(a) 대상 파일이 git status --porcelain 기준 clean (b) 변형 지점이 1~2 개이고 이번 스프린트 diff 범위 안 (c) 실행 후 원상 복구 확인. 하나라도 불충족이면 실행하지 말고 discrimination: static-only 를 남긴다.

금지 3 가지
  • 전체 repo mutation score 임계값을 세우지 마라. full mutation adequacy 달성은 산업 적용 보고에서 "neither practical nor desirable" 로 결론났다
  • 9 항 밖의 조건에 강제하지 마라 — 평가가 계약에 없는 비용을 만든다
  • cosmetic / doc-only 변경에 요구하지 마라 — [structural] 조건은 대상을 지우면 자명하게 실패하므로 음성 대조가 무의미하다

원본 작업트리를 변형한 채 남기는 것은 평가자가 평가 대상을 오염시키는 행위다.

Pre-Evaluation Checklist
평가를 시작하기 전 · 판정을 내리기 전
  • ✓계약을 ladder 로 결정론적으로 특정했고, 지문(경로 + sha256 + status)을 고정했는가?
  • ✓파싱한 조건 수가 frontmatter conditions: 값과 일치하는가? (다르면 평가를 시작하지 말고 BLOCKED)
  • ✓조건을 조건 섹션에서만 읽었는가? 서술 섹션(배경·GAP 분석 등)의 불릿을 조건으로 오파싱하지 않았는가?
  • ✓verify_seal 을 돌렸는가? SEAL_ABSENT 는 경고, 미해소 SEAL_BROKEN 은 REJECT다 — 조용히 다시 봉인하지 마라
  • ✓각 조건의 FAIL 상태를 1 문장으로 기술할 수 있는가? 범위어에 enumerate 가 있는가? 검증 수단이 명시됐는가?
  • ✓상태 의존 측정 명령(git diff 등)에 계약이 Given: 전제를 적었는가? 없으면 임의로 고르지 말고 플래그를 세우고 실제 사용한 상태를 근거란에 기록했는가?
  • ✓계약을 먼저 읽고 기대 행동을 확립한 뒤 코드를 봤는가? (코드를 먼저 읽으면 구현 추종 편향에 빠진다)
  • ✓안티패턴 Grep 전에 패턴의 스택과 대상 파일의 스택이 일치하는지 확인했는가? 불일치면 N/A (스택 불일치) 로 기록했는가? (매치 0 건을 PASS 로 적지 마라)
  • ✓판정 직전 모든 조건 ID 를 번호순으로 1 회 더 전수 스캔했는가? "비슷한 조건이 PASS 했으니 이것도 PASS" 를 쓰지 않았는가?
  • ✓같은 유형의 improvement 가 2 회째면 contract_ambiguity_notes 로 승격, 3 회째면 조건을 [low-confidence] 로 강등했는가?
  • ✓Improvement 를 구체 대체 문구로 적었는가? ("모호하다" 가 아니라 "Given: 스테이징 완료 후 를 붙이고 --cached 를 쓸 것")
  • ✓Unverifiable Summary 블록에 invalid_evidence · env_gaps · verified_coverage · 연속 ENV 승급 · verdict 영향을 전부 기록했는가?
평가자가 하지 않는 것

계약을 직접 수정하지 않는다(사용자 권한). 계약에 없는 요구를 만들지 않는다 — 그래서 Counterpart Enumeration 에도 평가자 전용 절이 없고, 평가자는 계약에 박힌 조건을 일반 조건으로 판정할 뿐이다. 사용자 로그 저장소를 변형하지 않는다 — User Correction Audit 은 읽기 전용이며 mkdir·touch·리다이렉트 쓰기가 금지다. 그 감사 결과(unreflected_corrections)는 표면화 전용이라 자동 REJECT 를 유발하지 않는다.
