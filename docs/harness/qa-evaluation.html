QA 평가 방법론

Test Oracle, LLM-as-Judge 편향 완화, IV&V 원칙 — qa-evaluator 에이전트가 Sprint Contract를 기계적으로 적용하여 구현을 판정하는 방법론

Test Oracle

Test Oracle로서의 역할

qa-evaluator는 "정답을 아는 존재"(Test Oracle)로서 계약 조건 대비 구현을 판정한다. Sprint Contract가 Oracle Specification이며, evaluator는 이를 기계적으로 적용한다.

⚠ 계약 외 판단 금지

계약에 없는 기준으로 판단하지 않는다. 코드 스타일, 성능 최적화 등 계약 외 사항은 평가 대상이 아니다.

📝 문자 그대로 적용

계약 조건의 "의도"가 아닌 "문자 그대로"를 적용한다. 해석의 여지를 제거하여 일관성을 보장한다.

🚫 추론 금지

"아마 이런 뜻일 것이다"는 해석을 하지 않는다. 모호한 조건은 FAIL이 아닌 미검증으로 표시한다.

LLM-as-Judge Bias

LLM-as-Judge 편향 유형

LLM이 판정자 역할을 할 때 발생하는 6가지 알려진 편향과 각각의 완화 전략

편향설명완화 전략
위치 편향 Position먼저 본 항목에 호의적조건 순서를 무작위로 평가
장황함 편향 Verbosity긴 코드/설명에 호의적조건 충족 여부만 판단, 코드 양 무시
자기강화 편향 Self-enhancement자기가 생성한 것에 호의적generator와 evaluator 컨텍스트 분리
구체성 편향 Concreteness구체적 코드에 추상 코드보다 호의적계약 조건 충족만 판단, 구현 스타일 무시
구현 추종 편향 Impl-following실제 구현을 "정답"으로 간주하는 경향계약 조건을 먼저 읽고, 코드는 증거 수집용으로만 사용
지시 해석 불일치 Misalignment평가 기준을 일관되지 않게 해석조건별 boolean 체크리스트 분해로 해석 여지 최소화
Bad: 구현 추종 편향
코드를 먼저 읽고 → 구현된 로직을 "의도된 행동"으로 추종 → 사실상 모든 것이 PASS
Good: Specification-First
계약 조건을 먼저 읽고 기대 행동 확립 → 코드는 증거 수집 대상 → 객관적 판정
IV&V 원칙

Independent Verification & Validation

evaluator는 generator의 의도나 과정을 알지 않는다. 계약과 산출물만으로 판정한다.

1 컨텍스트 독립

evaluator는 generator의 의도나 과정을 알지 않는다. 계약과 산출물만으로 판정한다.

2 증거 기반

모든 PASS/FAIL에는 {파일}:{라인} 형태의 증거가 필요하다. self-assertion은 증거가 아니다.

3 커밋 메시지 불인정

"커밋 메시지에 완료라고 썼다"는 증거가 아니다. 코드 자체를 검증해야 한다.

4 TODO 불인정

"TODO: 추후 수정"은 현재 PASS가 아니다. 현재 시점의 코드 상태만 판정한다.

Verification Depth

3-Level 검증 깊이

모든 조건은 L3까지 도달해야 한다. L1/L2에서 PASS해도 L3에서 FAIL이면 전체 FAIL.

Level검증 방법도구목적
L1 구조파일/디렉토리 존재 확인Glob, ls산출물이 있는가?
L2 내용파일 내용에 기대 요소 존재Read, Grep코드가 작성되었는가?
L3 의미코드 경로 추적, 행동 검증Read + 논리 추적코드가 의도대로 동작하는가?

CheckEval 프로토콜

각 계약 조건을 boolean 서브체크로 분해한다. Likert 스케일 대신 boolean 분해로 평가자 간 일치도를 0.45 향상 (EMNLP 2025).

1 Aspect Selection

조건에서 검증해야 할 핵심 측면(aspect)을 식별한다

2 Checklist Generation

각 측면을 Yes/No boolean 질문으로 변환. 질문당 하나의 검증 포인트만 다룬다

3 Boolean Evaluation

각 질문에 L1/L2/L3 레벨로 답한다. 전체 PASS가 조건 충족 기준이다

Confidence

판정 신뢰도 평가

각 조건의 PASS/FAIL 판정에 확신도를 부여하여 평가 품질을 추적한다.

확신도기준태그
높음L3 검증 완료 + 명확한 증거(파일:라인)—
중간L2까지 검증 + 정황 증거[medium-confidence]
낮음L1만 검증 또는 정적 분석 한계[low-confidence]
  • 낮은 확신도 PASS는 [미검증]과 동일 취급한다
  • 낮은 확신도 조건이 3개 이상이면 Sprint Feedback에 경고를 명시한다
  • 확신도는 판정을 뒤집지 않는다 — FAIL은 확신도와 무관하게 FAIL이다
