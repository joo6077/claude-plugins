Core Principles
Test Oracle 역할 + IV&V 독립성

qa-evaluator 는 "정답을 아는 존재" (test oracle) 로서 계약 조건 대비 구현을 판정한다. 계약이 oracle specification 이며 evaluator 는 이를 기계적으로 적용한다.

Test Oracle 원칙

계약에 없는 기준으로 판단하지 않는다. 조건의 "의도" 가 아닌 "문자 그대로" 를 적용한다. "아마 이런 뜻일 것이다" 는 해석을 하지 않는다.

Test Oracle Generation
IV&V 독립성

evaluator 는 generator 의 의도나 과정을 알지 않는다. 계약과 산출물만으로 판정. "커밋 메시지에 완료라고 썼다" ≠ 증거. "TODO: 추후 수정" ≠ 현재 PASS.

Bias Mitigation
LLM-as-Judge 편향 7종 + 완화 전략

LLM 이 판정자 역할을 할 때 발생하는 알려진 편향. Phase 3 카이젠은 2026 최신 연구를 추가해 7 가지 편향과 완화 전략을 명시했다.

편향설명완화 전략
위치 편향 (Position bias)먼저 본 항목에 호의적 — Response A 가 68% 선호Swap Test: (A,B) 와 (B,A) 양방향 평가, 일치 시 확정. 불일치 시 [low-confidence] 강등
자기 선호 편향 (Self-preference)LLM 이 자신과 perplexity 가 낮은 출력에 호의적generator 와 evaluator 컨텍스트를 물리적 분리 + 구현자 주석/커밋 메시지 증거 제외
장황함 편향 (Verbosity)긴 코드/설명에 호의적조건 충족 여부만 판단, 코드 양 무시
점수 분포 편향 (Scoring bias)특정 점수대에 판정이 몰림이진 PASS/FAIL 만 사용 — Likert 스케일 금지
구체성 편향 (Concreteness)구체적 코드를 추상적 코드보다 선호계약 조건 충족만 판단, 구현 스타일 무시
구현 추종 편향 (Implementation-following)실제 구현을 "정답" 으로 간주Specification-First: 계약 조건을 먼저 읽고 코드는 증거 수집용으로만
지시 해석 불일치평가 기준을 일관되지 않게 해석조건별 boolean 체크리스트 분해
구현 추종 편향 경고

LLM 은 코드를 읽을 때 구현된 로직을 "의도된 행동" 으로 추종하는 경향이 있다. qa-evaluator 는 반드시 계약 조건을 먼저 읽고 "기대 행동" 을 확립한 뒤 코드를 검증해야 한다. 코드를 먼저 읽으면 구현이 곧 정답이라는 착각에 빠진다.

Swap Test
Position Bias 검출 — (A,B) 와 (B,A) 양방향 평가

Phase 3 카이젠이 도입한 핵심 절차. 동일 조건을 양방향으로 1 회씩 총 2 회 평가하고, 두 결과가 일치할 때만 판정을 확정한다.

Bad — 단방향 평가
Evaluator: Response A 평가 → PASS → 판정 확정

position bias 검출 불가 — 먼저 본 항목에 68% 호의적인 편향이 그대로 반영됨.

Good — 양방향 Swap Test
Evaluator: (A, B) 평가 → PASS (B, A) 평가 → PASS → 일치 → 판정 확정 (A, B) 평가 → PASS (B, A) 평가 → FAIL → 불일치 → [low-confidence] → 2 회 재검증해도 불일치 시 [미검증] 처리

position bias 발견 시 자동 강등.

강등 규칙

Swap Test 불안정 강등 규칙: 동일 조건을 (A,B) 와 (B,A) 순서로 평가했을 때 PASS/FAIL 이 다르면 자동으로 [low-confidence] 로 강등. 2 회 재검증해도 일치하지 않으면 [미검증] 으로 처리하고 Sprint Feedback 에 position bias 의심 명시.

3-Level Verification
L1 / L2 / L3 — 모든 조건은 L3까지 도달

qa-evaluator 검증 깊이는 계약 조건의 specificity tag 와 별개의 개념이다. 모든 조건은 깊이 L3 까지 도달해야 한다. L1/L2 에서 PASS 해도 L3 에서 FAIL 이면 전체 FAIL.

L1 구조

파일/디렉토리 존재 확인. 도구: Glob, ls. 목적: 산출물이 있는가?

L2 내용

파일 내용에 기대 요소 존재. 도구: Read, Grep. 목적: 코드가 작성되었는가?

L3 의미

코드 경로 추적, 행동 검증. 도구: Read + 논리 추적. 목적: 코드가 의도대로 동작하는가?

L3 도달 절차

단순 Grep 매칭은 L2 에서 멈추는 함정이다. L3 도달을 위해: (1) Grep 존재 확인 → (2) Read 전체 내용 확인 → 의미 추적 (호출 흐름, 조건 분기, 반환 경로). audit-report.md, design-tokens.md 같은 산출 문서는 Grep 으로 존재만 확인하지 말고 Read 로 내용까지 확인해야 L3 커버리지 충족.

3-tier Code Review Model
전수 검사 조건 L3 절차

"모든 HTML 파일에 card 섹션이 있다" 나 "모든 SKILL.md 의 fenced code block 에 언어 힌트가 있다" 같은 전수 검사 조건은 샘플 1~2 건만 확인하면 L2 에서 멈추는 함정에 빠진다.

(1) Glob 으로 대상 파일 목록 수집 → (2) 각 파일을 Read 또는 Grep (위반 패턴 파일별 카운트) → (3) FAIL 파일명:라인 전체 나열 (샘플 기재 금지) → (4) "N 개 파일 중 M 개 위반" 전체 카운트 보고

실패 사례: DG-02 REJECT (2026-04-10) — 5 개 파일에서 언어 힌트 누락. evaluator 가 1 개 파일만 샘플 확인하고 PASS 처리. 전수 검사로 전환 시 FAIL 로 재판정.

Specificity Tag
contract-schema v2 태그 소비 규칙

계약 조건 끝의 [exact]/[structural]/[goal] 태그는 검증 방식을 지정한다. 모든 태그는 evaluator 검증 깊이 L3 까지 도달해야 한다 — 태그가 [exact] 라고 해서 L1 존재 확인에서 멈추지 않는다.

태그evaluator 검증 방식증거 형식
[exact] Grep 으로 literal 매칭 → Read 로 맥락 확인 파일:라인 + 매칭된 literal 문자열 인용
[structural] Glob/Grep 으로 섹션·필드 존재 확인 → Read 로 구조 검증 파일:라인 + 섹션 헤더 또는 필드명
[goal] Read 로 코드 경로 전체 추적 → 의미 분석 + 다관점 평가 필수 (기능/엣지/성능/보안 중 최소 2 개) 파일:라인 + 목표 달성 논증
조건: CG-01 [exact]: "조건 구체성 레벨" 표에서 컬럼 이름이 [exact]/[structural]/[goal] 로 교체됨 → evaluator: Grep 으로 [exact], [structural], [goal] literal 매칭 확인 후 Read 로 맥락 (표 헤더인가? 예시 코드인가?) 까지 검증. 조건: LO-01 [goal]: 로그인 실패 시 사용자에게 실패 원인이 전달된다 → evaluator: 로그인 실패 코드 경로 (datasource → repository → provider → UI) 를 Read 로 추적하고, UI 에서 실제로 사용자에게 전달되는지 렌더 로직까지 확인. RRD 적용: ① 실패 감지 ② 원인 분류 ③ 메시지 생성 ④ UI 전달 로 분해.
Aggregation Mode
enumerated vs collective — 평가자 검증 분기

다수 대상에 적용되는 조건은 [enumerated] 또는 [collective] 태그를 가진다. evaluator 는 태그에 따라 검증 방식을 분기한다.

모드evaluator 검증 방식PASS 기준
[enumerated] 대상 목록 파싱 → 각 대상별 개별 Grep/Read → 개별 증거 수집 모든 대상에 대해 각각 증거 확보 시 PASS. 누락 시 FAIL + 누락 대상명 나열
[collective] (기본) 포괄 경로·패턴 1 건을 Grep/Glob 으로 확인 포괄 매칭 1 건 증거로 PASS
실패 사례 — KZ-04 REJECT

react-kaizen References 섹션에 docs/react/kit-design/ 7 개 그룹 문서 (g1~g6, g5b) 개별 미명시. 계약이 [enumerated] 요구였는데 포괄 경로로 처리되어 REJECT. Phase 2 에서 contract-design-guide 가 모드 명시를 강제했고, evaluator 는 태그에 따라 검증 방식을 분기한다.

태그 조합 예시

[exact, enumerated] — 이름 목록을 개별 literal 매칭 (가장 엄격). [structural, enumerated] — 섹션/필드 목록을 개별 구조 검증. [structural, collective] — 포괄 경로 1 건 구조 검증 (기본값). [goal, collective] — 포괄 패턴 하나가 목표 달성에 기여하는지 의미 검증.

Rubric Decomposition
CheckEval boolean 분해 + Recursive Rubric Decomposition

각 계약 조건을 boolean 서브체크로 분해한다. CheckEval 패턴은 Likert 스케일 대신 boolean 분해로 평가자 간 일치도를 0.45 향상시켰다 (EMNLP 2025).

3단계 분해 프로토콜

(1) Aspect Selection: 검증할 핵심 측면 식별. (2) Checklist Generation: Yes/No boolean 질문으로 변환. (3) Boolean Evaluation: L1/L2/L3 레벨로 답변. 전체 PASS 가 조건 충족 기준 — PASS 비율 아님.

CheckEval — arxiv 2403.18771
Recursive Rubric Decomposition

고수준 루브릭 항목이 여전히 모호하면 한 번 더 서브포인트로 재귀 분해. 한 번 분해했는데도 서브체크 1 개가 10+ 라인을 Read 해야 판정 가능하면 재귀 분해 신호. [goal] 태그 조건에 특히 유용.

RRD — arxiv 2602.05125
조건: "대시보드에서 실시간 알림을 표시한다" ├── Aspect A: 알림 데이터 수신 │ ├── A-1: WebSocket/SSE 연결 코드가 존재하는가? (L1) │ ├── A-2: 서버 메시지 파싱 로직이 있는가? (L2) │ └── A-3: 파싱 데이터가 UI 상태로 전달되는 경로가 있는가? (L3) └── Aspect B: UI 표시 ├── B-1: 알림 렌더링 컴포넌트가 존재하는가? (L1) ├── B-2: 알림 데이터가 컴포넌트에 바인딩되어 있는가? (L2) └── B-3: 새 알림 수신 시 UI 가 자동 갱신되는가? (L3)
CoT 효용 한계

루브릭이 잘 정의되어 있으면 CoT (Chain-of-Thought) 가 판정 신뢰도에 주는 이득은 미미하다. 장황한 reasoning 을 작성하지 말고, 증거 (파일:라인) + 서브체크 boolean 결과에 집중. CoT 는 계약이 불명확할 때의 임시방편일 뿐, 본 가이드의 우선 전략은 계약을 선명히 쓰고 서브체크로 분해하는 것.

Quantitative Verification
수량/경계값 조건 검증 — 측정 → 비교 → 보고

수량이나 경계값이 포함된 조건 (>= N줄, <= M개, 정확히 K건) 은 측정 → 비교 → 보고 3단계를 반드시 수행한다. "대략 맞는 것 같다"는 L2 에서 멈추는 함정이다.

1 측정

조건의 대상을 실제로 카운트한다. 파일 줄 수는 wc -l, 항목 수는 Grep 카운트, 파일 수는 Glob 결과 카운트 등.

2 즉시 출력

측정값을 Sprint Feedback 근거에 명시한다. 예: 측정값: 1498줄 (기준: >= 1500)

3 비교 판정

측정값과 기준값을 비교하여 PASS/FAIL 판정. 경계값 미달은 무조건 FAIL (1498 >= 1500 → FAIL).

카운팅 패턴 주의사항

항목을 카운트할 때 Grep 패턴이 대상의 모든 변형을 포함하는지 확인한다:

Markdown 헤더: ## 뿐 아니라 ###, #### 등 하위 레벨도 고려. 번호 매기기: 1. 형식과 - 불릿 형식 모두 고려. Gotchas 항목 카운트: H2 하위의 H3 또는 불릿 형태 모두 매칭하는 범용 정규식 사용.

Bad — "거의 맞으니 PASS"
조건: docs/flutter/ >= 1500줄 측정값: 1498줄 판정: PASS (거의 1500줄이니까) → 경계값 무시

경계값 미달을 "거의 충족"으로 PASS 처리하면 안 된다.

Good — 정확한 측정 + 비교
조건: docs/flutter/ >= 1500줄 측정: wc -l → 1498줄 비교: 1498 >= 1500 → false 판정: FAIL (2줄 부족) → 근거에 측정값 명시

측정값과 기준값을 수치로 비교. 2줄 부족도 FAIL.

실제 사례 — AR-03 REJECT (2026-04-12)

docs/flutter/ 파일 총 줄 수가 1498줄로 기준 1500줄에 2줄 부족. 경계값 미달을 "거의 충족"으로 PASS 처리하지 않고 FAIL로 정확히 판정한 사례.

Set Intersection
스킬 트리거 키워드 배타성 검증

스킬 간 트리거 키워드 중복은 Claude 가 잘못된 스킬을 실행하는 직접 원인이다. 키워드 배타성 조건이 계약에 포함된 경우 아래 절차를 따른다.

검증 절차 4단계

(1) 대상 SKILL.md 의 description frontmatter 에서 트리거 키워드 목록을 Grep 으로 추출. (2) 같은 플러그인 내 모든 SKILL.md 파일 목록을 Glob 으로 수집. (3) 각 SKILL.md 의 description 을 Read 하여 키워드를 추출하고 대상 스킬의 키워드와 교차 비교. (4) 완전 일치뿐 아니라 부분 문자열 포함 관계도 배타성 위반으로 판정.

판정 기준

완전 일치: FAIL (명백한 중복). 부분 포함 관계: FAIL (의도치 않은 스킬 실행). 비슷한 의미의 다른 단어: 문맥 분석 후 판정, 불확실하면 [medium-confidence] 태그.

FAIL — 부분 포함 관계
스킬 A: "API 연동" 스킬 B: "API 연동 화면" → "API 연동"이 "API 연동 화면"의 부분 문자열 → 배타성 위반 FAIL
PASS — 부분 포함 없음
스킬 A: "컴포넌트 추출" 스킬 B: "화면 추출" → 부분 문자열 관계 없음 → PASS
실제 사례 — SK-05/RE-02 REJECT

react-run 의 'wasm-pack 빌드'와 react-wasm 의 'wasm-pack 빌드' 완전 중복, react-api 의 '"API 연동"'이 react-feature 의 '"API 연동 화면"'과 부분 포함 관계. Grep 기반 단순 존재 확인으로는 부분 포함 관계를 잡지 못해 Iter 1 에서 놓쳤던 케이스.

Code Block Hints
코드블록 언어 힌트 검증 (DG-02) — HTML 파일 적용 기준

Markdown SKILL.md 파일의 fenced code block 언어 힌트 누락 (DG-02) 조건이 계약에 포함된 경우의 적용 범위.

파일 유형적용 여부검증 방식
.md (Markdown) 필수 적용 ```언어명 형식의 언어 힌트 필수. 힌트 없는 ``` 블록은 FAIL
.html (HTML) 적용 제외 fenced code block 문법이 없으므로 DG-02 조건 적용 제외. 대신 <pre><code class="language-xxx"> 형식 확인
범위 확인 규칙

HTML 파일에 DG-02 를 적용하는 계약 조건은 범위를 *.md 파일로 한정했는지 확인하고, 한정하지 않았다면 HTML 파일은 PASS 처리 + 피드백에 "HTML 파일은 DG-02 적용 제외" 명시.

Multi-Perspective
다관점 평가 — Perspective-Based Reading

각 조건을 최소 2 개 관점에서 평가한다.

관점초점예시 질문
기능명시된 행동이 구현되었는가?"버튼 클릭 시 API 호출되는가?"
엣지 케이스경계 조건에서 올바른가?"빈 입력, null, 최대 길이에서?"
성능비효율이나 병목이 있는가?"N+1 쿼리, 불필요한 리렌더링?"
보안취약점이 있는가?"SQL 인젝션, XSS 가능성?"
Judgment Criteria
Evidence-Based 판정 + Metamorphic Testing + Specification-First

모든 PASS/FAIL 에는 증거가 필요하다. "확인했다", "문제 없다" 같은 self-assertion 은 증거가 아니다.

PASS 증거

{파일}:{라인} — 해당 코드가 조건을 충족하는 이유를 명시한다.

FAIL 증거

{파일}:{라인} — 해당 코드가 조건을 충족하지 않는 이유, 또는 코드 부재를 명시한다.

Metamorphic Testing

절대 정답을 모를 때 관계 기반으로 검증: 비례 관계, 멱등성, 독립성. 계약 조건으로 직접 판정 가능한 경우 불필요.

Specification-First 검증 순서

(1) 먼저 Sprint Contract 를 읽고 각 조건의 "기대 행동" 을 확립한다. (2) 그 다음 코드를 검증한다 — 코드는 증거 수집 대상이지, 기대 행동의 출처가 아니다. (3) 코드를 먼저 읽으면 구현 추종 편향에 빠진다.

Test Oracle Generation
Self-Diagnosis
qa-evaluator 자가 점검 + 교차 진단

qa-evaluator 실행 완료 후 다음 항목을 자가 점검하고, sprint-contract 서브에이전트로 교차 진단한다.

  • ✓ l3_unreached — L3 검증에 도달하지 못한 조건이 있는가?
  • ✓ bias_detected — 편향 징후 감지 (너무 관대, 증거 없이 PASS)
  • ✓ evidence_missing — 증거 없이 판정한 조건이 있는가?
  • ✓ contract_misinterpret — 계약 조건의 원래 의도와 다르게 해석했을 가능성
  • ✓ perspective_gap — 단일 관점에서만 평가한 조건이 있는가?
  • ✓ Swap Test 양방향 일치 — 불일치 시 [low-confidence] 강등
  • ✓ 모든 조건이 L3 까지 도달 — Glob/Grep 만으로 PASS 금지
  • ✓ 모든 PASS/FAIL 에 파일:라인 증거 첨부
  • ✓ Specification-First 검증 순서 준수 — 계약 먼저 읽고 코드 다음
  • ✓ 계약 조건 모호 발견 시 자체 재해석 금지 — REJECT 사유에 명시
  • ✓ 전수 검사 조건은 샘플 1~2 건이 아닌 전체 파일 카운트 보고
  • ✓ 키워드 배타성은 set intersection + 부분 포함 관계까지 검증
  • ✓ 수량/경계값 조건은 측정값을 수치로 명시 + 기준값과 비교 판정
교차 진단 프로토콜

qa-evaluator 실행 후 Agent tool 로 sprint-contract 서브에이전트를 호출한다. 전달: 평가 판정 결과 (출력만). 미전달: 평가 과정의 추론, 중간 메모. 핵심 질문: "계약 조건의 원래 의도를 정확히 해석했는가?" 결과는 피드백 YAML 의 cross_diagnosis 필드에 기록.

Human-in-the-loop Rubric Refinement

계약 조건의 해석 차이가 발견되면 evaluator 는 계약 수정 권장을 Sprint Feedback 에 명시한다 — 단, 실제 수정은 사용자 권한이다. LLM 이 1 차 평가 → 해석 충돌 발견 시 rubric 개선 제안 → 사용자가 승인·수정 → 이후 평가는 refined rubric 기준. evaluator 가 계약을 무단으로 재해석하거나 "의도를 미루어" PASS 처리하지 않는다.

Human-in-the-Loop Patch Evaluation
Confidence & Mutation
판정 확신도 + Mutation Testing — 평가자를 평가하라

각 조건의 PASS/FAIL 판정에 확신도를 부여하고, 주기적으로 의도적 결함을 삽입해 evaluator 자체를 테스트한다.

확신도기준태그
높음L3 검증 완료 + 명확한 증거 (파일:라인)—
중간L2 까지 검증 + 정황 증거[medium-confidence]
낮음L1 만 검증 또는 정적 분석 한계[low-confidence]
확신도 규칙

낮은 확신도 PASS 는 [미검증] 과 동일 취급. 낮은 확신도 조건이 3 개 이상이면 Sprint Feedback 에 경고 명시. FAIL 은 확신도와 무관하게 FAIL — 확신도는 판정을 뒤집지 않는다.

Anthropic Statistical Eval
Mutation Testing

evaluator-kaizen 이 주기적으로 수행: ① 기존 fixture 에 의도적 결함 삽입 → ② qa-evaluator 실행 → ③ 결함을 잡으면 PASS, 놓치면 약점 존재 → ④ 약점을 Gotchas 나 검증 로직에 반영.

Mutation Testing Method
피드백 수집 지표

verdict: APPROVE/REJECT/BLOCKED. conditions_total: 전체 조건 수. conditions_passed: PASS 조건 수. l3_coverage: L3 검증 도달 비율. reject_reasons: REJECT 시 사유 목록.

Phase 3 Kaizen 변경 요약

Phase 3 에서 qa-evaluation-guide 가 LLM-as-judge 2026 최신 연구를 대거 흡수했다. 핵심 변경: ① Swap Test 표준화 — (A,B)/(B,A) 양방향 평가, 불일치 시 [low-confidence] 강등, ② Self-preference bias 완화 — generator/evaluator 컨텍스트 물리적 분리, ③ Recursive Rubric Decomposition (RRD) — 모호 조건 재귀 분해, ④ CheckEval boolean 분해 — Likert 스케일 금지 + 평가자 일치도 0.45 향상, ⑤ CoT 효용 한계 — 루브릭이 잘 정의되면 CoT 이득 미미, ⑥ specificity tag / aggregation mode 소비 규칙, ⑦ legacy [L1]/[L2]/[L3] 태그 매핑, ⑧ Markdown 전수 검사 조건 L3 절차, ⑨ 수량/경계값 조건 검증 프로토콜 — 측정 → 비교 → 보고 3단계 + 카운팅 패턴 주의사항.
