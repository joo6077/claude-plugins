Corrections
2026-08 기준으로 틀렸던 것 3 가지

이 가이드가 과거에 잘못 적었거나, 문서가 바뀌어 더 이상 맞지 않는 항목이다. 예전 판을 기억하고 있다면 여기부터 고쳐 읽어라.

1. 중첩은 금지가 아니다 — 기본 3 층까지 허용된다

과거 이 가이드는 서브에이전트의 하위 위임을 금지된 것으로 기술했다. 현재 공식 동작은 다르다 — 서브에이전트는 기본적으로 자기 아래로 서브에이전트를 스폰할 수 있으며, 메인 대화 기준 3 층까지 중첩된다. 깊이 한계에 도달하면 Claude Code 가 Agent 도구를 회수하므로, 그 에이전트는 위임 없이 직접 일하고 요약 하나만 반환한다.

설계 함의: "리뷰어가 발견 항목마다 검증자를 띄우는" 구조가 이제 정상 선택지다. 다만 깊이를 설계 가정으로 삼지 마라 — 4 층째 위임을 전제한 설계는 조용히 단층으로 접힌다. 특정 에이전트만 스폰을 막으려면 tools 에서 Agent 를 빼거나 disallowedTools 에 추가한다.

Let subagents spawn their own subagents — Claude Code Docs
2. frontmatter 는 15 종이고 prompt · initialPrompt 는 그 안에 없다

prompt 는 --agents JSON 정의에서 markdown body 에 해당하는 필드다. 파일 기반 YAML frontmatter 표에는 존재하지 않으므로 .md 에이전트의 frontmatter 에 prompt: 를 적지 마라. initialPrompt 는 2026-07 판 표에 행으로 실려 있었으나 공식 15 종 목록에 없다 — 근거가 다시 확보되기 전까지 공식 필드로 소개하지 않는다.

필수는 name 과 description 둘뿐이며, 나머지 13 종(tools, disallowedTools, model, permissionMode, maxTurns, skills, mcpServers, hooks, memory, background, effort, isolation, color)은 선택이다. 플러그인으로 배포된 에이전트에서는 hooks · mcpServers · permissionMode 가 무시된다.

Supported frontmatter fields — Claude Code Docs (2026-08 재확인)
3. Binary Decidability 는 Gotcha 한 줄이 아니라 최상위 섹션이다

이 원칙이 skill-design-guide 에만 있고 이 가이드에는 §10 Gotchas 내 1 bullet 으로만 존재해 design-kit PH-01 REJECT 가 발생했다. 2026-08 사이클에서 독립 최상위 섹션(§3.5) 으로 승격됐다 — 평가자는 평가를 시작하기 전에 각 조건의 이진 판정 가능성을 전수 점검해야 한다.

Four Decisions
에이전트 파일을 쓸 때 실제로 결정하는 4 가지
1. description

언제 위임할지를 쓴다 — 무엇을 하는지가 아니라

Claude 는 서브에이전트를 undertrigger 하는 경향이 있다. 코드 작성 직후 자동으로 돌아야 하는 리뷰어라면 Proactively reviews… Use immediately after…, 에러 시 자동 개입하는 디버거라면 Use proactively when encountering… 를 넣는다. 반대로 명시적 호출이 필요한 에이전트(예: QA)는 use proactively 를 생략하고 트리거 키워드만 나열한다.

sibling agent 와 키워드는 set intersection + substring containment 가 모두 공집합이어야 한다. 에이전트가 2+ 개면 저장 전 rg -n "description:" agents/*.md 로 확인한다.

Understand automatic delegation — Claude Code Docs
2. tools

역할이 정해지면 도구는 거의 자동으로 정해진다

읽기 전용 리뷰어 Read, Grep, Glob · QA 평가자 Read, Grep, Glob, Bash(Edit/Write 금지) · 리서처 + WebFetch, WebSearch · 구현자 + Write, Edit · 데이터 분석가 Bash, Read, Write.

목록의 어느 항목도 실제 도구로 해석되지 않으면 에이전트가 launch 자체에 실패한다. 스킬을 컨텍스트에 미리 넣으려면 tools 에 Skill 을 적지 말고 skills 필드를 쓴다. 스폰 화이트리스트가 필요하면 Agent(worker, researcher) 문법을 쓰고, Agent 자체를 생략하면 모든 스폰이 불가하다.

Available tools — Create custom subagents
3. model

작업 복잡도에 맞춘다

코드베이스 탐색·파일 검색은 haiku(빠르고 저렴, 읽기 전용), 코드 리뷰·테스트 작성·구현은 sonnet, 아키텍처 판단·복잡한 평가는 opus, 메인 대화와 동일 수준이 필요하면 inherit.

추천 패턴: 메인 세션은 Opus, 서브에이전트는 Sonnet. 집중된 작업에서는 Sonnet 이면 충분하다. model 은 에이전트 단위 고정이므로, 작업별 라우팅이 필요하면 라우팅 에이전트가 서로 다른 모델의 서브에이전트를 호출하는 구조를 쓴다.

7 개 중 하나를 기반으로 삼는다

프롬프트 체이닝 · 라우팅 · 병렬화 · 오케스트레이터-워커 · 평가자-최적화자 · 계획-실행 분리 · Hook-Triggered Auto-Correction.

하드 리밋보다 항상 작게 잡는다

하드 리밋을 초과하면 Agent 도구가 Concurrent subagent limit reached / Subagent spawn limit reached 로 실패한다. 하드 리밋은 사고를 막는 최후 방어선이지 설계 목표가 아니다. 실측 사고: 단일 슬래시 커맨드가 49 서브에이전트를 2.5 시간 병렬 spawn 하여 $8K~15K 추정.

병렬 디스패치 — 3 가지 모두 충족 시
  • 3 개 이상의 독립적 작업
  • 작업 간 공유 상태 없음
  • 파일 경계가 명확하여 겹치지 않음

토큰 예산이 빡빡하면 순차, 시간 예산이 빡빡하면 병렬. 각 서브에이전트가 독립 context window 를 차지하므로 병렬은 latency 와 토큰을 동시에 키운다 — 디스패치 결정 시 어느 축을 우선하는지 한 줄로 명시한다.

Exploration Budget — 과탐색 stall 방지

구현·산출 전 "탐색만" 하는 단계에 상한을 둔다. read-only 탐색이 의미 있는 진전 없이 누적되면(같은 디렉토리 반복 Glob, 동일 노드 메타데이터 재조회) 중단하고 현재까지 발견을 요약한 뒤 진행 방향을 사용자에게 확인한다.

"조금만 더 보면 알 것 같다" 가 stall 의 가장 흔한 진입점이다. 서브에이전트는 raw 출력 전체가 아닌 요약(findings)만 반환한다.

Reviewer Agents
리뷰어·평가자를 만든다면 추가로 지켜야 할 4 가지
1. L3 커버리지

정적 Grep 만으로 PASS 를 주지 마라

파일 존재나 키워드 포함 확인은 L1/L2 수준이다. Reviewer/Evaluator 는 반드시 L3 — Read 로 파일 내용을 실제로 읽거나 Bash 로 명령을 실행해 결과를 확인 — 까지 수행해야 PASS 를 줄 수 있다.

cross-kit 키워드 중복은 Grep 만으로 탐지되지 않는다 — 정규식으로 키워드를 추출한 뒤 set intersection 으로 정확히 비교해야 한다. "같은 단어가 있는지" 만 Grep 하면 부분 문자열 오탐이 난다.

2. Unverifiable

검증 불가는 조용한 PASS 가 아니다

MCP 미설정·런타임 미실행·도구 미설치로 검증이 불가하면 (a) [미검증] 마커와 사유 한 줄 (b) 2 건 이상 누적 시 REJECT (c) 조용한 PASS 금지 (d) 생성자의 완료 주장을 증거로 취급 금지.

자기평가 궤적에서 실패의 75.8% 가 false success 였고, LLM 판정자는 AUROC 0.54~0.65 에 그쳤다 — 평가자는 주장이 아니라 도구 출력·상태 변화를 근거로 삼아야 한다.

From Confident Closing to Silent Failure — arxiv:2606.09863
3. 사용자 보고

PASS 를 준 뒤에도 REOPENED 가 될 수 있다

사용자가 "아직 깨져 있다" 고 보고하면 그 항목의 상태는 PASS 가 아니라 REOPENED 다. 에이전트의 테스트·스냅샷은 "내 환경에서의 관측" 일 뿐이며 반박 근거가 아니다.

절차는 (1) 오라클 유효성부터 6 축(URL·경로 / 브랜치·커밋 / viewport / 디바이스·플랫폼 / auth·cache / 데이터 상태)으로 대조 (2) 재현되면 원 PASS 취소·FAIL 로 재판정(이전 근거는 삭제하지 않음) (3) 완료 복귀는 재현·수정 후 재검증 / 축 값으로 환경 불일치 특정 / 사용자 직접 확인 3 택뿐.

How Coding Agents Fail Their Users — arxiv:2605.29442
4. Self-Audit

자기 규칙으로 전수 대조하는 패스를 넣어라

카이젠 Phase 처럼 서브에이전트 내부에서 QA 를 돌려야 하면, Phase subagent 가 자기 산출물을 자기 규칙 리스트로 전수 대조하는 self-evaluator pass 를 추가한다. 2026-04-24 카이젠이 Phase 1~11 1 회 iteration APPROVE 를 달성한 핵심 기법이다.

자기 평가는 외부 평가의 대체가 아니다 — Final 단계에서는 별도 evaluator 의 독립 평가가 여전히 필수다. self-audit 시 최종 산출물뿐 아니라 중간 결정·도구 상태까지 규칙에 대조한다.

Verify Before You Commit — arxiv:2604.08401
Hooks
같은 위반이 반복되면 프롬프트가 아니라 훅이다

훅은 skill-design-guide §3.7 의 E3(결정론적 게이트) 를 에이전트 측에서 구현하는 형태다. LLM 판단 없이 매 실행마다 같은 판정을 내리므로 문장 규칙·체크리스트와 달리 per-run 보장을 제공한다. 같은 위반이 반복되는데 프롬프트 문구만 계속 다듬고 있다면 그 규칙은 E3 로 올릴 후보다.

PostToolUse  (편집 후 quality gate)
  Edit/Write 발생 → 정적 검증(cargo fmt --check / dart format / eslint --max-warnings=0)
    → 위반 시 read-only 리뷰어 에이전트 spawn → 수정 제안서 → 메인 Claude 가 Edit

PreToolUse   (편집 전 risk gate)
  1. Origin Sync 가드   — upstream 보다 N 커밋 뒤지면 stderr 경고
  2. 좀비 프로세스 가드  — mcp_server 프로세스 5 건 초과면 정리 권고
  3. 보호 브랜치 가드   — 현재 브랜치가 main/master/dev 면 stderr 경고
적합 / 부적합
  • 적합 — 결정론적 자동 수정이 가능한 규칙(포맷팅·import 정렬·단순 lint), fix 가 단일 명령으로 끝나는 영역, 대량 편집 후 일관성 enforce
  • 부적합 — 의미적 판단이 필요한 리뷰(아키텍처 결정·도메인 로직·네이밍), 1 초 이상 걸리는 무거운 검증(전체 빌드·풀 테스트), 비결정론적 수정
graceful degradation 원칙

PreToolUse 훅은 exit 0 으로 편집 자체를 막지 않는다(stderr 경고만). 강한 차단이 필요하면 사용자가 settings 에서 enable 한다. false-positive(의도된 main 직접 편집) 시 워크플로우 마비를 막기 위함이다.

훅은 stateless 다 — 훅이 직접 에이전트를 spawn 하지 않는다. 명령이 비-zero exit 이면 메인 Claude 가 결과를 받아 후속 조치를 결정한다.

  • ✓name(소문자·하이픈)과 description 두 필수 필드가 있는가? name 은 파일명과 일치할 필요가 없지만, 훅이 이 값을 agent_type 으로 받는다는 것을 알고 정했는가?
  • ✓frontmatter 에 공식 15 종 밖의 필드(prompt, initialPrompt 등)를 쓰지 않았는가?
  • ✓플러그인 배포용이라면 hooks · mcpServers · permissionMode 에 의존하지 않는가? (무시된다 — 필요하면 .claude/agents/ 로 복사)
  • ✓tools 의 모든 항목이 실제 도구명인가? (하나도 해석되지 않으면 launch 자체가 실패한다)
  • ✓읽기 전용이어야 하는 에이전트에서 Edit/Write/Agent 를 뺐는가?
  • ✓sibling agent 와 트리거 키워드가 set intersection + substring 모두 공집합인가?
  • ✓자동 위임이 필요하면 use proactively 를, 명시 호출 전용이면 비트리거 조건을 description 에 넣었는가?
  • ✓백그라운드로 돌 수 있는 에이전트라면 — AskUserQuestion 이 실패한다는 것을 전제로 설계했는가? (권한은 미리 승인)
  • ✓반환값이 raw 출력이 아니라 요약(findings) 인가?
  • ✓같은 실패 패턴이 반복 관찰된다면 memory: project 를 고려했는가?
영속 메모리 — 대화를 넘어서는 학습

user(~/.claude/agent-memory/{name}/) — 모든 프로젝트에 걸친 학습 · project(.claude/agent-memory/{name}/) — 프로젝트별 지식, git 공유 가능 · local(.claude/agent-memory-local/{name}/) — 프로젝트별, git 미포함. 활성화하면 시스템 프롬프트에 메모리 읽기/쓰기 지침이 자동 추가된다. 작업 시작 전 "메모리를 확인하고 이전에 발견한 패턴을 참고해라", 완료 후 "배운 것을 메모리에 저장해라" 를 넣으면 시간이 지날수록 정확해진다.
