When to Use
스킬 vs 에이전트 — 무엇을 언제 쓰는가

Anthropic 핵심 원칙: "복잡성은 결과가 입증될 때만 추가하라". 단순한 스킬로 충분하면 에이전트를 만들지 마라. 에이전트는 격리·도구 제한·대량 출력·재사용성 측면에서 스킬과 다른 트레이드오프를 가진다.

기준스킬 사용에이전트 사용
컨텍스트메인 대화에서 실행별도 컨텍스트 윈도우에서 격리 실행
도구 제한메인 대화의 도구 전체 사용도구를 제한하여 안전하게 격리
출력량적음~중간대량 (테스트 실행, 코드베이스 탐색)

비용메인 컨텍스트 소비별도 컨텍스트 (메인 보존)

플러그인 에이전트 제약

hooks, mcpServers, permissionMode 필드는 플러그인으로 배포된 에이전트에서는 무시된다. 이 필드가 필요하면 .claude/agents/ 로 복사한 사본을 사용하라.

Use Proactively
"use proactively" — 공식 언더트리거 방지 메커니즘

Claude 는 서브에이전트를 필요한 상황에서도 undertrigger 하는 경향이 있다. Anthropic 공식 문서는 description 에 use proactively 또는 proactively 를 명시적으로 포함하라고 권장한다.

Bad — 기능만 설명
description: QA 관련 에이전트

위임 트리거 없음. Claude 가 호출 판단을 못 함.

Good — proactively + 트리거 키워드
description: > Expert code review specialist. Proactively reviews code for quality, security, and maintainability. Use immediately after writing or modifying code.

코드 작성·수정 직후 자동 위임을 명시.

코드 작성/수정 직후 리뷰어

"Proactively reviews... Use immediately after..." 패턴. 코드가 변경되면 자동으로 돌도록 description 에 명시.

Tool Scoping
최소 권한 원칙 + Agent(agent_type) 화이트리스트

에이전트와 스킬의 핵심 차이는 도구 제한이다. 역할에 따라 필요한 도구만 부여한다. v1.1.0 카이젠은 메인 스레드 에이전트가 다른 서브에이전트를 spawn 할 때 화이트리스트를 거는 Agent(agent_type) 문법을 추가했다.

Agent(agent_type) 문법
--- name: coordinator description: Coordinates work across specialized agents tools: Agent(worker, researcher), Read, Bash ---

worker 와 researcher 만 spawn 가능. 서브에이전트도 기본적으로 메인 대화 아래 3 층까지 다른 서브에이전트를 spawn 할 수 있다 — 깊이 한도에 도달하면 Agent 도구가 제거되고, CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1 로 중첩을 끌 수 있다.

Sub-agents Spawn Restrictions
화이트리스트 vs 전체 허용

Agent(...) 명시 → 화이트리스트. Agent 만 → 전체 허용. Agent 자체 생략 → 모든 서브에이전트 spawn 불가. 의도와 일치하는 모드를 선택하라.

Available Tools
Model & Patterns
모델 선택 + 6가지 디자인 패턴

작업 복잡도에 맞는 모델을 선택해 비용을 최적화한다. Anthropic 이 식별한 6 가지 핵심 패턴 중 하나를 기반으로 에이전트를 설계하라.

haiku — 탐색·검색

코드베이스 탐색, 파일 검색. 빠르고 저렴한 읽기 전용 작업에 적합. 내장 Explorer/Research 계열의 기본값.

sonnet — 리뷰·구현

코드 리뷰, 테스트 작성, 일반 구현. 능력과 속도의 균형. 가장 자주 쓰이는 선택지.

opus — 아키텍처 판단

아키텍처 판단, 복잡한 평가, 다중 시스템 트레이드오프. 최고 추론 능력.

inherit — 부모 수준

메인 대화와 동일 모델 상속. 메인 세션이 Opus 일 때 서브에이전트에서도 동일 능력이 필요한 경우.

#패턴설명적합
1프롬프트 체이닝LLM A → 게이트 검증 → LLM B → 결과단계가 명확하고 정확도 중요
2라우팅입력 → 분류기 → 전문가 A/B/C이질적 요청 유형 처리
3병렬화독립 하위 작업 동시 실행 후 합성자연 분할되는 작업, 다양한 관점
4오케스트레이터-워커동적 하위 작업 분해 → 워커어떤 파일을 수정할지 미리 모름
5평가자-최적화자생성 LLM ↔ 평가 LLM 반복명확한 평가 기준 + 반복 향상
6계획-실행 분리계획 에이전트(Read만) → 실행 에이전트(Edit/Write)계획·실행 오류 독립 디버깅
이 프로젝트 사례

qa-evaluator 는 패턴 5 (평가자-최적화자) 를 구현한다. Generator(메인 Claude)가 코드를 생성하고 QA Evaluator(독립 에이전트)가 Sprint Contract 기준으로 평가, REJECT 시 Generator 가 피드백을 반영해 재구현한다.

Building Effective Agents
Reviewer Gotchas
계약 모호성 방지 — 평가 전 이진 판정 가능성 점검

v1.1.0 카이젠은 Reviewer/Evaluator 에이전트가 평가 시작 전에 계약 조건의 이진 (PASS/FAIL) 판정 가능성을 검토하도록 의무화했다. 해석 여지가 있는 조건은 QA 도중 혼란을 유발하고 iteration 을 낭비한다.

정성적 표현 발견 시

"~충분히", "~정도", "~상당한" 같은 정성적 표현이 조건에 있으면 계약 작성자에게 구체화 요구. 평가 전 단계에서 차단해 iteration 낭비를 막는다.

Human-in-the-loop Rubric Refinement
경계 미명시 조건

파일 경로/함수명/라인 수가 명시되지 않은 조건은 해당 에이전트가 자체적으로 경계를 정의 후 진행하되, 판정 근거에 그 경계를 명시한다.

Empirical Study of LLM-as-a-Judge
specificity tag 소비

계약이 [exact] / [structural] / [goal] 태그를 사용하면 그 레벨에 맞춰 평가한다. [exact] 는 문자 그대로 매칭, [goal] 은 결과 상태만 확인.

Contract Design Guide §태그
모호성 발견 시 REJECT

평가 도중 조건의 모호성이 드러나면 REJECT 사유에 명시해 계약 작성자가 다음 iteration 에서 수정할 수 있도록 한다. 평가자가 조건을 무단 재해석하지 않는다.

Gotchas Checklist
에이전트에서 반복되는 실수 체크리스트

공식 문서 + 커뮤니티 경험 + Reviewer 전용 Gotchas. 새 에이전트를 만들거나 기존 에이전트를 손볼 때 위에서 아래로 점검하라.

  • ✓ 스킬로 충분한지 먼저 검토 — 격리·도구 제한·대량 출력이 필요할 때만 에이전트로 격상
  • ✓ description 에 트리거 키워드 + 비트리거 조건 명시. 자동 위임 대상이면 use proactively 포함
  • ✓ 도구는 최소 권한으로 — 읽기 전용 리뷰어는 Read, Grep, Glob 만
  • ✓ 메인 스레드 에이전트의 spawn 권한은 Agent(agent_type) 화이트리스트로 제한
  • ✓ 모델 선택 근거를 코멘트로 남김 (왜 sonnet 인지, 왜 opus 인지)
  • ✓ 서브에이전트는 기본적으로 메인 대화 아래 3 층까지 다른 서브에이전트를 spawn 할 수 있음 (CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1 로 차단 가능, 깊이 한도 도달 시 Agent 도구가 제거됨) — 깊이 예산을 설계에 반영
  • ✓ 플러그인 에이전트는 hooks/mcpServers/permissionMode 무시 — 필요 시 .claude/agents/ 로 복사
  • ✓ Reviewer 에이전트는 L3 (Read/Bash) 까지 도달 — Glob/Grep 만으로 PASS 금지
  • ✓ 트리거 키워드 cross-kit 중복은 set intersection 으로 정확히 비교 (단순 Grep 부분 매칭 금지)
  • ✓ 평가 전 계약 조건의 이진 판정 가능성 점검 — 모호 조건은 차단 또는 REJECT 사유 명시
  • ✓ 백그라운드 에이전트는 사용자에게 질문 불가 — 권한 사전 승인 필요
  • ✓ 호출 품질 4 요소: 컨텍스트 밀도 + 구체적 범위 + 파일 참조 + 성공 기준
