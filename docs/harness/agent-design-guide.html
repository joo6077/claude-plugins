When to Use
스킬 vs 에이전트 — 무엇을 언제 쓰는가

Anthropic 핵심 원칙: "복잡성은 결과가 입증될 때만 추가하라". 단순한 스킬로 충분하면 에이전트를 만들지 마라. 에이전트는 격리·도구 제한·대량 출력·재사용성 측면에서 스킬과 다른 트레이드오프를 가진다.

Supported Frontmatter Fields
Description

Claude는 서브에이전트를 필요한 상황에서도 undertrigger 하는 경향이 있다. Anthropic 공식 문서는 description에 use proactively를 명시적으로 포함하라고 권장한다.

Bad — 기능만 설명
description: QA 관련 에이전트

위임 트리거 없음. Claude가 호출 판단을 못 함.

Good — proactively + 트리거 키워드
description: > Sprint Contract 기반으로 구현 결과를 독립 평가하는 QA 에이전트. 구현 완료 후 APPROVE/REJECT 판정. "QA 돌려줘" 요청 시 사용.

언제 위임할지 구체적으로 명시.

코드 작성/수정 직후 리뷰어

"Proactively reviews... Use immediately after..." 패턴. 코드가 변경되면 자동으로 돌도록 description에 명시.

Agent(...) 명시 → 화이트리스트. Agent만 → 전체 허용. Agent 생략 → 모든 서브에이전트 spawn 불가. 의도와 일치하는 모드를 선택하라.

Available Tools
Model & Patterns
모델 선택 + 6가지 디자인 패턴

작업 복잡도에 맞는 모델을 선택해 비용을 최적화한다. Anthropic이 식별한 6가지 핵심 패턴 중 하나를 기반으로 에이전트를 설계하라.

haiku — 탐색·검색

코드베이스 탐색, 파일 검색. 빠르고 저렴한 읽기 전용 작업에 적합. 내장 Explorer/Research 계열의 기본값.

sonnet — 리뷰·구현

코드 리뷰, 테스트 작성, 일반 구현. 능력과 속도의 균형. 가장 자주 쓰이는 선택지.

opus — 아키텍처 판단

아키텍처 판단, 복잡한 평가, 다중 시스템 트레이드오프. 최고 추론 능력.

inherit — 부모 수준

메인 대화와 동일 모델 상속. 메인 세션이 Opus일 때 서브에이전트에서도 동일 능력이 필요한 경우.

Building Effective Agents
Execution
실행 패턴 — 병렬 vs 순차 vs 백그라운드

에이전트 실패의 대부분은 실행이 아니라 호출 품질 문제다. 좋은 호출의 4요소: 컨텍스트 밀도, 구체적 범위, 파일 참조, 성공 기준.

병렬 디스패치 조건 (3가지 모두 충족)

① 3개 이상의 독립적 작업
② 작업 간 공유 상태 없음
③ 파일 경계가 명확하여 겹치지 않음

순차 디스패치 필수 상황

작업 간 의존성 있음 / 공유 파일로 충돌 위험 / 범위가 불명확하여 이해 후 진행 필요

Bad 호출
"인증 고쳐줘"

컨텍스트 없음. 어느 파일, 어떤 버그인지 불명확.

Good 호출
"OAuth 리다이렉트 루프 수정. 로그인 성공 후 /dashboard 대신 /login으로 리다이렉트. src/lib/auth.ts 참조."

컨텍스트·범위·파일참조·성공기준 4요소 충족.

Fan-out & Budget
§7 Fan-out 상한 · Exploration Budget — 과탐색 stall · 비용 폭주 방지

§10 Gotcha "과도한 병렬화는 토큰 낭비"를 정량 규칙으로 승격한다. 비용·시간이 폭주하는 두 축은 fan-out 폭(병렬 spawn 수)과 exploration 깊이(구현 전 탐색 turn 수)다. 2026 사례: 단일 슬래시 커맨드가 49 서브에이전트를 2.5시간 병렬 spawn하여 $8K~15K 추정(CloudZero).

① Fan-out 상한 — 기본 5개 이하

1회 디스패치당 병렬 서브에이전트 기본 5개 이하. 6+ 개가 필요하면 batch로 쪼개 순차 처리하거나 사용자에게 비용/시간 trade-off를 먼저 보고하고 승인받는다. 단순 작업에 fan-out하지 않는다.

② 토큰 vs 시간 trade-off 명시

토큰 예산이 빡빡하면 순차 탐색, 시간 예산이 빡빡하면 병렬 탐색. 각 서브에이전트가 독립 context window를 차지하므로 병렬은 latency와 토큰을 동시에 키운다. 어느 축을 우선하는지 한 줄로 명시.

③ Exploration budget

구현·산출 전 "탐색만" 하는 단계에 상한을 둔다. read-only 탐색이 진전 없이 누적되면(같은 디렉토리 반복 Glob, 동일 노드 메타데이터 재조회) 중단하고 발견을 요약한 뒤 진행 방향을 사용자에게 확인한다. "조금만 더 보면 알 것 같다"가 stall의 가장 흔한 진입점.

④ Summary-only 반환

서브에이전트는 raw 출력 전체가 아닌 요약(findings)만 메인 컨텍스트로 반환한다. grep sweep·로그 trawl 같은 noisy 탐색일수록 필수.

Bad
오케스트레이터 → 20+ 서브에이전트 동시 spawn → 각자 raw 출력 전체 반환 → 메인 컨텍스트 폭주 + 비용 급증 탐색 에이전트 → Figma 노드 50회 재조회 → 진전 없이 stall → 사용자 중단
Good
오케스트레이터 → 5개 batch spawn (시간 우선 명시) → findings 요약만 반환 → 다음 batch 탐색 에이전트 → exploration budget 도달 → 발견 요약 + 진행 방향 확인 후 구현

Gotchas
에이전트에서 반복되는 실수 + Reviewer/Evaluator 전용 규칙

특히 Reviewer/Evaluator 에이전트는 정적 Grep만으로 PASS를 주지 말고 L3 커버리지까지 도달해야 한다.

L3 검증 깊이 의무
L1: 파일이 존재하는가? (Glob) L2: 키워드가 있는가? (Grep) L3: 실제 내용·실행 결과가 조건을 충족하는가? (Read/Bash) ← 여기까지 해야 PASS
[미검증] 마커 정책

MCP null, 런타임 미실행 등으로 검증 불가 시 [미검증] 마커 부착 필수. 2건 이상 누적 시 자동 REJECT. 조용한 PASS 금지.

  • !서브에이전트는 다른 서브에이전트를 생성할 수 없다. 중첩 위임이 필요하면 메인 대화에서 체이닝하라
  • !플러그인 에이전트는 hooks, mcpServers, permissionMode를 지원하지 않는다
  • !과도한 병렬화는 토큰 낭비다. 관련 작업을 묶어라
  • !백그라운드 에이전트는 사용자에게 질문할 수 없다 — 권한은 미리 승인해야 한다
  • !cross-kit 키워드 중복은 단순 Grep으로 탐지되지 않는다 — set intersection + substring containment 검사 필요
  • !Self-evaluator self-audit 시 최종 산출물뿐 아니라 중간 결정·도구 상태까지 규칙에 대조하라 — LLM은 유창하지만 제약을 위반하는 추론을 내기 쉽고 최종 성공만으로는 위반이 가려진다 (faithful-reasoning, arxiv:2604.08401). 자기 평가는 외부 평가의 대체가 아니다 — Final 단계 독립 evaluator는 여전히 필수
