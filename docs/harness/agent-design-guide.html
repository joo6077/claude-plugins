Sibling Agent 트리거 키워드 배타성 (substring 포함)

대응 · skill-design-guide §4 "트리거 키워드 중복 방지 원칙"

에이전트도 스킬과 같은 규칙을 따른다 — description 의 트리거 키워드는 sibling agent 와 set intersection + substring containment 가 모두 공집합이어야 한다. "QA 돌려줘" 같은 키워드가 여러 에이전트 description 에 겹치거나, 한 에이전트의 키워드가 다른 에이전트 키워드의 부분문자열이면 Claude 가 어떤 에이전트로 위임할지 예측할 수 없다.

플러그인 안 에이전트가 2+ 개이면 편집 시 반드시 rg -n "description:" agents/*.md 로 확인한 뒤 저장한다.

대응 · skill-design-guide §3.5 — 재발 방지 배경

지난 kaizen 사이클에서 이 원칙은 skill-design-guide 에만 있고 이 가이드에는 §10 Gotchas 안 1 bullet 로만 있어 design-kit PH-01 REJECT 가 났다. 그래서 독립 최상위 섹션으로 올렸다.

Reviewer / Evaluator 에이전트는 평가를 시작하기 전에 Sprint Contract 의 각 조건이 이진(PASS/FAIL) 판정 가능한지 스스로 검토해야 한다. 모호한 조건은 평가 중 해석 차이로 REJECT iteration 을 낭비시킨다.

Step 1

이진 판정 가능성 검사

각 조건이 "PASS" 또는 "FAIL" 중 하나로 귀결 가능한가? "충분히", "상당한", "어느 정도" 같은 정성적 수식어가 있으면 계약 작성자에게 구체화를 요청하거나 REJECT 사유로 명시한다.

Step 2

구체성 태그 존재 확인

contract-design-guide 의 태그 — [exact] 문자 그대로 매칭(정규식·라인번호·정확한 값) · [structural] 구조적 일치(섹션 존재·카운트·관계) · [goal] 결과 상태(빌드 성공·테스트 통과·사용자 경험).

Step 3

경계 정의 의무

파일 경로·함수명·라인 수가 없으면 에이전트가 스스로 경계를 정의하되 판정 근거 블록에 명시한다.

Step 4

모호성은 REJECT 사유에

평가 도중 조건의 모호성이 드러나면 다음 iteration 에서 계약 작성자가 고칠 수 있게 REJECT 사유에 모호성: [조건 ID] — [모호한 문구] — [제안하는 구체화] 를 넣는다.

평가자 자체 체크리스트 (평가 시작 직전)

  • ✓모든 조건에 구체성 태그([exact]/[structural]/[goal])가 붙어 있는가?
  • ✓정성적 수식어(충분히, 상당한 등)가 있는 조건은 경계 정의가 끝났는가?
  • ✓파일/라인 근거가 명시되지 않은 조건은 에이전트가 자체 경계 정의 후 근거 블록에 기록했는가?

문법

이 예시에서는 worker 와 researcher 서브에이전트만 스폰할 수 있다. 그 외를 부르면 요청이 실패하며, 에이전트는 허용된 타입만 프롬프트에서 볼 수 있다.

규칙
  • Agent(...) 로 명시하면 화이트리스트 방식 (나열된 것만 허용)
  • Agent 만 쓰면 전체 허용
  • Agent 자체를 생략하면 모든 서브에이전트 스폰 불가

단, 이 제한이 어디서 걸리고 어디서 안 걸리는지는 아래 한계 두 가지를 같이 읽어야 한다.

한계 1 — 괄호 안 타입 제한은 메인 스레드에서만 걸린다

이 제한은 claude --agent 로 띄운 메인 스레드에 적용되고, 그 에이전트가 서브에이전트로 불릴 때는 무시된다 ("Restrict which subagents can be spawned"). 즉 Agent(worker, researcher) 라고 적은 에이전트를 다른 에이전트가 띄우면 그 안에서는 어떤 타입이든 스폰할 수 있다.

Design Patterns
§6 에이전트 디자인 패턴

패턴 1~5 는 Anthropic 이 식별한 핵심 패턴이고, 6~7 은 이 레포에서 덧붙인 것으로 각자 아래에 출처를 단다. 에이전트를 설계할 때 이 가운데 하나를 기반으로 삼는다.

1

프롬프트 체이닝 (Prompt Chaining)

LLM 호출 A → 게이트 검증 → LLM 호출 B → 게이트 검증 → 결과

순차적 단계로 분해하고 중간에 프로그래밍적 검증 게이트를 넣는다.

적합: 정확도가 중요하고 단계가 명확한 작업
2

라우팅 (Routing)

입력 → 분류기 → 전문가 A / 전문가 B / 전문가 C

입력을 분류하여 전문 핸들러로 보낸다.

적합: 이질적인 요청 유형을 다루는 경우
3

병렬화 (Parallelization)

        ┌→ 작업 A ─┐
입력 ───┼→ 작업 B ──┼→ 합성
        └→ 작업 C ─┘

독립적인 하위 작업을 동시에 실행한다.

적합: 자연스럽게 분할되는 작업, 또는 다양한 관점이 필요한 경우
4

오케스트레이터-워커 (Orchestrator-Workers)

오케스트레이터 LLM → 동적으로 하위 작업 분해 → 워커들 → 합성

병렬화와 달리 하위 작업이 미리 정해지지 않고 동적으로 결정된다.

적합: 어떤 파일을 고칠지 미리 알 수 없는 코딩 작업
5

평가자-최적화자 (Evaluator-Optimizer)

생성 LLM ←→ 평가 LLM (반복 피드백 루프)

하나가 생성하고 다른 하나가 평가하여 반복 개선한다.

적합: 명확한 평가 기준이 있고, 반복으로 품질이 오르는 경우
6

계획-실행 분리 (Plan-Execute)

사용자 요청 → 계획 에이전트 (추론) → 실행 계획
  → 실행 에이전트 (도구 호출) → 결과

계획과 실행을 별도 에이전트로 나눈다. 계획 에이전트는 추론에, 실행 에이전트는 도구 호출에 집중한다. 오케스트레이터-워커는 하위 작업을 동적으로 나눠 주지만, 계획-실행 분리는 계획 자체를 별도 에이전트가 전담한다. 계획 에이전트에는 Read, Grep, Glob 만 주고 Edit, Write 는 실행 에이전트에만 주어 안전성을 높인다.

적합: 복잡한 멀티스텝 작업에서 계획 오류와 실행 오류를 따로 디버깅해야 하는 경우

적합
  • 결정론적 자동 수정 가능한 규칙 — cargo fmt, dart format, eslint --fix, prettier --write
  • 실패 발견 시 fix 가 단일 명령으로 끝나는 영역 (포맷팅, import 정렬, 단순 lint)

  • 훅 실행이 1 초 이상 걸리는 무거운 검증 (전체 빌드, 풀 테스트) — 별도 trigger 권장
  • 비결정론적 수정이 필요한 영역 (코드 리팩토링 제안)
구현 형태

훅은 .claude/settings.json 의 hooks.PostToolUse 에 matcher(Edit|Write) + command 로 등록한다. 명령이 비-zero exit 이면 메인 Claude 가 결과를 받아 후속 조치를 정한다. 에이전트 spawn 은 메인 Claude 가 결정한다 — 훅이 직접 spawn 하지 않는다. 훅은 stateless 다.

Enforcement 등급 관점

훅은 skill-design-guide §3.7 의 E3(결정론적 게이트) 를 에이전트 측에서 구현하는 형태다 — LLM 판단 없이 매 실행마다 같은 판정을 내리므로 문장 규칙(E1)·체크리스트(E2)와 달리 per-run 보장을 준다. 같은 위반이 반복되는데 프롬프트 문구만 계속 다듬고 있다면 그 규칙은 E3 로 올릴 후보다.

보완 패턴 — PreToolUse 가드 (사후 수정이 아닌 사전 차단)

1. Origin Sync 가드

"기본 5 개" 는 하드 리밋이 아니다

"기본 5 개" 는 이 하드 리밋과 별개인 자체 비용 예산이며 항상 하드 리밋보다 작게 잡는다 — 하드 리밋은 사고를 막는 최후 방어선이지 설계 목표가 아니다.

원칙 4 가지

1. Fan-out 상한

1 회 디스패치당 병렬 서브에이전트 기본 5 개 이하. 6+ 개가 필요하면 batch 로 쪼개 순차 처리하거나 사용자에게 비용/시간 trade-off 를 먼저 보고하고 승인받는다. 단순 작업에 fan-out 하지 않는다 (§10 Gotcha 와 같은 정신).

2. 토큰 vs 시간 trade-off 명시

토큰 예산이 빡빡하면 순차 탐색, 시간 예산이 빡빡하면 병렬 탐색. 각 서브에이전트가 독립 context window 를 차지하므로 병렬은 latency 와 토큰을 동시에 키운다. 디스패치 결정 시 어느 축을 우선하는지 한 줄로 적는다.

3. Exploration budget

구현·산출 전 "탐색만" 하는 단계에 상한을 둔다. read-only 탐색이 의미 있는 진전 없이 쌓이면(예: 같은 디렉토리를 반복 Glob, 동일 노드 메타데이터 재조회) 멈추고 지금까지 발견을 요약한 뒤 진행 방향을 사용자에게 확인한다. "조금만 더 보면 알 것 같다" 는 stall 의 가장 흔한 진입점이다.

4. Summary-only 반환

서브에이전트는 raw 출력 전체가 아닌 요약(findings)만 메인 컨텍스트로 돌려준다 (§10 Gotcha "에이전트 결과가 메인 컨텍스트를 채운다" 의 실행 규칙). grep sweep·로그 trawl 같은 noisy 탐색일수록 필수다.

잘 된 점
  • 독립 컨텍스트에서 실행 — "Generator(구현자)와 별도 컨텍스트에서 실행된다". 같은 컨텍스트에서 생성+검증을 할 때의 편향을 막는다. Anthropic 의 평가자-최적화자 패턴과 정확히 일치한다
  • 역할이 명확하다 — "문제를 찾는 것이 유일한 역할이다". 역할 혼합 없이 단일 책임
  • 설정 기반 — project.yaml 에서 카테고리, 안티패턴, 검증 절차를 읽는다. 에이전트에 프로젝트별 지식을 하드코딩하지 않는다
  • 도구가 적절히 제한되어 있다 — tools: Read, Grep, Glob, Bash. QA 평가자가 코드를 고치면 안 되므로 Edit, Write 불가
개선 기회
  • 모델 선택 근거가 없다 — model: sonnet 이 설정되어 있지만 왜 sonnet 인지 문서가 없다. 아키텍처적 판단이 필요한 평가라면 opus 가 나을 수 있고, 단순 체크리스트면 haiku 로 충분할 수 있다
  • 영속 메모리가 없다 — 반복 발견 패턴(예: "이 프로젝트에서 자주 실패하는 조건 유형")을 기억하면 점점 더 정확한 평가가 가능하다
  • description 에 비트리거 조건이 없다 — 스킬 설계 가이드(Section 4)가 권장하는 비트리거 조건이 에이전트 description 에도 필요하다. 예: "단순 텍스트 수정이나 설정 변경에는 사용하지 않는다."

Item 10 — 2026-09 사이클에 표에 올렸다

skill-design-guide §3.7 과 qa-evaluation-guide.md Parity Table 15 행에는 있었는데 이 표에만 없었다. 에이전트 측 짝은 한계 2 다 — 도구를 쥐여 줬다는 사실이 호출했다는 증거가 아니듯, 0 이 나왔다는 사실도 측정이 살아 있다는 증거가 아니다.

skill 가이드 §11 16 행(알려진 답 대조)은 생성 측 전용이라 이 표에 두지 않는다.

Item 8·9 — 2026-08 사이클 신규

Item 8 은 생성 측이 완료를 고집하고 평가 측만 REOPENED 로 다루면 두 판정이 충돌해 사용자가 중재자가 되기 때문에 양면으로 둔다.

Item 9 만 성격이 다르다 — 같은 개념을 공유하는 것이 아니라 이름이 비슷한 다른 개념이라, 양쪽 절이 서로를 참조해 용어 혼동을 막는 것이 parity 의 내용이다.

Item 5 · 6 · 7

Item 5 는 2026-07 사이클에서 양면으로 전환됐다 — 과거에는 "평가자 전용" 이었으나, 생성 측이 [미검증] 을 표기하지 않으면 평가 시점에야 미검증이 드러나 iteration 이 낭비된다. 네 칸은 양쪽이 같은 말을 쓰고, 2 건 기준은 세는 대상이 다르다.

Item 6 은 에이전트 측 fan-out/exploration 통제와 스킬 측 반환 최소화가 토큰 경제라는 같은 목적의 짝 원칙이다. Item 7 은 "원칙을 어떤 강도로 강제할지" 를 판정하는 공통 틀로, 에이전트 측에서는 훅(PostToolUse/PreToolUse)이 E3 게이트의 구현 형태다. Item 7 의 등급 원장은 skill-design-guide 측에만 두고 이 가이드는 참조만 한다 — 원장이 둘로 갈리면 같은 원칙이 두 등급을 갖게 된다. 나머지 1~4 도 양쪽에 있다.
