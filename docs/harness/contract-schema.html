v1 → v3 변경 이력

스키마 버전별 핵심 변경 사항. 각 버전은 sprint-contract 스킬과 qa-evaluator 에이전트 양쪽에 동시 마이그레이션된다.

v3 2026-04-24 (Phase 3 kaizen)

[미검증] 마커 임계값 프로토콜 추가 — 0개: 정상, 1개: 경고 후 진행, 2개 이상: 자동 REJECT. Sibling Enumerated 요건 추가 — sibling 범위 조건은 반드시 각 항목을 열거해야 [enumerated] 유효. Binary Decidability를 선택사항에서 작성 의무(author obligation)로 승격 — 모든 조건에 Pass/Fail 판정 기준이 사전에 명시되어야 함.

v2 2026-04-11 (Phase 2 kaizen)

조건 구체성 태그 ([exact]/[structural]/[goal])와 aggregation mode ([enumerated]/[collective]) 필수화. 숫자 레벨 태그 (L1/L2/L3) 금지 명시 — QA 평가 깊이와 충돌 방지.

v1 초기 스키마

메타데이터 frontmatter (feature, created, complexity, conditions) + 카테고리별 조건 + Anti-patterns + Reusability + Diagnostics 섹션. 조건 끝 태그 없음.

조건 포맷 — Specificity Tag + Aggregation Mode

v2부터 모든 계약 조건은 끝에 구체성 태그를 붙여야 한다. v3 전체 포맷은 아래와 같다.

- [ ] {PREFIX}-{NN}: {조건문} [{specificity}] [{aggregation}?] [{미검증}?]

Specificity Tag

태그의미기본값
[exact]이름/값/구조 문자 그대로 매칭
[structural]섹션/필드/파일 존재 확인✓ 기본
[goal]목표 달성 여부, 수단 무관

Aggregation Mode

모드의미기본값
[enumerated]각 대상을 개별 이름으로 명시해야 PASS
[collective]포괄 경로/패턴 하나로도 PASS✓ 기본
- [ ] UI-01: 라우터에 /settings 경로가 등록된다 [exact] - [ ] UI-02: 모든 버튼에 접근성 라벨이 존재한다 [structural] - [ ] LO-01: 로그인 실패 시 사용자에게 실패 원인이 전달된다 [goal] - [ ] RE-01: References에 g1, g2, g3, g4, g5 5개 파일이 각각 명시된다 [exact, enumerated] - [ ] SK-02: Gotchas 섹션이 존재하고 [미검증] 표시 없이 작성된다 [structural]
L1/L2/L3 태그 금지

숫자 레벨 태그는 QA 평가 깊이 전용으로 예약되어 있다. 계약 태그로 재사용 금지. 레거시 계약의 [L1]/[L2]/[L3]가 남아 있으면 qa-evaluator가 [exact]/[structural]/[goal]로 해석하지만 신규 계약에는 사용 금지.

v3 Additions
v3 신규 사항 — Binary Decidability · [미검증] · Sibling Enumerated

Phase 3 카이젠에서 추가된 세 가지 핵심 변경. 모두 sprint-contract 작성 의무와 qa-evaluator 소비 방식에 영향을 미친다.

1. Binary Decidability — 작성 의무

모든 조건은 Yes/No 판정이 사전에 명확해야 한다. "적절히 처리된다", "잘 동작한다" 같은 모호한 기준은 허용되지 않는다. 작성자는 조건을 작성하면서 "이 조건은 어떻게 Pass/Fail을 판정하는가?"를 자문해야 한다.

Binary Decidability 위반
- [ ] UI-01: 에러 메시지가 적절히 표시된다 [goal] - [ ] DG-01: 코드 품질이 양호하다 [structural]

평가자가 "적절히", "양호하다"를 각자 다르게 해석 — 결과 불일치.

Binary Decidability 준수
- [ ] UI-01: 로그인 실패 시 화면에 에러 메시지 텍스트가 보인다 [goal] - [ ] DG-01: flutter analyze 경고 0건 [exact]

외부에서 관찰 가능한 결과로 기술 — 평가자 해석 충돌 없음.

[미검증] 마커 임계값 프로토콜

조건 내용을 실제로 확인하지 못한 경우 [미검증] 마커를 붙인다. qa-evaluator는 마커 수를 집계하여 아래 임계값으로 판정한다.

0
정상 — 모든 조건이 실제 확인됨. 정상 진행.
1
경고 — 1개 항목 미검증. 경고 메시지 출력 후 평가 계속 진행. 최종 APPROVE 가능.
2+
자동 REJECT — 2개 이상 미검증. 조건 내용을 신뢰할 수 없어 평가 중단. 재작성 후 재평가.
- [ ] SK-02: Gotchas 섹션이 존재한다 [structural] [미검증]

Sibling Enumerated 요건

sibling 파일들(동일 디렉토리의 복수 SKILL.md 등)을 범위로 하는 조건은 반드시 각 파일을 개별 열거해야 [enumerated]가 유효하다. 포괄 경로만 명시하면 [collective]로 다운그레이드된다.

sibling 열거 없음 — collective로 강등
- [ ] H-01: harness 스킬 전체에 Gotchas 섹션이 존재한다 [structural, enumerated]

"전체"는 열거가 아님 — evaluator가 collective로 다운그레이드하거나 REJECT.

sibling 열거 완료 — enumerated 유효
- [ ] H-01: sprint-contract SKILL.md, create-skill SKILL.md, create-agent SKILL.md 각각에 Gotchas 섹션이 존재한다 [structural, enumerated]

각 파일명 열거 → evaluator가 파일별 개별 확인.

Required Sections
필수 섹션 — 4가지

모든 Sprint Contract는 아래 4가지 섹션을 반드시 포함한다. Reusability와 Diagnostics는 sprint-contract 스킬이 자동으로 추가한다.

1. 카테고리별 조건
## {CategoryID} - [ ] {PREFIX}-{NN}: {조건문} [tag]

CategoryID와 PREFIX는 project.yaml.contract_categories에서 가져온다.

2. Anti-patterns
## Anti-patterns - [ ] {id}: {message}

project.yaml.anti_patterns에서 최소 2개 선별. 해당 구현에서 발생 가능성이 높은 것을 우선.

3. Reusability (자동)
## Reusability - [ ] RE-01: private 일회용 컴포넌트가 없다 - [ ] RE-02: 기존 공용 컴포넌트 를 재사용한다

스킬이 자동 삽입.

4. Diagnostics (자동)
## Diagnostics - [ ] DG-01: analyze 경고 0건 - [ ] DG-02: analyze 에러 0건 - [ ] DG-03: 테스트 전체 통과 - [ ] DG-04: 콘솔 에러 0건

스킬이 자동 삽입.

Schema Validation
v3 계약 검증 체크리스트

계약 파일을 작성/수정한 뒤 자가 점검 항목. sprint-contract 스킬이 이 항목을 자동 검사한다.

  • ✓ 파일 경로가 .harness/sprint-contract.md와 일치
  • ✓ frontmatter에 feature, created, complexity, conditions 4 필드 존재
  • ✓ 모든 조건이 - [ ] 체크박스로 시작
  • ✓ 모든 조건에 ID (PREFIX-NN 형식) 부여됨
  • ✓ 모든 조건 끝에 specificity tag 명시
  • ✓ 다수 대상 조건은 aggregation mode 명시
  • ✓ [v3] 모든 조건이 Binary Decidability 기준 충족 — 모호 기준 없음
  • ✓ [v3] [미검증] 마커가 0개 또는 최대 1개
  • ✓ [v3] [enumerated] 조건은 각 대상이 이름으로 열거됨
  • ✓ 숫자 레벨 태그 (L1/L2/L3) 없음 (legacy 변환 완료)
  • ✓ Anti-patterns 섹션에 최소 2개 항목
  • ✓ Reusability 섹션 (RE-01, RE-02) 포함
  • ✓ Diagnostics 섹션 (DG-01 ~ DG-04) 포함
  • ✓ 복잡도와 조건 수가 가이드 비율과 일치
Consumers
스키마 소비자 — Cross-Surface Parity

contract-schema v3는 두 개의 핵심 소비자 + 카이젠 트랙이 동일하게 읽는다. 스키마 버전이 바뀌면 세 곳 모두 동시 마이그레이션되어야 한다.

sprint-contract 스킬

계약을 작성하는 측. 사용자와 합의하여 카테고리·조건·태그·anti-patterns를 결정하고 v3 포맷에 맞게 저장. Binary Decidability 자가 점검, [미검증] 마커 최소화, sibling 조건 열거 확인.

Contract Design Guide
qa-evaluator 에이전트

계약을 소비하는 측. specificity tag, aggregation mode, [미검증] 마커 수, sibling enumerated 열거 완전성을 소비하여 판정. 2개 이상 [미검증]이면 자동 REJECT.

QA Evaluation Guide
kaizen 트랙

contract-kaizen과 evaluator-kaizen이 글로벌 피드백과 스키마를 함께 분석해 가이드 문서를 갱신. 스키마가 v4로 bump되면 sprint-contract, qa-evaluator, contract-schema 세 곳 모두 동시 마이그레이션.

Skill Design Guide §Cross-Surface
왜 동기화가 필요한가

한 측(작성자)이 새 태그를 도입했는데 다른 측(소비자)이 이를 모르면 평가 시 silent failure가 발생한다. 예: 작성자가 [goal]을 추가했는데 평가자가 [exact]로만 처리하면 모든 [goal] 조건이 false negative REJECT가 된다. 스키마 변경은 항상 양쪽 동시 마이그레이션.

Phase 3 Kaizen 변경 요약

Phase 3에서 contract-schema가 v2 → v3로 bump되었다. 핵심 변경: ① Binary Decidability 작성 의무로 승격 — 모호한 기준(적절히, 잘 동작) 계약 조건 금지, ② [미검증] 마커 임계값 프로토콜 — 0개 정상/1개 경고/2개 이상 자동 REJECT, ③ Sibling Enumerated 요건 — sibling 범위 조건은 각 파일 이름 열거 없이 [enumerated] 유효 불가, ④ 전체 v3 예시 계약 추가. sprint-contract 스킬과 qa-evaluator 에이전트 양쪽에 동시 마이그레이션.
