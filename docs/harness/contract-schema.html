Sprint Contract 스키마

YAML frontmatter, 카테고리 구조, 조건 ID 포맷 — sprint-contract와 qa-evaluator가 공유하는 계약 포맷 정의

File Location

계약 파일 위치

Sprint Contract는 프로젝트 루트의 .harness/ 디렉토리에 Markdown 파일로 저장된다.

.harness/sprint-contract.md

contract-kaizen이 변경 제안 가능하며, evaluator-kaizen이 읽어서 평가 루브릭에 반영한다. 현재 스키마 버전: v1

YAML Frontmatter

메타데이터 필드

모든 Sprint Contract는 YAML frontmatter로 시작한다. 4개의 필수 필드가 계약의 범위와 복잡도를 정의한다.

---
feature: "{기능명}"
created: "{YYYY-MM-DD HH:mm}"
complexity: "{simple|medium|complex}"
conditions: {총 조건 수}
---
필드타입설명예시
featurestring구현할 기능의 명칭"로그인 화면 구현"
createddatetime계약 생성 시각"2026-03-30 14:00"
complexityenum기능 복잡도 (파일 영향 범위 기준)medium
conditionsint전체 조건 수 합계10
Required Sections

필수 섹션 목록

모든 Sprint Contract는 4가지 필수 섹션을 포함해야 한다. 카테고리별 조건은 프로젝트 설정에 따라 동적이고, 나머지 3개는 자동 포함된다.

1 카테고리별 조건
## {CategoryID}
- [ ] {PREFIX}-{NN}: {PASS/FAIL 이진 판정 가능한 조건문}
  • CategoryID와 PREFIX는 project.yaml.contract_categories에서 가져온다
  • 조건문은 능동태, 단일 조건, 측정 가능해야 한다
  • "잘 동작한다", "적절히 처리한다" 같은 모호 표현 금지
Bad
"로그인이 잘 동작한다"
"에러를 적절히 처리한다"
Good
"잘못된 비밀번호 입력 시 HTTP 401을 반환한다"
"네트워크 오류 시 재시도 다이얼로그를 표시한다"
2 Anti-patterns

project.yaml.anti_patterns에서 최소 2개 선별. 해당 구현에서 발생 가능성이 높은 것을 우선 선택한다.

## Anti-patterns
- [ ] {id}: {message}
3 Reusability 자동 포함
## Reusability
- [ ] RE-01: private 일회용 컴포넌트가 없다
- [ ] RE-02: 기존 공용 컴포넌트를 재사용한다
4 Diagnostics 자동 포함
## Diagnostics
- [ ] DG-01: analyze 경고 0건
- [ ] DG-02: analyze 에러 0건
- [ ] DG-03: 테스트 전체 통과
- [ ] DG-04: 콘솔 에러 0건
ID Format

조건 ID 포맷 규칙

모든 조건은 카테고리 PREFIX와 2자리 순번으로 고유하게 식별된다. qa-evaluator가 이 ID로 조건을 추적한다.

# 포맷: {PREFIX}-{NN}

UI-01: 로그인 폼이 화면 중앙에 위치한다
UI-02: 비밀번호 필드가 마스킹 처리된다
API-01: POST /auth/login 엔드포인트가 존재한다
RE-01: private 일회용 컴포넌트가 없다
DG-03: 테스트 전체 통과
Complexity Guide

복잡도별 조건 수 가이드

기능의 파일 영향 범위에 따라 적절한 조건 수를 설정한다. 과소 조건은 검증 누락을, 과다 조건은 불필요한 부담을 발생시킨다.

Simple
4-6
조건
파일 영향: 1-3개
Medium
8-12
조건
파일 영향: 4-8개
Complex
12-20
조건
파일 영향: 9+개
