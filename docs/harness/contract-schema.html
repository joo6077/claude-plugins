Specificity Tag
조건 끝 태그 — 모든 조건에 필수

v2 부터 모든 계약 조건은 끝에 구체성 태그를 붙여야 한다. 미명시 시 [structural] 로 간주된다 (기본값).

태그의미
[exact]이름/값/구조 문자 그대로 매칭
[structural]섹션/필드/파일 존재 확인 (기본값)
[goal]목표 달성 여부만 판정, 수단 무관
- [ ] UI-01: 라우터에 /settings 경로가 등록된다 [exact] - [ ] UI-02: 설정 화면에 접근성 라벨이 모든 버튼에 존재한다 [structural] - [ ] LO-01: 로그인 실패 시 사용자에게 실패 원인이 전달된다 [goal]
네이밍 규칙

숫자 레벨 태그 (L1/L2/L3) 는 QA 평가 깊이 전용으로 예약되어 있다. 계약 태그로 재사용 금지. 자세한 작성 기준은 Contract Design Guide 의 §태그 선택 기준 참조.

Aggregation Mode
다수 대상 조건 — enumerated vs collective

조건이 다수 대상 (파일/모듈/키워드) 에 적용될 때, 태그에 모드를 함께 명시한다. 기본값은 collective (포괄, 더 관대).

모드의미
enumerated각 대상을 개별 이름으로 명시해야 PASS
collective (기본)포괄 경로/패턴 하나로도 PASS
- [ ] RE-01: References 에 g1, g2, g3, g4, g5, g5b, g6 7 개 파일이 각각 파일명으로 명시된다 [exact, enumerated] - [ ] RE-02: References 에 docs/react/kit-design/ 경로가 명시된다 [structural, collective]
모드 적용 규칙

모드는 태그가 [exact] 또는 [structural] 일 때만 의미가 있다. [goal] 은 aggregation 개념 자체가 적용되지 않는다.

Contract Design Guide
네 가지 조합

[exact, enumerated] 가장 엄격, [structural, enumerated] 섹션별 검증, [structural, collective] 기본값, [goal, collective] 의미 매칭.

QA Evaluation Guide
Required Sections
필수 섹션 — 4가지

모든 Sprint Contract 는 아래 4 가지 섹션을 반드시 포함한다. Reusability 와 Diagnostics 는 sprint-contract 스킬이 자동으로 추가한다.

1. 카테고리별 조건
## {CategoryID} - [ ] {PREFIX}-{NN}: {조건문} [tag]

CategoryID 와 PREFIX 는 project.yaml.contract_categories 에서 가져온다.

2. Anti-patterns
## Anti-patterns - [ ] {id}: {message}

project.yaml.anti_patterns 에서 최소 2 개 선별. 해당 구현에서 발생 가능성이 높은 것을 우선.

3. Reusability (자동)
## Reusability - [ ] RE-01: private 일회용 컴포넌트가 없다 - [ ] RE-02: 기존 공용 컴포넌트 를 재사용한다

스킬이 자동 삽입.

4. Diagnostics (자동)
## Diagnostics - [ ] DG-01: analyze 경고 0건 - [ ] DG-02: analyze 에러 0건 - [ ] DG-03: 테스트 전체 통과 - [ ] DG-04: 콘솔 에러 0건

스킬이 자동 삽입.

Complexity Guide
복잡도별 조건 수 가이드

파일 영향 범위와 조건 수의 권장 비율. 과소 산정 안티패턴 방지용.

복잡도파일 영향조건 수예시
simple1-3 파일4-6 조건색상 변경, 텍스트 수정, 단일 위젯 추가
medium4-8 파일8-12 조건새 화면 + 라우트 + provider, API 연동
complex9+ 파일12-20 조건새 feature 모듈, 멀티 레이어 리팩터링
v1 vs v2
스키마 마이그레이션 — v1 계약을 v2 로

v1 으로 작성된 기존 계약을 v2 로 마이그레이션할 때의 변환 규칙.

v1 — 태그 없음
- [ ] UI-01: 라우터에 /settings 경로가 등록된다 - [ ] UI-02: 모든 버튼에 접근성 라벨이 존재한다 - [ ] RE-01: References 에 7 개 그룹 문서가 명시된다

판정 방식이 불명확 — QA Evaluator 가 해석 차이로 REJECT 가능.

v2 — 태그 + aggregation
- [ ] UI-01: 라우터에 /settings 경로가 등록된다 [exact] - [ ] UI-02: 모든 버튼에 접근성 라벨이 존재한다 [structural] - [ ] RE-01: References 에 g1, g2, g3, g4, g5, g5b, g6 7 개 파일 이 명시된다 [exact, enumerated]

판정 방식이 사전 합의됨 — 평가 시 해석 충돌 없음.

레거시 호환

v1 계약의 [L1] / [L2] / [L3] 태그가 남아 있는 경우, qa-evaluator 는 다음 매핑으로 해석한다: [L1] ≡ [exact], [L2] ≡ [structural], [L3] ≡ [goal]. 신규 계약에는 사용 금지.

QA Evaluation §Specificity Tag 소비
Schema Validation
v2 계약 검증 체크리스트

계약 파일을 작성/수정한 뒤 자가 점검 항목. sprint-contract 스킬이 이 항목을 자동 검사한다.

  • ✓ 파일 경로가 .harness/sprint-contract.md 와 일치
  • ✓ frontmatter 에 feature, created, complexity, conditions 4 필드 존재
  • ✓ 모든 조건이 - [ ] 체크박스로 시작
  • ✓ 모든 조건에 ID (예: UI-01) 가 부여됨
  • ✓ 모든 조건 끝에 specificity tag [exact]/[structural]/[goal] 명시
  • ✓ 다수 대상 조건은 aggregation mode [enumerated]/[collective] 명시
  • ✓ 숫자 레벨 태그 (L1/L2/L3) 가 조건에 등장하지 않음 (legacy 변환 완료)
  • ✓ Anti-patterns 섹션에 최소 2 개 항목
  • ✓ Reusability 섹션 (RE-01, RE-02) 자동 포함
  • ✓ Diagnostics 섹션 (DG-01 ~ DG-04) 자동 포함
  • ✓ 복잡도와 조건 수가 가이드 비율과 일치 (simple 4-6, medium 8-12, complex 12-20)
  • ✓ 모든 조건이 외부 관찰 가능한 행동 — 클래스명/메서드명/DB명 없음
Consumers
스키마 소비자 — 누가 이 파일을 읽는가

contract-schema v2 는 두 개의 핵심 소비자 + 카이젠 트랙이 동일하게 읽는다. 한쪽이 변경되면 다른 쪽도 동기화되어야 한다. 스키마 v2 는 단순한 형식 합의가 아니라 sprint-contract 와 qa-evaluator 사이의 계약 인터페이스다.

왜 동기화가 필요한가

한 측 (작성자) 이 새 태그를 도입했는데 다른 측 (소비자) 이 이를 모르면 평가 시 silent failure 가 발생한다. 예: 작성자가 [goal] 을 추가했는데 평가자가 [exact] 로만 처리하면 모든 [goal] 조건이 false negative REJECT 가 된다. 스키마 변경은 항상 양쪽 동시 마이그레이션.

sprint-contract 스킬

계약을 작성하는 측. 사용자와 합의하여 카테고리·조건·태그·anti-patterns 를 결정하고 v2 포맷에 맞게 저장. 작성 후 schema validation 자가 점검.

sprint-contract SKILL.md
qa-evaluator 에이전트

계약을 소비하는 측. 각 조건의 specificity tag 와 aggregation mode 에 따라 검증 방식을 분기. 모든 조건은 evaluator 검증 깊이 L3 까지 도달해야 한다.

qa-evaluator agent
kaizen 트랙

contract-kaizen 과 evaluator-kaizen 이 글로벌 피드백 + 스키마를 함께 분석해 가이드 문서를 갱신. 스키마가 v3 로 bump 되면 양쪽 모두 동시 마이그레이션.

Phase 2 Kaizen 변경 요약

Phase 2 에서 contract-schema 가 v1 → v2 로 bump 되었다. 핵심 변경: ① 모든 조건 끝에 specificity tag ([exact]/[structural]/[goal]) 필수화, ② 다수 대상 조건에 aggregation mode ([enumerated]/[collective]) 신설, ③ 숫자 레벨 태그 (L1/L2/L3) 금지 명시 — QA 평가 깊이와의 네이밍 충돌 해결, ④ legacy 계약 마이그레이션 매핑 ([L1]≡[exact] 등) 정의, ⑤ 카테고리 ID prefix 와 조건 ID 형식 ({PREFIX}-{NN}) 명문화. sprint-contract 스킬과 qa-evaluator 에이전트가 동일하게 v2 를 소비한다.
