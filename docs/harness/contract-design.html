단일 해석

해석이 단 하나인가. 능동태("시스템이 반환한다"), 단일 조건("A 이고 B" → 2 개로 분리), 모호 형용사 금지("빠르게"·"적절히"·"충분히" → 구체 수치). IEEE 29148 기반이다.

측정 가능성

파일·코드·실행 결과로 증명 가능한가. 증명 대상이 세상에 없으면 그 조건은 판정 불가다 — 승인 기록 같은 사람이 남겨야 생기는 증거는 기록물의 경로를 조건에 적는다.

FAIL 이미지를 먼저 떠올려라

평가 criteria 의 극단값(PASS/FAIL 양끝) 정의가 중간값 설명보다 judge alignment 에 더 큰 영향을 준다. 각 조건의 FAIL 상태를 한 문장으로 먼저 쓰고 그 부정으로 PASS 를 기술하면 이진 판정 가능성이 올라간다. FAIL 을 한 문장으로 못 쓰면 그 조건은 모호하다.

태그

[exact] / [structural] / [goal]

[exact] — 이름·값·구조가 그것이어야만 의미가 있을 때. "이름이 달라지면 계약 실패" 가 성립하면 이것. [structural] — "해당 구조가 존재한다" 만 검증(미명시 시 기본값). [goal] — 구현 방법은 자유, 결과만.

경험칙: "구현이 X 라서 REJECT 할 것인가?" 에 REJECT 가 부당하게 느껴지면 [goal] 로 완화하고, "이름이 달라도 된다" 고 했다가 실제로는 특정 이름을 강제하고 싶었다면 [exact] 로 강화한다.

숫자 레벨(L1/L2/L3)은 QA 평가 깊이 전용이므로 계약 태그로 재사용 금지.

aggregation

enumerated vs collective

enumerated — 각 대상을 하나씩 이름으로 명시해야 PASS. collective — 포괄 경로/패턴 하나로도 PASS(기본값).

태그 뒤에 콤마로 이어 쓴다: [exact, enumerated]. [goal] 에는 aggregation 개념이 적용되지 않는다.

KZ-04 REJECT: 구현자는 포괄 경로 하나로 처리했고 QA 는 개별 명시를 요구해 REJECT — 계약이 둘 중 하나를 명시했다면 사전에 해소 가능했다.

측정

어떻게 판정할지를 인라인으로

측정 명령(wc -l, grep, cargo build) · 도구(MCP Figma, Playwright, IDE Problems 패널) · 관찰 대상(파일 경로·섹션명·상태 코드) 중 하나 이상을 조건에 적는다.

외부 도구에 의존하면 3 단계 fallback 을 조건에 기술한다 — (1) 기본 검증 (2) 대체 정적 검증 (3) 둘 다 불가 시 [미검증] 허용(계약 전체 1 건까지). 작성 단계에서 [미검증] 예상치가 2 건 이상이면 조건을 재설계하라 — 평가 임계와 맞물려 REJECT 가 예측 가능하다.

범위

범위어는 반드시 인라인 enumerate

"주요"·"모든"·"대부분"·"핵심" 이 등장하면 무엇을 포함하고 무엇을 제외하는지 조건 안에 적는다. 범위가 5 개 이상이면 applies_to: <pattern> 로 대체한다.

SK-02 REJECT: "주요 interactive element 의 box-shadow offset ≥ 4px" 에서 badge/decoration 포함 여부 해석이 갈렸다. Good: "버튼·카드·입력 요소의 box-shadow offset 이 ≥ 4px (badge, decoration, 장식용 icon 은 범위 외) [exact, enumerated]".

구현 누수 금지 — 조건에 넣지 말아야 할 것

클래스명·메서드명·함수명, DB 테이블·컬럼·API 엔드포인트 경로, 프레임워크 용어(controller, service, repository, provider, notifier), 내부 상태 변수·플래그. 구현이 변경되면 조건도 깨지므로 조건의 수명이 짧아진다.

나쁜 예 → 좋은 예: "UserService 의 userRepository 가 비어있을 때" → "등록된 사용자가 없을 때" · "POST /api/users 호출 시 201 을 반환한다" → "신규 사용자 등록 요청 시 성공 응답을 반환한다"

이번 사이클은 문장을 추가하는 대신 재발한 규칙의 근본원인을 각각 막았다. 아래 5 개는 조건을 쓸 때 새로 확인해야 하는 항목이다.

1 · 봉인 (E3)

승인 후에는 조건 문구를 고치지 않는다

사용자 승인 직후 조건 체크박스 줄만 정규화 해시해 conditions_digest / locked_at 에 기록한다. 체크박스 토글과 서술 편집은 봉인을 깨지 않는다 — 일부러 그렇게 설계했다. 조건 문구 변조와 조건 추가·삭제만 깨진다.

SEAL_BROKEN 을 만나면 조용히 다시 봉인하지 마라 — 그것은 위반을 지우는 행위다. 레거시 계약(SEAL_ABSENT)은 경고이지 실패가 아니며 소급 봉인은 금지다. 봉인은 조건 문구의 불변성만 보장하고 조건이 옳았는지는 보장하지 않는다 — 게이트를 올리면 과차단 비용과 우회 유인이 함께 생기고, 우회된 게이트는 없는 게이트보다 나쁘다.

Reason Less, Verify More: Deterministic Gates — arxiv:2607.07405
2 · Amendment 2 축

방향과 동의를 따로 적는다

direction 은 PASS 집합의 증감으로만 정한다 — 허용 경로를 줄이면 narrowing, 요구 대상을 줄이면 relaxing. "범위 축소" 라는 말로 판정하지 마라.

narrowing 은 consent 와 무관하게 PASS 근거가 된다(제약 강화라 남용 불가). relaxing 은 사용자 앵커가 있을 때만. 앵커가 없으면 unanchored 라고 쓰는 것이 정답이며, 지어내면 narrowing 까지 무효가 된다. 집합형은 자기신고 대신 계산한다.

3 · 측정 커버리지

산문이 요구한 것과 측정이 훑는 것이 같은가

enumerated 조건은 산문 측 대상과 측정 측 대상을 같은 표기(백틱 · 공백 없는 토큰)로 적는다. 상위 패턴 하나로 여러 대상을 덮을 때는 작성 시점에 그 명령을 1 회 실행해 확장 결과를 열거한다.

이것은 blocking 게이트가 아니라 검출기다. 실측(계약 109 개 · enumerated 114 개): 나이브 형태 76 건, 좁힌 형태 29 건이 flagged — 오탐이 이 정도면 자동 FAIL 은 정상 계약을 막는다. UNCOVERED 1 건마다 조건을 고치거나 해소 기록 한 줄을 남긴다. lexical ambiguity linter 를 자동 판정기가 아니라 "검출기 + 사람의 해소 기록" 으로 쓰는 접근과 같은 결론이다.

4 · 인자 매트릭스

조합 케이스 수를 손으로 적지 마라

축이 2 개 이상이고 그 곱이 조건의 의미를 결정할 때만 쓴다. 축 값의 출처를 코드의 공유 상수/enum 으로 지정하고, cases_total 은 곱을 산출하는 명령의 출력을 쓴다.

LG-01 REJECT: "3 visibility × 6 relation = 18 케이스 중 15 케이스만 재현" · "16 종 매핑 중 2 종만 검증". 기본은 full Cartesian 이고, pairwise 로 낮추려면 곱셈 결과와 사유를 적고 승인받는다. combinatorial coverage 는 statement/branch coverage 와 다른 정적 test-set 속성이라 기존 커버리지 수치로 대체할 수 없다.

5 · 음성 대조

구현을 지워도 통과하는 측정문은 oracle 이 아니다

조건이 테스트·실행 산출물로 판정될 때만 필수다(파일·섹션 존재를 보는 [structural] 조건에는 적용하지 않는다 — 대상을 지우면 자명하게 실패하므로 무의미하다).

조건에 음성 대조: 절을 넣고 어느 구현 지점을 무력화하면 그 측정이 FAIL 하는지 적는다. 측정이 구현을 직접 호출하는지 확인한다 — 테스트가 로직을 재작성해 검증하면 결합이 없다. 작성 시점에 실제로 돌릴 수 없으면 그 사실을 조건에 적는다. "돌렸다" 고 적지 마라.

Bad — ER-02 실측
- [ ] ER-02: 낙관적 동시성 가드에 대한 테스트가 존재하고 통과한다 [structural] ← mutation test 로 확정: 실제 코드에서 가드를 완전히 삭제해도 통과한다
Good
- [ ] ER-02: 낙관적 동시성 가드가 conflict 경로를 실제로 막는다 [goal] (측정: 대상 행을 사전 변형한 뒤 실제 바이너리를 호출해 skipped 카운터 증가 관찰 · 음성 대조: 가드 술어를 제거하면 이 측정이 FAIL 해야 한다)

계약 테스트의 표준 관점도 같다 — consumer 측 검증만 하면 provider 가 예고 없이 바뀌고, provider 측만 검증하면 consumer 가 잘못된 요청을 보낸다. 양쪽을 다 검증해야 통합 실패가 잡힌다. 단 소비면의 내부 구현은 조건화하지 마라 — Pact 가 경고하는 과잉 계약(over-specified contract)이 된다. 열거 대상은 파일 경로와 외부 관찰 가능한 동작까지다.

조건 문장에 테스트·문서·스크린샷이 등장하고 태그가 [exact] 이면 그 산출물은 같은 스프린트 제출 대상이 된다. 평가자는 "구현은 됐지만 테스트가 없다" 를 조건 미충족으로 읽는다. 산출물을 낼 생각이 없다면 조건을 [goal] 로 낮추거나 산출물 문구를 조건에서 빼라 — 그대로 두면 REJECT 가 예정된 것이다 (UI-07 실측).

File Structure
계약 파일 헤더는 2 계층뿐이다 (E3)

기존 규칙은 "허용 헤더는 카테고리 + Anti-patterns / Reusability / Diagnostics 뿐" 이었는데, 실제 계약(특히 카이젠 계약)은 배경·리서치 소스·GAP 분석·범위 경계를 상시 사용해 왔다. 규칙이 실사용과 어긋나 있었기 때문에 재위반이 반복됐다 — 그래서 규칙을 강화하는 대신 헤더를 두 계층으로 분류했다.

두 목록 밖의 헤더(Notes, Appendix, 메모)는 금지다 — 평가자 파서가 조건 섹션인지 서술인지 판정할 수 없다. 서술 섹션에 - [ ] 를 쓰면 평가자가 조건으로 오인해 존재하지 않는 조건을 판정하려 든다. 이 규칙은 E3 이며 sprint-contract 는 저장 직후 결정론적 헤더 검사를 실행한다.

저장 직후 결정론적 검사 (위반 0 건 확인 후 다음 단계)
# (1) 헤더 목록 — 허용 목록 밖 헤더가 있으면 위반
grep -n '^## ' "$CONTRACT"

# (2) 서술 섹션에 조건 체크박스가 섞였는지 — 조건 섹션 밖의 '- [ ]' 는 위반
awk '/^## /{s=$0} /^- \[ \]/{print FILENAME":"FNR": "s" -> "$0}' "$CONTRACT"
amendment 는 계약 본문 섹션이 아니다

스프린트 도중 합의된 조건 변경을 기록하려고 ## 변경 이력 · ## Amendments · ## Notes 를 계약 본문에 추가하지 마라 — 허용 목록 위반이며 parser-incompatible-contract-section 재발이다. amendment 는 별도 사이드카 파일(sprint-amendments-<slug>.md)에 쓴다.

Pre-DRAFT Checklist
DRAFT 를 사용자에게 보이기 전에
  • ✓각 조건에 정성적 수식어(충분히 / 상당한 / 적절히 / 대부분 / 거의)가 없는가?
  • ✓각 조건의 FAIL 상태를 1 문장으로 쓸 수 있는가? 불가능하면 그 조건은 모호하다
  • ✓모든 조건에 [exact]/[structural]/[goal] 태그가 있는가? 다수 대상이면 aggregation mode 도 붙였는가?
  • ✓경계값(>=, <=, ==) 조건에 임계값 + 측정 대상 + 측정 방법 3 요소가 다 있는가?
  • ✓범위어("주요"·"모든"·"대부분")가 들어간 조건에 포함/제외 목록을 인라인 enumerate 했는가?
  • ✓측정 명령이 조건 의도와 같은 것을 재는가? 상태 의존적이면 Given: 전제를 박았는가?
  • ✓변경 범위 조건이 Diff-Scope Oracle 표준형 4 요소를 다 채웠고 baseline 을 실행해 붙였는가?
  • ✓계약·직렬화·공유 모델을 바꾸는데 consumer 면 조건이 있는가?
  • ✓서술 절의 설계 의도와 조건이 같은 방향을 가리키는가? 열거한 기존 식별자가 실제로 존재하는가?
  • ✓[goal] 조건이 참조하는 증거 기록물의 경로가 조건에 있는가?
  • ✓공통 원칙 조건이라면 sibling 스킬 개수를 숫자로 명시하고 이름을 전부 열거했는가?
  • ✓테스트 통과를 요구하는 조건에 음성 대조: 절이 있는가?
  • ✓2 개 이상 축의 곱이 의미를 결정하는 조건에 축·축 값·cases_total 산출 명령이 있는가?
  • ✓헤더가 2 계층 허용 목록 안에 있고, 서술 섹션에 - [ ] 가 섞이지 않았는가?
  • ✓사용자 승인 후 conditions_digest / locked_at 을 기록하고 검증 출력을 인용했는가?

GQM

Goal → Question → Metric

Goal 이 기능이 달성하려는 목표는 무엇인가 → Question 목표 달성을 어떻게 확인하는가 → Metric 어떤 구체적 지표로 측정하는가.

카테고리는 Goal 에서 도출한다. 단 project.yaml 의 contract_categories 가 이미 정의되어 있으면 그것을 따른다 — 카테고리를 새로 발명하면 조건 섹션 헤더 규약이 깨진다.

Consumer-Driven

평가자가 독립 검증할 수 없는 조건은 나쁜 조건이다

자기 점검은 한 문장이다 — "이 조건을 코드와 실행 결과만으로 PASS/FAIL 판정할 수 있는가?" YES 면 유효, NO 면 재작성.

LLM-as-Judge 연구 요지: "criteria 품질이 평가 품질을 결정하며, 추가적인 CoT 로 모호한 criteria 를 보완하는 것은 한계가 있다." 계약 작성 단계에서 criteria 를 명확히 하는 것이 가장 ROI 높은 개입이다.

구조화

복잡도 "중간" 이상이면 GWT / AAA 필수

Given {전제} / When {동작} / Then {기대 결과} 또는 Arrange / Act / Assert. 두 패턴은 같은 개념(사전 상태 → 행동 → 관찰)의 다른 어휘다.

Gherkin one When-Then pair 규칙 — 한 조건에 When-Then 쌍은 1 개만. 2 개 이상이면 복합 조건이므로 분리한다. 반구조화 조건이 비구조화 자연어보다 LLM 추론 정확도를 높이고 할루시네이션을 줄인다.

Gherkin Best Practices
예외

예외는 별도 문서가 아니라 조건 안에

조건이 특정 파일·상황·타입에 적용되지 않으면 조건 내부에 인라인으로 예외를 명시한다. 별도 문서로 분리하거나 구두로 합의하면 QA 시점에 반영되지 않는다.

예외는 "왜 제외하는가" 를 한 줄로 설명한다(이유 없는 예외 금지). 예외가 3 개를 초과하면 조건 자체를 범위 한정(applies_to)으로 재작성한다.
