Core Principles
검증 가능성 · 단일 해석 · 측정 가능성

모든 조건은 제3자가 코드만 보고 PASS/FAIL 을 판정할 수 있어야 한다. IEEE 29148 요구사항 품질 기준을 따른다.

검증 가능성 (Verifiability)

모든 조건은 제3자가 코드만 보고 PASS/FAIL 을 판정할 수 있어야 한다. 좋은 예: "로그인 실패 시 HTTP 401 반환". 나쁜 예: "로그인이 적절히 처리된다".

IEEE 29148 Requirements
단일 해석 (Unambiguity)

능동태 사용, 단일 조건 ("A이고 B" → 분리), 모호 형용사 금지 ("빠르게", "적절히", "충분히" → 구체 수치).

NASA Requirements Writing
측정 가능성 (Measurability)

조건의 충족 여부를 파일·코드·실행 결과로 증명할 수 있어야 한다. 실행 가능한 unit test 에 가까울수록 좋다.

LLM Agent SE Benchmark Survey
Condition Writing
조건 작성법 — NASA & Design by Contract

NASA Requirements Writing Standards 와 Design by Contract (Meyer, 1992) 구조를 결합하여 조건을 작성한다.

NASA 기반 규칙

각 조건은 하나의 "shall" (한국어 "~한다") 만 포함. 부정 조건보다 긍정 조건 선호 ("에러가 없다" → "정상 응답을 반환한다"). "and/or" 사용 금지 — 각각 별도 조건으로.

NASA Requirements Writing
Pre / Post / Invariant

Precondition: 구현 시작 전 충족 조건 (환경, 의존성). Postcondition: 구현 완료 후 반드시 참 (핵심 기능). Invariant: 구현 전후로 변하지 않는 조건 (기존 기능 보전).

Design by Contract (Meyer)
외부 관찰 가능성

조건은 시스템이 무엇을 하는지만 기술한다. 클래스명, 메서드명, DB 테이블, 프레임워크 용어, 내부 상태 변수 금지. 위반 시 "구현 누수(implementation leakage)".

IEEE 29148
Bad — 구현 누수
UserService의 userRepository가 비어있을 때 POST /api/users 호출 시 201을 반환한다

클래스명, 엔드포인트 경로가 노출됨. 구현이 변경되면 조건도 깨진다.

Good — 외부 행동
등록된 사용자가 없을 때 신규 사용자 등록 요청 시 성공 응답을 반환한다

구현 방식과 무관하게 외부 행동만 기술.

Specificity Tags
[exact] / [structural] / [goal] — 문자 태그 체계

계약의 각 조건이 어느 수준으로 판정될지 명시한다. 수준이 불명확하면 QA Evaluator 가 해석을 달리해 판정이 엇갈린다. 숫자 레벨 (L1/L2/L3) 은 QA 평가 깊이 전용으로 예약되어 있으므로 계약 태그로 재사용 금지.

태그정의판정 기준적합한 상황
[exact] 특정 이름/값/구조를 문자 그대로 매칭 해당 식별자가 코드에 존재하는지 직접 검색 함수명 계약, 파일명 계약, 특정 클래스 구조
[structural] 섹션/필드/파일의 존재 여부 및 필수 서브구조 지정된 섹션·필드가 존재하는지 확인 "X 섹션을 포함한다", "Y 필드가 있다"
[goal] 수단 무관, 목표 달성 여부만 판정 기능이 의도한 결과를 산출하는지 확인 "SSOT 달성", "회귀 없음", "파싱 성공"
- [ ] PU-01: 문서 파싱이 pyyaml 기반으로 동작한다 [goal] - [ ] SK-01: References 섹션에 7개 문서가 각각 파일명으로 명시된다 [structural] - [ ] CD-01: compare-bad/compare-good 클래스를 사용하는 비교 블록이 2쌍 이상 존재한다 [exact]
실제 발생 사례 — PU-04 REJECT

계약이 "pyyaml 기반 파싱 함수 사용"을 요구했으나 exact/goal 어느 수준인지 불명확해, 같은 목표를 달성한 구현이 "함수명 불일치"로 REJECT 됨. 계약에 [goal] 을 명시했다면 PASS 처리 가능했던 케이스다.

"구현이 X 라서 REJECT 할 것인가?" 라고 자문했을 때 REJECT 가 부당하다고 느끼면 태그가 [exact] 일 가능성이 높다 — [goal] 로 완화하라. 반대로 "이름이 달라도 상관없다"고 했다가 실제로는 특정 이름을 강제하고 싶었다면 [exact] 로 강화하라.

[exact]선택 기준

이름·값·구조가 그것이어야만 의미가 있을 때. 공개 API 정확한 함수 시그니처, 파일 경로 그 자체, 정규표현식 문자열 리터럴. "이름이 달라지면 계약 실패" 가 성립하면 [exact].

[goal]선택 기준

구현 방법은 자유이고 결과만 보고 싶을 때. "SSOT 유지", "파싱 성공", "중복 제거". 함수명·라이브러리·접근법이 달라도 목표만 달성하면 PASS.

Aggregation Mode
enumerated vs collective — 다수 대상 조건의 형식

조건이 다수의 대상 (파일·모듈·키워드·경로) 에 적용될 때, 계약 작성자는 개별 명시 (enumerated) 모드와 포괄 경로 (collective) 모드 중 어느 쪽을 요구하는지 명시해야 한다. 형식을 정하지 않으면 평가가 엇갈린다.

모드의미판정 방법예시
enumerated 각 대상을 하나씩 이름으로 명시해야 PASS 모든 개별 이름이 문서에 직접 등장하는지 확인 [exact, enumerated]
collective (기본) 포괄 경로/패턴 하나로 지정해도 PASS 경로·디렉토리 지정이 전체를 커버하는지 확인 [structural, collective]
Bad — 모드 미명시
- [ ] RE-01: References 에 7 개 그룹 문서가 명시된다

구현자는 포괄 경로 하나로 처리, QA 는 개별 명시 요구 → REJECT.

Good — 모드 명시
- [ ] RE-01: References 에 g1, g2, g3, g4, g5, g5b, g6 7 개 파일이 각각 파일명으로 명시된다 [exact, enumerated]

판정 방식이 사전에 합의됨.

실제 발생 사례 — KZ-04 REJECT

계약이 "react-kaizen References 섹션에 docs/react/kit-design/ 7 개 그룹 문서가 명시된다" 로 작성되었는데, 구현자는 포괄 경로 하나로 처리했고 QA 는 개별 명시를 요구해 REJECT. 계약이 [exact, enumerated] 또는 [structural, collective] 중 하나를 명시했다면 사전에 해소 가능했던 케이스.

Boundary Conditions
경계값 조건 — 임계값 + 측정 대상 + 측정 방법

수량·길이·크기 등 임계값을 포함하는 조건은 측정 방법을 함께 명시한다. 측정 방법이 없으면 QA Evaluator 가 다른 도구·기준으로 측정하여 판정이 엇갈린다.

임계값

구체적 숫자로 표현한다. >= 1500, == 0, <= 3 등. "충분한", "적절한" 같은 모호 표현 대신 수치를 명시.

측정 대상

무엇을 세는가. 줄 수, 파일 수, 바이트 수, 항목 수 등. 대상이 모호하면 측정 결과도 모호하다.

측정 방법

어떻게 세는가. 명령어, 도구, 계산식을 인라인으로 명시한다. 구현자와 평가자가 동일한 방법으로 확인 가능해야 한다.

Bad — 측정 방법 미명시
- [ ] AR-03: docs/flutter/ 문서가 충분한 분량이다 [goal] - [ ] AR-03: docs/flutter/ 문서가 1500줄 이상이다 [exact] ← 측정 방법 미명시: wc -l vs grep -c vs 에디터 줄 수?

임계값은 있지만 측정 도구가 없으면 구현자와 QA 가 다른 결과를 얻는다.

Good — 3요소 명시
- [ ] AR-03: docs/flutter/ 하위 .md 파일의 총 줄 수가 1500 이상이다 (측정: wc -l docs/flutter/*.md | tail -1) [exact]

임계값 + 측정 대상 + 측정 명령이 모두 인라인에 포함됨.

실제 발생 사례 — AR-03 REJECT

계약이 ">= 1500줄" 을 요구했으나 측정 방법을 명시하지 않아, 구현이 1498줄 (2줄 부족) 로 REJECT. 측정 명령이 사전에 합의되었다면 구현 중 즉시 확인이 가능했던 케이스.

Scope Granularity
스코프 세분화 — file / section / field 수준

조건이 포맷·구조·패턴의 적용을 요구할 때, 적용 단위를 명시한다. "일관된 포맷" 같은 표현은 파일 단위인지, 섹션 단위인지, 필드 단위인지 해석이 갈린다.

수준의미예시
file-level 파일 전체가 동일 포맷 "모든 .md 파일이 YAML frontmatter 를 포함한다"
section-level 특정 섹션 내부 구조 통일 "각 섹션의 소스 테이블이 동일 컬럼 구성이다"
field-level 개별 필드/컬럼까지 명시 "소스 테이블에 번호, 제목, URL, 태그 4개 컬럼이 존재한다"
적용 규칙

포맷 일관성을 요구하는 조건은 최소 section-level 까지 명시한다. field-level 까지 명시하면 가장 정확하지만 조건이 길어지므로 핵심 필드만 열거한다. "일관된 포맷" 단독 사용 금지 — 어떤 수준에서 일관적인지 반드시 부연.

실제 사례 — ER-02 / AR-03 REJECT

계약이 "6개 파일의 일관된 포맷" 을 요구했으나 컬럼 구성까지 명시하지 않아, 한 파일만 태그 컬럼이 누락된 채 통과하려 했고 QA 가 REJECT. field-level 로 "소스 테이블에 [official]/[blog] 태그 컬럼 포함" 을 명시했다면 사전에 해소 가능했던 케이스.

Structuring
Given-When-Then / Arrange-Act-Assert 구조화

BDD 의 GWT 또는 테스트 패턴 AAA 로 조건을 구조화한다. 두 패턴은 동일 개념 (사전 상태 → 행동 → 관찰) 을 다른 어휘로 표현. 반구조화 조건이 비구조화 자연어보다 LLM 추론 정확도를 높인다 (Thoughtworks 2025).

Bad — 복합 When-Then
When 사용자가 로그인을 시도하고 비밀번호가 잘못되었으며 3회 연속 실패한 경우 Then 계정이 잠기고 이메일 발송됨

한 조건에 When-Then 쌍이 2 개 이상 — 분리 필요.

Good — 1 When-Then per condition
- [ ] AU-01: 비밀번호 3회 연속 실패 시 계정이 잠긴다 [goal] - [ ] AU-02: 계정 잠금 시 이메일이 발송된다 [goal]

각 조건에 When-Then 쌍 1 개씩.

적용 기준

복잡도 중간 이상: 모든 핵심 조건에 GWT/AAA 구조 필수. 복잡도 단순: 선택 사항이나 권장. Gherkin one When-Then pair 규칙 준수.

Gherkin Best Practices
AAA Blueprint 패턴

LLM 코드 에이전트 벤치마크 연구는 PRD 를 evaluation blueprint 로 쓰고 GPT-4.1 이 Arrange-Act-Assert 형식으로 테스트 케이스를 생성하는 파이프라인을 제시. 계약 조건을 AAA 로 작성하면 그 자체가 실행 가능한 spec 에 가까워진다.

Exception Clause
예외 조항 포맷 — 인라인 명시 원칙

조건이 특정 파일·상황·타입에 적용되지 않을 경우, 조건 내부에 인라인으로 예외를 명시한다. 별도 문서로 분리하거나 구두로 합의하면 QA 시점에 예외가 반영되지 않는다.

Bad — 예외 없는 전체 적용
- [ ] CD-02: 모든 docs 페이지에 compare-bad/compare-good 비교 블록이 2쌍 이상 존재한다

integration.html (Final 통합 페이지) 에도 동일 적용되어 불필요한 REJECT.

Good — 인라인 예외
- [ ] CD-02: 모든 docs 페이지에 compare-bad/compare-good 비교 블록이 2쌍 이상 존재한다. 예외: (a) integration.html — Final 통합 페이지로 제외, (b) index.html — 목록 페이지로 콘텐츠 조건 비적용

예외에 "왜 제외하는가" 이유가 포함됨.

예외 규칙

예외는 "왜 제외하는가"를 한 줄로 설명 (이유 없는 예외 금지). 예외 항목이 3개를 초과하면 조건 자체를 applies_to 범위 한정으로 재작성. 예외 없이 작성된 조건은 해당 카테고리의 모든 파일에 적용된다고 간주.

applies_to 범위 한정

예외 3개 초과 시 조건 적용 범위를 파일 패턴이나 성격으로 한정한다. 예: docs/react/ 하위 콘텐츠 페이지(integration.html, index.html 제외)에 비교 블록 2쌍 이상 존재한다.

Property vs Example
Property 기반 vs Example 기반 조건

단순 기능은 Example 기반, 복잡한 로직은 Property 기반을 혼용한다.

Example 기반

"입력 'abc' 에 대해 'ABC' 를 반환한다" — 구체적이지만 범위 좁음. 단순 변환, 고정 입출력, 스모크 테스트에 적합.

Property 기반

"모든 입력에 대해 출력 길이가 입력 길이와 같다" — 범위 넓음. 복잡한 로직, 불변 조건, 경계값 조건에 적합.

Category Design
카테고리 설계 — GQM + Consumer-Driven

GQM (Goal-Question-Metric) Framework 로 카테고리를 도출하고, 계약의 "소비자" 인 qa-evaluator 가 독립 검증 가능한지 점검한다.

Goal

이 기능이 달성하려는 목표는 무엇인가? 카테고리는 Goal 에서 도출한다. project.yaml 의 contract_categories 가 이미 정의되어 있으면 그것을 따른다.

Question

목표 달성을 어떻게 확인하는가? 질문이 곧 조건의 카테고리가 된다. 기능 · 성능 · 보안 · 접근성 등으로 분화.

Metric

어떤 구체적 지표로 측정하는가? 지표가 곧 개별 조건이 된다. Consumer-Driven 자기 점검: "이 조건을 코드와 실행 결과만으로 PASS/FAIL 판정할 수 있는가?"

LLM-as-Judge 연구 요지

"Evaluation criteria are critical for reliability. Non-deterministic sampling improves alignment with human preferences over deterministic evaluation, and CoT reasoning offers minimal gains when clear evaluation criteria are present." — criteria 품질이 평가 품질을 결정하며, 추가적인 CoT 로 모호한 criteria 를 보완하는 것은 한계가 있다. 계약 작성 단계에서 criteria 를 명확히 하는 것이 가장 ROI 높은 개입이다.

Expression Variants
한·영 표현 변형 처리

한국어 + 영어가 혼용되는 도메인에서 동일 개념이 여러 표현으로 등장한다. 표현 변형이 있는 조건은 한·영 병기 또는 한쪽으로 통일 중 하나를 명시적으로 선택하라.

Bad — 변형 비통일
레이아웃 shift 발생 0 건

구현 코드가 layout-shift 로 작성되면 키워드 매칭이 어긋남.

Good — 병기 또는 통일
Layout shift (레이아웃 shift) 발생 0 건 [goal] 또는: Layout shift 발생 0 건 — 본 계약에서는 영어 표기 Layout shift 로 통일 [goal]

표현 변형이 사전에 합의됨.

Anti-patterns
계약 안티패턴 — Phase 2 추가 항목 포함

기존 안티패턴에 더해 Phase 2 가 신규로 강제하는 항목들. AR-03/ER-02 REJECT 패턴 반영으로 경계값 측정 미명시, 포맷 세분화 미명시가 추가되었다.

안티패턴문제수정 방법
모호한 조건"적절히 처리한다" → 해석이 여러 개구체적 행동과 결과로 재작성
단일 카테고리 편중모든 조건이 UI에만 집중GQM으로 카테고리 균형 확인
복합 조건"A이고 B이며 C이다"각각 독립 조건으로 분리
과소 안티패턴0–1개 안티패턴최소 2개 필수
테스트 불가 조건"사용자 경험이 좋다"측정 가능한 지표로 변환
복잡도 과소평가파일 수로만 판단영향 범위(레이어, 공개 API)로 판단
구현 누수조건에 클래스명/메서드명/DB명 포함외부 관찰 가능한 행동으로 재작성
NFR 누락기능 조건만 있고 비기능 조건 없음성능/보안/접근성 중 해당 항목 추가
판정 기준 범주 미명시 v2exact/structural/goal 어느 수준인지 불명확조건 끝에 문자 태그로 구체성 명시
예외 없는 전체 적용 v2특정 파일 타입에 부적합한데 예외 없이 전 범위 적용예외 조항 인라인 명시 또는 applies_to 로 범위 한정
Aggregation mode 미명시 v2다수 대상 조건에서 개별/포괄 중 무엇을 요구하는지 불명확[exact, enumerated] 또는 [structural, collective] 명시
한·영 표현 변형 비통일 v2"Layout shift" vs "레이아웃 shift" 혼재 → 키워드 매칭 불일치한·영 병기 또는 한쪽으로 통일 선언을 조건 내부에 명시
숫자 레벨 태그 혼용 v2QA 평가 깊이용 숫자 레벨을 계약 조건에 재사용반드시 문자 태그 [exact]/[structural]/[goal] 만 사용
경계값 측정 방법 미명시 v2">= N" 조건에 측정 명령/도구 없음 → 판정 엇갈림임계값 + 측정 대상 + 측정 방법(명령어)을 인라인으로 명시
포맷 세분화 수준 미명시 v2"일관된 포맷" 요구에 file/section/field 중 어느 수준인지 불명확최소 section-level 까지 명시, 핵심 필드는 field-level 로 열거
Gotchas Checklist
Sprint Contract 작성 체크리스트

계약 작성 후 자가 점검 항목. 하나라도 NO 가 나오면 수정 후 재검토.

  • ✓ 모든 조건이 PASS/FAIL 이진 판정 가능 (제3자가 코드만 보고 판단)
  • ✓ 모호 형용사 ("빠르게", "적절히", "충분히") 가 조건에 등장하지 않음
  • ✓ 모든 조건 끝에 specificity tag ([exact]/[structural]/[goal]) 명시
  • ✓ 다수 대상 조건은 aggregation mode ([enumerated]/[collective]) 명시
  • ✓ 숫자 레벨 (L1/L2/L3) 태그를 계약 조건에 재사용하지 않음
  • ✓ 한·영 표현 변형이 있으면 한·영 병기 또는 한쪽 통일 선언
  • ✓ 복잡도 중간 이상 조건은 GWT 또는 AAA 구조로 작성
  • ✓ 조건당 When-Then 쌍 1 개 — 2 개 이상이면 분리
  • ✓ 외부 관찰 가능한 행동만 — 클래스명/메서드명/DB명 등 구현 누수 없음
  • ✓ 예외 조항이 필요한 조건은 인라인으로 명시 (이유 1 줄 포함)
  • ✓ 경계값 조건에 임계값 + 측정 대상 + 측정 방법 3요소 포함
  • ✓ 포맷 일관성 조건에 적용 수준 (file/section/field) 명시
  • ✓ 안티패턴 최소 2 개 선별
  • ✓ 카테고리가 GQM (Goal-Question-Metric) 으로 도출되어 균형
Self-Improvement
자기개선 메커니즘 — 모호성 분류 + 진단

계약 검토 시 3 가지 유형의 모호성을 구분하여 점검한다. 각 유형은 다른 수정 전략을 요구한다.

유형설명예시수정 방법
어휘적 (Lexical)단어 자체가 여러 의미"처리한다", "관리한다"구체 동사로 대체 ("반환한다", "저장한다")
구문적 (Syntactic)문장 구조가 여러 해석 허용"A와 B를 포함하는 C"분리하여 각각 명시
의미적 (Semantic)도메인 맥락 없이 해석 불가"적절한 응답"구체적 상태 코드/값으로 명시
구조화 진단 체크리스트

sprint-contract 실행 후 9 항목 자가 점검: ambiguous_conditions, missing_error_paths, untestable_conditions, category_coverage_gap, complexity_underestimate, implementation_leakage, nfr_coverage, boundary_without_measurement, format_granularity_missing.

Phase 2 Kaizen 변경 요약

Phase 2 에서 contract-design-guide + contract-schema 가 v1 → v2 로 bump 되었다. 핵심 변경: ① 숫자 레벨 (L1/L2/L3) 네이밍 충돌 해결 — 문자 태그 [exact]/[structural]/[goal] 로 교체, ② Aggregation Mode ([enumerated]/[collective]) 신설, ③ 태그 선택 기준 서브섹션 추가, ④ AAA blueprint / Gherkin one When-Then pair 인용, ⑤ LLM-as-Judge 신뢰성 연구 인용 — criteria 품질이 평가 품질을 결정, ⑥ 경계값 측정법 — 임계값 + 측정 대상 + 측정 방법 3요소 필수 (AR-03 REJECT 반영), ⑦ 스코프 세분화 — file/section/field 수준 명시 필수 (ER-02 REJECT 반영), ⑧ 안티패턴 6 개 추가 (specificity 미명시, 예외 없는 전체 적용, aggregation 미명시, 한·영 표현 변형, 경계값 측정 미명시, 포맷 세분화 미명시), ⑨ 구조화 진단 체크리스트 7 → 9 항목 확장, ⑩ 실제 REJECT 사례 (PU-04, KZ-04, AR-03, ER-02) 의 사후 분석을 가이드에 명시.
