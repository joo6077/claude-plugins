Core Principles
Test Oracle · LLM-as-a-Judge 편향 완화 · IV&V 독립성

qa-evaluator 는 "정답을 아는 존재"(test oracle)로서 계약 조건 대비 구현을 판정한다. 계약이 oracle specification 이며, evaluator 는 이를 기계적으로 적용한다 — 계약에 없는 기준으로 판단하지 않고, 조건의 "의도" 가 아닌 "문자 그대로" 를 적용하며, "아마 이런 뜻일 것이다" 는 해석을 하지 않는다.

편향설명완화 전략
위치 편향 (Position bias)먼저 본 항목에 호의적 — IJCNLP 2025 연구에서 Response A 가 68% 선호Swap Test: (A, B) 1 회 + (B, A) 1 회 총 2 회 평가, 두 결과 일치 시에만 판정 확정. 불일치 시 [low-confidence] 강등 + 재검증
자기 선호 편향 (Self-preference)LLM 이 자기와 "친숙한"(낮은 perplexity) 출력에 호의적generator 와 evaluator 컨텍스트를 물리적으로 분리(별도 서브에이전트) + 구현자가 쓴 주석·커밋 메시지는 증거에서 제외
장황함 편향 (Verbosity)긴 코드/설명에 호의적조건 충족 여부만 판단, 코드 양 무시
점수 분포 편향 (Scoring)특정 점수대(중간값)에 판정이 몰림이진 PASS/FAIL 만 사용 — Likert 스케일 금지. 서브체크 단위로 분해
구체성 편향 (Concreteness)구체적 코드에 추상적 코드보다 호의적계약 조건 충족만 판단, 구현 스타일 무시
구현 추종 편향 (Implementation-following)실제 구현을 "정답" 으로 간주계약 조건(specification)을 먼저 읽고, 코드는 증거 수집용으로만 사용
지시 해석 불일치평가 기준을 일관되지 않게 해석조건별 boolean 체크리스트 분해로 해석 여지 최소화
구현 추종 편향 경고

LLM 은 코드를 읽을 때 구현된 로직을 "의도된 행동" 으로 추종하는 경향이 있다. qa-evaluator 는 반드시 계약 조건을 먼저 읽고 "기대 행동" 을 확립한 뒤 코드를 검증해야 한다. 코드를 먼저 읽으면 구현이 곧 정답이라는 착각에 빠진다.

계약 파싱 범위 — 조건 섹션 / 서술 섹션

계약 v4 부터 계약 파일의 ## 헤더는 조건 섹션(parsed) 과 서술 섹션(non-parsed) 2 계층으로 나뉜다. 평가자가 서술 불릿을 조건으로 오파싱하면 계약에 없는 요구를 스스로 만들어내고, 반대로 조건 섹션을 놓치면 커버리지 구멍이 생긴다.

파싱 규칙 4 항
  • 1조건은 조건 섹션에서만 읽는다. 조건 섹션 헤더는 project.yaml.contract_categories 의 각 id + Anti-patterns + Reusability + Diagnostics 이며 정확히 일치해야 한다
  • 2서술 섹션은 컨텍스트로만 읽는다. 배경·리서치 소스·GAP 분석·범위 경계·회귀 게이트 는 접두 일치로 식별하며 여기의 불릿은 조건이 아니다
  • 3조건 수를 frontmatter 와 대조한다. 파싱한 - [ ] {PREFIX}-{NN} 개수가 conditions: 값과 다르면 평가를 시작하지 말고 BLOCKED 로 보고한다 — 조건을 놓친 채 내린 verdict 는 무효다
  • 4허용 목록 밖 헤더 발견 시 그 섹션의 조건은 평가하되, Sprint Feedback 에 "계약 헤더 규약 위반" 을 계약 결함으로 기록한다. 평가자가 헤더를 임의로 재분류하지 않는다
결정론적 확인 (E3) — 평가 시작 전 1 회
# (1) 헤더 2 계층 확인 — 허용 목록 밖 헤더가 있으면 계약 결함 grep -n '^## ' "$CONTRACT" # (2) 조건 섹션 밖 체크박스 — 출력이 있으면 서술 섹션에 조건이 섞인 것 awk '/^## /{s=$0} /^- \[ \]/{print FNR": "s}' "$CONTRACT" # (3) 조건 수 대조 — 두 값이 달라야 할 이유는 없다 grep -cE '^- \[[ x]\] [A-Z]{2,}-[0-9]{2}' "$CONTRACT" grep -E '^conditions:' "$CONTRACT"

$CONTRACT 는 {CONTRACT_ROOT}/.harness/sprint-contract.md 이며, CONTRACT_ROOT 는 .harness/project.yaml 을 발견한 디렉토리의 절대경로다. 세션 중 cwd 가 바뀌어도 이 값을 기준으로 해석한다.

Pre-Check & Audit
Binary Decidability Pre-Check · Rule-by-Rule Audit

Sprint Contract 의 각 조건에 대해 조건별 정적 검증을 시작하기 전에 체크리스트를 전수 실행한다. 모호 조건은 [미검증] 또는 REJECT 사유로 명시하고, 평가자가 해석 여지를 임의로 메우지 않는다 (contract_misinterpret: 7회 진단).

사전 체크리스트 6 항
  • 1FAIL 상태 1 문장 테스트 — 기술 불가면 조건 모호. "로그인이 잘 동작한다" → 불가 → 모호. "로그인 실패 시 HTTP 401 반환" → FAIL: "401 이 아닌 응답" 명확
  • 2구체성 태그 확인 — 미명시면 [structural] 로 간주하되 REJECT 사유에 "태그 누락" 플래그
  • 3범위어 enumerate 확인 — "주요 / 모든 / 대부분 / 핵심 / 일부" 가 있으면 포함·제외 목록이 인라인 enumerate 되어 있는지 확인. 없으면 자체 해석하지 말고 "범위 미명시" 명시
  • 4검증 수단 존재 확인 — "측정: ...", 도구명, 관찰 대상 중 하나가 명시되었는가?
  • 5enumerated 대상 목록 확인 — 나열된 대상 N 개가 계약에 실제로 쓰여 있는지 확인
  • 6상태 의존 측정 명령의 전제 확인 — git diff/git status/빌드 산출물처럼 실행 시점 상태에 따라 결과가 달라지면 평가자가 상태를 임의로 고르지 마라. "상태 전제 미명시" 플래그 + 실제 사용한 상태를 근거란에 기록 (측정 상태: HEAD 대비 working tree)

위 6 항 중 하나라도 미충족이면 해당 조건은 FAIL 쪽으로 기운 엄격 해석 + Sprint Feedback 의 contract_ambiguity_notes 에 "조건 ID — 모호 유형 — 제안 구체화" 를 기록한다.

Rule-by-Rule Audit Before Completion

평가자가 조건 일부만 검증하고 "나머지는 비슷하니까 PASS" 로 뭉뚱그리는 패턴을 구조적으로 차단한다. 판정 직전에 모든 계약 조건을 1 회 더 전수 스캔한다.

  • 1모든 조건 ID 를 번호순으로 나열
  • 2각 조건에 대해 — 증거(파일:라인)가 기록되어 있는가? 검증 깊이(L1/L2/L3)가 명시되어 있는가? 구체성 태그에 맞는 검증 방식을 적용했는가? enumerated 조건이면 N 개 대상 전부 개별 증거를 수집했는가?
  • 3하나라도 결여되어 있으면 재검증. "비슷한 조건이 PASS 했으니 이것도 PASS" 는 금지

분기 C — [미검증]

증거 무효 (vacuous)

검증은 실행됐으나 그 출력이 아무것도 입증하지 못함. 빈 스냅샷 · 0 매치 grep 을 "위반 없음" 으로 해석 · 0 개 테스트가 실행된 테스트 통과.

  • !A 를 B 로 적지 마라. "구현이 안 돼서 확인할 게 없다" 는 미검증이 아니라 FAIL 이다. 이것이 v4 에서 마커 의미를 축소한 이유다
  • ·B 와 C 만 [미검증] 카운터에 합산된다. A 는 FAIL 이므로 1 건으로도 즉시 REJECT

마커 부착 절차 (3 단계 fallback)

① 단계 1(기본 검증) — 계약에 기술된 1차 검증 도구 실행
② 실패 시 단계 2(Fallback 정적 검증) — 계약에 명시된 대체 정적 검증 (파일 Grep, CSS 변수 대조, log tail)

Execution-Grounded Evidence — 실행 주장 조건의 산출물 검증

구현자가 도구·스킬·명령을 실제로 실행하지 않고 "실행했다 / 호출했다 / 생성했다" 고 서술만 하는 패턴. 조건이 "실행 / 호출 / 생성 / 재생성 / 발행 / 빌드 / 마이그레이션 적용" 처럼 동작이 실제로 수행되었음을 요구하면(단순 파일 존재·내용이 아니라 행위) 아래 절차를 적용한다.

검증 절차 — narrated 주장 대신 observable artifact
  • 1실행 산출물 식별 — 그 동작이 일어났다면 남았어야 할 흔적을 먼저 정한다: 명령 출력(exit code·stdout), 생성/수정된 파일·번들, 로그 라인, codegen 결과물, git diff, lockfile 변경
  • 2산출물 직접 수집 — evaluator 가 직접 Bash/Glob/Grep 으로 수집한다. 구현자의 "실행했다" 서술이나 대화 로그는 증거가 아니다
  • 3부재 시 [미검증] — "코드상 호출 경로가 있으니 실행됐을 것" 이라는 추론 PASS 금지. 호출 경로 존재는 L2 이며, 실제 실행 증거는 별개 축이다
  • 4재현 가능하면 직접 실행 — commands.analyze, 버전 출력 등은 직접 돌려 출력으로 판정한다
실행 판정 기준 & 연구 근거

· 실행 산출물 확보 → PASS (근거에 명령/산출물 → 관찰값 형식)
· 산출물 부재 + 재현 불가 → [미검증] (PASS 아님)
· 구현자가 "실행했다" 서술했으나 산출물 없음 → narrated claim 으로 분류, 증거 불인정

판정자는 narrated reasoning 이 아니라 observable evidence 에 대해 reasoning claim 을 검증해야 한다. CoT/서술을 신뢰하면 fabricated progress signal 에 속아 false positive 가 최대 90% 증가한다.

0 매치 판정 규칙 — "없음" 은 두 가지다

의도된 0 — 조건이 "위반 0 건" 을 요구하고, 그 grep 이 다른 파일에서는 매치를 낸다는 것을 확인한 경우에만 PASS. 즉 패턴이 살아 있다는 증거(positive control)를 같이 수집한다.
공허한 0 — 대상 경로가 틀렸거나, 파일이 비었거나, 패턴이 절대 매치되지 않는 경우. 이것은 PASS 증거가 아니라 측정 실패다 → [미검증].

Bad
grep -c 'unwrap()' src/ → 0 → "안티패턴 없음, PASS"

src/ 에 .rs 파일이 0 개였다면 이 0 은 아무것도 입증하지 않는다.

Good
(a) 대상 파일 목록을 먼저 센다 (예: 42 개) (b) 패턴이 유효함을 알려진 위치에서 1 회 확인 (c) 그 위에서 0 매치 → PASS 근거: "대상 42 파일 · 패턴 유효성 확인 · 매치 0"

정본 5 조항
  1. 마커는 [미검증] 하나로 통일한다. 동의어(미확인, N/A, TBD, unverified)를 만들지 않는다. [정적] 은 "런타임 없이 정적으로만 확인" 을 뜻하는 보조 태그이며 [미검증] 을 대체하지 않는다.
  2. [미검증] 은 검증 도구·환경 부재 전용이다. 대상이 없거나 미구현이면 그것은 미검증이 아니라 FAIL 이다. 증거는 있으나 공허하면(빈 출력·0 활성화) 그것도 [미검증] 이다 (3 분기: FAIL / 도구 부재 / 증거 무효).
  3. 임계값은 2 다. [미검증] 0 건은 통상 판정, 1 건은 PASS 허용 + 경고 명시, 2 건 이상은 개별 FAIL 이 없어도 verdict 는 REJECT. "CONDITIONAL APPROVE" 를 쓰는 킷은 그것이 "1 건 + FAIL 0" 인 경우에만 유효하며, 2 건 이상에는 쓸 수 없다.
  4. 생성자의 완료 주장은 증거가 아니다. 구현자가 "동작 확인함 / 실행했음" 이라고 쓴 문장, 코드 주석, 커밋 메시지의 자기 평가는 상태 검증이 아니다. 명시적 완료 주장을 포함한 자기평가 에이전트 궤적에서 실패의 75.8% 가 false success 였고, LLM 판정자의 AUROC 는 0.54~0.65 에 그쳤다. 근거는 도구 출력과 상태 변화여야 한다.
  5. 조용한 PASS 금지 + 집계 의무. 검증을 건너뛰고 정적 정황만으로 PASS 를 주지 않는다. 리포트에 미검증 N 건 을 반드시 집계하고, 건별로 [조건/항목 ID, 사유, 시도한 fallback 단계] 를 남긴다.

Methodology
3-Level 검증 · L3 Coverage Honesty · Sibling Enumerated

모든 조건은 L3 까지 도달해야 한다. L1/L2 에서 PASS 해도 L3 에서 FAIL 이면 전체 FAIL. 3계층 모델은 industry code review 의 lint → semantic → AI 모델과 대응한다.

Level검증 방법도구목적
L1: 구조파일/디렉토리 존재 확인Glob, ls산출물이 있는가?
L2: 내용파일 내용에 기대 요소 존재Read, Grep코드가 작성되었는가?
L3: 의미코드 경로 추적, 행동 검증Read + 논리 추적코드가 의도대로 동작하는가?
L3 도달 절차 — 단순 Grep 은 L2 에서 멈추는 함정
# ❌ L2에서 멈춤 Grep 으로 'design-tokens.md' 언급 확인 → PASS # ✅ L3 도달 Read 로 design-tokens.md 전체 내용 확인 → 토큰 구조가 조건이 요구하는 카테고리 (color/spacing/typography)를 모두 포함하는지 의미 매칭

Markdown 전수 검사 조건(CD-02, DG-02 계열): ① Glob 으로 대상 파일 목록 수집 ② 각 파일을 Read 또는 Grep 으로 위반 패턴 카운트 ③ FAIL 파일명:라인 모두 나열(샘플만 기재 금지) ④ "N 개 파일 중 M 개 위반" 형태로 전체 카운트 보고.

  • ·L3 전수 검증이 불가능하면 샘플링 대상과 미검증 대상을 명시적으로 분리 보고

Sibling Enumerated Verification (전수 Grep 절차)

[*, enumerated] 태그 발견 시: ① 대상 목록 파싱 — 조건 문장에서 나열된 sibling 스킬/파일 이름을 모두 추출하고 N 개를 정확히 센다 ② N 개 전수 Grep — 한 대상당 한 줄 증거(파일:라인 매칭 문자열) 기록 ③ 누락 대상명 나열 — 하나라도 증거가 없으면 FAIL, 누락 대상명을 모두 나열(샘플 한두 개만 기재 금지) ④ 카운트 보고 — "N 개 중 M 개 충족 (누락: X, Y, Z)".

혼동 방지 규칙

· 계약서의 [L1] 태그를 보고 "존재 확인(Glob)만 하면 된다" 고 해석하지 않는다. 계약의 [L1] 은 exact 이름 매칭 요구이지 evaluator 검증 깊이 L1 과 무관하다.
· evaluator 검증 깊이 L1~L3 는 계약 조건의 구체성 레벨과 무관하게 항상 L3 까지 도달해야 한다.
· contract-schema v2 부터 계약 조건은 문자 태그를 사용한다. legacy 매핑: [L1] ≡ [exact], [L2] ≡ [structural], [L3] ≡ [goal].

[structural]섹션/필드/파일 존재 확인Glob/Grep 으로 존재 확인 → Read 로 구조 검증 (필드 타입, 하위 항목 수)파일:라인 + 섹션 헤더 또는 필드명
[goal]목표 달성 여부만 판정, 수단 무관Read 로 코드 경로 전체 추적 → 의미 분석 + 다관점 평가 필수 (기능/엣지/성능/보안 중 최소 2 개)파일:라인 + 목표 달성 논증
[enumerated]각 대상을 개별 이름으로 명시 요구대상 목록 파싱 → 각 대상별 개별 Grep/Read → 개별 증거 수집모든 대상에 증거 확보 시 PASS. 하나라도 누락 시 FAIL + 누락 대상명 나열
[collective]포괄 경로/패턴 하나로 지정 가능 (기본값)포괄 경로·패턴 1 건을 Grep/Glob 으로 확인포괄 매칭 1 건 증거로 PASS
Rubric 기반 분해 (CheckEval) + Recursive Rubric Decomposition

각 계약 조건을 boolean 서브체크로 분해한다. CheckEval 은 Likert 스케일 대신 boolean 분해로 평가자 간 일치도를 0.45 향상시켰다 (EMNLP 2025). 3단계 프로토콜: ① Aspect Selection — 검증할 핵심 측면 식별 ② Checklist Generation — Yes/No 로 답할 수 있는 boolean 질문으로 변환(질문당 하나의 검증 포인트) ③ Boolean Evaluation — 각 질문에 L1/L2/L3 레벨로 답한다. PASS 비율이 아닌 전체 PASS 가 조건 충족 기준이다.

조건: "대시보드에서 실시간 알림을 표시한다" ├── Aspect A: 알림 데이터 수신 │ ├── A-1: WebSocket/SSE 연결 코드가 존재하는가? (L1) │ ├── A-2: 서버 메시지를 파싱하는 로직이 있는가? (L2) │ └── A-3: 파싱된 데이터가 UI 상태로 전달되는 경로가 있는가? (L3) └── Aspect B: UI 표시 ├── B-1: 알림을 렌더링하는 컴포넌트가 존재하는가? (L1) ├── B-2: 알림 데이터가 해당 컴포넌트에 바인딩되어 있는가? (L2) └── B-3: 새 알림 수신 시 UI 가 자동 갱신되는가? (L3)

RRD: 고수준 루브릭 항목이 여전히 모호하면 한 번 더 서브포인트로 재귀 분해한다. 한 번 분해했는데도 서브체크 1 개가 10+ 라인을 Read 해야 판정 가능하면 재귀 분해 신호다. CoT 효용 한계: 루브릭이 잘 정의되어 있으면 CoT 가 판정 신뢰도에 주는 이득은 미미하다 — 장황한 reasoning 대신 증거(파일:라인) + 서브체크 boolean 결과에 집중하라.

Specialized Protocols
수량 검증 · 키워드 배타성 · 안티패턴 스택 정합성 · 다관점 평가

수량이나 경계값이 포함된 조건(">= N줄", "<= M개", "정확히 K건")은 측정 → 즉시 출력 → 비교 판정 3단계를 반드시 수행한다. "대략 맞는 것 같다" 는 L2 에서 멈추는 함정이다.

수량/경계값 조건 검증

① 측정 — 줄 수는 wc -l, 항목 수는 Grep 카운트, 파일 수는 Glob 결과 카운트
② 즉시 출력 — 측정값을 근거에 명시 (측정값: 1498줄 (기준: >= 1500))
③ 비교 판정 — 경계값 미달은 무조건 FAIL

카운팅 패턴 주의: Markdown 헤더는 ## 뿐 아니라 ###·#### 도 고려, 번호 매기기는 1. 과 - 불릿 모두 고려, Gotchas 항목은 H3 또는 불릿 형태를 모두 매칭하는 범용 정규식 사용.

실제 사례 — AR-03 REJECT (2026-04-12)

docs/flutter/ 총 줄 수가 1498줄로 기준 1500줄에 2줄 부족. 경계값 미달을 "거의 충족" 으로 PASS 처리하지 않고 FAIL 로 정확히 판정한 사례.

스킬 트리거 키워드 배타성 (Set Intersection)

① 대상 SKILL.md 의 description frontmatter 에서 키워드 추출 ② 같은 플러그인 내 모든 SKILL.md 를 Glob 으로 수집 ③ Set Intersection 비교 ④ 부분 문자열 포함 관계도 배타성 위반으로 판정.

위반
스킬 A: "API 연동" 스킬 B: "API 연동 화면" → 부분 문자열 → 배타성 위반 FAIL
비위반
스킬 A: "컴포넌트 추출" 스킬 B: "화면 추출" → 부분 문자열 관계 없음 → PASS

완전 일치 키워드는 FAIL, 부분 포함 관계도 FAIL, 비슷한 의미의 다른 단어는 문맥 분석 후 판정(불확실하면 [medium-confidence]).

안티패턴 스택 정합성 (Stack Applicability)

digest stack-inappropriate-rust-antipatterns — 셸/compose 작업 계약에 Rust 전용 조건(unwrap(), println!)이 그대로 들어갔고 평가자가 그대로 판정했다. 계약 생성 측 결함이지만 평가자도 걸러낼 수 있다.

  • ·불일치하면 그 패턴은 N/A (스택 불일치: 패턴=Rust · 대상=shell/yaml) 로 기록한다. 매치 0 건을 PASS 로 적지 마라 — 애초에 매치될 수 없는 패턴의 0 은 공허한 0 이다
  • ·동시에 Sprint Feedback 에 "계약 결함: 대상 스택에 부적합한 안티패턴 조건" 을 기록한다. 조건 삭제·교체는 사용자 권한이므로 평가자는 권장만 한다
  • ·대상 파일이 여러 스택에 걸쳐 있으면 스택별로 나누어 판정하고 각각의 대상 파일 수를 기록한다
다관점 평가 (Perspective-Based Reading)

각 조건을 최소 2개 관점에서 평가한다. 구현자 시점만으로 평가하면 사용자 가치나 비즈니스 의도가 누락된다 (perspective_gap: 5회 diagnosis).

관점초점예시 질문
기능명시된 행동이 구현되었는가?"버튼 클릭 시 API 호출되는가?"
엣지 케이스경계 조건에서 올바른가?"빈 입력, null, 최대 길이에서?"
성능비효율이나 병목이 있는가?"N+1 쿼리, 불필요한 리렌더링?"
보안취약점이 있는가?"SQL 인젝션, XSS 가능성?"
User-Value사용자가 이 동작으로 무엇을 얻는가?"에러 메시지가 사용자에게 실제로 도움이 되는가?"
Business-Intent계약의 상위 의도에 부합하는가?"규제 준수·데이터 일관성·SLA 달성 측면에서 의도를 실현하는가?"

구현자 관점만으로 평가 금지. "코드가 동작한다" 만 확인하고 끝내지 마라. 조건이 사용자/비즈니스 의도를 어떻게 실현하는지 한 문장으로 서술 가능해야 한다.

Verdict & Confidence
Evidence-Based 판정 · 판정 신뢰도 · Specification-First

모든 PASS/FAIL 에는 증거가 필요하다 — PASS 증거는 {파일}:{라인} 과 그 코드가 조건을 충족하는 이유, FAIL 증거는 충족하지 않는 이유 또는 코드 부재. "확인했다", "문제 없다" 같은 self-assertion 은 증거가 아니다.

조건별 판정 확신도
확신도기준태그
높음L3 검증 완료 + 명확한 증거(파일:라인)—
중간L2 까지 검증 + 정황 증거[medium-confidence]
낮음L1 만 검증 또는 정적 분석 한계[low-confidence]
  • ·낮은 확신도 PASS 는 [미검증] 과 동일 취급한다
  • ·낮은 확신도 조건이 3개 이상이면 "⚠️ 낮은 확신도 조건 다수" 경고를 명시
  • ·확신도는 판정을 뒤집지 않는다 — FAIL 은 확신도와 무관하게 FAIL
  • ·Swap Test 불안정 강등 규칙: (A, B) 와 (B, A) 결과가 다르면 자동 [low-confidence]. 2 회 재검증해도 불일치면 [미검증] + position bias 의심 명시
A Statistical Approach to Model Evaluations — Anthropic
검증 순서 원칙 (Specification-First) · Metamorphic Testing

① 먼저 Sprint Contract 를 읽고 각 조건의 "기대 행동" 을 확립한다 ② 그 다음 코드를 검증한다 — 코드는 증거 수집 대상이지 기대 행동의 출처가 아니다 ③ 코드를 먼저 읽으면 구현 추종 편향에 빠진다.

Metamorphic Testing: 절대 정답을 모를 때 관계 기반으로 검증한다 — "입력을 2배로 하면 출력도 2배인가?"(비례), "같은 입력을 2번 넣으면 같은 결과인가?"(멱등성), "A를 추가해도 B에 영향 없는가?"(독립성). 계약 조건으로 직접 판정 가능한 경우 metamorphic testing 은 불필요하다.
