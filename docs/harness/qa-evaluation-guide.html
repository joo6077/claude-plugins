QA Evaluation Guide

qa-evaluator 에이전트가 참조하는 평가 방법론. Phase 3 카이젠(v3)에서 Binary Decidability Pre-Check, Rule-by-Rule Audit, [미검증] 마커 프로토콜, Sibling Enumerated Verification, L3 Coverage Honesty 규칙, User-Value/Business-Intent 관점을 흡수했다.

Core Principles
핵심 원칙 — Test Oracle · IV&V 독립성 · 편향 완화

qa-evaluator는 "정답을 아는 존재"(test oracle)로서 계약 조건 대비 구현을 판정한다. 계약이 oracle specification이며, evaluator는 이를 기계적으로 적용한다.

Test Oracle 역할

계약에 없는 기준으로 판단하지 않는다. 조건의 "의도"가 아닌 "문자 그대로"를 적용한다. "아마 이런 뜻일 것이다"는 해석 금지.

IV&V 독립성

evaluator는 generator의 의도나 과정을 알지 않는다. 계약과 산출물만으로 판정한다. "커밋 메시지에 완료라고 썼다" ≠ 증거.

Specification-First

먼저 Sprint Contract를 읽고 "기대 행동"을 확립한다. 그 다음 코드를 검증한다. 코드를 먼저 읽으면 구현 추종 편향에 빠진다.

Binary Decidability
평가 시작 전 필수 — Binary Decidability Pre-Check

Sprint Contract의 각 조건에 대해 Step 2(조건별 검증)를 시작하기 전에 아래 체크리스트를 전수 실행한다. 모호 조건은 [미검증] 또는 REJECT 사유로 명시하고, 평가자가 해석 여지를 임의로 메우지 않는다.

사전 체크리스트 (5항목)
  • 1FAIL 상태 1문장 테스트 — "이 조건이 FAIL인 상태를 1문장으로 기술 가능한가?" 불가능하면 조건 모호
  • 2구체성 태그 확인 — [exact]/[structural]/[goal] 태그 존재 여부. 미명시면 [structural]로 간주하되 REJECT 사유에 "태그 누락" 플래그
  • 3범위어 enumerate 확인 — "주요/모든/대부분/핵심" 같은 범위어가 있으면 포함/제외 목록이 인라인 enumerate되었는지 확인. 없으면 REJECT 사유에 "범위 미명시"
  • 4검증 수단 존재 확인 — "측정: ...", 도구명, 관찰 대상 중 하나가 명시되었는가? 없으면 기본 fallback 적용 + REJECT 사유에 "검증 수단 미명시"
  • 5enumerated 대상 목록 확인 — 태그가 enumerated이면 나열된 대상 N개가 계약에 실제로 쓰여 있는지 확인. N이 애매하면 REJECT 사유에 "enumerated 대상 수 불분명"
실패 사례 — PH-01

평가자가 모호 조건을 자체 해석 → 해석 충돌 → REJECT 반복. 사전 체크리스트 없이 평가를 시작한 결과.

실패 사례 — SK-02

"주요 interactive element" 범위어가 enumerate되지 않아 badge/decoration 포함 여부를 평가자가 자체 판단 → REJECT.

Rule-by-Rule Audit
판정 완료 전 필수 — Rule-by-Rule Audit Before Completion

Step 4(판정) 직전에 모든 계약 조건을 1회 더 전수 스캔한다. "자명하다"고 넘긴 조건이라도 판정 직전 체크리스트 형식으로 되돌아온다.

전수 점검 절차
  • 1Sprint Contract의 모든 조건 ID를 번호순으로 나열한다
  • 2각 조건 ID에 대해: 증거(파일:라인)가 기록되어 있는가? 검증 깊이(L1/L2/L3)가 명시되어 있는가?
  • 3구체성 태그에 맞는 검증 방식을 적용했는가? enumerated 조건이면 N개 대상 전부 개별 증거를 수집했는가?
  • 4하나라도 결여되어 있으면 해당 조건을 재검증한다. "비슷한 조건이 PASS했으니 이것도 PASS"는 금지
[미검증] 마커
[미검증] 마커 평가 프로토콜 — 카운팅 + 자동 REJECT 임계

MCP null, 런타임 미실행, 외부 도구 미가용 등으로 정적 검증이 불가능한 조건의 일관된 처리. fit-pal LG-02/DG-04 REJECT의 근본 원인이었다.

마커 부착 절차 (3단계)
  • 1단계 1(기본 검증) 시도 — 계약에 기술된 1차 검증 도구 실행
  • 2단계 1 실패 시 단계 2(Fallback 정적 검증) 시도 — 파일 Grep, CSS 변수 대조, log tail 등
  • 3단계 2도 실패 시 단계 3([미검증] 마커) 부착 — 근거 블록에 "검증 불가 사유 한 줄 + 사용한 단계 기록"
미검증 건수평가 결과
0건통상 판정
1건PASS 허용 (단, Sprint Feedback에 "미검증 1건" 경고 명시)
2건 이상자동 REJECT — 개별 조건 FAIL 없어도 전체 verdict REJECT
집계 의무 — Sprint Feedback 기록 형식
## Unverifiable Summary - 총 미검증 건수: N - 건 목록: [조건 ID, 사유, 시도한 fallback 단계] - Verdict 영향: {PASS 허용 | 자동 REJECT}
Verification Methodology
3-Level 검증 — L1 구조 · L2 내용 · L3 의미 (L3 필수)

모든 조건은 L3까지 도달해야 한다. L1/L2에서 PASS해도 L3에서 FAIL이면 전체 FAIL. 단순 Grep 매칭은 L2에서 멈추는 함정이다.

L1
구조 확인
파일/디렉토리 존재 확인. 도구: Glob, ls. "산출물이 있는가?"
L2
내용 확인
파일 내용에 기대 요소 존재. 도구: Read, Grep. "코드가 작성되었는가?"
L3
의미 검증
코드 경로 추적, 행동 검증. 도구: Read + 논리 추적. "의도대로 동작하는가?"
L2에서 멈춤 (Bad)
Grep으로 'design-tokens.md' 언급 확인 → PASS

파일 존재만 확인. 내용이 요구 조건을 충족하는지 미검증.

L3 도달 (Good)
Read로 design-tokens.md 전체 내용 확인 → 토큰 구조가 color/spacing/typography 카테고리를 모두 포함하는지 의미 매칭
L3 Coverage Honesty — 샘플링 시 미검증 명시 의무

시간 제약으로 L3 전수 검증이 불가능하면 샘플링 대상과 미검증 대상을 분리하여 보고한다. "20개 중 2개만 확인 + 나머지는 비슷하니까 PASS"는 금지.

- [x] AR-01: ... — PASS [L3, 샘플링-3/전체-20] - 근거: rust-api (파일:라인), rust-service (파일:라인) - [미검증-17] rust-init/-feature/-model 등 17개: 시간 제약으로 L3 미도달
Sibling Verification
Sibling Enumerated Verification — 전수 Grep 절차

플러그인 내 여러 스킬에 공통 원칙을 요구하는 조건([*, enumerated])에서 1~2개 샘플만 확인하고 PASS 처리하는 패턴 방지. rust-kit H-01/H-03 REJECT의 직접 원인.

절차 (4단계)
  • 1대상 목록 파싱 — 조건 문장에서 나열된 sibling 스킬/파일 이름을 모두 추출. N개 정확히 센다
  • 2N개 전수 Grep — 각 대상에 대해 개별 Grep 수행. 한 대상당 한 줄 증거(파일:라인 매칭 문자열) 기록
  • 3누락 대상명 나열 — 하나라도 Grep 증거가 없으면 해당 조건은 FAIL. 누락된 대상명을 모두 나열
  • 4카운트 보고 — Sprint Feedback에 "N개 중 M개 충족 (누락: X, Y, Z)" 형태로 집계
실패 — rust-kit H-01/H-03

"domain event + outbox 원칙이 rust-init, rust-feature, rust-service, rust-api 4개 스킬 Gotchas에 있다" 조건에서 rust-service만 확인하고 PASS. 실제로 3개 누락 → REJECT.

실패 — react-kit KZ-04

References에 7개 그룹 문서(g1~g6, g5b) 개별 명시 요구였는데 포괄 경로로 처리 → REJECT. enumerated 태그를 collective로 처리한 사례.

Tag Consumption
Specificity Tag 소비 규칙 + 용어 충돌 주의

이 가이드의 L1/L2/L3는 evaluator 검증 깊이를 의미한다. sprint-contract 계약서의 [L1]/[L2]/[L3] 태그는 조건 구체성 레벨로 동일 기호지만 의미가 다르다.

태그evaluator 검증 방식증거 형식
[exact] Grep으로 literal 매칭 → Read로 맥락 확인 파일:라인 + 매칭된 literal 문자열 인용
[structural] Glob/Grep으로 섹션·필드 존재 확인 → Read로 구조 검증 파일:라인 + 섹션 헤더 또는 필드명
[goal] Read로 코드 경로 전체 추적 → 의미 분석 + 다관점 평가 (최소 2개) 파일:라인 + 목표 달성 논증
다관점 평가 (Perspective-Based Reading)
관점초점예시 질문
기능명시된 행동이 구현되었는가?"버튼 클릭 시 API 호출되는가?"
엣지 케이스경계 조건에서 올바른가?"빈 입력, null, 최대 길이에서?"
성능비효율이나 병목이 있는가?"N+1 쿼리, 불필요한 리렌더링?"
보안취약점이 있는가?"SQL 인젝션, XSS 가능성?"
User-Value사용자가 이 동작으로 무엇을 얻는가?"에러 메시지가 실제로 도움이 되는가?"
Business-Intent계약의 상위 의도에 부합하는가?"규제 준수·데이터 일관성·SLA 달성?"

구현자 관점만으로 평가 금지. [goal] 조건에서 다관점 평가는 필수.
