Core Principles
핵심 원칙 — 검증 가능성 · 단일 해석 · 측정 가능성

모든 조건은 제3자가 코드만 보고 PASS/FAIL 을 판정할 수 있어야 한다. 이는 INVEST 원칙의 Testable 과 동일한 요구다 — "제3자가 objectively 확인 가능해야 하며, 측정 가능한 값과 구체 행동으로 기술한다."

검증 가능성 (Verifiability)

주관적 언어("잘 동작한다", "적절히", "충분히")는 금지.

좋은 예: "로그인 실패 시 HTTP 401을 반환한다"
나쁜 예: "로그인이 적절히 처리된다"

Agile Alliance INVEST
단일 해석 (Unambiguity)

IEEE 29148 기반 품질 기준:

· 능동태 사용 ("시스템이 반환한다" not "반환되어야 한다")
· 단일 조건 ("A이고 B이다" → 조건 2개로 분리)
· 모호 형용사 금지 ("빠르게", "적절히", "충분히" → 구체 수치)

측정 가능성 (Measurability)

조건의 충족 여부를 파일, 코드, 실행 결과로 증명할 수 있어야 한다.

LLM-as-Judge 연구 보강

평가 criteria 의 극단값(PASS/FAIL 양끝) 정의가 중간값 설명보다 judge alignment 에 더 큰 영향을 준다. 즉 "이 조건이 PASS 인 상태" 와 "FAIL 인 상태" 를 각각 한 문장으로 구체화하는 것이 중간 정도 서술을 풍부하게 하는 것보다 중요하다. 계약 작성 시 각 조건의 FAIL 이미지를 먼저 떠올리고 그 부정으로 PASS 를 기술하면 이진 판정 가능성이 올라간다.

Writing Conditions
조건 작성법 — NASA · Design by Contract · GWT/AAA

각 조건은 하나의 "shall"(또는 한국어 "~한다")만 포함하고, 부정보다 긍정 조건을 선호하며, "and/or" 사용을 금지한다.

Precondition / Postcondition / Invariant

Design by Contract (Meyer, 1992) 구조를 참고한다.

Precondition: 구현 시작 전 충족되어야 하는 조건 (환경, 의존성)
Postcondition: 구현 완료 후 반드시 참이어야 하는 조건 (핵심 기능)
Invariant: 구현 전후로 변하지 않아야 하는 조건 (기존 기능 보전)

Given-When-Then / Arrange-Act-Assert
Given {전제 조건} | Arrange {사전 세팅} When {동작} | Act {행동 1회} Then {기대 결과} | Assert {관찰 1회}

복잡도 "중간" 이상이면 모든 핵심 조건에 GWT 또는 AAA 구조 필수, "단순" 이면 선택이나 권장. Gherkin one When-Then pair 규칙: 한 조건에 When-Then 쌍은 1 개만 — 2 개 이상이면 복합 조건이므로 분리한다.

Gherkin Best Practices AAA blueprint — arxiv:2510.24358
외부 관찰 가능성 (External Observables Only)

조건은 시스템이 무엇을 하는지(외부 행동)만 기술한다. 어떻게 하는지(내부 구현)는 기술하지 않는다. 금지 요소: 클래스명·메서드명·함수명, DB 테이블·컬럼·API 엔드포인트 경로, 프레임워크 용어(controller, service, repository, provider, notifier), 내부 상태 변수·플래그.

Bad — 구현 누수
"UserService의 userRepository가 비어있을 때" "POST /api/users 호출 시 201을 반환한다"
Good — 외부 관찰
"등록된 사용자가 없을 때" "신규 사용자 등록 요청 시 성공 응답을 반환한다"

이 규칙을 위반하면 "구현 누수(implementation leakage)" 라 한다. 구현이 변경되면 조건도 깨지므로 조건의 수명이 짧아진다.

양면 조건 — Counterpart Conditions

계약·직렬화·공유 모델을 바꾸는 스프린트는 본질적으로 양면 작업이다. 서버 응답 형태를 바꾸고 클라이언트를 다음 스프린트로 미루면, 그 스프린트는 계약상 완료가 아니라 절반 완료다. 실측에서 사용자가 "당연히 그러면 클라까지 바꿔야지" 로 매번 개입해야 했고, UTC 직렬화 버그도 같은 계열이다.

설계 결정 — 이 원칙의 유일한 강제 지점은 계약 작성자다

Counterpart Enumeration 은 qa-evaluation-guide 에 대응 절을 두지 않는다. 평가자는 계약에 박힌 조건으로 이 원칙을 수용한다 (parity item 12). 따라서 이 원칙이 실제로 작동하려면 계약 작성자가 조건을 넣어야만 한다 — 안 넣으면 아무도 안 잡는다. 계약 테스트의 표준 관점도 동일하다: consumer 측 검증만 하면 provider 가 예고 없이 바뀌고, provider 측만 검증하면 consumer 가 잘못된 요청을 보낸다.

New in v4.0
계약 서두–조건 정합성 (Preamble–Condition Consistency)

계약에 배경·설계 의도 서술(preamble)이 있으면, 그것은 장식이 아니라 구현자가 읽는 지시다. 서술과 조건이 어긋나면 에이전트는 물어보지 않고 조용히 한쪽을 골라 구현한다 — "agents resolve the conflict silently by picking one instruction over the other".

실제 발생 사례 — RE-02 (fit-pal, 2026-07-22)

계약 preamble 은 단방향 차단 조회를 설계 의도로 서술했는데, 조건 RE-02 는 양방향 함수 batch_blocked_among 의 재사용을 literal 로 열거했다. 구현자는 preamble 을 따라 단방향 batch_blocking_out 을 새로 만들었고, 평가자는 조건의 literal enumeration 미충족으로 REJECT. 어느 쪽도 틀리지 않았고 계약이 자기모순이었다.

작성자 점검 (DRAFT 제시 전, E2)
  • ✓서술 절에 쓴 설계 의도와 각 조건이 같은 방향을 가리키는가? 어긋나면 조건을 고칠지 서술을 고칠지 먼저 정하고 사용자에게 알린다
  • ✓조건이 기존 식별자(함수·클래스·파일명)를 literal 로 열거한다면, 그 식별자가 지금 코드에 실제 존재하는지 grep 으로 확인했는가? 존재하지 않는 이름을 열거하면 자동 REJECT 다
  • ✓열거한 식별자의 의미(단방향/양방향, 동기/비동기, 단수/복수)가 설계 의도와 일치하는가?
  • ✓재사용을 요구하는 조건이라면 "이 이름이어야만 하는가"([exact])인지 "같은 목적을 달성하면 되는가"([goal])인지 태그로 구분했는가?

계약 작성 시 각 조건이 어느 수준으로 판정될지를 명시한다. 수준이 불명확하면 QA Evaluator 가 해석을 달리하여 판정이 엇갈린다.

네이밍 규칙 — 숫자 레벨 금지

숫자 레벨(L-one, L-two, L-three)은 QA 평가 깊이 전용으로 예약되어 있다. 계약의 조건 태그는 반드시 문자 태그([exact], [structural], [goal])만 사용하고, 숫자 레벨을 계약 조건에 재사용하지 마라. 혼용하면 QA 깊이와 조건 구체성이 구분되지 않아 판정이 엇갈린다.

태그정의판정 기준적합한 상황
[exact]특정 이름/값/구조를 문자 그대로 매칭해당 식별자가 코드에 존재하는지 직접 검색함수명 계약, 파일명 계약, 특정 클래스 구조
[structural]섹션/필드/파일의 존재 여부 및 필수 서브구조지정된 섹션·필드가 존재하는지 확인"X 섹션을 포함한다", "Y 필드가 있다"
[goal]수단 무관, 목표 달성 여부만 판정기능이 의도한 결과를 산출하는지 확인"SSOT 달성", "회귀 없음", "파싱 성공"
태그 선택 기준

[exact]: 이름·값·구조가 그것이어야만 의미가 있을 때. "이름이 달라지면 계약 실패" 가 성립하면 [exact].
[structural]: "해당 구조가 존재한다" 만 검증하고 싶을 때.
[goal]: 구현 방법은 자유이고 결과만 보고 싶을 때.

경험칙: 판정 시 "구현이 X 라서 REJECT 할 것인가?" 라고 자문했을 때 REJECT 가 부당하다고 느끼면 태그가 [exact] 일 가능성이 높다 — [goal] 로 완화하라. 태그 미명시 시 기본값은 [structural].

enumerated각 대상을 하나씩 이름으로 명시해야 PASS모든 개별 이름이 문서에 직접 등장하는지 확인

Verification Method
검증 수단 명시 의무 + 측정 oracle 타당성

Scope & Boundary
경계값 · 스코프 세분화 · 범위 인라인 · Sibling Consistency

수량·길이·크기 등 임계값을 포함하는 조건은 측정 방법을 함께 명시한다. 측정 방법이 없으면 QA Evaluator 가 다른 도구·기준으로 측정하여 판정이 엇갈린다.

경계값 조건 — 3 요소 필수

① 임계값: 구체적 숫자 (>= 1500, == 0, <= 3)
② 측정 대상: 무엇을 세는가 (줄 수, 파일 수, 바이트 수, 항목 수)
③ 측정 방법: 어떻게 세는가 (명령어, 도구, 계산식)

Good: - [ ] AR-03: docs/flutter/ 하위 .md 파일의 총 줄 수가 1500 이상이다 (측정: `wc -l docs/flutter/*.md | tail -1`) [exact] Bad: - [ ] AR-03: docs/flutter/ 문서가 1500줄 이상이다 [exact] ← 측정 방법 미명시: wc -l vs grep -c vs 에디터 줄 수?
실제 사례 — AR-03 REJECT

계약이 ">= 1500줄" 을 요구했으나 측정 방법을 명시하지 않아, 구현이 1498줄(2줄 부족)로 REJECT. 측정 명령이 사전에 합의되었다면 구현 중 즉시 확인이 가능했던 케이스.

스코프 세분화 (Scope Granularity)
수준의미예시
file-level파일 전체가 동일 포맷"모든 .md 파일이 YAML frontmatter 를 포함한다"
section-level특정 섹션 내부 구조 통일"각 섹션의 소스 테이블이 동일 컬럼 구성이다"
field-level개별 필드/컬럼까지 명시"소스 테이블에 번호, 제목, URL, 태그 4개 컬럼이 존재한다"

포맷 일관성을 요구하는 조건은 최소 section-level 까지 명시한다. "일관된 포맷" 단독 사용 금지 — 어떤 수준에서 일관적인지 반드시 부연한다.

실제 사례 — ER-02 / AR-03 REJECT

"6개 파일의 일관된 포맷" 을 요구했으나 컬럼 구성까지 명시하지 않아, 한 파일만 태그 컬럼이 누락된 채 통과하려 했고 QA 가 REJECT.

스코프 범위 인라인 명시 (Scope Range)

조건에 "주요", "모든", "대부분", "핵심" 같은 범위어가 등장하면 그 범위가 무엇을 포함하고 무엇을 제외하는지 조건 내부에 인라인 enumerate 해야 한다.

Bad — 범위 모호
- [ ] UI-02: 주요 interactive element 의 box-shadow offset 이 >= 4px 이다 [exact]

"주요 interactive element" 가 버튼·카드·입력만인지, badge 와 decoration 까지인지 불명확.

Good — 범위 인라인 명시
- [ ] UI-02: 버튼·카드·입력 요소의 box-shadow offset 이 >= 4px 이다 (badge, decoration, 장식용 icon 은 범위 외) [exact, enumerated]

범위가 5 개 이상이면 applies_to: <pattern> 로 대체한다. "주요 / 모든 / 대부분" 단독 사용 금지 — 작성자가 직접 열거 책임을 진다.

실제 사례 — SK-02 REJECT (harness, 2026-04)

형제 스킬 일관성 (Sibling Consistency)

동일 플러그인 내 여러 스킬이 공통 원칙을 요구할 때(헥사고날 패턴, 에러 처리 규칙, 코드 생성 템플릿 등), 계약은 "이 원칙이 sibling 스킬 전부에 적용되어 있다" 를 enumerated 형태로 명시해야 한다.

Bad — sibling cross-check 누락
- [ ] SK-03: rust-api 핸들러 예시가 domain event + outbox 원칙을 따른다 [structural]

rust-init, rust-feature, rust-service, rust-api 4 스킬 중 rust-api 만 점검하게 됨.

Good — sibling enumerated
- [ ] SK-03: domain event + outbox 원칙이 rust-init, rust-feature, rust-service, rust-api 4 개 스킬의 Gotchas 섹션 전부에 적용되어 있다 [exact, enumerated]

공통 원칙 조건은 반드시 [exact, enumerated] 또는 [structural, enumerated] 를 사용한다 (collective 금지 — 한 개만 통과하면 PASS 되므로). sibling 스킬 개수를 조건에 숫자로 명시하고 대상 스킬을 빠짐없이 열거한다.

예외 조항 포맷 (Exception Clause) · Property vs Example

조건이 특정 파일·상황·타입에는 적용되지 않을 경우, 조건 내부에 인라인으로 예외를 명시한다. 별도 문서로 분리하거나 구두로 합의하면 QA 시점에 예외가 반영되지 않는다.

- [ ] CD-02: 모든 docs 페이지에 compare-bad/compare-good 비교 블록이 2쌍 이상 존재한다. 예외: (a) integration.html — Final 통합 페이지로 개별 비교보다 전체 조합을 다루므로 제외, (b) index.html — 목록 페이지로 콘텐츠 조건 비적용

예외는 "왜 제외하는가" 를 한 줄로 설명한다(이유 없는 예외 금지). 예외 항목이 3개를 초과하면 조건 자체를 범위 한정(applies_to)으로 재작성한다. 예외 없이 작성된 조건은 해당 카테고리의 모든 파일에 적용된다고 간주한다.

Property 기반 vs Example 기반: Example 기반("입력 'abc'에 대해 'ABC'를 반환한다")은 구체적이지만 범위가 좁고, Property 기반("모든 입력에 대해 출력 길이가 입력 길이와 같다")은 범위가 넓다. 단순 기능은 Example, 복잡한 로직은 Property 를 혼용한다.

카테고리는 Goal 에서 도출한다 — ① Goal: 이 기능이 달성하려는 목표는 무엇인가? ② Question: 목표 달성을 어떻게 확인하는가? ③ Metric: 어떤 구체적 지표로 측정하는가? project.yaml 의 contract_categories 가 이미 정의되어 있으면 그것을 따른다.

v4.0 신설 — 규칙이 실사용과 어긋나 있었다

기존 규칙은 "허용 헤더는 카테고리 + Anti-patterns / Reusability / Diagnostics 뿐" 이었는데, 실제 계약(특히 카이젠 계약)은 배경·리서치 소스·GAP 분석·범위 경계를 상시 사용해 왔다. 규칙이 실사용과 어긋나 있었기 때문에 재위반이 반복됐다. 그래서 규칙을 강화하는 대신 헤더를 두 계층으로 분류한다.

계층허용 헤더조건 체크박스
조건 섹션 (parsed)project.yaml.contract_categories 의 각 id + Anti-patterns + Reusability + Diagnostics여기에만 - [ ] {PREFIX}-{NN}: 형태로 존재
서술 섹션 (non-parsed)배경 · 리서치 소스 · GAP 분석 · 범위 경계 · 회귀 게이트조건 체크박스 금지 (일반 불릿만)
  • ·조건 섹션 헤더는 정확히 일치해야 한다(괄호 부연 금지). 서술 섹션 헤더는 위 5 개 중 하나로 시작하면 되고 뒤에 부연을 붙일 수 있다 (## GAP 분석 (리서치 vs 현재 가이드) 허용)
  • ·위 두 목록 밖의 헤더(Notes, Appendix, 메모 등)는 금지다 — 평가자 파서가 조건 섹션인지 서술인지 판정할 수 없다
  • ·서술 섹션에 - [ ] 를 쓰면 평가자가 조건으로 오인해 존재하지 않는 조건을 판정하려 든다
  • ·이 규칙은 E3 다 — sprint-contract 는 저장 직후 결정론적 헤더 검사를 실행한다
Consumer-Driven 원칙

계약의 "소비자" 는 qa-evaluator 다. 평가자가 독립적으로 검증할 수 없는 조건은 나쁜 조건이다. 자기 점검: "이 조건을 코드와 실행 결과만으로 PASS/FAIL 판정할 수 있는가?" — YES 면 유효한 조건, NO 면 재작성 필요.

LLM-as-Judge 연구는 "Evaluation criteria are critical for reliability... CoT reasoning offers minimal gains when clear evaluation criteria are present" 라고 보고한다 — 즉 criteria 품질이 평가 품질을 결정하며, 추가 CoT 로 모호한 criteria 를 보완하는 것은 한계가 있다. 관련 survey 는 unit test 가 "a detailed, executable specification that provides a formal contract" 역할을 한다고 보고한다. 계약 조건은 실행 가능한 테스트에 최대한 가깝게 작성하라.

Anti-patterns
안티패턴 카탈로그 (22 종)

각 행은 실제 REJECT 에서 귀납되었다. 마지막 6 행이 v4.0 에서 추가되었다.

안티패턴문제수정 방법
모호한 조건"적절히 처리한다" → 해석이 여러 개구체적 행동과 결과로 재작성
단일 카테고리 편중모든 조건이 UI에만 집중GQM 으로 카테고리 균형 확인
복합 조건"A이고 B이며 C이다"각각 독립 조건으로 분리
과소 안티패턴0-1개 안티패턴최소 2개 필수
테스트 불가 조건"사용자 경험이 좋다"측정 가능한 지표로 변환
복잡도 과소평가파일 수로만 판단영향 범위(레이어, 공개 API)로 판단
구현 누수조건에 클래스명/메서드명/DB명 포함외부 관찰 가능한 행동으로 재작성
NFR 누락기능 조건만 있고 비기능 조건 없음성능/보안/접근성 중 해당 항목 추가
판정 기준 범주 미명시exact 요구인지 goal 허용인지 불명확 → QA 해석 엇갈림조건 끝에 [exact]/[structural]/[goal] 태그 명시
예외 없는 전체 적용특정 파일 타입에 부적합한데 예외 없이 전 범위 적용예외 조항 인라인 명시 또는 applies_to 범위 한정
Aggregation mode 미명시개별 명시 vs 포괄 경로 중 무엇을 요구하는지 불명확[exact, enumerated] 또는 [structural, collective] 명시
한·영 표현 변형 비통일"Layout shift" vs "레이아웃 shift" 혼재 → 키워드 매칭 불일치한·영 병기 또는 한쪽으로 통일 선언을 조건 내부에 명시
숫자 레벨 태그 혼용계약 조건 태그에 QA 평가 깊이용 숫자 레벨 재사용반드시 문자 태그만 사용
경계값 측정 방법 미명시">= N" 조건에 측정 명령/도구 없음임계값 + 측정 대상 + 측정 방법을 인라인 명시
포맷 세분화 수준 미명시"일관된 포맷" 요구에 file/section/field 중 어느 수준인지 불명확최소 section-level 까지 명시, 핵심 필드는 field-level
스코프 범위어 미명시"주요/모든/대부분" 이 인라인 enumerate 없이 등장범위 포함/제외 목록을 조건 내부에 명시 (SK-02 재발 방지)
검증 수단 미명시어떤 명령·도구·관찰로 판정되는지 기술 없음측정 수단 인라인 기술, 외부 도구 의존 시 3 단계 fallback 명시
측정 oracle 의미·전제 불일치명령이 조건 의도와 다른 것을 측정하거나 상태 전제 누락의미 일치 oracle 선택 + Given: 전제 인라인 명시 (LG-07/AR-01)
Sibling 스킬 커버리지 누락공통 원칙이 여러 스킬에 적용돼야 하는데 단일 스킬만 점검[exact, enumerated] + 스킬 숫자/이름 전부 열거 (H-01/H-03)
정성적 수식어 사용"충분히", "상당한", "적절히", "대부분" 등 binary 판정 불가구체 수치/기준값으로 대체 또는 조건 분리
한쪽 면만 계약producer 조건만 있고 consumer 조건이 없음 → 클라이언트가 다음 스프린트로 밀림producer/consumer 를 별도 조건 2 개로 분리하고 각 면의 파일 경로를 enumerated (Friction #4)
preamble–조건 모순서두 설계 의도와 조건이 서로 다른 것을 요구DRAFT 제시 전 서술↔조건 방향 대조 + 열거 식별자 grep 확인 (RE-02)
diff-scope oracle 자유 서술상태 전제·경로 한정·생성물 제외·기대 집합 없이 git diff 사용표준형 4 요소 전부 + 작성 시점 baseline 실행 (AR-01 3 회 재발)
[exact] 산출물 오분류조건에 테스트·문서 산출물이 등장하는데 이번 스프린트에 낼 생각이 없음낼 것이면 경로까지 조건화, 아니면 [goal] 로 낮추거나 문구 제거 (UI-07)
증거 없는 goal 조건사람이 남겨야 생기는 증거에 의존하는데 그 기록물이 없음증거 기록물의 경로를 조건에 명시, 못 적으면 조건을 만들지 않음 (UI-06)
미분류 섹션 헤더Notes 등 미분류 헤더 추가, 또는 서술 섹션에 - [ ] 배치헤더 2 계층 허용 목록만 사용 + 저장 직후 결정론적 헤더 검사
