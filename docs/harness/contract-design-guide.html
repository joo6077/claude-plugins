Principles
핵심 원칙 — 검증 가능성 · 단일 해석 · 측정 가능성
검증 가능성 (Verifiability)

모든 조건은 제3자가 코드만 보고 PASS/FAIL 을 판정할 수 있어야 한다. INVEST 원칙의 Testable 과 동일한 요구다 — "제3자가 objectively 확인 가능해야 하며, 측정 가능한 값과 구체 행동으로 기술한다".

  • 좋은 예 — "로그인 실패 시 HTTP 401 을 반환한다"
  • 나쁜 예 — "로그인이 적절히 처리된다"
Agile Alliance INVEST
단일 해석 (Unambiguity)

조건은 단 하나의 해석만 가능해야 한다. IEEE 29148 기반 품질 기준:

  • 능동태 사용 ("시스템이 반환한다" not "반환되어야 한다")
  • 단일 조건 ("A 이고 B 이다" → 조건 2 개로 분리)
  • 모호 형용사 금지 ("빠르게", "적절히", "충분히" → 구체 수치)
측정 가능성 (Measurability)

조건의 충족 여부를 파일·코드·실행 결과로 증명할 수 있어야 한다.

LLM-as-Judge 연구 보강

평가 criteria 의 극단값(PASS/FAIL 양끝) 정의가 중간값 설명보다 judge alignment 에 더 큰 영향을 준다. 즉 "이 조건이 PASS 인 상태" 와 "FAIL 인 상태" 를 각각 한 문장으로 구체화하는 것이 중간 정도 서술을 풍부하게 하는 것보다 중요하다. 계약 작성 시 각 조건의 FAIL 이미지를 먼저 떠올리고 그 부정으로 PASS 를 기술하면 이진 판정 가능성이 올라간다.

개정 규칙 · E3 의 한계

같은 결함이 다시 관측되면 이 표의 문구를 다듬지 말고 등급을 한 칸 올려라. 등급을 올릴 수 없으면(이미 E3) 조건 설계 자체가 잘못된 것이므로 원칙을 재작성한다.

E3 로 올렸다고 끝이 아니다. 봉인은 조건 문구의 불변성만 보장하고 조건이 옳았는지는 보장하지 않는다. 게이트를 올리면 과차단 비용과 우회 유인이 함께 생기며, 우회된 게이트는 없는 게이트보다 나쁘다 — 통과 기록이 안전을 오해하게 만들기 때문이다. 그래서 봉인은 체크박스 토글과 서술 편집을 일부러 통과시킨다.

Writing Conditions
조건 작성법 — NASA · Design by Contract · GWT/AAA
NASA Requirements Writing Standards
  • 각 조건은 하나의 "shall"(또는 한국어 "~한다")만 포함
  • 부정 조건보다 긍정 조건 선호 ("에러가 없다" → "정상 응답을 반환한다")
  • "and/or" 사용 금지 — 각각 별도 조건으로
Precondition / Postcondition / Invariant
  • Precondition — 구현 시작 전 충족되어야 하는 조건 (환경, 의존성)
  • Postcondition — 구현 완료 후 반드시 참이어야 하는 조건 (핵심 기능)
  • Invariant — 구현 전후로 변하지 않아야 하는 조건 (기존 기능 보전)

Design by Contract (Meyer, 1992) 구조를 참고한다.

Given-When-Then / Arrange-Act-Assert
Given {전제 조건} | Arrange {사전 세팅} When {동작} | Act {행동 1회} Then {기대 결과} | Assert {관찰 1회}
  • 복잡도 "중간" 이상: 모든 핵심 조건에 GWT 또는 AAA 구조 필수
  • Gherkin one When-Then pair 규칙: 한 조건에 When-Then 쌍은 1 개만 — 2 개 이상이면 복합 조건이므로 분리
Gherkin Best Practices

반구조화된(semi-structured) 조건이 비구조화된 자연어보다 LLM 의 추론 정확도를 높이고 할루시네이션을 줄인다. LLM 코드 에이전트 벤치마크 연구는 PRD 를 evaluation blueprint 로 쓰고 GPT-4.1 이 AAA 형식으로 테스트 케이스를 생성하는 파이프라인을 제시했다 — 계약 조건을 AAA 로 작성하면 그 자체가 실행 가능한 spec 에 가까워진다.

외부 관찰 가능성 (External Observables Only)

조건은 시스템이 무엇을 하는지(외부 행동)만 기술한다. 어떻게 하는지(내부 구현)는 기술하지 않는다. 이 규칙을 위반하면 "구현 누수(implementation leakage)" 라 하며, 구현이 변경되면 조건도 깨지므로 조건의 수명이 짧아진다.

Bad — 구현 누수
"UserService 의 userRepository 가 비어있을 때" "POST /api/users 호출 시 201 을 반환한다"

금지 요소: 클래스명·메서드명·함수명, DB 테이블·컬럼·API 엔드포인트 경로, 프레임워크 용어(controller, service, repository, provider, notifier), 내부 상태 변수·플래그.

Good — 외부 관찰 가능
"등록된 사용자가 없을 때" "신규 사용자 등록 요청 시 성공 응답을 반환한다"
Counterpart
양면 조건 — Counterpart Conditions

계약·직렬화·공유 모델을 바꾸는 스프린트는 본질적으로 양면 작업이다. 서버 응답 형태를 바꾸고 클라이언트를 다음 스프린트로 미루면, 그 스프린트는 계약상 완료가 아니라 절반 완료다. 계약 테스트의 표준 관점도 동일하다 — consumer 측 검증만 하면 provider 가 예고 없이 바뀌고, provider 측만 검증하면 consumer 가 잘못된 요청을 보낸다.

설계 결정 — 이 원칙의 유일한 강제 지점은 계약 작성자다

Counterpart Enumeration 은 qa-evaluation-guide 에 대응 절을 두지 않는다. 평가자는 계약에 박힌 조건으로 이 원칙을 수용한다(parity item 12). 따라서 이 원칙이 실제로 작동하려면 계약 작성자가 조건을 넣어야만 한다 — 안 넣으면 아무도 안 잡는다.

적용 대상 (하나라도 건드리면 필수)
  • API 계약 · 엔드포인트 시그니처 · 상태 코드 (빈 상태 204/200/404 포함)
  • 직렬화 포맷 — JSON 스키마, 날짜·타임존 표현, enum 값, null 허용 여부
  • 공유 모델 · 공용 타입 · 생성 코드 (OpenAPI, protobuf, codegen 산출물)
  • 공개 함수 시그니처 · 이벤트 페이로드 · DB 스키마
Pact — Contract tests are not functional tests
작성 규칙 5 가지
  • producer 면과 consumer 면을 각각 별도 조건으로 쓴다. 한 조건에 양면을 묶으면 부분 통과가 PASS 로 새어 나간다
  • 각 조건은 해당 면의 파일 경로를 enumerate 한다 — [exact, enumerated] 필수. collective 금지

Consistency
계약 서두–조건 정합성 · 작성자의 이진 판정 의무

계약에 배경·설계 의도 서술(preamble)이 있으면 그것은 장식이 아니라 구현자가 읽는 지시다. 서술과 조건이 어긋나면 에이전트는 물어보지 않고 조용히 한쪽을 골라 구현한다.

실제 발생 사례 (RE-02, fit-pal 2026-07-22)

계약 preamble 은 단방향 차단 조회를 설계 의도로 서술했는데, 조건 RE-02 는 양방향 함수 batch_blocked_among 의 재사용을 literal 로 열거했다. 구현자는 preamble 을 따라 단방향 batch_blocking_out 을 새로 만들었고, 평가자는 조건의 literal enumeration 미충족으로 REJECT. 어느 쪽도 틀리지 않았고 계약이 자기모순이었다.

네이밍 규칙 — 숫자 레벨을 계약 태그로 재사용 금지

숫자 레벨(L-one, L-two, L-three)은 QA 평가 깊이 전용으로 예약되어 있다. 계약의 조건 태그는 반드시 문자 태그만 사용한다. 숫자 레벨을 혼용하면 QA 깊이와 조건 구체성이 구분되지 않아 평가 판정이 엇갈린다.

[exact]

정의 — 특정 이름/값/구조를 문자 그대로 매칭.
판정 — 해당 식별자가 코드에 존재하는지 직접 검색.
적합 — 함수명 계약, 파일명 계약, 특정 클래스 구조.

선택 기준: 이름·값·구조가 그것이어야만 의미가 있을 때. "이름이 달라지면 계약 실패" 가 성립하면 [exact].

[structural]

정의 — 섹션/필드/파일의 존재 여부 및 필수 서브구조.
판정 — 지정된 섹션·필드가 존재하는지 확인.
적합 — "X 섹션을 포함한다", "Y 필드가 있다".

선택 기준: "해당 구조가 존재한다" 만 검증하고 싶을 때. 태그 미명시 시 기본값이다.

[goal]

정의 — 수단 무관, 목표 달성 여부만 판정.
판정 — 기능이 의도한 결과를 산출하는지 확인.
적합 — "SSOT 달성", "회귀 없음", "파싱 성공".

선택 기준: 구현 방법은 자유이고 결과만 보고 싶을 때. 함수명·라이브러리가 달라도 목표만 달성하면 PASS.

계약은 write-once 다. 사용자 승인 후에는 조건 문구를 고치지 않는다. 바꿔야 하면 사이드카에 쓴다. 이 규칙 자체는 새 것이 아니다 — 직전 사이클(2026-07-28)이 이미 amendment 사이드카를 도입했다. 그런데도 다음 사이클에 바로 재발했다. 문장을 한 줄 더 추가하면 6 번째 재발이 난다.

RC1 — Cross-Surface Parity 결손

규칙이 읽기 측 문서에만 있었다

grep -rn 'write-once' — qa-evaluator.md · qa-evaluation-guide.md 에는 있고 본 가이드와 sprint-contract/SKILL.md 에는 0 건이었다. 본문을 편집한 주체는 REJECT 문구 그대로 "생성자" 인데, 생성자가 읽는 문서에 규칙이 없었다.

RC2 — 보상 역전

준수 경로의 기대 보상이 위반 경로보다 낮았다

같은 날 "amendment A-01 은 prompt-log 앵커 부재로 unknown 분류, PASS 근거 불가" — 사이드카를 실제로 썼는데 효력이 0 이었다. 다음 시도에서 본문 직접 편집으로 전환됐다. §Amendment 방향 판정이 이것을 해소한다.

RC3 — 오라클 부재

위반이 탐지되지 않았다

저장 검사 게이트는 헤더와 조건 개수만 본다. 문구를 바꿔도 개수가 같으면 통과한다. RC3 이 본 절(봉인)의 대상이다.

규칙
  • 사용자 승인 직후 계약을 봉인한다 — 조건 체크박스 줄만 정규화 해시해 frontmatter conditions_digest 와 locked_at 에 기록한다
  • 봉인 이후 조건 줄을 편집하지 마라. 자신이 만든 산출물을 사후에 허용하려고 조건 문구를 넓히는 것이 실측된 위반 형태다
  • 체크박스 토글과 서술 섹션 보강은 봉인을 깨지 않는다 — 일부러 그렇게 설계했다
  • SEAL_BROKEN 을 만나면 조용히 다시 봉인하지 마라. 그것은 위반을 지우는 행위다. recorded / actual 두 값과 함께 보고한다
  • 레거시 계약(봉인 필드 없음)은 SEAL_ABSENT 이며 경고이지 실패가 아니다. 소급 봉인 금지 — 원문이 무엇이었는지 증명할 수 없는 봉인은 봉인이 아니다
트레이드오프

봉인은 조건 문구의 불변성만 보장한다. 조건이 애초에 옳았는지는 보장하지 않으며, 계약이 실제로 잘못됐을 때 수정 비용을 사이드카 쪽으로 밀어낸다. 그 비용을 감당 가능하게 만드는 것이 다음 절(Amendment 방향 판정)이다.

포맷 정의는 harness/references/contract-schema.md §계약 봉인 이 SSOT 다.

Amendment
Amendment 방향 판정 — Direction × Consent

v5 의 amendment 유형 은 강화/완화 방향과 사용자 동의 유무를 한 축에 뭉쳐 놓았다. 그래서 앵커가 없다는 이유만으로 방향 판정까지 unknown 이 되었고, 사이드카를 성실히 쓴 스프린트가 아무 효력도 얻지 못했다. 준수 경로의 보상이 0 이면 사람은 위반 경로를 택한다 — 이것이 RC2 다. 두 축을 분리한다. 현재 등급: E2.

direction 은 PASS 집합의 증감으로 판정한다

"범위 축소" 라는 말로 판정하지 마라 — 무엇의 범위인지에 따라 정반대가 된다. 허용 경로를 줄이면 PASS 집합이 줄어 narrowing, 요구 대상을 줄이면 PASS 집합이 늘어 relaxing 이다.

  • 집합형 조건(경로 화이트리스트 · 파일 열거 · 대상 목록)의 direction 은 자기신고하지 말고 계산한다
  • 실측 위반(3 경로 → 5 경로)은 계산상 relaxing added=2 removed=0 이다 — "범위 조정" 이라고 부를 여지가 사라진다
consent 와의 조합
  • narrowing 은 consent 와 무관하게 PASS 근거가 된다. 제약을 강화하는 방향이라 남용이 구조적으로 불가능하다
  • relaxing 은 사용자 앵커가 있을 때만 PASS 근거다. 승인 주체는 사용자뿐이며 reviewer 확인을 추가 요건으로 두지 않는다
  • 앵커가 없으면 unanchored 라고 쓰는 것이 정답이다. 앵커를 지어내면 narrowing 까지 함께 무효가 된다

트레이드오프: narrowing · unanchored 를 PASS 근거로 허용하면 방향 판정을 잘못한 amendment 가 통과할 여지가 생긴다. 그래서 집합형은 계산을 요구하고, 계산이 불가능한 서술형은 unknown 으로 남겨 표면화한다.

측정 커버리지 — 산문이 요구한 것과 측정이 훑는 것 (E2 검출기)

검증 수단을 적었는지와 그 수단이 조건이 요구한 대상 전부를 훑는지는 다른 문제다. 후자를 재지 않으면 "측정 방법을 명시하고도 엉뚱한 것을 잰" 계약이 통과한다. enumerated 조건은 산문 측 대상과 측정 측 대상을 같은 표기(백틱 · 공백 없는 토큰)로 적는다. 상위 패턴 하나로 여러 대상을 덮을 때는 작성 시점에 그 명령을 1 회 실행해 확장 결과를 측정 절에 열거한다 — 실행하지 않은 커버리지 주장은 추측이다.

검출기 + 사람의 해소 기록

lexical ambiguity linter 를 자동 판정기가 아니라 "검출기 + 사람의 해소 기록" 으로 써야 한다는 접근과 같은 결론이다 — lexical scope 에서 recall 을 높이고 false positive 는 사람이 판단한다.

따라서 UNCOVERED 1 건마다 (a) 조건을 고치거나 (b) 서술 절에 해소 기록 한 줄을 남긴다.

인자 매트릭스 — Factor Matrix

축이 2 개 이상이고 그 곱이 조건의 의미를 결정할 때만 쓴다. 축 하나짜리 조건이나 작은 변경에 강요하면 과잉 절차다.

규약
  • 축과 축 값을 조건에 열거하고, 값의 출처를 코드의 공유 상수/enum 으로 지정한다. 테스트가 값을 재입력하면 다시 어긋난다
  • cases_total 을 손으로 적지 마라. 곱을 산출하는 명령을 조건에 적고 그 출력을 쓴다 — 사람이 옮겨 적는 숫자 필드는 이 가이드가 이미 conditions: 에서 3 회 연속 틀린 형태다
  • 기본은 full Cartesian. pairwise 로 낮추려면 곱셈 결과와 사유를 서술 절에 적고 사용자 승인을 받는다. 임계 숫자를 지어내지 않는다
  • combinatorial coverage 는 statement/branch coverage 와 다른 정적 test-set 속성이므로 기존 커버리지 수치로 대체할 수 없다

두 번째 용법 — variant 구별성

탐색형 스프린트(시안 · 목업 · 변주)는 같은 매트릭스를 variant 쪽에 쓴다. variant 마다 축 값 조합을 [exact, enumerated] 로 열거하고 동일 조합이 2 개 이상이면 FAIL 이다.

축을 지정하는 것만으로는 부족하다 — UI-04 는 계약이 4 축을 지정했는데도 두 variant 가 4 축 전부 동일값이었다. 스킬 측 짝은 skill-design-guide §5.6 Variant Budget 의 Variant Matrix 이며, 계약은 그 매트릭스를 조건으로 받는다.

실측 REJECT 두 건이 같은 뿌리다 — "3 visibility × 6 relation = 18 케이스 중 15 케이스(5 relation)만 재현. GroupMemberAndFollower 관계가 전체 누락" · "16 종 매핑 단위 테스트 커버리지 부족 (2 종만 검증)".

음성 대조 — Negative Control

측정 명령이 존재하고 의미도 맞는데 구현과 결합되어 있지 않은 경우가 있다. 구현을 통째로 지워도 측정이 통과하면 그것은 oracle 이 아니다. 적용 범위는 조건이 테스트·실행 산출물로 판정될 때로 한정한다 — 파일·섹션 존재를 보는 [structural] 조건에는 적용하지 않는다.

Bad — ER-02 실측
- [ ] ER-02: 낙관적 동시성 가드에 대한 테스트가 존재하고 통과한다 [structural] ← 구현을 지워도 통과하는 테스트가 이 조건을 만족시킨다
Good — 음성 대조 절 포함
- [ ] ER-02: 낙관적 동시성 가드가 conflict 경로를 실제로 막는다 [goal] (측정: 대상 행을 사전 변형한 뒤 실제 바이너리를 호출해 skipped 카운터 증가 관찰 · 음성 대조: 가드 술어를 제거하면 이 측정이 FAIL 해야 한다)
근거의 성격

이 조항의 근거는 이 레포의 실측 REJECT 코퍼스다. 외부 문헌 앵커는 이번 사이클에 확보하지 못했으므로 인용하지 않는다. 작성 시점에 음성 대조를 실제로 돌릴 수 없으면 그 사실을 조건에 적는다. "돌렸다" 고 적지 마라.

  • 예외 없이 작성된 조건은 해당 카테고리의 모든 파일에 적용된다고 간주
Property 기반 vs Example 기반 · GQM
  • Example 기반 — "입력 'abc' 에 대해 'ABC' 를 반환한다". 구체적이지만 범위 좁음
  • Property 기반 — "모든 입력에 대해 출력 길이가 입력 길이와 같다". 범위 넓음

단순 기능은 Example, 복잡한 로직은 Property 를 혼용한다.

GQM (Goal-Question-Metric): Goal(이 기능이 달성하려는 목표) → Question(달성을 어떻게 확인하는가) → Metric(어떤 지표로 측정하는가). 카테고리는 Goal 에서 도출하되, project.yaml 의 contract_categories 가 정의되어 있으면 그것을 따른다.

계약 파일 헤더 2 계층 — 조건 섹션 / 서술 섹션

기존 규칙은 "허용 헤더는 카테고리 + Anti-patterns / Reusability / Diagnostics 뿐" 이었는데, 실제 계약(특히 카이젠 계약)은 배경·리서치 소스·GAP 분석·범위 경계를 상시 사용해 왔다. 규칙이 실사용과 어긋나 있었기 때문에 재위반이 반복됐다. 그래서 규칙을 강화하는 대신 헤더를 두 계층으로 분류한다.

Consumer-Driven 원칙

계약의 "소비자" 는 qa-evaluator 다. 평가자가 독립적으로 검증할 수 없는 조건은 나쁜 조건이다. 자기 점검: "이 조건을 코드와 실행 결과만으로 PASS/FAIL 판정할 수 있는가?" YES 면 유효, NO 면 재작성.

LLM-as-Judge 연구 요지: "Evaluation criteria are critical for reliability… CoT reasoning offers minimal gains when clear evaluation criteria are present." — criteria 품질이 평가 품질을 결정하며, 계약 작성 단계에서 criteria 를 명확히 하는 것이 가장 ROI 높은 개입이다.
