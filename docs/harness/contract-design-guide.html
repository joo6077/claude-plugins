Contract Design Guide

sprint-contract 스킬이 참조하는 계약 작성 원칙. Phase 2 카이젠(v3)에서 Binary Decidability 의무, Scope Range 인라인 명시, Verification Method Required, Sibling Consistency, Cross-Surface Parity 섹션을 추가했다.

Core Principles
핵심 3원칙 — 검증 가능성 · 단일 해석 · 측정 가능성

모든 조건은 제3자가 코드만 보고 PASS/FAIL을 판정할 수 있어야 한다. 주관적 언어("잘 동작한다", "적절히", "충분히")는 금지.

검증 가능성 (Verifiability)

INVEST 원칙 중 Testable과 동일 요구. 제3자가 objectively 확인 가능해야 하며 측정 가능한 값과 구체 행동으로 기술한다.

Agile Alliance INVEST
단일 해석 (Unambiguity)

조건은 단 하나의 해석만 가능해야 한다. IEEE 29148 기준: 능동태, 단일 조건, 모호 형용사 금지("빠르게", "적절히" → 구체 수치).

측정 가능성 (Measurability)

조건의 충족 여부를 파일, 코드, 실행 결과로 증명할 수 있어야 한다. 측정 명령을 조건에 인라인으로 명시하라.

LLM-as-Judge 연구 보강

평가 criteria의 극단값(PASS/FAIL 양끝) 정의가 중간값 설명보다 judge alignment에 더 큰 영향을 준다. 각 조건의 FAIL 이미지를 먼저 떠올리고 그 부정으로 PASS를 기술하면 이진 판정 가능성이 올라간다.

Condition Writing
조건 작성법 — Binary Decidability · GWT · 외부 관찰

계약 작성자는 조건을 제출하기 전, 각 조건이 PASS 또는 FAIL 중 정확히 하나로 귀결 가능한지 자체 점검한다.

작성자 체크리스트 (조건 제출 전)
  • □이 조건에 정성적 수식어(충분히 / 상당한 / 적절히 / 대부분)가 없는가?
  • □이 조건의 FAIL 상태가 1문장으로 기술 가능한가? 불가능하면 조건이 모호하다
  • □이 조건의 태그([exact]/[structural]/[goal])가 부여되어 있는가?
  • □이 조건을 읽고 2명의 평가자가 서로 다른 판정에 도달할 가능성이 있는가?
Given-When-Then / AAA 구조화
Given {전제 조건} | Arrange {사전 세팅} When {동작} | Act {행동 1회} Then {기대 결과} | Assert {관찰 1회}

복잡도 "중간" 이상: 모든 핵심 조건에 GWT/AAA 구조 필수. Gherkin one When-Then pair 규칙: 한 조건에 When-Then 쌍은 1개만.

외부 관찰 가능성만 기술

조건은 시스템이 무엇을 하는지만 기술. 어떻게 하는지(내부 구현)는 기술 금지.

Specificity Tags
조건 구체성 태그 — [exact] · [structural] · [goal]

계약 작성 시 각 조건이 어느 수준으로 판정될지를 명시한다. 숫자 레벨 태그(L1/L2/L3)는 QA 평가 깊이 전용으로 예약되어 있다 — 계약 조건에 재사용 금지.

태그정의판정 기준적합한 상황
[exact] 이름/값/구조를 문자 그대로 매칭 해당 식별자가 코드에 존재하는지 직접 검색 함수명 계약, 파일명 계약, 특정 클래스 구조
[structural] 섹션/필드/파일의 존재 여부 (기본값) 지정된 섹션·필드가 존재하는지 확인 "X 섹션을 포함한다", "Y 필드가 있다"
[goal] 수단 무관, 목표 달성 여부만 판정 기능이 의도한 결과를 산출하는지 확인 "SSOT 달성", "회귀 없음", "파싱 성공"
Aggregation Mode — 다수 대상 조건 형식
모드의미예시
enumerated각 대상을 이름으로 개별 명시해야 PASS[exact, enumerated] — g1, g2, g3 파일 각각 명시
collective포괄 경로/패턴 하나로 지정 가능 (기본값)[structural, collective] — 경로 1건으로 커버

모드 미명시 시 기본값은 collective. [goal] 태그에는 aggregation 개념이 적용되지 않음.

Bad — 태그 미명시
- [ ] PU-04: pyyaml 기반 파싱 함수를 사용한다

exact인지 goal인지 불명확. 함수명 불일치로 REJECT될 수 있음.

Good — 태그 명시
- [ ] PU-04: pyyaml 기반 파싱이 동작한다 [goal]

구현 방법은 자유이고 결과만 보면 됨이 명확.

v3 추가사항
v3 신규 — Scope Range · Verification Method · Sibling Consistency

Phase 2 카이젠(2026-04-24)에서 실제 REJECT 사례에서 귀납한 3가지 원칙을 추가했다.

스코프 범위 인라인 명시 (Scope Range) — SK-02 재발 방지

"주요", "모든", "대부분" 같은 범위어가 등장하면 포함/제외 목록을 조건 내부에 인라인 enumerate해야 한다.

Bad — 범위 모호
- [ ] UI-02: 주요 interactive element의 box-shadow offset이 >= 4px [exact]

badge/decoration 포함 여부 해석이 갈림 → SK-02 REJECT.

Good — 범위 인라인 명시
- [ ] UI-02: 버튼·카드·입력 요소의 box-shadow offset >= 4px (badge, decoration 제외) [exact, enumerated]
검증 수단 명시 의무 (Verification Method Required)

모든 조건은 어떻게 판정할지를 인라인으로 명시해야 한다. 측정 명령, 도구, 관찰 대상 중 하나 이상을 조건에 기술하라.

- [ ] AR-03: docs/flutter/ 총 줄 수 >= 1500 (측정: `wc -l docs/flutter/*.md | tail -1`) [exact] - [ ] LG-02: 모달 close 클릭 시 overlay dismiss (측정: 1차 MCP Figma · 2차 fallback: CSS display 확인 · 3차 불가 시 [미검증] 허용) [goal]

MCP/외부 도구 의존 조건은 3단계 fallback을 인라인 기술. 계약에 fallback이 없으면 평가자가 임의 선택 → 판정 엇갈림.

형제 스킬 일관성 (Sibling Consistency) — H-01/H-03 재발 방지

플러그인 내 여러 스킬에 공통 원칙을 요구할 때, 계약은 모든 sibling 전부를 enumerated 형태로 명시해야 한다.

Bad — 단일 스킬만 점검
- [ ] SK-03: rust-api가 domain event + outbox 원칙을 따른다 [structural]
Good — sibling 전수 요구
- [ ] SK-03: domain event + outbox 원칙이 rust-init, rust-feature, rust-service, rust-api 4개 스킬 Gotchas 전부에 있다 [exact, enumerated]
Anti-patterns
안티패턴 전체 목록

계약 작성 시 아래 안티패턴 중 하나라도 해당되면 재작성하라.

안티패턴문제수정 방법
모호한 조건"적절히 처리한다" → 해석이 여러 개구체적 행동과 결과로 재작성
복합 조건"A이고 B이며 C이다"각각 독립 조건으로 분리
구현 누수조건에 클래스명/메서드명/DB명 포함외부 관찰 가능한 행동으로 재작성
태그 미명시판정 기준 범주 불명확[exact]/[structural]/[goal] 중 하나 명시
숫자 레벨 혼용계약 조건에 L1/L2/L3 재사용문자 태그만 사용 (숫자는 QA 평가 깊이 전용)
Aggregation mode 미명시개별 명시 vs 포괄 경로 해석 엇갈림enumerated 또는 collective 명시
범위어 미명시"주요/모든/대부분" 인라인 enumerate 없음포함/제외 목록을 조건 내부에 명시
검증 수단 미명시평가자가 도구를 임의 선택측정 명령/도구/관찰 대상 인라인 기술
경계값 측정 방법 미명시구현자와 평가자가 다른 방법으로 측정임계값 + 측정 대상 + 측정 명령 세트로 명시
Sibling 커버리지 누락공통 원칙이 일부 스킬에만 적용[exact, enumerated] + 스킬 이름 전부 열거
정성적 수식어"충분히", "상당한" — binary 판정 불가구체 수치/기준값으로 대체
