이번 사이클에 새로 지켜야 하는 것 3 가지

v1.5.0 의 방침은 새 문장 추가가 아니라 등급 승급이었다. 즉 "이미 적혀 있는데 또 어긴 규칙" 을 문장으로 다듬는 대신 아티팩트나 게이트로 올렸다. 새로 외워야 하는 것은 아래 3 개다.

유형 11

탐색형 생성이 별도 스킬 유형이 됐다

시안·목업·후보안처럼 하나의 결정을 위해 변주안을 여러 개 만드는 스킬. 다른 유형과 달리 산출물 개수 자체가 실패 모드이므로 §5.6 Variant Budget 이 필수다.

§5.6

Variant Budget — 상한 3 · 축 1(+1)

기본 산출물 상한 3 개, primary axis 1 개 고정(필요 시 secondary 1 개까지), 나머지는 constants 로 고정. 실행 전 Variant Matrix 를 합의한다. 요청받지 않은 부대 산출물(토큰 파일·디자인 시스템·scaffold)은 만들지 않는다.

§3.8

User-Reported Failure Gate

사용자가 "아직 깨져 있다" 고 하면 그 항목은 PASS 가 아니라 REOPENED. 반박 전에 내 오라클이 사용자가 보는 것을 재고 있었는지 6 축으로 대조한다.

In 5 Minutes
스킬 하나를 쓸 때 실제로 결정해야 하는 것
1. 형태

파일이 아니라 폴더로 설계한다

메인 SKILL.md 에는 개요와 파일 목록만. 상세는 references/, 실행 로직은 scripts/, 출력 형식은 templates/ 로 뺀다. Claude 는 필요한 파일만 골라 읽으므로 이 분리가 곧 컨텍스트 절약이다.

Progressive disclosure patterns — Claude API Docs
2. 분량

본문 500 라인 · 참조는 1-level deep

SKILL.md 본문은 500 라인 미만(공식 token budget). 참조 파일이 또 다른 참조를 링크하면 Claude 가 head -100 으로 일부만 미리보다 정보를 놓친다 — 모든 reference 는 SKILL.md 에서 직접 링크한다.

Token budgets — Claude API Docs
3. 트리거

description 은 요약이 아니라 스위치다

name ≤ 64 자(소문자·숫자·하이픈, gerund 권장), description ≤ 1024 자 3 인칭 필수. Claude 는 스킬을 undertrigger 하므로 약간 "pushy" 하게 — 트리거 맥락·파일 유형·사용자가 말할 법한 표현까지 나열한다.

Writing effective descriptions — Claude API Docs
4. 배타성

키워드는 두 검사를 모두 통과해야 한다

sibling 스킬과 set intersection 공집합 + substring containment 공집합. 단순 Grep 은 후자를 놓친다 — 실제 REJECT: "API 연동" ⊂ "API 연동 화면"(react-kit RE-02), "wasm-pack 빌드" 완전 중복(SK-05).

5. 자유도

취약한 작업일수록 명령을 정확히 준다

여러 길이 성공하면 High freedom(텍스트 지침), 안전한 길이 하나뿐이면 Low freedom(파라미터 없는 정확한 명령). L1/L2/L3 은 QA 검증 깊이 전용이므로 자유도를 논할 때 쓰지 마라.

Set appropriate degrees of freedom — Claude API Docs
6. 검증

스스로 확인할 방법을 같이 준다

공식 문서가 "가장 레버리지가 큰 단 하나" 로 꼽는 항목이다. 검증 기준이 없으면 사용자가 유일한 피드백 루프가 되고, 모든 실수에 사용자의 주의가 필요해진다.

Enforcement
새 규칙을 넣을 때 — "어떤 강도로" 를 먼저 정하라

문장으로 적을지(E1), 아티팩트를 요구할지(E2), 결정론적으로 막을지(E3)를 규칙을 쓰기 전에 정한다. 등급을 적지 않은 원칙은 미완성이다 — 나중에 재발했을 때 "무엇에서 무엇으로 올릴지" 판정할 수 없어 결국 문장만 다시 다듬게 된다.

새 원칙을 넣는다
  │
  ├─ 위반 이력이 없다 ─┬─ 선호·휴리스틱·저위험, 판정에 문맥 해석 필요 ─→ E1 문장 규칙
  │                    ├─ 반복 누락 예상 · open-ended · 범위/개수/증거를 남겨야 함 ─→ E2 아티팩트
  │                    └─ 기계 판정 가능 + 위반 비용 큼 ─→ E3 결정론적 게이트
  │
  └─ 같은 위반이 재발했다 ─┬─ 2 회 이상 ─→ E1 에서 E2 로 (문장을 다듬지 마라)
                           └─ 3 회 이상 · 비가역 · 신뢰 손상 ─→ E2 에서 E3 로

Editing Discipline
편집 전 · 편집 중 · 완료 직전 — 세 시점의 규율
편집 전

Pre-Edit Batch Audit

리팩터링·대량 편집(3+ 파일, 1+ 규칙군) 시작 전, 대상 파일 전수를 읽어 모든 적용 규칙 위반을 enumerate 한 체크리스트를 제시하고 승인받는다. 항목마다 (a) 파일/라인 근거 (b) 위반 규칙 식별자 (c) 권장 조치.

편집 중

Scope-Bound Edits

사용자가 X 를 요청했으면 X 만 한다. 인접 개선점은 즉시 패치하지 말고 별도 list 로 보관해 승인 후 처리한다. 파일 삭제·패키지 제거·force push·main push·스키마 마이그레이션·시크릿 로테이션은 매번 명시 승인.

완료 직전

Rule-by-Rule Audit

완료 선언 전에 자기 규칙 리스트를 다시 읽고 각 규칙에 대한 위반 여부를 파일/라인 근거와 함께 보고한다. "그 외에도 혹시 놓친 규칙이 있는가?" 를 1 회 더 스스로 묻는다.

Bad — N 회 왕복
사용자 "X 함수 수정해" → Claude X 수정 + 옆 Y 도 정리 + Z 파일 삭제 + main push → 사용자가 놓친 규칙 지적 → 수정 → 사용자가 또 발견 → 반복…

insights 인용: "Claude fixes some issues, you point out missed ones, Claude fixes those, you find more."

Good — 1 review + 1 execution
대상 파일 전수 audit → 위반 N 건 체크리스트 → 사용자 승인 → 일괄 편집 (범위 밖은 별도 list) → 규칙 전수 대조 → 위반 0 확인 → 완료 선언
변경의 반대편도 같이 열거하라 — Counterpart Enumeration

Pre-Edit Batch Audit 는 변경 대상 파일 안을 훑는다. 그런데 반복 관측된 실패는 그 변경을 소비하는 반대편에서 났다 — 서버 API 계약을 바꾸고 클라이언트를 다음 스프린트로 미루는 형태다. API 계약 · 직렬화 포맷(날짜·타임존·enum·null) · 공유 모델 · 공개 시그니처 · DB 스키마 중 하나라도 건드리면, 편집 전에 producer 면과 consumer 면 파일을 양쪽 다 경로로 열거한다. 소비면을 못 찾으면 grep 하고, 그래도 없으면 "소비자 없음" 을 근거와 함께 명시한다 — 추측으로 넘어가지 않는다.

Completion
완료를 선언할 자격 — 증거 5 조항

검증 기준을 제공하는 것(§3.6)과 증거 없이 완료를 선언하지 못하게 하는 것(§3.7)은 다른 요구다. 기준이 있어도 실행 증거 없이 완료가 선언되면 사용자가 유일한 검증자가 된다.

  • 1증거 블록 의무 — 완료 보고에 실행한 명령과 그 출력(또는 파일:라인)을 포함한다. "동작한다" 는 서술만으로 완료를 선언하지 않는다
  • 2증거는 자기보고가 아니라 도구 출력 — 스스로 "확인했다" 고 쓰는 문장은 증거가 아니다
  • 3검증 불가 시 [미검증] 명시 — 인프라 부재·도구 미설치·런타임 미실행이면 마커와 사유 한 줄을 붙인다. 미검증 2 건 이상이면 완료가 아니라 부분 완료로 보고한다
  • 4렌더 가능한 산출물은 렌더 결과를 증거로 — 단 스냅샷이 비어 있으면 그것은 PASS 증거가 아니라 검증 실패 신호다. 빈 결과를 "문제 없음" 으로 읽는 것이 실제 사고 형태였다
  • 5피드백 루프를 닫는다 — 실행 → 실패 시 수정 → 재실행을 반복하고, 스킬 본문에 "검증을 통과하기 전에는 다음 단계로 진행하지 않는다" 를 명시한다
충돌 시

사용자 관측은 반증 대상이 아니라 재현 대상이다

사용자 보고가 자기 증거와 충돌하면 완료 판정을 먼저 보류하고(REOPENED), 내 오라클이 사용자가 보는 것을 재고 있었는지 6 축으로 대조한다 — URL/경로 · 브랜치/커밋 · viewport · 디바이스/플랫폼 · auth·cache · 데이터 상태. 값싼 축부터 확인하고 비싼 축은 앞 축이 전부 일치할 때 넘어간다.

How Coding Agents Fail Their Users — arxiv:2605.29442
오독 금지

"사용자 말이 무조건 맞다" 가 아니다

정확한 규약은 완료 판정을 보류하고 오라클 유효성을 먼저 의심한다이다. 원인이 사용자 환경(스테일 빌드·캐시)으로 밝혀지는 것도 정상 종결이다 — 단 "환경 문제 같다" 는 특정이 아니다. 6 축 중 어느 축의 어떤 값이 달랐는지를 제시해야 한다.

Sibling

같은 kit 의 형제 스킬에 원칙을 전파했는가

새 Gotcha 를 sibling 중 한 곳에 추가하면 전 sibling SKILL.md 를 동시에 grep 하여 동일 표현 누락 여부를 확인한다. 누락은 "일부 스킬만 원칙을 안다" 는 비대칭 지식 상태를 만들어, 사용자가 어떤 스킬로 들어오느냐에 따라 완성도가 달라진다 (rust-kit H-01/H-03 REJECT).
