Archetypes
9가지 스킬 유형 체크리스트

Anthropic이 내부 스킬 수백 개를 분석하여 발견한 패턴. 좋은 스킬은 하나의 유형에 명확히 속하고, 나쁜 스킬은 여러 유형에 걸친다. 팀에 아직 없는 유형을 점검하는 체크리스트로 활용하라.

Frontmatter
엄격 스키마 — name 64자, description 1024자

v1.1.0 카이젠에서 공식 스키마 문서를 다시 점검하여 필드 제약을 정확히 수치로 고정했다. 이 제약을 위반하면 Claude는 스킬 메타데이터를 시스템 프롬프트에 로드할 때 discovery 오류를 일으킨다.

필드제약금지권장
name≤ 64자, 소문자 + 숫자 + 하이픈XML 태그, anthropic/claude 예약어, helper/utils/toolsgerund: processing-pdfs, analyzing-spreadsheets
description≤ 1024자, 비어 있을 수 없음1인칭/2인칭, XML 태그3인칭 선언문 + 트리거 키워드 + 비트리거 조건
argument-hint(선택) Claude Code 전용—인자가 있을 때만 추가
user-invocable(선택) Claude Code 전용—사용자 슬래시 호출 허용 시 true
name 작성 규칙

최대 64자. 소문자·숫자·하이픈만 허용. gerund form 권장 — 동작이 명확해진다. helper/utils 같은 모호 어휘는 Claude 가 트리거를 잡지 못한다.

Skill Authoring Best Practices
description 3인칭 필수

"I can help..." / "You can use..." 같은 1·2인칭 표현은 시스템 프롬프트에 주입되었을 때 관점 불일치로 discovery 실패를 일으킨다. 반드시 3인칭 선언문으로 작성한다.

Writing Effective Descriptions
Undertrigger
"Pushy" description으로 언더트리거를 보정하라

Claude 는 구조적으로 스킬을 undertrigger (필요한데도 안 쓰는) 하는 경향이 있다. skill-creator 공식 가이드는 description 을 약간 "pushy" 하게 작성해 트리거 맥락·파일 유형·사용자가 말할 법한 키워드까지 명시적으로 나열하라고 권장한다.

Bad — 무엇을 하는지만 한 줄
description: How to build a simple fast dashboard to display internal data.

Claude 가 언제 쓸지 판단할 단서가 없어 호출이 거의 일어나지 않는다.

Good — 트리거 맥락 나열
description: > How to build a simple fast dashboard to display internal data. Use this skill whenever the user mentions dashboards, data visualization, internal metrics, or wants to display any kind of company data, even if they don't explicitly ask for a "dashboard".

키워드·맥락·near-miss 까지 나열해 undertrigger 를 보정한다.

트리거 키워드 나열

사용자가 실제로 말할 법한 표현 5~10개를 description 에 삽입. 캐주얼·포멀 표현을 모두 포함.

skill-creator SKILL.md
비트리거 조건 명시

"단순 수정에는 트리거하지 않는다", "이미 X 가 존재하면 트리거하지 않는다" 같은 부정 조건도 함께 나열한다.

Writing Effective Descriptions
set intersection 공집합

플러그인 내 다른 스킬의 트리거 키워드와 set intersection 이 공집합이어야 한다. 같은 키워드가 두 스킬에 등장하면 충돌.

Best Practices Overview
Progressive Disclosure
3-레벨 로딩 시스템 + SKILL.md 500 라인 상한

스킬은 3 단계로 컨텍스트에 로드된다. 메타데이터만 항상 상주하고 본문은 트리거 시 로드, 참조는 필요 시에만 읽는다. v1.1.0 카이젠은 본문 500 라인 상한과 Reference 1-level deep 규칙을 공식 문서에서 재확인해 명문화했다.

Level 1: Metadata

~100 단어. 항상 시스템 프롬프트에 상주. name + description. 100+ 스킬 중 어느 것을 로드할지 결정하는 유일한 단서.

Progressive Disclosure
Level 2: SKILL.md body

스킬이 트리거될 때 로드. 핵심 지침과 워크플로우. 500 라인 미만으로 유지 — 넘으면 컨텍스트 사용량이 급격히 증가한다.

Token Budgets
Level 3: Bundled resources

scripts/, references/, assets/. Claude 가 필요할 때만 읽는다. 500 라인 초과분은 여기로 분리.

Avoid Deeply Nested References
Bad — 2-level deep
# SKILL.md See [advanced.md](advanced.md)... # advanced.md See [details.md](details.md)... # details.md Here's the actual information...

Claude 는 중첩 참조에서 head -100 같이 부분만 미리보는 경향이 있다 → 정보 누락.

Good — 1-level deep
# SKILL.md **Basic usage**: [instructions inline] **Advanced features**: See [advanced.md](advanced.md) **API reference**: See [reference.md](reference.md) **Examples**: See [examples.md](examples.md)

모든 reference 는 SKILL.md 에서 직접 링크. 100 라인 초과 시 ToC 추가 권장.

Degrees of Freedom
자유도를 태스크의 취약성에 맞춰라

스킬의 구체성 레벨은 태스크의 fragility(취약성)와 variability(가변성)에 맞춰야 한다. v1.1.0 카이젠은 공식 3 단계 분류를 명문화하고, 이 프로젝트의 QA 평가 깊이 L1/L2/L3 와 혼동하지 않도록 네이밍 충돌 해결 권고를 추가했다.

자유도형식사용 시점비유
High freedom텍스트 지침여러 접근이 유효, 문맥 판단, 경험 기반 heuristic위험 없는 열린 들판 — 여러 길이 성공
Medium freedom파라미터 있는 pseudocode/script선호 패턴이 있으나 일부 변형 허용안내 표지가 있는 트레일
Low freedom파라미터 없는 정확한 명령취약한 작업, 일관성 필수, 정확한 순서 필요양옆이 낭떠러지인 좁은 다리
네이밍 충돌 주의

L1/L2/L3 는 QA 평가 깊이 (Glob → Grep → Read/Bash) 전용으로 예약되어 있다. 스킬 지침의 구체성을 논할 때는 반드시 high/medium/low freedom 어휘를 사용하라. 두 체계를 혼용하면 contract 와 evaluator 가 충돌한다.

Set Appropriate Degrees of Freedom
Evaluation-Driven
평가 먼저, 문서 나중

스킬 작성의 기본 순서는 문서 먼저가 아니라 평가(eval) 먼저다. 존재하지 않는 문제를 문서화하지 않기 위함이다. v1.1.0 카이젠은 공식 권장 개발 루프와 Trigger Eval Set 패턴을 추가했다.

Gap 식별 → Eval 3+ 시나리오 → Baseline 측정 → 최소 지침 작성 → 반복 개선
Eval 구조 예시
{ "skills": ["pdf-processing"], "query": "Extract all text from this PDF...", "files": ["test-files/document.pdf"], "expected_behavior": [ "Reads the PDF using a library or CLI", "Extracts text from all pages", "Saves to output.txt readable format" ] } Build Evaluations First
Trigger Eval Set 20 쿼리

스킬이 준비되면 description 의 트리거 정확도를 측정한다. 20 개 쿼리 (should-trigger 8~10 + should-not-trigger 8~10) 를 작성하고 각 쿼리는 구체적·현실적 (파일 경로, 회사명, 오타 포함) 이어야 한다.

Description Optimization
MCP Tools
Fully-Qualified Name 필수

스킬이 MCP (Model Context Protocol) 도구를 참조할 때는 반드시 fully-qualified name 을 사용한다. 여러 MCP 서버가 활성화된 경우 서버 prefix 가 없으면 Claude 가 도구를 찾지 못하거나 잘못된 서버의 도구를 호출한다.

Bad — server prefix 누락
Use the `bigquery_schema` tool to retrieve schemas.

"tool not found" 에러 또는 잘못된 서버 호출 발생.

Good — ServerName:tool_name
Use the `BigQuery:bigquery_schema` tool to retrieve table schemas. Use the `GitHub:create_issue` tool to create issues.

형식: ServerName:tool_name

왜 prefix 가 필요한가

한 워크스페이스에 여러 MCP 서버 (Notion, GitHub, BigQuery 등) 가 동시에 활성화되어 있을 때, 같은 이름의 도구가 여러 서버에 존재할 수 있다. prefix 없이 호출하면 Claude 가 임의의 서버를 골라 silent failure 가 발생한다.

SKILL.md 체크리스트

v1.1.0 카이젠이 정리한 핵심 점검 항목. 새 스킬을 만들거나 기존 스킬을 손볼 때 위에서 아래로 점검하라.

  • ✓ name ≤ 64자, 소문자/숫자/하이픈만, gerund form, 예약어 (anthropic/claude/helper/utils) 없음
  • ✓ description ≤ 1024자, 3인칭 선언문, 트리거 키워드 5+ 와 비트리거 조건 명시
  • ✓ 다른 스킬과 트리거 키워드 set intersection 이 공집합
  • ✓ SKILL.md body 500 라인 미만 — 초과분은 references/scripts/templates 로 분리
  • ✓ 모든 reference 는 SKILL.md 에서 직접 링크 (1-level deep)
  • ✓ 100 라인 초과 reference 파일 상단에 Table of Contents 포함
  • ✓ Gotchas 섹션에 Claude 가 반복 실패한 패턴이 한 줄씩 누적
  • ✓ 스킬 카테고리 ID·필드명·섹션명이 Sprint Contract 의 조건명과 1:1 매칭
  • ✓ Degrees of Freedom (high/medium/low) 결정 — L1/L2/L3 와 혼용 금지
  • ✓ 검증 가능한 성공 기준 포함 — Claude 가 self-verification 가능
