Structure
§1 파일이 아닌 폴더로 설계하라

스킬은 마크다운 파일 하나가 아니라 폴더 단위로 설계한다. 점진적 공개(Progressive Disclosure): 메인 MD에는 개요와 파일 목록만, 상세는 별도 파일로 분리한다.

폴더 구조 (밀키트 비유)
my-skill/ ├── my-skill.md # 개요 + 파일 목록 ├── references/ # API 문서, 코드 스니펫 │ └── api.md ├── scripts/ # 헬퍼 함수, 검증 스크립트 │ └── validate.sh └── templates/ # 출력 템플릿 └── report.md

밀키트 비유 — 레시피(지시문)뿐 아니라 재료(레퍼런스)와 도구(스크립트)까지 제공한다. 메인 파일에 모든 정보를 넣으면 컨텍스트가 과부하된다.

Progressive Disclosure
3-레벨 로딩 시스템

Level 1 — Metadata (~100단어, 항상 시스템 프롬프트에 상주): name + description

Level 2 — SKILL.md body (스킬이 트리거될 때 로드): 핵심 지침과 워크플로우. 500 라인 미만 유지.

Level 3 — Bundled resources (필요할 때만 읽음): scripts/, references/, assets/

메타데이터만 항상 상주하고 나머지는 on-demand 로 읽는다. 바로 이 구조가 "컨텍스트 절약"의 핵심이다.

Token Budgets
Reference 파일은 1-level deep (필수)

Claude는 참조 파일이 다른 참조 파일에서 다시 링크되어 있을 때 head -100으로 일부만 미리보는 경향이 있어 정보 누락이 발생한다. 모든 reference는 SKILL.md에서 직접 링크되어야 한다. 100 라인을 넘는 reference 파일에는 상단에 Table of Contents 를 포함한다.

Avoid Deeply Nested References
Archetypes
§2 스킬 10가지 유형 — 하나에 명확히 속해야 한다

Anthropic이 내부 스킬 수백 개를 분석하여 발견한 패턴. 좋은 스킬은 하나의 유형에 명확히 속하고, 나쁜 스킬은 여러 유형에 걸친다. 1~9 는 공식 분석 패턴, 10 은 본 레포 운영 경험에서 추가되었다.

1
라이브러리 레퍼런스
내부 라이브러리 사용법 및 함정 정리 — 사내 SDK 가이드
2
제품 검증
Playwright 등 도구로 코드 자동 확인 — E2E 테스트 스킬
3
데이터 조회
모니터링/분석 스택 연결 — Grafana 대시보드 조회
4
비즈니스 자동화
반복 업무 자동화 — 스탠드업 리포트, 위클리 리캡
5
코드 스캐폴딩
보일러플레이트 자동 생성 — 프로젝트 초기 설정
6
코드 리뷰
스타일 강제 또는 자동 리뷰 — PR 리뷰 스킬
7
CI/CD
PR 모니터링 및 자동 롤백 — 배포 파이프라인 스킬
8
런북(Runbook)
장애 시 자동 조사 및 보고서 — 인시던트 대응 스킬
9
인프라 운영
리소스 정리 및 비용 분석 — 미사용 리소스 정리
10
Session Lifecycle
세션 종료/이어가기/요약 자동화 — handoff, work-summary, resume-prompt

유형 10 은 긴 세션의 toll / network / output_token 한계로 truncation 이 잦은 환경에서 lifecycle 스킬이 별도 카테고리로 식별되어 추가되었다 (2026-05 /insights). 이 목록을 체크리스트로 사용하여 팀에 아직 없는 스킬 유형을 점검하라.

Gotchas
§3 Gotchas — 스킬에서 가장 가치 있는 섹션

Claude는 코딩을 이미 잘 안다. 파이썬 API 호출법 같은 일반 지식은 스킬에 불필요하다. 스킬에 담아야 할 것은 Claude가 추론만으로 절대 알 수 없는 정보 — 즉 반복적으로 실패하는 지점이다.

Gotchas 추가 흐름
Claude가 실수 → 실수 패턴 식별 → Gotchas에 한 줄 추가 → 다음부터 같은 실수 방지

대부분의 스킬은 몇 줄의 지시문 + 하나의 Gotchas로 시작하여 점진적으로 성장한다.

왜 Gotchas 인가

완벽한 지시문에도 Claude는 예상치 못한 실수를 한다. 신입 사원에게 매뉴얼보다 선배의 "이거 조심해" 조언이 더 유용한 것과 같다.

QA Name Matching
§3.5 QA 계약과 1:1 매칭되는 이름을 사용하라

스킬이 정의하는 카테고리, 필드, 섹션 이름은 QA 계약(Sprint Contract)에서 그대로 재사용된다. 이름이 어긋나면 평가자가 해석해야 하고 해석이 엇갈리면 REJECT 또는 모호한 PASS 가 발생한다.

Bad — 스킬과 계약 이름이 다름
스킬: "Anatomy 섹션 — 필수 파트: Header, Body, Footer" 계약: "SK-05: 레이아웃 구조 확인 (헤더/바디/푸터 포함 여부)"

"레이아웃 구조"가 Anatomy 를 가리키는지 불명확.

Good — 스킬과 계약 이름이 일치
스킬: "Anatomy 섹션 — 필수 파트: Header, Body, Footer" 계약: "SK-05: Anatomy 섹션 확인 — Header, Body, Footer 필수 파트 포함 여부"
  • 1스킬에 카테고리 ID(SK-xx, CD-xx 등)를 정의했으면, 계약 조건에도 동일 ID 를 사용
  • 2스킬 본문의 필드명을 계약 작성 시 그대로 복사하여 재해석 여지를 없앰
  • 3스킬을 수정할 때 이름이 바뀌면 기존 계약 템플릿도 함께 갱신
Verification
§3.6 검증 가능한 성공 기준 + 3 종 감사 패스

스킬이 산출물을 생성할 때 Claude가 스스로 결과를 검증할 수 있는 기준을 포함해야 한다. 검증 기준 없이 Claude는 "그럴듯해 보이지만 실제로는 동작하지 않는" 결과를 만든다. 사용자가 유일한 피드백 루프가 되면 모든 실수에 사용자의 주의가 필요하다.

스킬 유형검증 기준 예시
코드 스캐폴딩생성 후 commands.analyze 실행, 워닝 0개 확인

Rule-by-Rule Audit Before Completion

Claude는 리팩터링/대량 편집 시 규칙에 이미 기재된 위반을 놓치고 사용자가 지적해야 비로소 고치는 패턴을 반복한다. 스킬이 규칙 리스트를 보유할 경우, 완료 선언 전에 규칙별 1:1 대조 패스를 강제해야 한다. 마지막에 "그 외에도 혹시 놓친 규칙이 있는가?" 를 1 회 더 스스로 질문한다 (meta-audit).

Bad
편집 완료 → 사용자가 놓친 규칙 지적 → 반복
Good
편집 → 규칙 체크리스트 전수 대조 → 위반 발견 → 수정 → 완료
Pre-Edit Batch Audit — 리팩터링 시작 전 위반 전수 enumerate

Rule-by-Rule Audit 가 완료 시점의 안전망이라면, Pre-Edit Batch Audit 는 편집 시작 시점에 같은 규칙 리스트를 능동 적용한다. 두 패스가 짝을 이뤄야 N 회 round-trip 이 "1 review + 1 execution" 으로 축약된다. 대상은 3+ 파일 · 1+ 규칙군 규모의 리팩터링이다.

  • a항목마다 파일/라인 근거를 붙인다
  • b항목마다 위반 규칙 식별자를 붙인다
  • c항목마다 권장 조치를 붙이고, 사용자 승인 후 일괄 편집한다

아키텍처 선택(Stack vs Column, Service vs UseCase, widget extend vs new) 같은 false-dichotomy 영역도 enumerate 대상이다 — 옵션 A/B/C 를 모두 보여주고 trade-off 를 명시한 뒤 선택받는다. 본 원칙은 high-freedom(아키텍처·디자인)과 low-freedom(린트 규칙·토큰 마이그레이션) 양쪽에 적용된다.

Scope-Bound Edits — 허락 없는 삭제 / 디자인 선택 금지

사용자가 X 를 요청했을 때 X 만 수행하고, X 와 인접해 보이는 Y/Z 는 명시적 승인 없이 절대 건드리지 않는다. 빈번한 위반: 인접 코드 silently 정리, 범위 밖 파일 삭제, 임의 컬러/spacing/네이밍 결정, "겸사겸사" 패키지 업그레이드, main 직접 push.

  • 1요청 X 의 경계를 시작 전에 한 줄로 적고 사용자에게 확인
  • 2작업 중 인접 위반 발견 시 즉시 패치하지 말고 별도 list 로 보관 → 승인 후 별도 commit
  • 3Hard-stop actions 는 매번 명시 승인: file deletion, package removal, branch deletion, force push, main push, schema migration, secret rotation
  • 4훅으로 하는 결정론적 수정(lint/format)은 OK — 의미적 변경은 Hard-stop 대상
Bad: 사용자 "X 함수 수정해" → X 수정 + 옆 Y 정리 + Z 삭제 + main push Good: 사용자 "X 함수 수정해" → X 만 수정 → 인접 개선점은 별도 list → 승인 후 처리

§3.7 Completion Evidence Gate — 증거 없는 완료 주장 금지

§3.6 이 "검증 기준을 제공하라" 였다면 본 섹션은 "증거 없이는 완료를 선언하지 못하게 하라" 다. 두 요구는 다르다 — 기준이 있어도 실행 증거 없이 완료가 선언되면 사용자가 유일한 검증자가 된다.

75.8%
명시적 완료 주장을 포함한 자기평가 코딩 에이전트 궤적(AppWorld)에서 실패 중 false success 비중
0.54~0.65
LLM 판정자 AUROC (5 모델 × 5 프롬프트 전략) — 자기점검·LLM 재확인은 게이트가 아니다
91.49%
실사용 20,574 세션에서 가시적 misalignment 해소가 사용자의 명시적 교정을 필요로 한 비율
왜 문장 규칙만으로는 안 되는가

판정에 쓰인 신호는 검증된 상태 변화가 아니라 "자신 있는 마무리 문장" 같은 표면 프록시였다. 실사용 관측에서 전체 misalignment 비율은 내려가는데 부정확한 자기보고(inaccurate self-reporting)의 비중은 오히려 늘었다.

Enforcement 3 등급 — 원칙을 "어떤 강도로" 구현할지 판정하라

새 원칙을 스킬에 넣을 때는 문장으로 적을지, 아티팩트를 요구할지, 결정론적으로 막을지를 먼저 정한다.

E1 · 문장 규칙

Gotchas / Process 의 서술문

보장 수준: 통계적 개선만. 적합: 최초 도입, 위반 이력 없음.

E2 · 체크리스트 아티팩트

응답에 복사해 채우는 체크리스트 / 검증 전 생성하는 계획 파일

보장 수준: 흔적이 남아 사후 대조 가능 (여전히 자기보고). 적합: 다단계 워크플로우, 위반 1~2 회 재발.

E3 · 결정론적 게이트

스크립트 / 훅 / CI — LLM 호출 없는 순수 판정

보장 수준: per-run 보장. 적합: 비가역·신뢰 손상 영역, 3 회 이상 재발.

등급 승급 규칙

같은 위반이 2 회 이상 재발하면 E1 → E2, 3 회 이상이거나 비가역 변경·사용자 신뢰 손상이 걸리면 E2 → E3 로 올린다. 재발했는데 같은 등급에서 문장만 다시 다듬는 것은 개선이 아니다.

E3 게이트의 정의

g(입력, 현재상태) → {통과, 거부} 인 순수 함수. (a) 상태를 읽기만 하고 바꾸지 않는다 (b) LLM 을 호출하지 않는다 (c) 행위 직전에 실행된다 (d) 거부 시 구조화된 사유를 돌려준다.

해당 논문에서 4 개 게이트 도입만으로 벤치마크 성공률이 29.6% → 42.0% (+12.4pp) 로 올랐고, k=5 반복 신뢰도(pass_k)는 8.0% → 26.0% 로 개선됐다. 프롬프트는 확률을 올릴 뿐이고 게이트는 매 실행마다 금지된 전이를 막는다. 스킬에서 E3 는 보통 scripts/validate_*.sh + "검증 통과 전 다음 단계 진행 금지" 문구, 또는 PreToolUse/PostToolUse 훅으로 구현한다.

스킬이 지켜야 할 5 조항
  • 1증거 블록 의무. 산출물을 만드는 스킬은 완료 보고에 실행한 명령과 그 출력(또는 파일:라인)을 포함한다. "동작한다", "정상 렌더링된다" 같은 서술만으로 완료를 선언하지 않는다.
  • 2증거는 자기보고가 아니라 도구 출력이어야 한다. 스스로 "확인했다" 고 쓰는 문장은 증거가 아니다 (AUROC 0.54~0.65).
  • 3검증 불가 시 [미검증] 명시. 인프라 부재·도구 미설치·런타임 미실행으로 검증이 불가하면 조용히 넘기지 말고 마커와 사유 한 줄을 붙인다. 미검증 2 건 이상이면 완료가 아니라 부분 완료로 보고한다.
  • 4렌더 가능한 산출물은 렌더 결과를 증거로 쓴다. UI·문서·차트는 렌더 → 캡처 → 대조까지 수행한다. 단 스냅샷/캡처가 비어 있으면 그것은 PASS 증거가 아니라 검증 실패 신호다.
  • 5피드백 루프를 닫는다. 검증 스크립트가 있으면 실행 → 실패 시 수정 → 재실행 을 반복하고, 본문에 "검증을 통과하기 전에는 다음 단계로 진행하지 않는다" 를 명시한다.
Bad — 빈 결과를 "문제 없음" 으로 읽음
구현 → "정상 동작 확인했습니다" (도구 출력 없음) → 사용자가 실제로는 깨져 있음을 발견 스냅샷 빈 화면 반환 → "렌더링 정상" 으로 해석 → 반복 주장 → 신뢰 손상

빈 카탈로그를 MCP 스냅샷 근거로 "정상 렌더링" 이라 반복 주장한 것이 2026-07 Friction #2 의 실제 사고 형태였다.

Good — 도구 출력 인용 · 미검증 명시
구현 → 검증 명령 실행 → 출력 인용 → 실패분 수정 → 재실행 → 통과 후 완료 선언 검증 불가 → "[미검증] MCP 미설정 — 시각 대조 불가" → 부분 완료로 보고

Cross-Surface Parity: 본 원칙은 §11 parity 표 5 번째 항목 — agent-design-guide §10 "Unverifiable 조건 정책" 의 스킬(생성) 측 짝이다. 평가자만 미검증을 표기하고 생성자는 표기하지 않으면, 평가 시점에야 미검증이 드러나 iteration 이 낭비된다. 마커·임계값은 두 가이드가 동일 규약을 쓴다 (용어 분기 금지).

Description
§4 디스크립션은 트리거 조건이다 — frontmatter 규칙

스킬의 description 필드는 사람을 위한 요약이 아니라 Claude가 스킬을 선택하는 트리거 조건이다. Claude는 세션 시작 시 모든 스킬의 메타데이터를 시스템 프롬프트에 pre-load 하며, 이 값 하나로 100개 이상의 스킬 중 어느 것을 로드할지 판단한다.

name 필드 규칙

최대 64자. 소문자 + 숫자 + 하이픈만 허용. XML 태그 금지. 예약어 anthropic, claude 포함 불가. gerund form 권장: processing-pdfs, analyzing-spreadsheets, testing-code. 허용 대안은 명사구(pdf-processing) 또는 동사형(process-pdfs). helper, utils, tools, documents 같은 모호한 이름 금지.

description 필드 규칙

최대 1024자. 비어 있을 수 없음. XML 태그 금지. 반드시 3인칭으로 작성 — 1인칭("I can help...") 또는 2인칭("You can use this...")은 시스템 프롬프트에 주입되었을 때 관점 불일치로 discovery 실패를 일으킨다.

YAML Frontmatter Requirements
Undertrigger 경향과 "pushy" 디스크립션

Claude는 구조적으로 스킬을 undertrigger(필요한데도 안 쓰는) 하는 경향이 있다. 이를 보정하기 위해 description 은 약간 "pushy" 해야 한다 — 트리거 맥락, 파일 유형, 사용자가 말할 법한 키워드를 명시적으로 나열해라.

skill-creator — Description Best Practices
Bad — 기능만 설명
description: 배포 관련 스킬

트리거 약함. Claude가 언제 써야 하는지 알 수 없음.

Good — 트리거 맥락까지 나열
description: > Deploys services to production and verifies deployment status. Use when the user requests production deployment, PR merge checks, or asks to "deploy", "ship", or "roll out" a service.
트리거 키워드 중복 방지 — set intersection + substring 검사

플러그인이 여러 스킬을 포함할 때, description 의 트리거 키워드는 두 가지 검사를 모두 통과해야 한다: ① Set intersection 이 공집합 ② Substring containment 도 공집합. 단순 Grep 은 부분문자열 중복을 놓치므로 정규식 추출 후 두 검사를 모두 수행해야 한다.

Bad — substring 위반 (RE-02 REJECT)
react-feature: "API 연동 화면을 한 번에 생성" react-api: "API 연동 시 Clean Arch 4계층" → "API 연동" 이 부분문자열 → 배타성 위반

또 다른 실제 사례(react-kit SK-05): react-run 의 "wasm-pack 빌드" 가 react-wasm 과 정확히 일치 → set intersection 위반.

Good — 키워드 완전 분리
react-feature: "Clean Arch 4계층 복합 생성" react-api: "datasource→repository 단일 레이어"

예외: 동일 키워드라도 플랫폼/스택 컨텍스트로 명확히 구분되면 허용된다. 단 description 에 구분 조건을 반드시 명시해야 한다.

Progressive Disclosure Patterns
Degrees of Freedom
§5.5 자유도를 태스크에 맞춰라 + Counterpart Enumeration

스킬의 구체성 레벨은 태스크의 취약성(fragility)과 가변성(variability)에 맞춰야 한다. QA 평가 깊이 L1/L2/L3 과 이 자유도 개념을 혼동하면 안 된다 — L1/L2/L3 은 QA 검증 깊이 전용 용어로 예약한다.

자유도형식사용 시점
High freedom텍스트 지침여러 접근이 유효, 문맥에 따라 판단, 경험 기반 heuristic
Medium freedom파라미터 있는 pseudocode/script선호 패턴이 있으나 일부 변형 허용
Low freedom파라미터 없는 정확한 명령취약한 작업, 일관성 필수, 정확한 순서 필요

공식 문서의 비유: Claude 를 경로를 탐색하는 로봇으로 생각하라. 양옆이 낭떠러지인 좁은 다리(안전한 길이 하나) → Low freedom. 위험 없는 열린 들판(여러 길이 성공) → High freedom.

Enumerate-before-Act — Low-freedom 영역의 고정 규율

토큰 네이밍, Figma 컴포넌트 식별, 스펙 수치, 디자인 시스템 컬러, 계약 카테고리 ID 같은 low-freedom 영역은 편집 전 반드시 enumerate-before-act 를 적용한다: ① 기존에 존재하는 토큰/옵션/스펙을 전부 목록화 → ② 대상 후보를 1-N 인덱스로 나열 → ③ 지목된 항목을 확인 후 편집 시작.

Low-freedom 영역에서 "근사치로 추정" 또는 "아마도 이게 맞을 것 같다" 는 3+ iteration 재작업의 가장 큰 원인이다. 한 번의 enumerate 로 N 번의 왕복이 방지된다.

Set Appropriate Degrees of Freedom
Counterpart Enumeration — 변경의 반대편을 열거하라 NEW v1.4.0

Enumerate-before-Act 와 Pre-Edit Batch Audit(§3.6)는 둘 다 변경 대상 파일 안을 훑는다. 그런데 반복 관찰된 실패는 대상 파일이 아니라 그 변경을 소비하는 반대편에서 났다 — 서버 API 계약을 바꾸고 클라이언트를 같은 스프린트에 반영하지 않는 형태다. UTC 직렬화 버그도 같은 계열이며, 사용자가 "당연히 클라까지 바꿔야지" 로 매번 개입해야 했다.

적용 대상 (하나라도 건드리면 필수)
  • ·API 계약 / 엔드포인트 시그니처 / 상태 코드
  • ·직렬화 포맷 — JSON 스키마, 날짜·타임존 표현, enum 값, null 허용 여부
  • ·공유 모델 · 공용 타입 · 생성 코드(OpenAPI, protobuf, codegen 산출물)
  • ·공개 함수 시그니처 · 이벤트 페이로드 · DB 스키마
절차 3 단계
  • 1편집 착수 전, producer 와 consumer 파일을 양쪽 다 경로로 열거. 소비면을 못 찾겠으면 grep 으로 찾고, 그래도 없으면 "소비자 없음" 을 근거와 함께 명시 — 추측으로 넘어가지 않는다.
  • 2열거 결과를 계획 아티팩트(체크리스트 또는 계약 조건)로 남긴다. §3.7 등급 기준 E2 이상 — 문장 다짐으로 처리하지 않는다.
  • 3한 스프린트에서 양쪽을 다 못 바꾸면, 남는 쪽을 [미검증] 이 아니라 명시적 미완 항목으로 보고한다 (조용한 반쪽 완료 금지).
Bad: 서버 응답 필드 rename → 서버 코드만 수정 → "완료" → 클라이언트 런타임 파싱 실패 Good: 서버 응답 필드 rename → producer 1 파일 + consumer 3 파일 경로 열거 → 체크리스트 합의 → 4 파일 일괄 수정

부적합: 소비자가 존재할 수 없는 순수 내부 리팩터링(private 함수 본문, 로컬 변수명). 이 경우 열거 단계는 noise 다.

Sharing & Evaluation
§8 공유 전략 · §8.5 Evaluation-Driven Development

스킬 작성의 기본 순서는 문서 먼저가 아니라 평가(eval) 먼저다. 존재하지 않는 문제를 문서화하지 않기 위함이다.

공식 권장 개발 루프 (5단계)
  • 1Gap 식별: 스킬 없이 대표 태스크를 Claude 로 실행해 실패 지점을 기록
  • 2Eval 생성: 이 gap 을 검증할 최소 3개 시나리오 작성
  • 3Baseline 측정: 스킬 없는 상태에서 Claude 의 성능 측정
  • 4최소 지침 작성: gap 을 해결할 만큼의 최소한의 본문만 작성
  • 5반복: eval 실행 → baseline 대비 → 리팩터링
Build Evaluations First
Trigger Eval Set — 20개 쿼리

스킬이 준비되면 description 의 트리거 정확도를 측정한다. should-trigger 8~10 개 + should-not-trigger 8~10 개. 각 쿼리는 구체적·현실적(파일 경로, 회사명, URL, 오타 포함), 다양한 표현(캐주얼/포멀, 간접적 언급), near-miss(인접 도메인, 모호한 표현) 포함.

Bad
"Format this data" (너무 일반적)
Good
"ok so my boss just sent me this xlsx file... revenue is in column C..."

이 레포의 flutter-toolkit/evals/evals.json 이 이 패턴의 실제 구현이다.

§8.7 Code Examples — 3원칙

① 모든 fenced code block 에 언어 힌트 필수 — bare fence 금지. 실행 가능하면 bash/python/dart/typescript/yaml/json, 설명용이면 text 또는 pseudo
② 코드 템플릿 내부에 TODO/FIXME/미완성 placeholder 금지 — 사용자가 손으로 채울 부분은 명시적 주석으로 전환
③ 인용/모조 코드와 실행 코드의 구분 명확

검증법: rg -n '^```\s*$' <file> 로 bare fence 탐지, rg -n 'TODO|FIXME' <file> 로 placeholder 잔존 탐지. 둘 다 0건이어야 한다.

§8.8 Sibling-Skill Principle Consistency — H-01/H-03 재발 방지

하나의 kit 내 동일 계열 스킬(init/feature/api/service 등)에 공통으로 적용되는 원칙은 모든 sibling SKILL.md 의 Gotchas 에 동일한 표현으로 등장해야 한다. 누락은 "일부 스킬은 원칙을 알고 있지만 다른 스킬은 모른다" 는 비대칭 지식 상태를 만들어, 사용자가 어떤 스킬로 들어오느냐에 따라 완성도가 달라진다.

Bad — 비대칭 지식
rust-service: ["Composition Root", "domain event"] rust-api: ["... (Composition Root 누락)"] rust-init: ["... (domain event 누락)"]
Good — 전 sibling 동일 표현
rust-service: ["Composition Root", "domain event"] rust-api: ["Composition Root", "domain event"] rust-init: ["Composition Root", "domain event"]

운영 절차: 새 Gotcha 를 한 곳에 추가하면 전 sibling 스킬 SKILL.md 를 동시에 grep 하여 동일 표현 누락 여부 확인. kaizen Phase 에서 kit 단위 cross-check 를 필수로 수행한다.

Long-Running Skills
§9 Checkpoint Commits · SESSION_LOG · Pre-Sprint Sync

긴 멀티페이즈 스킬(kaizen-orchestrator, create-kit, /docs-site, sprint-level refactor)은 output_token_limit · sandbox 차단 · 백그라운드 에이전트 행업 등으로 중단될 가능성이 구조적으로 높다. 30일 세션 로그 분석에서 평균 세션 길이가 6시간에 달하고, 5+ 세션이 output 토큰 제한으로 잘렸다.

4가지 복원(resumability) 원칙
  • 1Checkpoint commit — 각 페이즈 완료 직후 commit & push. 마지막 한 번에 commit 금지
  • 2SESSION_LOG.md — 체크포인트마다 3-line 상태 append (무엇 완료 · 다음 할 일 · 블로커) → 다음 세션이 이 파일만 읽고 resume
  • 3응답당 300 라인 제한 — 스킬 지침에 명시
  • 4중첩 스킬 호출 간 반환 데이터 최소화 — 토큰 경제상 요약만 반환

적용 예시: kaizen-orchestrator 는 Phase 1~10 을 각 Phase 별 sub-agent + 각자 commit 으로 분할하여 어느 Phase 에서 중단되어도 독립적으로 재개할 수 있다.

Pre-Sprint Sync Check — 병행 작업 충돌 방지

여러 세션·cron·협업자가 같은 레포에서 동시에 자동화를 돌리는 환경에서, 시작 직전 병행 작업 확인을 의무화한다.

git fetch --all git log origin/<base> --oneline -20

인접 파일 동시 수정 흔적이 있으면 reconciliation commit 후 진행. orchestrator 류 스킬은 이 단계를 Step 0 (pre-flight)에 흡수한다.

부적합: 1 파일 변경, 단순 질의, read-only 분석 — noise 가 된다. 적합: kaizen, create-kit, 멀티 Phase orchestrator, sprint-level refactor.

스킬 성장 사이클 — 처음부터 완벽하게 만들지 마라
v0.1: 지시문 3줄 + Gotchas 1개 ↓ Claude가 API 호출 순서 틀림 v0.2: Gotchas에 호출 순서 규칙 추가 ↓ 같은 API 문서를 매번 설명해야 함 v0.3: references/api.md 분리 ↓ 반복되는 검증 로직 발생 v0.4: scripts/validate.sh 추가 ↓ 출력 형식이 매번 다름 v0.5: templates/report.md 추가

스킬은 문서가 아니라, 에이전트의 실패를 관찰하며 경험치를 쌓는 살아 있는 시스템이다.

Cross-Surface Parity
§11 원칙 전수성 — 12 항목 parity 체크리스트

지난 kaizen 사이클에서 §3.5 계약 모호성 방지 원칙 이 이 가이드에만 추가되고 agent-design-guide 에 전수되지 않아 design-kit PH-01 REJECT 가 발생했다. 가이드 레벨의 변경이 파생 산출물로 자동 전파되지 않는 구조적 공백을 메우기 위한 체크리스트다.
