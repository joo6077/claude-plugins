Structure
파일이 아닌 폴더로 설계하라

스킬은 마크다운 파일 하나가 아니라 폴더 단위로 설계한다. 점진적 공개(Progressive Disclosure): 메인 MD에는 개요와 파일 목록만, 상세는 별도 파일로 분리한다.

폴더 구조 (밀키트 비유)
my-skill/ ├── my-skill.md # 개요 + 파일 목록 ├── references/ # API 문서, 코드 스니펫 │ └── api.md ├── scripts/ # 헬퍼 함수, 검증 스크립트 │ └── validate.sh └── templates/ # 출력 템플릿 └── report.md Progressive Disclosure
3-레벨 로딩 시스템

Level 1 — Metadata (~100단어, 항상 시스템 프롬프트에 상주): name + description

Level 2 — SKILL.md body (스킬이 트리거될 때 로드): 핵심 지침과 워크플로우. 500라인 미만 유지.

Level 3 — Bundled resources (필요할 때만 읽음): scripts/, references/, assets/

Token Budgets
Reference 파일은 1-level deep (필수)

Claude는 참조 파일이 다른 참조 파일에서 다시 링크되어 있을 때 head -100으로 일부만 미리보는 경향이 있어 정보 누락이 발생한다. 모든 reference는 SKILL.md에서 직접 링크되어야 한다. 100라인을 넘는 reference 파일에는 상단에 Table of Contents 포함.

Avoid Deeply Nested References
Archetypes
스킬 9가지 유형 — 하나에 명확히 속해야 한다

Anthropic이 내부 스킬 수백 개를 분석하여 발견한 패턴. 좋은 스킬은 하나의 유형에 명확히 속하고, 나쁜 스킬은 여러 유형에 걸친다.

1
라이브러리 레퍼런스
내부 라이브러리 사용법 및 함정 정리
2
제품 검증
Playwright 등 도구로 코드 자동 확인
3
데이터 조회
모니터링/분석 스택 연결
4
비즈니스 자동화
스탠드업 리포트, 위클리 리캡
5
코드 스캐폴딩
보일러플레이트 자동 생성
6
코드 리뷰
스타일 강제 또는 자동 리뷰
7
CI/CD
PR 모니터링 및 자동 롤백
8
런북(Runbook)
장애 시 자동 조사 및 보고서
9
인프라 운영
리소스 정리 및 비용 분석
Gotchas
Gotchas — 스킬에서 가장 가치 있는 섹션

Claude가 반복적으로 실패하는 지점을 모아 놓은 목록이다. 완벽한 지시문에도 Claude는 예상치 못한 실수를 한다. 신입 사원에게 매뉴얼보다 선배의 "이거 조심해" 조언이 더 유용한 것과 같다.

Gotchas 추가 흐름
Claude가 실수 → 실수 패턴 식별 → Gotchas에 한 줄 추가 → 다음부터 같은 실수 방지

대부분의 스킬은 몇 줄의 지시문 + 하나의 Gotchas로 시작하여 점진적으로 성장한다.

QA Name Matching
§3.5 QA 계약과 1:1 매칭되는 이름을 사용하라

스킬이 정의하는 카테고리, 필드, 섹션 이름은 QA 계약(Sprint Contract)에서 그대로 재사용된다. 이름이 어긋나면 평가자가 해석해야 하고 해석이 엇갈리면 REJECT가 발생한다.

Bad — 스킬과 계약 이름이 다름
스킬: "Anatomy 섹션 — 필수 파트: Header, Body, Footer" 계약: "SK-05: 레이아웃 구조 확인 (헤더/바디/푸터 포함 여부)"

"레이아웃 구조"가 Anatomy를 가리키는지 불명확.

Good — 스킬과 계약 이름이 일치
스킬: "Anatomy 섹션 — 필수 파트: Header, Body, Footer" 계약: "SK-05: Anatomy 섹션 확인 — Header, Body, Footer 필수 파트 포함 여부"
Verification
§3.6 검증 가능한 성공 기준 + Rule-by-Rule Audit

스킬이 산출물을 생성할 때 Claude가 스스로 결과를 검증할 수 있는 기준을 포함해야 한다. 검증 기준 없이 Claude는 "그럴듯해 보이지만 실제로는 동작하지 않는" 결과를 만든다.

스킬 유형별 검증 기준
스킬 유형검증 기준 예시
코드 스캐폴딩생성 후 analyze 실행, 워닝 0개
코드 리뷰지적 사항마다 파일:라인 근거 필수
계약 생성모든 조건이 PASS/FAIL 이진 판정 가능한지 자가 검증
데이터 조회쿼리 결과가 비어 있으면 쿼리 자체를 재검증
Rule-by-Rule Audit Before Completion

Claude는 리팩터링/대량 편집 시 규칙에 이미 기재된 위반을 놓치고 사용자가 지적해야 비로소 고치는 패턴을 반복한다. 스킬이 규칙 리스트를 보유할 경우, 완료 선언 전에 규칙별 1:1 대조 패스를 강제해야 한다.

Bad
편집 완료 → 사용자가 놓친 규칙 지적 → 반복
Good
편집 → 규칙 체크리스트 전수 대조 → 위반 발견 → 수정 → 완료
Description
디스크립션은 트리거 조건이다 — frontmatter 규칙

스킬의 description 필드는 사람을 위한 요약이 아니라 Claude가 스킬을 선택하는 트리거 조건이다. Claude는 세션 시작 시 모든 스킬의 메타데이터를 시스템 프롬프트에 pre-load하며, 이 값 하나로 100개 이상의 스킬 중 어느 것을 로드할지 판단한다.

name 필드 규칙

최대 64자. 소문자 + 숫자 + 하이픈만 허용. XML 태그 금지. anthropic, claude 포함 불가. gerund form 권장: processing-pdfs, analyzing-spreadsheets. helper, utils, tools 같은 모호한 이름 금지.

description 필드 규칙

최대 1024자. 비어 있을 수 없음. XML 태그 금지. 반드시 3인칭으로 작성 — 1인칭("I can help...") 또는 2인칭("You can use this...")은 시스템 프롬프트에 주입되었을 때 관점 불일치로 discovery 실패를 일으킨다.

Writing Effective Descriptions
Bad — 기능만 설명
description: 배포 관련 스킬

트리거 약함. Claude가 언제 써야 하는지 알 수 없음.

Good — 트리거 맥락까지 나열
description: > Deploys services to production and verifies deployment status. Use when the user requests production deployment, PR merge checks, or asks to "deploy", "ship", or "roll out" a service.
트리거 키워드 중복 방지 — set intersection + substring 검사

플러그인이 여러 스킬을 포함할 때, description의 트리거 키워드는 두 가지 검사를 모두 통과해야 한다: ① Set intersection이 공집합 ② Substring containment도 공집합. 단순 Grep은 부분문자열 중복을 놓치므로 정규식 추출 후 두 검사를 모두 수행해야 한다.

Bad — substring 위반 (RE-02 REJECT)
react-feature: "API 연동 화면을 생성" react-api: "API 연동 시 Clean Arch" → "API 연동"이 부분문자열 → 배타성 위반
Good — 키워드 완전 분리
react-feature: "Clean Arch 4계층 복합 생성" react-api: "datasource→repository 단일 레이어"
Degrees of Freedom
§5.5 자유도를 태스크에 맞춰라 + L1/L2/L3 충돌 해결

스킬의 구체성 레벨은 태스크의 취약성(fragility)과 가변성(variability)에 맞춰야 한다. QA 평가 깊이 L1/L2/L3과 이 자유도 개념을 혼동하면 안 된다.

자유도형식사용 시점
High freedom텍스트 지침여러 접근이 유효, 문맥에 따라 판단, 경험 기반 heuristic
Medium freedom파라미터 있는 pseudocode/script선호 패턴이 있으나 일부 변형 허용
Low freedom파라미터 없는 정확한 명령취약한 작업, 일관성 필수, 정확한 순서 필요
Enumerate-before-Act — Low-freedom 영역의 고정 규율

토큰 네이밍, Figma 컴포넌트 식별, 스펙 수치, 계약 카테고리 ID 같은 low-freedom 영역은 편집 전 반드시 enumerate-before-act를 적용한다: 기존에 존재하는 토큰/옵션/스펙을 전부 목록화 → 대상 후보를 1-N 인덱스로 나열 → 지목된 항목을 확인 후 편집 시작.

Evaluation-Driven
§8.5 평가 먼저, 문서 나중 — Evaluation-Driven Development

스킬 작성의 기본 순서는 문서 먼저가 아니라 평가(eval) 먼저다. 존재하지 않는 문제를 문서화하지 않기 위함이다.

공식 권장 개발 루프 (5단계)
  • 1Gap 식별: 스킬 없이 대표 태스크를 Claude로 실행해 실패 지점을 기록
  • 2Eval 생성: 이 gap을 검증할 최소 3개 시나리오 작성
  • 3Baseline 측정: 스킬 없는 상태에서 Claude의 성능 측정
  • 4최소 지침 작성: gap을 해결할 만큼의 최소한의 본문만 작성
  • 5반복: eval 실행 → baseline 대비 → 리팩터링
Build Evaluations First
Advanced Patterns
§8.6 MCP Fully-Qualified Name · §8.7 Code Examples · §8.8 Sibling Consistency

v1.3.0 카이젠에서 추가된 고급 원칙. Code Examples 품질 규칙은 react-kit DG-01/DG-02 REJECT에서 귀납했다.

§8.6 MCP 도구 — Fully-Qualified Name 필수
Bad
Use the `bigquery_schema` tool
Good
Use the `BigQuery:bigquery_schema` tool

형식: ServerName:tool_name. 서버 prefix 없으면 Claude가 도구를 찾지 못하거나 잘못된 서버를 호출할 수 있다.

§8.7 Code Examples — 3원칙

① 모든 fenced code block에 언어 힌트 필수 — bare fence(``` 단독) 금지
② 코드 템플릿 내부에 TODO/FIXME/미완성 placeholder 금지
③ 인용/모조 코드와 실행 코드의 구분 명확 — 예시 블록은 text로, 생성 블록은 해당 언어로

검증법: rg -n '^```\s*$' file으로 bare fence 탐지, rg -n 'TODO|FIXME' file으로 placeholder 잔존 탐지.

§8.8 Sibling-Skill Principle Consistency — H-01/H-03 재발 방지

하나의 kit 내 동일 계열 스킬(init/feature/api/service 등)에 공통으로 적용되는 원칙은 모든 sibling SKILL.md의 Gotchas에 동일한 표현으로 등장해야 한다.

Bad — 비대칭 지식
rust-service: ["Composition Root", "domain event"] rust-api: ["... (Composition Root 누락)"] rust-init: ["... (domain event 누락)"]
Good — 전 sibling 동일 표현
rust-service: ["Composition Root", "domain event"] rust-api: ["Composition Root", "domain event"] rust-init: ["Composition Root", "domain event"]

운영 절차: 새 Gotcha를 한 곳에 추가하면 전 sibling 스킬 SKILL.md를 동시에 grep하여 동일 표현 누락 여부 확인.

Long-Running & Parity
§9 Long-Running Skills + §11 Cross-Surface Parity

긴 멀티페이즈 스킬은 중단 복원 가능성(resumability)을 설계 시점부터 원칙으로 삼는다. 또한 스킬 설계 가이드가 개정되면 agent-design-guide · contract-design-guide · qa-evaluation-guide에 대응 원칙이 있는지 체크한다.

Long-Running Skills — 4가지 복원 원칙
  • 1Checkpoint commit — 각 페이즈 완료 직후 commit & push. 마지막 한 번에 commit 금지
  • 2SESSION_LOG.md — 체크포인트마다 3-line 상태 append (무엇 완료 · 다음 할 일 · 블로커)
  • 3응답당 300라인 제한 — 스킬 지침에 명시
  • 4중첩 스킬 호출 간 반환 데이터 최소화 — 토큰 경제상 요약만 반환
