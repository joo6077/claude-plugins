Foundation
§1 스킬은 파일이 아니라 폴더다

스킬은 마크다운 파일 하나가 아니라 폴더 단위로 설계한다. Claude 는 폴더를 탐색하고 필요한 파일만 골라 읽을 수 있어서, 메인 파일에 모든 정보를 넣는 순간 컨텍스트가 과부하된다. 밀키트 비유가 정확하다 — 레시피(지시문)뿐 아니라 재료(레퍼런스)와 도구(스크립트)까지 상자에 담되, 무엇이 들었는지 목록을 겉면에 적어 둔다.

폴더 레이아웃
my-skill/ ├── SKILL.md # 메인 지시문 (개요 + 파일 목록) ├── references/ # API 문서, 코드 스니펫 │ └── api.md ├── scripts/ # 헬퍼 함수, 검증 스크립트 │ └── validate.sh └── templates/ # 출력 템플릿 └── report.md Skill Authoring Best Practices — Claude API Docs
왜 폴더인가
  • Claude 가 폴더를 탐색하고 필요한 파일만 선택적으로 읽는다
  • 메인 파일에 다 넣으면 컨텍스트가 과부하된다
  • 점진적 공개 — 메인 MD 에는 개요와 파일 목록만, 상세는 별도 파일로
  • 반복되는 참조가 생기면 references/, 반복 로직이 생기면 scripts/

Archetypes
§2 스킬 11 가지 유형 — 10·11 은 본 레포 운영 경험에서 추가됐다

Anthropic 이 내부 스킬 수백 개를 분석해 9 가지 유형을 식별했다. 좋은 스킬은 하나의 유형에 명확히 속하고, 나쁜 스킬은 여러 유형에 걸친다. 여기에 이 레포 운영에서 관측된 2 종을 더해 11 종을 쓴다 — 10 은 긴 세션의 truncation 환경에서 lifecycle 스킬이 별도 카테고리로 식별된 것(2026-05), 11 은 탐색이 발산해 산출물이 수십 개로 불어나고 변주끼리 구별되지 않는 실패가 반복 관측된 것(2026-08 · 글로벌 REJECT UI-04)이다.

다른 유형과 달리 산출물 개수 자체가 실패 모드이기 때문이다. 이 목록은 체크리스트로 써서 팀에 아직 없는 스킬 유형을 점검하는 용도이기도 하다.

Gotchas
§3 가차스가 스킬에서 가장 가치 있는 섹션이다

Claude 는 코딩을 이미 잘 안다. 파이썬 API 호출법 같은 일반 지식은 스킬에 불필요하다. 스킬에 담아야 할 것은 Claude 가 추론만으로 절대 알 수 없는 정보 — 즉 반복적으로 실패하는 지점이다.

가차스 한 줄의 형태
## Gotchas - 우리 빌링 립은 이 함수 호출 전에 반드시 tenant_id 를 먼저 설정해야 한다

신입 사원에게 매뉴얼보다 선배의 "이거 조심해" 조언이 더 유용한 것과 같다. 대부분의 스킬은 몇 줄의 지시문 + 하나의 가차스로 시작해 점진적으로 성장한다.

skill-creator SKILL.md — anthropics/skills

Claude 가 실수
  ↓
실수 패턴 식별
  ↓
Gotchas 에 한 줄 추가
  ↓
다음부터 같은 실수 방지

완벽한 지시문에도 Claude 는 예상치 못한 실수를 한다. 그 실수를 관찰해 한 줄씩 쌓는 것이 스킬을 키우는 유일한 방법이다.

Naming
§3.5 QA 계약과 1:1 매칭되는 이름을 써라

스킬이 정의하는 카테고리·필드·섹션 이름은 Sprint Contract 에서 그대로 재사용된다. 이름이 어긋나면 평가자가 "이 조건이 어느 항목에 해당하는지" 해석해야 하고, 해석이 엇갈리면 REJECT 또는 모호한 PASS 가 발생한다.

Bad — 스킬과 계약의 이름이 다름
스킬 본문: "Anatomy 섹션 — 필수 파트: Header, Body, Footer" 계약 조건: "SK-05: 레이아웃 구조 확인 (헤더/바디/푸터 포함 여부)"

평가자가 SK-05 를 검증할 때 "레이아웃 구조" 가 Anatomy 를 가리키는지 불명확하다.

Good — 이름이 그대로 재사용됨
스킬 본문: "Anatomy 섹션 — 필수 파트: Header, Body, Footer" 계약 조건: "SK-05: Anatomy 섹션 확인 — Header, Body, Footer 필수 파트 포함 여부"

스킬 본문의 필드명을 계약 작성 시 그대로 복사하여 재해석 여지를 없앤다.

  • ✓스킬에 카테고리 ID(SK-xx, CD-xx 등)를 정의했으면 계약 조건에도 동일 ID를 쓴다
  • ✓스킬을 수정해 이름이 바뀌면 기존 계약 템플릿도 함께 갱신한다
Verification
§3.6 검증 가능한 성공 기준을 제공하라

Anthropic 공식 문서가 "가장 레버리지가 큰 단 하나" 로 꼽는 원칙이다 — Give Claude a way to verify its work. 검증 기준 없이 Claude 는 "그럴듯해 보이지만 실제로는 동작하지 않는" 결과를 만든다. 사용자가 유일한 피드백 루프가 되면 모든 실수에 사용자의 주의가 필요해진다.

스킬 유형검증 기준 예시
코드 스캐폴딩생성 후 commands.analyze 실행, 워닝 0 개 확인
코드 리뷰지적 사항마다 파일:라인 근거 필수
계약 생성모든 조건이 PASS/FAIL 이진 판정 가능한지 자가 검증
데이터 조회쿼리 결과가 비어 있으면 쿼리 자체를 재검증

Rule-by-Rule Audit Before Completion — 완료 선언 전 규칙 전수 대조

Claude 는 리팩터링·대량 편집 시 규칙에 이미 기재된 위반을 놓치고 사용자가 지적해야 비로소 고치는 패턴을 반복한다. 스킬이 규칙 리스트(Gotchas, anti-patterns, contract categories, style migrations)를 보유하면, 완료 선언 전에 규칙별 1:1 대조 패스를 강제한다.

Bad — N 회 왕복
Claude 편집 완료 → 사용자가 놓친 규칙 지적 → Claude 수정 → 사용자가 또 발견 → 반복…

insights 인용: "Claude fixes some issues, you point out missed ones, Claude fixes those, you find more."

Good — 1 review + 1 execution
Claude 편집 → 규칙 체크리스트 전수 대조 → 위반 목록 발견 → 수정 → 완료 선언

"그 외에도 혹시 놓친 규칙이 있는가?" 를 1 회 더 스스로 묻는 meta-audit 까지 포함한다.

Pre-Edit Batch Audit — 편집 시작 전 위반 전수 enumerate

Rule-by-Rule Audit 이 완료 시점의 안전망이라면, Pre-Edit Batch Audit 는 편집 시작 시점에 같은 규칙 리스트를 능동 적용한다. 두 패스가 짝을 이뤄야 N 회 round-trip 이 "1 review + 1 execution" 으로 축약된다.

적용 시점

리팩터링·대량 편집(3+ 파일, 1+ 규칙군) 시작 전, 대상 파일 전수를 읽어 모든 적용 규칙 위반을 enumerate 한 체크리스트를 사용자에게 제시하고 승인받는다.

항목당 3 요소
  • (a) 파일/라인 근거
  • (b) 위반 규칙 식별자
  • (c) 권장 조치
false-dichotomy 도 대상

Stack vs Column, Service vs UseCase, widget extend vs new 같은 아키텍처 선택도 enumerate 대상이다. 옵션 A/B/C 를 모두 보여주고 trade-off 를 명시한 뒤 선택받는다.

본 원칙은 high-freedom 영역(아키텍처·디자인 선택)과 low-freedom 영역(린트 규칙·토큰 마이그레이션) 양쪽 모두에 적용된다 — §5.5 Enumerate-before-Act 가 low-freedom 만 다룬 것을 확장한 것이다.

Scope-Bound Edits — 허락 없는 삭제·디자인 선택 금지

Pre-Edit Batch Audit 가 시작 시점의 enumerate 라면, 본 원칙은 모든 편집 동안의 boundary enforcement 다. 사용자가 X 를 요청했으면 X 만 하고, X 와 인접해 보이는 Y/Z 는 명시적 승인 없이 절대 건드리지 않는다.

가장 빈번한 위반 5 종
  • 리팩터링 중 "보기 안 좋아 보이는" 인접 코드를 silently 정리
  • 본 작업 범위 외 파일을 "안 쓰는 듯해서" 삭제
  • 시안이 명시되지 않은 영역에서 임의로 컬러·spacing·네이밍 결정
  • 범위 밖 패키지를 "겸사겸사" 업그레이드·제거
  • main 직접 push, force push, branch 삭제
Hard-stop actions — 매번 명시 승인
file deletionpackage removal branch deletionforce push main pushschema migration secret rotation

자동화 훅(PostToolUse 등)으로 하는 결정론적 수정(lint/format)은 OK 다. 하지만 의미적 변경은 Hard-stop 대상이다.

Bad
사용자 "X 함수 수정해" → Claude X 수정 + 옆 Y 도 정리 + Z 파일 삭제 + main push
Good
사용자 "X 함수 수정해" → Claude X 만 수정 → 인접 개선점 발견 → 별도 list → 사용자 승인 후 처리

Enforcement 3 등급 — 원칙을 "어떤 강도로" 구현할지 먼저 정하라

E1 · 문장 규칙

Gotchas / Process 의 서술문

보장 수준은 통계적 개선만. 최초 도입이고 위반 이력이 없을 때 쓴다.

E2 · 체크리스트 아티팩트

응답에 복사해 채우는 체크리스트 · 검증 전 생성하는 계획 파일

흔적이 남아 사후 대조 가능(여전히 자기보고). 다단계 워크플로우, 위반 1~2 회 재발.

E3 · 결정론적 게이트

스크립트 / 훅 / CI — LLM 호출 없는 순수 판정

per-run 보장. 비가역·신뢰 손상 영역, 3 회 이상 재발.

등급 승급 규칙

같은 위반이 2 회 이상 재발하면 E1 → E2, 3 회 이상이거나 비가역 변경·사용자 신뢰 손상이 걸리면 E2 → E3 로 올린다. 재발했는데 같은 등급에서 문장만 다시 다듬는 것은 개선이 아니다.

E3 게이트의 정의: g(입력, 현재상태) → {통과, 거부} 인 순수 함수. (a) 상태를 읽기만 하고 바꾸지 않는다 (b) LLM 을 호출하지 않는다 (c) 행위 직전에 실행된다 (d) 거부 시 구조화된 사유를 돌려준다. 논문 실측에서 게이트 4 개 도입만으로 성공률 29.6% → 42.0%, k=5 반복 신뢰도(pass_k)는 8.0% → 26.0% 로 올랐다.

초기 등급 선택 기준 — 위반 이력이 없을 때 무엇으로 시작하는가

시작 등급이런 성격의 규칙
E1선호·휴리스틱·저위험 규칙. 위반해도 되돌리기 쉽고, 판정에 문맥 해석이 필요하다

E3기계 판정이 가능하고 위반 비용이 큰 규칙, 또는 E2 를 붙였는데도 반복 위반되는 규칙

등급을 적지 않은 원칙은 미완성이다. 등급을 명시하지 않으면 나중에 그 원칙이 재발했을 때 "무엇에서 무엇으로 올릴지" 를 판정할 수 없어 결국 문장만 다시 다듬게 된다 — 그것이 등급 체계를 도입한 이유를 무효화하는 실패 경로다.

1. 증거 블록 의무

산출물을 만드는 스킬은 완료 보고에 실행한 명령과 그 출력(또는 파일:라인)을 포함한다. "동작한다", "정상 렌더링된다" 같은 서술만으로 완료를 선언하지 않는다.

2. 증거는 자기보고가 아니라 도구 출력

스스로 "확인했다" 고 쓰는 문장은 증거가 아니다 (AUROC 0.54~0.65).

3. 검증 불가 시 [미검증] 명시

인프라 부재·도구 미설치·런타임 미실행으로 검증이 불가하면 조용히 넘기지 말고 [미검증] 마커와 사유 한 줄을 붙인다. 미검증 2 건 이상이면 완료가 아니라 부분 완료로 보고한다. 마커·임계값은 agent-design-guide §10 과 동일 규약을 쓴다.

4. 렌더 가능한 산출물은 렌더 결과를 증거로

UI·문서·차트는 렌더 → 캡처 → 대조까지 수행한다. 단 스냅샷/캡처가 비어 있으면 그것은 PASS 증거가 아니라 검증 실패 신호다 — 빈 결과를 "문제 없음" 으로 읽는 것이 실제 사고 형태였다(빈 카탈로그를 MCP 스냅샷 근거로 "정상 렌더링" 이라 반복 주장).

5. 피드백 루프를 닫는다

검증 스크립트가 있으면 실행 → 실패 시 수정 → 재실행을 반복하고, 스킬 본문에 "검증을 통과하기 전에는 다음 단계로 진행하지 않는다" 를 명시한다.

Degrees of Freedom
§5.5 자유도를 태스크의 취약성에 맞춰라

스킬의 구체성 레벨은 태스크의 취약성(fragility) 과 가변성(variability) 에 맞춘다. 공식 비유가 정확하다 — Claude 를 경로를 탐색하는 로봇으로 생각하라. 양옆이 낭떠러지인 좁은 다리면 안전한 길이 하나뿐이므로 Low freedom(정확한 명령), 위험 없는 열린 들판이면 여러 길이 성공하므로 High freedom(일반 방향만 제시)이다.

Enumerate-before-Act — Low-freedom 영역의 고정 규율

토큰 네이밍, Figma 컴포넌트 식별, 스펙 수치, 디자인 시스템 컬러, 계약 카테고리 ID 같은 low-freedom 영역은 편집 전 반드시 enumerate-before-act 를 적용한다. Low-freedom 영역에서 "근사치로 추정" 또는 "아마도 이게 맞을 것 같다" 는 3+ iteration 재작업의 가장 큰 원인이다. 한 번의 enumerate 로 N 번의 왕복이 방지된다.

Step 1

지목된 항목을 최종 확인한 뒤 편집을 시작한다.

Counterpart Enumeration — 변경의 반대편을 열거하라

Enumerate-before-Act 와 Pre-Edit Batch Audit 는 둘 다 변경 대상 파일 안을 훑는다. 그런데 반복 관찰된 실패는 대상 파일이 아니라 그 변경을 소비하는 반대편에서 났다 — 서버 API 계약을 바꾸고 클라이언트를 같은 스프린트에 반영하지 않는 형태다. UTC 직렬화 버그도 같은 계열이며, 사용자가 "당연히 클라까지 바꿔야지" 로 매번 개입해야 했다.

적용 대상 (하나라도 건드리면 필수)
  • API 계약 / 엔드포인트 시그니처 / 상태 코드
  • 직렬화 포맷 — JSON 스키마, 날짜·타임존 표현, enum 값, null 허용 여부
  • 공유 모델 · 공용 타입 · 생성 코드(OpenAPI, protobuf, codegen 산출물)
  • 공개 함수 시그니처 · 이벤트 페이로드 · DB 스키마
절차 3 단계
  • 편집 착수 전, producer 면과 consumer 면 파일을 양쪽 다 경로로 열거. 소비면을 못 찾으면 grep 으로 찾고, 그래도 없으면 "소비자 없음" 을 근거와 함께 명시한다 — 추측으로 넘어가지 않는다
  • 열거 결과를 계획 아티팩트(체크리스트 또는 계약 조건)로 남긴다. E2 이상 — 문장 다짐으로 처리하지 않는다
  • 한 스프린트에서 양쪽을 다 못 바꾸면 남는 쪽을 [미검증] 이 아니라 명시적 미완 항목으로 보고한다
Create verifiable intermediate outputs — Claude API Docs 
Bad:  서버 응답 필드 rename → 서버 코드만 수정 → "완료" → 클라이언트 런타임 파싱 실패
Good: 서버 응답 필드 rename → producer 1 파일 + consumer 3 파일 경로 열거 → 체크리스트 합의 → 4 파일 일괄 수정

부적합: 소비자가 존재할 수 없는 순수 내부 리팩터링(private 함수 본문, 로컬 변수명). 이 경우 열거 단계는 noise 다.

왜 축 선언만으로는 부족한가

실측: 글로벌 REJECT UI-04 는 계약이 4 축(버블 컨테이너 유무 / 정렬 컬럼 수 / 메타 위치 / 묶음 단위)을 이미 명시했는데도 variant 두 개가 4 축 전부에서 같은 값이었다. 즉 축을 선언해도 구현이 무시한다. 축 값의 상이성이 기계적으로 검사 가능해야 조항이 작동한다. DOE 의 factor / level / design matrix 가 그 형태다 — 입력 factor 와 그 level 을 먼저 정하고, design matrix 로 조합을 제한한다.

조항 5 요소
  • 기본 산출물 상한 3 개. 4 개 이상은 사용자 승인이 선행되어야 한다
  • primary axis 1 개 고정, 필요하면 secondary axis 1 개까지. 3 축 이상 동시 변주는 비교 불가능한 산출물을 만든다
  • 각 variant 는 축 값이 서로 달라야 하고 나머지는 constants 로 고정한다. 같은 축 값 조합이 2 개 이상이면 그 세트는 실패다
  • 실행 전에 Variant Matrix 를 만들어 합의한다
  • 요청받지 않은 부대 산출물을 만들지 않는다 — 디자인 시스템, 토큰 파일, 문서, 컴포넌트 라이브러리, scaffold
Design of Experiments — ASQ (factor / level / design matrix)
제약은 탐색을 막지 않고 유도한다

디자인 제약 연구도 같은 방향을 지지한다 — 제약은 탐색을 막는 것이 아니라 특정 방향으로 유도한다. "많이 뽑아 놓고 고르게 하자" 는 수량으로 품질을 대체하려는 시도이며, 실제로는 사용자가 전부 지우게 만든다.

§8.5 Evaluation-Driven Development

스킬 작성의 기본 순서는 문서 먼저가 아니라 평가(eval) 먼저다. 존재하지 않는 문제를 문서화하지 않기 위함이다.

  • Gap 식별 — 스킬 없이 대표 태스크를 실행해 실패 지점 기록
  • Eval 생성 — 이 gap 을 검증할 최소 3 개 시나리오
  • Baseline 측정 — 스킬 없는 상태의 성능
  • 최소 지침 작성 — gap 해결에 필요한 최소 본문만
  • 반복 — eval 실행 → baseline 대비 → 리팩터링
Build evaluations first — Claude API Docs
Trigger Eval Set — 20 개 쿼리

스킬이 준비되면 description 의 트리거 정확도를 측정한다. 20 개 쿼리(should-trigger 8~10 개 + should-not-trigger 8~10 개)를 작성한다.

  • 구체적이고 현실적 (파일 경로, 회사명, URL, 오타 포함)
  • 다양한 표현 (캐주얼/포멀, 간접적 언급)
  • near-miss 도 포함 (인접 도메인, 모호한 표현)

§8.7 Code Examples — Fenced Block 품질
  • 모든 fenced code block 에 언어 힌트 필수. bare fence 금지. 설명용이면 text 또는 pseudo
  • 코드 템플릿 내부에 TODO / FIXME / 미완성 placeholder 금지 — 사용자가 채워야 하는 부분은 // 여기에 비즈니스 로직 구현 같은 명시적 주석으로 전환
  • 인용/모조 코드와 실행 코드의 구분 명확

검증법: rg -n '^```\s*$' <file> 로 bare fence, rg -n 'TODO|FIXME' <file> 로 placeholder 잔존 탐지. 둘 다 0 건이어야 한다.

§8.8 Sibling-Skill Principle Consistency — 형제 스킬 간 원칙 일관성

하나의 kit 내 동일 계열 스킬(init / feature / api / service 등)에 공통 적용되는 원칙은 모든 sibling SKILL.md 의 Gotchas 에 동일한 표현으로 등장해야 한다. 누락은 "일부 스킬은 원칙을 알고 있지만 다른 스킬은 모른다" 는 비대칭 지식 상태를 만들어, 사용자가 어떤 스킬로 들어오느냐에 따라 완성도가 달라진다.

Bad — 원칙 비대칭 (rust-kit H-01/H-03 REJECT)
rust-service: ["Composition Root 단일화 …", "domain event + outbox …"] rust-api : ["… (Composition Root 누락) …"] rust-init : ["… (domain event 누락) …"]
Good — 전 sibling 에 동일 표현
rust-service: ["Composition Root 단일화 원칙", "domain event + outbox"] rust-api : ["Composition Root 단일화 원칙", "domain event + outbox"] rust-init : ["Composition Root 단일화 원칙", "domain event + outbox"]

운영 절차: 새 Gotcha 를 sibling 중 한 곳에 추가하면 전 sibling SKILL.md 를 동시에 grep 하여 동일 표현 누락 여부를 확인한다. kaizen Phase 에서 kit 단위 cross-check 는 필수다.

긴 멀티페이즈 스킬(kaizen-orchestrator, create-kit, /docs-site, sprint-level refactor)은 output_token_limit · sandbox 차단 · 백그라운드 에이전트 행업으로 중단될 가능성이 구조적으로 높다. 30 일 세션 로그 분석에서 평균 세션 길이가 6 시간에 달했고 5+ 세션이 output 토큰 제한으로 잘렸다.

  • Checkpoint commit — 각 페이즈 완료 직후 commit & push
  • SESSION_LOG.md — 체크포인트마다 3-line 상태 append (무엇 완료 · 다음 할 일 · 블로커)

  • 중첩 스킬 호출 간 반환 데이터 최소화 — 토큰 경제상 요약만 반환
Pre-Sprint Sync Check — 병행 작업 충돌 방지

여러 세션·cron·협업자가 같은 레포에서 동시에 자동화를 돌리는 환경에서 시작 직전 병행 작업 확인을 의무화한다. 30 일 분석에서 "이미 다른 세션이 같은 작업을 완료했거나 인접 파일을 수정 중" 으로 인한 hours-level 재작업이 반복 식별되었다.

Bad:  세션 시작 → 작업 → commit → push 거부 (다른 세션이 먼저 push) → 충돌 해결로 hours 소모
Good: 세션 시작 → git fetch --all && git log origin/<base> --oneline -20 → 병행 흔적 확인 → reconciliation 또는 progress

부적합: 1 파일 변경, 단순 질의, read-only 분석 — 이 단계는 noise 가 된다. 적합: kaizen, create-kit, 멀티 Phase orchestrator, sprint-level refactor.

Item 7 은 멀티세션 orchestrator 행동에만 관련되어 agent 가이드에 대응이 없다. Item 8 은 hook + agent 협업 패턴으로 agent 가이드 전용. Item 12 는 코드를 생성·수정하는 측의 규율이라 평가자 가이드에 대응 섹션을 두지 않고 계약 조건으로 흡수한다. Item 13 만 성격이 다르다 — 동일 개념 공유가 아니라 이름이 비슷한 다른 개념이라 양쪽 절이 서로를 참조해 용어 혼동을 막는 것이 parity 의 내용이다. Item 14 는 2026-08 사이클 신규. 나머지 (1~6, 9~11, 14) 는 양쪽 모두 존재한다.
