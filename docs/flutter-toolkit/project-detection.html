Flutter Toolkit · SSOT

프로젝트 감지

모든 flutter-toolkit 스킬은 코드 생성이나 명령 실행 전에 프로젝트 환경을 감지한다. 이 단일 기준으로 SDK 명령, Makefile 우선순위, 의존성 플래그, 아키텍처, 코드 관습과 UI 시각 검증 채널을 결정한다.

Step 2b · Monorepo

Makefile 기반 monorepo 감지

프로젝트 루트에 Makefile이 있고 Flutter 관련 타겟(app-run, app-test, app-analyze, app-codegen, app-preflight 등)이 정의되어 있으면 HAS_MAKEFILE = true다. 이 경우 flutter-preflight와 flutter-run 스킬은 $FLUTTER 직접 호출 대신 make <target>을 우선 사용한다.

Makefile을 먼저 쓰는 이유

dart-define-from-file=.dart_defines.json, --observatory-port=8181, launch.json/tasks.json 연동 설정이 Makefile 타겟 한 곳에 모여 있기 때문이다. fvm flutter run을 직접 호출하면 이 설정이 누락되어 앱이 다른 환경으로 기동되거나 디버거가 연결되지 않는다. 이 규칙은 실제 앱 프로젝트 sprint-feedback iter 2 AC-6에 근거한다.

감지 순서

  • 1프로젝트 루트에서 Makefile 존재를 확인한다.
  • 2app-run, app-run-staging, app-run-prod, app-run-profile, app-test, app-analyze, app-fix, app-clean, app-codegen, app-codegen-filter, app-build, app-preflight 중 하나 이상을 찾는다.
  • 3$MAKE = make를 제공한다. Windows에서는 gmake 또는 프로젝트 관습을 우선한다.

집중 관리되는 실행 설정

Step 4 · Architecture

아키텍처 패턴 감지

lib/ 디렉토리 구조를 분석해 ARCH를 정하고, 감지된 구조에 맞는 레이어 규칙을 적용한다.

디렉토리 패턴감지 결과
lib/features/*/data/, lib/features/*/domain/, lib/features/*/presentation/ARCH = clean (Clean Architecture)
lib/features/*/ui/, lib/features/*/view_models/ 또는 lib/*/views/, lib/*/view_models/ARCH = mvvm (MVVM — Flutter 공식 권장)
lib/features/*/이며 data/domain/presentation 없음ARCH = feature_first
lib/src/ 또는 flat 구조ARCH = flat

Clean Architecture 규칙

domain/은 data/와 presentation/을 import하지 않는다. data/는 presentation/을 import하지 않는다. Repository는 interface를 domain에, impl을 data에 분리한다.

MVVM 원칙

감지된 MVVM 구조에는 Flutter 공식 아키텍처 가이드의 레이어 역할을 적용한다.

Flutter 공식 아키텍처 가이드

View ↔ ViewModel

View와 ViewModel은 1:1 관계를 유지한다.

Flutter 공식 아키텍처 가이드

ViewModel

Repository에서 데이터를 받아 UI 상태로 변환하고, Command 패턴으로 액션을 노출한다.

Flutter 공식 아키텍처 가이드

Repository

도메인 모델을 제공하며 캐싱, 에러 처리와 재시도를 담당한다.

Flutter 공식 아키텍처 가이드

Service

최하위 레이어에서 API, 파일, 플랫폼 코드 같은 외부 데이터 소스를 래핑한다.

시각 채널 플래그

HAS_VISUAL_CHANNEL = (VISUAL_CHANNEL != none)

HAS_VISUAL_CHANNEL = false이면 UI 스킬은 완료가 아니라 부분 완료 + [미검증]으로 보고한다.

MCP 도구 이름을 추측하지 마라

프로젝트마다 등록된 서버와 도구 이름이 다르다. 설정 파일에서 확인된 이름만 사용하고, 확인되지 않으면 채널이 없는 것으로 취급한다. 존재하지 않는 도구를 호출한 뒤 실패를 “검증 완료”로 넘긴 경로가 /insights 2026-07-27 Friction #2의 실제 사고 사례다.

Bad · 도구 이름 추측
추정한 MCP 도구 호출
→ 호출 실패
→ "검증 완료"로 보고

실패한 호출은 렌더 증거가 아니다.

Good · 등록 설정 확인
mcpServers 키 읽기
→ 확인된 서버명만 사용
→ 없으면 VISUAL_CHANNEL = none
→ 부분 완료 + [미검증]

검증 채널의 실제 존재 여부와 보고 상태를 일치시킨다.

### 0. 프로젝트 감지

`references/project-detection.md`의 절차를 실행하여 프로젝트 환경을 파악한다.

Gotchas checklist

놓치기 쉬운 감지 규칙

완료 전 원본 절차의 분기 조건을 빠짐없이 확인한다.

  • ✓pubspec.yaml의 name과 environment.sdk를 읽고 $FLUTTER, $DART를 SDK 매니저에 맞게 확정했는가?
  • ✓HAS_MAKEFILE = true일 때 codegen에 app-build나 app-preflight 같은 묶음 타겟을 넣지 않았는가?
  • ✓app-codegen-filter는 사용자가 그 이름을 직접 부른 경우에만 사용하고, codegen 전후 삭제 수를 계속 세는가?
  • ✓기본 fix 뒤에는 git diff --name-only에서 이번에 바뀐 Dart 파일만 골라 생성물을 제외하고 포맷하는가?
  • ✓의존성은 dependencies와 dev_dependencies를 함께 검사하고 필요한 HAS_*가 없으면 설치 안내를 출력하는가?
  • ✓생성 코드가 감지된 ARCH, import, 위젯 베이스, 상태 관리, 네이밍과 라우트 관습을 따르는가?
  • ✓UI 스킬에서 MCP 도구 이름을 추측하지 않고 설정 파일의 mcpServers 키에서 실제 서버명을 확인했는가?
  • ✓VISUAL_CHANNEL = none이면 완료가 아니라 부분 완료 + [미검증]으로 보고하는가?
