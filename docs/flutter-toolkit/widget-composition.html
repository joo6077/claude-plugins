위젯 컴포지션

Stateless/Stateful/HookWidget 선택, 작은 위젯 분해, const, Key, rebuild 최소화를 다룬다.

version 0.1.0 last updated 2026-04-05 5 principles
Principles

다섯 가지 원칙

위젯을 어떤 타입으로 만들고 어떻게 분해할지, rebuild 경계를 어디에 그을지 결정하는 다섯 가지 기본 원칙이다. 각 원칙은 Flutter 공식 문서를 출처로 한다.

01

상태 소유권이 타입을 결정한다

위젯 타입 선택 기준은 "상태 소유권과 lifecycle 필요성"이다. 내부 상태가 없으면 Stateless, 위젯 lifecycle에 묶인 상태가 있으면 Stateful, hooks로 lifecycle을 분해 재사용하고 싶으면 HookWidget.

docs.flutter.dev/ui
02

분해가 성능의 기본 전제

Flutter는 aggressive composition 최적화가 전제다. 작은 위젯으로 분해하는 것이 기본적으로 성능에 유리하다 — 큰 build 메서드보다 쪼개진 서브 위젯이 rebuild 경계를 좁힌다.

docs.flutter.dev/resources/inside-flutter
03

const로 canonical 공유하라

const 생성자를 적극 사용해 동일 위젯 인스턴스를 재사용한다. const 위젯은 element tree에서 canonical하게 공유되어 rebuild 비용이 0에 수렴한다.

docs.flutter.dev/perf/best-practices
04

Key는 semantic identity를 보존한다

Key는 같은 타입 반복 children의 semantic identity를 보존한다. 리스트 재정렬·삽입·삭제 시 state 보존 여부를 결정한다.

api.flutter.dev/Key-class
05

Rebuild 범위를 좁히는 조합

Rebuild 최소화는 setState 범위 축소 + child hoisting + select/selector 조합으로 달성한다. const로 상수화할 수 없는 child는 부모 밖으로 끌어올려 참조 공유로 재사용한다.

docs.flutter.dev/perf/best-practices
Numbers & Boundaries

수치·경계값

Key 사용에 대한 사실 기반 경계 조건. 추측으로 GlobalKey를 남발하지 않도록 한계선을 명확히 해둔다.

항목설명
일반 child의 key 명시적 key가 필요 없다 — 타입과 위치로 충분히 식별된다.
Key 유일성 범위 sibling 범위에서만 유일하면 된다. 트리 전역 유일성은 요구되지 않는다.
GlobalKey 전역에서 유일해야 하며, 매 build마다 재생성하면 안 된다 (보통 State 필드로 보관).
Anti-patterns

하지 말아야 할 것 vs 해야 할 것

현업에서 반복적으로 관찰되는 위젯 컴포지션 실수와 그에 대응하는 올바른 접근을 나란히 비교한다.

Anti-patterns
  • 500줄짜리 단일 build 메서드 — 분해하지 않으면 rebuild 경계가 전체가 된다.
  • 리스트 아이템에 index 기반 key — reorder 시 identity가 무너져 state가 잘못 매핑된다.
  • 모든 위젯에 GlobalKey를 다는 습관 — 메모리·lifecycle 비용이 커지고 hot reload 이슈가 늘어난다.
  • rebuild 원인을 모르는 채 const만 붙이는 습관 — 부모가 rebuild되면 const child는 이미 재사용되므로 이득이 없다.
Preferred
  • 책임 단위로 서브 위젯을 쪼개 rebuild 경계를 좁힌다.
  • 안정적인 도메인 ID(ValueKey/ObjectKey)로 identity를 고정한다.
  • GlobalKey는 정말 전역 참조가 필요한 곳에만 제한적으로 사용한다.
  • rebuild 원인을 먼저 프로파일링하고, const는 그 결과에 근거해서 적용한다.
Gotchas

반복되는 함정

공식 문서에는 묻혀 있지만 프로덕션에서 자주 부딪히는 세부 사항. 체크리스트로 확인하라.

✓

Reorderable 리스트의 findChildIndexCallback. reorder 가능한 리스트에서 findChildIndexCallback을 지정하지 않으면 key가 있어도 상태가 손실될 수 있다 — SliverChildBuilderDelegate의 옵션을 확인하라.

✓

HookWidget은 복잡도를 줄이지 않는다. StatefulWidget을 HookWidget으로 바꿔도 상태의 본질적 복잡도는 줄지 않는다 — 단지 재사용 축이 lifecycle에서 hook으로 옮겨갈 뿐이다. 상태가 복잡하면 먼저 책임 분리부터 검토하라.
