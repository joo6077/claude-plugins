Clean Architecture

Flutter Clean Architecture 레이어 분리, Repository 패턴, UseCase의 적절한 사용, DI 전략, 디렉토리 구조를 실무 관점에서 정리한 리서치 문서.

Principles

다섯 가지 원칙

Flutter 공식 App Architecture Guide와 케이스 스터디가 권장하는 레이어 분리·데이터 흐름·DI 패턴. 각 원칙은 "왜 그렇게 해야 하는가"의 근거 출처를 함께 제공한다.

PRINCIPLE 01

레이어 의존 방향은 Presentation → Domain → Data 단방향

바깥 레이어(UI, Data)가 안쪽 추상화(Domain)에 의존하게 만든다. Flutter 공식 아키텍처 가이드도 UI/Data 분리를 기본으로 두고 Domain layer는 선택적으로 둔다. 반대 방향 의존은 테스트 불가·순환 참조의 원인이 된다.

Flutter App Architecture Guide
PRINCIPLE 02

Repository는 앱 데이터의 source of truth

외부 API/DB/plugin 접근은 Service/DataSource로 분리하고, Repository는 여러 DataSource를 조합하여 도메인 모델을 반환한다. 호출부는 어디에서 데이터가 왔는지 몰라도 된다.

Flutter App Architecture Guide
PRINCIPLE 03

UseCase는 필수가 아닌 선택

복잡한 비즈니스 규칙이 있을 때에만 Domain layer에 둔다. 간단한 CRUD 앱에선 과설계다. 모든 액션에 UseCase를 강제하면 파일 수만 폭발하고, 변경 비용이 오히려 증가한다.

Flutter App Architecture Guide
PRINCIPLE 04

UI는 feature-first, data/domain은 layer-first 혼합

대형 앱에서 가장 실용적인 조합. Flutter 공식 케이스 스터디도 lib/ui/, lib/domain/, lib/data/, lib/routing/으로 분리하여 feature × layer의 매트릭스 탐색을 가능하게 한다.

Flutter Architecture Case Study
PRINCIPLE 05

DI는 get_it 또는 Riverpod 중 하나를 명확히 채택

Widget에서 repository/service를 직접 new하지 않는다. get_it은 service locator, Riverpod은 provider graph 기반. 두 방식을 혼용하면 의존성 추적이 불가능해지므로 프로젝트 단위로 한 가지를 택한다.

Anti-patterns

피해야 할 패턴

레이어 경계가 무너졌을 때 나타나는 전형적 증상들. 코드 리뷰에서 이 패턴이 보이면 리팩토링 대상이다.

안티패턴 문제
Repository가 DTO/DioException/JSON Map을 UI로 노출 transport 세부사항이 UI까지 전파되어 스키마 변경이 전 레이어에 영향
모든 액션마다 UseCase 클래스 강제 파일 수 폭발, 변경 비용 증가, 간단 CRUD에 과설계
feature-first와 layer-first 혼합 규칙 없음 탐색성 붕괴 — 어디에 파일이 있는지 예측 불가
Widget 안에서 repository/service 직접 new 테스트 불가, DI 원칙 위반, mock 주입 불가
Gotchas

실무 주의사항

Clean Architecture를 Flutter에 적용할 때 가장 자주 빠지는 두 함정.

!
Clean Architecture 과설계 주의 작은 앱에 과도한 추상화는 변경 비용을 오히려 증가시킨다. 레이어 수는 비즈니스 복잡도에 비례해야 한다.
!
Riverpod ≠ 아키텍처 분리 상태관리 도구와 Clean Architecture는 별개다. Riverpod을 써도 Domain/Data 경계는 자동으로 생기지 않는다 — 경계는 설계자가 명시해야 한다.
