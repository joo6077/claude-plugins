Scope
적용 대상 스킬 6 종

UI 를 만들거나 고치는 스킬 다섯, 그리고 스킬을 거치지 않은 UI 수정 뒤에 이 규약을 따로 돌리는 flutter-ui-verify 가 대상이다.

flutter-widget

커스텀 위젯 생성. 새로 만드는 위젯이면 기준 캡처 칸에 신규 라고 적는다.

flutter-screen

Screen/Page 위젯 생성 + 라우터 등록. 화면을 가리키는 요청이면 대상은 그 화면의 위젯 파일과 라우트다.

flutter-skeleton

스켈레톤 shimmer 로딩 UI. 빈 화면과 스켈레톤을 혼동하기 가장 쉬운 스킬이다.

flutter-transition

커스텀 페이지 전환 애니메이션.

flutter-responsive

반응형 레이아웃 적용. breakpoint 별 캡처가 필요하다.

flutter-ui-verify

스킬을 거치지 않은 UI 수정 뒤 이 규약을 따로 돌리는 스킬. 화면을 실제로 띄워 편집 전·후 캡처를 대조한다.

Step 0 · 편집 전
무엇을 바꾸는지 먼저 확정한다

편집을 시작하기 전에 다음 6 줄을 응답에 남긴다. 시각 작업은 말이 의도를 충분히 규정하지 못한다.

1

대상

바꿀 위젯을 파일:라인 으로 지목한다 (신규 생성이면 "신규" 라고 명시).

2

바꿀 것 / 바꾸지 않을 것

색상·크기·모션·레이아웃 중 유지할 속성을 열거한다.

3

교체 여부

기존 위젯을 Flutter 기본 위젯이나 다른 컴포넌트로 교체하려면 편집 전에 승인을 받는다.

4

되말하기

사용자 문장을 대상 위젯 이름과 배치로 바꿔 한 문장으로 되말한다. 두 갈래로 읽히면 묻고 시작한다 (예: '추가 칩만 오른쪽 고정' 과 '줄 전체 오른쪽 고정').

5

화면 자체

화면을 가리키는 요청이면 대상은 그 화면의 위젯 파일과 라우트다. 그 화면으로 들어가는 진입점(버튼·칩)이나 화면을 흉내 낸 그림이 아니다. 경로를 밝힌다.

관례 표

같은 역할의 서로 다른 기존 화면 2 개 이상을 Read 해서 그 경로와 함께 표로 남긴다. 칸은 아래 표와 같다.

캡처 점검 목록

기준 캡처와 재캡처마다 아래 넷을 본다. 하나라도 걸리면 그 캡처로 PASS 를 주지 않는다.

1 · 글자 넘침

노랑·검정 줄무늬 경고, 잘린 글자, 뜻밖의 말줄임. 캡처하는 동안의 앱 로그에서 RenderFlex overflowed 도 센다.

2 · 깨진 글리프

네모나 빈칸으로 나온 글자와 이모지. golden·위젯 시험 캡처는 시험용 글꼴로 그려져 글자 모양을 판정할 수 없으니 글자 항목은 실제 앱 캡처로 본다.

3 · 칩·뱃지와 줄 모양

칩·뱃지 모양, 그리고 카드인지 평평한 줄인지를 Step 0 관례 표와 대조한다.

4 · 디버그 겹침

떠 있는 디버그 단추나 디버그 띠가 판정할 자리를 가리는지 본다. 가렸으면 겹친 것을 치우거나 옮긴 뒤 같은 자리를 다시 찍는다.

결함이라 단정하기 전에

잘라낸 조각만 보고 결함이라 단정하기 전에 전체 화면을 한 장 더 찍는다.

넘침은 데이터를 고쳐 재현하지 말고, 기기 글자 크기를 키운 상태로 한 장 더 찍는다 (위젯 시험이면 글자 배율을 키운다).

고장이라 말하기 전에 셋을 확인한다

캡처가 실패해 여기 왔다면 고장이라 말하기 전에 셋을 확인한다. 서버와 도구 이름은 이 문서에 적지 않는다 — 프로젝트 .mcp.json 에서 읽는다 (Step 1 표 3 행).

1

인자 이름

실패한 호출의 인자 이름을 도구 설명의 인자 목록과 대조한다. 틀린 키는 도구 고장이 아니다.

2

붙은 앱이 내 앱인가

도구가 붙은 앱이 내가 띄운 앱인지 확인한다 — 기기 식별값, 연결 정보 파일의 수정 시각, 실행 중인 프로세스를 본다. 여러 세션이 기기나 연결 파일을 나눠 쓰면 남의 앱에 붙어 있을 수 있다.

3

따로 뜨는 층

바텀시트·다이얼로그처럼 따로 뜨는 층의 위젯도 위젯 트리 도구로 한 번 찾아본다. 첫 트리 출력에 없다고 없는 위젯으로 단정하지 않는다.

세 확인의 출력을 먼저 남긴다

세 확인의 출력을 응답에 남긴 뒤에만 아래 [미검증] 절차로 간다. 멈추고 말하라. 추측하지 마라.

[미검증] 절차
1

[미검증] 을 달고 네 칸을 채운다

해당 항목에 [미검증] 을 달고 아래 표의 네 칸을 채운다. 칸의 뜻은 harness/docs/guides/skill-design-guide.md §3.7 5 조항 3 항이 정한다.

2

한 칸이라도 비면 INVALID

네 칸 가운데 하나라도 비면 평가 측이 [미검증:INVALID] 로 센다. 사유 한 줄로 끝내지 않는다.

3

서술로 완료를 대체하지 않는다

"정상 동작합니다" / "정상 렌더링됩니다" 같은 문장은 증거가 아니다.

4

확인 요청을 1~3 개로 좁혀 제시

사용자에게 확인이 필요한 지점을 1~3 개로 좁혀서 제시한다.

칸적는 것
막는 것실행한 명령과 그 실패 출력
시도한 우회위 세 확인과 채널을 확인한 순서. 정말 없으면 없음 — 이유
통제 불가 사유한 문장
재검증 명령채널이 생기면 돌릴 명령
임계값은 canonical 을 따른다

[미검증] 1 건은 경고 명시 후 진행 가능, 2 건 이상이면 완료가 아니라 부분 완료로 보고한다.

Artifact (E2)
Visual Evidence Block — 완료 보고에 복사해 채운다

이 블록이 이 규약의 E2 아티팩트다. 필드는 아홉이다. [미검증] 인 칸은 사유를 그 자리에 쓰지 않고 마지막 미검증 줄의 네 칸으로 보낸다.

## Visual Evidence - 대상: <파일:라인 또는 "신규"> - 유지할 속성: <색상/크기/모션/레이아웃 중 열거> - 채널: <golden | integration_test | mcp:<서버명> | none> - 기준 캡처: <본 것을 요소 단위로 서술 | 신규 | [미검증] — 네 칸은 아래 미검증 줄> - 기준 캡처 파일: <경로 | 신규 | [미검증] — 네 칸은 아래 미검증 줄> - 재캡처: <본 것을 요소 단위로 서술 | [미검증] — 네 칸은 아래 미검증 줄> - 재캡처 파일: <경로 | [미검증] — 네 칸은 아래 미검증 줄> - 대조 결과: <의도한 변경만 발생 | 의도 외 변경 발견 → self-reject N회> - 미검증: N 건 [항목 — 막는 것 — 시도한 우회 — 통제 불가 사유 — 재검증 명령]
Bad

위젯 수정 → "다크 모드에서도 정상적으로 보입니다" (캡처 없음)

스냅샷이 빈 화면 반환 → "렌더링 정상" 으로 해석 → 반복 주장 → 신뢰 손상

hot restart 성공 줄만 보고 "갱신했다" → 재캡처가 기준 캡처와 같은데 확인 안 함

Good

기준 캡처("카드 3행·헤더 '내 그룹'") → 보더만 변경 → 반영 확인(표식: 보더 색) → 재캡처 → 배경색 동일 확인 → 완료

채널 없음 → "[미검증] 막는 것: 채널 감지 출력(golden 0 · integration_test 없음 · .mcp.json 에 캡처 서버 없음) · 시도한 우회: 세 채널을 순서대로 확인 · 통제 불가 사유: 이 환경에 캡처 채널이 없다 · 재검증 명령: 채널을 붙인 뒤 같은 캡처" → 부분 완료로 보고 + 확인 요청 2건 제시

Summary
규약 요약 — Step 0 ~ 4

한 화면에서 확인하는 실행 순서다. 시점 칸이 「편집 전」 인 줄은 완료 직전에 몰아서 할 수 없다.
