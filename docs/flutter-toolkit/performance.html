성능

Flutter 성능 최적화는 rebuild 최소화, const 적극 사용, RepaintBoundary로 repaint hotspot 격리, AutomaticKeepAlive로 스크롤 캐시 관리, ListView.builder로 lazy 렌더, 이미지 캐시 관리, DevTools Performance view로 병목 측정, 무거운 CPU 작업은 isolate로 분리하는 원칙으로 요약된다. 모든 최적화는 frame budget 안에서 build + render를 끝내는 것을 목표로 한다.

Principle 0 · Environment-first

환경을 배제한 뒤에 앱 코드를 의심한다

성능 조사는 앱 코드가 아니라 측정 환경에서 시작한다. 이 순서를 뒤집으면 존재하지 않는 병목을 고치게 된다.

0

측정 환경이 먼저다

공식 문서는 거의 모든 성능 디버깅을 물리 Android/iOS 기기 + profile mode에서 하라고 하며, debug mode 나 simulator/emulator 의 성능은 release 동작을 대표하지 않는다고 명시한다. profile mode 자체가 emulator/simulator 에서 비활성이다.

실측 사례: 18일간 누수된 시뮬레이터 render host 가 호스트 swap 을 포화시켜 프레임이 무너진 것을 앱 코드 최적화에 착수하기 전에 규명했고, 그 덕에 불필요한 리팩터가 통째로 사라졌다.

Principles

앱 코드 최적화 5원칙

환경을 배제한 다음에 적용한다. 측정 우선, build 비용 최소화, lazy 렌더, 선별적 격리, CPU 분리.

1

Profiler-first — 측정 후 최적화

환경을 배제한 다음, DevTools Performance view와 "Track widget rebuilds", "Highlight repaints" 옵션으로 실제 병목을 식별한다. 직감에 기반한 최적화는 대체로 무효하거나 역효과를 낸다.

docs.flutter.dev/perf/best-practices
2

Build 비용을 작게 유지

build 메서드는 자주 호출된다. 비싼 계산, 객체 생성, 리스트 필터링을 build 안에 두지 말고 initState / Notifier / memoization으로 밖으로 빼라. 변하지 않는 서브트리는 const로 만들어 재사용되도록 한다.

docs.flutter.dev/perf/best-practices
3

긴 리스트는 ListView.builder

아이템 수가 많거나 길이가 불확정인 리스트는 반드시 ListView.builder (또는 .separated / .custom)로 lazy 빌드한다. ListView(children: [...])는 모든 아이템을 미리 빌드하므로 메모리와 프레임을 동시에 낭비한다.

api.flutter.dev/flutter/widgets/ListView/ListView.builder.html
4

Repaint 격리와 keep-alive는 선별 적용

잦은 repaint가 일어나는 서브트리는 RepaintBoundary로 감싸 주변 트리의 재페인트를 막는다. 스크롤 아이템 상태를 유지해야 할 때만 AutomaticKeepAliveClientMixin을 적용한다. 둘 다 비용이 있으므로 무조건 씌우면 오히려 메모리와 layer 비용이 증가한다.

api.flutter.dev/flutter/widgets/RepaintBoundary-class.html api.flutter.dev/flutter/widgets/AutomaticKeepAliveClientMixin-mixin.html
5

무거운 CPU 작업은 isolate로

대용량 JSON 파싱, 이미지 디코딩, 암호 연산 같은 CPU bound 작업은 메인 isolate(UI thread)를 막는다. compute() 또는 Isolate.run으로 별도 isolate에 넘겨 UI 프레임을 보호한다.

docs.flutter.dev/perf/isolates

Anti-patterns

안티패턴 vs 권장

프레임 예산을 태우는 대표적 실수들. 첫 항목이 이번 사이클에 추가된 환경 오판이다.

Avoid
  • simulator/emulator 나 debug mode 의 jank 를 앱 코드 결함으로 단정 — 두 환경은 성능 대표성이 없다
  • 크고 정적인 리스트를 ListView(children: [...])로 한 번에 전개
  • 애니메이션 진행 중 Opacity, ClipRect, ShaderMask, saveLayer 남용
  • 모든 탭·모든 리스트 아이템에 AutomaticKeepAlive 일괄 적용
  • Profiler로 원인을 확인하지 않은 채 RepaintBoundary와 isolate를 뿌림
  • 큰 이미지를 원본 해상도 그대로 Image.network로 띄움
Prefer
  • 물리 기기 + profile mode 로 재현하고, 불가능하면 [미검증] 등급으로 남긴다
  • ListView.builder로 lazy 렌더 — 보이는 아이템만 빌드
  • offscreen saveLayer 경로를 피하고 FadeTransition 계열 사용
  • 상태 유지가 필요한 아이템에만 선별적으로 keep-alive
  • DevTools로 병목 확인 후 hotspot에만 RepaintBoundary 배치
  • cacheWidth / cacheHeight로 디코딩 비용 축소
환경을 배제하기 전의 최적화는 존재하지 않는 병목을 고치는 일이다. profile mode 자체가 emulator/simulator 에서 비활성이라는 사실이 이 안티패턴의 근거다.

Snippet

예시 · compute로 CPU 분리

수십 ms 이상 걸리는 CPU bound 작업만 isolate로 넘긴다.

// 큰 JSON 파싱은 메인 isolate를 막는다 — compute로 넘긴다
Future<List<Article>> loadArticles(String jsonStr) async {
  return compute(_parseArticles, jsonStr);
}

// top-level 또는 static 함수여야 한다 (isolate message 제약)
List<Article> _parseArticles(String jsonStr) {
  final raw = json.decode(jsonStr) as List;
  return raw.map((e) => Article.fromJson(e)).toList();
}

// 주의: 작은 작업에 쓰면 직렬화 비용이 더 커서 역효과

lazy 렌더와 이미지 디코딩 비용 축소를 한 번에.

Scrolling

스크롤 성능

리스트·그리드에서 프레임을 지키는 실전 규칙.

  • ListView.builder + itemExtent 조합이 가장 빠른 스크롤 — 프레임워크가 offset 계산을 O(1) 로 처리한다.
  • Scrollbar 위젯은 내부적으로 ScrollController 를 공유한다 — 별도 controller 를 붙이면 conflict.
  • physics: ClampingScrollPhysics() 는 Android 기본, iOS 에서는 BouncingScrollPhysics() — platform 감지가 자동 적용된다.
  • 큰 그리드(100+ 아이템)에서 SliverGrid + addAutomaticKeepAlives: false 로 메모리를 절약한다.
  • cacheExtent 를 늘리면 viewport 밖 아이템을 미리 빌드해 빠른 스크롤 시 빈 화면을 방지하지만, 메모리 사용이 증가한다.
  • 기본 cacheExtent 는 250 logical pixels — 고속 스크롤이 많은 UI 에서는 500~1000 으로 조정 검토.
  • ScrollController.keepScrollOffset 이 true(기본)이면 PageStorage 에 offset 을 저장해 탭 전환 후 복귀 시 위치를 복원한다.
  • 무한 스크롤 리스트에서 NotificationListener<ScrollEndNotification> 으로 스크롤 끝을 감지해 다음 페이지를 로드하는 패턴이 표준이다.
  • 출처: api.flutter.dev/flutter/widgets/ListView-class.html
Memory · Build

메모리 관리와 빌드 성능

런타임 메모리와 개발 빌드 시간은 별개의 예산이다.

메모리 관리

flutter_image_compress 로 업로드 전 이미지 크기를 줄이고, CachedNetworkImage 의 maxWidthDiskCache / maxHeightDiskCache 로 디스크 캐시 크기를 제한한다. WidgetsBindingObserver.didReceiveMemoryWarning 에서 캐시를 클리어한다.

docs.flutter.dev/perf/best-practices

빌드 성능 (개발 시)

--dart-define 으로 환경별 분기 시 각 값 조합이 별도 compilation unit 이 되므로 define 수를 최소화한다. Dart AOT 의 tree-shaking 은 dart:mirrors 사용 시 무력화되므로 리플렉션을 쓰지 않는다. split-debug-info + obfuscate 는 release 빌드 크기를 10~30% 줄인다.

docs.flutter.dev/deployment/obfuscate
Gotchas

Gotchas 체크리스트

isolate 비용, RepaintBoundary 오해, const 연쇄, ImageCache 튜닝, setState 범위.

  • ✓
    Isolate의 spawn/message 비용 compute는 인자와 결과를 복사(직렬화)한다. 작은 작업에 isolate를 쓰면 오히려 더 느리다. 실제로 수십 ms 이상 걸리는 CPU bound 작업에만 사용한다.
  • ✓
    RepaintBoundary는 만능이 아니다 서브트리가 실제로 자주 repaint되고, 부모는 그렇지 않을 때만 이득이 있다. 그렇지 않으면 layer 생성/합성 비용만 추가된다. DevTools의 "Highlight repaints"로 효과를 확인한 뒤 적용한다.
  • ✓
    const 생성자 연쇄 부모에 const를 붙이려면 모든 파라미터가 const여야 한다. 한 곳에서 const가 깨지면 상위까지 전부 재빌드되므로, 디자인 시스템 레벨 위젯부터 const 가능성을 설계에 포함한다.
  • ✓
    ImageCache 재설정 이미지가 많은 앱에서는 PaintingBinding.instance.imageCache의 maximumSize / maximumSizeBytes를 조정해야 한다. 기본값은 모든 앱에 최적은 아니다.
  • ✓
    setState 범위 큰 위젯 전체의 setState 대신 상태가 바뀌는 작은 서브트리로 분리(또는 ValueListenableBuilder / Riverpod select)하여 rebuild 범위를 좁힌다.
  • ✓
    환경 정보 없는 성능 리포트는 근거가 아니다 build mode, 기기, renderer, refresh rate 가 빠진 수치는 재현도 비교도 불가능하다. 8항 체크리스트를 리포트 서두에 붙인다.
Summary

한 문장 요약

환경 배제 → 측정 → hotspot만 격리

먼저 profile mode · 물리 기기 · renderer · refresh rate 를 확정해 환경을 배제한다. 그 다음 Profiler 로 병목을 확인한 뒤에만 RepaintBoundary 와 isolate 를 적용한다. build 는 가볍게, 긴 리스트는 ListView.builder 로 lazy 렌더, const 로 재빌드 범위를 좁힌다. 이미지는 cacheWidth/cacheHeight 로 디코딩 비용을 줄이고, CPU bound 작업은 compute 로 UI thread 를 보호한다. 모든 최적화의 목표는 프레임 예산 안에서 build + render 를 마치는 것이다.
