01

원칙

Hook은 React에서 넘어온 패턴이지만 Dart/Flutter에서는 호출 순서에 더 민감하다. 5개 핵심 원칙을 공식 문서 기준으로 정리한다.

1

Hook은 HookWidget / StatefulHookWidget / HookConsumerWidget의 build 메서드 안에서만, 항상 같은 순서로 호출한다

조건문/반복문 안에서 호출 금지. 호출 순서가 hook의 identity를 결정하므로 순서가 바뀌면 내부 상태 매핑이 전부 어긋난다.

flutter_hooks/use.html
2

HookWidget은 별도 lifecycle 메서드 없이 local state와 disposable 객체를 선언적으로 관리한다

StatefulWidget의 보일러플레이트(initState/dispose)를 대체하는 용도. dispose를 신경 쓸 필요가 없어 leak 위험이 낮다.

HookWidget-class
3

목적별로 훅을 구분해 쓴다

side effect는 useEffect, 비싼 계산 캐싱은 useMemoized, 순수 local ephemeral 값은 useState. 혼용하면 rebuild cost와 예측 가능성이 모두 망가진다.

useEffect
4

AnimationController는 useAnimationController로 생성한다

수동 dispose 없이도 위젯 제거 시 자동 해제된다. 수동 lifecycle 관리 경로를 피할 수 있는 대표적인 훅.

flutter_hooks docs
5

Riverpod과 함께 쓸 때는 HookConsumerWidget을 사용한다

HookWidget + Consumer 중첩은 피한다. 트리가 얕아지고 ref와 hook이 같은 build 범위에 있게 된다.

03

안티패턴

코드 리뷰에서 발견되면 즉시 수정해야 하는 4가지 구조.

!

조건문/반복문 안에서 hook 호출 (if (cond) useState(...)).

!

useEffect에 keys 인자 생략해서 매 build마다 effect가 재실행되는 구조.

!

전역/비즈니스 상태를 useState에 가둬 화면 재진입 시 날아가는 설계.

!

HookWidget이 결국 StatefulWidget보다 코드가 길어지는데도 유지하는 선택.

04

Gotchas

훅 리팩토링 중 가장 자주 터지는 함정 2가지.

✓

Hook 호출 순서가 바뀌면 각 hook의 내부 상태 매핑이 깨진다. 리팩토링 중 훅을 재배치할 때 가장 자주 터지는 버그 포인트다. 조건 분기 안에 훅을 넣었거나, 훅 두 개를 단순히 자리를 바꿨을 때도 동일한 증상이 발생한다.

✓

useMemoized는 캐시지 reactive recompute가 아니다. 값이 keys 변화 없이 바뀔 일이 있다면 useState + useEffect 조합이나 Riverpod provider로 빼라. memo는 deps가 바뀔 때만 다시 계산한다는 사실을 잊으면 "왜 값이 안 갱신되지?" 버그로 이어진다.
