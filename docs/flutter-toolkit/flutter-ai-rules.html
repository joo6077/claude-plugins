Flutter 공식 AI Rules

Flutter 공식 repo docs/rules/rules.md 의 AI rules 요약 + 2026 생태계(Riverpod 3.0 · Freezed 3.0 · go_router · Flutter 3.29+) 정합 노트. flutter-toolkit 스킬이 참조하는 베이스라인 규범.

1 · 위젯 패턴

Flutter 위젯 작성의 핵심 4원칙. 복잡도가 커져도 성능 저하 없이 유지보수되게 만든다.

01

Composition Over Inheritance

복잡한 위젯은 상속이 아닌 합성으로 구성. StatefulWidget 상속 대신 기존 위젯을 감싸 새 위젯 구성.

02

Private Widget Class

헬퍼 메서드(_buildHeader())가 아닌 private Widget 클래스로 추출. const 최적화 유지.

03

Const Constructor

가능한 모든 곳에 const 사용. 리빌드 시 동일 const 객체 재사용으로 성능 향상.

04

Build 분리

큰 build() 메서드는 작은 private 위젯으로 분해. 가독성 + 부분 리빌드 최적화.

flutter/flutter · docs/rules/rules.md
2 · State Management — 공식 우선순위

서드파티 패키지 없을 때. 프로젝트에 Riverpod/Bloc 이 이미 있으면 해당 패턴을 따른다.

  1. ValueNotifier + ValueListenableBuilder — 단일 값
  2. Stream + StreamBuilder — 비동기 이벤트 시퀀스
  3. Future + FutureBuilder — 일회성 비동기
  4. ChangeNotifier + ListenableBuilder — 복합/다중 위젯 상태
  5. MVVM 패턴 — 복잡한 앱
3 · 아키텍처

레이어 분리 — Presentation → Domain → Data → Core. 대규모 프로젝트는 feature-first 구조.

Layer-first (소형)

lib/
├── presentation/
├── domain/
├── data/
└── core/

전체 앱 공통 레이어. 피처 수가 적을 때 간단하고 직관적.

Feature-first (대형)

lib/features/
├── auth/
│   ├── presentation/
│   ├── domain/
│   └── data/
└── home/
    ├── presentation/
    ├── domain/
    └── data/

피처 내부에 레이어. 모듈 독립성 높고 팀 병렬 개발 용이.

MVVM 구조

View ↔ ViewModel (1:1)
     ↔ Repository
     ↔ Service

View 와 ViewModel 1:1 매칭. 테스트성 + 상태 분리 명확.

4 · Do's & Don'ts
✓ Do
  • go_router 내비게이션 (딥링크 · 웹 지원)
  • SOLID 원칙 준수
  • dart:developer.log 사용
  • compute() — 비용 큰 연산은 Isolate
  • 모든 public API 에 /// 문서화
  • dart_format, dart_fix 도구 활용
  • 다양한 화면 크기 테스트
✗ Don't
  • print() 사용 금지 → dart:developer.log
  • build() 내 네트워크 호출 금지
  • 같은 Row/Column 에 Flexible + Expanded 혼용 금지
  • ! 연산자 남용 금지 (non-null 보장된 경우만)
  • 깊은 위젯 트리 중첩 금지 → 합성으로 분해
5 · 코드 생성 · 테스트 · 기타

코드 생성

dart run build_runner build \

테스팅

  • Arrange-Act-Assert 구조
  • Mock 보다 Fake/Stub 선호
  • Unit → Widget → Integration 순서
  • 높은 테스트 커버리지 목표

라인 길이

최대 80자. analysis_options.yaml 에 page_width: 80 설정.

로깅

dart:developer 의 log 사용. DevTools 에서 필터링/레벨 관리 가능. print() 는 프로덕션 로그로 부적합.

6 · 2026 생태계 — Riverpod 3.0

Flutter 공식 rules 외에 2026 기준으로 flutter-toolkit 이 정합해야 하는 변화. 최종 리서치 2026-04-11.

Ref.mounted 공식 패턴

disposed Notifier 접근 시 에러 throw. async 메서드 끝에 if (!ref.mounted) return; 필수.

riverpod.dev · What's New

Notifier 라이프사이클

2.x pseudo-singleton 폐기. Timer/StreamSubscription/Controller 를 Notifier 필드로 유지하면 리소스 누수. 별도 provider + ref.onDispose 로 분리.

riverpod.dev · 3.0 Migration

Legacy Provider 대체

StateNotifierProvider · StateProvider · ChangeNotifierProvider 모두 legacy. 신규 코드는 @riverpod / Notifier 기반.

pub.dev · flutter_riverpod

== 기반 알림 필터링

StreamProvider/StreamNotifier 동등성 이벤트가 listener 에 전달되지 않음. 모델의 operator == / hashCode 정의가 알림 동작 결정. .valueOrNull → .value (dart fix --apply).

10 · 안티패턴 vs 올바른 패턴
✗ Bad — 헬퍼 메서드
Widget _buildHeader() {
  return Container(...);
}

리빌드마다 새 Container 생성. const 최적화 불가.

✓ Good — Private Widget
class _Header extends StatelessWidget {
  const _Header();
  @override
  Widget build(BuildContext c) =>
    Container(...);
}

const 인스턴스 재사용. 트리 리빌드 최적화.

✗ Bad — print()
print('Error: $err');

프로덕션 로그 레벨 · 필터링 불가. DevTools 에서 관리 안 됨.

✓ Good — developer.log
import 'dart:developer';
log('Error', error: err);

DevTools Logging 뷰에서 레벨 필터링.

✗ Bad — build() 내 fetch
Widget build(BuildContext c) {
  fetchData().then((d) => ...);
  return ...;
}

매 리빌드마다 네트워크 호출. 서버 부하 + 레이스 컨디션.

✓ Good — initState/Notifier
void initState() {
  super.initState();
  _future = fetchData();
}

1회 호출. Riverpod 에서는 @riverpod async 함수 사용.

✗ Bad — Flexible + Expanded
Row(children: [
  Flexible(child: A()),
  Expanded(child: B()),
])

같은 Row 에 혼용. 공간 분배 규칙 불명확.

✓ Good — 일관
Row(children: [
  Expanded(flex: 1, child: A()),
  Expanded(flex: 2, child: B()),
])

flex 비율로 명시적 분배. 둘 중 하나로 통일.

✗ Bad — ref.mounted 미체크
await fetch();
state = newState; // disposed 후 호출 → 에러

Riverpod 3.0 은 disposed Notifier 접근 시 에러 throw.

✓ Good — mounted 가드
await fetch();
if (!ref.mounted) return;
state = newState;

async 메서드 끝마다 mounted 확인.

11 · Gotchas 체크리스트

flutter-audit 에서 자주 지적되는 항목.

  • ✓
    Composition > Inheritance — StatefulWidget 상속 대신 기존 위젯 감싸기.
  • ✓
    Private Widget 클래스 — 헬퍼 메서드 대신 class _Foo extends StatelessWidget.
  • ✓
    const 최대 활용 — 모든 가능 위치에 const. prefer_const_constructors lint 활성화.
  • ✓
    print() 금지 — dart:developer log 사용.
  • ✓
    build() 내 네트워크 금지 — initState 또는 @riverpod 함수로.
  • ✓
    go_router 사용 — 딥링크 · 웹 지원. Navigator 1.0 은 지양.
  • ✓
    Ref.mounted 가드 — Riverpod 3.0 async 메서드 끝에 필수.
  • ✓
    Freezed abstract/sealed — factory 생성자만 있는 class 는 abstract 또는 sealed.
  • ✓
    pattern matching — .when / .map 대신 switch expression.
  • ✓
    Makefile 우선 — HAS_MAKEFILE 감지 시 make <target>, 직접 fvm flutter 지양.
  • ✓
    80자 라인 — analysis_options.yaml page_width: 80.
  • ✓
    모든 public API 에 /// — dartdoc 생성. 팀 협업 · AI 이해도 증가.
