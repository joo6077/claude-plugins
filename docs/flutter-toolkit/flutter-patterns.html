Widget Patterns
위젯 설계 원칙
Flutter 공식 AI Rules가 정의하는 위젯 구성 4대 원칙. 상속보다 합성, 메서드보다 클래스 추출을 우선한다.
Composition Over Inheritance
복잡한 위젯은 상속이 아닌 합성으로 구성한다. 위젯 트리를 작은 단위로 나누어 조합하면 재사용성과 테스트 용이성이 높아진다.
Private Widget Classes
헬퍼 메서드(_buildHeader())가 아닌 private Widget 클래스로 추출한다. 별도 클래스는 독립적인 리빌드 범위를 가지며 성능에 유리하다.
Const Constructor
가능한 모든 곳에 const를 사용하여 리빌드를 최소화한다. const 위젯은 프레임워크가 리빌드를 건너뛸 수 있다.
Build 메서드 분리
큰 build() 메서드는 작은 private 위젯으로 분해한다. 각 위젯이 단일 책임을 가지면 가독성과 유지보수성이 향상된다.

Architecture
아키텍처 원칙
레이어 분리, Feature-first 구조, MVVM 패턴의 핵심 규칙.
레이어 분리
Presentation
  ↓
Domain
  ↓
Data
  ↓
Core
Feature-first
대규모 프로젝트에서는 feature 내부에 presentation, domain, data를 모두 배치한다. 기능 단위로 응집도를 높이고 의존성을 명확히 한다.
MVVM
Flutter 공식 권장. View ↔ ViewModel은 1:1, ViewModel이 Repository에서 데이터를 받아 UI 상태로 변환하고 Command 패턴으로 액션을 노출한다.
Do's vs Don'ts
올바른 패턴과 안티패턴
Flutter 공식 AI Rules에서 명시하는 권장 사항과 금지 사항을 비교한다.
✓ Do's
  • ✓go_router 네비게이션 (딥링크, 웹 지원)
  • ✓SOLID 원칙 준수
  • ✓dart:developer.log 사용
  • ✓compute()로 비용 큰 연산을 Isolate에서 실행
  • ✓모든 public API에 /// 문서화
  • ✓dart format, dart fix 도구 활용
  • ✓다양한 화면 크기 테스트
✗ Don'ts
  • ✗print() 사용 금지
  • ✗build() 내 네트워크 호출 금지
  • ✗같은 Row/Column에 Flexible + Expanded 혼용 금지
  • ✗! 연산자 남용 금지 (non-null 보장된 경우만)
  • ✗깊은 위젯 트리 중첩 금지 (합성으로 분해)
