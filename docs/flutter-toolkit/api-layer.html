Flutter Toolkit v0.1

API 레이어

Dio/Retrofit API 클라이언트, 인터셉터, Failure 변환, Freezed 모델, JsonSerializable, 응답 매핑까지 네트워크 경계의 모든 관심사를 하나의 레이어 규칙으로 정리한 리서치 문서.

Principles

다섯 가지 원칙

Dio·Retrofit·Freezed·JsonSerializable 조합을 실무에 적용할 때 흔들리지 말아야 할 기본 원칙. 각 원칙은 pub.dev와 Flutter 공식 문서에서 직접 확인한 근거 출처를 제공한다.

PRINCIPLE 01

Dio는 singleton으로 공통 BaseOptions와 함께 초기화

baseUrl, timeout, headers를 BaseOptions로 한 번만 설정하고 전체 앱에서 공유한다. 매 호출마다 Dio 인스턴스를 새로 만들면 connection pool 이점이 사라지고 interceptor가 중복 설치된다.

dio on pub.dev
PRINCIPLE 02

공통 처리는 Dio interceptor에서 한 번만

auth 토큰 주입, 로깅, 에러 변환, 재시도 같은 횡단 관심사는 Interceptor에 집중시키고, 개별 호출부에서는 반복하지 않는다. Interceptor 순서도 토큰 → 로깅 → 에러 변환 순으로 명시한다.

dio on pub.dev
PRINCIPLE 03

retrofit 인터페이스 + json_serializable DTO + freezed domain 조합

retrofit으로 API 인터페이스를 선언하고, DTO는 json_serializable로 직렬화하며, 도메인 모델은 freezed로 불변·copyWith·union을 얻는다. 세 패키지의 역할이 명확히 분리되어야 코드 생성 충돌이 없다.

retrofit JSON Serialization freezed
PRINCIPLE 04

Repository 경계에서 DioException → Failure로 변환

DioException은 transport 레이어 에러다. Repository가 잡아 도메인의 Failure 타입으로 변환하여 UI 레이어는 Failure만 다루게 한다. UI가 DioException을 직접 알면 네트워크 라이브러리 교체가 불가능해진다.

dio on pub.dev
PRINCIPLE 05

DTO와 Domain 모델 분리, 매핑은 repository/mapper에서

API 스키마 변경이 UI까지 전파되지 않도록 DTO와 Domain 모델을 분리하고, 변환은 repository 또는 전용 mapper에서 수행한다. 두 모델을 같은 클래스로 사용하면 서버 스키마가 UI 계약이 된다.

Anti-patterns

피해야 할 패턴

API 레이어 경계가 무너졌을 때 나타나는 전형적 증상들. 코드 리뷰에서 발견되면 즉시 리팩토링 대상.

안티패턴 문제
Notifier/Widget에서 dio.get 직접 호출 레이어 경계 붕괴, 테스트 불가, mock dio 주입 불가
DTO에 비즈니스 로직 포함 스키마 변경 시 비즈니스 로직까지 영향, 도메인 불변성 상실
모든 에러를 단일 Exception으로 뭉갬 네트워크/파싱/서버 에러 구분 불가, UX 분기 구현 막힘
Map<String, dynamic>를 UI까지 전파 타입 안전성 상실, 런타임 KeyNotFound 에러 빈발
Gotchas

실무 주의사항

retrofit·json_serializable을 도입할 때 프로젝트 초기에 반드시 합의해야 할 두 가지.

!
retrofit Parser.FlutterCompute는 Map-heavy 응답에 역효과 isolate 전송 비용이 파싱 비용보다 클 수 있다. 큰 배열이나 깊은 객체에만 선택적으로 적용하고, 작은 응답에는 메인 isolate 파싱이 더 빠르다. 벤치마크로 검증 후 결정한다.
!
json_serializable 옵션은 초기 합의 필수 explicitToJson, fieldRename, genericArgumentFactories는 프로젝트 시작 시 통일해야 한다. 후행 변경은 전수 리제너레이션을 유발하고 diff가 거대해진다.
