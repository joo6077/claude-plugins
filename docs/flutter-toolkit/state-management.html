01

원칙

상태 관리 선택은 프로젝트 수명의 방향을 결정한다. 아래 5개 원칙은 Riverpod 공식 문서와 pub.dev의 maintainer 가이드에서 도출되었다.

1

변경 가능한 복잡 상태는 Riverpod의 NotifierProvider / AsyncNotifierProvider를 기본으로 쓴다

단순 파생값은 Provider, 비동기 로딩은 AsyncNotifierProvider. 새 화면의 상태를 설계할 때 첫 선택지는 언제나 Notifier 계열이다.

docs-v2.riverpod.dev
2

provider 패키지는 얇은 InheritedWidget 래퍼, flutter_bloc은 이벤트/상태 전이 모델이다

팀 규모와 상태 복잡도에 맞춰 선택하고 한 프로젝트에서 혼용하지 않는다. 두 라이브러리가 공존하면 onboarding 비용이 두 배, 테스트 전략도 두 배가 된다.

pub.dev/packages/provider pub.dev/packages/flutter_bloc
3

비동기 UI 상태는 AsyncValue처럼 loading / error / data 3 케이스 타입으로 표현한다

bool isLoading + nullable data 조합 금지. 3 케이스 sealed 타입은 UI 분기를 강제하여 "로딩 중인데 에러" 같은 불가능한 상태를 컴파일 타임에 막는다.

pub.dev/packages/flutter_riverpod
4

상태 객체는 immutable + copyWith 기본

freezed로 sealed union과 copyWith를 자동 생성한다. 수작업 copyWith는 필드 추가 시 누락 버그의 온상이다.

pub.dev/packages/freezed
5

Provider/Notifier 내부에서 await 이후 UI에 반영하기 전 ref.mounted를 확인한다

dispose 이후 접근은 state 설정 예외를 발생시킨다. 화면 빠른 전환 시 실전에서 가장 많이 발생하는 런타임 에러 중 하나.

03

안티패턴

코드 리뷰에서 발견되면 반드시 수정해야 하는 구조. 초기에는 동작하지만 시간이 지나면 버그 리포트와 성능 저하로 돌아온다.

!

Notifier 바깥에서 state의 내부 필드를 직접 mutate (state.items.add(...)).

!

build 메서드 안에서 HTTP/DB 호출을 바로 시작하는 구조.

!

loading/error/data를 bool isLoading + nullable 값으로 표현.

!

같은 feature 안에 Bloc / Riverpod / Provider를 섞어 쓰는 구조.

04

Gotchas

공식 문서에 숨어 있지만 놓치기 쉬운 함정. 체크리스트로 훑어보고 설계 리뷰에 반영하라.

✓

ChangeNotifierProvider는 Riverpod 공식 문서상 scalable app에서는 migration 용도로만 권장된다. 새 코드는 Notifier / AsyncNotifier를 쓰는 편이 장기적으로 안전하다. 마이그레이션 중인 레거시 기능이 아니면 선택하지 말 것.

✓

sealed union + Result.when 분기는 강력하지만 단순 로그인 폼처럼 상태가 3개 이하인 화면에는 과한 ceremony가 된다. 화면당 상태 수를 보고 판단하라 — 2~3개의 간단한 flag라면 일반 Notifier + named constructor로 충분하다.
