Principles

다섯 가지 핵심 원칙

빠른 unit을 바닥에, 느린 integration을 꼭대기에 — 비용이 낮은 층에서 원인을 국소화한다.

1

테스트 피라미드 — unit → widget → integration

빠르고 안정적인 unit 테스트가 바닥, 느리고 깨지기 쉬운 integration 테스트가 꼭대기에 있는 피라미드 형태를 유지한다. 느리고 flaky한 검증을 위로 밀어 올리지 말고, 가능한 한 아래 층에서 원인을 국소화한다.

docs.flutter.dev/testing/overview
2

widget test의 기본 단위

testWidgets, WidgetTester, pumpWidget, Finder, Matcher가 widget test의 기본 구성 요소다. pumpWidget으로 트리를 렌더링하고 find.byType / find.text / find.byKey로 대상을 잡은 뒤 expect로 Matcher를 통해 검증한다.

docs.flutter.dev/cookbook/testing/widget/introduction
3

Finder는 명확히, pump는 명시적으로

Finder는 text / type / key 기준으로 모호하지 않게 잡아야 한다. 스크롤, 애니메이션, 비동기 상태 갱신은 pump(Duration) 또는 pumpAndSettle로 명시적으로 프레임을 진행시킨다. 단, pumpAndSettle을 만능 대기 함수처럼 쓰면 무한 애니메이션에서 타임아웃이 난다.

docs.flutter.dev/cookbook/testing/widget/finders
4

Golden test는 환경 고정이 전제

Golden(스크린샷) 테스트는 UI 회귀 방지에 강력하지만 theme, font, platform, device pixel ratio에 민감하다. 렌더 환경을 고정(폰트 로더, 테마 강제 지정, 고정 크기)하지 않으면 CI/로컬 간 깨짐이 반복된다. 모든 화면에 일괄 적용하지 말고 회귀 비용이 큰 화면에만 적용한다.

docs.flutter.dev/cookbook/testing/widget/introduction
5

Integration test는 integration_test 패키지

실제 디바이스·에뮬레이터에서 앱 전체 플로우를 검증할 때는 integration_test 패키지를 사용한다. flutter_driver는 더 이상 권장되지 않는다. 사용자 시나리오(로그인 → 목록 → 상세) 같은 end-to-end 검증에 적합하다.

docs.flutter.dev/cookbook/testing/integration/introduction

Anti-patterns

안티패턴 vs 권장

테스트 flake와 디버깅 비용을 늘리는 관행들.

Avoid
  • Widget test에서 실제 네트워크 호출이나 실제 DB 접근을 수행
  • pumpAndSettle을 모든 비동기 대기의 만능 해결책으로 사용
  • Golden test를 모든 화면에 무차별 적용 → 기계적 수락
  • mockito와 mocktail을 팀 규칙 없이 혼용
  • Integration test로 유닛 단위 버그까지 잡으려 시도
Prefer
  • 외부 의존은 fake/mock으로 격리해 widget test에서 순수 UI만 검증
  • 무한 애니메이션이 있으면 pump(Duration)로 명시적 진행
  • 회귀 비용이 큰 대표 화면에만 golden 적용
  • 하나의 mock 라이브러리를 팀 규칙으로 고정
  • 원인 localization은 unit/widget, integration은 시나리오 검증만
Pyramid

테스트 피라미드 시각화

Decision

Mockito vs Mocktail

팀 규칙으로 하나를 고정한다.

Mockito (5.6.3)

build_runner codegen이 필요하다. 타입 안전성이 명시적이며 컴파일 타임에 mock 시그니처가 검증된다. 이미 codegen 파이프라인이 있는 프로젝트(Freezed, Retrofit 등)에 잘 맞는다.

Mocktail (1.0.4)

codegen이 없다. null-safety와 상성이 좋고 설치가 가볍다. 타입 검증이 런타임에 일어나는 점은 trade-off. codegen을 피하고 싶거나 작은 프로젝트에 적합하다.

Snippet

예시 · widget test 기본 골격

pumpWidget → 한 프레임 더 pump() → Finder → expect.

void main() {
  testWidgets('counter increments', (WidgetTester tester) async {
    // 1. 트리 렌더
    await tester.pumpWidget(const MyApp());

    // 2. 초기 프레임 한 번 더 (FutureBuilder, 초기 애니메이션 반영)
    await tester.pump();

    // 3. Finder — 명확한 대상 지정
    expect(find.text('0'), findsOneWidget);

    // 4. 상호작용
    await tester.tap(find.byKey(const Key('inc')));
    await tester.pump(); // setState 반영

    // 5. 검증
    expect(find.text('1'), findsOneWidget);
  });
}
Gotchas

Gotchas 체크리스트

flake의 원인과 CI/로컬 간 깨짐을 일으키는 함정들.

  • ✓
    Mockito vs Mocktail 선택 Mockito는 build_runner codegen이 필요하지만 타입 안전성이 명시적이다. Mocktail은 codegen이 없고 null-safety에 더 잘 맞지만, 타입 검증이 런타임에 일어난다. 팀 관습과 codegen 파이프라인 유무로 하나를 선택하고 일관되게 사용한다.
  • ✓
    Integration test의 한계 동작은 검증할 수 있지만 실패 원인을 특정 레이어로 좁히기 어렵다. 원인 localization은 unit/widget test에 맡기고, integration은 "사용자 관점 시나리오가 끝까지 통과하는가"만 확인한다.
  • ✓
    Golden test의 플랫폼 의존 macOS에서 통과한 golden이 Linux CI에서 깨지는 경우가 흔하다. CI 환경의 폰트·렌더러를 기준으로 golden을 관리하거나, 플랫폼별 golden을 분리한다.
  • ✓
    pumpWidget 후 pump() 한 번 더 FutureBuilder, StreamBuilder, 초기 animation 프레임은 pumpWidget 직후 한 프레임 더 pump()해야 반영된다. 이 누락이 widget test flake의 흔한 원인이다.
  • ✓
    pumpAndSettle 타임아웃 무한 반복 애니메이션이 화면에 있으면 pumpAndSettle은 settle되지 못하고 타임아웃된다. 그 화면에서는 반드시 pump(Duration)으로 정해진 프레임만 진행시킨다.
  • ✓
    Finder의 모호성 같은 텍스트·타입이 여러 개 존재하면 find.text가 여러 개를 반환하여 assertion이 실패한다. 중복이 있는 화면에서는 find.byKey 또는 find.descendant로 범위를 좁힌다.
Summary

한 문장 요약

아래에서 국소화, 위에서 시나리오

Unit/Widget에서 원인을 국소화하고, Integration에서는 사용자 관점 시나리오만 확인한다. mockito/mocktail 중 하나를 팀 규칙으로 고정한다. Golden은 회귀 비용이 큰 화면에만, 환경을 고정해 적용한다. pumpAndSettle 대신 pump(Duration)으로 명시적 프레임을 진행시켜 flake를 줄인다.
