다중 샘플과 페이지네이션 변동성

계약을 승격하기 전에 샘플을 몇 개, 어디까지 모아야 하는지에 대한 규칙. 컬렉션 응답은 한 페이지만 보면 계약이 아니라 우연을 봉인하게 된다. v0.1.0 · 최종 갱신 2026-09-04

먼저 읽어라 — 1 샘플은 계약이 아니라 후보다

enum 은 1 샘플에서 확정하지 않는다. 후보로 표시하고 경고만 낸다. 승격은 독립 샘플 3 개 이상에서만 일어난다(2026-09-04 확정). 사용자가 직접 확정하는 수동 경로는 별도로 둔다.

이유는 하나다 — 오탐 실패가 도구 신뢰를 가장 빨리 깎는다. status 를 한 번 관측하고 enum: ["active"] 로 닫아버리면 두 번째로 등장한 정상 값 shipped 가 회귀로 보고된다. 이런 실패가 한 번 나오면 사용자는 도구를 끄고, 꺼진 도구는 회귀를 하나도 잡지 못한다.

컬렉션 응답은 여기서 한 단계 더 나쁘다. 첫 페이지 하나만 보면 종료 envelope 조차 관측하지 못한다 — nextLink 의 부재나 has_more=false 는 마지막 페이지에서만 나타난다. 그래서 샘플 예산은 “몇 번 호출하나” 가 아니라 “어떤 상태를 관측했나” 로 센다.

이 문서가 결정하는 것

수집 → 점수화 → 승격

계약 강도를 정하는 것은 추출기가 아니라 수집한 샘플이다. 샘플 예산을 정하지 않으면 첫 응답의 우연한 형태가 그대로 baseline 이 된다.

1 — 수집 샘플 예산을 먼저 정한다 최소 3 captures, 최대 5 pages 또는 500 items. first · next · terminal 세 종류를 구분해 남긴다.
2 — 점수화 path 별 변동성을 잰다 presence · type set · scalar churn · 배열 길이 · 순서 churn. 점수 없이 승격하면 partial 로 충분한 필드에 pin 이 붙는다.
3 — 승격 점수가 계약 강도를 정한다 변동성이 큰 path 는 partial, 관계가 성립하는 path 는 pin, 네 조건 모두 통과한 컬렉션만 exact. 
page 1 (first)     envelope + item 집합 + nextLink 존재
page 2 (next)      cursor 를 그대로 재사용해 획득
page N (terminal)  nextLink 부재 / has_more=false / hasNextPage=false
                   ↓
             path 별 변동성 점수
                   ↓
   partial ──────── pin ──────── exact
   (형태)      (경로별 assertion)   (본문 전체 diff)
컬렉션의 계약은 페이지 본문이 아니라 페이지네이션 프로토콜이다. envelope schema · item schema · pagination marker semantics 세 조각을 각각 따로 계약한다. 본문만 봉인하면 종료 조건이 바뀌는 실제 회귀를 놓친다.
승격 게이트

enum 승격 — 1 샘플은 경고, 3 샘플부터 계약

관측 횟수는 계약 강도를 정하는 입력값이다. 샘플이 부족하면 강도를 낮추는 것이 아니라 승격 자체를 보류한다.

1 샘플 — 후보 표시 + 경고. enum 확정 금지. schema 는 type: string 까지만.
≥ 3 독립 샘플 — 승격 하한. 다중 샘플 추론 도구들의 교집합 판정에 필요한 최소치.
≥ 2 distinct value — 값이 하나뿐이면 enum 이 아니라 const 후보다.
≤ 12 domain 크기 — 후보 집합이 이보다 크면 열린 문자열로 둔다.
1 샘플에서 확정
# GET /orders 를 한 번 호출하고 추출
$.data[].status  observed: ["active"]

contract:
  status: { enum: ["active"] }

# 다음 실행 — 정상 데이터인데 실패한다
$.data[3].status = "shipped"   FAIL

실패 하나가 계약 전체의 신뢰를 깎는다. 사용자는 회귀를 의심하지 않고 도구를 의심한다.

3 샘플에서 승격
# 3 회 이상 독립 호출 + 페이지 샘플
sample 1  status: active
sample 2  status: active, shipped
sample 3  status: shipped, cancelled

contract:
  status: { enum: [active, shipped, cancelled] }
# samples=3 · distinct=3 · domain=3  → 승격

승격 근거(샘플 수 · distinct · domain)를 계약에 같이 남기면 나중에 왜 닫았는지 설명된다.

일반 샘플 예산 (captures) ≥ 3
최대 수집 페이지 5 pages
최대 수집 item 500 items
수집 중지 후보 (신규 path 없음) 연속 2 페이지
컬렉션 exact — duplicate stable id 0
컬렉션 exact — ordering variance 0

막대 길이는 각 항목의 상한 대비 비율을 눈으로 비교하기 위한 것이며, 서로 다른 단위의 값을 같은 축에서 재지 않는다.

구조

경로 간 불변식은 Hurl 로 표현되지 않는다

페이지네이션 계약에서 가장 자주 쓰이는 assertion 이 $.meta.total ≥ len($.data) 인데, 이건 Hurl 문법으로 쓸 수 없다. Hurl 의 assert 는 경로 1 개에 predicate 1 개다 (jsonpath "$.meta.total" >= 0). 두 경로를 서로 비교하는 표현이 없다. 

# Hurl 로 쓸 수 있는 것 — 경로 1 개 : predicate 1 개
jsonpath "$.meta.total" >= 0
jsonpath "$.data" count > 0

# Hurl 로 쓸 수 없는 것 — 두 경로 비교
$.meta.total >= len($.data)     ← 문법 없음

pin Hurl 이 직접 검사

pin:
  - path: $.data[].id
    assert: "^ord_"
    engine: hurl
  - path: $.meta.total
    assert: ">= 0"
    engine: hurl

단일 경로 + predicate 로 환원되는 assertion. Hurl 실행 중에 바로 판정된다.

pin 킷이 후처리로 검사

pin:
  - path: $.meta.total
    assert: ">= len($.data)"
    engine: post
  - path: $.data[].isDefault
    assert: "true 인 항목 정확히 1개"
    engine: post

계약 YAML 의 pin 에만 기록하고, /api-verify 가 Hurl 실행 뒤 후처리 단계에서 검사한다.

상수로 근사하지 마라. $.meta.total ≥ len($.data) 를 $.meta.total ≥ 3 으로 박으면 데이터가 늘어난 순간 그 assertion 은 아무것도 검사하지 않는다. 계약 파일은 Hurl 이 검사하는 pin 과 킷이 후처리로 검사하는 pin 을 구분해 표기한다.

원칙

샘플링과 페이지네이션 규칙 9 가지

1

단일 응답은 계약이 아니라 후보다

이 문서의 핵심

quicktype, GenSON, json-schema-inferrer 는 모두 여러 샘플을 합쳐 required, nullable, union, 공통 필드를 판단한다. 변동이 있는 API 는 반복 호출과 페이지 샘플을 먼저 모은 뒤에 추출한다. 샘플 예산을 정하지 않으면 첫 응답의 우연한 형태가 그대로 baseline 이 된다.

→ quicktype → GenSON → json-schema-inferrer
2

prod 샘플링은 safe method 로 제한한다

범위 미확정

prod 에서 반복 샘플링할 때는 서버 상태를 바꾸지 않는 method 만 쓴다. HTTP 는 GET · HEAD · OPTIONS · TRACE 를 safe method 로 정의한다. 이 킷의 prod read-only 범위는 아직 미확정이며 기본값은 GET / HEAD / OPTIONS 다(2026-09-04 결정) — 확장은 사용자 명시 승인이 있을 때만.

기본 허용GET · HEAD · OPTIONS 승인 필요그 외 전부
→ RFC 9110 §9.2.1 Safe Methods
3

페이지네이션 프로토콜을 먼저 식별한다

nextLink, @odata.nextLink, GraphQL edges/pageInfo, Stripe data/has_more 같은 envelope 를 먼저 찾는다. 컬렉션의 계약은 페이지 본문이 아니라 페이지네이션 프로토콜이다. 프로토콜을 모른 채 본문만 봉인하면 종료 조건 변경 같은 실제 회귀를 놓친다.

→ Microsoft Graph paging → Relay Connections → Stripe pagination
4

cursor 는 opaque 다

cursor, $skiptoken, nextLink 는 불투명 값으로 취급한다. 반환된 전체 URL 또는 cursor 를 그대로 다음 요청에 쓰고, 파싱 · 수정 · 합성하지 않는다. 토큰 내부 구조는 계약이 아니며 사전 공지 없이 바뀐다.

→ Microsoft Graph paging → Data API builder $after → Relay Connections
5

안정 정렬이 있어야 순서 계약을 건다

exact

배열 index assertion 과 컬렉션 exact diff 는 안정 정렬이 보장될 때만 허용한다. GraphQL connection 은 페이지 간 edge 순서 일관성을 요구하고, Microsoft 가이드라인도 모든 페이지에 동일한 filter / sort 를 쓰라고 규정한다. 정렬 보장이 없으면 순서는 pin 대상이 아니라 variance 신호다.

→ Relay Connections → Microsoft Azure API Guidelines
6

승격 전에 변동성을 점수화한다

path 별로 presence, type set, scalar 값 churn, 배열 길이, 순서 churn 을 점수화한 뒤 계약 강도를 정한다. snapshot 도구들의 scrubber / redaction 관례가 같은 순서 — 비결정 출력을 먼저 안정화하고 그다음 비교 — 를 따른다. 점수 없이 승격하면 partial 로 충분한 필드에 pin 이 붙어 오탐이 쌓인다.

→ Jest Snapshot Testing → insta redactions → ApprovalTests Scrubbers
7

optionality 는 전 페이지 item 집합에서 계산한다

item 필드의 required / optional 은 첫 페이지가 아니라 수집한 모든 페이지의 item 집합으로 판정한다. Microsoft 는 snapshot 보장이 없는 paginated collection 에서 skip / duplicate 가 발생할 수 있다고 경고한다 — 즉 페이지마다 관측 모집단이 다르다.

→ Microsoft Azure API Guidelines → GenSON
8

대표 페이지를 나눠서 남긴다

첫 페이지만 보면 종료 envelope 차이(nextLink 부재, has_more=false)를 놓친다. 가능한 경우 first, next 중 최소 하나, terminal 세 종류를 구분해 증거로 남긴다.

안티패턴

한 페이지만 보고 봉인하면 생기는 일

아래 두 쌍은 컬렉션 계약에서 가장 자주 나오는 실패다. 둘 다 “계약이 틀렸다” 가 아니라 “관측이 부족했다” 가 원인이다.

BAD첫 페이지 item 개수를 컬렉션 길이로 봉인
# GET /orders 첫 페이지만 관측 (서버 page size = 100)
contract:
  $.data:       { length: 100 }
  $.meta.total: { const: 100 }

# 데이터가 늘어도 줄어도 첫 페이지는 늘 100 개다
# → 컬렉션 크기 변화를 영원히 감지하지 못한다
GOODenvelope · item · marker 를 나눠 계약
contract:
  envelope:
    $.data:       { type: array }
    $.meta.total: { type: integer }
  invariant:                       # 후처리 검사
    - "$.meta.total >= len($.data)"
  marker:
    terminal: "has_more == false"

# page size 는 서버 정책이지 계약이 아니다

서버 page size 를 컬렉션 크기로 착각하는 것이 첫 페이지 봉인의 전형적 결과다. 길이는 계약 대상이 아니고, 길이와 total 의 관계가 계약 대상이다.

BADcursor 를 파싱해 재조립 · 정렬 없는 index pin
# nextLink 에서 token 만 뜯어 다른 query 에 붙임
token = parse(nextLink).query["$skiptoken"]
GET /orders?$skiptoken={token}&$top=50

# 정렬 보장이 없는 컬렉션에 index pin
pin:
  - path: $.data[0].id
    assert: '= "ord_8812"'   # 순서가 바뀌면 실패
GOODcursor 는 통째로 재사용 · 순서는 variance 신호로
# 반환된 URL/cursor 를 그대로 다음 요청에 쓴다
GET {nextLink}

# 순서 보장이 없으면 index 대신 집합·패턴으로
pin:
  - path: $.data[].id
    assert: "^ord_"
  - path: $.data[].status
    assert: "∈ {active, shipped, cancelled}"

cursor 내부 구조는 계약이 아니며 사전 공지 없이 바뀐다. 정렬 보장이 없는 컬렉션에서 순서는 pin 대상이 아니라 variance 신호다.

안티패턴문제
첫 페이지의 item 개수를 전체 컬렉션 길이로 봉인 서버 page size 를 컬렉션 크기로 착각한다. 데이터가 늘어도 줄어도 감지 못한다
offset/skip 기반 페이지를 live-changing 컬렉션의 exact diff 기준으로 사용 항목이 삽입/삭제되면 페이지 경계가 밀려 매번 diff 가 난다
nextLink 에서 token 만 뜯어 다른 query 에 붙임 cursor 는 opaque 다. 내부 구조가 바뀌면 조용히 잘못된 페이지를 읽는다
정렬 보장 없는 컬렉션에 index 기반 pin 사용 $.data[0].id 같은 assertion 이 정상 동작에도 실패한다
auto-pagination helper 결과만 저장하고 페이지별 raw evidence 를 버림 envelope 와 종료 marker 증거가 사라져 페이지네이션 회귀를 진단할 수 없다
Gotchas

수집 실행 전 확인

아래는 관측을 잘못 해석해 계약을 망가뜨리는 항목이다. 대부분 첫 실행에서는 조용히 통과한다.

  • ! nextLink: null 을 표준 종료 marker 로 일반화하지 않는다 — Microsoft Azure 가이드라인은 마지막 페이지에서 nextLink 를 아예 생략하라고 한다. 부재와 null 은 다른 신호다.
  • ! GraphQL backward pagination 에서 순서를 뒤집지 않는다 — last/before 도 forward 와 같은 logical order 를 유지해야 한다. 역순으로 저장하면 페이지 간 비교가 깨진다.
  • ! skip / duplicate 는 item schema 위반이 아니다 — snapshot 보장이 없는 live collection 에서는 정상 현상이며, 컬렉션 variance 신호로 분류해야 한다. schema 실패로 올리면 오탐이다.
  • ! nextLink 의 absolute/relative 정책은 provider 마다 다르다 — 증거에는 원문을 그대로 남기고, 계약에는 provider 별 canonical 규칙을 따로 기록한다.
  • × 1 샘플로 enum 을 닫지 마라 — 후보 표시 + 경고까지만이다. 승격은 독립 샘플 ≥3, distinct value ≥2, domain ≤12 를 모두 만족할 때만.
  • × 경로 간 불변식을 Hurl assert 로 쓰려 하지 마라 — Hurl 은 경로 1 개에 predicate 1 개다. $.meta.total ≥ len($.data) 는 계약 YAML 의 pin 에 기록하고 /api-verify 후처리에서 검사한다.
  • × 불변식을 상수로 근사하지 마라 — ≥ 3 으로 박으면 데이터가 늘어난 순간 그 assertion 은 아무것도 검사하지 않는다.
  • ✓ prod 반복 샘플링은 GET / HEAD / OPTIONS 로 시작한다 — 범위 확장은 사용자 명시 승인이 있을 때만.
  • ✓ first · next · terminal 세 종류를 각각 남겼는지 확인한다 — terminal 이 없으면 종료 marker 계약은 근거가 없다.
  • › 수집을 언제 멈출지 미리 정한다 — 연속 2 페이지에서 신규 path/type 이 없으면 변동성이 수렴한 것으로 보고 중지 후보로 올린다. 상한은 5 pages 또는 500 items.

수집 요약

샘플 3 개 이상을 모으고, first · next · terminal 을 각각 남기고, path 별 변동성을 점수화한 뒤에 강도를 정한다. 이 순서를 지키면 partial 로 충분한 필드에 pin 이 붙지 않고, pin 이 필요한 관계가 partial 로 새어 나가지도 않는다.
