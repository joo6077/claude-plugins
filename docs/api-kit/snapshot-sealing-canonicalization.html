스냅샷 봉인과 정규화

응답을 baseline 으로 봉인할 때 무엇을 원본 증거로 남기고 무엇을 비교 기준선으로 파생시킬지 가르는 규칙. 비교 기준선은 RFC 8785 JCS canonical JSON 이며, 사람이 읽는 화면 표시용 포매팅은 기준선이 아니다. v0.1.0 · 최종 갱신 2026-09-04

기준선은 JCS 하나다

스냅샷 비교에서 "같다 / 다르다" 를 판정하는 대상은 RFC 8785 JCS 로 정규화한 바이트 하나뿐이다. pretty print 결과, 키 삽입 순서, diff UI 가 만들어 낸 문자열은 어떤 경우에도 기준선이 될 수 없다. 표시 포매터가 바뀌는 순간 계약이 통째로 깨지기 때문이다.

이 문서의 나머지 규칙은 전부 이 한 축에서 파생된다. raw 를 왜 따로 보관하는지, I-JSON 게이트를 왜 앞에 두는지, 헤더 정규화를 왜 JCS 밖으로 빼는지, baseline id 를 왜 응답 바이트가 아니라 매니페스트 digest 로 만드는지 — 전부 "기준선은 JCS 여야 한다" 를 지키기 위한 배치다.

이 문서가 결정하는 것

응답 하나는 봉인될 때 두 갈래로 갈린다. 하나는 다시 열어 볼 증거, 다른 하나는 다음 실행과 대조할 기준선이다. 두 갈래를 섞으면 증거가 오염되거나 기준선이 흔들린다.

01 · 증거 raw 보존 상태코드, 원본 헤더 라인, wire/content 바이트, 디코딩 전후 digest. 시크릿 값만 마스킹한다.
02 · 기준선 I-JSON 게이트 → JCS 먼저 I-JSON 으로 검문하고, 통과한 것만 JCS 로 정규화한다. 실패는 정규화 대상이 아니다.
03 · 식별 매니페스트 digest baseline id 는 응답 바이트가 아니라 매니페스트의 digest 로 만든다.

기준선의 정의 · RFC 8785 JCS

JCS 는 "예쁘게 정리한 JSON" 이 아니라 같은 데이터가 항상 같은 바이트가 되도록 강제하는 규격이다. 다섯 가지 요구를 모두 만족해야 JCS 결과다.

input I-JSON 입력

정규화 이전에 I-JSON 제약을 만족해야 한다. 만족하지 못하면 정규화가 아니라 실패다.

whitespace 토큰 사이 공백 0개

들여쓰기 · 줄바꿈 · 토큰 사이 여백이 전부 제거된다. pretty print 와 정반대 방향이다.

number ECMAScript primitive serialization

숫자와 문자열의 직렬화 방식이 고정된다. 구현마다 다른 표기가 나오지 않는다.

order 객체 property 재귀 정렬

중첩 객체까지 property 이름 순으로 정렬한다. 배열 순서는 정렬 대상이 아니다.

encoding UTF-8 출력

결과 바이트 인코딩이 UTF-8 로 고정된다. digest 를 바이트 단위로 비교할 수 있는 근거다.

NOT A BASELINE 표시용 pretty print — 포매터 설정이 곧 계약이 된다 
{
  "b": 1,
  "a": [3, 1, 2],
  "n": 1.0E2
}

# 들여쓰기 2 → 4 로 바꾸면 digest 가 바뀐다
# 키 삽입 순서가 바뀌어도 digest 가 바뀐다
BASELINE JCS 결과 — 같은 데이터면 항상 같은 바이트 
{"a":[3,1,2],"b":1,"n":100}

# property 는 정렬됨 (a, b, n)
# 배열 [3,1,2] 는 순서 보존
# 1.0E2 → 100 (primitive serialization)
# 토큰 사이 공백 0

왼쪽은 사람이 읽기 위한 산출물이고 오른쪽은 기계가 대조하기 위한 산출물이다. 둘 다 만들어도 되지만, digest 를 뜨는 대상은 오른쪽 하나여야 한다.

원칙 7

1·6·7 은 무엇을 남길지, 2·3 은 무엇을 기준선으로 삼을지, 4·5 는 JCS 밖의 경계를 정한다.

1

원본 증거 보존

Raw Evidence Preservation

baseline 은 raw 를 보관한다. 상태코드, 원본 헤더 라인, wire/content 바이트, 디코딩 전후 digest 를 그대로 남긴다. 단 시크릿 값만 마스킹한 raw 다 — 토큰 · 키 · 쿠키 값은 자리를 유지한 채 값만 가린다(2026-09-04 결정). 계약 비교 입력은 이 raw 에서 파생된 별도 산출물이고, JCS 역시 원본 전송 데이터와 canonical counterpart 를 분리하는 사용 모델을 전제한다.

→ RFC 8785 JCS → RFC 9530 Digest Fields
2

JCS 정규 형식

JCS Canonical Form

정규화된 계약 입력의 JSON 기준선은 RFC 8785 JCS 로 고정한다. JCS 는 I-JSON 입력, 토큰 사이 공백 0개, ECMAScript primitive serialization, 객체 property 재귀 정렬, UTF-8 출력을 요구한다. 따라서 pretty print 결과는 어떤 경우에도 비교 기준이 될 수 없다.

→ RFC 8785 JCS
3

정규화 전 I-JSON 게이트

fail before canonicalize

JCS 로 넘기기 전에 I-JSON 으로 먼저 검문한다. 중복 키, Unicode 로 표현 불가한 문자열, IEEE 754 binary64 로 표현 불가한 숫자, NaN/Infinity, lone surrogate 는 정규화 대상이 아니라 실패 또는 fallback 대상이다. 게이트를 건너뛰면 파서가 조용히 값을 바꾼 뒤의 결과를 봉인하게 된다.

→ RFC 8785 JCS → RFC 7493 I-JSON
4

헤더 정규화는 JCS 밖에서

not JSON

HTTP 헤더는 JSON 이 아니므로 JCS 에 섞지 않고 별도 규칙을 둔다. field name 은 대소문자 무시, 같은 이름의 field line 결합은 그 field 가 comma-list 를 허용할 때만 가능하며 Set-Cookie 는 예외로 특별 취급한다.

→ RFC 9110 HTTP Semantics
5

미디어 타입 처리 경계

representation

JSON 파싱 여부는 Content-Type 과 Content-Encoding 을 해석한 뒤의 representation 의미로 판단한다. application/json 에는 charset parameter 가 정의되어 있지 않고, 네트워크로 오가는 JSON 은 UTF-8 이어야 한다. 따라서 charset 선언은 파싱 근거가 아니라 증거로만 남긴다.

→ RFC 8259 JSON → RFC 9110 HTTP Semantics
6

변동 필드 레지스트리와 마스킹 경계

path registry

timestamp, id, nonce, token 류는 raw 를 건드리지 말고 normalized 단계에서 path registry 로 처리한다. Jest propertyMatchers, insta redactions, ApprovalTests scrubbers 가 모두 같은 관례 — 비결정 값을 비교 직전에 안정화하고 원본은 그대로 둔다 — 를 제공한다.

→ Jest Snapshot Testing → insta redactions → ApprovalTests Scrubbers
7

매니페스트 해싱과 불변 baseline ID

manifest digest

baseline id 는 응답 바이트가 아니라 매니페스트의 digest 로 만든다. 매니페스트에는 raw digest, normalized JCS digest, redaction registry 버전, media type, extraction mode 를 담는다. HTTP digest fields 가 content digest 와 representation digest 를 분리하고 algorithm agility 를 두는 것이 이 구조의 선례다.

→ RFC 9530 Digest Fields → RFC 8785 JCS
수치 기준

허용치가 0 인 항목이 많다. 정규화는 "웬만하면 맞춰 준다" 가 아니라 "규격을 벗어나면 봉인하지 않는다" 는 게이트이기 때문이다.

항목값근거
중복 JSON object member 허용치 0 중복 이름은 I-JSON/JCS 위반 (RFC 7493)
안전 정수 범위 -9007199254740991 ~ 9007199254740991 범위 밖 정수는 exact interchange 를 기대할 수 없음 (RFC 7493)
JCS 토큰 사이 추가 공백 0 byte JCS 정의 (RFC 8785)
lone surrogate / noncharacter 허용 0 정상 surrogate pair 는 허용, 단독 surrogate 는 실패 (RFC 8785, RFC 7493)
manifest digest 기본 알고리즘 sha-256 (옵션 sha-512) 추론 — RFC 9530 의 algorithm agility 와 sha-256/sha-512 사용례
baseline 내 시크릿 원문 0건 2026-09-04 결정 — raw 보존과 시크릿 0건을 동시에 만족하기 위해 값만 마스킹

표의 근거 열에 나오는 RFC 링크는 위 원칙 카드의 → 출처와 같은 문서다: RFC 7493 I-JSON · RFC 8785 JCS · RFC 9530 Digest Fields.

허용치를 같은 축에 놓으면 이 문서의 성격이 드러난다. 여섯 항목 중 넷이 0 이다.

중복 member 0
토큰 사이 공백 0 byte
lone surrogate 0
baseline 내 시크릿 0건
manifest digest 알고리즘 1 + 옵션 1
안전 정수 범위 2^53−1

막대는 표의 허용치를 성격별로 표시한 것이다. 0 항목은 위치만 보이도록 최소 폭을 남겼고, 범위 항목은 상한을 100% 로 두었다.

게이트 위치가 중요하다: 위 허용치는 파싱 이후 검사가 아니라 파싱 게이트 에서 본다. 파서가 "last key wins" 로 중복 키를 삼킨 뒤에 검사하면 이미 값이 소실된 상태라 검사 자체가 의미가 없다.
안티패턴

다섯 가지 모두 "기준선이 JCS 하나" 라는 축을 흔든다. 흔들린 기준선은 회귀를 못 잡거나, 없는 회귀를 만들어 낸다.

BAD 배열을 "안정화" 한다며 정렬 
입력:  {"items":[3,1,2]}

"정렬해서 안정화"
   ↓
{"items":[1,2,3]}

# 서버가 순서를 바꿔도 digest 가 같다
# → 순서 회귀를 영원히 못 잡는다
GOOD JCS 규칙 그대로 — object 만 정렬 
입력:  {"items":[3,1,2],"a":1}

JCS
   ↓
{"a":1,"items":[3,1,2]}

# property 는 정렬, array order 는 보존
# 순서가 바뀌면 digest 가 바뀐다 = 회귀 검출

JCS 는 object property 만 정렬하고 array order 는 보존한다. 배열 정렬은 정규화가 아니라 실제 순서 회귀의 은폐다.

BAD Set-Cookie 를 comma-join 해서 정규화 입력에 투입 
Set-Cookie: a=1; Path=/; Expires=Mon, 01 Sep 2026 ...
Set-Cookie: b=2; Path=/

comma-join
   ↓
Set-Cookie: a=1; Path=/; Expires=Mon, 01 Sep 2026 ..., b=2; Path=/

# Expires 안의 comma 와 구분되지 않는다
# 쿠키가 잘못 병합된다
GOOD 예외 헤더로 특별 취급 — 라인 단위 보존 
headers:
  set-cookie:
    - "a=1; Path=/; Expires=Mon, 01 Sep 2026 ..."
    - "b=2; Path=/"

# field name 은 대소문자 무시
# 결합은 comma-list 를 허용하는 field 에서만
# Set-Cookie 는 결합하지 않는다

헤더 정규화는 JCS 밖의 별도 규칙이다. JSON 규칙을 헤더에 적용하려는 순간 이런 종류의 손실이 생긴다.

BAD — 표시 산출물을 해싱

pretty-print JSON, 키 삽입 순서, diff UI 문자열을 해싱해 기준선으로 쓴다. 표시 포매터가 바뀌면 계약이 통째로 깨진다. 서버는 아무것도 안 바뀌었는데 전 항목이 FAIL 로 뜬다.

GOOD — JCS 결과만 해싱

digest 대상은 JCS 바이트 하나다. 표시용 포매팅은 화면 전용 산출물로 따로 만들고, 기준선 경로와 섞지 않는다.

BAD — 파싱 후 중복 키 검사

파서가 "last key wins" 로 삼킨 뒤에 중복 키를 검사한다. 이미 값이 소실된 상태라 검사 자체가 무의미하다. 로그에는 "중복 없음" 이 찍힌다.

GOOD — 파싱 게이트에서 검문

I-JSON 게이트를 JCS 앞에 두고 파싱 시점에 중복 키 · NaN/Infinity · lone surrogate 를 잡는다. 걸리면 정규화하지 않고 실패 또는 fallback 으로 보낸다.

BAD — 마스킹 결과만 저장

마스킹된 결과만 남기고 raw digest 와 원본 접근 경계를 기록하지 않는다. 회귀 조사 시 원본을 복원할 수 없어 baseline 이 증거로서 기능하지 못한다.

GOOD — 값만 가리고 자리는 남긴다

시크릿은 자리를 유지한 채 값만 마스킹하고, raw digest 와 decoded representation digest 를 매니페스트에 나눠 기록한다. baseline 내 시크릿 원문은 0건이면서 구조는 복원 가능하다.

Gotchas · 봉인 전 확인

아래가 확인되지 않은 상태로 봉인하면, 나중에 나오는 diff 가 "서버 변경" 인지 "우리 정규화" 인지 구분할 수 없다.

  • ! JCS property sort 는 UTF-16 code unit 순서다 — unescaped property name 기준이라 UTF-8 byte sort 와 비ASCII 구간에서 결과가 달라진다. 자체 구현 정렬을 쓰지 말고 JCS 구현을 썼는가.
  • ! Unicode normalization 은 하지 않는다 — NFC/NFD 가 화면상 같아 보여도 JCS digest 는 다르다. "같아 보이는데 왜 다르냐" 는 대부분 이 케이스다.
  • ! Content-Encoding: gzip 이면 digest 가 둘이다 — raw content bytes digest 와 decoded representation digest 가 다르므로 매니페스트에 둘을 구분해 기록했는가.
  • × charset parameter 는 파싱 근거가 아니다 — application/json; charset=utf-8 의 charset 은 compliant recipient 에게 의미가 없지만, 증거에는 원문 그대로 남긴다.
  • ✓ digest 를 뜬 대상이 JCS 바이트인가. pretty print 결과나 diff UI 문자열이 기준선 경로에 섞이지 않았는가.
  • ✓ I-JSON 게이트가 JCS 앞 에 있는가. 중복 키 · NaN/Infinity · binary64 밖 숫자 · lone surrogate 가 파싱 시점에 걸리는가.
  • ✓ 배열을 정렬하고 있지 않은가. JCS 는 object property 만 정렬한다 — array order 는 보존이 원칙이다.
  • ✓ 변동 필드(timestamp · id · nonce · token)를 raw 가 아니라 normalized 단계의 path registry 로 처리했는가.
  • ✓ 헤더 정규화가 JCS 밖의 별도 규칙으로 돌아가는가. Set-Cookie 를 comma-join 하고 있지 않은가.
  • ✓ baseline id 가 응답 바이트가 아니라 매니페스트 digest 인가. 매니페스트에 raw digest · normalized JCS digest · redaction registry 버전 · media type · extraction mode 가 모두 들어 있는가.
한 줄 요약: raw 는 다시 열어 보기 위한 것이고, JCS 는 대조하기 위한 것이다. 둘을 한 산출물로 합치는 순간 증거도 기준선도 아니게 된다.
