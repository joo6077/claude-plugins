API 인벤토리 정규화

OpenAPI 스펙, 사람이 쓴 md, curl·Talend·HAR 덤프를 하나의 operation 인벤토리로 합칠 때 적용하는 판단 규칙. 키 표준화, 출처 신뢰도, 충돌 처리, 커버리지 집계를 다룬다. v0.1.0 · 최종 갱신 2026-09-04

이 문서가 결정하는 것
인벤토리는 계약 검증의 좌표계다. 어떤 operation 이 존재하고, 그 근거가 어디서 왔고, 스펙과 실호출이 어디서 갈라지는지를 여기서 정한다. 좌표계가 흔들리면 이후의 probe·계약·회귀 diff 가 전부 엉뚱한 대상에 붙는다.
step 1 · 수집 서로 다른 3 종 출처 OpenAPI 문서(계약 설명), curl·Talend·HAR 덤프(실제로 본 호출), 사람이 쓴 md(설명 증거). 형식도 완결성도 다르다.
step 2 · 정규화 canonical key 로 접기 키는 METHOD + normalized path template. 파라미터는 (in, name) 쌍. 모든 필드에 provenance 를 남긴다.
step 3 · 집계 합치지 말고 나눠 센다 operations / conflicts / coverage 3 축. 충돌은 버리지 않고 레코드로 보존한다. 
출처 3 종                       정규화                                  산출
──────────────                  ──────────────────────────              ────────────────
openapi.yaml  ─┐
api-notes.md  ─┼──>  key   = METHOD + normalized path      ──>  operations[]  (canonical)
curl-dump.sh  ─┤     param = (in, name)                          conflicts[]   (미병합 보존)
har-export    ─┘     prov  = source + confidence                 coverage{}    (3 축 분리)

                     operationId 는 별칭 컬럼에만 저장 — 키로 쓰지 않는다
한 줄 규칙. 병합은 근거가 완전히 일치할 때만 한다. 하나라도 어긋나면 병합이 아니라 conflict 다. 충돌을 지우는 순간 인벤토리는 계약 검증 근거로서의 자격을 잃는다.
원칙 9

아홉 개 전부 "무엇을 같은 것으로 볼 것인가" 와 "무엇을 다르게 남길 것인가" 를 가르는 규칙이다. 앞의 다섯은 키와 파라미터의 동일성, 뒤의 넷은 충돌·집계의 보존 정책을 다룬다.

1

Operation Key 표준화

canonical key
operation 의 기본 키는 METHOD + normalized path template 로 잡는다. operationId 는 별칭 컬럼에만 저장하고 키로 쓰지 않는다. operationId 는 있으면 유일해야 하지만 선택 필드이고 대소문자를 구분하므로, 원시 키로 삼으면 md·curl 출처와의 매칭이 깨진다.
→ OpenAPI 3.1.0 Operation Object
2

Source Confidence Matrix

provenance
출처마다 구조 신뢰도를 다르게 매기고, 모든 필드에 provenance 를 남긴다. 유효한 OpenAPI 는 계약 설명 형식이므로 최상위, curl·Talend·HAR 는 "실제로 본 호출" 증거, 사람이 쓴 md 는 설명 증거다. 신뢰도가 높은 출처라도 낮은 출처의 값을 자동으로 덮어쓰지 않는다 — 덮어쓰면 drift 가 사라진다.
→ OpenAPI 3.1.0 Introduction
3

Path Template Resolution

matching order
concrete path 는 templated path 보다 먼저 매칭한다. /users/me 는 /users/{id} 보다 우선한다. 같은 hierarchy 에서 {id} 와 {name} 처럼 변수명만 다른 path 는 동일 path 로 보고 무효 처리한다. 모호한 후보는 임의로 고르지 않고 conflict 로 남긴다.
→ OpenAPI 3.1.0 Paths Object
4

Parameter Location Canonicalization

(in, name)
파라미터 키는 (in, name) 쌍이다. in 은 path / query / header / cookie 넷으로 정규화하고, in: path 는 항상 required 로 강제한다. HTTP header 이름은 case-insensitive 이지만 OpenAPI 파라미터 이름 자체는 case-sensitive 이므로, header 비교만 case-fold 하고 나머지는 원문 그대로 비교한다.
→ OpenAPI 3.1.0 Parameter Object → RFC 9110 Field Names
5

Reserved Protocol Headers 분리

3 헤더 예외
Accept, Content-Type, Authorization 은 파라미터 테이블에 넣지 않는다. OpenAPI 는 이 셋을 header parameter 로 정의해도 무시한다. 각각 media negotiation, requestBody media type, security requirement 에서만 파생시킨다.
→ OpenAPI 3.1.0 Parameter Object
6

Media Type 우선순위

most specific
request/response content 에서 여러 media range 가 동시에 매칭되면 가장 구체적인 key 하나만 적용한다. text/plain 이 text/* 보다 우선한다. wildcard 는 fallback 후보 목록에만 남기고 기본 선택값으로 쓰지 않는다.
→ OpenAPI 3.1.0 Request Body Object → OpenAPI 3.1.0 Response Object
7

Auth Scope Mapping

OR / AND
operation-level security 가 있으면 top-level security 를 override 한다. security requirement 배열의 원소 간 관계는 OR, 한 객체 안의 여러 scheme 은 AND 다. OAuth2 / OpenID Connect scheme 의 값 배열은 scope 목록이고, 그 외 scheme 은 빈 배열이어야 한다.
→ OpenAPI 3.1.0 Security Requirement Object
8

Duplicate Collapse + Conflict Flagging

보존 우선
canonical key 가 같은 후보만 collapse 한다. method, path template, parameter location, auth scheme, media type 중 하나라도 충돌하면 병합하지 않고 conflict 레코드로 보존한다. 충돌을 버리는 순간 인벤토리는 계약 검증 근거로 쓸 수 없다.
→ OpenAPI 3.1.0 Operation Object → OpenAPI 3.1.0 Paths Object
9

Coverage Accounting 분리

3 축
커버리지는 단일 숫자로 합치지 않는다. OpenAPI operation, observed-only request(스펙에 없는데 덤프에서 관측된 호출), generated probe 세 축을 각각 센다. 합산하면 스펙에 없는 실호출이 커버리지에 흡수돼 블랙박스 검증의 핵심 신호가 사라진다.
→ OpenAPI 3.1.0 Paths Object
수치 기준
앞 네 줄은 사양이 정한 값이고, 뒤 세 줄은 이 킷의 추론값이다. 근거 = 추론 인 항목은 실측으로 조정할 여지가 있다.
항목 값 근거
operation / path item 내 (name, in) 중복 허용치 0 → OpenAPI Operation Object
같은 hierarchy 내 path template ambiguity 허용치 0 → OpenAPI Paths Object
header name case 구분 0 (case-insensitive 비교) → RFC 9110 Field Names
servers 누락 시 기본 server URL / → OpenAPI Paths Object

auto-collapse 조건 method·path-template exact match 그리고 param-set Jaccard >= 0.80 추론
conflict 판정 임계 top-2 후보 confidence 차이 < 0.15 추론

안티패턴
아래 다섯 가지가 인벤토리를 조용히 망가뜨린다. 모두 "에러 없이 통과하지만 결과가 틀린" 부류다.
안티패턴 문제
operationId 만으로 dedupe 선택 필드라 외부 덤프에는 대부분 없어 dedupe 자체가 동작하지 않는다
raw path 문자열만 비교 /users/me 와 /users/{id} 의 우선순위를 놓쳐 잘못된 operation 에 probe 를 붙인다
path/query/header/cookie 를 한 namespace 에 병합 이름이 같고 위치가 다른 파라미터가 서로를 덮어써 사라진다
Authorization 을 일반 header parameter 로 저장 auth scheme·scope 판단 경로가 끊겨 인증 요구사항을 재현할 수 없다
충돌 시 가장 최신 파일만 채택 스펙과 실호출의 drift 를 숨긴다 — 계약 검증 문서로서의 가치가 사라진다

① 키 산출 — raw path 비교 vs 템플릿 우선순위

BAD 문자열이 다르므로 서로 다른 operation 으로 남는다 
key = "GET " + raw_url_path

GET /users/me      -> key "GET /users/me"
GET /users/42      -> key "GET /users/42"
GET /users/43      -> key "GET /users/43"

# 결과: 사용자 수만큼 operation 이 늘어난다
GOOD concrete 를 먼저 매칭하고, 남는 것만 세그먼트 단위로 변수화 
key = METHOD + normalized_path_template

GET /users/me      -> "GET /users/me"        (concrete 우선)
GET /users/42      -> "GET /users/{id}"
GET /users/43      -> "GET /users/{id}"

# operationId 는 alias 컬럼에만: ["getUser", "GetUser"]

원칙 1 · 3. /users/me 를 {id} 로 흡수해서도 안 되고, concrete URL 마다 키를 새로 만들어서도 안 된다.

② 파라미터 — 단일 namespace vs (in, name) 쌍

BAD 위치가 다른 동명 파라미터가 서로를 덮어쓴다 
params = {
  "id": { required: true },   # path 의 id
  "id": { required: false }   # query 의 id 가 덮어씀
}

# Authorization 까지 같은 표에 섞임
params["Authorization"] = "Bearer ..."
GOOD 키가 쌍이므로 충돌하지 않고, 예약 헤더는 표 밖에 있다 
params = [
  { in: "path",  name: "id", required: true  },
  { in: "query", name: "id", required: false }
]

# Accept / Content-Type / Authorization 은
# media negotiation · requestBody · security 에서 파생

원칙 4 · 5. in: path 는 required 강제. header 비교만 case-fold 한다.

BAD — 충돌을 승자독식으로 해결
스펙과 curl 덤프의 auth scheme 이 다르자 confidence 가 높은 OpenAPI 값으로 통일하고 덤프 쪽을 버렸다. 인벤토리에는 경고 하나 남지 않는다.
결과 — 실제 서버가 스펙과 다르게 동작한다는 신호(drift)가 통째로 삭제된다. 회귀 diff 는 계속 PASS 를 낸다.
GOOD — 충돌을 레코드로 보존
conflicts[] 에 두 후보를 모두 남기고 각각의 provenance 와 confidence 를 붙인다. top-2 차이가 0.15 미만이면 자동 채택 자체를 하지 않는다.
결과 — drift 가 눈에 보이고, 사람이 판단할 대상 목록이 된다.
BAD — 커버리지 한 숫자
"커버리지 92%" 하나로 보고한다. 스펙에 없는데 덤프에서 관측된 호출 12 건이 분모·분자 어딘가에 섞여 수치가 올라간다.
결과 — 블랙박스 검증에서 가장 중요한 신호인 스펙 밖 실호출이 보이지 않는다.
GOOD — 3 축 분리 집계
OpenAPI operation / observed-only request / generated probe 를 각각 센다. 축끼리 더하지 않는다.
결과 — "스펙에 없는 호출 12 건" 이 독립 숫자로 남아 후속 작업의 입력이 된다.
Gotchas — 인벤토리 확정 전 확인
아래 항목은 전부 "돌아가는 것처럼 보이는" 실패다. 인벤토리를 확정하기 전에 하나씩 대조하라.
  • ! OpenAPI path template 변수값에는 unescaped /, ?, # 가 들어갈 수 없다. 관측 덤프의 concrete URL 을 역으로 템플릿화할 때 슬래시가 포함된 세그먼트를 하나의 {id} 로 접으면 실제로는 존재하지 않는 operation 을 만든다. 세그먼트 경계에서만 변수화한다.
  • ! GET request body 는 문법상 허용되지만 의미가 정의돼 있지 않다. 스펙에 GET + requestBody 가 있어도 probe 기본값으로 body 를 생성하지 않는다. 서버·프록시마다 처리가 달라 실패가 계약 위반인지 전송 계층 문제인지 구분되지 않는다.
  • ! md·curl 예시는 auth·base URL·environment 를 생략하는 경우가 많다. 이런 출처는 "불완전한 관측치" 로 표시하고, 누락 필드를 기본값으로 채우지 말고 미상(unknown)으로 남긴다. 채우면 스펙과의 diff 가 가짜로 사라진다.
  • × operationId 는 대소문자를 구분한다. getUser 와 GetUser 는 서로 다른 별칭이다. 별칭 매칭에서 case-fold 하면 서로 다른 operation 이 하나로 붙는다.
  • ✓ Accept · Content-Type · Authorization 이 파라미터 테이블에 남아 있지 않은지 확인했다(원칙 5).
  • ✓ in: path 파라미터가 전부 required 로 강제됐고, header 비교만 case-fold 되는지 확인했다(원칙 4).
  • ✓ operation-level security 가 top-level 을 override 했고, 배열 원소 간 OR / 객체 내 AND 관계가 유지되는지 확인했다(원칙 7).
  • ✓ wildcard media range(text/*)가 기본 선택값이 아니라 fallback 후보로만 남아 있는지 확인했다(원칙 6).
  • ✓ 커버리지가 세 축으로 분리 보고되고, 어디에서도 하나의 백분율로 합산되지 않는지 확인했다(원칙 9).
  • ✓ conflicts[] 가 비어 있다면 그것이 진짜 충돌 없음인지, 아니면 자동 채택이 충돌을 삼킨 것인지 확인했다.
