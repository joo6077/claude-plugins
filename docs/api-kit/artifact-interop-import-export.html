api-kit / artifact interop

생태계 입출력 상호운용

curl·Talend·HAR·OpenAPI 를 읽어들이고 .hurl·HAR·JUnit 으로 내보낼 때의 변환 규칙. 재현 단위, 원본 linkback, 손실 경고 정책을 다룬다. v0.1.0 · 최종 갱신 2026-09-04

이 문서가 결정하는 것
api-kit 은 남의 포맷을 읽어서 남의 포맷으로 내보낸다. 그 사이에 무엇을 재현 단위로 삼을지, 무엇을 계약의 근거로 승격할지, 무엇을 손실로 보고할지가 이 문서의 범위다. 세 결정은 서로 독립이며, 하나라도 뭉개면 실패를 원본으로 되돌릴 수 없게 된다.
import 읽는다 — 증거로만 curl · Talend · HAR · OpenAPI. 실행 예시는 신뢰도를 보강할 뿐 계약의 근거로 승격되지 않는다.
SSOT 재현 단위는 .hurl plain-text request + assert + capture + variable chaining 이 한 파일에 있어 실패를 그대로 재실행할 수 있다.
export 내보낸다 — 역할별로 HAR 는 실행 관측 기록, JUnit 은 CI 요약, --curl 은 공유용 부가 산출물. 셋 다 재현 SSOT 가 아니다. 
  import                       내부 표현                    export
  ─────────────                ────────────────             ──────────────────────────
  curl dump    ─┐                                      ┌─>  .hurl        재현 SSOT
  Talend dump  ─┼──>  operation + provenance  ──────────┼─>  HAR 1.2      실행 관측 기록
  HAR export   ─┤     + linkback(operationRef)          ├─>  JUnit XML    CI 결과 요약
  OpenAPI doc  ─┘     + schemaVersion                   └─>  curl 명령    공유용 부가물

  변환마다 기록: source type · source version · 원본 hash · 처리 못한 필드 목록
  처리 못한 필드가 1 개라도 있으면 → 경고 (조용한 손실 = false pass)
한 줄 규칙. 읽어들인 것은 증거, 내보내는 것은 역할이 정해진 산출물. .hurl 하나만 재현 SSOT 이고 나머지는 파생물이다. 파생물만 남기고 SSOT 를 버리면 실패를 다시 만들어낼 방법이 없다.
원칙 9

1~3 은 입력 충실도, 4 는 원본으로 돌아가는 길, 5~7 은 출력별 역할 구분, 8~9 는 손실과 버전 관리다. 어느 것도 "대충 비슷하게" 가 허용되지 않는다.

1

Curl Import Fidelity

tokenization
curl 덤프는 shell tokenization 과 curl option 의미론을 보존해 파싱한다. 옵션은 URL 앞뒤 어디에나 올 수 있고 --header, --url-query 처럼 반복 가능한 옵션이 있으므로 공백 split 기반 파서를 쓰지 않는다. quoting, 줄바꿈 이어쓰기, @file 참조를 모두 처리한다.
→ curl manpage → everything.curl.dev — Command line options
2

Curl Body/Form Semantics Boundary

증거 ≠ 계약
--data, --data-binary, --data-urlencode, --form, --get 은 서로 다른 wire 결과를 만든다. 하나로 뭉뚱그리지 않고 각각의 인코딩을 그대로 재현한다. 다만 curl 한 줄은 실행 예시이지 schema 계약이 아니므로, operation 후보의 신뢰도를 보강하는 증거로만 쓰고 계약의 근거로 승격하지 않는다.
→ curl manpage
3

Talend Dump Mapping

계층 보존
Talend API Tester 는 Swagger/OpenAPI/HAR import 를 지원하고, Talend portal 의 Try flow 는 operation, query/header, BaseUrl, auth 환경변수를 함께 생성한다. 따라서 Talend 덤프의 project / service / scenario 계층은 평탄화하지 말고 provenance 와 환경 매핑으로 보존한다.
→ Talend API Tester — Importing requests → Talend Qlik Developer Portal
4

OpenAPI Linkback

operationRef
변환된 probe 와 export artifact 에는 원본으로 되돌아갈 참조를 반드시 저장한다. 가능하면 operationRef(JSON Pointer)를, 없으면 operationId 를 쓴다. OpenAPI 는 name clash 가능성 때문에 external reference 에서 operationRef 를 선호한다.
→ OpenAPI 3.1.0 Link Object
5

HAR Export

관측 기록
실행된 HTTP transaction 은 HAR 1.2 entries 로 내보낸다. request 에는 method, absolute URL, headers, cookies, queryString, postData 를 넣고, response 에는 status, headers, content, timing 을 넣는다. HAR 는 실행 관측 기록이고 계약이 아니다.
→ HAR 1.2 Spec
6

JUnit Export

CI 요약
JUnit XML 은 재현 artifact 가 아니라 CI 결과 요약이다. Hurl 8.0.1 의 JUnit report 는 .hurl 파일 하나를 testcase 하나로 매핑하며, assert error 는 failure, runtime error 는 error 로 표현한다. 이 매핑을 임의로 바꾸면 CI 대시보드의 실패 분류가 계약 실패와 환경 실패를 구분하지 못한다.
→ Hurl Running Tests → hurl::report::junit
7

Hurl Reproducer Export

재현 SSOT
api-kit 의 재현 단위는 .hurl 파일이다. Hurl 은 plain-text HTTP request, response assert, capture, variable chaining 을 한 파일에 담으므로 실패를 그대로 재실행할 수 있다. 외부 공유용으로 curl 명령이 필요하면 --curl 로 부가 산출물을 뽑되, 재현 SSOT 는 .hurl 로 유지한다.
→ Hurl Manual → Hurl File Format
8

Lossy Conversion Warning

손실 = 보고 대상
import / export 마다 source type, source version, 원본 hash, 처리하지 못한 필드 목록을 기록한다. unsupported / unknown 필드가 하나라도 있으면 경고를 낸다. 블랙박스 계약 검증에서 조용한 필드 손실은 곧 false pass 이므로, 손실은 무시가 아니라 보고 대상이다.
→ HAR 1.2 Spec
9

Artifact Schema Versioning

x- 확장
모든 artifact 는 버전 필드를 갖는다. OpenAPI 는 openapi, HAR 는 log.version 을 요구하며, api-kit 자체 artifact 도 schemaVersion 을 명시한다. 스펙이 정의하지 않는 부가 정보는 임의 필드로 흘리지 말고 OpenAPI 의 x- prefix 확장으로 보존한다.
→ OpenAPI 3.1.0 OpenAPI Object → HAR 1.2 Spec

artifact 별 역할과 신뢰 등급

artifact 방향 역할 계약 근거로 승격?
OpenAPI import 계약 설명 형식 가능
curl 덤프 import 실행 예시 — 신뢰도 보강 증거 불가 (상한 0.85)
Talend 덤프 import operation + 환경변수 계층 계층 보존 시 부분
HAR 양방향 transaction archive 불가
.hurl export 재현 SSOT 재실행 가능
JUnit XML export CI 결과 요약 불가
curl 명령 (--curl) export 공유용 부가 산출물 불가

--curl 은 Hurl 에서 curl 명령을 뽑는 기능이다. 반대 방향(curl 읽기)은 별도 파서가 담당한다.

안티패턴
변환 계층의 실패는 대부분 예외를 던지지 않는다. 결과 파일이 만들어지고, CI 는 초록색이고, 다만 내용이 틀려 있다.
안티패턴 문제
curl 덤프를 공백 split 으로 파싱 quoting, @file 참조, 반복 옵션이 깨져 잘못된 요청을 생성한다
HAR 를 OpenAPI 대체물로 사용 HAR 는 transaction archive 이지 schema / operation 계약이 아니다
JUnit 만 저장하고 .hurl·HAR 를 폐기 CI 요약만 남아 실패를 재현할 수 없다
Talend 환경변수·auth 값을 .hurl 에 inline 시크릿이 파일에 박히고 환경이 고정돼 다른 stage 에서 못 돌린다
linkback 없는 export 실패를 원래 OpenAPI operation 으로 되돌릴 수 없어 계약 diff 가 불가능하다

① curl 파싱 — 공백 split vs shell tokenization

BAD quoting·반복 옵션·@file 이 전부 깨진다 
tokens = line.split(" ")
opts   = dict(zip(tokens[1::2], tokens[2::2]))

# 입력
curl -H 'X-Tag: a b' -H 'X-Tag: c' \
     --data @body.json https://api.example.com/v1/orders

# 결과
#  X-Tag 는 뒤 값만 남고 'a b' 는 두 토큰으로 쪼개짐
#  @body.json 은 리터럴 문자열로 전송됨
GOOD shell tokenizer + curl option 의미론 
argv    = shell_tokenize(line)      # quoting · 줄바꿈 이어쓰기
parsed  = curl_optspec.parse(argv)  # 옵션은 URL 앞뒤 어디든

headers = [("X-Tag","a b"), ("X-Tag","c")]   # 반복 유지
body    = read_file("body.json")             # @file 해석
encoding= "--data"                           # --form 과 구분

confidence = min(computed, 0.85)   # 증거이지 계약이 아니다

원칙 1 · 2. --data / --data-binary / --data-urlencode / --form / --get 은 서로 다른 wire 결과이므로 인코딩 종류를 값과 함께 보존한다.

② HAR queryString — dict 변환 vs 배열 유지

BAD 반복 name 의 앞 값이 조용히 사라진다 
{
  "request": {
    "url": "/v1/posts?tag=a&tag=b",
    "queryString": { "tag": "b" }
  }
}

# ?tag=a&tag=b 였는데 a 가 없어졌다
# 예외도 경고도 없다
GOOD list of {name, value} 로 유지, URL 은 absolute 
{
  "request": {
    "url": "https://api.example.com/v1/posts?tag=a&tag=b",
    "queryString": [
      { "name": "tag", "value": "a" },
      { "name": "tag", "value": "b" }
    ]
  }
}

# fragment(#...) 는 제거, base URL 을 합쳐 절대 URL

원칙 5 · 8. HAR 는 관측 기록이므로 관측한 그대로가 아니면 기록으로서 가치가 없다.

BAD — CI 요약만 보관
파이프라인이 JUnit XML 만 아티팩트로 올리고 .hurl 과 HAR 를 워크스페이스와 함께 버린다. 실패 목록은 남지만 요청 본문도, 응답도, 재실행 수단도 없다.
결과 — 실패한 계약을 재현하려면 사람이 로그를 읽고 요청을 손으로 복원해야 한다. 그 복원본은 원본과 같다는 보장이 없다.
GOOD — SSOT + 파생물 동시 보관
.hurl(재현) · HAR(관측) · JUnit(요약) 을 함께 보관하고, 각 artifact 에 operationRef linkback 과 schemaVersion 을 박는다.
결과 — CI 실패 한 건에서 원본 operation 까지 한 번에 되돌아간다. .hurl 을 그대로 다시 돌리면 같은 실패가 재현된다.
BAD — 미지원 필드 조용히 폐기
import 파서가 모르는 키를 만나면 건너뛴다. 로그에도 남지 않는다. Talend 의 project / service 계층은 평탄화되고, auth 환경변수는 값째로 .hurl 에 박힌다.
결과 — 손실이 곧 false pass 다. 검증은 통과하는데 실제 요청과 다르다.
GOOD — 손실을 레코드로
변환마다 source type · source version · 원본 hash · 미처리 필드 목록을 남기고, 미처리 필드가 1 개 이상이면 경고를 낸다. 환경변수는 참조로만 남긴다.
결과 — 무엇을 못 읽었는지가 산출물 안에 있어 다음 사이클의 작업 목록이 된다.
Gotchas — 변환 실행 전 확인
아래 항목은 전부 실제 포맷 사양에서 나온 함정이다. import / export 파이프라인을 확정하기 전에 대조하라.
  • ! HAR queryString 은 같은 name 이 반복될 수 있다. map / dict 로 변환하면 ?tag=a&tag=b 의 뒤 값만 남아 조용히 손실된다. 배열(list of {name, value})로 유지한다.
  • ! HAR request URL 은 absolute URL 이고 fragment 를 포함하지 않는다. 상대 경로나 # 이후를 그대로 넣으면 스펙 위반이다. base URL 을 합쳐 절대 URL 로 만들고 fragment 는 버린다.
  • × Hurl --curl 은 export 전용이다. Hurl 에서 curl 명령을 뽑는 기능이지 curl 을 읽어들이는 기능이 아니다. curl import 는 별도 파서가 필요하다.
  • ! Talend 의 operation-level Try 는 draft request 만 만든다. 전체 project 가 생성된다고 가정하고 project / service 계층을 찾으면 비어 있다. 단건 draft 는 "불완전한 관측치" 로 취급한다.
  • ✓ HAR postData 에서 text 와 params 를 동시에 채우지 않았는지 확인했다 — 상호 배타다.
  • ✓ HAR timing 이 milliseconds 이고, 값이 없는 필드가 0 이 아니라 -1 로 기록되는지 확인했다.
  • ✓ 모든 export artifact 에 operationRef(없으면 operationId) linkback 이 있는지 확인했다(원칙 4).
  • ✓ JUnit 에서 assert error 가 failure, runtime error 가 error 로 나뉘어 있는지 확인했다 — 이 구분이 계약 실패와 환경 실패를 가른다(원칙 6).
  • ✓ .hurl 에 auth 값·시크릿이 inline 되지 않고 환경 참조로만 남았는지 확인했다.
  • ✓ 미처리 필드 목록이 비어 있다면 그것이 진짜 무손실인지, 아니면 파서가 모르는 키를 조용히 건너뛴 것인지 확인했다(원칙 8).
