베이스라인 거버넌스와 승격

실제 응답을 SSOT 로 삼을 때 그 응답을 무엇으로 저장하고, 언제 새 truth 로 승격할지 정하는 규칙. 보관 형식, 승격 리뷰, 환경 lineage, 만료를 다룬다. v0.1.0 · 최종 갱신 2026-09-04

확정 결정 — raw 를 보관한다, 단 시크릿 값만 마스킹한 raw

설계문서 §12 확정 결정표의 「baseline raw 보관」 항목은 보관 이다. 시크릿 값만 마스킹한 raw 응답을 남긴다 (2026-09-04 사용자 확정). 요약본이나 스키마만 남기면 값 drift 를 재현할 수 없고, 마스킹 없는 raw 를 남기면 저장소가 자격증명 저장소가 된다.

같은 표의 「prod 스냅샷」 항목은 커밋하지 않음, 스키마만 커밋 이다. 두 결정은 충돌하지 않는다 — dev/stg 는 마스킹된 raw 를 커밋해 회귀 기준선으로 쓰고, prod 는 값이 아니라 형태만 남긴다.

마스킹은 Hurl 에 맡기지 않는다. 설계문서 §8.2 는 킷 자체 scrubber 를 필수 게이트로 두고, redaction 에 실패하면 스냅샷을 저장하지 않는 fail-closed 동작을 규정한다.

01 · 승격 게이트

baseline 승격은 파일을 덮어쓰는 동작이 아니라 다섯 단계를 통과하는 절차다. 앞 단계를 건너뛰면 회귀가 새 truth 로 올라간다. CI 는 이 절차를 자동으로 밟을 수 없다 — 자동 write 허용 횟수는 0 이다.

Gate 1 — 실행 diff 를 확보한다 /api-verify 가 old/new 차이를 낸다. diff 를 보지 않은 승격은 회귀를 truth 로 만드는 행위다.
Gate 2 — 정규화 normalize · mask 규칙 확정 timestamp·uuid·정렬 순서를 그대로 승격하면 이후 모든 실행이 실패한다. 규칙을 먼저 정하고 baseline 과 함께 커밋한다.
Gate 3 — lineage 어느 환경의 진실인가 환경·브랜치·provider/API 버전을 붙인다. lineage 없는 baseline 은 비교 대상이 되지 못한다.
Gate 4 — 리뷰 사람이 승인한다 기본 1명, breaking schema drift 또는 prod lineage 변경은 2명. 코드 리뷰와 같은 절차를 탄다.
Gate 5 — 기록 승인을 증거로 남긴다 old/new diff, 승인자, 이유, 근거 run, schema version. 이 기록 자체가 다음 판정의 입력이다.
차단 규칙. CI 는 이 다섯 게이트를 대신 밟지 않는다. diff 가 실패한 순간 baseline 을 자동 갱신하지 않고, 갱신은 명시적 promote 명령과 리뷰 메타데이터가 있을 때만 일어난다. 자동 승격을 허용하면 회귀가 다음 실행부터 green 이 된다. 
실행 결과
  │
  ├─ 기대와 일치 ────────────────────────► baseline 유지
  │
  └─ diff 발생
       │
       ├─ 의도치 않은 변경 ──────────────► 회귀. 게이트 파괴. 승격 금지
       │
       └─ 의도된 변경
            │
            ├─ Gate 2  normalize / mask 규칙 확정
            ├─ Gate 3  env · branch · API version lineage 부착
            ├─ Gate 4  승인자 1명 (breaking · prod 는 2명)
            └─ Gate 5  drift acceptance record 작성
                        │
                        └─► 새 baseline 커밋
                             dev/stg : 마스킹된 raw 응답
                             prod    : 스키마 계약만 (raw 는 gitignore)

승인본과 실행 산출물은 같은 파일에 섞지 않는다. 섞는 순간 "무엇이 승인된 값인지"가 사라진다.

02 · 보관 형식 확정 결정

baseline 은 raw 를 보관한다 — 단 시크릿 값만 마스킹한 raw 다. 마스킹 규칙 자체를 baseline 과 함께 버전 관리한다.

dev · stg

마스킹된 raw 를 커밋

값까지 커밋해 회귀 diff 의 기준선으로 쓴다. 토큰·쿠키·Authorization·API key 값은 마스킹된 상태다.

prod

스키마 계약만 커밋

실 고객 데이터가 들어오므로 raw 스냅샷은 .gitignore 하고 형태만 남긴다. 증거는 로컬·CI artifact 로만 보관한다.

공통

마스킹 규칙도 함께 커밋

규칙이 바뀌면 같은 응답의 baseline 이 달라진다. 규칙을 버전 관리하지 않으면 diff 를 재현할 수 없다.

결정 항목확정 내용근거
baseline raw 보관 보관. 시크릿 값만 마스킹한 raw 를 남긴다 설계문서 §12 (2026-09-04 사용자 확정)
prod 스냅샷 커밋하지 않음, 스키마만 커밋 설계문서 §12 · §8.3
redaction 주체 Hurl 이 아니라 킷 자체 scrubber. redaction 실패 시 스냅샷을 저장하지 않는다 (fail-closed) 설계문서 §8.2
마스킹 대상 키 이름 deny list(token·password·authorization·secret·ssn 등) + 값 형태 정규식 설계문서 §8.2

키 이름만으로는 못 잡는 값이 있다. 이메일·전화번호·JWT 형태·카드번호 형태는 값 패턴으로 걸러야 한다.

03 · 원칙

열 개 원칙은 baseline 의 생애를 따라간다. 1–3 은 무엇으로 저장하는가, 4–7 은 언제 새 truth 가 되는가, 8–10 은 언제 신뢰를 잃는가.

1

Baseline Immutability

보관

승인된 baseline 은 임의로 덮어쓰는 캐시가 아니라 리뷰를 거친 증거다. ApprovalTests 관례처럼 승인본(.approved)은 소스 컨트롤에 두고 실행 산출물(.received)은 생성물로만 취급한다.

둘을 같은 파일에 섞으면 "무엇이 승인된 값인지"가 사라진다.

→ ApprovalTests — Approval files
2

Masked-raw Baseline

확정 결정

baseline 은 raw 를 보관한다 — 단 시크릿 값만 마스킹한 raw 다. 요약본이나 스키마만 남기면 값 drift 를 재현할 수 없고, 마스킹 없는 raw 를 남기면 저장소가 자격증명 저장소가 된다.

마스킹 대상은 토큰·쿠키·Authorization·API key 이며, 마스킹 규칙 자체를 baseline 과 함께 버전 관리한다.

→ OWASP Secrets Management Cheat Sheet 보관 형식은 api-kit 확정 결정 (설계문서 §12)
3

Contract Versioning — prod 는 스키마만 커밋

버전

prod 환경의 raw 스냅샷은 커밋하지 않고 스키마 계약만 커밋한다. OpenAPI 가 openapi(feature set)와 info.version(API 계약 버전)을 구분하듯, baseline 도 contract version 과 evidence version 을 분리해 기록한다.

prod 증거는 로컬·CI artifact 로만 보관한다.

→ OpenAPI Specification v3
4

Promotion Review

리뷰

baseline 승격은 코드 리뷰 대상이다. Jest 문서도 snapshot 을 코드처럼 커밋·리뷰하고, 실패 원인을 확인하지 않은 채 재생성하는 습관을 피하라고 명시한다.

diff 를 보지 않은 승격은 회귀를 truth 로 만드는 행위다.

→ Jest Snapshot Testing
5

Env-specific Lineage

lineage

baseline 은 환경, 브랜치, provider/API 버전 lineage 를 함께 갖는다. Pact 의 pending 여부도 contract content, verification result, provider branch 조합으로 계산된다.

lineage 없는 baseline 은 어느 환경의 진실인지 알 수 없어 비교 대상이 되지 못한다.

→ Pact Pending Pacts
6

Drift Acceptance Record

기록

accepted drift 에는 old/new diff, 승인자, 이유, 근거가 된 실행(run), 관련 schema version 을 남긴다.

Pact 가 verification result 를 broker 에 publish 해 배포 가능성 판단에 쓰듯, 승인 기록 자체가 다음 판정의 입력이다.

→ Pact Provider Verification
7

Branch Baseline Policy

브랜치

main/release baseline 과 feature/WIP baseline 을 같은 파일에 섞지 않는다.

Pact pending pacts 는 새 계약이 provider 빌드를 불필요하게 깨지 않게 하되, 한 번 accepted 된 뒤의 실패는 회귀로 처리한다. 같은 분리를 브랜치 축에도 적용한다.

→ Pact Pending Pacts
8

Expiry Warning

만료

live response 기반 baseline 은 영구 진실이 아니다. 시크릿에 lifecycle 과 만료가 있듯 baseline 에도 "언제 다시 검증할지" 를 명시한다.

만료된 baseline 은 품질 게이트에서 경고 또는 차단 대상으로 올린다.

→ OWASP Secrets Management — Secret lifecycle
9

Human Override Audit

감사

override 는 이유와 행위자가 남는 감사 이벤트여야 한다. GitHub push protection 도 bypass 시 reason, alert, audit log 를 남기는 모델을 제공한다.

사유 없는 강제 승격은 로그상 정상 승격과 구별되지 않는다.

→ GitHub Push Protection
10

Secret-free Baselines

이중 방어

마스킹에만 의존하지 않고 gitignore 와 secret scanning 으로 저장소 유입을 이중으로 막는다. OWASP 와 GitHub 모두 hardcoded credential 을 저장소에 넣지 않는 것을 기본 통제로 둔다.

마스킹은 실수할 수 있고 스캐닝은 그 실수를 잡는 계층이다.

→ OWASP Secrets Management Cheat Sheet → GitHub Push Protection

승격 기록에 남기는 필드

무엇이 달라졌나

old/new diff. 승인된 변경의 실제 내용이다.

누가, 왜

승인자와 이유. "expected updated" 만으로는 6개월 뒤 판단 근거가 되지 못한다.

무엇에 근거했나

근거가 된 실행(run)과 관련 schema version. 배포 시점도 함께 남긴다.

05 · 안티패턴

승격 절차가 무너지는 지점은 대체로 셋 중 하나다. 자동 승격, 환경 혼합, 사유 없는 기록.

Bad — 실패하면 갱신

diff 실패 시 baseline 을 자동 승격한다. "빨간불이 뜨면 기준을 맞춘다"는 습관이다.

회귀가 새 truth 가 되어 다음 실행부터 green 이 된다. 게이트는 통과하지만 실제 계약은 이미 깨져 있다.

Good — 승격은 별도 명령

CI 자동 write 는 0회. 갱신은 명시적 promote 명령과 리뷰 메타데이터가 있을 때만 일어난다.

실패는 실패로 남고, 승격은 사람이 diff 를 본 뒤에만 일어난다.

Bad — 환경 하나로 합치기

staging/prod/local 이 하나의 baseline 파일을 공유한다.

환경 차이가 회귀로, 회귀가 환경 차이로 오판된다. 어느 쪽으로 틀려도 게이트는 신뢰를 잃는다.

Good — lineage 로 분리

환경·브랜치·provider 버전을 baseline 에 붙이고, main/release 와 feature/WIP 을 섞지 않는다.

같은 엔드포인트라도 lineage 가 다르면 다른 baseline 이다.

BAD사유 없는 승격 기록
promoted:
  at: 2026-09-04
  note: "expected updated"

6개월 뒤 그 변경이 의도된 것인지 사고인지 판단할 근거가 없다. 강제 승격과 정상 승격이 로그에서 구별되지 않는다.

GOOD감사 가능한 기록
promoted:
  at: 2026-09-04
  by: reviewer-a
  reason: "orders API v2 - status enum 확장"
  run: verify/2026-09-04T02:11Z
  schema_version: 2.3.0
  lineage: { env: stg, branch: main }
  diff: { added: [status.partial], removed: [] }

승인 기록 자체가 다음 판정의 입력이 된다. override 였다면 이유와 행위자가 같은 자리에 남는다.

필드 구성은 원칙 6(Drift Acceptance Record)이 요구하는 항목을 YAML 형태로 보인 예시다. 실제 파일 포맷을 규정한 것은 아니다.

06 · Gotchas 체크리스트

승격 명령을 실행하기 전에 확인한다. Gate 2 를 건너뛰면 이후 모든 실행이 빨간불이 되고, Gate 5 를 건너뛰면 6개월 뒤 아무도 이유를 모른다.

  • !normalize · mask 규칙을 승격 전에 확정했는가. baseline 은 비결정적 필드를 영구화하기 쉽다. timestamp, uuid, 정렬 순서를 그대로 승격하면 이후 모든 실행이 실패한다. 규칙을 baseline 과 함께 커밋한다.
  • ✗prod raw 스냅샷이 커밋 대상에 섞이지 않았는가. prod evidence 커밋은 0건 이고 스키마 계약만 커밋한다. 한 번 히스토리에 들어가면 지워도 남는다.
  • !스키마는 배포보다 먼저 merge 될 수 있다. live response 와 schema version 의 배포 순서를 기록하지 않으면 "아직 배포되지 않은 계약"을 회귀로 오판한다. lineage 에 배포 시점을 남긴다.
  • ✗gitignore 는 과거 유출을 제거하지 않는다. 이미 커밋된 비밀은 무시 규칙을 추가해도 히스토리에 남는다. 발견 즉시 rotate/revoke 가 필요하며, 마스킹 규칙 추가만으로 해결됐다고 보고하지 마라.
  • !feature branch baseline 을 main truth 로 승격하지 않았는가. 아직 지원되지 않는 계약이 accepted 로 오인되어, 실제 배포된 API 와 어긋난 기준이 게이트를 통과시킨다.
  • ✓승인 기록에 다섯 필드가 다 있는가. old/new diff, 승인자, 이유, 근거 run, schema version. 하나라도 비면 다음 판정의 입력으로 쓸 수 없다.
  • ✓승인자 수가 변경 성격에 맞는가. 기본 1명, breaking schema drift 또는 prod lineage 변경은 2명.
  • ✓승인본과 실행 산출물이 분리되어 있는가. ApprovalTests 관례대로 승인본은 커밋하고 .received.* 는 커밋하지 않는다.
  • !대형 artifact 를 별도로 스캔했는가. public repo push 가 50MB 를 넘으면 push protection scan 이 skip 될 수 있다. 마스킹만 믿지 말고 스캐닝 계층을 함께 둔다.
  • ✓만료일을 확인했는가. 30일 경과는 warning, 90일 경과는 block. 만료된 baseline 의 green 은 검증이 아니라 착각이다.
