인증·시크릿 수명주기

OAuth2 client_credentials 와 커스텀 로그인(id/pw → JSON 토큰)을 다루는 규칙. 자격증명 주입, 토큰 캡처·갱신, 로그 마스킹의 한계를 정의한다. MFA·CSRF 는 범위 밖이다. v0.1.0 · 최종 갱신 2026-09-04

마스킹은 Hurl --secret 에 맡기지 않는다

Hurl 의 --secret 은 stderr 로그와 리포트만 exact match 로 가린다. stdout 의 HTTP 응답, --include, --json 출력, JSON 리포트에 저장된 원본 응답 body 는 가리지 않는다. Hurl 이 stdout 을 "unaltered output" 으로 취급하기 때문이다.

그래서 api-kit 은 스냅샷 저장 직전에 킷 자체 scrubber 를 통과시킨다. 저장·렌더되는 데이터는 전부 이 scrubber 를 지난 것이고, 지나지 않은 데이터는 어디에도 남기지 않는다 — 설계문서 §8.2 결정. 이건 선택이 아니라 필수 게이트다.

scrubber 는 네 가지로 구성된다. 키 이름 deny list(token, password, authorization, secret, ssn 등), 값 형태 정규식 (키 이름만으로는 못 잡는 이메일 · 전화번호 · JWT 형태 · 카드번호 형태), 도메인별 deny path 추가, 그리고 redaction 실패 시 스냅샷을 저장하지 않는 fail-closed 규칙.

이 문서가 결정하는 것

자격증명은 세 구간을 지난다. 주입되고, 캡처되어 재사용되고, 마지막에 기록으로 남는다. 구간마다 다른 규칙이 걸리고, 마지막 구간이 가장 자주 새는 곳이다.

01 · 주입 env 별 auth profile dev / stg / prod 가 각자 token endpoint · client id · scope · credential source 를 가진다. 공유하지 않는다.
02 · 순환 캡처와 TTL 갱신 첫 entry 에서 토큰을 capture 하고 redact 로 secret 처리한다. expires_in 기준으로 갱신한다.
03 · 기록 저장 전 scrubber 응답을 artifact 로 남기기 전에 킷 자체 redaction 레이어를 통과시킨다. 실패하면 저장하지 않는다. 
credential source            토큰 순환                     기록
─────────────────            ──────────                    ────
--secret / secrets file  ┐
.api/credentials.local.json ├─→ 첫 entry capture  ─→ redact ─→ ┐
외부 secret store        ┘        │                            │
                                  │ expires_in (TTL)           ↓
                                  └─→ expires_at − max(60s, TTL의 10%)
                                                               │
                                          ┌────────────────────┴───────────────┐
                                          │  api-kit scrubber (fail-closed)    │
                                          │   key deny list / 값 형태 정규식     │
                                          └────────────────────┬───────────────┘
                                                               ↓
                                                    snapshot · report · ui.html

--secret 은 위 그림의 마지막 화살표를 책임지지 않는다. 그 자리에 킷의 scrubber 가 들어간다.

원칙 9

앞의 다섯은 자격증명을 어떻게 다룰지, 뒤의 넷은 그 결과를 어떻게 읽고 남길지를 정한다.

1

env 별 auth profile 분리

no sharing

dev / stg / prod 각각 token endpoint, base URL, client id, scope, credential source 를 따로 정의한다. 한 profile 을 여러 env 가 공유하지 않는다. OAuth 보안 BCP 도 명시적 metadata 가 misconfiguration 을 줄인다고 본다 — profile 이 곧 그 metadata 다.

→ RFC 9700 §2.6 OAuth 2.0 Security BCP
2

토큰은 첫 entry 에서 캡처

capture + redact

OAuth client_credentials 응답이나 커스텀 로그인 응답의 JSON 토큰은 파일 첫 entry 에서 capture 하고 이후 entry 에서 변수로 참조한다. 캡처된 동적 값은 Hurl redact 로 secret 처리하여 이후 로그 · 리포트 마스킹 대상에 넣는다.

→ Hurl — Capturing Response
3

TTL 기반 갱신

expires_in

OAuth token response 의 expires_in 은 초 단위 lifetime 이다. expires_in=3600 이면 1시간이다. 만료 정보가 응답에도 profile 기본값에도 없으면 자동 갱신을 추측하지 말고 금지한다 — 매 실행 재발급으로 되돌린다.

→ RFC 6749 §5.1 Successful Response
4

시크릿은 주입만

0600

client secret, id/password, bearer token 은 .hurl 본문에 쓰지 않는다. --secret, secrets file, 외부 secret store 중 하나로 주입한다. api-kit 은 자격증명을 .api/credentials.local.json 에 두고 gitignore 와 파일 권한 0600 을 강제한다.

→ Hurl — Templates / Secrets → OWASP Secrets Management Cheat Sheet
5

리포트 전 마스킹 등록

exact match

Hurl --secret 은 stderr 로그와 리포트에서 해당 값을 exact match 로 가린다. 부분 일치나 인코딩 변형은 잡지 못한다. base64 인코딩본, 대소문자 변환본, Bearer 접두 포함본 같은 변형값은 각각 별도 secret 으로 등록해야 한다.

→ Hurl — Templates / Secrets
6

stdout 은 마스킹되지 않는다

unaltered output

Hurl 은 HTTP 응답 stdout 을 "unaltered output" 으로 취급한다. 기본 stdout, --include, --json stdout, JSON 리포트의 raw response dump 에는 secret 이 그대로 남는다. 따라서 응답 본문을 artifact 로 남길 때는 api-kit 이 별도 redaction 레이어를 거쳐야 한다 — --secret 에 위임할 수 없다.

→ Hurl — Templates / Secrets → Hurl — JSON Report
7

bearer 는 헤더로만 전달

no query param

bearer token 은 Authorization: Bearer <token> 헤더로 보낸다. URI query parameter 방식은 쓰지 않는다. RFC 6750 은 header 방식을 권고하고, query 방식은 로그 · Referer · 브라우저 히스토리에 남는 문제로 비권장한다.

→ RFC 6750 §2.1 Authorization Request Header Field
8

인증 실패 분류

2 axes

토큰 발급 실패와 리소스 접근 실패를 다른 축으로 분류한다. token endpoint 오류는 invalid_client, invalid_grant, invalid_scope 등으로, 리소스 접근 오류는 invalid_token(401 후보)과 insufficient_scope(403 후보)로 나눈다. 전부 "login failed" 로 합치면 재시도 판단이 불가능해진다.

→ RFC 6749 §5.2 Error Response → RFC 6750 §3.1 Error Codes
9

scope 최소화와 granted scope 검증

least privilege

요청 scope 는 검증에 필요한 최소로 잡는다. 응답 scope 가 요청과 다르면 요청값이 아니라 실제 granted scope 를 기준으로 계약을 검증한다. OAuth BCP 도 access token 권한을 최소 필요 범위로 제한하라고 규정한다.

→ RFC 6749 §3.3 Access Token Scope → RFC 9700 §2.3
마스킹 경계 · 어디가 가려지고 어디가 안 가려지는가

--secret 이 닿는 채널과 닿지 않는 채널을 외워 두는 것보다, "저장되는 건 전부 scrubber 를 지난 것" 이라는 한 문장이 안전하다.

masked stderr 로그

Hurl --secret 이 exact match 로 가린다. 변형값은 별도 등록해야 가려진다.

masked 리포트 (HTML/TAP 등)

등록된 secret 값에 한해 가려진다. 리포트에 포함된 raw response dump 는 예외다.

raw 기본 stdout

HTTP 응답은 "unaltered output". 토큰이 평문으로 나온다.

raw --include

응답 헤더까지 그대로 출력한다. Authorization 계열이 여기서 샌다.

raw --json stdout

기계 판독용 출력에도 마스킹이 적용되지 않는다.

raw JSON 리포트의 raw body 파일

원본 응답 body 가 그대로 파일로 떨어진다. artifact 보관 시 가장 위험한 경로.

킷 자체 scrubber — 저장·렌더의 유일한 입구

api-kit 은 --secret 을 마스킹의 최종 방어선으로 쓰지 않는다. 스냅샷 · 리포트 · ui.html 에 들어가는 데이터는 저장 직전에 킷의 scrubber 를 통과한 것만 허용한다. 통과하지 않은 데이터는 렌더 대상이 아니다.

1. 키 이름 deny list — token, password, authorization, secret, ssn 등.
2. 값 형태 정규식 — 키 이름만으로는 못 잡는다. 이메일, 전화번호, JWT 형태, 카드번호 형태를 값으로 판정한다.
3. 도메인별 deny path — 프로젝트가 경로 단위로 추가한다.
4. fail-closed — redaction 이 실패하면 스냅샷을 저장하지 않는다. 부분 저장도 하지 않는다.
출처 없음 — 이 킷의 설계 결정 (설계문서 §8.2 "Redaction — Hurl 에 맡기면 안 되는 지점")
인증 실패 두 축

실패를 뭉개면 "갱신하면 되는 실패" 와 "재시도해도 안 되는 실패" 가 구분되지 않는다. 발급 축과 접근 축을 분리해서 기록한다.

축 1 — token endpoint 오류

invalid_client클라이언트 인증 실패. 자격증명 자체를 고쳐야 한다.
invalid_grantgrant 가 무효 · 만료 · 폐기됨.
invalid_scope요청 scope 가 유효하지 않거나 범위를 넘었다.
RFC 6749 §5.2error response 정의가 여기 있다.

축 2 — 리소스 접근 오류

invalid_token401 후보. 토큰 만료 · 폐기 · 형식 오류.
insufficient_scope403 후보. 토큰은 유효하지만 권한이 모자란다.
RFC 6750 §3.1bearer token error code 정의가 여기 있다.
granted scope응답 scope 가 요청과 다르면 granted 쪽을 계약 기준으로 쓴다.
판정: invalid_token 은 갱신 후 재시도 후보다. insufficient_scope 는 같은 profile 로 몇 번을 다시 보내도 결과가 같다 — 재시도가 아니라 scope 재협상 대상이다. 두 개를 "login failed" 로 합치면 이 구분이 사라진다.
수치 기준

RFC 에서 온 값, Hurl 문서에서 온 값, 이 킷이 확정한 값을 근거 열로 구분한다. 추론 과 api-kit 확정 결정 은 성격이 다르다 — 앞은 조정 가능, 뒤는 이 킷의 규약이다.

항목값근거
bearer token 권장 lifetime 1시간 이하 RFC 6750 §5.3
expires_in=3600 1시간 RFC 6749 §5.1
--secret 등록 단위 exact value 1개당 secret 1개 (변형값 N개면 +N개) Hurl Templates/Secrets
token response 캐시 헤더 Cache-Control: no-store, Pragma: no-cache RFC 6749 §5.1
갱신 시점 expires_at − max(60s, TTL의 10%) 추론 — 만료 경계 요청 실패 회피
자격증명 파일 .api/credentials.local.json, gitignore 강제, 권한 0600 api-kit 확정 결정
토큰 캐시 위치 repo 밖 ~/.cache/api-kit/, 디렉토리 0700 / 파일 0600 api-kit 확정 결정

TTL 1시간(3600초) 토큰의 갱신 시점을 계산하면 이렇게 된다. TTL의 10% 가 360초이고 60s 보다 크므로 360초 전에 갱신한다.

토큰 유효 구간 3240s
갱신 여유 구간 360s
하한 (max 의 다른 항) 60s

막대는 expires_in=3600 을 100% 로 두고 그린 것이다. 짧은 TTL 에서는 60s 하한이 이겨서 여유 구간이 상대적으로 커진다.

만료 정보가 없으면: 응답에도 profile 기본값에도 expires_in 이 없으면 갱신 주기를 추측하지 않는다. 자동 갱신을 끄고 매 실행 재발급으로 되돌린다. 추측한 TTL 은 만료 직전 구간에서 조용히 401 을 만든다.
안티패턴

다섯 가지 모두 "한 번 새면 되돌릴 수 없는" 형태다. git 히스토리, 액세스 로그, 저장된 artifact 는 사후에 지워도 이미 복제된 뒤일 수 있다.

BAD .hurl 본문에 자격증명 직접 작성 
POST https://auth.example.com/oauth/token
[FormParams]
grant_type: client_credentials
client_id: acme-web
client_secret: s3cr3t-live-9f2a

HTTP 200
[Captures]
token: jsonpath "$.access_token"
GOOD 주입 + capture 시점 redact 
POST {{token_endpoint}}
[FormParams]
grant_type: client_credentials
client_id: {{client_id}}
client_secret: {{client_secret}}

HTTP 200
[Captures]
token: jsonpath "$.access_token" redact

# 실행:
#   hurl --secret client_secret=... \
#        --variables-file .api/env.dev

.hurl 에 쓴 secret 은 git 히스토리에 영구 기록된다. 되돌릴 수 없다. 자격증명은 .api/credentials.local.json(gitignore 강제 · 0600) 또는 외부 secret store 로만 들어온다.

BAD --secret 만 믿고 stdout 을 artifact 로 저장 
hurl --test --json \
  --secret token=$TOKEN \
  cases/me.hurl > .api/snapshots/me.json

# .api/snapshots/me.json 안:
#   "Authorization": "Bearer eyJhbGciOi..."
# stdout 은 마스킹 대상이 아니다
GOOD 킷 scrubber 를 통과한 데이터만 저장 
hurl --test --json \
  --secret token=$TOKEN \
  cases/me.hurl \
  | api-kit scrub --profile dev \
  > .api/snapshots/me.json

# scrub 단계:
#   key deny list + 값 형태 정규식
#   실패하면 exit != 0, 파일을 쓰지 않는다

저장 경로에 scrubber 가 없으면 --secret 을 아무리 정확히 등록해도 평문 토큰이 파일로 남는다. fail-closed 이므로 redaction 이 실패한 응답은 스냅샷 자체가 생성되지 않는다.

BAD — query string 으로 토큰 전달

GET /me?access_token=... 형태로 보낸다. 액세스 로그 · Referer · 프록시 로그에 토큰이 남고, 이 경로들은 대부분 킷의 scrubber 바깥이라 사후 회수가 불가능하다.

GOOD — Authorization 헤더

Authorization: Bearer <token> 헤더로만 보낸다. RFC 6750 이 권고하는 방식이고, 헤더는 로그 정책으로 통제할 수 있는 지점이다.

BAD — env 간 자격증명 공유

prod 와 stg 가 같은 client credential 또는 같은 token audience 를 쓴다. stg 유출이 그대로 prod 침해가 되고, audience 검증이 무의미해진다.

GOOD — profile 완전 분리

env 마다 token endpoint · client id · scope · credential source 를 따로 둔다. prod auth 프로파일과 토큰 캐시는 다른 환경과 물리적으로 분리한다.

BAD — 실패를 한 덩어리로

만료 · 폐기 · 권한 부족을 모두 "login failed" 로 기록한다. 갱신하면 되는 실패와 재시도 불가 실패가 구분되지 않아, 게이트가 무한 재시도로 빠지거나 반대로 조기 포기한다.

GOOD — 두 축으로 태깅

token endpoint 오류(invalid_client / invalid_grant / invalid_scope)와 리소스 접근 오류(invalid_token / insufficient_scope)를 분리 기록한다.

Gotchas · 실행 전 확인

아래 중 하나라도 미확인이면 실제 자격증명으로 실행하지 마라. 마스킹은 사후에 고칠 수 없는 종류의 결함이다.

  • × --secret 은 stdout 응답을 가리지 않는다 — stderr 로그와 리포트만 마스킹한다. 기본 stdout, --include, --json stdout, JSON 리포트의 raw response body 파일에는 secret 이 평문으로 남는다. 응답 저장 경로에 킷 scrubber 를 걸었는가.
  • ! --secret 은 exact value 매칭이다 — 값 하나당 등록 하나다. base64 본, 대소문자 변환본, Bearer 접두 포함본처럼 변형이 N개면 secret 도 N개를 따로 등록해야 한다. 하나라도 빠지면 그 형태로 로그에 노출된다.
  • ! redact capture 는 소급 적용되지 않는다 — 이후 로그 · 리포트 마스킹에는 유효하지만, 이미 출력된 원본 응답을 지우지는 못한다.
  • ! Hurl 옵션 우선순위는 env < CLI < [Options] — 파일 안 [Options] 가 profile 설정을 덮어쓴다. profile 충돌은 실행 전에 api-kit 이 먼저 잡아야 한다.
  • ✓ 저장·렌더되는 데이터가 전부 킷 scrubber 를 통과했는가. 통과하지 않은 경로(직접 > 리다이렉션, 수동 복사)가 하나라도 남아 있지 않은가.
  • ✓ scrubber 가 fail-closed 로 동작하는가. redaction 실패 시 스냅샷이 저장되지 않아야 한다 — 경고만 찍고 저장하면 fail-open 이다.
  • ✓ .api/credentials.local.json 이 gitignore 에 있고 권한이 0600 인가. 이미 추적 중인 파일은 gitignore 로 빠지지 않는다 — 추적 검사를 함께 했는가.
  • ✓ 토큰 캐시가 repo 밖(~/.cache/api-kit/, 디렉토리 0700 / 파일 0600)에 있는가. prod 캐시가 다른 env 캐시와 분리되어 있는가.
  • ✓ 응답의 granted scope 를 요청 scope 와 비교했는가. 다르면 granted 를 기준으로 계약을 검증하고 있는가.
  • ✓ expires_in 이 응답에도 profile 에도 없을 때 자동 갱신이 꺼지는가. 추측한 TTL 로 갱신 주기를 만들고 있지 않은가.
