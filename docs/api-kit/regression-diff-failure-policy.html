api-kit / regression diff failure policy

회귀 diff 실패 분류 정책

baseline 과 실제 응답의 차이를 어떤 실패로 부를지 정하는 판단 규칙. 상태·스키마·값 drift 분류, 계약 실패와 환경 실패의 분리, exit code 계약, CI artifact 매핑을 다룬다. v0.1.0 · 최종 갱신 2026-09-04

이 문서의 중심축 — 계약 실패와 환경 실패를 exit code 로 가른다

서버가 죽은 것과 계약이 깨진 것은 대응이 다르다. 앞은 재시도·인프라 확인이고 뒤는 코드 리뷰다. 둘을 같은 실패로 묶으면 CI 대시보드는 원인을 집계하지 못하고, 게이트는 노이즈로 채워진다. api-kit 은 이 분리를 문장이 아니라 종료 코드로 강제한다 — 런타임 오류는 3, assert 실패는 4다.

이 분리가 가능한 이유는 실행 엔진이 고정되어 있기 때문이다. 설계문서 §12 확정 결정표는 실행 엔진을 Hurl 8.0.1 로 못박았고, /api-verify 는 그 종료 코드 체계를 재매핑 없이 승계한다.

아래 exit code 표는 2026-09-05 에 로컬 hurl 8.0.1 로 5 종 전부 재현해 확인했다. 정상 실행으로 0, --no-such-flag 로 1, 깨진 [Asserts 블록으로 2, 닫힌 포트 9999 로 3, 틀린 jsonpath 로 4 를 각각 받았다. 문서 기재와 일치한다 — docs/api/research-log.md 「2026-09-05 — Hurl 8.0.1 실측 대조」 절이 정본이다.

01 · 이 문서가 결정하는 것

회귀 실행 결과 하나를 놓고 세 가지를 순서대로 정한다. 무엇이 달라졌는지(분류), 그 차이가 게이트를 깨는지(심각도), 그 결과를 어떤 모양으로 CI 에 남기는지(artifact). 이 셋은 독립이 아니라 앞 단계가 뒤 단계의 입력이다.

Step 1 — 분류 무엇이 달라졌는가 status drift · schema drift · value drift 를 각각 다른 카테고리로 센다. normalize 이후에도 남는 차이만 값 drift 로 인정한다.
Step 2 — 심각도 게이트를 깨는가 계약 실패인지 환경 실패인지 가르고, 계약이 accepted baseline 을 가졌는지(모드)로 게이트 파괴 여부를 정한다.
Step 3 — artifact 어떻게 기록하는가 JUnit XML 의 failure / error / skipped 중 하나로 내보낸다. 전부 failure 로 미는 순간 집계가 무의미해진다. 
실행 결과
   │
   ├─ exit 0 ─────────────────────────────► pass
   │
   ├─ exit 1 / 2 ── 도구·계약 파일 오류 ──► 실행 중단 (재시도 금지)
   │
   ├─ exit 3 ────── 환경 실패 ────────────► 계약 판정 보류 · JUnit error
   │                (DNS · TLS · connect · timeout)
   │
   └─ exit 4 ────── 계약 실패 ────────────► 분류 분기
                    │
                    ├─ status drift  : 상태 클래스 단위로 비교
                    ├─ schema drift  : 필드 추가·삭제·타입 변경
                    └─ value drift   : normalize 후 남은 차이만
                                       │
                                       └─► 모드 판정 (observe / accepted)
                                            → 게이트 파괴 여부 결정

exit 1 과 2 는 대상 API 를 건드리지도 못한 상태다. 이 둘을 회귀 통계에 넣으면 계약 실패율이 도구 설정 실수로 오염된다.

02 · 확정 결정 — exit code 승계

계약 실패와 환경 실패는 리포트 문구가 아니라 종료 코드로 구분한다. /api-verify 는 Hurl 의 코드 체계를 그대로 쓰고 임의로 재매핑하지 않는다.

0 pass 전 assertion 통과. JUnit 에서는 result child 없이 testcase 만 남는다.
1 tool CLI 옵션 파싱 오류. 사용자가 잘못 부른 것이므로 재시도해도 같다.
2 input 입력 .hurl 파싱 오류. 계약 파일 자체를 고쳐야 한다.
3 env 런타임 오류 — DNS · TLS · connect · timeout. 계약 판정을 보류한다.
4 contract assert 실패. 계약이 깨졌다는 뜻이며 게이트를 깬다.
판정 규칙. 3 은 "계약을 확인하지 못했다"이고 4 는 "계약이 어긋났다"다. 3 을 실패율에 넣으면 인프라 사고가 계약 품질 지표를 갉아먹고, 4 를 재시도로 넘기면 회귀가 green 으로 통과한다.

근거 문서와 검증 상태를 분리해 표기한다. 실측 은 로컬 hurl 8.0.1 을 직접 돌려 관측했다는 뜻이고, 설계 확정 은 실행이 아니라 이 킷의 결정으로 고정된 값이라는 뜻이다. 둘은 성격이 다르므로 같은 배지를 쓰지 않는다.

항목값검증 상태근거
Hurl exit code 체계 0 성공 / 1 CLI 파싱 / 2 입력 파싱 / 3 런타임 / 4 assert 실측 2026-09-05 → Hurl Exit Codes hurl 8.0.1 로 5 종 재현 — 정상 / --no-such-flag / 깨진 [Asserts / 닫힌 포트 9999 / 틀린 jsonpath
실행 엔진 고정 Hurl 8.0.1 실측 2026-09-05 설계문서 §12 확정 결정표 hurl --version → hurl 8.0.1 (x86_64-apple-darwin25.0) libcurl/8.7.1
계약 실패 기준 partial 기본 + pin + exact 옵트인. pin 은 값 고정이 아니라 경로별 명시 assertion 설계 확정 설계문서 §12 · §9.2
exact 모드 범위 본문만. 헤더는 매 호출 변하는 값이 많아 제외 설계 확정 설계문서 §12 (2026-09-04 확정)

왜 검증 상태를 굳이 배지로 표시하는가

리서치 시점에는 로컬에 hurl 바이너리가 없었고, 옵션 우선순위 · --retry-interval · --max-redirs · exit code 체계 · --secret 마스킹 범위 다섯 항목이 "문서를 옮겼을 뿐 실행으로 확인하지 않은" 상태로 남아 있었다. exit code 는 이 문서 전체의 판정 축이라 그중 가장 먼저 대조해야 할 항목이었다.

2026-09-05 에 hurl 8.0.1 을 로컬에 설치해 다섯 항목을 모두 대조했다. exit code 는 5 종을 각각 재현해 문서 기재와 일치함을 확인했고, --secret 마스킹 범위 하나만 문서보다 새는 면적이 넓어 정정됐다. 배지를 남겨 두는 이유는 지금 값이 어느 쪽인지 다음 사람이 다시 물어보지 않게 하기 위해서다.

03 · 원칙

아홉 개 원칙 전부가 판정 규칙이다. 각 원칙은 "어떤 차이를 어떤 실패로 부를지"를 한 축씩 정한다.

1

Status Drift Classification

상태

HTTP 상태 변화는 문자열 diff 가 아니라 상태 클래스 단위로 분류한다. 2xx·3xx·4xx·5xx 는 의미가 다르므로 200 -> 500 과 200 -> 404 를 같은 심각도로 묶지 않는다.

200 -> 404 는 데이터 부재일 수도, 권한 은닉일 수도 있다. 단정하지 말고 후보 원인을 함께 기록한다.

→ RFC 9110 Status Codes
2

Schema Drift Classification

구조

응답 본문의 구조 변화는 API 표면 변화로 본다. OpenAPI Description 은 API surface 와 semantics 를 기술하는 계약 문서다.

따라서 필드 추가·삭제·타입 변경 같은 schema mismatch 는 value diff 와 별도 카테고리의 계약 실패다. 같은 통에 넣으면 "타입이 바뀐 것"과 "숫자가 바뀐 것"이 같은 줄로 보고된다.

→ OpenAPI Specification v3
3

Value Drift Classification

값

상태와 스키마가 같아도 값은 달라진다. timestamp, id, 정렬 순서 같은 값 drift 는 normalize 를 먼저 적용하고, normalize 이후에도 남는 차이만 assertion failure 로 판정한다.

normalize 규칙 자체가 diff 결과의 일부이므로 리포트에 함께 남긴다. 규칙을 감추면 같은 실행이 다른 판정을 내도 이유를 알 수 없다.

→ Hurl Asserting Response
4

Network / Auth / Data Split

분리

연결 실패, 인증 실패, 데이터 부재를 하나의 regression 으로 묶지 않는다. Hurl 도 runtime error 와 assert error 를 별도 exit code 로 나눈다.

OAuth Bearer 규격은 invalid_token = 401, insufficient_scope = 403 으로 구분한다. 인증 실패도 한 덩어리로 처리하지 않는다.

→ Hurl Exit Codes → RFC 6750 §3.1
5

Exit Code Contract

중심축

CLI 종료 코드는 문서화된 계약이다. 4(assert 실패)와 3(런타임 실패)이 구분되어야 CI 가 "계약이 깨졌다"와 "서버가 죽었다"를 다르게 다룰 수 있다.

/api-verify 는 Hurl 의 코드 체계를 그대로 승계하고 임의로 재매핑하지 않는다. 재매핑하는 순간 상위 도구의 문서와 실제 동작이 어긋난다.

→ Hurl Exit Codes ✓ 실측 2026-09-05 — hurl 8.0.1 로 0~4 5 종을 각각 재현, 문서 기재와 일치
6

Mode-aware Severity

모드

같은 실패라도 모드에 따라 게이트 파괴 여부가 다르다. 새로 만든 계약이나 관찰(observe) 모드는 실패를 기록하되 게이트를 깨지 않는다.

accepted baseline 이 존재하는 계약의 실패는 회귀로 게이트를 깬다. Pact pending pacts 의 "첫 성공 전은 pending, 성공 후 실패는 breaking" 모델을 따른다.

→ Pact Pending Pacts
7

Retry Confirmation

flaky

retry 로 성공한 실패를 green 으로 숨기지 않는다. 동일 커밋·동일 입력에서 pass/fail 이 뒤집히는 테스트는 flaky 다.

retry 성공은 "안정"이 아니라 "불안정 신호"로 분류해 별도 카운터에 남긴다. 지우면 같은 불안정이 무한 반복된다.

→ Google Testing Blog — Where Do Our Flaky Tests Come From?
8

CI Artifact Shape

artifact

JUnit XML 로 내보낼 때 계약 assertion mismatch 는 failure, 실행 불능·환경 오류는 error, quarantine 또는 의도된 미실행은 skipped 로 기록한다.

CI 대시보드는 이 구조로 실패 원인을 집계한다. 전부 failure 로 밀어 넣으면 집계가 무의미해진다.

→ JUnit XML 포맷 레퍼런스 → Ant JUnit XMLConstants
9

Baseline Promotion Gate

승격

diff 가 실패한 순간 baseline 을 자동 갱신하지 않는다. Jest snapshot 관례처럼 baseline 은 코드와 함께 리뷰되며, CI 는 암묵적으로 새 스냅샷을 쓰지 않는 것이 기본값이다.

갱신은 별도 promote 명령의 책임이다. 자동 갱신은 회귀를 새 truth 로 승격시킨다.

→ Jest Snapshot Testing

05 · 안티패턴

아래 셋은 리포트를 만들 때 가장 자주 나오는 실수다. 왼쪽이 하지 말아야 할 형태, 오른쪽이 이 정책이 요구하는 형태다.

Bad — 한 줄 요약

모든 차이를 diff failed 한 줄로 출력한다.

상태·스키마·값 중 무엇이 깨졌는지 알 수 없어 대응 우선순위를 정하지 못한다. 결국 사람이 raw 로그를 다시 읽는다.

Good — 축별 분류

status / schema / value 세 축을 각각 카운트하고, 축마다 원인 후보를 붙인다.

"5xx 1건, 필드 삭제 2건, normalize 후 잔여 값차 3건" 처럼 읽히면 대응 순서가 바로 정해진다.

BAD환경 오류를 계약 실패로 승격
if [ $? -ne 0 ]; then
  echo "API regression detected"
  exit 1
fi

exit 3(타임아웃)과 exit 4(assert 실패)가 같은 문장으로 보고된다. 서버가 죽은 날 회귀 실패율이 100% 로 찍힌다.

GOOD코드별로 다르게 다룬다
code=$?
case "$code" in
  0) exit 0 ;;
  1|2) echo "tool/input error"; exit "$code" ;;
  3) echo "env failure - verdict deferred"
     record_junit error; exit "$code" ;;
  4) echo "contract failure"
     record_junit failure; exit "$code" ;;
esac

환경 실패는 error, 계약 실패는 failure 로 나뉘어 대시보드에서 따로 집계된다.

코드는 판정 분기의 형태를 보이기 위한 예시다. 실제 /api-verify 구현 코드가 아니다.

BADretry 성공 시 실패 기록 삭제
attempt 1 -> exit 4
attempt 2 -> exit 0
report: PASS

flaky 신호가 사라진다. 같은 불안정이 다음 주에도, 그 다음 주에도 그대로 재현된다.

GOOD재실행 결과를 별도 카운터에
attempt 1 -> exit 4
attempt 2 -> exit 0
report: PASS (flaky-confirmed: 1)

동일 커밋·동일 입력에서 결과가 뒤집혔다는 사실이 남는다. 계속 실패하면 원 분류를 유지한다.

06 · Gotchas 체크리스트

회귀 리포트를 만들기 전에 확인한다. 하나라도 비어 있으면 리포트의 판정을 신뢰할 수 없다.

  • ✓exit code 값을 실측으로 확인했다. 2026-09-05 에 hurl 8.0.1 로 0~4 5 종을 각각 재현했고 Hurl 공식 문서 기재와 일치했다. 엔진 버전을 올리면 이 재현을 다시 돌려라 — 코드 번호가 바뀌면 계약 실패 집계 자체가 어긋난다.
  • !exit 3 의 subreason 을 별도 필드로 남겼는가. Hurl 3 은 DNS·TLS·timeout·connect 를 모두 포함한다. 코드만으로는 일시적 타임아웃과 인증서 만료가 구분되지 않는다.
  • ✓실행 모드를 diff 결과와 함께 기록했는가. additive field 는 tolerant 모드에서는 호환이고 exact·golden 모드에서는 실패다. 모드를 모르면 같은 diff 를 두 사람이 다르게 읽는다.
  • !404 에 원인 후보를 둘 다 남겼는가. 진짜 데이터 부재일 수도, 존재를 감추는 403 대체 정책일 수도 있다. 자동으로 한쪽으로 단정하지 마라.
  • ✗redaction 을 리포트 생성 전에 수행했는가. 실패 artifact 에는 stdout 과 raw body 가 들어간다. 생성 후 마스킹하면 이미 파일과 CI 로그에 비밀이 남아 있다.
  • ✓normalize 규칙을 리포트에 함께 실었는가. normalize 는 판정의 일부다. 규칙을 감추면 값 drift 판정을 재현할 수 없다.
  • ✓JUnit 매핑이 세 갈래로 나뉘어 있는가. assertion mismatch 는 failure, 실행 불능은 error, quarantine 은 skipped. 전부 failure 면 집계가 죽는다.
  • ✓accepted baseline 유무로 심각도를 갈랐는가. 첫 성공 전 계약의 실패는 기록만, accepted 이후의 실패는 회귀다. Pact pending pacts 모델을 따른다.
  • ✗실패 시 baseline 을 자동으로 쓰지 않는가. CI 에서 baseline 자동 write 허용 횟수는 0 이다. 갱신은 명시적 promote 명령과 리뷰 메타데이터가 있을 때만 일어난다.
  • ✓인증 실패를 400/401/403 으로 세분했는가. RFC 6750 §3.1 은 malformed·invalid token·insufficient scope 를 각각 다른 코드로 규정한다.
