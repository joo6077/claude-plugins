Probe 합성과 Hurl 실행 의미론

인벤토리의 operation 에서 실행 가능한 .hurl probe 를 합성할 때의 값 생성 순서, 직렬화 규칙, 그리고 Hurl 8.0.1 실행 엔진의 의미론을 다룬다. v0.2.1 · 최종 갱신 2026-09-24

이 페이지의 Hurl 값은 두 번 실측했다 — 2026-09-24 에 변수 한 줄을 고쳤다

처음은 2026-09-05 다. hurl 8.0.1(x86_64-apple-darwin25.0 · libcurl/8.7.1) 을 로컬에 설치하고 127.0.0.1:8731 에 고정 JSON 을 돌려주는 픽스처 서버를 띄워 대조했다. 두 번째는 2026-09-24 로, 같은 hurl 8.0.1 과 127.0.0.1 픽스처 서버로 환경변수 변수 행을 다시 쟀다. 두 번 모두 외부 호출은 없다.

2026-09-05 판은 「이 우선순위는 옵션에만 적용되고, 환경변수로는 변수가 들어오지 않는다」 는 단서를 달았다. HURL_who 하나만 재고 내린 결론이었다. Hurl 8.0.0 에서 변수를 받는 환경변수 접두가 HURL_VARIABLE_ 로 바뀌었고, HURL_VARIABLE_who 는 {{who}} 를 채운다. 그래서 원칙 6 과 수치 표 한 행을 고쳤다.

--secret 이 어느 출력을 가리고 어느 출력을 그대로 두는지는 이 페이지 원본이 다루지 않는다. 채널마다 나눈 표는 인증과 시크릿 수명 페이지 에 있다. 이 페이지는 probe 를 만들고 돌릴 때 걸리는 두 줄 — --very-verbose 와 redact capture — 만 Gotchas 에 남긴다.

실측 은 로컬 hurl 8.0.1 을 돌려 관측한 값이다. 문서 기재 는 공식 문서를 옮겼을 뿐 아직 실행으로 확인하지 않은 값이고, retry 기본값 · entry 번호 시작값 · --test 병렬 3 건이 그 상태로 남아 있다. 추론 은 사양 문서도 실행도 아닌 이 킷의 설계 결정이다. 셋을 섞어 읽지 마라 — 실측이 아닌 값을 실측 근거로 인용하는 것이 이 표시가 막으려는 일이다.

이 문서가 결정하는 것
operation 하나를 실행 가능한 요청으로 바꾸려면 세 가지를 정해야 한다. 어떤 값을 넣을지, 그 값을 어떻게 직렬화할지, 그리고 돌아온 실패를 어떻게 분류할지. 셋 중 마지막이 가장 자주 빠지고, 빠지면 회귀 diff 가 노이즈에 덮인다.
step 1 · 값 example → default → enum 우선순위대로 고르고, 고른 뒤 schema 검증을 한 번 더 돌린다. default 는 annotation 이지 validation 이 아니다.
step 2 · 직렬화 경로는 하나만 query 는 URL 문자열과 [Query] 섹션 중 하나만. Accept·Content-Type·Authorization 은 명시적으로 만든다.
step 3 · 분류 exit code 로 나눈다 4 만 계약 위반. 2 는 probe 생성 버그, 3 은 네트워크·환경 문제, 1 은 CLI 파싱 실패다. 
operation                     probe 합성                          실행 / 분류
─────────────                 ──────────────────────────          ─────────────────────
schema        ─┐              값 = example > default > enum
examples      ─┼──>           query = [Query] 섹션 하나만    ──>   hurl --test *.hurl
security      ─┤              헤더 3 종 명시 생성                    │
requestBody   ─┘              의존 흐름은 한 파일 안에               ├─ exit 4  계약 위반
                                                                    ├─ exit 3  환경 문제
                              파일 경계 = 격리 경계                  ├─ exit 2  probe 버그
                              (--test 는 파일 단위 병렬)             ├─ exit 1  CLI 파싱
                                                                    └─ exit 0  통과
한 줄 규칙. 추론에 맡기는 순간 실패 원인이 흐려진다. 값도, 헤더도, 직렬화 경로도 명시적으로 만든다. non-zero = 실패 로 뭉뚱그리지 않는다.
원칙 9

1~3 은 요청을 만드는 규칙, 4~5 는 흐름과 격리, 6~9 는 Hurl 실행 엔진의 의미론이다. 6(옵션 우선순위)과 9(exit code)는 hurl 8.0.1 로 실측했고, 6 의 변수 부분은 2026-09-24 에 다시 재서 고쳤다. 7 · 8 은 사양 서술이라 실행 대조 대상이 아니다.

1

Example-Default-Enum Precedence

값 생성
값 생성 우선순위는 media type 의 explicit example / examples → schema example → JSON Schema default → const / enum 순이다. default 는 validation 키워드가 아니라 annotation 이므로 그 값이 schema 를 만족한다는 보장이 없다. enum 에서 값을 고른 뒤에도 schema 검증을 한 번 더 돌린다.
→ OpenAPI 3.1.0 Media Type Object → JSON Schema 2020-12 Validation
2

Deterministic Query Serialization

경로 하나
query 는 URL 문자열과 [Query] 섹션 중 한 경로만 쓴다. Hurl 은 둘 다 있으면 둘 다 전송하므로 파라미터가 중복된다. 기본은 [Query] 섹션이고, OpenAPI 의 style / explode / allowReserved 를 반영해 직렬화한다.
→ Hurl Request → OpenAPI 3.1.0 Parameter Object
3

Explicit Accept / Content-Type / Authorization

추론 금지
이 세 헤더는 추론에 맡기지 않고 명시적으로 생성한다. Accept 는 기대 response media type, Content-Type 은 requestBody media type, Authorization 은 해당 operation 에 적용되는 security requirement 에서 각각 파생시킨다. 생략하면 클라이언트 기본값이 끼어들어 실패 원인이 계약인지 전송인지 구분되지 않는다.
→ RFC 9110 Accept → OpenAPI 3.1.0 Parameter Object
4

Dependency Capture

[Captures]
앞 entry 의 응답에서 필요한 값만 [Captures] 로 뽑아 이후 entry 의 변수로 쓴다. Hurl 은 status, header, cookie, body, jsonpath, xpath, duration 등을 capture 할 수 있다. 같은 이름으로 다시 capture 하면 새 값이 이전 값을 덮으므로, 체인 안에서 이름을 재사용하지 않는다.
→ Hurl Capturing Response
5

Entry Isolation

파일 = 경계
상태를 공유해야 하는 흐름(로그인 → 조회 → 삭제 등)은 반드시 한 .hurl 파일 안에 둔다. Hurl 은 같은 파일 안에서 cookie store 를 공유하고, --test 모드는 파일 단위로 병렬 실행하므로 파일 간 의존은 실행 순서를 보장받지 못한다. 파일 경계 = 격리 경계다.
→ Hurl Entry → Hurl Manual
6

Hurl Option Precedence

env < CLI < [Options] 실측
설정 우선순위는 environment variable < command-line option < per-entry [Options] 다. 뒤쪽이 앞쪽을 이긴다. cli-only 옵션은 [Options] 로 내려쓰지 않는다 — 파일에 적혀 있어도 적용되지 않아 문서와 실제 실행이 어긋난다.
옵션 환경변수는 HURL_INSECURE 가 --insecure 가 되는 식이다. 변수는 접두가 다르다 — HURL_who 를 걸어도 {{who}} 는 채워지지 않고, Hurl 8.0.0 부터는 HURL_VARIABLE_who 가 채운다. HURL_SECRET_<이름> 은 --secret 처럼 값을 가린다. 변수도 같은 우선순위를 따라 명령줄 --variable 이 환경변수를 이긴다.
→ Hurl Manual — Configuration → Hurl CHANGELOG — 8.0.0 실측 hurl 8.0.1 · 2026-09-05 · 2026-09-24
7

Response Capture Policy

최소 assert
최소 assert 는 expected HTTP status 하나다. body 전체 capture 는 downstream dependency 가 실제로 그 값을 쓰거나 진단 목적일 때만 켠다. 일반 body / query capture 는 decompressed·decoded 본문 기준이고, 원본 바이트가 필요하면 rawbytes 를 쓴다.
→ Hurl Response → Hurl Capturing Response
8

Continue-on-error Strategy

독립 배치 전용
기본 동작은 assert error 발생 시 해당 파일 실행 중단이다. --continue-on-error 는 assert error 에도 파일 끝까지 진행시키지만, dependency chain 에서는 오염된 변수로 후속 요청이 돌아 전이 실패를 만든다. 서로 독립인 probe 배치에만 켠다.
→ Hurl Manual — Run Options
9

Exit Code 기반 실패 분류

4 만 계약 실측
Hurl 종료 코드로 실패 종류를 나눈다. 4(assert)만 계약 위반이고, 2(input parse)는 probe 생성 버그, 3(runtime)은 네트워크·환경 문제다. 이 구분 없이 non-zero 를 전부 계약 실패로 보고하면 회귀 diff 가 노이즈로 덮인다.
→ Hurl Manual — Exit Codes 실측 2026-09-05 — 5 종 재현
변수와 옵션이 들어오는 길
원칙 6 을 세 자리로 펼친 그림이다. 옵션과 변수는 같은 순서로 겹치고 뒤쪽이 이긴다. 다른 것은 환경변수 이름뿐이다 — 옵션은 HURL_ 뒤에 옵션 이름을, 변수는 HURL_VARIABLE_ 뒤에 변수 이름을 붙인다.
1 · 환경변수 (가장 약함) HURL_… 옵션 — HURL_INSECURE → --insecure, HURL_MAX_REDIRS=3 변수 — HURL_VARIABLE_who → {{who}}. HURL_who 는 변수가 되지 않는다 시크릿 — HURL_SECRET_<이름> 은 --secret 처럼 가린다
2 · 명령줄 hurl --… 옵션 — --max-redirs 5 변수 — --variable who=… 가 HURL_VARIABLE_who 를 이긴다(실측 2026-09-24)
3 · entry [Options] (가장 강함) [Options] 옵션 — max-redirs: 7. 그 entry 에서만 유효하다 변수 — variable: 만은 다음 entry 로 이어진다(Gotcha 첫 줄)

환경변수로 변수 넣기 — 옛 접두 vs 8.0.0 접두

BAD HURL_<이름> 은 옵션용이다. 변수는 비어 있다 
$ HURL_who=from-env hurl who.hurl

# {{who}} 가 채워지지 않는다
# assert 결과 — actual: none
GOOD HURL_VARIABLE_ 접두. 겹치면 명령줄이 이긴다 
$ HURL_VARIABLE_who=from-env hurl who.hurl
# 통과 — {{who}} = from-env

$ HURL_VARIABLE_who=from-env \
    hurl --variable who=from-cli who.hurl
# {{who}} = from-cli (명령줄 값)

원칙 6 · 수치 표 「환경변수로 들어가는 변수」 행. 2026-09-05 판은 왼쪽 한 줄만 재고 「환경변수로는 변수가 들어오지 않는다」 로 적었다. 이름 하나가 안 된다는 관측을 규칙 전체로 넓힌 것이 틀린 자리였다. who.hurl 은 설명을 위해 붙인 파일 이름이다.

옵션 우선순위. environment variable → command-line option → per-entry [Options]. 뒤쪽이 이긴다. cli-only 옵션을 [Options] 에 적으면 무시되므로, 파일에 적힌 실행 의미와 실제 실행이 갈라진다. 변수도 같은 순서를 따른다 — 환경변수로 넣으려면 HURL_VARIABLE_ 접두가 필요하고, 명령줄 --variable 이 그 값을 이긴다(실측).
수치 기준
확인 열은 값의 출처가 아니라 어떻게 확인했는지다. 실측 은 로컬 hurl 8.0.1 로 실행해 관측한 것, 문서 는 아직 실행으로 확인하지 않은 것이다. 근거 칸에는 실측한 행에 한해 그 방법을 함께 적었다.

안티패턴
다섯 가지 모두 "실행은 되는데 결과 해석이 틀리는" 부류다. 실패가 나도 원인이 엉뚱한 곳을 가리킨다.
안티패턴 문제
URL query 와 [Query] 섹션을 동시에 생성 Hurl 이 둘 다 전송해 같은 파라미터가 중복된다
dependent flow 를 여러 .hurl 파일로 분할 --test 가 파일을 병렬 실행해 순서 보장이 깨진다
cli-only 옵션을 [Options] 에 기입 무시되어 파일에 적힌 실행 의미와 실제 실행이 달라진다
모든 response body 를 capture 리포트가 비대해지고 토큰·시크릿이 로그에 남는다
auth 실패 뒤에도 continue-on-error 로 진행 이후 probe 실패가 계약 위반이 아니라 인증 전이 실패가 된다

① query 직렬화 — 두 경로 동시 사용 vs 한 경로

BAD Hurl 이 둘 다 전송해 파라미터가 중복된다 
GET https://api.example.com/v1/orders?status=paid&page=2
[Query]
status: paid
page: 2

# 실제 전송: ?status=paid&page=2&status=paid&page=2
# 서버가 첫 값을 쓰는지 마지막 값을 쓰는지에 결과가 좌우된다
GOOD [Query] 섹션 하나만. style/explode 를 반영 
GET https://api.example.com/v1/orders
Accept: application/json
Authorization: Bearer {{token}}
[Query]
status: paid
page: 2

HTTP 200

원칙 2 · 3. 헤더 3 종은 추론에 맡기지 않는다 — 생략하면 클라이언트 기본값이 끼어들어 실패 원인이 흐려진다.

② 의존 흐름 — 파일 분할 vs 한 파일 안 chaining

BAD --test 는 파일 단위 병렬 — 순서 보장 없음 
# 01-login.hurl
POST /v1/login
HTTP 200
[Captures]
token: jsonpath "$.token"

# 02-orders.hurl   ← 별도 파일
GET /v1/orders
Authorization: Bearer {{token}}

# token 이 정의되지 않은 채 먼저 실행될 수 있다
# cookie store 도 파일 간에 공유되지 않는다
GOOD 한 파일 = 한 격리 단위. capture 이름 재사용 금지 
# order-flow.hurl
POST /v1/login
HTTP 200
[Captures]
login_token: jsonpath "$.token"

GET /v1/orders
Authorization: Bearer {{login_token}}
HTTP 200
[Captures]
first_order_id: jsonpath "$.items[0].id"

DELETE /v1/orders/{{first_order_id}}
HTTP 204

원칙 4 · 5. 같은 이름으로 다시 capture 하면 새 값이 이전 값을 덮으므로 체인 안에서 이름을 재사용하지 않는다.

BAD — non-zero 를 전부 계약 실패로
hurl --test 의 종료 코드가 0 이 아니면 전부 "계약 실패" 로 집계한다. DNS 실패도, probe 파일 문법 오류도, 오타 난 플래그도 같은 칸에 쌓인다.
결과 — 회귀 diff 가 환경 잡음에 덮여, 진짜 4(assert) 한 건이 묻힌다. 도구를 못 믿게 되는 가장 빠른 경로다.
GOOD — 코드별로 갈라 보고
4 만 계약 위반으로 센다. 2 는 합성기 버그 큐로, 3 은 환경 점검 큐로 보낸다. 1 은 킷이 만든 명령줄 문제다.
결과 — 실패 목록이 곧 작업 분배표가 된다. 코드 번호는 실측 으로 확정했다 — 5 종을 각각 재현했다(2026-09-05).
BAD — 전부 capture + verbose 로그
진단이 편하다는 이유로 모든 응답 body 를 capture 하고 --very-verbose 를 상시 켠다. Hurl 의 --secret 이 알아서 가려 줄 거라 가정한다.
결과 — 리포트가 비대해지고 토큰·시크릿이 로그에 남는다. --very-verbose 는 body 를 stderr 에 찍고, --secret 은 등록한 그 값만 *** 로 바꾼다 — 같은 값의 base64 본은 그대로 남는다(실측). redact capture 로 막으려 하면 --very-verbose 와 함께 돌지 않는다.
GOOD — 최소 assert + 필요한 capture 만
최소 assert 는 expected status 하나. body capture 는 downstream 이 실제로 그 값을 쓰거나 진단이 필요할 때만 켠다. 바이트 계약은 rawbytes 로 명시한다.
결과 — 저장하고 출력하는 값이 줄어 시크릿이 샐 수 있는 자리도 함께 줄어든다. 출력마다 가려지는지 여부는 인증과 시크릿 수명 페이지 의 채널 표를 따른다.
Gotchas — probe 실행 전 확인
앞의 일곱 줄은 원본 Gotchas 를 모두 옮긴 것이고, 뒤의 여섯 줄은 원칙에서 나온 확인 항목이다. Hurl 동작에 걸린 줄은 실측 결과를 반영했다.
  • ! [Options] 의 variable 만 다음 entry 로 이어진다. 다른 [Options] 항목은 그 entry 에서만 유효한데 variable 은 예외다. entry 별로 같은 이름 변수를 다르게 주면 뒤 entry 가 앞 값을 조용히 상속하거나 덮는다.
  • ! rawbytes 가 아닌 capture / assert 는 decoded·decompressed 본문 기준이다. gzip 응답의 바이트 길이나 원본 인코딩을 검증하려 했는데 디코딩된 값이 비교돼 통과해 버린다. 바이트 수준 계약은 rawbytes 로 명시한다.
  • ! redirect follow 는 기본으로 꺼져 있다. 3xx 를 받고 assert 가 실패하면 계약 위반처럼 보이지만 실제로는 follow 미설정이다. 필요하면 entry 의 location: true 또는 --location 을 켠다.
  • ! --very-verbose 는 request / response body 를 stderr 에 출력한다. 다만 --secret 을 걸어 두면 그 값은 *** 로 바뀐다(실측). 문제는 등록하지 않은 변형본이다 — base64 본은 그대로 남는다.
  • × --verbose 로는 body 가 안 찍힌다. 그래서 "--verbose 로그에 토큰이 없다" 는 관측은 마스킹의 증거가 아니다. body 가 찍히는 건 --very-verbose 부터다.
  • × redact capture 와 --very-verbose 는 함께 못 쓴다. Hurl 8.0.1 이 redacted secret not authorized in verbose 로 실행을 거부한다.
  • × exit code 1 은 계약과 무관하다. CLI 파싱 실패다. 오타 난 플래그 하나로 1 이 나오는데, 이걸 실패 통계에 넣으면 계약 회귀처럼 보인다.
  • ✓ query 가 URL 문자열과 [Query] 섹션 중 한 경로로만 만들어졌는지 확인했다(원칙 2).
  • ✓ Accept · Content-Type · Authorization 을 명시적으로 넣었는지 확인했다(원칙 3).
  • ✓ 상태를 공유하는 흐름이 한 .hurl 파일 안에 있고, capture 이름이 체인 안에서 재사용되지 않는지 확인했다(원칙 4 · 5).
  • ✓ 환경변수로 변수를 넣는 자리가 HURL_VARIABLE_<이름> 접두를 쓰는지, 같은 변수를 명령줄 --variable 로도 주고 있지 않은지 확인했다 — 겹치면 명령줄 값이 이긴다(원칙 6).
  • ✓ --continue-on-error 가 서로 독립인 probe 배치에만 켜져 있는지 확인했다 — dependency chain 에서는 전이 실패를 만든다(원칙 8).
  • ✓ enum / default 에서 고른 값도 schema 검증을 한 번 더 돌렸는지 확인했다 — default 는 annotation 이라 schema 를 만족한다는 보장이 없다(원칙 1).
