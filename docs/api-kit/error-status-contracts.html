오류·상태 코드 계약

실제 오류 응답을 SSOT 로 삼아 계약을 만들 때, 무엇을 고정하고 무엇을 class 수준으로만 둘지 판정하는 규칙. v0.1.0 · 최종 갱신 2026-09-04

먼저 읽어라 — 사람이 읽는 문자열은 계약이 아니다

오류 계약은 status, content-type, 기계 판독 가능한 식별 필드로만 만든다. detail 같은 사람용 설명 문자열은 서버 배포마다 바뀌고 다국어에 따라 달라진다. 그 문자열을 파싱해 판정하면 문구 변경과 실제 회귀를 구분할 수 없게 된다.

두 번째 함정은 방향이다. RFC 9457 problem detail 안의 status member 는 advisory 이고, 실제 전송 계층의 결과는 HTTP status 다. 둘이 어긋나면 body 가 아니라 HTTP status 를 기준으로 판정하고, 불일치 자체를 서버 버그 신호로 본다.

→ RFC 9457 §3.1.4 detail → RFC 9110 §15 Status Codes
이 문서가 결정하는 것

오류 응답을 어느 강도까지 계약으로 올릴 것인가

같은 오류 응답이라도 계약으로 올릴 수 있는 부분은 셋으로 나뉜다 — status, 식별자, retry metadata. 본문의 설명 문자열은 어느 단계에도 들어가지 않는다.

1 — status class 로 시작한다 exact status 가 배포마다 흔들리면 먼저 4xx/5xx class 정책으로 계약하고, 안정성이 관측된 뒤에 좁힌다.
2 — 식별자 problem type 이 1 차 키 오류 종류를 구분하는 키는 title 이나 detail 이 아니라 type URI 다.
3 — retry 재시도 가능성도 계약 Retry-After 는 delay-seconds 또는 HTTP-date. 429 · 503 에서 계약 후보로 다룬다. 
오류 응답 도착
   │
   ├─ HTTP status ─────────────────────────── 계약 대상
   │     4xx deterministic → exact status pin 후보
   │     흔들림          → class(4xx/5xx) 로 내린다
   │     5xx            → class + envelope + retry 만
   │
   ├─ Content-Type ────────────────────────── 계약 대상
   │     application/problem+json → RFC 9457 의미로 해석
   │
   ├─ type (URI) ──────────────────────────── 1차 식별자
   │     없으면 about:blank — 누락 자체는 실패가 아니다
   │
   ├─ Retry-After ────────────────────────── 계약 후보
   │     delay-seconds(정수 ≥ 0) | HTTP-date
   │
   ├─ errors[] + JSON Pointer ─────────────── 필드 경로·오류 키만
   │
   └─ title · detail (사람용 문자열) ───────── 계약 대상 아님
본문에서 계약으로 올릴 수 있는 건 구조와 키뿐이다. validation 오류도 errors[] 의 필드 경로와 오류 키까지만 고정하고, 각 항목의 메시지 문자열은 제외한다.
원칙

오류 계약 규칙 9 가지

오류 응답은 정상 응답보다 비결정적이다. 그래서 “무엇을 계약하느냐” 보다 무엇을 계약하지 않느냐를 먼저 정한다.

1

오류 계약은 machine-readable 필드로만

이 문서의 핵심

status, content-type, 그리고 기계 판독 가능한 식별 필드로 계약을 잡는다. detail 같은 사람용 설명 문자열을 파싱해 판정하지 않는다. 설명 문구는 서버 배포마다 바뀌고 다국어에 따라 달라져 계약이 쉽게 깨진다.

→ RFC 9457 §3.1.4 detail
2

problem+json 호환 해석

응답 content-type 이 application/problem+json 이면 type, title, status, detail, instance 를 RFC 9457 의미대로 해석한다. type 이 없으면 about:blank 로 간주되므로, 누락 자체를 계약 위반으로 잡지 않는다.

→ RFC 9457 §3.1 Members of a Problem Details Object
3

problem type 이 1 차 식별자

pin

problem detail 의 primary identifier 는 type URI 다. 오류 종류를 구분하는 키는 title 이나 detail 이 아니라 type 이다. absolute URI 가 권장되며, 도구는 디버그 목적이 아닌 한 이 URI 를 자동으로 dereference 하지 않는다.

→ RFC 9457 §3.1.1 type
4

불안정하면 status class 로 계약

class

exact status 가 배포마다 흔들리는 API 는 먼저 4xx / 5xx class 정책으로 계약화하고, 안정성이 관측된 뒤에 exact 로 좁힌다. RFC 9110 은 status code 의 첫 자리로 class 의미를 정의하며 4xx 를 client error class 로 규정한다.

→ RFC 9110 §15 Status Codes
5

인증 오류 분리

401 은 유효한 인증 정보가 없거나 실패한 경우이며 WWW-Authenticate challenge 를 동반한다. 403 은 서버가 요청을 이해했으나 거부한 경우다. OAuth bearer 오류도 같은 축으로 invalid_token 과 insufficient_scope 를 분리해 계약한다.

401토큰 갱신으로 풀린다 — invalid_token 403권한 자체가 없다 — insufficient_scope
→ RFC 9110 §15.5.2 401 Unauthorized → RFC 6750 §3.1 Error Codes
6

validation 오류는 안정 필드만

validation 오류는 stable extension field 만 계약 대상으로 삼는다. 메시지 문자열은 제외한다. RFC 9457 예시는 errors[] 배열과 JSON Pointer 를 problem extension 으로 두므로, 필드 경로와 오류 키만 고정한다. 

{ "type": "https://example.com/probs/validation",
  "status": 422,
  "errors": [
    { "pointer": "/order/quantity", "code": "out_of_range" },
    { "pointer": "/order/currency", "code": "unsupported" }
  ] }

계약: pointer + code   |   계약 아님: 사람용 message
→ RFC 9457 §3 Problem Details JSON Object
7

Retry-After 처리

429 · 503

Retry-After 는 delay-seconds(0 이상 정수) 또는 HTTP-date 두 형식을 가진다. 파서는 둘 다 받아야 한다. 429, 503, 일부 redirect 응답에서 재시도 가능성을 설명하는 계약 후보로 다룬다. 

Retry-After: 3600
Retry-After: Wed, 04 Sep 2026 07:28:00 GMT
→ RFC 9110 §10.2.3 Retry-After → RFC 6585 §4 429 Too Many Requests
8

4xx 는 exact pin 후보

pin

같은 입력에 같은 코드가 돌아오는 deterministic client error 는 exact status pin 후보다. malformed request, 인증 실패, 권한 부족, validation 실패, rate limit 이 대표 사례다.

→ RFC 9110 §15.5 Client Error 4xx
9

5xx 는 계약 제외 버킷

class 본문 exact 0 개

5xx 응답 본문은 기본적으로 exact 계약에서 제외하고 status class + envelope 형태 + retry metadata 만 검증한다. RFC 9457 도 problem detail 이 구현 디버깅 도구가 아니며 내부 정보 노출 위험이 있다고 경고한다 — 그런 본문을 golden 으로 고정하면 안 된다.

→ RFC 9457 §4 Defining New Problem Types → RFC 9457 §5 Security Considerations
버킷

4xx 와 5xx 는 다른 계약을 받는다

같은 오류라도 client error 와 server error 는 결정성이 다르다. 4xx 는 같은 입력에 같은 코드가 돌아오는 것이 정상이고, 5xx 는 그렇지 않다.

pin 4xx — deterministic client error

같은 입력에 같은 코드가 돌아오면 exact status pin 후보다.

  • malformed request
  • 인증 실패 401 + WWW-Authenticate
  • 권한 부족 403
  • validation 실패 — errors[] pointer + code
  • rate limit 429 + Retry-After

class 5xx — 계약 제외 버킷

본문은 exact 계약에서 제외한다. 검증 대상은 셋뿐이다.

  • status class (5xx)
  • envelope 형태 (problem+json 여부, 필수 member 존재)
  • retry metadata (Retry-After 파싱 가능성)
  • 본문 exact pin: 0 개 — 내부 정보 노출 · 비결정성
status 가 흔들리는데 exact 로 고정

같은 요청이 배포에 따라 400 과 422 를 오가는 API 에 exact status 를 걸면 매 실행이 실패한다. 그 실패는 회귀를 알리지 않고 알람만 만든다.

class 로 내렸다가 관측 후 좁힌다

먼저 4xx class 로 계약하고, 반복 관측에서 코드가 안정적임이 확인된 뒤에 exact status 로 좁힌다. 좁히는 근거를 계약에 같이 남긴다.

안티패턴

오류 계약이 깨지는 전형적 방식

아래 두 쌍은 오류 응답에서 가장 자주 나오는 계약 실패다. 둘 다 “서버가 바뀌었다” 가 아니라 “계약이 잘못된 것을 봤다” 가 원인이다.

BAD사람용 문자열을 exact match 로 고정
contract:
  $.detail:
    const: "주문 수량은 1 이상이어야 합니다."

# 문구를 다듬거나 로케일이 바뀌면
$.detail = "수량은 1개 이상이어야 합니다."   FAIL
$.detail = "Quantity must be at least 1."   FAIL
# 실제 회귀와 구분되지 않는다
GOODtype URI + 오류 키만 계약
contract:
  http_status: 422
  content_type: ^application/problem\+json
  $.type:
    const: "https://example.com/probs/validation"
  $.errors[].pointer: { type: string }
  $.errors[].code:
    enum: [out_of_range, unsupported]
# detail 은 계약 대상이 아니다

type 이 primary identifier 다. title · detail 은 사람이 읽는 필드이고, 계약에 들어가는 순간 문구 변경이 회귀로 보고된다.

BAD500 본문을 golden 으로 저장 · body status 만 신뢰
# 500 응답의 stack trace 를 그대로 baseline 에 저장
exact: true
body:
  trace: "at com.example.OrderService.load(...)"
  node:  "api-prod-7f3c"

# 실제 HTTP 401 인데 body 만 보고 판정
HTTP/1.1 401
{ "status": 500 }     ← body 값을 그대로 채택
GOOD5xx 는 class + envelope + retry, 판정은 HTTP status
contract:
  http_status_class: 5xx        # exact 아님
  content_type: ^application/problem\+json
  $.type:   { type: string }
  retry:    "Retry-After 파싱 가능하면 기록"
  body_exact: 0                 # 본문 고정 없음

# body.status 와 HTTP status 불일치 → 서버 버그 신호
# 판정 기준은 언제나 HTTP status

5xx 본문은 배포마다 달라지고 내부 구조를 저장소에 남긴다. RFC 9457 도 problem detail 이 디버깅 도구가 아니라고 경고한다.

안티패턴문제
detail 문자열 전체를 exact match 로 고정 문구 · 다국어 변경만으로 계약이 깨진다. 실제 회귀와 구분되지 않는다
body 의 status 필드와 실제 HTTP status 가 다를 때 body 만 신뢰 HTTP status 가 실제 전송 계층 결과다. body 값은 advisory 다
401 / 403 / invalid_token / insufficient_scope 를 하나로 합침 토큰 갱신으로 풀리는 실패와 권한 자체가 없는 실패가 섞인다
500 응답의 stack trace 를 golden contract 로 저장 내부 구조가 저장소에 남고, 배포마다 달라져 항상 실패한다
429 를 단순 실패로만 처리하고 Retry-After 무시 재시도 가능 신호를 버려 불필요한 재실행 · 추가 차단을 부른다
Gotchas

오류 계약 작성 전 확인

아래는 계약을 만들 때 조용히 잘못 판정되는 지점이다. 대부분 정상 응답에서는 드러나지 않는다.

  • ! RFC 9457 의 status member 는 advisory 다 — 그래도 generator 는 실제 HTTP status 와 일치시켜야 한다. 불일치는 서버 버그 신호로 보고 HTTP status 를 기준으로 판정하라.
  • ! unknown extension 은 무시 가능해야 한다 — 응답에 모르는 필드가 늘어난 것을 breaking change 로 판정하면 오탐이 쏟아진다.
  • ! about:blank 은 “type 없음” 의 기본값이다 — type 누락 자체는 실패가 아니다. 단, 이 경우 오류 식별자가 없으므로 status class 로 계약을 내려야 한다.
  • ! Retry-After 는 HTTP-date 도 온다 — 정수 파싱만 구현하면 date 형식에서 조용히 무시된다. 두 형식 모두 처리하라.
  • × title · detail 을 계약에 넣지 마라 — 사람이 읽는 문자열이다. 오류 종류를 구분하는 키는 type URI 다.
  • × 5xx 본문을 golden 으로 저장하지 마라 — 본문 exact pin 은 0 개다. 내부 정보가 저장소에 남고 배포마다 달라진다.
  • × problem type URI 를 자동으로 dereference 하지 마라 — 디버그 목적이 아닌 한 네트워크로 나가지 않는다. URI 는 식별자이지 가져올 리소스가 아니다.
  • ✓ status 가 흔들리면 class 로 내려라 — 4xx / 5xx 로 먼저 계약하고, 반복 관측에서 안정성이 확인된 뒤에 exact 로 좁힌다.
  • ✓ 401 에는 WWW-Authenticate challenge 가 동반되는지 확인한다 — 403 과 섞으면 토큰 갱신으로 풀리는 실패를 권한 문제로 오진한다.
  • › 오류 본문 스냅샷은 8KB 까지만 남긴다 — 대용량 stack trace 가 저장소에 쌓이는 것을 막는다.

판정 요약

HTTP status 로 판정하고, type URI 로 오류를 식별하고, Retry-After 로 재시도 가능성을 기록한다. class 로 시작해 안정성이 관측된 것만 pin 으로 좁히고, 5xx 본문은 어느 단계에서도 exact 로 올리지 않는다.
