계약 추출 모드 — partial · pin · exact

봉인된 baseline 에서 어떤 강도의 계약을 뽑을지 결정하는 규칙. 강도는 3 단계이며 각 단계가 잡아내는 회귀의 종류가 다르다. v0.1.0 · 최종 갱신 2026-09-04

먼저 읽어라 — pin 은 값 고정이 아니다

pin 은 payload 를 얼리는 모드가 아니라 경로마다 assertion 하나를 명시하는 모드다. 값 고정(const)은 pin 이 표현할 수 있는 assertion 중 한 종류일 뿐이다. total · cursor · id · timestamp 처럼 매 호출 변하는 필드에는 범위 · 패턴 · 불변식을 건다.

이 재정의는 나중에 붙인 설명이 아니라 초안을 뒤집은 결과다. 설계문서 초안은 “지정 필드는 값까지 고정” 이라고 적었는데, 픽스처에서 pin 을 건 $.meta.total(주문 총건수)이 매 호출 변하는 값이라 그 정의로는 자기모순이었다. 이어서 조사한 주류 도구 어디에서도 pin 이 그 뜻으로 쓰이지 않았다 — 발견된 용례는 버전 pin 과 기준 snapshot pin 뿐이다.

필드별 검증 강도를 실제로 표현하는 어휘는 Hurl 의 assert + predicate, Karate 의 schema marker, Pact 의 matcher, JSON Schema 의 const/enum 이다. 이름은 UI 전반에 아이콘이 이미 깔려 있어 pin 으로 유지하되 의미만 ‘경로별 명시 assertion’ 으로 재정의했다.

강도 3 단계와 각 단계가 잡는 회귀

같은 baseline 이라도 어떤 강도로 계약을 뽑느냐에 따라 잡히는 회귀가 달라진다. 기본은 partial 이고, 필요한 경로만 pin 으로 올린 뒤, 자격 조건을 통과한 응답에만 exact 를 건다.

기본값 partial 존재 · 타입 · enum — 형태만 본다. 객체를 닫지 않으므로 서버의 필드 추가는 통과한다.
옵트인 pin partial + 경로별 명시 assertion — 타입은 멀쩡한데 값만 망가진 회귀를 잡는다.
자격 필요 exact 정규화 후 본문 전체 diff. 변동 필드 레지스트리 적용 후 안정적일 때만 허용한다. 
partial (기본)  존재 · 타입 · enum          — 형태만 본다
pin             위 + 경로별 명시 assertion   — 타입은 멀쩡한데 값만 망가진 회귀를 잡는다
exact           정규화 후 본문 전체 diff
왜 중간 단계가 필요한가. exact 를 기본으로 두면 서버가 필드 하나 추가할 때마다 깨진다. partial 만 두면 조용한 회귀를 놓친다 — partial 은 "Bearer" → "bearer", 47 → -1, "active" → "ACTIVE" 를 전부 통과시킨다. 타입이 그대로이기 때문이다. 그래서 중요한 경로만 pin 으로 올리는 중간 단계를 둔다.
pin 의 실제 모양

assertion 종류 — 값 고정은 그중 하나다

pin 의 assertion 종류는 exists, type, nullable, pattern, range, enum, const, header predicate 등이다. 필드 성격에 따라 어떤 assertion 이 적합한지가 달라진다.

$.token_type = "Bearer"
값 고정(const) — 안정값에만 쓴다. discriminator · API 버전 · 통화 코드 · 고정 status.
$.meta.total >= len($.data)
불변식 — 매 호출 값이 변해도 관계는 유지된다.
$.data[].status ∈ {active, shipped, cancelled}
집합 소속 — 열거형 필드.
$.orderId ^ord_
패턴 — 식별자처럼 값은 변하지만 형식이 계약인 필드.
$.createdAt : string(date-time)
타입 + format.
필드 성격적합한 assertion예
안정값값 고정$.token_type = "Bearer"
열거형집합 소속$.data[].status ∈ active·shipped·cancelled
변동 수치범위 · 불변식$.meta.total ≥ len($.data) · $.price > 0
식별자패턴$.orderId ^ord_
컬렉션개수 불변식$.data[].isDefault 가 true 인 항목 정확히 1개

경로 간 불변식($.meta.total ≥ len($.data))은 Hurl assert 문법으로 쓸 수 없다 — Hurl 의 assert 는 경로 1 개에 predicate 1 개다. 이런 assertion 은 계약 YAML 의 pin 에만 기록하고 /api-verify 가 Hurl 실행 뒤 후처리 단계에서 검사한다. 상수로 근사하지 마라.

원칙

추출 규칙 9 가지

모드는 “얼마나 엄격하게” 가 아니라 “무엇을 계약으로 볼 것인가” 를 정한다. 같은 응답도 모드에 따라 계약 대상이 달라진다.

1

partial 은 최소 계약이다

partial

partial 은 관측된 안정 필드에 대한 최소 계약이다. JSON Schema 에서 properties 는 명시된 필드만 검증하고, additionalProperties 를 생략하면 열린 schema 로 동작한다. partial 에서는 객체를 닫지 않는다 — 서버가 필드를 추가했다는 이유로 실패하면 안 된다.

→ JSON Schema 2020-12 Core
2

pin 은 '값 고정' 이 아니라 경로별 명시 assertion 이다

pin 이 문서의 핵심

pin 은 payload 를 얼리는 모드가 아니다. 경로마다 하나의 assertion 을 명시하는 모드다. assertion 종류는 exists, type, nullable, pattern, range, enum, const, header predicate 등이며, 값 고정(const)은 그중 한 종류일 뿐이다. total · cursor · id · timestamp 처럼 매번 변하는 필드에는 범위 · 패턴 · 불변식을 건다. 

$.token_type = "Bearer"                        값 고정 (const)
$.meta.total >= len($.data)                    불변식
$.data[].status ∈ {active, shipped, cancelled} 집합
$.orderId ^ord_                                패턴
$.createdAt : string(date-time)                타입 + format
→ JSON Schema 2020-12 Validation
3

exact 는 자격 조건을 통과해야 쓴다

exact

exact 는 변동 필드 레지스트리를 적용한 뒤 JCS 정규화 payload 전체가 안정적일 때만 가능하다. JCS 는 object key order 를 제거하지만 array order 와 값 변화는 그대로 계약 차이로 남긴다. 자격 미달인 응답에 exact 를 걸면 매 실행이 실패하고, 그 실패는 곧 무시된다.

→ RFC 8785 JCS
4

exact 는 본문만 본다

exact 확정 결정 §12

exact diff 대상은 응답 본문뿐이다(2026-09-04 확정). Date 는 응답마다 생성되는 필드이고 X-Request-Id 류도 매 호출 달라지므로 헤더를 전체 diff 에 넣으면 항상 실패한다. 계약에 필요한 헤더는 exact 가 아니라 pin 으로 개별 지정한다. 

# 헤더는 exact 대상이 아니다 — 필요한 것만 pin
Content-Type   ^application/json
Cache-Control  = "no-store"
exact 본문 O · 헤더 0 개
→ RFC 9110 HTTP Semantics → RFC 8785 JCS → api-kit 설계 §12 확정된 결정 — exact 모드 범위
5

required 와 optional 은 샘플 교집합으로 판정한다

required 는 property name 의 존재 조건이지 값의 non-null 조건이 아니다. GenSON 은 관측된 모든 object 에 등장한 key 의 교집합만 required 로 삼는다. 단일 샘플에서 본 필드를 required 로 올리는 것은 그 자체로 오탐 생성기다.

→ JSON Schema 2020-12 Validation → GenSON
6

null 과 missing 을 합치지 않는다

null 은 '없는 필드' 가 아니라 하나의 JSON 값이다. JSON Schema 에서는 type: ["string", "null"] 처럼 null type 을 명시해야 하고, OpenAPI 3.0 의 nullable 은 같은 Schema Object 에 type 이 있을 때만 의미가 있다.

→ JSON Schema — null → OpenAPI 3.0.4
7

enum 은 1 샘플이면 후보로만 표시한다

확정 결정 §12

JSON Schema enum 은 닫힌 값 집합이고 const 는 단일 값 enum 과 동등하다 — 둘 다 관측 밖의 값을 실패시킨다. 그래서 1 샘플에서는 enum 을 확정하지 않고 후보로 표시하며 경고만 낸다(2026-09-04 확정). 3 샘플 이상에서 승격하고, 사용자가 직접 확정하는 수동 경로도 둔다. 오탐 실패가 도구 신뢰를 가장 빨리 깎기 때문이다. GenSON 은 seed 없이는 enum 을 아예 추론하지 않고, json-schema-inferrer 는 enum extractor 를 별도 설정으로 분리한다.

→ JSON Schema 2020-12 Validation → GenSON → json-schema-inferrer
8

배열 item 은 union 으로 일반화한다

JSON array 의 원소는 같은 type 일 필요가 없다. 여러 샘플 · 여러 item 에서 type 이 섞이면 첫 item 기준 schema 를 쓰지 말고 union / anyOf 계열로 일반화한다.

→ RFC 8259 JSON → json-schema-inferrer
9

additionalProperties 정책은 모드가 결정한다

partial pin exact

additionalProperties: false 는 관측되지 않은 모든 property 를 실패시키는 strict 정책이다. partial 에서는 열고, pin 에서는 명시한 path 만 검사하고, exact 에서만 전체 diff 로 닫는다. 모드와 무관하게 닫으면 서버의 정상적인 필드 추가가 전부 회귀로 보고된다.

→ JSON Schema 2020-12 Core

안티패턴

이렇게 하면 계약이 매번 깨진다

아래 두 쌍은 실제로 이 킷 초안이 걸렸던 지점이다. 오탐 한 번이면 사용자는 도구를 끄고, 꺼진 도구는 회귀를 하나도 못 잡는다.

BADpin 을 payload value freeze 로 구현
# 초안 정의: "지정 필드는 값까지 고정"
pin:
  - path: $.meta.total
    freeze: 47          # 주문 총건수
  - path: $.data[0].id
    freeze: "ord_8812"

# 두 번째 실행
$.meta.total  47 -> 48   FAIL
$.data[0].id  ord_8812 -> ord_8813   FAIL
GOOD경로별 assertion — 변동 필드는 관계로 건다
# 재정의: "경로마다 assertion 하나"
pin:
  - path: $.meta.total
    assert: ">= len($.data)"   # 후처리 검사
  - path: $.data[].id
    assert: "^ord_"            # Hurl 검사

# 두 번째 실행
$.meta.total  48 >= 12   PASS
$.data[].id   ord_8813   PASS

픽스처의 $.meta.total 이 자기모순을 드러낸 지점이다. 값 고정은 안정 필드에만 쓰고, 매 호출 변하는 필드에는 범위 · 패턴 · 불변식을 건다.

BAD단일 샘플 scalar 를 바로 닫힌 enum 으로 승격
# 샘플 1 개에서 status = "active" 만 관측
{ "properties": {
    "status": { "enum": ["active"] }
} }

# 정상 값 shipped 가 등장하면
$.data[0].status = "shipped"   FAIL (오탐)
GOOD1 샘플은 후보 + 경고, 3 샘플 이상에서 승격
# 1 샘플 — 확정하지 않는다
{ "properties": {
    "status": { "type": "string" }
} }
# WARN  enum 후보: status = ["active"] (samples=1)

# 3 샘플 이상 · distinct >= 2 에서만
{ "status": { "enum": ["active","shipped","cancelled"] } }

확정 결정 §12 1 샘플은 후보 표시만(경고), 3 샘플 이상에서 승격. 수동 확정 경로는 별도로 둔다.

닫힌 partial

partial 모드에서 additionalProperties: false 를 기본값으로 쓰면 서버의 정상적 필드 추가가 전부 실패로 잡힌다. 이 실패는 회귀가 아니라 도구의 오탐이다.

모드가 정책을 정한다

partial 에서는 열고, pin 에서는 명시한 path 만 검사하고, exact 에서만 전체 diff 로 닫는다. 닫는 시점을 모드에 묶어두면 “왜 실패했나” 가 항상 설명된다.

안티패턴문제
단일 샘플 scalar 를 바로 const 또는 닫힌 enum 으로 승격 두 번째 정상 값이 회귀로 보고된다. 오탐 한 번이면 사용자는 도구를 끈다
null 을 missing 과 합쳐 optionality 계산 nullable 필드가 optional 로 오분류되어 필드 소실 회귀를 놓친다
partial 모드에서 additionalProperties: false 를 기본값으로 사용 서버의 정상적 필드 추가가 전부 실패로 잡힌다
pin 을 payload 전체 value freeze 로 구현 total · cursor · timestamp 때문에 매번 실패한다. pin 은 경로별 assertion 이다
빈 배열이나 첫 item 하나로 items schema 확정 이후 등장하는 다른 type 원소가 전부 위반이 된다. union 으로 일반화해야 한다
Gotchas

추출 실행 전 확인

계약을 커밋하기 전에 아래를 하나씩 확인한다. 대부분은 조용히 통과한 뒤 나중에 오탐으로 돌아오는 항목이다.

  • ! required 는 non-null 을 보장하지 않는다 — 필드가 있어도 값이 null 일 수 있다. non-null 을 원하면 type 에서 null 을 제외해야 한다.
  • ! format 은 구현마다 annotation / assertion 지원이 다르다 — format 을 hard fail 조건으로 쓰려면 validator 설정에 명시적으로 묶어야 한다. 안 그러면 조용히 통과한다.
  • ! OpenAPI 3.0 nullable: true 는 다른 제약을 무력화하지 않는다 — enum 에 null 이 없으면 nullable 을 켜도 null 이 실패한다.
  • ! composition 에서는 additionalProperties 보다 unevaluatedProperties 가 정확하다 — additionalProperties 는 같은 schema object 의 properties / patternProperties annotation 에만 의존하기 때문이다.
  • × pin 을 값 고정으로 읽지 마라 — 경로별 assertion 이다. 변동 필드에 const 를 걸면 픽스처의 $.meta.total 과 같은 자기모순에 걸린다.
  • × 경로 간 불변식을 Hurl assert 로 쓰려 하지 마라 — Hurl 은 경로 1 개에 predicate 1 개다. 계약 YAML 의 pin 에 기록하고 /api-verify 후처리에서 검사한다. 상수로 근사하면 데이터가 늘어난 순간 무의미해진다.
  • ✓ exact 를 걸기 전에 자격 조건을 먼저 재라 — 동일 request fingerprint 로 ≥3 회 반복해 normalized JCS digest variance 가 0 인지 확인한다.
  • ✓ exact 대상은 본문뿐이다 — 헤더는 0 개. 필요한 헤더는 Content-Type ^application/json 처럼 pin 으로 개별 지정한다.
  • ✓ enum 을 자동 승격하기 전에 샘플 수를 세라 — 독립 샘플 ≥3, distinct value ≥2, 최근 20 관측에서 신규 값 없음, domain 크기 ≤12.
  • › required / optional / 미확정 3 분류로 제시하고 사용자에게 확정받는다 — 스냅샷이 2 개 이상이면 교집합을 required 후보로, 합집합 차분을 optional 후보로 올린다.

모드 선택 요약

partial 로 시작한다 → partial 이 통과시키는 값 회귀가 실제로 아프면 그 경로만 pin 으로 올린다 → 본문 전체가 반복 실행에서 완전히 동일함을 실측했을 때만 exact 를 건다. 단계를 건너뛰면 계약이 아니라 알람 소음이 된다.
