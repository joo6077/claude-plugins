api-kit / environment safety gates

환경 안전 게이트

실제 API 를 호출하기 전에 무엇을 허용할지 판정하는 규칙. 메서드 분류, prod 정책, 재시도·리다이렉트·부하 예산을 실행 직전에 결정한다. v0.1.0 · 최종 갱신 2026-09-04

분류(safe)와 허용(allow)은 다른 축이다

RFC 9110 은 TRACE 를 safe 로 분류한다. 그런데 TRACE 는 요청을 그대로 loop-back 하므로 쿠키와 Authorization 헤더가 응답 본문에 실려 돌아온다. 표준 분류를 그대로 실행 허용 목록으로 옮기면 Cross-Site Tracing 경로가 열린다. api-kit 은 분류는 RFC 를 따르되 허용은 따로 판정한다.

그래서 prod 기본 허용 동사는 GET · HEAD · OPTIONS 세 개로 고정됐다 — 사용자 확정 결정(2026-09-04, 설계문서 §12 · §8.1). 이 세 개를 넘어서는 범위를 allowlist 로 넓힐지는 아직 판단 유보 상태이며, 여지만 남겨 두고 기본값은 건드리지 않는다.

prod 실행 자체를 막지 않는다는 점도 같이 기억하라. 이 게이트는 차단이 아니라 좁히기다. 상태 변경은 4중 키 allowlist 로 승격됐을 때만 열린다.

이 문서가 결정하는 것

게이트는 요청 하나하나를 세 번 나눠 본다. 무슨 동사인가, 어느 환경인가, 총 부하가 얼마인가. 셋 중 하나라도 판정되지 않으면 실행하지 않는다.

01 · 분류 메서드 클래스 safe / unsafe 로 나눈다. TRACE 는 safe 로 분류되지만 허용에서는 빠진다.
02 · 정책 env 와 allowlist prod 는 read-only 가 기본. unsafe 는 env + host + path + method 4중 일치로만 열린다.
03 · 예산 부하 · 재시도 · 타임아웃 파일 × 요청 × --repeat × --jobs 를 곱해 상한과 비교하고, 타임아웃을 주입한다.

판정 순서는 고정이다. 앞 단계가 거부하면 뒤 단계는 계산하지 않는다.

1 method class 판정 safe / unsafe. 동사만 보고 끝내지 않고 path 패턴도 함께 본다.
2 env 정책 조회 prod 는 read-only 기본. dev / stg 는 각자 정책을 따른다.
3 allowlist 조회 env + host + path + method 네 값이 모두 일치해야 unsafe 가 열린다.
4 retry 정책 판정 멱등이 아니면 0회. 멱등이어도 파일 전체에 거는 방식은 쓰지 않는다.
5 redirect 정책 판정 same-origin 또는 명시 allow host 만. cross-host 는 0회.
6 부하 예산 계산 파일 수 × 요청 수 × --repeat × --jobs 를 상한과 비교한다.
7 타임아웃 주입 확인 connect-timeout 과 max-time 이 둘 다 있어야 실행한다.

기본 허용

GET HEAD OPTIONS

allowlist 없이 실행되는 유일한 집합. prod 기본값도 이 세 개다.

allowlist 승격 시에만

POST PUT PATCH DELETE

전부 상태 변경 메서드다. PUT · DELETE 가 멱등이라는 사실은 재시도 근거일 뿐이다.

기본 제외

TRACE

RFC 상 safe 지만 XST 위험으로 0회. 자격증명이 붙는 프로파일에서는 명시 요청도 거부한다.

원칙 9

각 원칙은 게이트의 한 판정 축이다. 하나를 빼면 그 축의 사고가 그대로 통과한다.

1

Safe 메서드 기본 허용

RFC 9110

기본 실행 허용 메서드는 GET, HEAD, OPTIONS 세 개다. 나머지는 allowlist 없이 실행하지 않는다. RFC 9110 은 TRACE 도 safe 로 분류하지만 api-kit 기본값에서는 보안 예외로 뺀다.

→ RFC 9110 §9.2.1 Safe Methods
2

TRACE 기본 제외

OWASP XST

TRACE 는 요청을 그대로 loop-back 하므로 쿠키나 Authorization 헤더가 응답 본문에 실려 돌아온다. OWASP 는 이를 Cross-Site Tracing 위험으로 다룬다. 기본 허용 횟수는 0이며, 사용자가 명시 요청해도 자격증명이 붙는 프로파일에서는 거부한다.

→ OWASP Cross-Site Tracing
3

prod 는 read-only 우선

env policy

prod 실행 자체는 허용한다. 다만 기본값은 read-only 이고, prod 에서의 상태 변경은 명시적 승격이 있을 때만 열린다. read-only 의 정확한 범위는 아직 확정되지 않았다 — 현재는 GET / HEAD / OPTIONS 로 두고, allowlist 로 넓힐 여지만 남긴다.

→ RFC 9110 §9.2.1 Safe Methods
4

unsafe 메서드는 4중 키 allowlist

env+host+path+method

POST, PUT, PATCH, DELETE 는 env + host + path + method 네 값이 모두 일치하는 항목이 allowlist 에 있을 때만 실행한다. PUT / DELETE 가 idempotent 라는 사실은 재시도 판단 근거이지 실행 허용 근거가 아니다 — 둘 다 상태 변경 메서드다.

→ RFC 9110 §9.3 Method Definitions
5

재시도는 멱등 요청만

retry = 0 default

자동 재시도는 safe 메서드, PUT, DELETE, 그리고 명시적으로 idempotent 태깅된 요청에만 허용한다. 그 외는 0회다. Hurl --retry 는 HTTP 실패뿐 아니라 assert · capture · runtime 오류에도 재시도하므로, 파일 전체에 걸지 말고 게이트가 더 좁게 잘라야 한다.

→ RFC 9110 §9.2.2 Idempotent Methods → Hurl Manual
6

크로스 호스트 리다이렉트 차단

same-origin only

리다이렉트 추종은 same-origin 이거나 명시적으로 allow 된 host 일 때만 허용한다. 크로스 호스트는 0회다. Hurl --location-trusted 는 리다이렉트된 모든 host 로 인증 정보를 전달하므로 기본 금지 옵션으로 취급한다.

→ Hurl Manual → RFC 6750 §5.2 Threat Mitigation
7

요청량 예산을 실행 전에 계산

files × req × repeat × jobs

env 별 최대 요청 수를 파일 수 × 요청 수 × --repeat × --jobs 기준으로 실행 전에 계산하고 상한과 비교한다. Hurl test mode 는 파일 단위 병렬 실행이 기본이고 --jobs 기본값이 CPU 수 기반이라, 단일 파일 감각으로 잡으면 prod 부하가 예상보다 커진다.

→ Hurl Manual → RFC 6585 §4 429 Too Many Requests
8

타임아웃 예산 강제

connect + max-time

모든 실제 호출에는 연결 타임아웃(connect-timeout)과 전체 실행 상한(max-time)이 둘 다 지정되어야 한다. Hurl 이 두 옵션을 제공하므로, 값이 비어 있으면 게이트가 env 기본값을 주입하고 그래도 없으면 실행을 막는다.

→ Hurl Manual
9

폭발 반경 태깅

blast radius

실행 항목마다 env, host, auth profile, method class, retry 횟수, concurrency, 최대 요청 수를 태깅하고 이 태그로 게이트를 판정한다. safe 메서드도 반복 · 병렬이면 서버에 "unusual burden" 이 되므로, 메서드 하나가 아니라 총 부하로 판단해야 한다.

→ RFC 9110 §9.2.1 Safe Methods → RFC 6585 §4
확정 결정 · prod 기본 허용 동사

prod 에서 자동 실행되는 동사는 GET · HEAD · OPTIONS 세 개다. 이건 기본값이 아니라 고정값이다.

무엇이 확정됐고 무엇이 열려 있는가

사용자 확정 결정(2026-09-04)으로 prod 의 기본 허용 동사 집합은 GET / HEAD / OPTIONS 로 고정됐다. 쓰기 메서드는 케이스에 prodWrite: true 를 명시해야 하고, 실행 시 대상 목록을 보여준 뒤 사용자 확인을 받는다. 목록 밖 호스트로 나가는 요청은 allowHosts 화이트리스트에서 무조건 차단한다 — baseUrl 변수 오염으로 stg 케이스가 prod 를 때리는 사고를 막기 위해서다.

아직 열려 있는 것은 이 세 개를 넘어 read-only 범위를 어디까지 넓힐지다. 그 판단은 유보 상태이며 allowlist 로 확장할 여지만 남겨 두었다. 유보를 "아직 아무것도 안 정해졌다" 로 읽지 마라 — 기본 집합 자체는 정해졌고, 확장 경로만 비어 있다.

규칙: prod 실행 계획에 GET · HEAD · OPTIONS 밖의 동사가 하나라도 있으면, 그 항목은 4중 키 allowlist 항목과 사용자 확인 없이 실행 큐에 들어갈 수 없다. prod auth 프로파일과 토큰 캐시도 다른 환경과 분리한다.
출처 없음 — 이 킷의 설계 결정 (설계문서 §12 확정 결정표 · §8.1 prod 가드)
수치 기준

표준에서 온 값과 이 킷이 추론한 값을 섞지 않는다. 근거 열이 추론 이면 프로젝트가 조정할 수 있는 값이고, RFC · OWASP 근거면 조정 대상이 아니다.

항목값근거
기본 safe allowlist GET, HEAD, OPTIONS (3개) RFC 9110 §9.2.1 + OWASP XST
TRACE 허용 0회 OWASP Cross-Site Tracing
non-idempotent 재시도 0회 RFC 9110 §9.2.2
Hurl 재시도 간격 기본값 1000ms Hurl Manual
prod --jobs 1 추론 — 병렬 기본값이 CPU 수 기반이라 상한 고정
prod unsafe 요청 0건 (allowlist 승격 시에만) 추론 — prod read-only 기본 정책
cross-host 리다이렉트 0회 추론 — 토큰 audience 가정 붕괴
same-origin 리다이렉트 상한 3회 추론
prod connect-timeout 5s 추론
prod max-time 30s 추론

허용 횟수 만 같은 축에 놓고 보면 게이트의 성격이 드러난다. 대부분이 0 이고, 0 이 아닌 항목은 두 개뿐이다.

TRACE 0회
non-idempotent retry 0회
cross-host redirect 0회
prod unsafe 요청 0건
prod --jobs 1
same-origin redirect 3회

막대 길이는 표의 횟수를 그대로 비율로 옮긴 것이다 (최대값 3회 = 100%). 0회 항목은 위치를 알아볼 수 있도록 최소 폭만 남겼다.

부하 예산: 총 요청 수 = 파일 수 × 파일당 요청 수 × --repeat × --jobs. prod 에서 --jobs 를 1 로 고정하는 이유가 이 곱셈에 있다. Hurl test mode 의 --jobs 기본값은 CPU 수 기반이라, 계산에서 빼면 실제 부하를 코어 수만큼 과소평가한다.
안티패턴

아래 다섯 가지는 전부 "게이트를 통과시켜 놓고 나중에 사고를 확인하는" 형태다. 실행 전에 판정하지 않으면 실행 후에 되돌릴 수 없다.

BAD --retry 를 Hurl 파일 전체에 지정 
hurl --test \
  --retry 3 \
  --retry-interval 1000 \
  cases/*.hurl

# cases/orders.hurl 안에는
#   POST /orders
#   POST /payments
# 가 섞여 있다 → 중복 생성·중복 결제
GOOD 게이트가 멱등 요청만 골라 재시도를 붙인다 
# 1) 게이트가 요청 단위로 분류
#    GET /orders/{id}   → idempotent  → retry 3
#    POST /orders       → non-idem    → retry 0

hurl --test --retry 0 cases/orders.hurl
# 멱등 항목에만 [Options] 로 개별 부여
#   [Options]
#   retry: 3

Hurl --retry 는 HTTP 실패뿐 아니라 assert · capture · runtime 오류에도 재시도한다. 파일 단위로 걸면 "assert 가 한 번 틀렸다" 는 이유로 POST 가 세 번 더 나간다.

BAD 인증 요청에 --location-trusted 
hurl --location-trusted \
  --secret token=$TOKEN \
  cases/me.hurl

# 302 → https://assets.example.net/...
# Authorization 헤더가 그대로 따라간다
GOOD same-origin 또는 allow host 로만 추종 
# 게이트 판정
#   redirect target host == request host ? 추종
#   allowHosts 에 있는가 ?          → 추종
#   그 외                           → 0회, 실행 거부

hurl --max-redirs 3 cases/me.hurl
# --location-trusted 는 기본 금지 옵션

호스트가 바뀌면 토큰 audience 가정도 함께 깨진다. 실행이 200 으로 끝나도 검증 대상이 의도한 서버가 아닐 수 있다.

BAD — 목적이 면책이 된다

prod 에서 POST / DELETE 를 "계약 검증이니까" 라며 기본 실행한다. 검증 목적은 상태 변경 면책이 아니다. 실데이터가 바뀌고, 스냅샷은 그 바뀐 상태를 baseline 으로 봉인한다.

GOOD — 승격을 거쳐 실행한다

prod 쓰기는 prodWrite: true 명시 + 4중 키 allowlist + 실행 전 대상 목록 확인을 모두 통과해야 한다. 세 관문 중 하나라도 비어 있으면 실행 큐에 들어가지 않는다.

BAD — 동사만 보고 판정

GET /delete?id=42 를 메서드만 보고 safe 로 통과시킨다. 메서드는 safe 여도 서버 동작은 mutation 이다. 분류는 요청의 형식이지 서버의 효과가 아니다.

GOOD — path 패턴을 함께 본다

method class 판정 단계에서 path 패턴 deny 목록(/delete, /remove, /purge 류)을 같이 조회한다. 걸리면 safe 동사여도 allowlist 경로로 보낸다.

BAD — 예산 없는 반복

--repeat 과 test mode 병렬을 예산 계산 없이 실행한다. 파일 수 × jobs 배로 부하가 늘어 rate limit(429) 또는 장애를 유발한다.

GOOD — 곱셈을 먼저 한다

실행 전에 파일 × 요청 × repeat × jobs 를 계산해 env 상한과 비교한다. 상한을 넘으면 실행하지 않고 계획을 되돌린다. safe 메서드라도 총 부하로 판단한다.

Gotchas · 실행 전 확인

아래 항목이 하나라도 미확인이면 실행 큐를 만들지 마라. 게이트는 실행 후에 다시 열 수 없는 판정이다.

  • ! TRACE 는 RFC 상 safe 다 — 표준만 보고 기본 safe set 에 넣으면 XST 경로가 열린다. 분류(safe)와 허용(allow)을 분리해서 판단했는지 확인하라.
  • ! Hurl --test 는 파일 단위 병렬이 기본 — 단일 파일 기준으로 계산한 요청 수는 실제 부하와 다르다. --jobs 를 곱해서 계산했는가.
  • × PUT / DELETE 는 재시도 후보이지 prod 기본 허용 후보가 아니다 — idempotent 와 read-only 는 다른 축이다. 둘을 같은 표에 놓고 판단하지 마라.
  • × 리다이렉트로 host 가 바뀌면 토큰 audience 가정도 깨진다 — 실행이 성공해도 검증 대상이 의도한 서버가 아닐 수 있다. 최종 응답의 host 를 기록했는가.
  • ✓ prod 실행 계획에 GET · HEAD · OPTIONS 밖의 동사가 있는가. 있다면 4중 키 allowlist 항목과 사용자 확인이 각각 존재하는가.
  • ✓ 모든 실제 호출에 connect-timeout 과 max-time 이 둘 다 지정되어 있는가. 비어 있으면 게이트가 env 기본값을 주입했는가.
  • ✓ 재시도가 붙은 항목이 전부 safe · PUT · DELETE · 명시 idempotent 태깅 중 하나인가. 나머지는 0회인가.
  • ✓ 요청량 곱셈(파일 × 요청 × repeat × jobs) 결과를 env 상한과 비교했는가. prod 에서 --jobs 가 1 로 고정되어 있는가.
  • ✓ 실행 항목마다 env, host, auth profile, method class, retry, concurrency, 최대 요청 수가 태깅되어 있는가. 태그 없는 항목은 게이트가 판정할 수 없다.
  • ✓ allowHosts 화이트리스트가 env 별로 채워져 있고, baseUrl 변수가 그 목록 안의 host 로만 해석되는가.
한 줄 요약: 메서드가 safe 라는 사실은 요청 하나가 안전하다는 뜻이지, 그 요청을 --repeat 로 수백 번 prod 에 날려도 된다는 뜻이 아니다. 게이트는 동사가 아니라 총 부하를 본다.
