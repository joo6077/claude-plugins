Format Checklist — 가이드 MD 포맷 표준

/setup-guide가 생산하는 모든 셋업 가이드 MD는 11개 섹션을 이 순서로 구성한다. 다만 순서는 표준이지 채우기 할당량이 아니다 — 해당 없는 섹션은 "해당 없음" 한 줄로 닫거나 생략한다. 그리고 각 Step의 맨 윗줄은 **출처:**다. 그 줄을 채울 수 없으면 그 Step은 아직 쓸 준비가 안 된 것이다.

11개 섹션 순서 흐름

헤더 → 사전 요구사항 → 설정 단계 → 코드 변경 → 권한 → 비용 → 환경 분기 → Rollback → 보안 → 검증 → 트러블슈팅. 이 순서는 사용자의 실제 진행 흐름을 반영하므로 임의로 재배열하지 않는다.

순서는 표준, 분량은 아니다. 요청 서비스에 해당 없는 섹션(클라이언트 전용 SDK의 IAM, 단발 셋업의 환경 분기 등)은 해당 없음 한 줄로 닫거나 생략한다. 억지 내용으로 부피를 늘리는 것은 스코프 이탈이다 (SKILL.md Gotcha 7).
1
헤더 필수
# <서비스명> 설정 가이드 제목.
> 작성일: YYYY-MM-DD — 가이드 신선도 확인용.
> 기준 버전: <SDK/CLI 버전> — 가능한 한 정확한 버전 명시.
> 공식 문서: <URL> — 1차 출처. 단 이 대표 URL은 Step별 출처를 대체하지 않는다.
2
사전 요구사항 필수
필요한 계정/권한, 설치할 CLI 도구(버전 포함), 프로젝트 전제조건.
사이트 혼동 주의 박스 — Apple/Google/AWS 가이드는 필수. 작업별 표로 명시한다.
콘솔 라벨 경계 한 줄 — 로그인이 필요한 콘솔을 다루면 필수.
3
설정 단계 (Step 1~N) 필수
각 Step은 4단 구조: 출처 → 어디서 → 무엇을 → 확인 방법.
Step 헤더 수와 **출처:** 줄 수가 같아야 한다 — guide_gate G1이 기계적으로 센다.
4
프로젝트 코드 변경 필수
확정한 그 스택의 파일만 쓴다. Flutter면 lib/main.dart · pubspec.yaml, 네이티브 iOS면 ios/Runner/AppDelegate.swift · Info.plist.
스택 혼용 금지 — guide_gate G3이 Flutter 가이드의 Swift 코드블록을 잡는다.
5
권한 / IAM 해당 시
| 시스템 | 필요한 권한 | 누구에게 | 3열 표. 최소 권한 원칙, 셋업용/운영용 권한 분리 권장.
클라이언트 전용 SDK처럼 IAM이 없는 서비스는 "해당 없음"으로 닫는다.
6
비용 필수
무료 한도 / 유료 진입점(어느 시점부터 과금) / 예상 월비용 범위 세 항목.
7
환경 분기 (dev / staging / prod) 해당 시
환경별 별도 프로젝트 필요 여부, 키/설정 파일 분리 패턴, Build Configuration 별 차이.
단발 셋업이면 "해당 없음" 한 줄.
8
Rollback / 정리 필수
잘못 설정했을 때 되돌리는 구체적 명령어 또는 콘솔 경로. 사용 안 할 때 리소스 정리(과금 방지).
9
보안 체크리스트 필수
비밀 키(.p8, service account JSON) 안전 저장소 보관 · .gitignore 패턴 추가 · 클라이언트 노출 가능 키와 서버 전용 키 구분 · 등록 토큰의 서버 측 격리.
10
검증 체크리스트 필수
체크박스 항목마다 확인 명령어 또는 콘솔 위치를 병기한다. 사용자가 직접 체크 가능한 형태로.
11
트러블슈팅 필수
각 항목 3단: 증상(에러 메시지/현상) + 원인 + 해결(번호 매긴 구체 단계).
설정 단계 — Step 4단 구조

맨 위 **출처:** 줄이 출처 원장(SKILL.md §출처 원장)의 아티팩트다. 이 줄을 채울 수 없으면 그 Step은 fetch 없이 학습 데이터로 쓰였다는 뜻이므로, 아직 쓸 준비가 안 된 것이다.

Step 템플릿 (마크다운)

## Step N — <단계 제목>

**출처:** <이 Step 의 근거 1차 출처 URL — 조회 YYYY-MM-DD>

**어디서:** <URL 또는 터미널 위치>

**무엇을:**

1. <구체적 액션 — 클릭 경로 또는 명령어>
2. ...

**확인 방법:** <성공 검증 — 명령어, 콘솔 위치, 예상 출력>
↗ Firebase — Set up FCM on Flutter (Step별 출처 인용 예시)
1
중복 허용

같은 URL 반복 OK

여러 Step이 같은 문서를 근거로 하면 같은 URL을 반복해도 된다. 중복이 보기 싫다는 이유로 생략하지 않는다 — 생략하는 순간 G1이 깨진다.
↗ 단일 문서가 여러 Step의 근거가 되는 실제 사례
2
대체 불가

헤더 URL ≠ Step 출처

헤더(§1)의 대표 공식 문서: URL은 Step별 출처를 대체하지 않는다. 대표 URL 하나로 전체를 정당화하는 것이 이 스킬의 대표 실패 형태였다.
↗ Apple Developer Help — Account (섹션별 근거 분리 예)
3
기계 판정

Step 수 = 출처 줄 수

권고가 아니라 판정이다. guide_gate G1이 ^## Step 수와 ^**출처:** 수를 세어 비교한다. 하나라도 어긋나면 G1_LEDGER FAIL.
↗ QA Evaluation Guide — 증거 아티팩트 규약
3단 Step — fetch 흔적이 없다
  • **출처:** 줄 없이 어디서 / 무엇을 / 확인 방법만 씀 → 어느 문서를 근거로 썼는지 재현 불가
  • 헤더의 대표 URL 하나로 8개 Step 전체를 정당화
  • "최신 정보 기준" 이라고 적었지만 조회일이 어디에도 없음
  • Step 8개 · 출처 0줄 → G1_LEDGER FAIL steps=8 ledger=0
4단 Step — 원장이 남는다
  • Step 맨 위 **출처:** <URL> (조회 2026-08-13)
  • 같은 문서를 쓰는 Step은 같은 URL을 그대로 반복
  • fetch 실패 Step은 [미검증:ENV] + 4요건 근거로 남김
  • Step 8개 · 출처 8줄 → G1_LEDGER PASS steps=8 ledger=8
출처 원장 — 미검증 마커 분류

fetch가 끝까지 실패한 항목은 조용히 넘기지 않는다. 마커는 접미로 분류한다 — 접미 없는 [미검증]은 정본에서 INVALID로 해석되므로 쓰지 않는다.

상황마커카운터판정 처리
1차 출처 문서에 접근 자체가 불가했다 — 네트워크·도구 부재·크로스호스트 fetch 실패 등 통제 불가 요인 [미검증:ENV] env_gaps 자동 REJECT 카운터에 합산하지 않는다. 검증 커버리지로 따로 보고
도구 부재라고 적었지만 fallback 사다리를 안 탔거나, 조회는 됐는데 그 출력이 아무것도 입증하지 못한다 [미검증:INVALID] 임계 카운터 건수별 판정은 정본이 정한다 — 킷에서 숫자를 재정의하지 않는다
문서에 그 내용이 없다 / 아직 안 썼다 / 이번엔 안 돌리기로 했다 마커 아님 — FAIL — 해당 Step을 쓰지 않거나 사용자에게 묻는다
접미 없는 레거시 표기 [미검증] — 정본에서 INVALID로 해석 · guide_gate G2가 bare로 세어 즉시 FAIL
임계 숫자를 이 킷에서 다시 적지 않는다. 킷마다 임계를 따로 쓰면 같은 상태가 킷마다 다른 판정으로 갈린다 (정본이 기록한 실측 drift: 킷별 2 / 3 / 0 건). 마커 의미·분류·임계의 정본은 harness/docs/guides/qa-evaluation-guide.md §Canonical Unverified-Evidence Protocol 이며, 동의어(미확인, N/A, unverified)를 새로 만들지 않는다.

[미검증:ENV] 4요건 — 하나라도 없으면 INVALID 강등

요건 ①
1차 도구 시도 기록과 그 출력
요건 ②
fallback 사다리 4단계를 실제로 탄 기록
요건 ③
실패를 서술이 아닌 출력으로
요건 ④
왜 통제 밖인지 한 문장 + 재검증 명령

사다리를 실제로 타지 않은 :ENV 주장은 [미검증:INVALID]로 강등된다 — "이번엔 안 조회하기로 했다"는 마커가 아니라 그냥 미완이다

Guide Conformance Gate — G1~G4 기계 판정

이 규칙들은 문장(E1)이나 자기보고 체크리스트(E2)가 아니라 결정론적 게이트(E3)다. LLM을 호출하지 않는 순수 판정이며, 지금 쓰는 가이드와 이미 배포된 가이드 양쪽에 똑같이 적용된다.

규칙은 소급된다. 실측 2026-08-13 — 이 킷의 쇼케이스 예제가 킷 자신의 evals 6 케이스 중 3개를 3개월간 위반한 채 배포돼 있었다 (출처 원장 0/8, Flutter 가이드에 네이티브 Swift 초기화, 출처에 없는 .p12 deprecated 단정). 규칙과 evals는 고쳤는데 이미 나간 산출물을 다시 재는 경로가 없었다.
G1
출처 원장 완전성 — grep -c '^## Step ' 과 grep -c '^\*\*출처:\*\*' 두 값이 같아야 한다. 열거값은 타이핑하지 말고 계산한다. 출력: G1_LEDGER PASS steps=8 ledger=8
G2
미검증 마커 분류/임계 — bare(접미 없는 [미검증])는 0건이어야 하고, invalid는 정본 임계 미만이어야 한다. env는 별도 카운터로 센다. 게이트 안의 상수는 정본을 구현한 값이지 킷이 새로 정한 값이 아니다 — 정본이 바뀌면 같이 바꾸되 여기서 먼저 바꾸지 않는다.
G3
스택 혼용 — 스택 인자가 flutter 인데 ```swift 코드펜스가 있으면 실패. 산문으로 "Flutter는 AppDelegate를 건드리지 않는다"고 쓰는 것은 통과한다 — 코드 지시만 잡는다.
G4
deprecation 주장 결합 — ❌ Deprecated 박스를 쓴 Step은 그 Step의 **출처:** 줄이 "출처가 실제로 deprecated 라고 말했다"는 근거를 담아야 한다. 근거 없는 박스 수를 unsourced_boxes로 센다.

보고 규약

게이트 출력을 그대로 붙여라

"게이트 통과함"이라는 문장은 증거가 아니다 — GATE_PASS를 포함한 5줄 출력이 증거다.

G1_LEDGER PASS steps=8 ledger=8
G2_MARKER PASS bare=0 invalid=0 env=0
G3_STACKMIX PASS stack=flutter swift_fence=0
G4_DEPRECATION PASS unsourced_boxes=0
GATE_PASS

GATE_FAIL이면 완료 보고를 하지 말고 고친 뒤 다시 돌린다.

↗ 실제 산출물에 돌린 게이트 출력 — FCM iOS 예제
Regeneration Drift

이미 있는 가이드부터 잰다

같은 서비스의 가이드가 이미 있으면 덮어쓰거나 무시하지 말고 기존 파일에 게이트를 먼저 돌린다.

find docs/setup -type f -name '*.md' 2>/dev/null | while IFS= read -r f; do
  printf '%s\n' "--- $f"; guide_gate "$f" "$STACK"
done

GATE_FAIL이 나오면 그것이 이번 작업의 첫 산출물이다. 글로빙 대신 find를 쓰는 이유: zsh는 nomatch가 기본이라 매치 0인 글로브가 명령을 통째로 죽인다.

↗ Setup Guide — Phase 1 Regeneration Drift 검사
게이트를 우회하거나 조건을 느슨하게 고치지 마라. 우회된 게이트는 없는 게이트보다 나쁘다. 게이트가 잡는 것은 기계로 판정 가능한 4가지뿐이며, 사실 정확성·스코프·경로 날조는 여전히 Gotchas와 Phase 4 검증의 몫이다. 단일 게이트는 보장이 아니다.
사전 요구사항 — 두 개의 필수 박스

섹션 2의 맨 위에는 두 가지가 들어간다. 하나는 작업별 사이트 표, 다른 하나는 콘솔 라벨 경계 한 줄이다. 둘 다 사용자가 가장 먼저 막히는 지점을 겨냥한다.

박스 ① — 작업별 사이트 표

박스 ② — 콘솔 라벨 경계

로그인 뒤 화면은 검증 불가다

로그인이 필요한 콘솔을 다루는 가이드라면 아래 한 줄이 필수다.

> **ℹ️ 콘솔 라벨 경계:** 이 가이드의 섹션명·버튼 라벨은 **로그인 없이 볼 수 있는
> 공식 문서**에서 확인한 것입니다. 로그인 뒤 실제 화면은 공개 문서로 검증할 수
> 없어 표기가 다를 수 있습니다 (A/B 롤아웃 · 언어 설정). 화면에서 못 찾으면
> **상위 섹션명**(`Identifiers`, `Keys`, `Cloud Messaging`)으로 검색하세요.

못 찾을 때 쓸 상위 섹션명 검색어를 함께 주는 것까지가 절차다. 없는 확신을 파는 것보다 정직한 경계 표시가 사용자를 덜 헤매게 한다.

↗ Search Strategy — WebFetch로 닿지 않는 것
Deprecated / 현재 권장 박스 — 출처보다 강한 주장 금지

❌ Deprecated 박스는 1차 출처가 실제로 deprecated 라고 말한 경우에만 쓴다. "권장하지 않음" · "새 방식이 권장됨"을 deprecation으로 승격하지 마라 — 출처보다 강한 주장을 쓰는 것도 날조다.

날조 — 실제로 3개월간 배포됐던 문장
  • ❌ Deprecated: APNs Certificate (.p12) — 2020년 이후 비권장
  • 1차 출처(FCM Apple/Flutter 문서)는 .p12를 deprecated로 표기한 적이 없다
  • .p8을 안내한다는 사실로부터 .p12의 deprecation을 추론했다
  • 박스는 있는데 그 Step의 **출처:** 줄에 근거가 없음 → G4_DEPRECATION FAIL unsourced_boxes=1
출처 강도 그대로 — 현행 예제 표기
  • ✅ 현행 가이드가 안내하는 방식: APNs Authentication Key (.p8)
  • ".p12 방식도 여전히 존재하지만, 이 가이드는 1차 출처가 안내하는 .p8 흐름만 다룬다"
