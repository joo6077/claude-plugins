Format Checklist — 가이드 MD 포맷 표준

/setup-guide 가 만드는 셋업 가이드 MD 는 11 개 섹션을 이 순서로 쓴다. 순서는 표준이지만 채우기 할당량은 아니다 — 해당 없는 섹션은 "해당 없음" 한 줄로 닫거나 뺀다. 각 Step 의 맨 윗줄은 **출처:** 이고, 그 줄을 채울 수 없으면 그 Step 은 아직 쓸 준비가 안 된 것이다. 사전 요구사항의 막는 요구는 출처 · 막히는 것 · 우회 세 칸으로 쓴다. 이 페이지는 사용자가 따라가다 막히지 않도록 섹션마다 빠뜨리기 쉬운 것을 모은 목록이다.

11개 섹션 순서 흐름

헤더 → 사전 요구사항 → 설정 단계 → 코드 변경 → 권한 → 비용 → 환경 분기 → Rollback → 보안 → 검증 → 트러블슈팅. 사용자가 실제로 진행하는 순서를 따른 것이라 임의로 바꾸지 않는다.

순서는 표준, 분량은 아니다. 요청 서비스에 해당 없는 섹션(클라이언트 전용 SDK 의 IAM, 단발 셋업의 환경 분기 등)은 해당 없음 한 줄로 닫거나 뺀다. 억지 내용으로 부피를 늘리지 않는다 (SKILL.md Gotcha 7 — 요청한 서비스 · 범위만 가이드한다).
1
헤더 필수
# <서비스명> 설정 가이드 제목.
> 작성일: YYYY-MM-DD — 가이드가 얼마나 최근 것인지 알려 준다.
> 기준 버전: <SDK/CLI 버전> — 가능한 한 정확한 버전.
> 공식 문서: <URL> — 1차 출처. 이 대표 URL 은 Step 별 출처를 대신하지 않는다.
2
사전 요구사항 필수
필요한 계정 · 권한(예: Apple Developer Program 가입), 설치할 CLI 도구(버전 포함), 프로젝트 전제조건.
막는 요구면 세 칸으로 쓴다 2026-09-24 — 출처 · 막히는 것 · 우회 (SKILL.md Gotcha 9).
사이트 혼동 주의 박스 — Apple / Google / AWS 가이드는 필수. 작업별 표로 쓴다.
콘솔 라벨 경계 한 줄 — 로그인이 필요한 콘솔을 다루면 필수.
3
설정 단계 (Step 1~N) 필수
Step 마다 4단 구조: 출처 → 어디서 → 무엇을 → 확인 방법.
Step 헤더 수와 **출처:** 줄 수가 같아야 하고, Step 마다 출처 줄이 정확히 하나여야 한다 — guide_gate G1 이 센다.
4
프로젝트 코드 변경 필수
확정한 그 스택의 파일만 쓴다. Flutter 면 lib/main.dart · pubspec.yaml, 네이티브 iOS 면 ios/Runner/AppDelegate.swift · Info.plist.
코드 블록마다 언어 라벨 필수. 스택 혼용은 guide_gate G3 가 Flutter 가이드의 Swift 코드 블록으로 잡는다.
5
권한 / IAM 해당 시
| 시스템 | 필요한 권한 | 누구에게 | 3열 표. 최소 권한 원칙, 셋업용 권한과 운영용 권한을 나눈다.
클라이언트 전용 SDK 처럼 IAM 이 없는 서비스는 "해당 없음" 으로 닫는다.
6
비용 필수
무료 한도(예: FCM 무제한, Firebase Spark plan) / 유료 진입점(어느 시점부터 과금) / 예상 월비용 범위 세 항목.
7
환경 분기 (dev / staging / prod) 해당 시
환경마다 별도 프로젝트가 필요한지, 환경별 키 · 설정 파일을 나누는 방식, Build Configuration 별 차이.
단발 셋업이면 "해당 없음" 한 줄.
8
Rollback / 정리 필수
잘못 설정했을 때 되돌리는 구체적 명령어 또는 콘솔 경로. 쓰지 않을 때 리소스 정리(과금 방지).
9
보안 체크리스트 필수
비밀 키(.p8, JSON service account 등) 안전 저장소 보관 · .gitignore 에 비밀 파일 패턴 추가 · 클라이언트에 노출돼도 되는 키와 서버 전용 키 구분 · FCM 등록 토큰 / 사용자 토큰을 서버 쪽에 격리.
10
검증 체크리스트 필수
체크박스 항목마다 확인 명령어 또는 콘솔 위치를 붙인다. 사용자가 직접 하나씩 체크할 수 있는 모양으로.
11
트러블슈팅 필수
항목마다 3단: 증상(에러 메시지 · 현상) + 원인 + 해결(번호 매긴 구체 단계).
§2 사전 요구사항 — 두 개의 필수 박스

사전 요구사항에는 박스 두 개가 들어간다. 하나는 작업별 사이트 표, 다른 하나는 콘솔 라벨 경계 한 줄이다. 둘 다 사용자가 가장 먼저 막히는 자리를 겨냥한다. 막는 요구를 쓰는 법은 바로 다음 절에 따로 둔다.

박스 ① — 사이트 혼동 주의 (Apple / Google / AWS 필수)

"셋업은 전부 A 사이트" 는 금지

진입할 사이트 URL 과 비슷한 다른 사이트의 차이를 작업별 표로 적는다. 어느 사이트냐는 작업마다 갈린다. 뭉뚱그려 안내하면 앱 레코드 생성 · 빌드 업로드 · TestFlight 에서 사용자가 곧바로 막힌다. SKILL.md Gotcha 3 의 Apple 7 행 표가 형식 예시다 (조회 2026-08-13, Apple 공개 Help 기준).

작업사이트섹션 / 흐름
Bundle ID / App ID 등록Apple Developer AccountCertificates, Identifiers & Profiles → Identifiers → App IDs
APNs 키 생성Apple Developer AccountCertificates, Identifiers & Profiles → Keys (APNs 선택 → .p8 다운로드)
인증서Apple Developer AccountCertificates
Provisioning ProfileApple Developer AccountProfiles / Provisioning Profiles
앱 레코드 생성App Store ConnectApps → + → New App
빌드 업로드App Store ConnectXcode / Transporter / API — bundle ID + version + build string 으로 연결
TestFlightApp Store Connectbeta build 배포 · 테스터 관리 · 피드백

키 · 식별자 발급은 Developer Account, 앱이라는 레코드와 배포는 App Store Connect 다. 요청받은 셋업이 어느 행인지 먼저 정하고 그 행만 가이드에 넣는다. 같은 모양이 다른 플랫폼에도 있다 — GCP Console 과 Firebase Console, AWS Console 과 AWS Marketplace.

박스 ② — 콘솔 라벨 경계 (로그인 콘솔 필수)

로그인 뒤 화면은 검증할 수 없다

로그인이 필요한 콘솔을 다루는 가이드라면 "이 가이드의 섹션명 · 버튼 라벨은 공개 문서 기준이며, 로그인 뒤 실제 화면과 다를 수 있다" 를 적고, 못 찾을 때 쓸 상위 섹션명 검색어를 함께 준다 (SKILL.md Gotcha 2).

> **ℹ️ 콘솔 라벨 경계:** 이 가이드의 섹션명·버튼 라벨은 **로그인 없이 볼 수 있는
> 공식 문서**에서 확인한 것입니다. 로그인 뒤 실제 화면은 공개 문서로 검증할 수
> 없어 표기가 다를 수 있습니다 (A/B 롤아웃 · 언어 설정). 화면에서 못 찾으면
> **상위 섹션명**(`Identifiers`, `Keys`, `Cloud Messaging`)으로 검색하세요.

상위 섹션명 검색어까지 주는 것이 절차의 끝이다. 없는 확신을 파는 것보다 경계를 정직하게 적는 쪽이 사용자를 덜 헤매게 한다.

§2 막는 요구는 세 칸으로 쓴다 — SKILL.md Gotcha 9

계정 등급 · 기기 · 권한 · 출시 상태처럼 없으면 어떤 작업이 멈추는 요구마다 세 칸을 채운다. 「이게 없으면 진행할 수 없다」 한 줄로 끝내지 않는다 — 실제로 막히는 범위는 대개 셋업 전체가 아니라 그중 한 작업이다.

1
칸 ① 출처

그 요구를 적은 1차 출처

1차 출처 URL 과 조회일을 적는다. 출처가 요구하지 않으면 막는 요구로 쓰지 않는다 — 요구를 적은 문장이 출처에 없으면 그 줄을 지운다.
↗ 예: Firebase Apple 셋업 — 실기기 요구를 적은 문서
2
칸 ② 막히는 것

멈추는 Step · 작업

요구가 없으면 멈추는 Step · 작업을 적는다. 안 막히는 작업도 함께 적는다 — 그래야 사용자가 지금 할 수 있는 일을 먼저 끝낸다.
↗ 예: Apple 지원 기능 표 — 계정 종류별로 막히는 기능
3
칸 ③ 우회

출처가 제시하는 우회 하나

출처에 우회가 있으면 하나를 적는다. 출처에 없으면 우회 없음(출처 확인) 으로 적고 우회를 지어내지 않는다.
↗ 예: Apple 가입 비용 면제 — 출처가 직접 적은 우회
한 줄 — 셋업 전체가 막힌 것처럼 읽힌다
  • 실기기가 필요합니다. 없으면 진행할 수 없습니다.
  • 유료 개발자 계정이 필요합니다. — 어느 작업이 막히는지 없음
  • 앱을 먼저 출시해야 합니다. — 출처가 요구하지 않는 요구
  • 사용자는 프로젝트 생성 · Firebase 구성처럼 지금 할 수 있는 작업까지 멈춘다
세 칸 — 막히는 범위가 보인다
  • 요구마다 출처 URL + 조회일
  • 막히는 것: APNs · FCM 원격 메시지 수신 확인 · 안 막히는 것: 프로젝트 생성 · Firebase 구성 · 일반 앱 실행
  • 우회: 출처에 있으면 하나, 없으면 우회 없음(출처 확인)
  • 출처가 요구하지 않는 「앱 출시」 는 막는 요구 칸에 쓰지 않는다

예 — FCM iOS (조회 2026-09-24)

원본 체크리스트가 형식 예시로 싣는 세 요구다. 셋 가운데 하나는 막는 요구가 아니다 — 출처를 읽으면 드러난다.

§3 설정 단계 — Step 4단 구조

맨 위 **출처:** 줄이 출처 원장(Step 마다 근거 URL 과 조회일을 남기는 기록 — SKILL.md §출처 원장)의 실물이다. 이 줄을 채울 수 없으면 그 Step 은 fetch 없이 학습 데이터로 쓴 것이니 아직 쓸 준비가 안 된 것이다.

Step 템플릿 (마크다운)

## Step N — <단계 제목>

**출처:** <이 Step 의 근거 1차 출처 URL — 조회 YYYY-MM-DD>

**어디서:** <URL 또는 터미널 위치>

**무엇을:**

1. <구체적 액션 — 클릭 경로 또는 명령어>
2. ...

**확인 방법:** <성공 검증 방법 — 명령어, 콘솔 위치, 예상 출력>
↗ Firebase — Set up FCM on Flutter (Step 별 출처 인용 예)
1
반복 허용

같은 URL 반복 OK

여러 Step 이 같은 문서를 근거로 하면 같은 URL 을 반복해도 된다. 보기 싫다고 빼지 않는다 — 빼는 순간 G1 이 깨진다.
↗ 한 문서가 여러 Step 의 근거가 되는 실제 사례
2
대신할 수 없음

헤더 URL ≠ Step 출처

헤더(§1)의 대표 공식 문서: URL 은 Step 별 출처를 대신하지 않는다. 대표 URL 하나로 전체를 정당화하는 것이 이 스킬의 대표 실패 형태였다.
↗ Setup Guide — 출처 원장 (Source Ledger)
3
기계 판정

Step 수 = 출처 줄 수

권고가 아니라 판정이다. guide_gate G1 이 두 값을 세어 비교하고, Step 마다 출처 줄이 정확히 하나인지도 따로 센다. 어긋나면 G1_LEDGER FAIL.
↗ QA Evaluation Guide — 증거 규약
필요할 때 넣는 박스 ①

⚠️ 주의 박스

그 Step 에서 흔히 하는 실수를 적는다. 예: 글로벌 유니크 식별자(Bundle ID · Package Name · Project ID)는 전 세계 모든 계정에 걸쳐 겹치면 안 된다 — 조직 도메인을 거꾸로 붙인 접두어를 쓴다.

> **⚠️ 주의:** Bundle ID 는 빌드 업로드 후 바꿀 수 없다.

필요할 때 넣는 박스 ②

❌ Deprecated / ✅ 현재 권장

§3 출처 원장 — 미검증 마커 분류

fetch 가 끝까지 실패했으면 **출처:** [미검증:ENV] — <시도 · 실패 출력 · 통제 불가 사유 · 재검증 명령> 으로 남긴다. 마커는 접미로 나눈다 — 접미 없는 [미검증] 은 정본(기준이 되는 원본 문서)에서 INVALID 로 읽히므로 쓰지 않는다. 분류 · 임계는 SKILL.md §출처 원장을 따르고, 그 정본은 harness/docs/guides/qa-evaluation-guide.md §Canonical Unverified-Evidence Protocol 이다.

상황마커카운터판정
1차 출처 문서에 접근 자체가 불가했다 — 네트워크 · 도구 부재 · 호스트를 넘는 fetch 실패처럼 통제할 수 없는 요인 [미검증:ENV] env_gaps 자동 REJECT 카운터에 더하지 않는다. 검증 커버리지 (총 Step − env_gaps) / 총 Step 로 따로 보고
도구 부재라고 적었지만 fallback 사다리를 안 탔거나, 조회는 됐는데 그 출력이 아무것도 입증하지 못한다 [미검증:INVALID] 임계 카운터 건수별 판정은 정본 §카운팅 및 자동 REJECT 임계가 정한다 — 킷에서 숫자를 다시 정하지 않는다
문서에 그 내용이 없다 / 아직 안 썼다 / 이번엔 안 돌리기로 했다 마커 아님 — FAIL — 그 Step 을 쓰지 않거나 사용자에게 묻는다
접미 없는 옛 표기 [미검증] — 정본에서 INVALID 로 읽힘 · guide_gate G2 가 bare 로 세어 바로 FAIL
임계 숫자를 이 킷에서 다시 적지 않는다. 킷마다 임계를 따로 쓰면 같은 상태가 킷마다 다른 판정으로 갈린다 (정본이 기록한 실측: 킷별 2 / 3 / 0 건). 커버리지 임계도 정본 §검증 커버리지 게이트를 따른다. 동의어(미확인, N/A, unverified)를 새로 만들지 않는다.

Deprecated / 현재 권장 박스 — 출처보다 강한 주장 금지

❌ Deprecated 박스는 1차 출처가 실제로 deprecated 라고 말한 경우에만 쓴다. "권장하지 않음" · "새 방식이 권장됨" 을 deprecation 으로 끌어올리지 않는다 — 출처보다 강한 주장을 쓰는 것도 날조다.

날조 — 실제로 3 개월간 배포됐던 문장
  • ❌ Deprecated: APNs Certificate (.p12) — 2020년 이후 비권장
  • 1차 출처(FCM Apple / Flutter 문서)는 .p12 를 deprecated 로 적은 적이 없다
  • .p8 을 안내한다는 사실에서 .p12 의 deprecation 을 추론했다
  • 박스는 있는데 그 Step 의 **출처:** 줄에 근거가 없음 → G4_DEPRECATION FAIL unsourced_boxes=1
출처가 쓴 강도 그대로 — 현행 예제 표기
  • ✅ 현행 가이드가 안내하는 방식: APNs Authentication Key (.p8)
  • ".p12 방식도 여전히 있지만, 이 가이드는 1차 출처가 안내하는 .p8 흐름만 다룬다"
  • "1차 출처가 .p12 를 어떤 강도로 평가하는지 대신 판단하지 않는다"
  • 박스 자체를 안 쓰므로 G4 대상이 아님 → unsourced_boxes=0
박스를 쓸 수 있는 조건

근거를 출처 줄에 묶는다

박스를 쓰면 그 Step 의 **출처:** 줄에 "출처가 deprecated 라고 명시" 근거를 함께 적는다. 한국어 1차 출처면 그 표기 그대로 적는다 — "출처가 '지원 종료' 라고 명시", "폐지", "중단".

G4 가 근거로 인정하는 낱말은 영문 deprecated · sunset · removed 와 한국어 지원 종료 · 폐지 · 중단 · 서비스 종료 · 단종 이다. 박스가 있는 Step 의 출처 줄에 이 가운데 하나도 없으면 FAIL.

실측 2026-07-27 · 재확인 2026-08-13: FCM Apple / Flutter 문서는 APNs 인증 키(.p8)를 안내하지만 인증서(.p12)를 deprecated 로 적지 않는다.

영문 낱말에만 묶여 있던 동안의 구멍. G4 가 영문 토큰만 볼 때는 한국어 1차 출처가 "지원 종료" 라고 분명히 적어도 근거가 없는 박스로 세어 FAIL 이었다. 지금은 두 언어를 모두 근거로 인정한다.
Guide Conformance Gate — G1~G4 기계 판정

위 규칙들은 문장(E1)이나 자기보고 체크리스트(E2)가 아니라 결정론적 게이트(E3) 로 잰다. guide_gate <가이드.md> <스택> 은 LLM 을 부르지 않는 순수 판정이고, 지금 쓰는 가이드와 이미 배포된 가이드를 똑같이 잰다. 함수 본문은 SKILL.md §Guide Conformance Gate 에 있다.

규칙은 이미 나간 가이드에도 소급된다. 실측 2026-08-13 — 이 킷의 쇼케이스 예제가 킷 자신의 evals 6 케이스 중 3 개를 3 개월간 어긴 채 배포돼 있었다 (출처 원장 0/8, Flutter 가이드에 네이티브 Swift 초기화, 출처에 없는 .p12 deprecated 단정). 규칙과 evals 는 고쳤는데 이미 나간 산출물을 다시 재는 경로가 없었다.
G1
출처 원장 완전성 — grep -c '^## Step ' 와 grep -c '^\*\*출처:\*\*' 두 값이 같아야 하고 Step 이 0 개면 FAIL. 전체 수만 맞추면 한 Step 에 출처 둘 · 다른 Step 에 0 인 배치가 통과하므로 Step 마다 정확히 하나인지 따로 세어 misplaced= 로 낸다. 값은 손으로 적지 말고 계산한다.
G2
미검증 마커 분류 · 임계 — bare(접미 없는 [미검증])는 0 건, invalid 는 정본 임계 미만이어야 한다. env 는 따로 센다. 게이트 안의 상수는 정본을 구현한 값이지 킷이 새로 정한 값이 아니다 — 정본이 바뀌면 같이 바꾸되 여기서 먼저 바꾸지 않는다.
G3
스택 혼용 — 스택 인자가 flutter 인데 ```swift 코드 펜스가 있으면 FAIL. 산문으로 "Flutter 는 AppDelegate 를 건드리지 않는다" 고 쓰는 것은 통과한다 — 코드 지시만 잡는다. 스택 인자가 비면 PASS 가 아니라 FAIL (stack=unset) 이다. 2026-09-08 까지는 빈 스택을 PASS 로 흘렸고, 다시 재는 루프의 $STACK 이 어디에도 없어 이 검사가 3 개월간 아무것도 막지 못했다.
G4
deprecation 주장 결합 — ❌ Deprecated 박스를 쓴 Step 은 그 Step 의 **출처:** 줄이 "출처가 실제로 deprecated 라고 말했다" 는 근거를 담아야 한다. 근거 없는 박스 수를 unsourced_boxes 로 센다. 근거 낱말은 영문과 한국어를 모두 인정한다.

게이트 출력을 그대로 붙여라

"게이트 통과함" 이라는 문장은 증거가 아니다 — GATE_PASS 를 포함한 5 줄 출력이 증거다.

G1_LEDGER PASS steps=8 ledger=8
G2_MARKER PASS bare=0 invalid=0 env=0
G3_STACKMIX PASS stack=flutter swift_fence=0
G4_DEPRECATION PASS unsourced_boxes=0
GATE_PASS

실패하면 이렇게 나온다 — 어느 칸이 왜 깨졌는지 출력에 그대로 있다.

G1_LEDGER FAIL steps=8 ledger=8 misplaced=2
G3_STACKMIX FAIL stack=unset swift_fence=0
GATE_FAIL

GATE_FAIL 이면 완료 보고를 하지 말고 고친 뒤 다시 돌린다.

Regeneration Drift

이미 있는 가이드부터 잰다

같은 서비스의 가이드가 이미 있으면 덮어쓰거나 무시하지 말고 기존 파일에 게이트를 먼저 돌린다.

STACK=flutter   # Phase 1 에서 확정한 스택. 비워 두면 G3 가 FAIL 한다.
find docs/setup -type f -name '*.md' 2>/dev/null | while IFS= read -r f; do
  printf '%s\n' "--- $f"; guide_gate "$f" "$STACK"
done

GATE_FAIL 이 나오면 그것이 이번 작업의 첫 산출물이다. 글로빙 대신 find 를 쓰는 이유: zsh 는 nomatch 가 기본이라 매치 0 인 글로브가 명령을 통째로 죽인다.

↗ Setup Guide — Phase 1 Regeneration Drift 검사
게이트를 우회하거나 조건을 느슨하게 고치지 마라. 우회된 게이트는 없는 게이트보다 나쁘다. 게이트가 정당한 경우를 막는다고 보이면 사용자에게 보고하고 판단을 받는다. 게이트가 잡는 것은 기계로 판정할 수 있는 4 가지뿐이고, 사실 정확성 · 범위 · 경로 날조는 여전히 Gotchas 와 Phase 4 검증의 몫이다.
게이트 함수를 고쳤으면 evals 부터. sh onboarding-kit/skills/setup-guide/evals/run-gate-evals.sh 가 EVALS_PASS 로 끝나야 한다. 이 스크립트는 SKILL.md 에서 함수를 그대로 뽑아 evals/evals.json 의 gate_cases 입력마다 zsh · bash 두 셸의 출력을 기대 출력 전체와 맞대 본다. 판정이 바뀌는 수정이면 기대 출력도 같은 커밋에서 고친다.
§4 프로젝트 코드 변경 — 스택 혼용 금지, 그리고 반대 방향 오해

이 섹션에는 확정한 그 스택에 실제로 있는 파일만 쓴다. 파일 경로를 적고, 추가 · 변경할 코드 블록(언어 라벨 필수)과 설정 파일 변경(pubspec.yaml, .env 등)을 구체적으로 적는다. 한 스택의 절차에 다른 스택의 파일 · 코드를 섞으면 사용자는 없는 파일을 찾게 된다.

스택 혼용 — 대표 사고 형태 (Gotcha 1)
  • Flutter 가이드에 ios/Runner/AppDelegate.swift 초기화를 최소 필수처럼 넣음
  • ```swift 코드 펜스로 네이티브 초기화 호출을 지시
  • Flutter 의 현행 절차(FlutterFire CLI + Dart 초기화)에는 나오지 않는 단계
  • G3_STACKMIX FAIL swift_fence=1
스택을 정한 뒤 그 스택만
  • Flutter: lib/main.dart · pubspec.yaml
  • 네이티브 iOS: ios/Runner/AppDelegate.swift · Info.plist
  • 코드 블록마다 언어 라벨(dart / swift / bash)
  • 경로는 레포를 Glob / Grep 으로 실제로 찾은 것만 — 없으면 "이 Step 에서 새로 만든다" 로 적는다
  • G3_STACKMIX PASS stack=flutter swift_fence=0
반대 방향 오해도 막아라. "네이티브 코드 수정 없음" 이 "Xcode 프로젝트 설정도 없음" 은 아니다. Capability 추가, Background Modes 같은 Xcode 프로젝트 설정은 Flutter 앱에서도 여전히 필요한 iOS 프로젝트 작업이다. 코드 변경 섹션과 프로젝트 설정 Step 을 나눠서 쓴다.

톤 / 표기 규칙

가이드 전체에 같은 표기 규칙을 쓴다. 특히 클릭 경로는 중간 단계를 건너뛰지 않는다 — 한 단계라도 빠지면 사용자가 화면에서 못 찾는다.

항목규칙예시
클릭 경로 → 화살표로 잇는다 · 중간 단계 생략 금지 Settings ⚙️ → General → Cloud Messaging 탭 → iOS app configuration → APNs authentication key → Upload
명령어 코드 블록 + 언어 라벨 bash · swift · dart
라벨 병기 영문 라벨이 정본, 한국어는 괄호 Upload (업로드) — 반대로 쓰면 화면에서 못 찾는다
외부 도메인 링크 마크다운 링크로 — bare URL 금지 [Identifiers 페이지](https://...)
어려운 용어 괄호 풀이 Service Account (서비스 계정 — 자동화용 가상 사용자)
클릭 경로 실측 예. Firebase Console 경로는 FCM Apple 클라이언트 문서 2026-07-27 조회 기준 문서 표기 그대로 Settings ⚙️ → General → Cloud Messaging 탭 → iOS app configuration → APNs authentication key → Upload 다. 이전 표기는 General 단계가 빠져 있었다 — 한 단계가 빠지면 사용자는 거기서 멈춘다.
한국어 라벨은 번역 추정이다. 콘솔이 여러 언어를 지원하면 사용자가 화면에서 맞춰 보도록 두 라벨을 함께 적는다. 다만 1차 출처는 대개 영문이므로 영문 라벨을 정본으로 적고 한국어를 괄호에 넣는다. 한국어를 정본으로 적으면 콘솔 언어가 영어인 사용자가 화면에서 찾지 못한다.
