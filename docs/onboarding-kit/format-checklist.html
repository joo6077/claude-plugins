Format Checklist — 11개 표준 섹션

생성되는 모든 셋업 가이드 MD가 따라야 하는 11개 섹션의 순서와 각 섹션의 필수 내용. 섹션 순서는 사용자가 따라가는 흐름과 일치하도록 설계되었다. 하나라도 빠지면 사용자가 실패 지점에서 막히게 된다.

11개 섹션 순서 흐름

섹션 순서는 임의로 바꿀 수 없다. 헤더 → 사전 요구사항 → 설정 단계 → 코드 변경 → 권한 → 비용 → 환경 분기 → Rollback → 보안 → 검증 → 트러블슈팅 순서는 사용자의 실제 진행 흐름을 반영한다.

1
헤더 필수
# <서비스명> 설정 가이드 제목.
> 작성일: YYYY-MM-DD — 가이드 신선도 확인용.
> 기준 버전: <SDK/CLI 버전> — 가능한 한 정확한 버전 명시.
> 공식 문서: <URL> — 1차 출처 링크, 절대 생략 불가.
2
사전 요구사항 필수
필요한 계정/권한 (예: Apple Developer Program 가입, Editor 이상 Firebase 권한).
설치해야 할 CLI 도구 (버전 포함).
사이트 혼동 주의 박스 — Apple/Google/AWS 가이드는 필수. 진입할 사이트 URL과 다른 비슷한 사이트의 차이를 표로 명시.
3
설정 단계 (Step 1~N) 필수
각 Step은 3단 구조: 어디서 (URL 또는 터미널 위치) + 무엇을 (클릭 경로 또는 명령어) + 확인 방법 (성공 검증).
각 Step에 필요시 ⚠️ 주의 박스, ❌ Deprecated / ✅ 현재 권장 박스 삽입.
4
프로젝트 코드 변경 필수
스택별로 변경할 파일과 코드를 구체적으로. 파일 경로 명시 (예: lib/main.dart, ios/Runner/AppDelegate.swift).
추가/변경할 코드 블록 (언어 라벨 필수). 설정 파일 변경 (pubspec.yaml, .env).
5
권한 / IAM 필수
최소 권한 원칙으로 표 형식 기술. 셋업용 권한과 운영용 권한 분리 권장.
예: Apple Developer — Account Holder 또는 Admin / Firebase Console — Editor 이상.
6
비용 필수
무료 한도 (예: FCM 전송량 제한 없음 무료). 유료 진입점 (어느 시점부터 과금). 예상 월비용 범위.
7
환경 분기 (dev / staging / prod) 필수
환경별로 별도 프로젝트가 필요한지. 환경별 키/설정 파일 분리 패턴.
Build Configuration 별 차이 (예: Xcode Run Script로 환경별 plist 교체).
8
Rollback / 정리 필수
잘못 설정했을 때 되돌리는 방법 (구체적 명령어 또는 콘솔 경로). 사용 안 할 때 리소스 정리 (과금 방지).
9
보안 체크리스트 필수
비밀 키 안전 저장소 보관 (.p8, JSON service account 등). .gitignore에 비밀 파일 패턴 추가.
클라이언트 노출 가능 키와 서버 전용 키 구분. 등록 토큰/사용자 토큰의 서버 측 격리.
10
검증 체크리스트 필수
최소 3~5개 체크박스 항목. 각 항목에 확인 명령어 또는 콘솔 위치를 병기. 사용자가 직접 체크 가능한 형태로.
11
트러블슈팅 필수
각 항목 3단 구조: 증상 (에러 메시지 또는 현상) + 원인 (원인 분석) + 해결 (구체적 단계). 최소 3개 케이스 포함.
설정 단계 — Step 3단 구조 상세

모든 Step은 어디서 + 무엇을 + 확인 방법 3단으로 구성해야 한다. 하나라도 빠지면 사용자가 진행 중 막힌다.

잘못된 Step 작성 — 막힘 유발
  • "Firebase 콘솔에서 앱을 등록하세요." — 어디서, 무엇을, 확인 방법 모두 없음
  • URL 없이 "설정 페이지로 이동" — 사용자가 못 찾음
  • 확인 방법 없이 단계 나열 — 성공 여부를 알 수 없음
  • 스택별 코드 분기 없이 통합 예시 — 잘못된 코드 복붙 위험
  • 명령어에 버전 없이 "최신 버전 설치" — 재현 불가
올바른 Step 작성 — 사용자가 따라갈 수 있음
  • 어디서: https://developer.apple.com/account → Identifiers
  • 무엇을: 1. + 버튼 클릭 2. App IDs 선택 3. Bundle ID 입력 4. Push Notifications 체크 5. Register
  • 확인 방법: Identifiers 목록에 새 App ID가 보이고 Push Notifications 활성화 표시
  • Flutter 전용 코드 블록에 dart 언어 라벨 + 파일 경로 명시
  • dart pub global activate flutterfire_cli — 정확한 명령어

Step 템플릿 (마크다운)

## Step N — <단계 제목>

**어디서:** https://<URL> 또는 <터미널 위치>

**무엇을:**

1. <구체적 액션 — 클릭 경로 또는 명령어>
2. ...

> ⚠️ **주의:** <흔한 실수>  ← 필요시만 삽입

**확인 방법:** <성공 검증 — 명령어, 콘솔 위치, 예상 출력>

사이트 혼동 주의 박스는 사전 요구사항 섹션 최상단에 위치해야 한다 — 중간에 삽입하면 사용자가 이미 잘못된 사이트에 진입한 뒤임

Deprecated / 현재 권장 박스 형식

설정 단계에서 deprecated된 방법을 발견하면 조용히 생략하지 않고 명시적 박스로 대비한다. 사용자가 인터넷에서 검색하면 옛 방법이 상위에 노출되기 때문에 가이드에서 명확히 구분해줘야 헤매지 않는다.

Deprecated 박스 형식

마크다운 템플릿

> **❌ Deprecated:** <옛 방법>
> <비추천 이유 — 간결하게>
>
> **✅ 현재 권장:** <새 방법>
> <새 방법의 장점>

실제 예시:

> **❌ Deprecated:** APNs Certificate (.p12)
> 매년 갱신 필요, 환경별 분리, 2020년 이후 비권장.
>
> **✅ 현재 권장:** APNs Authentication Key (.p8)
> 갱신 불필요, dev/prod 모두 커버, Team 전체 앱 공유 가능.
↗ Firebase — APNs 인증 방식 비교
Deprecated 감지 기준

언제 박스를 삽입하는가

  • ×문서의 마지막 업데이트가 2년 이상 지남
  • ×본문에 "deprecated", "legacy", "will be removed", "removed in" 키워드 발견
  • ×API/SDK 메이저 버전 변경 안내 포함
  • ×"use X instead" 같은 대체 권장 발견
  • +하나라도 해당하면 ❌/✅ 박스 삽입 — 조용한 생략 금지
↗ Apple Developer — Private Key 생성
권한 / IAM 표 + 비용 섹션 형식

권한과 비용은 가이드에서 자주 생략되지만, 셋업 후 운영 단계에서 가장 많이 문제가 되는 부분이다. 최소 권한 원칙과 무료 한도를 명확히 해야 사용자가 예상치 못한 과금을 피할 수 있다.

섹션 6: 비용

3항목 필수 기재

톤 / 표기 규칙

가이드 전체에서 일관된 표기 규칙을 적용한다. 일관성이 없으면 사용자가 화면에서 텍스트를 매칭할 때 혼란을 겪는다.

항목 규칙 예시

명령어 코드 블록 + 언어 라벨 필수 ```bash, ```swift, ```dart
한국어 / 영어 병기 콘솔이 다국어 지원 시 병기 업로드 (Upload), 클라우드 메시징 (Cloud Messaging)
외부 도메인 링크 마크다운 링크로 — bare URL 금지 [Identifiers 페이지](https://developer.apple.com/...)
어려운 용어 괄호 풀이 병기 Service Account (서비스 계정 — 자동화용 가상 사용자)

트러블슈팅 섹션 (섹션 11) 형식

트러블슈팅은 실제 사용자가 막히는 지점에서 수집된 에러 케이스를 기반으로 작성한다. 최소 3개 케이스를 포함하고 각각 3단 구조를 따른다.

트러블슈팅 항목 템플릿 (마크다운)

**증상:** <에러 메시지 또는 사용자가 보는 현상>
**원인:** <기술적 원인 분석 — 왜 이 현상이 발생하는지>
**해결:**

1. <구체적 해결 단계 1>
2. <구체적 해결 단계 2>
3. ...
↗ FlutterFire — FCM 트러블슈팅
필수 포함 케이스 유형: ① 글로벌 유니크 식별자 충돌 에러 ("not available") ② 등록과 활성화 누락 에러 ③ 플랫폼별 권한/인증 실패 에러. 이 세 가지는 모든 외부 서비스 가이드에서 공통으로 발생하는 패턴이다.
케이스 예시 1

App ID 충돌

증상: App ID 등록 시 "An App ID with Identifier 'com.example.app' is not available"

원인: Bundle ID는 전 세계 Apple Developer 계정에 걸쳐 유니크. 흔한 조합은 이미 선점됨.

해결: 조직/도메인 reverse prefix 강화 — com.<github핸들>.appname 또는 환경별 분리 suffix (.dev, .staging).

↗ Apple — Bundle ID 정책
케이스 예시 2

등록 ≠ 활성화

증상: App ID는 등록했는데 Xcode Signing & Capabilities에서 Push Notifications 추가가 안 됨 또는 회색.

원인: Apple Developer Portal의 App ID에 Push Notifications capability가 비활성 상태. 또는 무료 개인 계정 Team 사용 (Push 불가).

해결: Identifiers 페이지 → 해당 App ID → Capabilities → Push Notifications 체크 → Save. Xcode 재시작.

↗ Apple — Push Notifications Capability
