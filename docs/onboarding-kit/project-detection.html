Project Detection — 스택 무관 탐지 패턴

의존성 파일 글로브 탐색, 코드 grep, 인프라 파일 스캔을 종합하여 프로젝트 스택과 외부 서비스 의존성을 자동 탐지한다. 단일 스택 프로젝트부터 멀티스택 모노레포까지 커버한다. 탐지 실패 시 추측 금지 — 사용자에게 명시적으로 묻는다.

탐지 3단계 흐름

스택 탐지는 3가지 소스를 순서대로 종합한다. 하나의 소스만으로 판단하면 모노레포나 레거시 프로젝트에서 오탐이 발생한다.

1
Layer 1

의존성 파일 스캔

루트에서 글로브 탐색으로 의존성 파일을 찾는다. 파일 존재 여부와 내부 키 패턴으로 스택을 매핑한다.

pubspec.yaml→Flutter / Dart
Cargo.toml→Rust
package.json→Node.js / JS
go.mod→Go
↗ pub.dev — pubspec.yaml 구조
2
Layer 2

코드 grep — SDK 패턴

의존성 파일만으로 탐지되지 않는 활성 서비스는 코드 내 SDK 초기화 패턴을 grep해서 찾는다.

firebase_core→Firebase
Sentry.init→Sentry
stripe.api_key→Stripe
passport-→OAuth
↗ Firebase — SDK 초기화 패턴
3
Layer 3

인프라 파일 스캔

환경변수, Docker, IaC 파일에서 외부 서비스 키 패턴을 확인한다.

.env*→환경변수 키
docker-compose*.yml→컨테이너 의존성
terraform/*.tf→IaC 리소스
k8s/*.yaml→K8s 매니페스트
↗ FlutterFire — Firebase 환경 설정
의존성 파일 → 스택 매핑 전체

글로브 탐색에서 찾은 파일 이름과 내부 키 패턴의 조합으로 스택을 확정한다. 파일이 존재해도 내부 키 패턴이 없으면 보조 힌트로만 처리한다.

파일 (글로브) 스택 확정 세분화 조건 우선순위 주의사항
pubspec.yaml Flutter / Dart flutter: 키 존재 시 Flutter 확정. 없으면 순수 Dart 패키지 Flutter 프로젝트는 ios/Podfile도 보유 — Podfile 단독으로 iOS 네이티브로 판단하면 오탐
Cargo.toml Rust [workspace] 있으면 Rust 워크스페이스 모노레포 —
package.json Node.js / JS dependencies 안의 react, next, vue, express 등으로 세분 프론트엔드 vs 백엔드 구분 필수 — SDK 설치 명령과 초기화 코드가 다름
requirements.txt / pyproject.toml Python poetry, pip, uv 중 어느 패키지 매니저 사용 여부 확인 Django / FastAPI / Flask 세분화로 SDK 초기화 방식 결정
go.mod Go 모듈 이름으로 주요 프레임워크(Gin, Echo, Fiber) 추론 가능 —
Gemfile Ruby rails gem 포함 여부로 Rails 확정 —
composer.json PHP Laravel 여부 별도 확인 (laravel/framework 키) —
build.gradle / build.gradle.kts JVM (Android / Kotlin / Java) com.android.application 플러그인 존재 시 Android 확정 Flutter 프로젝트도 android/build.gradle 보유 — pubspec.yaml 우선
Podfile iOS 네이티브 (Swift/Obj-C) — 우선순위 낮음 — Flutter도 ios/Podfile 보유하므로 pubspec.yaml 먼저 확인
*.xcodeproj / *.xcworkspace iOS 네이티브 — 마찬가지로 Flutter 프로젝트에도 존재 — pubspec.yaml 우선
.csproj / .sln .NET ASP.NET Core vs MAUI vs Blazor 세분 —

Flutter 프로젝트는 pubspec.yaml + ios/Podfile + android/build.gradle을 동시에 보유하므로 pubspec.yaml을 최우선으로 처리한다

외부 서비스 의존성 grep 패턴

코드 안의 SDK 사용 흔적을 찾아 활성 서비스 목록을 도출한다. 의존성 파일에서 패키지가 선언되어 있어도 실제 코드에서 초기화 패턴이 없으면 사용 여부 불명확으로 처리한다.

서비스 grep 패턴 (코드 내) 환경변수 패턴 (.env*)
Firebase firebase_core, firebase_messaging, FirebaseApp.configure, initializeApp FIREBASE_*, GOOGLE_APPLICATION_CREDENTIALS
GCP google-cloud-, from google.cloud, GOOGLE_APPLICATION_CREDENTIALS GOOGLE_CLOUD_PROJECT, GCP_PROJECT_ID
AWS boto3, aws-sdk, @aws-sdk/, import software.amazon.awssdk AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_REGION
Stripe stripe.api_key, import Stripe from "stripe", stripe.Client( STRIPE_SECRET_KEY, STRIPE_PUBLISHABLE_KEY
Sentry Sentry.init, sentry-sdk, sentry_dsn SENTRY_DSN, SENTRY_AUTH_TOKEN
OAuth oauth2, passport-, next-auth, Sign in with OAUTH_CLIENT_ID, NEXTAUTH_SECRET
멀티스택 모노레포 처리

루트에 의존성 파일이 여러 개 있거나 하위 디렉토리에 별도 스택이 있으면 모노레포로 판단하고 디렉토리별로 재스캔한다.

A
탐지 로직

모노레포 판단 조건

루트에 위 의존성 파일 2개 이상이 존재하면 모노레포로 판단한다. 하위 디렉토리(예: app/, server/, web/)별로 재귀 스캔을 실행한다.

전형적인 패턴:

myproject/
├── app/          # pubspec.yaml → Flutter
├── server/       # package.json → Node.js
└── infra/        # terraform/*.tf → GCP/AWS

이 경우 어느 스택의 가이드를 만들지 사용자에게 명시적 확인이 필수다.

↗ FlutterFire 멀티플랫폼 설정
B
공통 충돌

Flutter 프로젝트 오탐 방지

Flutter 프로젝트는 아래 파일들을 동시에 보유한다:

  • pubspec.yaml — Flutter 확정
  • ios/Podfile — Flutter가 생성, iOS 네이티브 아님
  • android/build.gradle — Flutter가 생성, Android 네이티브 아님
  • ios/Runner.xcworkspace — Flutter가 생성

따라서 pubspec.yaml이 있으면 나머지 파일의 스택 시그널을 무시하고 Flutter로 확정한다.

↗ pub.dev — flutter 프로젝트 구조
탐지 결과 0건 처리

의존성 파일과 grep 패턴이 모두 매칭되지 않을 때의 처리 방침. 추측해서 잘못된 가이드를 작성하는 것보다 사용자에게 묻는 것이 훨씬 낫다.

잘못된 처리 — 추측 기반 작성
  • 파일이 없어도 "Flutter일 것 같으니" 그냥 Flutter 가이드 작성
  • 사용자가 서비스 이름만 언급했다고 임의 스택 가정
  • 이전 대화의 스택을 새 프로젝트에 그대로 적용
  • 탐지 없이 "일반적인" 가이드 작성 — 어느 스택에도 정확히 안 맞음
올바른 처리 — 명시적 확인
  • 탐지 실패 시 즉시 사용자에게 질문: "어떤 환경에서 진행하시나요?"
  • 선택지 제시: Flutter / 네이티브 iOS (Swift) / React Native / Node 백엔드 / 기타
  • 사용자 답변 후 해당 스택에 맞는 가이드만 작성
  • 멀티스택 모노레포라면 어느 하위 스택의 가이드인지 재확인
탐지 실패 질문 템플릿: "프로젝트 스택이 자동 감지되지 않습니다. 어떤 환경에서 진행하시나요? (Flutter / 네이티브 iOS / React Native / Node 백엔드 / 기타)" — 이 문장을 그대로 사용하면 된다.
인프라 / 환경 파일 스캔 상세

코드와 의존성 파일에서 서비스 사용이 탐지되지 않더라도 인프라 파일은 별도로 스캔한다. 팀에서 외부 서비스를 사용하고 있지만 클라이언트 코드에 아직 연동하지 않은 경우를 커버한다.

파일 패턴 탐지 대상 핵심 패턴
.env, .env.local, .env.production 환경변수에서 외부 서비스 키 흔적 FIREBASE_*, AWS_*, STRIPE_*, GOOGLE_*
docker-compose*.yml, Dockerfile 컨테이너 의존성 서비스 서비스 이름, 이미지 이름에서 외부 서비스 추론
terraform/*.tf, terraform/**/*.tf IaC로 프로비저닝되는 외부 서비스 리소스 google_firebase_project, aws_s3_bucket, aws_sns_topic
k8s/*.yaml, helm/** Kubernetes 환경의 서비스 의존성 ConfigMap, Secret 이름 패턴
firebase.json, .firebaserc Firebase CLI 구성 — Firebase 사용 강력한 신호 파일 존재 자체로 Firebase 확정
GoogleService-Info.plist Firebase iOS 구성 — Firebase + iOS 조합 확정 파일 존재 자체로 Firebase + iOS 확정
google-services.json Firebase Android 구성 — Firebase + Android 확정 파일 존재 자체로 Firebase + Android 확정
탐지 완료 검증 체크리스트

Phase 1에서 스택과 서비스 탐지를 완료한 후 가이드 작성을 시작하기 전에 아래 체크리스트를 실행한다.

  • ✓
    스택 단일 확정 — 여러 스택 파일이 탐지됐다면 우선순위 규칙(pubspec.yaml 최우선 등)으로 하나로 좁혔는가, 또는 멀티스택임을 사용자에게 확인했는가
  • ✓
    서비스 목록 확정 — 의존성 파일 + 코드 grep + 인프라 파일 세 소스를 모두 스캔했는가. 빈 인자 실행이라면 탐지된 서비스 목록을 사용자에게 제시하고 선택을 받았는가
  • ✓
    Flutter 오탐 방지 — ios/Podfile 또는 android/build.gradle만 보고 네이티브 스택으로 분류하지 않았는가. pubspec.yaml 존재 여부를 먼저 확인했는가
  • ✓
    멀티스택 확인 — 루트에 의존성 파일이 2개 이상이라면 하위 디렉토리별로 재스캔했는가. 어느 스택의 가이드인지 사용자에게 명시적으로 확인했는가
  • ✓
    추측 없음 — 탐지 결과 0건일 때 임의로 스택을 가정하지 않았는가. 사용자에게 선택지를 제시하고 답변을 기다렸는가
  • ✓
    Firebase 구성 파일 확인 — GoogleService-Info.plist, google-services.json, firebase.json 존재 여부를 별도 체크했는가. 이 파일들은 Firebase 사용의 강력한 시그널이다
