Project Detection — 스택 무관 탐지 패턴

/setup-guide 스킬이 프로젝트 스택을 자동 감지할 때 참조한다. 단일 스택부터 멀티 스택 모노레포까지 커버한다. 의존성 파일로 스택을 정하고, 코드 grep 과 인프라·환경 파일로 쓰고 있는 외부 서비스를 찾는다. 아무것도 안 나오면 추측하지 않고 묻는다.

01 · 이 문서를 쓰는 자리

/setup-guide 의 Phase 1 은 스택을 먼저 확정하고, 그다음 외부 서비스 의존성을 찾는다. 이 문서의 표 셋이 그 두 단계에 그대로 쓰인다. 스택을 확정하지 않고 가이드를 쓰면 같은 서비스라도 SDK 설치 명령과 초기화 코드가 통째로 틀린다.

02 · 의존성 파일 → 스택 매핑

원본 표 11 행을 그대로 옮겼다. 파일 이름만으로 정해지는 행이 있고, 파일 안의 키를 한 번 더 봐야 세분되는 행이 있다. 비고 칸이 그 차이다.

파일 (글로브 탐색) 스택 비고
pubspec.yaml Flutter / Dart flutter: 키 존재 시 Flutter 확정
Cargo.toml Rust [workspace] 있으면 워크스페이스
package.json Node.js / JS dependencies 안의 react/next/vue 등으로 세분

build.gradle / build.gradle.kts JVM (Android/Kotlin/Java) —

.csproj / .sln .NET —

B
우선순위 낮음

Podfile 하나로 iOS 네이티브라 정하지 않는다

Flutter 프로젝트도 ios/Podfile 을 갖고 있다. 그래서 원본은 Podfile 행을 우선순위 낮음으로 둔다. pubspec.yaml 에 flutter: 키가 있으면 Flutter 로 확정하고, ios/Podfile 은 그 Flutter 프로젝트의 일부로 읽는다.

이걸 뒤집으면 Flutter 앱에 네이티브 iOS 가이드가 나간다. Flutter 와 네이티브 iOS 는 같은 서비스라도 SDK 설치 명령과 초기화 코드가 다르다.

03 · 멀티스택 모노레포 탐지

원본의 세 줄은 순서대로 읽힌다. 판단하고, 하위 폴더에서 다시 찾고, 마지막에 사용자에게 묻는다. 셋째 줄을 건너뛰고 한 스택을 골라 쓰지 않는다.

  1. 1
    판단 — 루트에 위 파일 여러 개가 있으면 모노레포로 판단
  2. 2
    다시 스캔 — 하위 디렉토리(예: app/, server/, web/)별로 다시 스캔
  3. 3
    확인 — 사용자에게 명시적으로 어느 스택의 가이드를 만들지 확인
예
하위 폴더별 결과 예시

폴더마다 스택이 따로 나온다

폴더 이름은 원본이 든 예(app/ · server/ · web/)를 썼다. 각 폴더의 파일은 설명을 위한 예다.

myproject/
├── app/       # pubspec.yaml  → Flutter / Dart
├── server/    # package.json  → Node.js / JS
└── web/       # package.json  → Node.js / JS

이 상태에서 「FCM 설정」 을 요청받으면 app 쪽 가이드인지 server 쪽 가이드인지가 갈린다. 그래서 3 번에서 묻는다.

↗ project-detection.md — 멀티스택 모노레포 탐지
!
요청한 범위만

확인한 스택 하나만 가이드한다

사용자가 고른 스택의 가이드만 만든다. 나머지 폴더에서 찾은 서비스를 「있으면 좋으니까」 같이 묶지 않는다.

인자 없이 /setup-guide 를 부른 경우에는 탐지한 서비스 목록을 먼저 보여 주고 어떤 가이드를 만들지 고르게 한다.

04 · 외부 서비스 의존성 grep 패턴

코드 안의 SDK 사용 흔적을 찾아 활성 서비스 목록을 도출한다. 원본 표 6 행 21 패턴을 줄이지 않고 옮겼다 — Firebase 의 import 문도 원문 그대로다.

서비스 grep 패턴
Firebase firebase_core, firebase_messaging, FirebaseApp.configure,
import { initializeApp } from "firebase/app"
GCP google-cloud-, from google.cloud, GOOGLE_APPLICATION_CREDENTIALS
AWS boto3, aws-sdk, @aws-sdk/, import software.amazon.awssdk
Stripe stripe.api_key, import Stripe from "stripe", stripe.Client(
Sentry Sentry.init, sentry-sdk, sentry_dsn
OAuth oauth2, passport-, next-auth, Sign in with
grep 대상에서 빼는 파일: .env* 와 **/*.p8 은 Grep 으로 훑지 않고 Glob 으로 있는지만 본다. 값이나 키가 든 파일이라 Grep 으로 훑으면 내용이 그대로 출력된다. 키 이름이 필요하면 .env.example 같은 예시 파일을 따로 연다. 위 패턴 가운데 GOOGLE_APPLICATION_CREDENTIALS 처럼 환경변수 이름인 것도 코드에서 찾는다 — 값이 든 파일을 열어서 찾지 않는다.

근거: SKILL.md Gotcha 8 1 번 — 패턴으로 탐색한다

05 · 인프라 / 환경 파일

코드 grep 과 별도로 인프라·환경 파일도 본다. 원본은 네 가지를 든다. 첫 줄만 이번 판에서 바뀌었다.

파일 보는 것 여는가
.env.example 류 환경변수 키 이름에서 외부 서비스 흔적
(FIREBASE_*, AWS_*, STRIPE_*)		 연다
값이 든 .env 파일
(.env.local · .env.production 등)		 있는지만 본다 열지 않는다
docker-compose*.yml, Dockerfile 컨테이너 의존성 연다
terraform/*.tf IaC 리소스 연다
k8s/*.yaml, helm/ Kubernetes 매니페스트 연다

원본의 첫 줄 하나를 「연다」 와 「열지 않는다」 두 행으로 나눠 보였다. 원본 문장은 06 절에 그대로 있다.

06 · 값이 든 .env 는 열지 않는다

옛 판은 .env* 를 통째로 훑으라고 적었다. 그 글자대로 하면 .env.local 을 열게 되고, 열린 순간 비밀 값이 대화 기록에 남는다. 이번 판은 키 이름을 얻는 자리와 있는지만 볼 자리를 나눴다.

project-detection.md — 인프라/환경 파일 첫 줄
−.env* — 환경변수에서 외부 서비스 키 흔적 (FIREBASE_*, AWS_*, STRIPE_*)
+.env.example 류 — 환경변수 키 이름에서 외부 서비스 흔적 (FIREBASE_*, AWS_*, STRIPE_*). 값이 든 .env 파일(.env.local · .env.production 등)은 있는지만 보고 열지 않는다 (SKILL.md Gotcha 8)
하지 않는다
  • 설정 방법을 묻는 질문에 .env 를 바로 연다 — 비밀 값이 대화 기록에 남는다
  • .env* 를 Grep 으로 훑는다 — 매칭된 줄이 값째로 출력된다
  • 프로젝트가 이미 다른 이름의 키를 쓰는데(.env.example · 코드에 있다) 확인 없이 관례적인 이름(FIREBASE_SERVER_KEY 등)으로 안내한다
이렇게 한다
  • 값이 든 .env 는 Glob 으로 있는지만 본다
  • 키 이름은 .env.example 같은 예시 파일이나 그 키를 읽는 코드에서 얻는다
  • 둘 다 없으면 사용자에게 키 이름을 묻는다
  • 사용자가 그 값을 보여 달라고 직접 요청한 경우만 예외다
