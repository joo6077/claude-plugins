Search Strategy — 최신 정보 수집 우선순위

WebFetch → Context7 → Codex → WebSearch 순서로 1차 출처를 수집한다. 학습 데이터 추측은 금지. 각 도구는 역할이 다르며, 순서를 지키지 않으면 deprecated 정보가 가이드에 포함될 위험이 있다.

4단계 우선순위 래더

각 도구는 잘하는 영역이 다르다. WebFetch는 콘솔 UI 경로에 가장 빠르고, Context7은 SDK API 시그니처에 가장 정확하다. 역할을 혼동하면 불필요하게 Codex에 위임하거나, 단순 fetch로 해결될 것을 복잡하게 만든다.

1
WebFetch
콘솔 UI / 공식 help 페이지 — 가장 빠르고 정확
콘솔 클릭 경로, 메뉴 라벨, + 버튼 옵션 리스트는 매번 직접 fetch한다. 학습 데이터로 답하면 사용자가 화면에서 버튼을 못 찾는다.

주요 fetch 대상:
developer.apple.com/help/account/ firebase.google.com/docs/ cloud.google.com/docs/ docs.aws.amazon.com/ stripe.com/docs/ docs.sentry.io/

WebFetch 프롬프트 예시:
"Apple Developer Portal에서 새 App ID를 등록하는 정확한 클릭 경로를 step-by-step으로 추출해줘. 좌측 메뉴 위치, + 버튼 이후 옵션, Capabilities 체크리스트 위치, 최종 등록 버튼 라벨까지. 한국어로 정리."
2
Context7
SDK API 문서 — 메서드 시그니처, 초기화 코드, 마이그레이션 가이드
라이브러리/SDK의 메서드 시그니처, 초기화 패턴, 버전 마이그레이션 가이드는 Context7이 가장 정확하다. 학습 데이터의 API 정보는 deprecated됐을 가능성이 높다.

Context7 흐름:
1. mcp__context7__resolve-library-id — 라이브러리 ID 검색
2. mcp__context7__query-docs — 구체 API 질의

대상 라이브러리: firebase-ios-sdk, FlutterFire (firebase_messaging, firebase_core), AWS SDK, Stripe SDK, Sentry SDK 등.
3
Codex 위임
정책 검증 / 교차검증 / 깊은 분석 — codex-rescue 에이전트, MODE=research
단순 페이지 fetch(WebFetch가 더 빠름)나 API 시그니처(Context7이 더 정확)에는 쓰지 않는다. Codex는 여러 출처를 종합해 판단해야 할 때 투입한다.

Codex 투입 기준:
  • + 정책 사실 검증 (예: Apple Bundle ID 변경 정책, FCM 전송 한도)
  • + 여러 출처 교차검증 필요
  • + WebFetch 한 페이지로 답이 안 나올 때
  • × 단순 페이지 fetch 목적 → WebFetch 사용
  • × API 시그니처 목적 → Context7 사용

~/.claude/codex-prompt-template.md 템플릿 필수. --write 없이 research mode.
4
WebSearch — fallback
위 세 가지로 안 잡힐 때만. 반드시 현재 연도 포함
위 세 가지 도구로 해결되지 않을 때만 사용한다. 검색어에 현재 연도 필수. 연도 없이 검색하면 deprecated 결과가 상위 노출된다.

검색어 패턴:
"2026 Firebase FCM iOS setup"
"2026 Apple APNs authentication key"
연도를 앞에 붙이면 검색엔진이 날짜 기준으로 필터링한다.
도구별 역할 비교 매트릭스

어떤 정보를 어느 도구로 수집할지 명확히 구분한다. 역할 혼동이 토큰 낭비와 품질 저하의 주원인이다.

1순위 도구가 실패하거나 정보가 없을 때만 다음 순위 도구로 내려간다

Deprecated 감지 규칙

수집한 정보가 최신인지 검증하는 규칙. 하나라도 해당하면 가이드에 ❌/✅ 박스를 삽입하고 현재 권장 방법을 병기한다. 조용한 생략은 사용자가 deprecated 방법을 따르게 만든다.

자동 감지 신호

4가지 Deprecated 시그널

  • 날짜 문서의 마지막 업데이트가 2년 이상 지남 — 자동 ⚠️ 경고 박스
  • 키워드 본문에 deprecated, legacy, old method, will be removed, removed in 발견
  • 버전 API/SDK 메이저 버전 변경 안내 포함 — 마이그레이션 가이드 별도 링크
  • 대체 "use X instead", "prefer X" 같은 대체 권장 표현 발견
↗ Firebase — APNs 인증서 deprecated 안내
처리 방법

감지 후 가이드에 삽입

감지 즉시 가이드 해당 Step 상단에 박스 삽입:

> **❌ Deprecated:** <옛 방법>
> <비추천 이유>
>
> **✅ 현재 권장:** <새 방법>
> <장점>

실제 사용 예:

> **❌ Deprecated:** APNs Certificate (.p12)
> 매년 갱신, 환경별 분리, 2020년 이후 비권장
>
> **✅ 현재 권장:** APNs Key (.p8)
> 갱신 불필요, dev/prod 모두 커버
↗ Apple — Authentication Key (.p8)
1차 출처 도메인 화이트리스트

가이드에 포함되는 모든 외부 링크는 아래 도메인 목록에 속해야 한다. 비공식 블로그, Medium, Qiita, StackOverflow는 정보 참조는 가능하지만 가이드 링크로 직접 포함하지 않는다.

서비스 허용 도메인 비허용 예시

가이드 Phase 4 검증 단계에서 모든 링크 도메인을 이 목록 기준으로 재확인한다

안티패턴 — 잘못된 정보 수집

정보 수집 단계에서 발생하는 실수 패턴과 올바른 처리를 대비한다. 이 실수들은 실제로 deprecated 정보가 가이드에 포함된 사례에서 수집되었다.

잘못된 수집 — deprecated 위험
  • 학습 데이터로 콘솔 클릭 경로 답변 — "Firebase Console에서 설정 페이지로 가세요"
  • 연도 없이 WebSearch — "Firebase FCM iOS setup"으로 검색 → 2021년 결과 상위
  • SDK 메서드를 Context7 없이 학습 데이터로 작성 — deprecated API 사용
  • Codex를 단순 페이지 fetch에 사용 — WebFetch보다 느리고 비쌈
  • Stack Overflow 답변을 1차 출처로 가이드에 링크 — 오래된 정보 가능성
  • 검색 결과 첫 페이지를 교차검증 없이 신뢰
올바른 수집 — 최신 정보 보장
  • WebFetch로 developer.apple.com/help/account/ 직접 fetch → 현재 UI 경로 추출
  • 연도 포함 검색: "2026 Firebase FCM iOS setup"
  • Context7 resolve-library-id → query-docs로 현재 API 시그니처 조회
  • 정책 검증에만 Codex 투입 — 단순 fetch는 WebFetch
  • 공식 도메인 (firebase.google.com, developer.apple.com) 링크만 가이드에 포함
  • 여러 페이지 교차검증 후 최신 정보 확정
검색 결과 검증 체크리스트

Phase 2에서 수집한 정보를 가이드에 포함하기 전에 아래 체크리스트를 실행한다. 한 페이지의 정보를 절대적으로 신뢰하지 않고 교차검증한다.

  • ✓
    공식 도메인 확인 — 수집한 URL이 developer.apple.com, firebase.google.com, cloud.google.com, docs.aws.amazon.com 등 화이트리스트 도메인에 속하는가
  • ✓
    문서 날짜 추출 — 페이지의 마지막 업데이트 날짜를 확인. 없으면 "날짜 미확인 — 교차검증 필요" 메모. 2년+ 이면 ⚠️ 경고 박스 삽입
  • ✓
    Deprecated 키워드 grep — 본문에 "deprecated", "legacy", "old method", "will be removed", "removed in", "use X instead" 중 하나라도 있는가
  • ✓
    교차검증 — 최소 2개 이상의 공식 페이지에서 같은 정보를 확인했는가. 한 페이지만 보고 판단하지 않는다
  • ✓
    버전 매칭 — 수집한 SDK 코드 예시의 버전이 현재 프로젝트의 버전과 호환되는가. 메이저 버전 차이가 있으면 마이그레이션 가이드 별도 확인
  • ✓
    스택 매칭 — 수집한 코드 예시가 확정된 프로젝트 스택(Flutter / 네이티브 iOS / Node 등)과 일치하는가. 다른 스택 코드를 혼용하지 않는다
  • ✓
    WebSearch 사용 시 연도 확인 — WebSearch를 fallback으로 사용한 경우 검색어에 현재 연도가 포함됐는가. 결과의 날짜가 최근 1~2년 이내인가
WebFetch 실패 대응: WebFetch가 페이지 fetch에 실패하거나 접근 차단될 경우 Context7 → Codex → WebSearch 순서로 바로 내려간다. 실패한 도구에서 재시도를 반복하면 토큰 낭비다.
Codex 위임 조건 상세

Codex는 강력하지만 단순 fetch나 API 조회에 투입하면 과잉이다. 아래 조건에 해당할 때만 codex-rescue 에이전트에 위임한다.

위임 O — Codex 투입

적합한 Codex 태스크

  • +Apple Bundle ID 변경 불가 정책이 현재도 유효한지 검증
  • +Firebase 무료 한도가 현재 기준으로 정확한지 교차검증
  • +APNs .p8 vs .p12 정책 비교 — 공식 문서 여러 페이지 종합
  • +FCM 전송 제한 정책의 최신 상태 (변경 이력 포함)
  • +여러 SDK 버전 간 호환성 매트릭스 분석
↗ Firebase FCM — 정책 검증 대상
위임 X — 다른 도구 사용

Codex 과잉 투입 패턴

  • ×"Firebase Console 클릭 경로 알려줘" → WebFetch 사용
  • ×"firebase_messaging 초기화 코드" → Context7 사용
  • ×단순 공식 문서 페이지 fetch → WebFetch 사용
  • ×이미 Context7에서 확인된 API 시그니처 재확인 → 중복 투입
  • ×"Stripe 대시보드 경로" → WebFetch로 stripe.com/docs/ fetch
↗ FlutterFire — Context7 대상 API
