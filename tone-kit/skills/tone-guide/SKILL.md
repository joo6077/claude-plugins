# Tone Guide

구현·리뷰 전에 규칙을 로드하고, 완료 전에 전수 대조하는 게이트.

## Gotchas

1. **"이미 알고 있다"며 Read 를 건너뛰지 마라** — 규칙은 갱신된다. 기억에 있는 버전으로 판정하면 최근 개정분을 놓친다. Step 1 의 Read 는 매번 실행하고, 그 호출과 출력을 근거로 제시한다. 기존에 읽은 파일을 "호출했다"로 둔갑시키지 마라.
2. **완료 선언 전에 대조하라. 사용자가 첫 피드백 루프가 되면 안 된다** — 편집을 끝내고 보고한 뒤 사용자가 놓친 규칙을 지적하는 왕복이 반복된다. Step 5 를 건너뛰면 이 왕복이 그대로 발생한다.
3. **보존 대상을 먼저 표시한 다음 지워라** — 안티패턴 카탈로그의 H 는 위반이 아니라 **보존 카테고리** 다. 삭제 후보부터 고르면 함정·제약·실패 모드를 설명하는 주석이 같이 사라진다. 순서를 뒤집지 마라.
4. **주석만 지우고 이름을 그대로 두지 마라** — 이름 번역 주석이 붙어 있었다는 것은 이름이 약했다는 증거다. 주석만 지우면 정보가 사라지고 다음 사람이 같은 주석을 다시 단다.
5. **규칙 강도를 임의로 올리지 마라** — 각 규칙에 `MUST` / `SHOULD` / `관측 컨벤션` 이 붙어 있다. `관측 컨벤션` 을 위반으로 단정해 보고하면 근거 없는 지적이 된다. 강도를 그대로 인용하라.
6. **정규식 일괄 치환으로 정리하지 마라** — 카테고리 패턴이 겹쳐 있어서 한 번에 지우면 계약 문서 주석과 실패 모드 주석까지 매칭된다. 파일 단위로 판정한다.
7. **grep 히트가 곧 위반이 아닌 패턴이 있다** — 어댑터의 대조 목록에 "히트가 위반인지" 판정이 병기돼 있다. 확인 없이 건수를 위반으로 보고하지 마라.
8. **0건을 "통과" 로 읽기 전에 패턴이 살아 있는지 확인하라** — 준수 상태에서 0건이 정상인 패턴이 있고, 패턴이 깨져서 0건인 경우도 있다. 둘은 구분되지 않는다.
9. **대량 편집으로 번지지 마라** — 요청 범위 밖 파일에서 같은 위반을 발견해도 그 자리에서 고치지 않는다. 보고하고 사용자 판단을 받는다. 파일 단위 정리 캠페인은 `tone-campaign` 이 담당한다.
10. **프로젝트 판정을 재논쟁하지 마라** — 규칙 충돌에 대한 프로젝트 결정이 오버레이 파일에 있으면 그것이 이긴다. 세션마다 다시 정하면 코드가 세션별로 갈린다.

## Process

### Step 1. 프로젝트 파라미터 확보

`../../references/project-detection.md` 를 읽고 그 절차를 따른다.

- 오버레이 파일이 있으면 읽는다. 결정론적 값은 코드가 바뀌었을 수 있으므로 재확인한다.
- 없으면 감지를 수행하고, 확인이 필요한 값은 후보와 근거를 표로 제시해 **한 번에** 확인받는다. 키마다 따로 묻지 않는다.
- 감지 실패한 키는 비워 두고 진행한다. 추측값을 넣지 마라.

이 단계에서 정해지는 것: 어댑터 · 주석 언어 · 스코프 경로 · 네이밍 파라미터 · 명령.

### Step 2. 코어 규칙 로드 (건너뛰기 금지)

아래 네 파일을 **실제로 Read** 한다.

- [core-comment.md](../../references/core-comment.md) — 주석 경제성 (`C-01`~)
- [core-naming.md](../../references/core-naming.md) — 역할 네이밍 (`N-01`~)
- [core-structure.md](../../references/core-structure.md) — 구조·추출 (`S-01`~)
- [core-antipatterns.md](../../references/core-antipatterns.md) — 안티패턴 카탈로그 (A~J)

로드했다는 근거로 각 파일에서 이번 작업에 걸리는 규칙 ID 를 인용한다. 파일명만 나열하는 것은 근거가 아니다.

### Step 3. 조건부 로드

Step 1 결과에 따라 추가로 읽는다.

| 조건 | 로드 |
|---|---|
| 주석 언어가 한국어 | `../../references/locale-korean.md` |
| 어댑터가 dart-flutter | `../../references/adapter-dart-flutter.md` |
| 어댑터 없음 | 스택 고유 게이트 비활성. 코어만으로 진행하고 그 사실을 보고에 명시 |

어댑터 슬롯 구조가 궁금하면 `../../references/adapter-contract.md` 를 본다.

### Step 4. 구현 또는 리뷰

로드한 규칙을 적용해 작업한다. 판정이 갈리는 지점에서는 규칙 ID 와 강도를 근거로 제시한다.

리뷰 모드라면 발견을 `../../templates/briefing-table.md` 의 위반 제안 표 형식으로 낸다. 편집 전에 승인을 받는다.

### Step 5. 완료 전 규칙 전수 대조 (건너뛰기 금지)

**완료를 선언하기 전에** 로드한 규칙 목록을 다시 읽고 각 규칙에 대한 위반 여부를 파일·라인 근거와 함께 보고한다.

1. 코어 규칙 ID 를 순서대로 훑으며 이번 변경분에 위반이 있는지 판정한다.
2. 어댑터가 있으면 그 대조 목록을 실행한다. 각 패턴의 "히트가 위반인지" 판정을 함께 확인한다.
3. 결과를 표로 낸다.

```text
| 패턴 / 규칙 | 건수 | 판정 |
|---|---|---|
| C-04 | 0 | 통과 |
| N-07 | 2 | 위반 — path/to/file:12, path/to/file:31 |
```

4. 위반이 있으면 고치고 다시 대조한다. 대조 없이 "규칙을 지켰다" 고 서술하는 것은 대조가 아니다.

### Step 6. meta-audit

"놓친 규칙이 있는가" 를 한 번 더 자문한다. 특히 확인한다.

- 로드했지만 한 번도 판정하지 않은 규칙 ID 가 있는가
- 보존 대상(H)을 삭제하지 않았는가
- 이름을 고쳐야 할 자리에서 주석만 지우지 않았는가
- 강도가 `관측 컨벤션` 인 항목을 위반으로 단정하지 않았는가
- 요청 범위 밖 파일을 건드리지 않았는가
