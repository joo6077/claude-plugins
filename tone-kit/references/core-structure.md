# 코드 구조 — 관심사 분리 · 추출 임계 · 파일 조직

스택 무관 코어. 구조를 쪼갤지 둘지 판정하기 직전에 Read 한다. 산문이 아니라 **판정 절차**로 읽어라.

## 상위 원칙 — 판정식은 관심사, 줄 수는 신호

```text
[판정식]  관심사(책임)가 실제로 다른가?   → 다르면 분리 / 같으면 유지
   ↑
[신호]    줄 수 · 헬퍼 개수 · 파일 개수    → 판정을 "지금 하라"고 부르는 알람일 뿐
```

줄 수 임계치는 분리 여부를 결정하지 않는다. **"이미 한참 늦었다"를 알리는 하한 알람**이다. 두 방향 모두 성립한다.

- 임계치 **미만**이어도 관심사가 다르면 분리한다.
- 임계치를 **넘겨도** 관심사가 하나면 쪼개지 않는다.

임계치를 판정식으로 쓰면 두 가지가 동시에 깨진다 — 관심사가 하나인 긴 코드를 억지로 쪼개고, 관심사가 섞인 짧은 코드는 통과시킨다. 이 문서의 나머지 규칙은 전부 이 원칙의 적용 메커니즘이며, 각 규칙의 수치는 판정 근거가 아니라 진입 트리거다.

## 추출 판정 절차

대상 코드 블록 하나마다 위에서부터 순서대로 통과시킨다. 먼저 걸리는 항에서 멈춘다.

```text
1. 발생하지 않는 조합을 방어하고 있는가?
   YES → 제거한다. 추출하지 않는다.          (S-07)
   NO  → 2

2. 이 블록의 책임이 주변과 다른가?
   NO  → 유지한다. 길기만 한 것은 분리 사유가 아니다.   (S-01 · S-02)
   YES → 3

3. 본문보다 의미를 더하는 이름을 붙일 수 있는가?
   NO  → 유지하거나 인라인한다. 이름이 못 붙으면 관심사 경계를 잘못 그은 것이다.  (S-03)
   YES → 4

4. 추출 결과가 자기 책임을 갖는가? (전달만 하지 않는가)
   NO  → pass-through 래퍼다. 만들지 않는다.   (S-04)
   YES → 5

5. 추출한다. 별도 파일에 둔다.               (S-08 · S-09)
   → 분리 형태(함수 · 클래스 · 컴포넌트) 선택은 adapter-dart-flutter.md
```

**2번이 실질 판정이다.** 1·3·4번은 과분할 차단 게이트이고 5번은 배치 규칙이다. 판정 근거는 몇 번 항에서 멈췄는지로 쓴다 — "500줄이 넘어서"는 근거가 아니고 "표시와 상호작용이 한 단위에 있어서"가 근거다. 관심사 축은 **표시 / 콘텐츠 / 상호작용 / 비즈니스 로직 / 데이터 접근**이며, 한 단위에 둘 이상이 섞이면 2번은 YES 다.

## 과분할 방지

"관심사 분리 의무"와 "과분할 금지"는 충돌하지 않는다. **적용 지점이 다르다** — 과분할 금지는 위 절차 2번이 NO 로 떨어진 코드에만 적용된다. 관심사가 다른 단위의 추출 의무를 취소하지 않는다.

| 상황 | 조치 | 이유 |
|---|---|---|
| 이름이 본문과 같은 수준의 정보만 준다 | 인라인 | 가독성이 오르지 않고 읽기 비용이 호출부에서 정의부로 이동만 한다 |
| 받은 값을 그대로 하위에 넘기기만 한다 | 인라인 | 책임 없는 간접층. 형제 유무와 무관하다 |
| 실사용처가 1~2곳인데 "나중에 쓸 것 같아서" 뺐다 | 인라인 | 타입 수만 는다. 3곳부터 검토한다 |
| 헬퍼가 다른 헬퍼를 부른다 | 인라인 또는 독립 단위로 승격 | 주 흐름을 읽는 데 왕복 이동이 강제된다 |
| 발생하지 않는 null 조합을 헬퍼로 감쌌다 | 분기째 제거 | 가상 복잡도를 구조화해 영구화한 것이다 |

**헬퍼 체인 허용 깊이는 0단이다.** `main → helperA → helperB` 가 보이면 중간 단계를 개별 판정한다 — 대개 S-03(이름이 의미를 더하지 않음)으로 떨어진다. 그리고 **조합 제약은 흐름이 아니라 경계에서 표현한다** — 내부 호출자 제약은 생성자·팩토리의 단언으로, 외부 입력은 명시적 검증으로 막는다. 유효하지 않은 조합을 본문 분기로 방어하면 그 분기는 영원히 실행되지 않으면서 읽는 예산만 먹는다.

## 파일 조직

```text
<컴포넌트 루트>/
├── <component>_<part_a>.<ext>       # 하위 단위 — 인라인 클래스로 두지 않고 파일로 뺀다
├── <component>_<part_b>.<ext>
└── <sub_group>/                     # 관련 파일 3쌍 이상 → 전용 서브폴더
    └── <component>_<detail>.<ext>

test/<컴포넌트 루트와 동일 경로>/     # 테스트는 소스 구조를 미러링한다
└── <sub_group>/
```

- **S-09 는 관측 컨벤션이다.** 공개 1차 출처가 지지하는 범위는 "다른 단위로 나눠라"까지이고, "별도 *파일*"은 지지하지 않는다. 파일 단위 규칙을 쓸 때 근거는 성능이 아니라 **탐색성**이라고 밝혀라 — 컴포넌트 파일이 길어지면 로직 위치를 못 찾는다.
- **서브폴더 트리거는 3쌍(6파일)이다.** 하위 단위 추출로 파일이 형제들 사이에 쏟아져 시각적으로 뭉치기 시작하는 지점이다. 폴더명은 컴포넌트·도메인명을 쓰고 공백·특수문자를 넣지 않는다.
- **폴더를 옮겨도 프로젝트 접두사(`{widget_prefix}`)는 유지한다.** 화면 한정 하위 단위라고 접두사를 화면 이름으로 갈아끼우지 마라 — 전역 컨벤션이 폴더 위치보다 우선한다. 공용 단위와 컴포넌트 종속 단위의 디렉토리도 분리한다. 종속 단위를 공용 디렉토리에 두면 재사용 후보와 1회성이 섞여 다음 추출 판정이 불가능해진다.

## 구현 통일성

같은 카테고리(같은 디렉토리, 같은 역할)의 코드는 같은 패턴을 쓴다. 파일 A에서 고른 방식을 파일 B에서도 동일하게 적용한다.

| 통일 대상 | 판정 질문 |
|---|---|
| 파라미터·Props 구조 | 같은 역할의 인자를 한쪽은 묶고 한쪽은 펼치지 않았는가 |
| 값 처리 방식 | 같은 성격의 값 일부만 추출하고 나머지를 인라인으로 두지 않았는가 |
| 트리·조립 구조 | 같은 카테고리인데 조립 순서·중첩 깊이가 제각각이지 않은가 |
| 하위 단위 분리 방식 | 한쪽은 파일로 빼고 한쪽은 인라인으로 두지 않았는가 |

**배치 작업 순서 (S-13).** 여러 파일을 같은 규칙으로 정리할 때는 파일마다 감으로 판단하지 않는다.

```text
1. 기준 파일 1개를 먼저 끝낸다
2. 거기서 확정된 패턴을 명시적으로 적어 사용자에게 보고한다
3. 승인된 패턴을 나머지 파일에 일괄 적용한다
```

2번을 건너뛰면 배치 중반에 패턴이 바뀌어 앞선 파일을 다시 손대게 된다. 패턴을 못 정하겠으면 배치를 시작하지 마라.

**이동은 복사가 아니다 (S-14).** 코드를 다른 파일·다른 계층으로 옮길 때 원문 그대로 붙여넣지 않는다. 이동 대상 안의 하드코딩 값, 수동 여백 처리, 타입 비교로 대체 가능한 분기 같은 개선 기회를 같이 정리한다. 이동 커밋은 그 코드를 마지막으로 정독하는 기회다.

## 수치 트리거

전부 **트리거**다. 판정식이 아니다 — 걸렸으면 [추출 판정 절차](#추출-판정-절차)를 돌리라는 뜻이지, 걸렸으니 쪼개라는 뜻이 아니다.

| 항목 | 값 | 성격 |
|---|---|---|
| 인라인 유지 상한 | 100줄 이하 + 주 경로 1개 | 관측 컨벤션 |
| 분할 하한 트리거 | 파일 500줄 초과 또는 단위 반환 헬퍼 8개 이상 | 관측 컨벤션 |
| 헬퍼 체인 허용 깊이 | 0단 (헬퍼 → 헬퍼 호출 금지) | 관측 컨벤션 |
| 추출 검토 반복 임계 | 같은 패턴 3곳 이상 | 관측 컨벤션 |
| 서브폴더 그룹화 트리거 | 관련 파일 3쌍 이상 | 관측 컨벤션 |
| 공식 길이 임계값 | 없음 | 공개 1차 출처에 존재하지 않음 |

## 안티패턴

| 안티패턴 | 문제 |
|---|---|
| 줄 수 임계치를 분리 여부의 판정식으로 사용 | 관심사가 하나인 긴 코드를 쪼개고 관심사가 섞인 짧은 코드는 방치한다 |
| 이름이 본문과 같은 수준인 헬퍼 추출 | 읽기 비용이 정의부로 이동만 하고 가독성은 그대로다 |
| 헬퍼가 헬퍼를 부르는 다단 체인 | 주 흐름을 읽는 데 왕복 이동이 강제된다 |
| pass-through 래퍼 레이어 추가 | 자기 책임 없는 간접층이 하나 는다 |
| "재사용 가능성"만으로 1회성 로직 승격 | 실사용처가 1곳이면 타입 수만 는다 |
| 발생하지 않는 조합을 헬퍼로 감싸 은닉 | 제거 대상을 추출 대상으로 오인해 가상 복잡도를 영구화한다 |
| 하위 단위 추출 후 같은 폴더에 평면 나열 | 형제 컴포넌트 파일과 뒤섞여 소유 관계가 사라진다 |
| 소스 구조와 다른 테스트 경로 | 대응 테스트를 찾지 못해 수정 시 테스트가 방치된다 |
| 파일마다 감으로 패턴 결정 · 이동 시 원문 복사 | 같은 카테고리 안에서 패턴이 갈라지고 기존 결함이 새 위치에서 살아남는다 |

## 강도 표기 규약

- **SHOULD** — 공개 1차 출처가 방향은 지지하나 기계적 판정식은 주지 않는다.
- **관측 컨벤션** — 공개 1차 출처 없음. 관측 프로젝트 실측에서 승격된 규칙.

**두 강도를 임의로 올리지 마라.** S-08("큰 단위를 분리하라")이 SHOULD 인 이유는 공식 문서에 길이 임계값이 없기 때문이고, S-09("모든 하위 단위를 별도 파일로")가 관측 컨벤션인 이유는 공개 근거가 "다른 단위"까지만 지지하기 때문이다. 프로젝트 규칙으로 MUST 승격하는 것은 가능하지만, 그때는 **승격 사유(측정 결과 또는 팀 합의 일자)를 규칙 옆에 병기**해야 한다. 사유 없는 MUST 는 킷의 창작이고, 나중에 아무도 그 규칙이 왜 있는지 재구성하지 못한다.
