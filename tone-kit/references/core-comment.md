# 주석 경제성 — 코어 판정 규칙

주석을 언제 남기고 언제 지우는가. 스택·언어 무관 코어. 스킬이 런타임에 Read 해서 판정에 쓴다.
전제: 주석은 코드와 함께 썩는 자산이다. **남길 이유를 한 줄로 대지 못하면 지운다.**

## 1. 규칙표

강도 3단계: `MUST` 위반 시 REJECT · `SHOULD` 위반 시 근거 요구 · `관측 컨벤션` 프로젝트가 완화 가능.

| ID | 규칙 | 강도 | 축 |
|---|---|---|---|
| C-01 | what 이 아니라 why 만 남긴다. 동작 설명은 코드가 이미 한다 | SHOULD | 중복제거 |
| C-02 | 타입·이름·시그니처가 말하는 것을 문장으로 반복하지 않는다 | SHOULD | 중복제거 |
| C-03 | 주석을 달아야 이해되는 이름은 주석 대신 이름을 고친다 | SHOULD | 이름이동 |
| C-04 | 템플릿 마커(`// 상태`, `// 구현부`)와 구분선 블록은 0개 | 관측 컨벤션 | 구조 |
| C-05 | 보존 대상은 §2 의 세 범주뿐. 사전 카테고리를 미리 늘리지 않는다 | SHOULD | 보존 |
| C-06 | 공개 API 는 doc 주석으로 계약을 쓴다. 구현 이유는 라인 주석 | MUST | 계약 |
| C-07 | 주석으로 복잡도를 덮지 않는다. 해설 3줄 초과는 구조 문제 | SHOULD | 구조 |
| C-08 | 같은 디렉토리·같은 역할 파일은 같은 주석 밀도를 갖는다 | 관측 컨벤션 | 일관성 |
| C-09 | 섹션 라벨은 항목 2개 이상을 묶을 때만 유효 | 관측 컨벤션 | 라벨 |
| C-10 | 디자인 툴 참조(노드 ID·변수 경로·CSS 원문·프레임명) 제거 | MUST | 툴참조 |
| C-11 | pair 관계는 주석이 아니라 이름 접미사로 표현 (`Start`/`End`) | SHOULD | 이름이동 |
| C-12 | 계산 근거 주석(`// 440 - 40`) 금지. 값만 남기거나 코드로 표현 | SHOULD | 중복제거 |
| C-13 | 자화자찬 헤더("AI 기반", "자동 생성") 금지 | MUST | 헤더 |
| C-14 | 파일 헤더는 고정 필드만. 구현 메모를 섞지 않는다 | 관측 컨벤션 | 헤더 |
| C-15 | 주석 종결형은 파편형·단문. 서술문으로 늘이지 않는다 | 관측 컨벤션 | 문체 |
| C-16 | 값에서 인간이 못 읽는 메타는 인라인 주석 허용 (alpha `// 10%` 등) | 관측 컨벤션 | 보존 |
| C-17 | 로컬 구현 세부를 doc 주석으로 감싸지 않는다 | 관측 컨벤션 | 계약 |

실측 기준선: 안티패턴 57파일 / 약 275건 중 **보존 가치가 있던 것은 약 11%(약 30건)**. 나머지는 코드를 다시 읽어 준 문장이었다.

## 2. 삭제 vs 보존 판정 절차

주석 1건마다 아래를 순서대로 돌린다. 먼저 걸리는 곳에서 멈춘다.

| 단계 | 질문 | YES | NO |
|---|---|---|---|
| S1 | 보존 3범주(아래 표) 중 하나에 해당하는가 | **보존** | S2 |
| S2 | 이름·타입·시그니처가 이미 같은 말을 하는가 | **삭제** | S3 |
| S3 | 정보는 필요한데 위치가 틀린 것인가 | **이동** (§S3 목적지) | S4 |
| S4 | 해설이 3줄을 넘는가 | **구조 수정** 후 재판정 | **삭제** |

### 보존 3범주 (이것만 보존한다)

| 범주 | 판정 질문 | 보존 형태 |
|---|---|---|
| 프레임워크 함정 | 이 코드를 지우거나 순서를 바꾸면, 문서를 읽은 사람도 예측 못 할 동작이 나오는가 | 비직관적 기본 동작 1줄 |
| 제약·trade-off | 외부 API·스펙이 강제해서 다른 선택지가 없었는가 (변경 불가 옵션, 내부 하드코딩) | 버린 대안 + 이유 1줄 |
| 실패 모드 | 이 구조를 되돌리면 재현된 버그가 되살아나는가 | 되살아나는 증상 1줄 |

세 범주 어디에도 안 걸리는데 지우기 아까우면, 그건 보존 대상이 아니라 **이름이 약하다는 신호**다 (C-03).

### S3 이동 목적지 (세 곳뿐)

- 이름으로 — 번역 주석이 붙어 있었다는 것 자체가 이름 결함의 증거다
- 함수·파일 경계로 — 자명한 구조 라벨(`// 제목`, `// 좌측 영역`)은 경계가 흡수한다
- 공개 API 계약 doc 으로 — 오용을 유발하는 규칙(옵션 A 를 넘기면 옵션 B 가 무시됨)

### 이 절차를 건너뛰면 생기는 사고

- **전면 삭제 과교정** — 안티패턴 목록만 보고 일괄 삭제하면 보존 대상 약 11% 가 같이 날아간다. S1 을 먼저 돌려라.
- **정규식 일괄 치환** — 유형별 패턴이 겹쳐 있어 계약 doc 과 실패 모드 주석까지 매칭된다. §6 grep 은 **후보 표시용**이지 삭제 명령이 아니다.
- **주석만 지우고 이름은 그대로** — 정보가 순삭되고 다음 사람이 같은 주석을 다시 단다.
- **한 파일만 정리하고 종료** — 형제 파일이 옛 정책으로 남으면 일관성 결함이 새 기준이 된다 (C-08). 카테고리 전체를 범위로 잡거나 착수하지 마라.

## 3. 디자인 툴 참조 제거

강도 `MUST` (C-10). 코드는 디자인 소스의 참조가 아니라 구현물이다. 의미로 읽혀야 한다.

| 형태 | 예 | 조치 |
|---|---|---|
| 노드 ID | `(14644:26672)`, `(12159:8715)` | 삭제 |
| 변수 경로 | `Color/Display Field/display-label-default` | 삭제 후 역할명으로 |
| 파생 표시 | `(bg-card 파생)`, `(디자인 변수)` | 삭제 |
| CSS 원문 | `from-[#111] to-[#181818]`, `linear-gradient(...)` | 삭제 |
| 프레임·레이어명 | `Button/Find`, `Vector 19` | 삭제 |

```text
Before: // 라이트 버튼 그라데이션 보더 하단 (노드 14644:26672 Button/Find)
        // 상단은 {token_class}.white, 하단이 이 값
After:  // 라이트 버튼 베벨 하단, white 와 쌍
최종:    (주석 삭제 — 토큰명이 lightBevelBottom / lightBevelTop 이면 주석 불필요, C-11)
```

**예외 1건**: 파일 헤더의 `참고` 필드에 넣는 **URL 형태**는 허용한다 (조회 목적). 인라인 노드 ID 는 헤더에서도 금지.

## 4. 섹션 라벨 경제성

- 섹션 라벨은 **항목 2개 이상**을 묶을 때만 유효하다. 항목 1개짜리 라벨은 이름과 1:1 이라 한쪽이 잉여다 — 라벨을 지우고 이름에 흡수시킨다.
- 라벨과 바로 아래 항목명이 같은 의미면 한쪽을 지운다.
- 토큰 파일의 섹션 헤더는 **축 단위만** 허용(너비 / 높이 / 반지름). 위젯별·용도별 구분은 금지 — 쓰임새는 호출처에서 읽힌다.

```text
Before: // 다크 배경 라벨
        // 다크 카드 보조 텍스트
        static const displayLabelDefault = ...;
After:  static const darkCardSubText = ...;
```

## 5. 파일 헤더

여기서는 판정에 필요한 것만 둔다. 필드 구성·구분선·정렬·언어 의존 라벨 상세는 [`../templates/file-header.md`](../templates/file-header.md) 가 소유한다.

- 고정 필드만 — 파일명 / 설명 한 줄 / 작성자 / 참고 / 수정이력.
- 금지: 구현 메모, 계산 근거, 자화자찬 문구(C-13), 인라인 노드 ID·변수 경로(C-10).
- 클래스 내부에 상수로 정의되는 값(화면 식별자 등)은 헤더에 중복 기재하지 않는다.
- 작성자는 기존 파일에서 복사하지 말고 현재 `git config user.name` 으로 채운다.
- 코드 생성기 산출물에는 헤더를 붙이지 않는다.

## 6. 완료 전 대조 grep

아래는 실행 검증된 패턴이다 (BSD/GNU grep 공통, `-E` 확장 정규식). `{DIR}` 과 `{EXT}` 를 대상에 맞게 치환한다.
**결과는 삭제 대상이 아니라 판정 후보다.** 각 히트에 §2 절차를 돌린 뒤 처리한다.

| ID | 대상 규칙 | 목표 |
|---|---|---|
| G1 | C-04 구분선 블록 | 0건 |
| G2 | C-10 노드 ID | 0건 |
| G3 | C-10 변수 경로 | 0건 |
| G4 | C-10 CSS 원문 | 0건 |
| G5 | C-13 자화자찬 | 0건 |
| G6 | C-12 계산 근거 | 후보 검토 |
| G7 | C-04 짧은 마커 | 후보 검토 |
| G8 | C-02 트레일링 번역 주석 | 후보 검토 |

```bash
D={DIR}; X='--include=*.{EXT}'
grep -rnE  $X '^[[:space:]]*//[[:space:]]*[-=_*~]{4,}' "$D"                          # G1
grep -rnE  $X '//.*[0-9]{3,}:[0-9]{3,}' "$D"                                        # G2
grep -rnE  $X '//.*[A-Za-z][A-Za-z -]*/[A-Za-z -]+/[A-Za-z-]+' "$D"                 # G3
grep -rnE  $X '//.*(#[0-9a-fA-F]{3,8}|rgba?\(|linear-gradient|from-\[|to-\[)' "$D"  # G4
grep -rniE $X '//.*(자동 생성|자동생성|AI 기반|auto-generated|generated by)' "$D"      # G5
grep -rnE  $X '//.*[0-9]+[^0-9]*[-+*][^0-9]*[0-9]+' "$D"                            # G6
grep -rnE  $X '^[[:space:]]*//[[:space:]]*[^/].{0,9}$' "$D"                         # G7
grep -rnE  $X '[,;)][[:space:]]*//[[:space:]]*.{1,12}$' "$D"                        # G8
```

주의 사항:

- G1 은 `//` 로 시작하는 줄만 잡는다. `///` 파일 헤더 구분선은 의도적으로 제외했다 (§5).
- G4 와 G6 은 히트가 겹칠 수 있다 (CSS hex 안의 숫자). 중복 제거 후 세라.
- G6 의 `//` 는 주석 여는 기호가 아니라 나눗셈일 수도 있다. 언어에 따라 오탐이 난다.
- G7 은 G1 결과를 포함한다. G1 처리 후 다시 돌려라.
- G8 은 C-16 예외(alpha 퍼센트 등)를 함께 잡는다. 예외는 남긴다.
- 한국어 주석은 멀티바이트라 `{0,9}` 같은 길이 한정자가 문자 수와 정확히 일치하지 않는다. 경계값은 눈으로 확인한다.

### G9 — 섹션 라벨 항목 수 (C-09)

라벨 아래 딸린 선언 개수를 세서 `decl=1` 만 남긴다. 실행 검증된 awk 다.

```bash
awk '/^[[:space:]]*\/\/[^\/]/ {if(lbl)printf "%s:%d decl=%d\n",FILENAME,ln,n; lbl=1; ln=NR; n=0; next}
     /^[[:space:]]*$/ {next}
     /^[[:space:]]*[})\];,]*[[:space:]]*$/ {next}
     lbl {n++}
     END{if(lbl)printf "%s:%d decl=%d\n",FILENAME,ln,n}' {FILE} | grep 'decl=1$'
```

### 완료 판정

G1~G5 가 0건이고, G6~G9 후보에 §2 절차를 전부 돌렸으면 통과다.
같은 카테고리의 형제 파일에도 동일 명령을 돌려 밀도가 갈리지 않는지 확인한다 (C-08).
