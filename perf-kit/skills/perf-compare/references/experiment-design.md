# 비교 설계

두 버전의 차이를 재려면 차이 말고 다른 것이 모두 같아야 한다. 이 문서는 그 조건을 정한다.

## 변수는 하나

- A 와 B 사이에 바뀐 것은 하나여야 한다. 앱 빌드 · 서버 코드 · 데이터 · 계정 · 기기 · 네트워크 중 바꾼 것 하나를 빼고 나머지는 `fixed` 에 적는다
- 서버만 바꾸는 비교면 앱은 같은 빌드 하나로 두 서버를 잰다. 앱만 바꾸는 비교면 서버를 고정한다
- 운영 데이터처럼 시간에 따라 바뀌는 데이터를 쓰면 측정 사이에 데이터가 바뀌지 않았는지(건수 같은 값) 처음과 끝에 한 번씩 본다

## 예열

- 첫 실행은 디스크 캐시 · JIT · 커넥션 풀 · DB 버퍼가 비어 있어 느리다. 쪽마다 처음 1 회 이상을 예열로 잰 뒤 뺀다
- 예열 개수를 1 회로 고정하지 말고 첫 측정의 표본을 보고 정한다. 값이 한 방향으로 계속 움직이면 아직 정상 상태가 아니다. 통제된 환경의 작은 결정적 벤치마크도 정상 상태에 이르지 못하는 일이 흔하다 (Barrett et al. — 기계 3 대에서 정상 상태에 꾸준히 이른 조합이 최대 43.5%)
- 스크립트는 예열을 뺀 표본이 4 개 이상이고 모두 같은 방향으로 바뀌면 `주의:` 줄을 남긴다. 이때는 예열을 늘려 다시 잰다
- 예열 표본도 기록에 남기고 `warmup` 에 개수를 적는다 — 지우면 예열이 충분했는지 나중에 볼 수 없다
- 콜드 스타트를 재는 비교라면 예열은 "앱 설치 직후 첫 실행" 을 빼는 것이지 캐시를 데우는 것이 아니다. 매 회 앱 프로세스를 완전히 끈다

## 표본 수

판정은 양측 Mann-Whitney U(순위 검정)로 한다. 표본 분포를 가정하지 않아 작은 표본과 튀는 값에 강하다.
대신 표본 수가 작으면 아무리 갈려도 유의수준 0.05 를 넘지 못한다.

| 쪽마다 표본 | 낼 수 있는 가장 작은 p |
| --- | --- |
| 3 | 0.1 |
| 4 | 0.029 |
| 5 | 0.008 |
| 6 | 0.002 |

- 예열을 뺀 뒤 쪽마다 **5 개 이상**을 기본으로 한다. 편차가 크면(IQR 이 중앙값 차이보다 크면) 10 개로 늘린다
- 전송 bytes · 쿼리 수처럼 매번 같은 값이 나오는 결정값 지표는 쪽마다 2 개면 된다. 두 번이 같은지 확인하는 용도다
- 쪽마다 합이 20 개 이하면 스크립트가 중간 순위로 순열을 전부 센다. 동순위가 있어도 맞는 순열 검정이다 — SciPy 문서도 `exact` 는 동순위를 보정하지 않으니 동순위가 있고 표본이 작으면 순열 검정을 쓰라고 한다. 합이 20 을 넘으면 동순위 보정 정규 근사를 쓴다

## 최소 효과

- 유의해도 차이가 작으면 `차이 미미` 다. 기본 5% 이고 지표마다 `min_effect_pct` 로 바꾼다
- 사용자가 느낄 수 있는 차이를 기준으로 정한다. 시작 시간 50ms 는 1% 일 수 있지만 프레임 시간 1ms 는 6% 다

## 순서

| 순서 | 언제 | 방법 |
| --- | --- | --- |
| 섞어 번갈아 (`randomized`) | 기본값. 플래그 · 주소 · 앱 두 개처럼 바꾸기 싸다 | 한 라운드에 A · B 를 한 번씩 재고, 라운드마다 A · B 순서를 동전 던지기로 정한다 |
| 동시 실행 (`duet`) | 서버 두 벌을 다른 포트로 같이 띄울 수 있다 | A · B 를 한 기계에서 동시에 돌리고 같은 요청을 두 쪽에 함께 보낸다. 간섭이 두 쪽에 같이 걸린다 |
| 같은 순서로 번갈아 (`interleaved`) | 순서를 섞을 수 없다 | A B A B … 로 잰다 |
| 몰아 재기 (`blocked`) | 서버 재배포 · 빌드 교체처럼 바꾸기 비싸다 | A 전부 → B 전부 → A 몇 회를 더 재서 첫 A 와 마지막 A 를 대조 지표처럼 비교한다 |

- 같은 순서로 번갈아 재면 주기적인 간섭(배치 작업 · 백업 · 열 조절)의 주기가 한 회 길이와 맞을 때 한쪽만 계속 맞는다. 라운드마다 순서를 섞으면 이를 막는다 — Abedi · Brecht 의 RMIT(Randomized Multiple Interleaved Trials)다
- 서버 비교처럼 두 버전을 함께 띄울 수 있으면 `duet` 이 가장 정확하다. 공유 기계에서 두 대상을 동시에 돌려 상대 성능을 함께 보면 정확도가 평균 5.03 배(ScalaBench · DaCapo), 37.4 배(SPEC CPU 2017) 좋아졌다. 단 두 버전이 CPU · DB 커넥션을 나눠 쓰므로 절대값이 아니라 A 대비 B 비율만 쓴다
- `interleaved` · `blocked` 면 스크립트가 `주의:` 줄을 남긴다

```bash
# randomized 순서 만들기: 라운드마다 A B 또는 B A
python3 -c 'import random; print("\n".join(" ".join(random.sample("AB", 2)) for _ in range(6)))'
```

### A/A 예비 측정

- 처음 꾸린 측정 환경은 A 를 두 벌로 놓고 같은 절차로 한 번 잰다. A 대 A 가 `차이 없음` 이 아니면 환경이 아직 비교에 쓸 수 없는 상태다
- Abedi · Brecht 도 같은 대상 A · B 를 비교해 방법론이 "통계적으로 같다" 를 내는지로 방법론을 시험했다

## 대조 지표

- 바꾼 변수가 영향을 줄 수 없는 구간을 하나 이상 같이 잰다 (`role: control`)
- 서버만 바꾼 비교: 앱 프로세스 시작 → `main()`, `main()` → 첫 화면 그리기 전
- 앱만 바꾼 비교: 서버의 정적 응답 시간, 같은 API 단독 호출 시간
- 대조 지표가 `개선` · `악화` 면 비교가 무효다 — 맥이나 기기의 다른 작업, 열 · 전원 상태, 네트워크가 흔들렸다
- 대조 지표가 `표본 부족` 이면 무효는 아니지만 흔들림을 못 본 것이라 `주의:` 로 남는다

## 결과 동일성

- 성능만 보고 결과가 달라진 것을 놓치면 안 된다. 같은 입력에 대한 A · B 출력을 비교한다
- API: 응답 JSON 을 키 정렬해 `diff`. 의도해서 뺀 필드가 있으면 그 필드만 빼고 나머지가 같은지 본다
- 화면: 같은 상태에서 두 버전 캡처나 위젯 찾기 결과를 비교한다
- 의도한 차이도 `same: true` 로 두고 `seen` 에 무엇이 다른지 적는다. 의도하지 않은 차이는 `same: false` 다
