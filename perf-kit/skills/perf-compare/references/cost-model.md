# 비용 모델

측정한 효율 지표를 월 비용으로 바꾼다. 계산은 한 가지 식이다.

```text
월 비용 = 지표 평균 × scale × volume × price
```

| 칸 | 뜻 | 예 |
| --- | --- | --- |
| 지표 평균 | 한 번(요청 · 화면 · 실행)당 측정값. 스크립트가 예열을 뺀 평균을 넣는다 | 5,309,776 bytes |
| `scale` | 지표 단위를 단가 단위로 바꾸는 수 | bytes → GB 면 `1e-9` |
| `volume` | 한 달에 그 일이 일어나는 횟수 | 앱 시작 3,000회/일 × 30 = 90,000 |
| `price` | 단가 단위 하나의 값 | 0.09 USD/GB |

A · B 에 같은 `volume` · `price` 를 쓴다. 바뀌는 것은 지표 평균뿐이다.

중앙값이 아니라 평균인 이유: 청구서는 쓴 양을 모두 더한 값이고, 합은 평균 × 횟수다. 요청 셋이 1 · 1 · 100 MB 면 중앙값(1)으로는 3 MB, 실제 합은 102 MB 다. 가끔 크게 튀는 요청이 있는 지표(LLM 토큰 · 응답 크기)일수록 중앙값은 비용을 적게 잡는다.

## 범주

| `category` | 지표 | scale | 단가 단위 |
| --- | --- | --- | --- |
| `network` | 응답 bytes | `1e-9` (bytes → GB) | 통화/GB (CDN · 클라우드 egress) |
| `server` | 요청당 CPU 초 | `1 / 3600` (초 → vCPU 시간) | 통화/vCPU 시간 (인스턴스 시간 단가 ÷ vCPU 수) |
| `server` | 요청당 DB 쿼리 시간(ms) | `1 / 3600000` (ms → 시간) | 통화/DB 시간 (DB 인스턴스 시간 단가) |
| `external_api` | 요청당 입력 · 출력 토큰 | `1e-6` (토큰 → 백만 토큰) | 통화/백만 토큰. 입력과 출력 단가가 다르면 항목을 나눈다 |
| `external_api` | 요청당 STT 초 | `1 / 60` (초 → 분) | 통화/분 |
| `device` | 화면 한 번에 받는 bytes | `1e-9` | 사용자 데이터 요금 통화/GB — 근거가 있을 때만 |

- 서버 자원은 인스턴스 하나가 버티는 처리량으로 인스턴스 수가 정해지는 구조라 CPU 시간 비례 환산은 어림값이다. 보고에 어림값이라고 적는다
- 고정 요금(월 정액 · 예약 인스턴스)은 사용량이 줄어도 바로 줄지 않는다. 그럴 때는 비용 대신 "여유 용량" 으로 해석한다

## 출처 규칙

- **단가**: 공급자 요금표 주소와 확인 날짜, 또는 사용자가 준 청구서 값. 기억으로 적지 않는다. 예시 단가를 쓰면 `price_source` 에 `(예시 단가)` 를 붙인다
- **양**: 운영 로그 · 분석 대시보드 · 청구서에서 읽은 값. 없으면 사용자에게 묻고, 사용자도 모르면 가정한 식을 적고 `(가정)` 을 붙인다
- 둘 다 없으면 비용 항목을 만들지 않는다. 효율 지표의 변화율만 보고한다

## 기기 부담 — 예산으로 본다

프레임 드랍 · 발열 · CPU · 메모리 · 배터리는 돈으로 바꿀 근거가 없다. 지표로 재고 `budgets` 의 상한과 대조한다.
상한은 프로젝트가 정한다. 아래는 출발점이고, 쓰기 전에 사용자에게 확인받는다.

| 지표 | 단위 | 출발점 | 근거 |
| --- | --- | --- | --- |
| 프레임 예산 초과 비율 | % | ≤ 1 | 60Hz 는 16.7ms, 120Hz 는 8.3ms 가 한 프레임 시간이다. 기기 주사율로 기준을 정한다 |
| 멈춘 프레임 수 | 개 | 0 | Android 는 700ms 넘는 프레임을 멈춘 프레임(frozen frame)으로 본다 |
| 발열 단계 | 단계 | ≤ 1 | Android 열 상태 0~6 중 3 `SEVERE` 를 공식 문서가 "UX is largely impacted" 로 적는다 (source.android.com 열 완화 문서). iOS 는 `nominal` · `fair` · `serious` · `critical` 순서로 0~3 을 매겨 쓴다 |
| 앱 CPU 평균 | % | 프로젝트가 정함 | 같은 시나리오에서 A 대비 악화가 없는지가 먼저다 |
| 최대 메모리 | MB | 프로젝트가 정함 | 기기마다 여유가 달라 지원하는 가장 낮은 사양 기기로 정한다 |
| 시나리오당 배터리 | mAh 또는 % | 프로젝트가 정함 | 실기기에서만 잰다. 시뮬레이터 값은 쓰지 않는다 |

예산은 기본으로 중앙값과 대조한다. 한 번이라도 넘으면 안 되는 예산(멈춘 프레임 0 개 같은)은 `"stat": "worst"` 를 적는다 — 상한이면 가장 큰 값, 하한이면 가장 작은 값과 대조한다. 5 회 중 0 · 0 · 0 · 2 · 3 개 멈췄다면 중앙값은 0 이라 지키는 것으로 보이지만 최악값 3 은 넘는다.

예산은 B 만이 아니라 A 도 대조한다. A 가 이미 넘던 예산을 B 가 지키면 개선이고, A 가 지키던 예산을 B 가 넘으면 회귀다.
