# Perf Compare

## Gotchas

- **결정값은 표시해야 결정값이다** — 전송 bytes · 쿼리 수처럼 매번 같은 값이 나오는 지표는 `"deterministic": true` 를 적는다. 표시가 없으면 측정 시간이 우연히 같게 나온 것과 구별할 수 없어 스크립트가 검정하고, 2:2 는 `표본 부족` 이 된다 (E3 — 표시한 지표의 값이 흔들리면 검사가 막는다)
- **3:3 표본은 아무리 갈려도 유의하지 않다** — 양측 Mann-Whitney 에서 3:3 의 가장 작은 p 는 0.1 이다. 4:4 는 0.029, 5:5 는 0.008 이다. 예열을 뺀 뒤 쪽마다 5 개 이상 잰다. 2026-11-08 TC-056 은 랜딩 프리로드를 3:3 으로 재서 -23.9% 를 냈지만 이 표본으로는 우연과 가를 수 없다 (E3 — 스크립트가 `표본 부족` 으로 판정한다)
- **변화율만 보고 개선이라 하지 않는다** — 판정은 스크립트가 p 와 최소 효과(`min_effect_pct`, 기본 5%)로 낸다. 응답이나 보고에 `개선` 을 쓰려면 그 지표의 스크립트 판정이 `개선` 이어야 한다 (E2 — 5 완료 전 대조 항목)
- **대조 지표 없는 비교는 환경 흔들림을 못 본다** — 바꾼 변수와 관계없는 구간(앱 `main()` 까지 시간, 정적 파일 응답 시간)을 같이 잰다. 대조 지표가 `개선` · `악화` 로 나오면 비교가 무효다. 시뮬레이터 · 로컬 서버는 맥의 다른 작업에 따라 흔들린다 (E3 — 스크립트가 무효로 판정한다)
- **빨라졌는데 결과가 달라졌으면 최적화가 아니다** — 응답 · 화면 결과가 옛 버전과 같은지 `equivalence` 에 남긴다. 의도한 차이(뺀 필드)는 무엇이 다른지 `seen` 에 적는다 (E3 — `same: false` 면 무효)
- **한쪽씩 몰아 재면 시간 변화가 섞이고, 같은 순서로 번갈아 재면 주기적 간섭이 한쪽에 겹친다** — 라운드마다 A · B 순서를 섞어 잰다(`randomized`). 서버 두 벌을 함께 띄울 수 있으면 동시에 돌린다(`duet`). 서버 재배포처럼 바꾸기 비싸면 A → B → A 로 재서 첫 A 와 마지막 A 가 같은지 본다 (E2 — 스크립트가 `interleaved` · `blocked` 에 `주의:` 를 남긴다)
- **예열 1 회가 정상 상태를 보장하지 않는다** — 예열 뒤 표본이 한 방향으로 계속 움직이면 아직 데워지는 중이다. 예열을 늘려 다시 잰다 (E2 — 스크립트가 4 개 이상 한 방향이면 `주의:` 를 남긴다)
- **단가를 지어내지 않는다** — 비용 항목마다 단가 출처(요금표 주소와 확인 날짜, 또는 사용자가 준 값)와 양 출처(로그 · 대시보드 · 가정)를 적는다. 가정이면 `(가정)` 을 붙인다. 출처가 없으면 비용 칸을 빼고 사용자에게 묻는다 (E3 — 출처 키가 없으면 검사가 막는다)
- **기기 부담은 돈으로 바꾸지 않고 예산으로 본다** — 프레임 드랍 · 발열 · CPU · 메모리 · 배터리는 `budgets` 의 상한과 대조한다. 사용자 데이터 요금처럼 돈으로 바꿀 근거가 있을 때만 `cost` 의 `device` 분류에 넣는다 (E1)
- **디버그 빌드 수치는 같은 빌드끼리 서버 쪽 차이에만 쓴다** — 프레임 · CPU · 메모리 · 앱 자체 시작 시간은 릴리스나 프로파일 빌드에서 잰다. 디버그 빌드는 JIT 와 검사 코드가 섞여 앱 쪽 절대값을 믿을 수 없다 (E1)

## 하는 일

두 버전을 같은 조건에서 반복 측정해 `perf.json` 하나에 모으고, `scripts/perf_compare.py` 가 지표마다 판정(개선 · 악화 · 차이 미미 · 차이 없음 · 표본 부족), 월 비용, 예산 지킴 여부를 계산해 `perf-report.html` 을 만든다.
대조 지표가 움직이거나 결과가 달라지면 비교 전체를 무효로 표시한다.

측정 범위는 네 가지다.

| 범위 | 예 | 결과 자리 |
| --- | --- | --- |
| 속도 | 시작 시간, API 응답 시간, 동시 호출 소요 | `metrics` |
| 효율 | 화면 한 번에 받는 bytes, 요청당 쿼리 수, 요청당 CPU 시간 | `metrics` |
| 비용 | 네트워크 전송, 서버 자원, 외부 API(LLM 토큰 · STT 분) | `cost` |
| 기기 부담 | 프레임 드랍률, 발열 단계, CPU %, 메모리, 배터리, 사용자 데이터 | `metrics` + `budgets` |

## Input

`$ARGUMENTS`: 비교할 두 버전이나 바꾼 것 (선택). 없으면 이번 대화에서 바꾼 것을 대상으로 삼고, A · B 가 무엇인지 한 문장으로 되묻는다.

## Process

### 1. 스택 감지와 비교 설계

- 아래 표로 스택을 정하고 해당 문서만 읽는다. 둘 이상 해당하면 모두 읽는다 — 앱만 바꿨어도 대조 지표는 `server.md` 에서 고를 수 있다

| 감지 | 읽을 문서 |
| --- | --- |
| 비교 대상이 HTTP API · 서버 구간 | `references/stacks/server.md` |
| `pubspec.yaml` 에 `flutter:` | `references/stacks/flutter.md` — 문서의 환경 다섯 줄을 측정 전에 응답에 남긴다 |
| `Cargo.toml` | `references/stacks/rust.md` |
| `package.json` 에 화면 라이브러리 · `vite`, 또는 `src-tauri/` | `references/stacks/web.md` |
| 처리량 · 동시 접속 · p95 · p99 를 비교 | `references/stacks/load.md` |
| 해당 없음 | 사용자에게 무엇으로 잴지 묻는다. 새 스택 문서가 필요하면 보고에 적는다 |

- `references/experiment-design.md` 를 읽고 설계한다
- 아래 표를 채워 한 번 보여 주고 확인받는다. 확인 전에는 측정하지 않는다

```text
| 항목 | 값 |
|---|---|
| 질문 | {바꾼 것} 이 {지표} 를 줄이는가 |
| A / B | {옛 버전 이름 · 커밋} / {새 버전 이름 · 커밋} |
| 고정한 조건 | {빌드 · 계정 · 데이터 · 기기 · 네트워크} |
| 목표 지표 | {이름 · 단위 · 낮을수록 좋음/높을수록 좋음 · 측정 방법} |
| 대조 지표 | {바꾼 변수와 관계없는 구간} |
| 결과 동일성 | {무엇을 무엇과 비교하나} |
| 반복 | 예열 {N}회 + 쪽마다 {N}회, 순서 {randomized · duet · A→B→A} |
| 비용 · 예산 | {범주 · 단가 출처 · 양 출처} / {상한과 이유} |
```

완료 기준: 사용자가 표를 확인했다는 응답이 대화에 있다.

### 2. 측정 도구 확인 — 알려진 답 대조

- 측정 방법은 1 에서 읽은 스택 문서에서 고르고, 그 문서의 함정을 측정 전에 한 번 읽는다
- 스택 문서가 "첫 회에 확인" 이라고 적은 출력 형식(JSON 키 · 로그 줄 · 파일 위치)은 첫 회 원문을 보고 맞춘다 — 도구 판이 바뀌면 형식이 바뀐다
- 이번에 새로 짠 측정 명령(로그 파싱 · bytes 합산 · CPU 시간 차)은 본 측정 전에 손으로 답을 셀 수 있는 작은 입력으로 돌려 기대값 · 실제값 · 명령을 남긴다. 둘이 다르면 고친 뒤 넘어간다
- 측정이 0 이나 빈 값을 내면(프레임 0 개, 로그 줄 0 개) 그 지표는 측정 실패다. 측정 경로를 바꾸거나 지표를 빼고 보고에 적는다 — 0 을 "문제 없음" 으로 읽지 않는다

완료 기준: 새 측정 명령마다 기대값 · 실제값 · 명령 세 줄이 응답에 있다.

### 3. 측정

- 처음 꾸린 측정 환경이면 A 대 A 를 먼저 한 번 잰다 (`experiment-design.md` §A/A 예비 측정)
- 1 에서 정한 순서대로 잰다. 원시 표본을 그때그때 파일에 남긴다 — 중앙값만 적어 두면 다시 판정할 수 없다
- 예열 표본도 `a` · `b` 목록 앞에 그대로 두고 `warmup` 에 개수를 적는다
- A 와 B 를 바꿀 때마다 무엇을 바꿨는지(배포한 WAR, 바꾼 플래그) 한 줄씩 남긴다
- 결과 동일성은 같은 입력에 대한 두 버전의 출력을 비교 명령(`diff`, `jq` 정렬 뒤 비교)으로 확인한다

완료 기준: 지표마다 쪽별 원시 표본이 예열 + 5 개 이상이다 (결정값 지표는 2 개 이상이고 기록에 `"deterministic": true` 를 적는다).

### 4. 기록과 판정

- `references/samples-format.md` 형식으로 `perf.json` 을 쓴다. 비용 · 예산은 `references/cost-model.md` 를 따른다
- 결과 폴더는 앱 저장소면 `.mcp_screenshots/test-evidence/{케이스 폴더}/`(시나리오 보고서와 같은 폴더), 아니면 `perf-evidence/{PERF-번호}-{영문 요약}/` 이다. git 에서 빠져 있는지 `git check-ignore` 로 확인한다

`{스킬 폴더}` 는 이 스킬을 불렀을 때 알려 주는 스킬 기본 폴더다.

```bash
python3 "{스킬 폴더}/scripts/perf_compare.py" check "{결과 폴더}/perf.json"
python3 "{스킬 폴더}/scripts/perf_compare.py" report "{결과 폴더}/perf.json"
```

- `check` 가 종료 코드 0 으로 끝날 때까지 오류 줄이 가리키는 필드를 고친다. 통과 전에는 `report` 를 돌리지 않는다
- `report` 가 같은 폴더에 `perf-report.html` 을 쓰고 `판정:` · `주의:` · `지표:` · `비용:` · `예산:` 줄을 찍는다
- 보고서를 연다 (macOS 는 `open "{결과 폴더}/perf-report.html"`)

완료 기준: `report` 가 `보고서:` 줄을 찍고 종료 코드 0 으로 끝난다.

### 5. 완료 전 대조

완료를 말하기 전에 아래를 하나씩 확인하고 결과를 응답에 남긴다.

- [ ] `check` 종료 코드 0
- [ ] 2 의 알려진 답 대조를 새 측정 명령마다 남겼다
- [ ] 응답에 쓴 `개선` · `악화` 가 `report` 출력의 `지표:` 줄 판정과 같다 — `표본 부족` 지표를 개선이라 부르지 않았다
- [ ] `판정: 무효` 면 결론 대신 무효 사유와 다시 잴 조건을 보고했다
- [ ] 비용 항목마다 단가 · 양 출처가 있고, 가정은 `(가정)` 이 붙어 있다
- [ ] 측정 실패로 뺀 지표를 보고에 적었다
- [ ] 위 Gotchas 를 한 줄씩 다시 읽고 어긴 것이 없다

보고는 아래 네 줄로 시작한다.

```text
보고서: {결과 폴더}/perf-report.html
판정: {유효 | 무효 — 사유}
지표: {개선 N · 악화 N · 차이 미미 N · 차이 없음 N · 표본 부족 N}
비용: {합계 A → B 통화/월 (차이)} (비용 항목이 없으면 "없음")
```

## 표본 부족 · 무효가 나온 뒤

- 표본 부족: 그 지표만 쪽마다 5 개 이상으로 다시 잰다. 앞 표본과 섞지 않고 새 측정으로 바꾼다 — 조건이 같다는 보장이 없다
- 무효(대조 지표 움직임): 맥 · 기기의 다른 작업을 멈추고 순서를 번갈아 재기로 바꿔 전부 다시 잰다
- 무효(결과 다름): 성능 비교를 멈추고 결과가 달라진 원인을 먼저 고친다. 고치는 일은 이 스킬 밖에서 한다
